      About diagnostics and privacy

      Complete disclosure for this launcher and its distributed player diagnostics module. Open the sections below for the collection paths, data categories, payload fields and limits. This information is available offline; opening it does not turn on diagnostics.
      

      Your choices and turning them off

      Launcher diagnostics and Game diagnostics are separate, optional choices, both off by default. Client patches are a separate gameplay preference, not permission to upload diagnostics. Local launcher, game and patch logs can exist with uploads off. Normal login, downloads, updates and game-server operational records are independent of these switches.
      

      Launcher diagnostics enables small setup/Play attempt summaries. Game diagnostics enables detailed launcher events, including adoption before Play, a module loaded into the game on Play, live game logs and an automatic session log ZIP. Upload debug logs is a separate explicit upload when pressed, even with both choices off; it can include earlier sessions.
      

      Turning a choice off closes that launcher's future send gate and clears its unsent queue; requests already in flight may finish. It does not recall received data, erase local logs or remove retained install identity. An already loaded game module has its own uploader and session token: exit the running game to stop it. The checkbox changes module injection for the next Play.
      

      Launcher summaries, local logs and detailed events

      Launcher diagnostics summaries: random event/attempt IDs; install, compatibility preparation, repair, uninstall and launch operation; ending phase/outcome; fixed failure code; total and starting/running/download/extraction durations; retries; normalized launcher version, OS/architecture; overflow/expiry/rejection totals. This schema has no adoption or update summary variant. It contains no arbitrary text, name, path, chat, URL, cookie, token or persistent install/machine ID. This limited payload description does not apply to Game diagnostics or log uploads. Receiving services still see connection metadata.
      

      Local launcher logs: times, severity, target, messages and fields for launcher information/warnings/errors and other warnings/errors. Startup/build/configuration, catalog/download/archive/install/repair/update/uninstall, compatibility/PhysX, UI/settings/login/adoption, resource/helper/launch/patch outcomes, timing and panic/error text. Recognized home/username segments are replaced before writing; other paths or sensitive free text may remain. Daily rotation keeps seven files, not a strict seven-calendar-day lifetime or size limit.
      

      Detailed events, with Game diagnostics: startup, crash, launcher update, game update, install, repair, launch, settings, telemetry, UI, login and adoption target families, at information level and above. Timestamps/sequences, operation/phase IDs, start/finish/outcome, timings, retry/HTTP/error/failure codes, file/byte/scan/missing/changed/unsafe totals, bounded relative file names and expected/actual hashes, content manifest hash, overlay IDs, patch IDs/verdicts/reasons, build/version/fingerprint, injection/process/exit metadata and upload/patch counters. Raw panic text stays local; forwarded panic uses coarse location/thread classes. Install/patch results can wait for the next opted-in session.
      

      Adoption/integrity checks read entries, file identities/attributes/sizes and bytes/hashes inside the selected install tree, including extra/mod files needed for safety checks. Selected archives are read for verification/extraction. Relative names can contain personal text. This is not an upload of every game/archive file's contents.
      

      Forwarding replaces recognized home/user segments, absolute paths and IP literals, limits strings, and restricts targets/scalars at the receiver. Pattern matching is imperfect; relative names and unrecognized values may remain.
      

      Game module: every collection family

      Game diagnostics are not anonymous. They include a persistent random install ID, a machine ID derived from the computer name, session/build/process identifiers, detailed launcher/adoption events, game events and log text. The server can associate them with your character and game activity. Emission depends on supported executable fingerprints, platform/Wine behavior, active hooks, capture settings, sampling and dropped events.
      

        

      • Boot/session/hooks: session/install/machine IDs; launcher/module version, branch, revision, tags/flavor; game/helper process IDs, start/exit times/codes; EXE/module paths; hook availability, code fingerprints, expected/observed instruction bytes, in-process addresses, import/vtable/protection and hook-install results.
        • 

      • Engine/UI/Lua logs: BigWorld messages/unknown entities, UE3 category/text/assert/fatal errors, log4cxx logger/source-file/line/text, debug output, CEGUI messages, Lua call/error/status/source/line and Debug log/warn/error text, including game-produced stack traces.
        • 

      • Performance/resources: frame ticks/counts/percentiles, hitches/phase age; process working/private/peak memory and free virtual memory; map/package/object/class names, loading/streaming/async archive times/failures; repeated-event rollups, queue/drop/upload/failure counts.
        • 

      • World/entities/sequences: entity IDs/types, creation/entry/exit/destruction, appearance scheduling, world/cache/deferred membership/queue counts, delivered/dropped/replayed messages, state flags, event names/catalog, animation/notify, sequence IDs/times/drop reasons, actor names/classes/positions, cinematics start/stop/input flags and timeline position/length.
        • 

      • Abilities/combat/UI: press source/route, send/drop reasons, supported outbound arguments, decoded incoming abilities/effects/sequences/cooldowns/stats/known abilities/feedback, target/cast IDs, applied UI results/timing joins. The ability decoder excludes ordinary chat channels; other logs do not.
        • 

      • Navigation/input/game camera: controller mode/button bits, mouse edges/held times, drag offsets/input axes, hover/selection/UI ownership; pawn position/orientation/movement/attachment changes; virtual camera/pawn pose, zoom, yaw/pitch offsets/flags at interactions/use-item/sequence joins. The console hook reports invocation without decoding the command; other logs can contain command text.
        • 

      • Protocol/network: outgoing method/route/message/entity IDs; incoming method/property IDs/lengths; receive flags, acknowledgements, sequences, windows/gaps/fragments, packet/bundle parsing, socket/errors, datagram lengths/fingerprints, bounded raw fault-byte samples (up to 24 bytes at a failing message). Game socket events include the remote IPv4 peer address and port. The socket hook observes the game's process-wide import, not all computer traffic.
        • 

      • Cooked cache/file calls: PAK/category/entry names, versions read/set/held, metadata extraction/stream/CRT results, file-open paths/errors/access/disposition/existence, cache writes/resync. Game-opened paths can be outside the install root; this is not an upload of every opened file's contents.
        • 

      • Graphics/media/physics: D3D9 adapter index, resolution/format/windowed/buffers/multisampling/interval/refresh, results/device-loss/reset timing; movie names/open/close/ticks, sound-event names/start/stop/results; PhysX codes/messages/source-file/line/asserts. Metadata/events, not recorded audio/video.
        • 

      • OS/exceptions: thread stack size/flags, loaded library names/paths, sampled foreground-window-query occurrence (not other windows' titles), exception codes/addresses/module/relative address/thread/access-kind/target/flags. An exception is not proof of a fatal crash. Error traces and bounded in-process code/stack observations are not a full-machine memory dump.
        • 

      

      Free-form logs and open event fields can include account/character/NPC names, chat, inventory/trade/mission data, commands, locations, paths, addresses and other sensitive values produced by the game, mods or components. These categories are not a finite allowlist of possible text/field values. Truncation does not anonymize them. Developer capture/firehose/raw/unfilter settings can broaden capture or change game logging thresholds.
      

      Which log files are read and uploaded

      Automatic live logs: newly completed lines in game-binaries SGWDebugLog* files and recursively in sessions/*.log and sessions/*.txt. Existing files start at their end; new session files start at the beginning. Source-file label, timestamp/sequence, severity/category, optional packet number and unfiltered text. Live streaming has no special exclusion for *-keys.txt: do not put secrets in this folder.
      

      Automatic exit ZIP: selected top-level SGWDebugLog* and recursive session .log files modified since session start, with relative names/timestamps. Whole selected file bytes, including earlier lines, not only the streamed tail. Raw logs are sent without the manual-upload line scrubber, with session/install/machine IDs, launcher version, session start/end, event/drop totals and ZIP hash/size. The server expands/replays bounded lines.
      

      Upload debug logs: existing launcher.*.log and selected-game SGWDebugLog* plus recursive sessions/*.log, up to 20,000 launcher and 20,000 game records per press. Time, file label/relative name, physical line, severity/target, message, upload ID, launcher version/OS and truncation. Saved byte offsets usually send new complete records on subsequent presses; rewritten/truncated logs can start again. Messages are capped at 2,048 bytes after scrubbing. Closing the launcher cancels at a chunk boundary; received chunks remain received.
      

      Session-file selection for manual uploads and ZIPs excludes session JSON, .txt key files and .dmp by selecting .log only; this does not apply to live tail. Top-level SGWDebugLog* selection is by prefix. Manual lines use pattern-based home/path/address/long-token scrubbing; ordinary chat/names remain. No guarantee removes every personal value, credential or secret. Module events, live logs and raw ZIPs do not share that manual scrubber.
      

      Identity, destinations and normal server records

      Install identity is a random UUID created on first game opt-in and retained after opt-out. Machine ID is the first 16 hexadecimal characters of SHA256(computer name): the hostname is read locally; its hash is persistent and potentially guessable, not random. Manual upload reuses stored identity or a temporary unsaved identity if none exists.
      

      Session creation sends install/machine IDs, branch, revision, launcher version, tags, optional session kind/upload purpose. The shared protocol supports optional account name; this desktop mint currently does not send it. Server correlation by machine/address/world entry can still link telemetry to characters and enrich entity IDs with names/items/abilities. Local current-session.json contains identity, bearer token, expiry, endpoint and batching settings for the module. Tokens authenticate requests; arbitrary log text is not guaranteed secret-free.
      

      At launcher startup, summaries use the first effective login server only when it is HTTPS; later entries are not searched. Summaries are sent over https. No fallback is currently configured, so if the first server is HTTP, a later HTTPS entry does not enable sending. Changes to the server list apply on the next launcher start (loopback HTTP fixtures are a development exception). Game diagnostics/manual logs use the login server's session service and minted telemetry endpoint. Native policy permits HTTPS, or HTTP to loopback or the exact configured HTTP login-server host/port. These transports are not unconditionally HTTPS-only.
      

      Receiving servers, proxies/CDNs and hosting infrastructure see connection addresses/metadata independently of redaction. The server uses addresses for admission/quotas/correlation; current ingest rows omit the receiving HTTP caller's connection address. Addresses inside game events or log text, including the remote game socket peer, can still be recorded. Server logging can forward events through OpenTelemetry to SigNoz and other configured sinks. The launcher does not control infrastructure access logs.
      

      Normal game-server logging is independent of optional diagnostics: movement/combat, missions/inventory, connection/session and other operational records. An explicit .bug note records free text, caller/selected target, mission/region, nearby named entities and ability-state context. Login/content/update downloads contact their services regardless of these toggles.
      

      Local reads, storage, limits and retention

      Local state includes settings/consent/install paths and install/operation records, diagnostics identity, current-session token/configuration, logs, queues, manual-upload offsets/file fingerprints. Normal setup reads selected archives/install files, its own resources/cache/state, home/user environment for identity/redaction, applicable game-created Documents/My Games/Firesky state, process/module information and the AGEIA registry for PhysX. Reads are not all confined to the install directory.
      

        

      • Summary queue: launcher-summaries.json, at most 64 entries, 24-hour expiry, batches up to 32; opting in discards old queue.
        • 

      • Launcher forwarding: 512-record memory channel, batches up to 64, no disk retry queue; default receiver 300 records/launcher session and 3,000/minute globally, configurable.
        • 

      • Game backlog: plain JSONL queue/inflight files, 100 MiB drop-oldest cap, survives restart while opted in and can upload with a later token; retries can duplicate rows. No general age expiry. Opt-out discards unsent entries; deletion can fail.
        • 

      • Module: 4,096-entry memory ring/retry batch, sampling/rate budgets/repeat rollups/overflow loss and bounded exit flush. Local cimmeria-client-telemetry.log beside SGW.exe is rewritten each launch, up to 2,000 boot/diagnostic lines, plus debug output. Game/patch logs have separate retention from the launcher's seven daily files.
        • 

      • Manual upload: uploaded-log-offsets.json keeps offsets and game-file head/tail fingerprints for up to 2,048 files. At most 40,000 records/400 chunks per press, paced at least 3.5 seconds apart. Upload does not delete local logs.
        • 

      • Receiver defaults: manual logs 40,000 kept/session, 80,000/install/day, 400,000 received/address/day, 40,000 received/minute globally; events 30,000/minute/session plus 3,000 priority. Bundle 32 MiB, expanded 64 MiB, up to 1,024 replayed entries/250,000 lines with another ZIP-entry safety guard. Configurable limits can drop data.
        • 

      

      Remote retention, backups, access and other sinks are configured by the server operator. Guidance proposes 30-day logs, 14-day traces and 90-day metrics; these are not a verified live retention guarantee. Neither toggle deletes received records or controls server retention. Game/mod logs may outlive launcher logs.
      

      What these diagnostics do not do

        

      • No webcam or microphone recording, screenshot/video feed or captured game audio. Camera telemetry is the virtual game camera; sound telemetry is game sound events.
        • 

      • No browser-history, clipboard, password-manager or personal-document crawler, and no system-wide keyboard listener/keystroke transcript. Game input/file calls/arbitrary logs are still observed as listed. This describes collector scope, not a sandbox around the original game, mods or external software.
        • 

      • No upload of all game assets or every file the game opens merely for diagnostics. Selected logs, bounded protocol/code samples, hashes and metadata are included.
        • 

      • No lab remote-control bridge in the distributed player module. Lab-only memory read/write commands, Lua evaluation, native-call/injected-input controls and lab crash-dump capture are excluded by player build/release checks. Player exception records are not full-machine memory dumps.
        • 

      • No claim that rich telemetry is anonymous, has no chat/paths/keys, reads nothing outside the game directory, always uses encrypted HTTPS or instantly stops a running module when unchecked. Original game logs/crash handling and separate lab builds have different capabilities.
        • 

      

      Launcher sign-in and linked accounts

      When you sign in, the launcher keeps a refresh token, your account name and display name in your operating system's credential store (Windows Credential Manager or the macOS Keychain), never in launcher files or logs. Sign-in requests go only to the first login server's HTTPS address. Those requests carry the one-time sign-in code, the stored refresh token (to refresh and to sign out) and, while the game runs, a launch id; they never carry an email address. While the game runs, the launcher also writes your account name and a one-time launch ticket into the game's LoginInternal.lua file in your install folder; it is overwritten with the plain server list when the game exits.
      

      The server stores which provider you used, that provider's account id, a display name, and, only for providers the server operator marks as verifying email, your verified email address, used to match accounts with the same email. Linking with a password sends it once over HTTPS and removes it from the account. Signing out deletes the stored token; no token, password or code goes to diagnostics, only event names and error codes.
      

      Exact fixed payload field names

      Schema keys, not your current values. Optional fields may be absent. Open message/fields bags are described above; free-text values are not limited to this list. Event type is client_log, debug_log, client_native or session_meta. Session meta kinds cover started, file rotation, dropped windows and game exit, with counts/reasons/file labels or process/exit details.
      


      Stored launcher sign-in: refresh_token, account_name, display_name.
      

      Summary request: schema_version, client_dropped, summaries.
      

      Summary record: event_id, attempt_id, operation, phase, outcome, error_code, duration_ms, retry_count, phases, launcher_version, os, arch.
      

      Summary drop counts: overflow, expired, rejected.
      

      Summary phase duration: phase, duration_ms.
      

      Desktop session creation: install_id, machine_id, branch, git_sha, launcher_version, tags, session_kind, purpose.
      

      Shared session creation protocol: install_id, machine_id, branch, git_sha, launcher_version, tags, account_name.
      

      Exit ZIP metadata: session_id, install_id, machine_id, launcher_version, session_started_at_ms, session_ended_at_ms, event_count, dropped_lines, zip_sha256, zip_bytes.
      

      Game log event: ts_ms, seq, source_file, level, category, packet_no, message.
      

      Debug log event: ts_ms, seq, source_file, level, message.
      

      Native launcher/game event: ts_ms, seq, target, level, fields.
      

      Session lifecycle event: ts_ms, seq, kind, fields.
      

      Manual log event fields: message, log_level, log_target, file, line_no, upload_id, truncated, launcher_version, os. Transport includes session ID, bearer authorization, content/compression metadata and chunk/sequence information; the module also supplies process ID/send-clock headers. Session replies store session_id, token, expires_at_ms, upload_endpoint, chunk_max_bytes and flush_interval_ms locally.
      

      The shared wire model retains a legacy key_dump variant (ts_ms, seq, source_file, key_b64), not a current ordinary player collector. This is not an exclusion for key-like text streamed as ordinary log lines.

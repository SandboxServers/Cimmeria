# DW-20B-E patrol and authoring source findings (2026-10-16)

- `crates/cell-console/src/cell/console/patrol.rs::{path_add,path_show,path_clear,path_assign}` uses `SpaceManager.patrol_authoring[path_id]`, shared by GMs in one cell process; only `seed.rs::record` queues SQL per caller. That split lets GM A queue a parent point-set header, GM B queue only a child point on the shared nonempty buffer, and A cancel, leaving B's confirm to fail the FK. A preexisting same-ID wrong-world header can also accept a child because the header uses `ON CONFLICT DO NOTHING` without a world check. `.seedcancel` does not revert the shared path buffer or an already applied entity edit. See `docs/analysis/dev-workbench/evidence/DW-20B-E.md`.
- `seed.rs::confirm` sends `ExecuteAuthoringSql` and reports the send before base SQL completes. `crates/base-session/src/base/console_authoring/mod.rs::handle_execute_authoring_sql` later distinguishes positive rows, zero rows, failure and absent DB. Neither stage edits `db/resources/` seed files; a developer must merge emitted SQL.
- `crates/cell-console/src/cell/console/entity.rs::look_at` calls `placement.rs::settle_npc` for every non-player spawnable, including a prop or pet; when autosave is enabled, that calls `.savespawn`, which may refuse or queue placement SQL. The other entity-authoring handlers do not queue authoring SQL. `entity.rs::set_visible(true)` only acknowledges a future AoI refresh; it does not set a visibility field or send a show message.
- `entity.rs::set_name` writes `npc_name` even on player targets, but `crates/cell-world/src/cell/space_manager/lab_snapshots.rs::{snapshot_entity,live_entity_name}` prefers `character_name`, so `server_entity_get.name`/`entity_name` cannot verify a player rename attempt. NPC snapshot readback can show the changed `npc_name`.
- `patrol.rs::{waypoint_set,path_set_tp,path_clear_tp,path_set_tp_delay}` queues SQL with `ORDER BY point_id OFFSET index`; the row is chosen at later `.seedconfirm`, so an intervening insert/delete can retarget it. The three `waypoint_set` commands all use `path_seq` as the base feedback label. `path_clear` queues child and parent DELETEs separately, without one transaction; one can succeed while the other fails. The DW-20B typed palette must pin `point_id` server-side for waypoint edits and report both clear results, or leave the actions disabled.

# Ring map click routing in the QA lab client (2026-10-13)

Live Cellblock probe on a fresh character: the server sent `onRingTransporterList` for source region 1 and destination region 2, and the map rendered the destination. `client_input_mouse` placed the CEGUI cursor and clicked the marker, but sent no `setRingTransporterDestination`. The same tool closed the map through its X button. A temporary click-event probe showed the map click on `WorldMapImageWin`, while the stock `WorldMap.lua` subscribes `WorldMapMod.onClick` on `WorldMapWin`; the parent saw no click in this lab session. Invoking `WorldMapMod.onClick` directly at the image pixel selected the destination.

Binding `WorldMapImageWin.EventMouseClick` to the existing `WorldMapMod.onClick` once through Lua, then using `client_input_mouse`, produced inbound method 91 `setRingTransporterDestination(1,2)`. The transport and mission step completed after pad entry. The lab helper instead tries real input first, then invokes the stock handler at the same pixel only if the map stays open; it reports that fallback as N3. This establishes a lab-session event-route workaround; it does not contradict the owner's report that manual clicks work in the normal client. Issue: #1686. Source: live packet tap, CEGUI probe, `SGWGame/Content/UI/Core/WorldMap/WorldMap.lua` in the QA client.

LR-00 grading rule: `client_world_map_click.native_pass` requires a successfully delivered left click, native cursor placement, no Lua handler fallback and a closed map. Lua cursor placement is N3 even when the posted click closes the map; an open map is `effect_ok: false` and never passes. For a UAT claim that the destination was selected, require a packet-tap clause for inbound method 91; map closure alone does not prove that server request.

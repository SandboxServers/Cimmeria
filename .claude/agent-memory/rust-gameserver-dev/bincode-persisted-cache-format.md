Anything in this repo that bincode-encodes to **disk** must pin
`bincode::config::legacy()`, not `config::standard()`.

**Why:** bincode 1.x's free `serialize`/`deserialize` used fixed-width
little-endian ints. bincode 2's `standard()` varint-encodes them. `legacy()` is
bincode 2's reproduction of the 1.x defaults. Verified empirically during the
2.0.1 bump (PR #591): a crate pinned to `bincode = "=1.3.3"` emitted a fixture
that `legacy()` decodes byte-identically and re-encodes byte-identically.

**How to apply:** The trap is that a config mismatch is **not** a loud error.
Decoding genuine 1.x bytes under `standard()` returned `Ok` after consuming
10 of 197 bytes and produced a garbage struct. Two consequences:

1. Always use `decode_from_slice` and assert `bytes_consumed == data.len()` in
   the test. That assertion is the only thing that catches the mismatch.
2. A save-then-load round-trip test **cannot** guard an on-disk format — it
   writes and reads with the same (wrong) config, so it passes either way. You
   need a byte fixture generated by the old version. Generate one with a
   throwaway crate in the scratchpad pinning the old bincode; copy the struct
   defs verbatim.

Fixture gotcha: `HashMap` iteration order is non-deterministic, so a byte-exact
fixture must use exactly **one** entry per map.

Known non-hardening: `legacy()` inherits 1.x's absence of a decode size limit,
so a cache corrupted into a bogus length prefix aborts on allocation rather
than returning `Err`. Truncation *does* error cleanly. Adding `with_limit`
would change behaviour and was deliberately left out of the dep bump.

Current site: `crates/upk-objects/src/package_index.rs` (`CACHE_CONFIG`) —
the only bincode user in the workspace. `package_index.bin` is gitignored,
never shipped, and only written by the `build-package-index` dev binary.

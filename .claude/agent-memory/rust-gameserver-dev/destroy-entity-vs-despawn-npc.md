`SpaceManager::destroy_entity` (`crates/services/src/cell/space_manager/entities.rs`) is a pure state-removal primitive: it drops the entity from `space.entities` and the spatial grid, but does **not** touch any other entity's `witnesses` set and sends no `LeftAoI`. The next AoI tick will *eventually* notice and clean up, but only for players the tick happens to visit, and only after up to a full tick of the client rendering a corpse that's already gone server-side. This is the same failure shape as the Castle Cellblock invisible-corpse bug (issue #582).

`SpaceManager::despawn_npc` (same file) is the correct primitive for any NPC removal that content or a GM command triggers and that observers need to see disappear immediately: it fans `LeftAoI` to every witness synchronously, scrubs the target out of every other entity's `witnesses` set in the same pass, then calls `destroy_entity`. It is NPC-only — refuses a player target structurally (`DespawnOutcome::RefusedPlayer`), independent of any caller-side check. Already used by the `.despawn` GM console command (`cell/console/spawn/`).

**Found 2026-09-17 (C08b, Castle Cellblock rebuild):** `content::executor::world::destroy_tagged_entity` (the `Action::DestroyTaggedEntity` arm, used by content chains via the `destroy_entity` seed verb) was calling the bare `destroy_entity`, not `despawn_npc` — meaning every content-authored NPC despawn (e.g. chain 1032's `ArmYourself_AmbernolVial`, and now chain 1161's Col Marsh despawn) had this exact latent gap. Fixed by switching to `despawn_npc`; the function became `async` and gained a `tx: &mpsc::Sender<CellToBaseMsg>` parameter as a result. Revert-verified: reverting the fix drops the witness-fanout test's assertion from `[(1,101),(2,101)]` to `[]` with zero panics (silent, not a crash — exactly the kind of regression a resolve-only chain-replay test cannot catch, per TESTING.md's `move_entity` warning).

**Follow-up audit (2026-09-18, same PR):** code review on C08b's PR correctly flagged that the fix above was narrower than its own "audit further call sites" framing. Grepped every `.destroy_entity(`/`.despawn_npc(` call site in `crates/services/src/cell/` and fixed the two more that matched the same bug shape (external NPC removal, observers may be watching):
- `cell_methods::gm::handle_despawn` (the `.despawn` GM console command) -- was calling the bare `destroy_entity` directly even though the `.despawn` GM command was cited in this very memory file as "the` despawn_npc`-using precedent" before this fix; it wasn't.
- `service::npc_ai::lifecycle::npc_ai_despawn` (scripted AI cleanup, e.g. "boss died, bodyguards retreat off-screen") -- its own doc comment claimed "fires AoI-left events to all witnesses," which was false until this fix.

The remaining bare `destroy_entity(` call sites (`gate_travel.rs`, `ring_transport/dispatch.rs`, `space_transfer/mod.rs`, `cell_methods/gm/travel.rs`, `cell_methods/player/combat/respawn.rs`, `content/executor/transport.rs`, `service/base_messages/lifecycle.rs`, `space_manager/entities.rs`'s own `disconnect_entity`) are all **player**-entity lifecycle transitions (cross-world teleport, gate travel, ring transport, GM `.goto`, respawn, disconnect) -- `despawn_npc` structurally refuses player targets (`DespawnOutcome::RefusedPlayer`), so it isn't the right primitive there regardless; those paths broadcast `LeftAoI` (or the transfer-specific equivalent) through their own dedicated logic before the bare destroy, the same pattern `disconnect_entity` uses internally. Not individually deep-audited line-by-line in this pass -- if one of them turns out to skip its own witness notification, that's a new, differently-shaped bug from this one (missing broadcast entirely vs. wrong destroy primitive), not this rule of thumb.

**Rule of thumb:** if a content chain, GM command, or scripted AI action destroys an **NPC** and observers (other players in AoI) might be watching, always reach for `despawn_npc`, never the bare `destroy_entity`. A **player** entity leaving a space is a different code path by construction (`despawn_npc` refuses it) -- those need their own explicit witness-notification audit if ever suspected, not this fix.

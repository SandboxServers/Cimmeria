# Organizations: Squads, Teams and Commands

> Type: how-to. Audience: the Claude Code coordinator, packet workers and the owner.
> Updated: 2026-09-27. Companions: [audit](audit.md), [work packets](work-packets.md), [session resume](handoffs/session-resume.md), [RE findings](../../reverse-engineering/findings/organization-restoration.md), [wire formats](../../reverse-engineering/findings/organization-wire-formats.md), [documentation index](../../readme.md).

## Purpose

This campaign restores the three organization types the client ships a full UI for:

- **Squad** (`EOrganizationType` 0): the ephemeral party of up to six;
- **Team** (1): a small persistent group;
- **Command** (2): the persistent guild, with the full rank and permission editor, a shared vault and a treasury.

The 2009 server never implemented any of it: every organization method in the legacy Python is `pass`, and the `SGWPlayerGroupAuthority` files are empty. This is greenfield server work against a known wire contract. The client needs no patch: every method is indexed in `docs/protocol/`, and the Organization, Team, Command, Squad and vault windows are wired in the shipped Lua.

It supersedes the six-phase plan in issue [#568](https://github.com/SandboxServers/Cimmeria/issues/568) and folds in the security acceptance criteria from the closed audit issue #472 ([CAT-M](../../security-audit/2026-05-31-server-authority/findings/CAT-M-org-squad-duel.md) M-01 to M-11, M-16 to M-18).

Out of scope:

- Organization experience. Nothing in the client or data says how an organization earns XP, so `onOrganizationExperienceUpdate` always sends 0.
- Alliances, the calendar, the history log, insignia, adjectives and recruiting descriptions. They have permission bits but no UI in either editor.
- Duels (CAT-M-12 to M-15). They share the audit category, not the system.
- **Vault storage and the treasury.** The Team and Command vaults (containers 19 and 20), the banker NPCs (interaction types 11 and 12) and cash transfer (CM 19 `organizationTransferCash`) belong to the **Bank / Vault campaign** (cimmeria-97), which also owns the personal bank (17). This campaign gives it a stable API instead: organization ids, membership, rank permissions, the `cash` column, the org fanout primitive and the CM 19 route ([work-packets.md § Bank campaign API](work-packets.md#bank-campaign-api-org-api)).

| ID | Status | Decision | Reason |

| D-ORG03 | PROPOSED (coordinator default) | **Squad state lives on the cell, service-wide** (one registry across all spaces), not per space. Squads are never persisted. | Squad members travel between worlds independently. #584's per-space `SquadManager` loses the squad on the first gate trip (audit A-30). The cell already reaches any player in any space (`SpaceManager::find_online_player_by_name`, `CellToBaseMsg::EntityMethodCall`). |
| D-ORG04 | PROPOSED | **Team and Command authority lives on the base**, with the database as the source of truth. **Named invariant ORG-LOCK:** every Team/Command mutation (membership, rank, permissions, texts, disband, and the Bank campaign's cash and vault changes) opens a transaction, takes `lock_org` (`SELECT … FOR UPDATE` on the org row) **first**, and authorizes inside that transaction; nothing is ever authorized from a pool read. The global lock order is the org row, then `sgw_player` rows, then item rows, which matches trade and vendor (`trade/execute/mod.rs:9-10`). The in-memory state is the existing online-session map plus two bounded maps with a TTL, pending invites and pending creations. Both are lost on a restart by design: the player just asks again. | The contact list uses the same stateless shape (`presence_fanout.rs`), and organization mutations are rare. With no cache there is nothing to drift. The lock and the order come from the security review: a membership check outside the lock lets a kicked or demoted member act (TOCTOU), and a different lock order would deadlock the first bank PR against trade. |
| D-ORG05 | PROPOSED | **One organization-id space on the wire.** Team and Command ids come from the database sequence; the schema pins `CHECK (org_id BETWEEN 1 AND 0x3FFF_FFFF)`. Squad ids come from a monotonic cell counter in `[SQUAD_ORG_ID_MIN = 0x4000_0000, 0x7FFF_FFFF]` and are never reused within a server run. Cell methods that carry an org id (CM 9, 10, 13-19) route on that range: squad ids stay on the cell, positive ids below the range go to the base, and anything else is rejected. **Routing is not authorization:** the cell still checks `caller.squad_id == org_id`, and the base still checks membership under ORG-LOCK. | The client uses one id field for all three types. A disjoint range makes routing a comparison, and a forged id of the wrong kind simply misses. Never reusing an id means a stale pending entry cannot join a different squad. |
| D-ORG06 | PROPOSED | **Pending invites.** Each entry is keyed by the invitee's **session `player_id` and the request id together**; a request id alone never finds an entry. Entries record the inviter's `player_id`, the org id and type, and a 60-second expiry, and are **consumed on the first response**, accept or decline. On accept, everything is re-validated (under the squad registry or ORG-LOCK): the org still exists, the inviter is still a member holding `Invite`, the invitee is still in no org of that type, and there is still room. The cell allocates squad request ids from `1..` and the base allocates Team/Command request ids with `BASE_INVITE_REQUEST_FLAG = 1 << 29` set, so CM 8 routes on that flag. A monotonic counter is enough, and no CSPRNG is needed, because guessing another player's request id finds nothing under the composite key. Entries are cleared on every disconnect path. Squad members and pending creations are keyed by `player_id` too, never by entity id, because entity ids are recycled. | CAT-M-18 and the security review. The flag is bit 29 so it cannot be confused with the squad id range, which starts at bit 30. |
| D-ORG07 | PROPOSED | **Ranks per type.** Squad: the leader is `Leader` (8) and everyone else is `Member` (2). Team: `Member` (2), `SeniorMember` (3) and `Leader` (8), which are the only ranks `Team.lua` edits. Command: `Initiate` (1) to `Leader` (8). New Team members join at 2, new Command members at 1. | Client evidence (audit A-12). |
| D-ORG08 | PROPOSED | **Default rank permissions**, used when a Team or Command is created: `Leader` has all 26 bits; `SeniorOfficer` has `Officer`'s bits plus Promote, Demote, RankNames and AlterPerms; `Officer` has Invite, Eject, RosterNotes, OfficerNotes, OfficerChat, MOTD, DepositBank, WithdrawBank and DepositCash; `SeniorVeteran` to `Member` have RosterNotes and DepositBank; `Initiate` has nothing. Team's `SeniorMember` gets `Officer`'s bits. `Leader`'s row is pinned to all bits: no editor, including a GM command, may change it. `TransferLeader` stays outside `editable_for` until a transfer feature exists. | The client ships no defaults. The ladder is #584's with the vault bits added. The owner can change any other rank in the in-game editor. |
| D-ORG09 | PROPOSED | **Rank authority invariants** on every rank change, kick, permission edit, rank rename and officer note, all checked under ORG-LOCK. (1) The actor holds the bit for the action, and a rank change uses `Promote` or `Demote` according to its direction. (2) The actor's rank is strictly above the target's current rank and strictly above any rank being assigned. (3) Nobody edits their own rank's permissions or name. (4) `Leader` is never assigned by a rank change. (5) Any assigned rank must be in `OrgRank::for_type(type)`, so 0, and Team rank 5, are rejected. (6) A new permission mask is clamped to `editable_for(type)` **and** must satisfy `new_mask & !actor_permissions == 0`, so an editor can grant only the bits it holds. | CAT-M-05, M-06, M-07 and M-10, plus the security review. Without (6), an Officer holding `AlterPerms` could grant `WithdrawCash`, which it does not hold itself. |
| D-ORG10 | PROPOSED | **Text rules**, enforced server-side by rejecting (not truncating) with feedback. Decoders bound each `WSTRING`'s declared length by the remaining payload before allocating. Every text field rejects lone surrogates, C0/C1 controls (MOTD and notes may keep a newline), bidi controls (U+202A-202E, U+2066-2069) and zero-width characters (U+200B-200D, U+FEFF). Caps, in UTF-16 units: organization name 1-60, MOTD 255, note and officer note 128, rank name 32. Organization names are also NFC-normalised, have their internal whitespace collapsed and their ends trimmed, and are restricted to Latin letters, digits, space and the characters `'`, `-` and `.`; uniqueness is per type on the case-folded normalised form, stored in a `name_key` column. (The `varchar` limits count code points, which is harmless because the server cap is stricter.) | The name rule comes from the client `.int` string. The rest are server policy for CAT-M-03, M-08 and M-10. A Latin-only name rule rules out homoglyph impersonation without a confusables table. |
| D-ORG11 | PROPOSED | **Online status stays client-derived.** The server sends no online flag. It sends each online member's entity id as the member id, and 0 for an offline member; the client shows "Online" only for members whose entity it has streamed (ORG-E1 confirms how the ids are populated). Sending the live entity id of a member in another space leaks only that the member is online, which is accepted. | `RosterInfo` has no online field; the client computes it from its entity cache (audit A-11). A true cross-world flag would need a client patch. |
| D-ORG12 | PROPOSED | **Losing a leader.** A Squad leader leaving or disconnecting promotes the longest-standing remaining member. A Team or Command leader cannot leave while other members remain (the leave is rejected with feedback). Leaving as the last member disbands the organization and deletes its rows, and any vault items or cash in it are lost. **Deleting the leader's character**, by any path, promotes the highest-ranked, longest-standing remaining member to `Leader`, or disbands the organization if nobody remains. A database trigger on the member row's delete does this, so the character-delete handler, GM tools and test cleanup are all covered. The remaining members are counted under ORG-LOCK, so two last members leaving at once cannot race. A GM can disband with `.org_disband`. | There is no `TransferLeader` UI in either editor. Silent auto-promotion on an ordinary leave would hand the treasury to whoever joined second, but a deleted leader must never leave an organization with no leader and its treasury stuck (both reviews). |
| D-ORG13 | PROPOSED | **GM test commands use the `.` console** (`cell-console` registry), because only `gmReloadOrganizations` (164) has a native binding, and it is already gated as part of the `SGWGmPlayer` tail. They are GameMaster-gated like every other `.` command, keep the D-ORG10 caps and the D-ORG09 mask clamp, and log `org.gm_action` with the actor. No privilege bit ever travels in a cell-to-base payload; the base re-reads the access level from its own session map. | Project convention (#523, `feedback_gm_commands_intent_over_legacy`), plus the security review. |
| D-ORG14 | PROPOSED | **The chat channel ids follow `enumerations.xml`** (server 8, feedback 9, tell 10, officer 6) once ORG-E1 confirms whether the client hardcodes any `EChannel` value. Until then the registered set is left alone. | The doc and code use server 7 and tell 9, which conflicts with the enum. A wrong id raises the client's unknown-channel popup, so this changes only with evidence (audit A-40). |
| D-ORG15 | **ASK OWNER** (recommend: free, configurable) | **Creation cost.** Recommendation: `ORG_CREATE_COST_TEAM` and `ORG_CREATE_COST_COMMAND` constants, both 0 for now. A non-zero cost is debited from `sgw_player` inside the base's `create_org` transaction, so a rejected name costs nothing. | No cost appears anywhere in the client or data (audit A-14). Free creation keeps UAT simple; the constant makes a later price a one-line change. |
| D-ORG16 | **ASK OWNER** (recommend: leader only) | **Who may set the Squad loot mode.** Recommendation: the leader only. A non-leader's change is rejected with an `onErrorCode` and a re-send of the current `onSquadLootType`, so the menu visibly snaps back. Values outside `RoundRobin` (0) and `FreeForAll` (1) are rejected. | The client offers the menu to every member (audit A-16); CAT-M-11 and the #472 criteria require leader only. | D-ORG17 | **TRANSFERRED** to the Bank campaign (2026-09-27) | Vault size and expansion. Nothing settles cross-type exclusion: `records` is keyed per organization, `squad` is a separate property, no "already in a team" string exists, and the only exclusion found is that the two creation dialogs cannot be open together (audit A-17). |

## Where confidence is low

- Whether the client fills the roster's member ids from `onOrganizationRosterInfo` or only from `onMemberJoinedOrganization` (ORG-E1 Q1). It decides whether a login roster shows anyone as online.
- Whether `squadKick` is a thin wrapper over `organizationKick` or its own wire path (ORG-E1 Q2).
- Which client method shows a minimap ping to the other members; `receivedMinimapPing` is a server-internal cell method (ORG-E1 Q3).
- Whether `onOrganizationCreationResult`'s `RetCode` is ever turned into text (ORG-E1 Q4). If not, feedback for a rejected name has to come from `onErrorCode` or a chat line.
- Every value in D-ORG08 and D-ORG10 is project policy, not recovered data, and the docs must say so.

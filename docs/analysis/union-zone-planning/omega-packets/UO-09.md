## Why

Missions 1423 and 1500 are `can_abandon true` (`missions.sql:433,493`). An abandon removes the instance (`crates/cell-content/src/cell/missions/lifecycle.rs:243-254`). Nothing would offer it again, because 1655 is already completed and the induction chains are gated on 1655 active. The route would soft-lock (D-UO10, CIMMERIA_RECONSTRUCTION). The fix is a "?" re-offer from the same NPC with the same shipped dialog (maps 63802 and 63803, flags 8388608).

The offer guard lets the re-accept through: the abandoned mission has no instance left (`lifecycle.rs:87-90`). Re-offering 1655 itself is SGC's concern, not Omega's (handoff note).

  Omega chains use `scope_type 'mission'` with the mission id, or `'space'` with the world id. Triggers use `scope 'player'` and `once false`.
- **Event keys:**
  - `player_loaded`: the world name, `'Omega_Site'` (world 18) or `'Omega_Site_CmdCenter'` (world 80).
  - `teleport_in`: the ring region id as text (`'17'` = the world-80 pad). The test param is `region_id` as a JSON number.
  - `dialog_choice`: the dialog id as text.
- **Conditions** (`crates/content-engine/src/conditions/mod.rs:297-346`):
  - `mission_status`: target_id = mission; values `not_active`, `active`, `completed`. A missing key reads as `not_active`.
  - `step_status`: target_id = mission, target_key = step as text, `eq active`.
  - `objective_status`: target_id = mission, target_key = objective as text. `mission_context.rs:189` sets `completed` for completed objectives only.
  - `archetype`: value as text. A missing archetype reads as `-1`. The gates are: Human `gte 1` **and** `lte 4`, Asgard `eq 5`, Free Jaffa `eq 7`.
  - `world`: target_id = world id, `eq`, value `NULL` (copy `(8003, 'world', 61, NULL, 'eq', NULL, 0)` from `dakara_e1_space_chains.sql`). It fails closed when the context has no world.
  - `dialog_choice` matches on the dialog id alone; the button has no authorable condition. Dialogs 4641 and 5025 have exactly one button, `Accept`, on their final screen, and 6168 has none. `fire_dialog_choice` and `fire_teleport_in` both set `archetype` (`event_dispatch/dialog.rs:113`, `region.rs:158`, guarded by `dialog_archetype_tests.rs`). The castle_701 header comment that says otherwise is stale.
- **Actions → enum** (`crates/content-engine/src/actions.rs`, loader `loader/action.rs`):

  |---|---|---|---|---|
  | `advance_step` | mission | step as text | | `AdvanceStep { mission_id, step_id }` |
  | `complete_mission` | mission | | | `CompleteMission { mission_id }` |
  | `complete_objective` | mission | objective as text | | `CompleteObjective { mission_id, objective_id }` |
  | `accept_mission` | mission | | | `AcceptMission { mission_id }` |

  The `add_dialog_set` target is a map id: `executor/dialog/mod.rs:191` looks it up in `dialog_set_maps`.
- **Bind facts:**
  - `add_dialog_set` pushes onto `available_interactions[slot]` with **no dedupe** (`executor/dialog/mod.rs:195-199`). `remove_dialog_set` is `retain(dsm_id != id)` (`:285`), and on an absent entry it does nothing. **So every Omega bind chain runs `remove_dialog_set` (sort 0) before `add_dialog_set` (sort 1)**, as castle chain 1204 does, and a re-fire can never stack a second entry.
  - A bound map with a non-NULL `dialog_id` opens that dialog on click through `handle_interact` (`cell-interactions/.../dispatch/interact.rs:125-148`, INFO `interact: per-player dialog set → onDialogDisplay`). Omega therefore writes **no `interact_tag` chains**. An `interact_tag` chain would short-circuit `handle_interact`, skip the `last_interaction_target` pin, and show a second dialog (`chain_replay_tests/mission_1324.rs:17-28`).
  - Every map an Omega chain binds has non-zero `interaction_flags`, because the cast templates have `interaction_type 0`.
- **Order inside a chain:** `remove_dialog_set` runs **before** `complete_mission`. `complete_mission` awaits `fire_mission_completed` mid-list (`mission_1324.rs:46-53`).
- **No `complete_objective` on 1655 (F21).** O5645 and O5646 (S4940) are both optional (`db/resources/Missions/Seed/mission_objectives.sql:3136,3138`), and the engine completes a mission once no required objective is left open on its step (`crates/content-engine/src/progression.rs:464-506`). A chain that completes an objective of 1655 therefore completes the whole mission early. Omega only advances the step (63801) and completes the mission on the Accept (63822, 63832). The proof is the absence of "Content: completing mission" for 1655 before the Accept.
- **`mission_abandoned`** fires after the mission instance is removed, so on that event the abandoned mission already reads `not_active` (F22). Its INFO line is "fire_mission_abandoned: matched" (`event_dispatch/mission.rs:217`). The event key is the mission id as text.
- **The 1655-active guard.** Every delivery chain (63820-63822, 63830-63832) carries `mission_status 1655 eq active` at sort 1, and every re-offer chain (63840-63845) carries `mission_status 1655 eq completed`. The two families can never both match one event, so one click never resolves two binds or two accepts.
- **Order on a ring beam into world 80:** `player_loaded 'Omega_Site_CmdCenter'` fires first, at entity creation (`player_init/mod.rs:532`). `teleport_in '17'` fires after it (`event_dispatch/region.rs:140`). `resolve_event` evaluates every chain against the **pre-event** context, so on the first beam both events see step 4940.

### Why 6007 is disabled rather than shipped as-is

World 57 has a navmesh, so the arrival is validated. `resolve_recovery_position`
has **no candidate** for a player landing there: reprojection fails at ±3-unit
extents, the AABB clamp declines because the point is inside the mesh bounds,
and the respawner branch filters on `world_name == "Harset"` — and world 57's
respawner (row 20) also waits on M0, so there is none. The outcome is a silent
`CorrectionSuppressed`: the player moves on their own screen, never moves for
witnesses, cannot interact, and gets no error. A visibly dead one-way door is a
strictly better failure than a silently ghosted player.

The coordinate was **not adjusted**. The campaign rule is that every Harset
coordinate is either recovered from the Python or pinned in-game.

### Why 6006 is safe to ship enabled

World 68 has no navmesh, so the movement validator fails open —
`is_position_valid` returns `true` unconditionally with no mesh loaded and bounds
fall back to the 20 km box. There is no off-mesh failure mode to guard against,
so the raw 2009 coordinate ships as recovered. This is the same reason Cellblock
chain 1109's Castle arrival has never bitten.

## Linter adoption

**There is no scan list to add the file to.** Both linter tests `read_dir` the
seed directory and take every `*_chains.sql`, so `harset_space_chains.sql` is
linted the moment it lands. This is recorded as a doc comment on
`every_chain_region_key_matches_a_seeded_point_set` because the packet brief
assumed an explicit list, and the *loader* registration (`\ir` in
`db/database.sql`) really is a separate, easy-to-forget step that the linters do
**not** catch.

**Dotless ring point-set names (2052-2056) are handled.** The superseded
per-file "one canonical case per world prefix" heuristic derived a prefix by
splitting on `.`, so a dotless name had no bucket and was skipped. The current
cross-file check is a plain set-membership test against every `point_sets.name`
with no prefix logic at all, so `HarsetRingLeftBottomPS` and friends are already
in scope. **No fix was needed** — but the property was untested, so H10 adds
`dotless_point_set_names_are_not_skipped`, which fails if anyone reintroduces
prefix-based grouping that exempts them.

**Five allowlist entries (6001-6005).** Entity template 3 ("Ring Transporter
Switch") already carries `interaction_type = 32` (`INT_RingNetwork`) as a
template default, and the spawner reads that column onto every spawned entity.
The three already-shipped Cellblock ring switches (spawns 17, 23, 79) are the
same template and inherit the same bit. Seeding five redundant
`set_interaction_type` actions would imply the bit needs setting and invite a
later "fix" of a non-bug, so the allowlist — whose own doc comment names exactly
this case ("inherit the bit from the entity template default") — is the right
instrument.

> **Reviewer flag (#97):** five entries at once sits right at the threshold the
> allowlist's doc comment calls out. The template-default family is now 16 of the
> 20 entries. The entity-template walker (issue #97 stretch goal) is the real fix
> for the whole family; H10 does not attempt it.

## Zero relog-restore chains

The campaign rule — "every chain that sets an interaction bit or binds a dialog
set has a `player_loaded` restore chain gated on the active step" — exists
because *chain-set* `interaction_type` bits live in memory only and do not
survive a restart. No chain in this packet sets a bit or binds a dialog set: the
ring switches' bit comes from the template column, which the spawner re-reads
from the DB on every spawn.

So the Common Acceptance clause (c) — "asserts the relog-restore chain re-paints
every interaction bit and dialog-set binding the packet sets" — is **vacuously
satisfied**: the set is empty. Recording it here rather than writing an empty
test, so the absence is not read as an omission.

Dependency U3 is confirmed landed on this base: `space_castle_cellblock_chains.sql`
is gone from `db/resources/Content/Seed/`, so the Cellblock `player_loaded` noise
the ledger warned about no longer pollutes Harset relog tests. (Its two now-dead
allowlist entries at `interact_tag_linter.rs` are harmless; removing them is a
different packet's cleanup.)

### Design choices worth defending at review

- **Chain ids are pinned alongside the action**, following the `mission_640`
  shape rather than the variant-only filter in `region_transition_accepts`. All
  five ring chains emit the same *variant*, so a variant-only count cannot tell
  "6001 fired with region 4" from "6003 fired with region 4 after a copy-paste".
- **Total `resolved.actions.len()` is asserted**, not just the filtered count.
  `build_engine` loads the entire DB into one engine and `resolve_event` appends
  every matching chain's actions into one flat vec with no per-file
  partitioning, so a filtered count of 1 still passes when another seed file's
  chain matched the same key and appended unrelated actions. That is the exact
  shape `region_transition_accepts` exists to catch.
- **The exact teleport coordinate is pinned.** `convert_action` *drops* a
  `cross_world_teleport` with missing or non-finite params rather than
  defaulting to the origin, so a malformed row yields **zero** actions. Pinning
  the coordinate also forces a future M0 re-pin through this test.
- **The cross-product negative is the load-bearing one.** If two `regionId`
  params were transposed, every per-tag positive still sees "one
  TriggerTransporter". Only the cross-product catches it — and a transposed
  `regionId` is the single most likely authoring error in this table.
- **`regionId` is camelCase and the loader uses `unwrap_or(0)`**, not
  drop-with-warn. A snake_case typo produces a live
  `TriggerTransporter { region_id: 0 }` that reaches the ring runtime, finds no
  transporter, and only logs — a dead switch with no authoring-time signal.
  Asserting the exact region id is what converts that into a test failure.

### Deliberate deviation from the packet's Acceptance clause

`work-packets.md` §H10 Acceptance says "`is_point_valid` passes for every seeded
coordinate against `harset.nav`". For chain 6007 that is **inverted on purpose**:
the coordinate is recovered, not pinned, it fails `is_point_valid`, and the
campaign forbids me from inventing a replacement. The packet's own scope text
anticipates this ("the audit measured this return point 27 units off the mesh …
so a pin is mandatory"), and Common Acceptance forbids seeding an unpinned
coordinate — so the two clauses cannot both be satisfied until M0 runs. The
resolution is the disabled chain plus the biconditional guard: the coordinate
ships as recovered, the door is off, and the test enforces that pairing in both
directions. Flagging it here because a reviewer checking the Acceptance line
literally will otherwise read it as a miss.

### The one acceptance clause that is untestable

Common Acceptance and the H10 brief both ask for "zero resolutions for the
**wrong world**" on the door chains. **World is not in the door chains' match
surface at all** — see "Integration requests" below. What the tests assert
instead is the property that actually separates the two doors today: byte-
distinct region keys, each resolving exactly its own teleport and zero of the
other's. A test named "wrong world resolves nothing" would pass for the wrong
reason and is deliberately not written.

### What the review changed

Six findings, all adopted:

1. **M6 hole.** Deleting only 6007's `content_triggers` row left every test green:
   "row exists, deliberately off, resolves nothing" reads identically to a
   structurally dead door, and the breakage would only surface after M0 flips the
   flag. `harset_return_door_is_disabled_pending_an_m0_pin` now also pins the
   trigger's `event_key` and the action's `target_key` and x/y/z.
2. **L2 hole.** `dotless_point_set_names_are_not_skipped` re-implemented the
   membership filter in its own body, so it was asserting that
   `HashSet::contains` is case-sensitive — a property of std, not of the linter —
   and stayed green when a prefix heuristic was added to the real check. The
   predicate is now factored out as `region_key_violations` and both the
   production test and the dotless test call it.
3. **Redundant test deleted.** `no_harset_ring_tag_resolves_another_rings_region`
   was provably implied by the positive test (which asserts `len() == 1` *and*
   the exact `(chain_id, action)` pair), passed vacuously under M1, and cost a
   second full `build_engine` DB load for no marginal signal. Removed. Replaced
   with something strictly better:
4. **Ring identity cross-check added.** The old pair of tests were both driven by
   `RINGS`, a table I authored — so neither could catch a transposition made *at
   authoring time*, because the mistake would have been copied into both places.
   `harset_ring_chain_tags_agree_with_their_regions_point_set` re-derives the
   pairing through rows this packet did not write
   (`ring_transport_regions.point_set_id` → `point_sets.name`) and asserts the
   shipped `<tag>PS` naming convention holds.
5. **Navmesh test made a biconditional and data-driven.** It hardcoded the
   coordinate, so an M0 re-pin that left `enabled = false` would have kept it
   green while asserting a coordinate no longer in the DB. It now reads the
   coordinate from `content_actions` and asserts *enabled ⟺ on-mesh*, which
   passes before and after M0 and fails on either half-done change.
6. **Two unpinned claims pinned.** `entity_templates` row 3's
   `interaction_type = 32` is what the five allowlist entries rest on — zero it
   out and all five rings go un-clickable while the linter stays silent
   *because of the allowlist*. And the anti-ping-pong clearance was asserted in
   prose in the seed comments and nowhere in code, despite having the worst
   failure mode in the packet (an inescapable teleport loop). Both now have
   live-DB guards.

## Integration requests

These are outside H10's owned paths. Each needs an owner.

**IR-1 — world-scope the region-trigger dispatch site.** `TRIGGER_REGION` takes a
client-supplied `region_id` and resolves it through `SpaceManager::get_region`, a
flat `HashMap<u32, RegionData>` spanning every world. `RegionData` carries
`world_name` (and `regions_for_world` already filters on it) but the dispatch
site never compares it to the player's world before calling `fire_enter_region`.
In 2009 this was structural — the subscription lived on the `Script` instance
owned by the space.

Both advisors independently recommend fixing it at the **dispatch site**, not the
condition layer: one change fixes every chain in the seed at once including
Castle's, needs no schema or loader work, and a condition-layer fix would be
incomplete anyway because `fire_interact_tag` never populates `world_name`.
Reject a region whose `RegionData.world_name` differs from the acting entity's
world, with a `warn!` per the negative-logging convention.

Suggested owner: `server-authority-enforcer` + `rust-gameserver-dev`. This is an
inbound-message trust question, not a movement one. **Not urgent for H10** (both
Harset doors are unconditionally open to everyone, so the exploit grants
nothing), but the next `enter_region` chain that grants or completes something
needs it.

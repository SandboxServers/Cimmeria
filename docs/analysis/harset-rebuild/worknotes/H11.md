## What changed

### New ability sets

`ability_set_abilities` has `PRIMARY KEY (ability_set_id)`
(`db/resources/_primary_keys.sql`), and `db/database.sql` applies the primary
keys at line 264 *before* the seed at line 273 — so **a set can hold exactly one
ability**, and a second row aborts the whole DB load. Verified against the live
DB (`pg_get_constraintdef` returns `PRIMARY KEY (ability_set_id)`). The planned
guard/elite split is therefore impossible without a schema change; see
[Integration requests](#integration-requests).

**`respawn_secs` on 159/160 was reverted after the H13 handoff** (coordinator
decision, 2026-09-18). The first draft set a 300s template default on both rows
on the reasoning that `COALESCE(s.respawn_secs, t.respawn_secs)` makes a template
default free cover for any spawn row that omits the column. That reasoning is
sound but the blast radius is wrong: **templates 159 and 160 are shared with
Castle world 8** (spawns 119, 121, 123, 124), so a template default silently opts
Castle's guards into respawning — a Castle-ledger call, not Harset's. H13 sets
`respawn_secs = 30` on each Harset *spawn* row of 159/160 instead, which is where
a per-zone value belongs. The guard in
`praxis_jaffa_guard_templates_use_the_staff_ability_set` now asserts
`respawn_secs IS NULL` on those two rows so a future packet cannot reintroduce
the leak. The new Harset-only templates 200-248 keep their template default —
they are shared with nothing.

`ability_set_id` on 163 is deliberately left NULL: an NPC that must never fight
does not need an attack ability, and the staff set is on template 221.

**Merge order with H13 runs the other way round from the packet ledger's
dependency arrow.** H13 depends on H11 for the ability-set ids, but H11's faction
flip on Petbe (163 → explicit faction 1, and the new hostile 221) must not land
without H13's respawn rows, or the Harset plaza is back to one-shot guards with
no template fallback. The two are intended to be merged in the same PR, **H13
first**.

## Level derivation

The packet said to derive mob levels from the introducing mission's level. **That
rule was not used as the primary source**, because the mission `level` column
reads `1` on every Human and Goa'uld Harset mission (1360, 567, 1361, 1362, 1363,
1365, 1240, 1241, 1244, 1200, 742, 1580) while their content is clearly level
30-45 — it is an unset placeholder, not a design value. Only the Jaffa chain
carries real mission levels (6, 8, 10, 24, 36, 38, 41, 42, 46).

The better evidence is in `texts.sql`: the original mob display-name monikers
encode a rank and a level band, e.g. `DN_Mb_Harset_Malac_Lt_14-16_Fac`. Seven of
the roster carry one. The rules used, in order:

1. **Moniker band present** → midpoint, floored. The band is a range because the
   2009 server rolled a level per spawn; `spawnlist` has no `level` column, so
   the midpoint is the honest collapse. Full bands are recorded in the seed
   comments for a future randomizer.
2. **No band, talk-only** → **50**. This matches every named Harset NPC template
   already in the seed (42 Ba'al, 43 Anat, 46 Lethander, 48 CaptCoppleman, 53
   Nerus, 54 Moh'Katan) and the two Praxis guard rows. Per the advisor it is the
   importer's "level unknown" sentinel rather than a semantic rank — General
   Hammond and Teal'c are level 1 — so it is documented as a Harset-local
   convention, not a meaning. It is inert: `level` only drives max HP
   (`200 + 50*level`), kill XP (`10*level`) and `onLevelUpdate`; nothing in AI,
   threat, range or leash reads it.
3. **No band, hostile** → the introducing mission's level (208 Free Jaffa
   Attacker from 1348 L38, 221 Petbe (hostile) from 1245 L42), or the nearest
   sibling's band where the mission level is the L1 placeholder (202 Bra'hin).

## Scope additions beyond the packet's roster

Three templates the packet did not name — **221 Petbe (hostile)**, **222 Lance
Corporal Grogan (hostile)**, **223 Dawson (hostile)**. Coordinator may veto; the
consequence of vetoing is spelled out below.

The reason is a hard engine constraint, verified in code, not a preference:

- `useAbility` rejects a player's single-target ability whenever
  `target.faction != HOSTILE_FACTION` (`HOSTILE_FACTION = 10`,
  `cell/combat/mod.rs:21`; gate at
  `cell/abilities/use_ability/handle.rs:223-237`). The damage pipeline is never
  entered. The AoE and cone paths exclude non-10 targets the same way.
- Right-click `interact` on an **alive** faction-10 NPC is rerouted to
  auto-attack instead of dialog
  (`cell/cell_methods/player/interaction/interact.rs:44-46`).
- Nothing can change an entity's faction at runtime. `set_aggression` writes only
  `entity.aggression`; `Action::ModifyProperty` is declared in
  `content-engine/src/actions.rs` with **no executor arm**; there is no
  `set_faction`.

So faction is fixed at spawn, and an NPC that is talked to in one mission and
killed in another cannot be one template. The three affected characters:

| Character | Talked to | Killed | Templates |
|---|---|---|---|
| Petbe | 742 (disguise), 1363 Prudence — spec test M-10 says tagging must **not** aggro | 1245 Extreme Prejudice | 163 (faction 1) + **221** (faction 10) |
| Grogan | 1580 step 4700 "Approach Lance Corporal Grogan in Storage" | 1580 step 4702 "Eliminate Grogan and the NID Operative" | 216 (faction 1) + **222** (faction 10) |
| Dawson | 741 steps 2493/2495 | 1365 step 4052 | 217 (faction 1) + **223** (faction 10) |

The hostile clone carries the same `name_id` as the talk row, so the player sees
one character; only `template_name` differs (it is UNIQUE). If the coordinator
vetoes these three rows, H45 (1245), H34 (1580) and H33 (1365) are blocked until
a `set_faction` primitive exists.

**200 Mala'c is faction 10 for the same reason**, and that is a constraint on
H21, not a choice: at faction 1 the player's ability is rejected before the
damage path, so the `entity_health_below Rinla_Malac:30` trigger D-H11 depends on
could never fire. Consequence H21 must plan for: his challenge dialog cannot be
right-click, it has to be chain-driven (`add_dialog_set` / `display_dialog`),
which is how every other Harset dialog is authored anyway. Faction 10 alone does
**not** make him attack on sight — the AI tick admits an Idle NPC only when
`aggression > 0` — so the chain's `set_aggression` still starts the duel.

One further column beyond the packet's letter: **163's `name_id`**. The packet
named faction, level and alignment. `onNameIdUpdate` is only sent when `name_id`
is `Some` and non-zero (`mercury/aoi/create.rs:211-218`), so the shared-hub Petbe
currently renders with no display name at all — same NULL-column defect class,
same row, one line. Flagged here so it can be reverted independently.

### Revert proof

`revert.sql` restores the exact pre-H11 state of every row this packet touched:
deletes templates 200-299, deletes `ability_sets`/`ability_set_abilities` 4 and
5, nulls `ability_set_id` on 159/160, and nulls `level`/`alignment`/`faction`/
`name_id` on 163. Statement order is load-bearing —
`entity_templates_ability_set_id_fkey` and
`ability_set_abilities_ability_set_id_fkey` are both `ON DELETE RESTRICT`, so
every referencing row has to stop pointing at sets 4/5 before those sets can be
deleted. The first draft of the script had the order wrong and would have aborted
mid-revert, producing a state that was not pre-H11 and a proof that meant
nothing; the testing-validation-engineer review caught it before it ran.

```text
##### 1. BASELINE (seed rows applied -- every guard must PASS)
Summary [1.616s] 11 tests run: 11 passed, 2004 skipped

##### 2. REVERT SEED ROWS
UPDATE 2 / DELETE 33 / DELETE 2 / DELETE 2 / UPDATE 1
 templates_200_299 | sets_4_5 | guards_still_pointing
                 0 |        0 |                     0

##### 3. GUARDS AGAINST REVERTED DB (every guard must FAIL)
Summary [0.646s] 11 tests run: 0 passed, 11 failed, 2004 skipped
```

Every run is grepped for `skipping live-DB test`, because `require_db_or_skip!`
turns an unreachable database into a self-skip that still reports `ok` — a green
run against the wrong `DATABASE_URL` would prove nothing. No skip line appeared in
any of the three runs.

## Integration requests

1. **H03 (`spawn_entity`) — mission-scoped respawn suppression.** Highest
   priority. `COALESCE(s.respawn_secs, t.respawn_secs)` has no way to express
   "this spawn never respawns", and every mob template in this packet has a
   300s default. A mission-scoped instance spawn of 202, 203, 208, 211, 218, 221,
   222 or 223 will therefore repopulate 300 seconds after the player kills it,
   inside the player's own instance. H03 needs a per-spawn suppression (an
   explicit sentinel, or a spawn-time override on the `spawn_entity` params)
   before H23, H25, H33, H34, H43 or H45 ship.
2. **Schema — widen `ability_set_abilities_pkey` to `(ability_set_id,
   ability_id)`.** Owner: whoever owns `db/resources/_primary_keys.sql`. The
   Rust side is already multi-ready (`array_agg` in the loader,
   `choose_npc_ability` walks N ids); only the key blocks it. Until then no NPC
   can have more than one ability. Note that a variety set also needs abilities
   with a non-NULL `event_set_id`, which rules out most of the staff list.
3. **A `set_faction` (or `set_hostile`) executor arm.** Five lines, and it
   collapses every talk-then-fight NPC from two templates to one. Without it the
   only shape available is despawn-and-respawn-the-other-template, and half of
   that (`spawn_entity`) is H03's unlanded work. Raise with the H03/H04 lane.
4. **H47 needs a hostile Lethander template.** Mission 1247 Patsy kills a
   Lethander clone in the Market; template 46 is the shared-hub talk Lethander
   and cannot be both. Same shape as 221/222/223. Not authored here because the
   packet's roster does not name Lethander — say the word and it is one more row.
5. **H12/H14 own the `SecondBug` / `ThirdBug` baskets** as new *spawn rows* of
   template 164, not new templates. Confirming so they do not fall between
   packets.
6. **Templates 34/35 (SGC Jaffa) should point at ability set 4.** They already
   carry `WP-Jaffa.WP_Staff_Plasma_4A` in `components` and still fall back to 592
   Pistol Shot. One column each. Left alone here only because the Castle campaign
   is editing the same file concurrently.
7. **Art follow-up (H-B14 class).** `components` on 159, 160 and 163 carries no
   `WP-*` entry, so those Jaffa mime their staff. Same for template 54
   Moh'Katan's `BS_JaffaFemale` body set with male `AR_JM_*` components (the
   original H-B14). Both are art-data fixes outside this packet.
8. **H99 — three Harset monikers have empty `text`.** 7582 (NID Operative), 7585
   (Opheltes) and 7587 (Ra's Jaffa) exist but render as a blank name over the
   head, so this packet points those three templates at substitute monikers from
   other zones (7581, 7068, 7455). Backfilling the Harset rows is the real fix;
   `harset_templates_with_a_name_id_resolve_to_non_empty_text` stops anyone
   "correcting" the substitutes back to the empty rows before then.
9. **No `docs/spec/` chapter covers any of this.** Every guard in this packet
   cites `docs/analysis/harset-rebuild/`, and "spec L-01" appears in the tests as
   a bare label with no chapter path. The invariants these tests encode — the
   faction gate, the `COALESCE(spawn, template)` resolution order, the
   `append_appearance` branch, the one-ability-per-set key — are exactly the kind
   of section-4 claims a chapter should own. Route a chapter proposal through
   `documentation-writer`; this packet should not invent one.

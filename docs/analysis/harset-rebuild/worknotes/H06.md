## Behaviour implemented

### 1. Dial gate (CAT-O-01)

`handle_dial_gate` took `target_address_id` — a raw client `INT32` — and
looked it up in the world-global `stargates` cache. Any client could dial any
of the 28 seeded gates and cross-world teleport itself into content it never
unlocked. `known_stargates` was loaded from the DB, serialised to the client
in `setupStargateInfo`, and read by nothing on the server.

The check sits **immediately after the `-1` cancel**, before the `stargates`
lookup, for three reasons:

- It is the dial *request* gate. CA10 arms a 4-second pending dial further
  down the same function; the refusal has to land before anything is armed.
- Putting it above the `stargates` lookup removes an existence oracle: "that
  address does not exist" and "that address is not yours" are now the same
  observable.
- One call at the top of the handler is what makes CA10's rebase mechanical.

**Refusal shape.** `onErrorCode` (121), the only error surface `SGWPlayer.def`
exposes — 2009's free-text `onError("Failed to dial: not a known stargate
address")` has no Cimmeria equivalent. Seven bytes, `SystemID = 0`
(`ERRORCODE_SYSTEM_Ability`, the only token `EErrorCodeSystem` defines),
`InstanceID = 0`, `ErrorCodeID = 180`
(`CONDITION_FEEDBACK_EntityDoesNotHaveStargateAddress`). `InstanceID` is
deliberately **0 and not the stargate id**: under `SystemID = 0` the client
reads that field as an ability id, and feeding it an address is a type
confusion into a client-side lookup nobody has traced.

**No hidden list.** 2009 accepted `knownStargates ∪ hiddenStargates`.
Cimmeria has neither a column nor a wire slot for hidden —
`mercury::world_data::map_loaded` hardcodes an empty hidden array — so
"known" is the whole address book. The field is named `known_stargates`
rather than `stargates` so the missing half stays visible.

**No GM exemption in the primitive** — but `gmDHD` needed handling.
`handle_dial_gate` has no `access_level` branch: that would put a second
authorization surface on a check whose whole value is having exactly one.
The advisor's reasoning for this ("GM cross-world travel goes through
`cell_methods::gm::travel`") is only three-quarters right —
`gm::travel::handle_dhd` calls `handle_dial_gate` *directly*, so the gate
silently broke `gmDHD` for any address the GM's own character did not hold.
Fixed at that call site instead: the arm is already authorised by the
cell-method GM gate against the session's `access_level`, so it tops up the
caller's **in-memory** address book with a `gm_address_grant` audit warn and
then dials. Nothing is persisted — a debug dial should not rewrite the
character's book — and `handle_dial_gate` keeps exactly one authorization
surface. This mirrors 2009's `giveaddress` console command.

**Check placement vs. transit.** The gate is on the dial and only the dial.
2009 gates `onDialGate`; `GateTravel.stargatePassed()` is transit and is
ungated. CA10's `REGION_FLAG_STARGATE` volume-entry route should inherit this
decision from the pending-dial record it already holds rather than re-running
it — otherwise a player cannot walk through a wormhole somebody else opened.

### 2. Unlock on arrival — and a correction to the packet's premise

**There is no unlock-on-visit anywhere in the 2009 Python.**
`SGWPlayer.addStargateAddress` (`SGWPlayer.py:609`) has exactly two callers:
the GM console command `giveaddress` (`cell/commands/Player.py:74`) and the
Atrea authoring node `Act_StargateAddress`
(`entities-editor/editor/Nodes.xml:2428`). Addresses were authored content.
The packet describes the rule as "the 2009 unlock-on-visit rule"; it is new
behaviour, implemented because with the dial gate enforced it is the only
grant path in the game, but it should be recorded as a decision, not a port.

**It learns both ends of the trip, and the origin is the half that works.**
The packet says "write the destination gate into `known_stargates` on
successful arrival". On the dial route that is a no-op by construction: the
dial gate refuses an address you do not already hold, so a dialled
destination is always already known. What a traveller does not have is a way
*back* — `handle_gate_travel` is also the transport for GM `.gotolocation`
cross-world, the respawn fork, content `cross_world_teleport` and cross-world
ring transport, none of which consult the address book. Learning the world
you departed from is what makes the rule do anything. Both ends are learned;
the deviation from the packet text is the addition, not a substitution.

**One statement, not two.** The destination-persistence UPDATE and the
address append target the same row with the same key, so they were merged:
atomicity for free, one round trip instead of two, and — the real reason —
no duplicated `WHERE player_id = $ AND account_id = $` whose two copies had
to stay byte-identical for the error reporting to make sense. The append is
inline and correlated rather than a CTE: under READ COMMITTED a correlated
sub-SELECT in `SET` is re-evaluated against the freshly-locked row on an
EvalPlanQual recheck, while a CTE is a stable subplan from the old snapshot
and could double-append.

**The trap the merge creates, and its guard.** The obvious way to avoid a
no-op write is `AND EXISTS (... NOT (x = ANY(known_stargates)))` in the
`WHERE`. That would silently stop persisting `world_location` and `pos_*` on
every arrival at an already-known world, and the player would rubber-band to
their pre-gate location on relog.
`an_arrival_with_nothing_new_to_learn_still_persists_the_destination` exists
solely to catch that.

`array_agg(DISTINCT x ORDER BY x)`, not a plain aggregate: the
`NOT (x = ANY(known_stargates))` filter only compares against the pre-update
array, so a duplicate *within* the input would pass twice and append twice —
and `resources.stargates.stargate_id` carries no uniqueness constraint.

**Ordering.** The write runs after every mid-transfer abort branch (nothing
is written for a transfer that did not happen) and before
`query_player_load_data`, which fills the `setupStargateInfo` list the client
is about to receive. Get the second one wrong and the client renders an
address book one hop out of date while the cell enforces the current one. No
`updateStargateAddress` (66) is emitted: the client is mid-teardown and is
about to be handed the whole book again.

### 3. Region trigger — world scope and containment

`SpaceManager::get_region` is a world-**global** `HashMap` keyed on a
client-supplied id (H10 worknote IR-1), and the arm parsed the client's own
x/y/z into `_x/_y/_z` and threw them away without ever testing where the
player actually was. In 2009 both were structural:
`GenericRegionManager.load(worldId)` built one manager per space, and
`triggerRegion` gated every entering trigger on
`region.isPointInRegion(entity.position)` — the **server-known** position,
never the RPC's (`deprecated/python/cell/GenericRegion.py:167-170`).

`resolve_hinted_region` is one function above everything else in the arm, so
all three gates also cover the ring forwarding and CA10's `REGION_FLAG_STARGATE`
branch when it lands:

1. Non-negative id (pre-existing, moved).
2. `RegionData::world_name` equals the caller's world.
3. Containment on **entry only**, against `entity.position`.

**Exits stay ungated**, matching the Python's own `# TODO: Check !entering
and isPointOutsideRegion() too`. A player who has left a volume is by
definition outside it; gating the exit would refuse every legitimate "on
leave" event. World scoping still applies to exits.

**The threshold is 1.5 units**, `Config.GENERIC_REGION_CHECK_THRESHOLD`
verbatim. The client fires the hint at the instant *its* capsule crossed the
boundary while the server tests the last position it accepted, so a zero
tolerance would make region entry flaky at exactly the place it always
happens. `server-authority-enforcer` asked for 2–3; 1.5 is the shipped 2009
value, is inside the band they described, and is a named constant that can be
tuned from a real client session without touching the logic.

**Point-count risk, measured not assumed.** 2009 refuses any region whose
point list is not exactly 4, and so does this. Against `sgw_harset`: 62
`AreaSet` point sets, 43 single-point cylinders that the loader's workaround
expands to 4, and 19 already authored with 4. **Zero** regions are outside
the rule, so no shipped chain or ring pad changes behaviour on point count.

The AABB is taken over all four corners *after* the workaround, so it
inherits the deliberate `py + h` asymmetry on the fourth — that asymmetry is
what gives an expanded cylinder its ceiling. The `RegionData::height` and
`radius` fields are not read; for the one seeded region with four authored
points *and* a non-zero radius the test is therefore corner-derived only,
which is exactly what 2009 did.

### Live-DB note

The four live-DB tests in `persist_arrival` create and delete their own
sentinel `account` + `sgw_player` rows in `0x7006_06xx` and clean up by exact
id. They need `extra_name` and `bodyset` in the INSERT — both are `NOT NULL`
with a `NULL::varchar` default, so they must be named even though nothing in
the test reads them.

The merged UPDATE's semantics were checked directly against `sgw_harset`
inside a rolled-back transaction before the Rust was written: duplicate input
collapses, an already-held address is skipped, a second identical call grows
nothing but still writes `pos_x`, and a wrong `account_id` matches 0 rows.

## Open questions

1. **Is the origin gate known from character creation?** (Integration request
   3.) 2009's answer was no — every address was authored content — but 2009
   also had a content action that granted them and Cimmeria does not. H06
   implements neither; it learns on travel, which only helps a character who
   has already travelled once.
2. **Does the client render feedback code 180 usefully?** `SystemID = 0` is
   the ability subsystem and 180 is a condition-handler feedback the client
   has a string for, but nobody has traced `onErrorCode`'s handler in the
   binary. If it routes to the ability feedback widget the refusal may appear
   in an odd place. Observable in the first UAT that tries a forged dial;
   until then the refusal is correct and the presentation is unverified.
3. **Is 1.5 units enough slop on a real connection?** The constant is 2009's
   and the maths works out at run speed, but it has never been exercised
   against a real client on a real link. If M1 shows flaky region entry, raise
   `GENERIC_REGION_CHECK_THRESHOLD`; it is one named constant with tests on
   both sides of it.

### The one design decision that needed making: where the template comes from

The ledger's action shape needs an `entity_templates` row, and
`crates/services/src/cell/messages/base_to_cell.rs` stated flatly that "the cell has no template
cache" — the GM `.spawn` path round-trips cell → base → cell to resolve one. Reusing that
round-trip for a content action is **wrong**, not merely slower, for two reasons the
`npc-ai-spawn-advisor` confirmed:

1. **Action ordering.** The executor runs a chain's actions as an ordered list against one
   `&mut SpaceManager` borrow, and the action after a spawn is routinely `set_aggression` /
   `generate_threat` / `add_dialog_set` / `set_interaction_type` — all of which resolve through
   `find_entity_by_tag`. Deferring the spawn to a message round-trip makes every one of them
   miss, and the chain half-executes with nothing but "entity tag not found" debug lines. That
   is not testable-around.
2. **Instance lifetime.** `GmSpawnNpcReady` carries a `space_id` captured at request time.
   Mission spawns target per-player instanced spaces that can be torn down in flight.

So the cell now caches every `entity_templates` row at startup as a prototype `SpawnRecord`,
exactly the way it already caches `dialog_set_maps`, `mission_defs`, `stargates`, `item_defs`,
`loot_tables` and `ring_regions`. 186 rows in the current seed, ~65 KB. The GM path keeps its
round-trip on purpose (a live query reflects `entity_templates` edits without a restart, which
is what an authoring command wants); the stale comment in `base_to_cell.rs` is corrected in this
diff rather than left to misdirect the next reader.

### Three corrections the advisors forced

- **`respawn_secs` is forced to `None`, unconditionally.** `npc_respawn_tick` selects purely on
  `ai_state == Dead && respawn_at <= now`; `spawn_id = -1` gives no protection at all (the GM
  path's comment crediting the sentinel describes the right behaviour via the wrong mechanism —
  its `respawn_secs: None` does all the work). Inheriting the template's value would opt every
  mission spawn into respawn *silently*, and a revived mission NPC re-fires its
  `entity_dead_tag` chain, so a kill objective can complete twice. The action param stays
  authorable but warns and is ignored. Recorded as a gap in §5.
- **`is_stationary` and `aggression` have no template column** (`is_stationary` lives on
  `spawnlist`; aggression is a pure runtime `CellEntity` field). `None` therefore means "off",
  not "inherit" — the doc comments say so now.
- **Non-player actor is refused.** Cover-node and NPC-death chains fire with an NPC as the
  acting entity. An NPC source resolves a *valid* space, so an unguarded spawn succeeds in the
  wrong instance — silent and wrong rather than loud. Same guard shape as
  `world::set_follow_target`.

### `set_visible`: what it used to do

It sent one `CellToBaseMsg::EntityMethodCall` addressed to the target. Base routes that through
`entity_to_addr`, which only holds player entries, so an NPC id resolved to no address and the
packet was dropped. Every seeded `set_visible` row was a silent no-op, and the existing test
asserted only that the message was *constructed* — which is exactly why it passed for as long as
it did. It now mirrors `ring_transport::wire_helpers::send_visible`'s asymmetric shape:
`EntityInvisible` per witness to hide, entity method `onVisible(1)` per witness to show (C++
`ClientHandler::leaveAoI` / `enterAoI`, `client_handler.cpp:507-528`). Unlike the ring helper it
does **not** add the target to the audience — the ring hides a player who must see their own
fade; a content target is an NPC with no client.

## 5. Gaps recorded (not fixed here)

1. **Content-scoped spawns cannot respawn.** The respawn tick has no instance-lifetime
   awareness, and a revived mission NPC re-fires its `entity_dead_tag` chain, so a kill
   objective could complete twice. `spawn_entity` accepts `respawn_secs` and warns that it is
   ignored. Fixing it needs the respawn tick to understand instance lifetime.
2. **`set_visible` is not durable across an AoI re-entry.** `mercury/aoi/create.rs` appends
   `onVisible(1)` unconditionally in the create cascade, so a witness who leaves and returns —
   or connects after the hide — sees a content-hidden entity. This matters for **H27** ("hide
   Crogan's body"), whose whole point is a durable mission-state hide. The fix is a `hidden` bit
   on `CellEntity` that the create cascade consults; it touches `crates/entity` and
   `mercury/aoi/`, both outside H03.
3. **Content spawns are not persistent.** They live and die with the instance — no
   cross-session restore. Relog re-fires the chain, which is precisely why idempotence keys on
   the tag.
4. **Wave spawns need one tag per NPC.** Exact-tag semantics mean H23/H25's `entity_dead_tag`
   counters need either N rows with distinct tags plus N trigger rows, or prefix matching in
   `content-engine`'s trigger matcher. The latter is a trigger change, not a spawn change.
5. **The one real seeded `set_visible` row is never replayed.** `sgc_w1_chains.sql` chain
   **3013** (`SGC_W1_SecurityDoor`) is the production row H-B5 broke, and the sibling module
   `chain_replay_tests/sgc_w1_move_entity.rs` already loads from that seed file. A type-6 replay
   of 3013 would prove the fix works for shipped content rather than only for a sentinel. Left
   undone because `sgc_w1_*` is not H03's content; it is a one-test follow-up for whoever owns
   that seed.
6. **Template field-mapping fidelity is unguarded.** `templates.rs` claims a content-spawned mob
   is "armed, paced and configured identically to a seeded or GM-spawned one", but nothing
   compares the two. One live-DB test in `cell/spawner/tests/live_db_loaders.rs` asserting
   `load_spawn_templates(pool)[id]` equals `base::gm_spawn::load_spawn_record_for_template(pool,
   id)` field-for-field (modulo the documented spawn-instance placeholders) would pin the whole
   mapping in a single assertion. `spawner/tests/` is outside H03's owned paths.
7. **The startup wiring itself is untested.** Deleting `space_mgr.spawn_templates = map;` from
   `cell/service/startup.rs` fails nothing — the replay fixture assigns the cache itself, so it
   guards `load_spawn_templates` the function, not its installation. No cheap harness exists for
   cell startup today.

## 7. Proposed H99 documentation text

For [content-engine.md](../../../content/content-engine.md) §3, "Authorable and executed" table
— two new rows, inserted after `destroy_entity`:

```markdown
| `spawn_entity` | `SpawnEntity` | 0 |
| `despawn_entity` | `DespawnEntity` | 0 |
```

And the following prose beneath that table:

> **Entity lifecycle verbs (H03).** `spawn_entity` instantiates an `entity_templates` row into
> the **acting player's current space** — the seed row never names a space, because a chain
> authored for a per-player instance cannot know which instance the firing player is in.
> `target_id` is the template, `target_key` is the spawn tag (both mandatory), and `params`
> carries `x`/`y`/`z` (mandatory, finite), plus optional `heading`, `is_stationary`,
> `aggression` and `allow_shared`. Four refusals, each warned: a non-player acting entity, an
> uncached template id, a non-instanced destination world without `allow_shared: true`, and a
> tag already live in that space (the relog-restore case — re-firing a spawn chain is a no-op,
> not a second NPC). A `respawn_secs` param is accepted but **not honoured**: the respawn tick
> has no instance-lifetime awareness and a revived mission NPC would re-fire its
> `entity_dead_tag` chain, so content spawns are always one-shot.
>
> `despawn_entity` takes the tag in `target_key`. It and `destroy_entity` are now the same
> behaviour: both fan `LeftAoI` to every current witness and scrub the witness sets before
> destroying, via `SpaceManager::despawn_npc`. Before H03, `destroy_entity` called bare
> `destroy_entity`, which left the dead id in every observer's witness set — the client kept
> rendering a corpse-less ghost until an AoI tick happened to visit that player.
>
> `set_visible` now fans out over the target's witness list. Before H03 it addressed the
> target's own client, which for an NPC does not exist, so every seeded row was a silent no-op.
> Hide and show use different primitives (`BASEMSG_ENTITY_INVISIBLE` and `onVisible(1)`
> respectively), mirroring the engine's `leaveAoI` / `enterAoI`. The hidden state is **not**
> durable across an AoI re-entry — the create cascade always sends `onVisible(1)` — so a hide
> only holds for witnesses who stay in range.

The "dispatch-side gap list" the H99 entry mentions (`dialog_set_open` and `effect_*` never
fire) is unchanged by this packet.

## 8. Open questions

1. **Is the shared-world refusal the right default, or should `allow_shared` be inverted?**
   Shipped as refuse-by-default, matching the campaign rule in
   [work-packets.md](../work-packets.md) ("Shared-hub NPCs are never the target of
   `set_aggression`, `generate_threat`, `destroy_entity` or `set_visible`"). If a Harset packet
   legitimately needs a hub spawn, it sets the flag and the reviewer sees it in the diff.
2. **Should the idempotence guard match corpses?** Shipped as yes — a relog after the kill must
   not re-open completed content. The cost is that no chain can re-spawn the same tag within
   one instance lifetime; a wave-2 spawn needs a distinct tag anyway (gap 4).
3. **Gap 2 (durable hide) before or after H27?** H27's "hide the body" objective reads
   correctly today for a player who stays put, and wrong for one who walks away and back. If
   that is unacceptable at M4, the `CellEntity.hidden` bit needs its own packet against
   `crates/entity` + `mercury/aoi/`.

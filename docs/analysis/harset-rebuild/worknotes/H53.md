## The names another session will consume

- **Column:** `resources.worlds.navmesh_mode`, `character varying(16)`,
  `DEFAULT 'enforce' NOT NULL`, `CHECK (navmesh_mode IN ('enforce',
  'advisory'))`. Defined in `db/resources/Worlds/Tables/worlds.sql`, seeded in
  `db/resources/Worlds/Seed/worlds.sql`. World 57 (`Harset`) is the only row
  that names it; every other row takes the default.
- **Enum:** `cimmeria_services::cell::space_manager::NavmeshMode`, variants
  `Enforce` (`#[default]`) and `Advisory`, with `as_db_str()` and a
  case-sensitive `TryFrom<&str>`.
- **Predicate:**
  `pub fn SpaceManager::enforces_navmesh_containment(&self, space_id: u32) -> bool`
  — true only when a mesh is resident for that space **and** the space's world
  is `Enforce`.
- **Wrappers** (both `pub(crate)`, same decision expressed as an
  `Option<&NavMesh>` for call sites that already branch that way):
  `containment_navmesh(space_id)` and
  `containment_navmesh_for_world(world_name)`.
- **Mode lookup:** `pub fn SpaceManager::navmesh_mode(&self, world_name: &str)
  -> NavmeshMode`.
- **Loader:** `cell::spawner::load_world_rows(pool) -> HashMap<String,
  WorldRow>`, where `WorldRow { world_id: i32, navmesh_mode: NavmeshMode }`
  has a `WorldRow::enforcing(id)` fixture constructor.
- **Stamp:** `SpaceManager::stamp_world_rows(&HashMap<String, WorldRow>)`.
- **Startup summary:** `SpaceManager::log_navmesh_summary(&[SpawnRecord])`.

`load_world_ids` and `stamp_world_ids` no longer exist under those names. The
rename was deliberate — both now carry two columns, and keeping the old names
would have made "ids" a lie at the one seam where a world's id and its
movement gate must arrive together.

### Deliberately left alone

`SpaceManager::is_position_valid` still means "is this point on the mesh" and
still answers truthfully in an advisory world. That keeps every informational
consumer honest: `find_path`, `line_of_sight` / `has_line_of_sight`,
`get_navmesh_height`, `cell/service/npc_ai/wander.rs` validity, and the
`on_navmesh` fields in `cell/console/bookmark.rs` and `cell/spawner/npcs.rs`.
Bounds, speed and teleport are untouched — an advisory world still hard-rejects
NaN, out-of-AABB and teleport-sized moves, and there are guards for the last
two.

## The measurement

Probed with `NavMesh::is_point_valid` against the shipped
`data/spaces/harset.nav` (19,345 polygons) on 2026-09-19. At the plaza floor
band `Y = -68`, stepping X in 2-unit increments across `X -24..0`:

| Z | Coverage across X -24..0 |
|---|---|
| -190 to -198 | full |
| **-200 to -228** | **none** |
| -230 to -236 | a strip at X -18..-10 only |

That is the packet's stated 30-unit hole, confirmed by the real Detour query
rather than by vertex proximity. Two notes for whoever rebakes it:

- The packet's fixture Y of `-58.65` is the *sentry spawn* height, and every
  point in that corridor is off-mesh at that Y, in both directions. There are
  two distinct floors here: one around `Y -41` (covered continuously through
  the corridor) and one around `Y -68/-71` (the plaza floor, with the hole).
  `-58.65` sits between them, outside the vertical tolerance of both, which is
  the H51 finding about the nine inert sentries seen from a different angle.
  The tests use `Y -68` because the ring pads sit at `-67.828` and chain
  6007's door coordinate at `-67.6`, so that band is demonstrably where
  players stand.
- `NavMesh::get_nearest_point` returns its input unchanged on a miss. Every
  one of the four probe seeds came back identical to the input with
  `is_point_valid == false`, which is the documented `unwrap_or(*pos)`
  behaviour in `crates/entity/src/navigation/mod.rs`. Do not use it as a
  "how far off-mesh is this" measure.

## Tests

14 new guards, all within `cimmeria-services`:

| File | Count | Kind |
|---|---|---|
| `cell/space_manager/tests/movement_validation/advisory.rs` | 6 | Unit, against the real `harset.nav` |
| `cell/space_manager/navmesh_mode.rs` (`mod tests`) | 5 | Unit (parse, fallback direction, predicate truth table) |
| `cell/arrival.rs` (`mod tests`) | 1 | Unit, against the real `harset.nav` |
| `cell/spawner/worlds.rs` (`mod live_db_tests`) | 2 | Live-DB, against the real seed |

Every real-mesh test asserts three controls before any verdict: ring pad 4
(`-25.641, -67.828, 15.249`) reads on-mesh (so the mesh loaded and was
injected), the start point reads on-mesh, and the target point reads off-mesh.
Without the first, the advisory half would pass just as well against a mesh
that failed to load.

**Revert verification.** `enforces_navmesh_containment` was temporarily
rewritten to `space.navmesh.is_some()` — the "mesh loaded" behaviour the
packet names — and the suite re-run. Four failed:

- `advisory::a_step_into_a_mesh_hole_is_accepted_in_an_advisory_world`
- `advisory::a_player_standing_in_a_hole_is_corrected_back_not_relocated`
- `arrival::an_advisory_destination_is_unvalidated_not_off_mesh`
- `navmesh_mode::containment_needs_both_a_mesh_and_the_enforce_mode`

The four enforce-side controls (`the_same_step_is_rejected_off_navmesh...`,
the out-of-bounds guard, the teleport guard, the GM guard) stayed green, which
is the right shape: the weakening is invisible to them by construction. The
predicate was then restored and the suite re-run clean.

The two live-DB tests cannot be revert-proven by weakening the predicate —
they read the seed, not the code. They are proven by the seed itself: deleting
`'advisory'` from the world-57 INSERT makes
`harset_loads_advisory_and_a_meshed_neighbour_loads_enforce` fail on the
Harset assertion, and adding a second advisory row makes
`exactly_one_world_is_seeded_advisory` fail on the list comparison. The two
assert opposite directions on purpose: "Harset is advisory" alone would pass
against a loader that hardcoded advisory for every world, which would drop
containment server-wide with one green test.

## Findings and judgement calls

**1. The gate-arrival behaviour change goes further than the snap-back, and
the coordinator should see it.** Routing `check_arrival` means a Castle →
Harset gate crossing is no longer *refused*. Before H53 the traveller stayed
in Castle with an `arrival_unrecoverable_off_mesh` warning; now the
destination is `Unvalidated` and they arrive on gate 3's authored coordinate,
which nobody has ever stood on. They can walk away from it — that is the whole
point — but it could still be inside geometry or above a drop. This is what
the packet asked for ("H01 stops refusing or redirecting arrivals at Harset's
unpinned-but-real floor") and it is the right trade, but it is a visible
change to a path the operator guide documented, so rows C4.2/C4.2a were
rewritten rather than left. M0 closes the residual risk.

**2. Chain 6007's guard was re-read, not relaxed.** The validator is no longer
the objection. What remains is that `(0, -67.6, -231)` came out of a prop
transform and nobody has stood on it, and off-mesh is the only automated proxy
the repo has for "unverified". The biconditional is unchanged; both assertion
messages and both doc comments now say *why*, and add the case the next editor
will hit: if M0 pins a verified point the mesh still does not cover (entirely
possible on an advisory world), replace the guard with one that records the
in-game verification rather than relaxing it.

**3. `mode_from_db_value` fails closed; the runtime predicate fails open.**
These look contradictory and are not. An unparseable column value is a data
defect and must not silently demote a gate, so it reads `Enforce`. A world
that reaches the runtime predicate with no mesh has nothing to enforce, so it
reads `false`. Both are documented at their definitions because the pairing is
the sort of thing a later reader "fixes".

**4. The advisory TRACE is level-gated on purpose.** In an advisory world,
logging which positions are off-mesh needs a Detour query per inbound position
packet per player. The branch is guarded by
`tracing::enabled!(target: "movement.navmesh", Level::TRACE)` *before* the
query, so it costs nothing in production. With the level on it is the only
record of which parts of a mesh real players actually walk through, which is a
better rebake input than a static probe.

**5. The shared `space_manager` test fixture is load-bearing, and it cost a
round trip.** The first cut added a non-instanced Harset world to
`TEST_SPACES_XML` / `TEST_CELL_SPACES_XML` in
`crates/services/src/cell/space_manager/tests/mod.rs`. Four tests in that
module pin `space_count()` and the exact `(cell_id << 16) | index` startup
space ids, so one extra startup world broke all four
(`parse_spaces_xml_loads_all_worlds`, `startup_spaces_get_correct_ids`,
`instanced_space_created_on_demand`, `create_entity_in_instanced_space`) —
and none of them are in any filter a Harset-shaped test run would use, so it
only surfaced on the full suite. The advisory tests now build their own
one-world manager. Anyone adding a world to that fixture should expect the
same. A related one: `cell::arrival::test_insert_navmesh_space` grafted a
space and a `world_spaces` entry but no `WorldDef`, so `stamp_world_rows`
(which walks `self.worlds`) silently could not reach it — fixed there, and
worth remembering if another per-world field is ever added.

**6. Pre-existing naming drift, not introduced here.**
`client_move.rs` calls the navmesh gate "Layer 4" while
`docs/architecture/movement-validation.md`'s execution-order table numbers it
2 (bounds, navmesh, speed, teleport — which is the order the code actually
runs). The new ADR sidesteps it by saying "the navmesh containment layer".
Worth one small PR by whoever owns that ADR; out of scope here.

**7. File sizes.** `client_move.rs` is 626 lines and `arrival.rs` is 657,
both inside CLAUDE.md's 500-line soft / 700-line hard band and both already in
that band before this packet. Each has one obvious seam (lift the `mod tests`
into `arrival/tests.rs`), and I left both whole: five Harset sessions are
editing these files concurrently and a file-to-directory move would collide
with all of them for no behavioural gain. Worth doing in a quiet moment.

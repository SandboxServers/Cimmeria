## What shipped

A seventh authorable condition, `world`, gating a chain on the acting player's world.

**Authoring shape** (`resources.content_conditions`):

| column | value |
|---|---|
| `condition_type` | `'world'` |
| `target_id` | `resources.worlds.world_id` (Harset 57, Harset_CmdCenter 68, Harset_Market 69, Harset_StorageRm 70) |
| `operator` | `'eq'` or `'neq'` |
| `target_key`, `value` | unused (NULL) |

`target_id` follows the `stat_below_max` precedent (a foreign key in the typed integer column) rather than `archetype` (an id parsed out of the `value` text). A world id is an FK to `resources.worlds`, so a bad value fails at insert instead of being silently dropped by `.parse().ok()?`.

The optional `world_name` string alternative the packet allowed was **left out**, on the mission-systems advisor's recommendation. The trigger layer already owns the name-keyed form (`OnPlayerLoaded { world_name }`), so adding a second name-keyed spelling would leave an author choosing between three ways to write one gate; and `SpaceManager::canonical_world_name` exists precisely because exact-case world-name matching has bitten this project before.

## Behaviour, and the three judgment calls

**1. Typed field, not a params key.** `ExecutionContext.space_id` is a runtime space *instance* handle (`(cell_id << 16) | local_index`) and several live instances of one world share a world id, so nothing downstream can re-derive the world from the context. A typed field also distinguishes "nobody populated it" from "populated with 0", which a `params` key read through `unwrap_or` cannot.

**2. Fail-closed for every operator, including `neq`.** An unset `world_id` evaluates `false` and logs at `debug`. This is deliberately *not* the engine's uniform rule — `MissionStatus`/`StepStatus`/`ObjectiveStatus` fall back to `"not_active"` and can therefore fail **open**; only `StatBelowMax` fails closed. Joining the minority is correct here: a chain that fires in the wrong world is the exact defect the condition exists to prevent, and the ergonomic cost ("anywhere but Harset" is dead on an unpopulated path) only bites on a wiring regression, which is when you want the chain dead.

**3. An ordered operator is kept, not rejected — overriding the advisor.** The mission-systems advisor recommended returning `None` from the loader for `gte`/`lt`/…, on the grounds that the loader's "Unknown condition_type" warn is louder than a condition that never matches. Overridden after reading `build_chains_from_rows`: a row whose conversion returns `None` is dropped **and the chain is kept**, so a chain whose only condition is a typo'd `world` row would load *ungated* and fire in every world. That is strictly worse than never matching. The row is kept (so the chain stays gated), the evaluator answers `false` for ordered operators, and the loader warns. Pinned by `convert_world_condition_keeps_ordered_operator_so_the_chain_stays_gated`.

**Where the id comes from.** `entities/spaces.xml` carries world *names* only; the numeric id exists solely in `resources.worlds`. Five cell-side loaders (spawns, stargates, respawners, regions, ring transport) already JOIN that table and throw the id away. Rather than a parallel `HashMap<String, i32>`, the id is stamped onto the existing `WorldDef` — `self.worlds` is already the canonical keyed-by-world-name table, and a second map keyed identically would be free to drift.

**`fire_player_loaded` resolves its caller-supplied world.** This site takes the world name as an argument and can fire before the player's entity is in a space, where the entity→space→world resolution yields nothing. Two consequences, both handled: the populator's space-derived `world_name` (which degrades to `"Unknown"`) must not overwrite the caller's — so the explicit `set_param` sits *below* the populator call — and `ctx.world_id` falls back to `space_mgr.world_id_for_world(world_name)`. Without that fallback a `world`-gated `player_loaded` chain, one of the two shapes this packet exists for, would fail closed on every arrival.

## Gaps

- **The seed rows are not written.** There are zero `condition_type='world'` rows in `db/resources/Content/Seed/`; the tests use sentinel chains. Authoring the Harset door chains belongs to the chain packets.
- **16 of the 17 dispatch sites have no test proving they populate.** `fire_enter_region` and `fire_player_loaded` are guarded; the rest rest on the shared populator's own tests. See integration request 2.
- **`world_name` and `world_id` can still disagree** at any *other* site that takes a world from its caller. Only `fire_player_loaded` does today.

## Advisor and test-review findings

**mission-systems-advisor** (one round, pre-implementation):

- Corrected the packet's premise: `player_loaded` chains **can** already be world-scoped via `OnPlayerLoaded { world_name }` from `content_triggers.event_key`. H-B10's real cause is 28 Cellblock chains with `event_key = NULL`, which the matcher treats as a wildcard — not a missing condition. **This packet is not the H-B10 remedy**; it is the primitive that prevents the next one.
- Confirmed the typed field, the fail-closed `neq`, `target_id` over `value`, and dropping the `world_name` form. Recommended reject-at-load for ordered operators; overridden, see above.
- Confirmed no cell-side world-name → id map exists (checked stargates, respawners, regions, npcs, ring transport) and that `SpaceManager` is the right owner, but preferred stamping `WorldDef` over a parallel map. Adopted.
- Noted that for the Harset doors specifically, world-qualifying the two new `point_sets.name` values (`Harset.CommandCenterTransition` / `Harset_CmdCenter.CommandCenterTransition`) costs no code at all. The condition is defence in depth against an author who reuses a bare name, not a substitute for that naming discipline. **Worth passing to whoever authors those point sets.**

**testing-validation-engineer** (one round, post-diff). Five findings, all fixed before the commit:

1. `world_ordered_operators_never_match` was half tautology — the fixture only compared 68 against 57, where `Lt`/`Lte` answer `false` under a numeric fall-through anyway. Now every operator runs against worlds on both sides of the authored id.
2. `convert_world_condition_requires_target_id` passed identically with the `"world"` arm deleted (`_ => None` gives the same answer). Now asserts a positive conversion in the same test as a control.
3. `populate_world_context_sets_world_id_not_space_id` carried an `assert_ne!` that could never fail (the first space id is 65536, never 57). Assertion dropped, test renamed to what it actually checks.
4. `fire_player_loaded`'s guard used `.any(matches!(GrantXP))`, which passes if the chain fires twice or if some unrelated chain fires. Now asserts an exact sorted vector of two distinctive amounts.
5. **Both chain-replay tests shared sentinel chain id `0x7007_0000`.** Under plain `cargo test` (unlike the serialised `ci-live-db` nextest profile) one test's opening cleanup can delete the other's rows mid-load, surfacing as a failure that reads exactly like a missing loader arm. Split into `0x7007_0000` / `0x7007_0001`, threaded through the seed/cleanup/load helpers.

It also identified the `fire_player_loaded` `world_id` gap as a probable production bug rather than a coverage gap; that is the `world_id_for_world` fallback described above, and it is now guarded.

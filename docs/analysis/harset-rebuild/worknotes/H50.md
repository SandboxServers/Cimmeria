## The defect, in three halves

`populate_mission_context` was never the problem. It already had both
loops — one over `active_objectives`, one over `completed_objectives` —
so `mission_<m>_obj_<o>_status` was emitted correctly for whatever the
instance held. The instance just held nothing useful after a relog,
because all three of these were broken at once:

| # | Where | Was |
|---|---|---|
| 1 | every executor arm | `active_objective_ids: vec![step_id]` on accept and `advance_step`; both arrays empty on `complete` |
| 2 | `Action::CompleteObjective` | sent the `onObjectiveUpdate` wire frame and **no** `MissionUpdate` at all |
| 3 | `player_init` hydration | roster taken from the saved array, `hidden: false, optional: false` hardcoded |

Fixing any one alone changes nothing observable, which is why this sat
latent long enough to become a playtest finding. Each half now has its
own revert proof (below).

## What the WIP got right

Most of it. The previous worker's design decisions all survived review:

- **One serializer** (`cell/missions/persist.rs`) read back from the live
  instance *after* the mutation, rather than each arm hand-rolling the
  message. The emitted row cannot disagree with cell state, and the
  auto-complete branch inside `complete_objective` persists its own
  post-transition status and bumped `repeats` for free.
- **`complete_objective` returns `bool`** so the executor can skip the
  persist on a no-op. This is load-bearing for test integrity, not
  cleanliness: if a no-op persisted, a dead executor arm and a live one
  would produce identical DB traffic and no guard could tell them apart.
- **Def-driven hydration** (see the decision below).
- **Firing `mission_completed` from the auto-complete branch.** Before
  persistence existed, a mission that ended via its last required
  objective silently skipped the follow-up event. Harmless while nothing
  was saved; player-bricking once the row says "completed" but the
  follow-on chains never ran.
- The union-with-dedup in `completed_objective_ids`.

## What the WIP got wrong

1. **It did not compile cleanly and was never run.** One `unused_mut`, and
   it had never been through `cargo fmt`.
2. **Two halves of it contradicted each other.** It added a contains-guard
   to `MissionInstance::complete_objective` *and* a unit test
   (`duplicate_completions_are_deduped`) whose precondition asserted that
   the same function still pushes duplicates. That test failed on first
   run. Rewritten as `an_objective_in_both_sources_is_written_once`, which
   pins the half that is actually still reachable: the same id arriving at
   the serializer from `completed_objectives` *and* from an
   `active_objectives` entry already flipped to `STATUS_COMPLETED`.
3. **It shipped no end-to-end guard.** Every test it added was a unit test
   over a hand-built fixture. The defect it was fixing had survived
   precisely because the existing pin hand-built its fixture too, so
   more of the same would not have caught a regression.

## Decision: `hidden` and `optional` come from the mission defs

**Ruled: the step definition (`resources.mission_objectives`, via the
`step_objectives` cache), not the saved row.**

The packet allowed the saved row "if it is the only place a runtime
reveal is recorded". It is not. A repo-wide search for writes to
`MissionObjective::hidden` / `::optional` finds exactly two producers —
`progression::advance_step` and `executor::mission::accept_or_advance` —
and both copy straight from `MissionObjectiveDef`. Nothing reveals a
hidden objective at runtime, and `sgw_mission` has no column for it. The
flags are a property of the mission design, not of the player's progress,
so the seed stays the single source of truth and the schema is unchanged.

**The same reasoning extends to the roster itself, and that turned out to
matter more than the flags.** Hydration reconstructs the current step's
objective list from the step definition and uses the saved arrays purely
as a status overlay (an id in `completed_objective_ids` comes back
`STATUS_COMPLETED`, everything else `STATUS_ACTIVE`). Two consequences:

- **It self-heals.** Every `sgw_mission` row written before this change
  holds the *step* id in `active_objective_ids`. Hydrating that verbatim
  would produce a required, `STATUS_ACTIVE` pseudo-objective that no
  `complete_objective` can ever match, so `all_required_complete` would
  be false forever and the mission permanently stuck. The repo does no DB
  migrations, so hydration is the only lever available.
- **This is the "server restart left all three bug baskets dark for
  everyone" case** the lane recorded. The restart re-read rows whose
  objective array was `[2504]`; every basket chain is gated
  `objective_status 742 29xx eq active`, which `Condition::ObjectiveStatus`
  answered from its `unwrap_or("not_active")` fallback. Guarded by
  `a_pre_h50_row_holding_the_step_id_self_heals_on_login`.

There is a deliberate fallback: if the step is not in the cache (unseeded
step, or a completed row whose `current_step_id` is NULL) the saved array
is used verbatim with `(false, false)`, so an unseeded mission degrades
rather than losing its roster. It warns when it does.

## Correction to the packet's 1200 claim

The dispatch said a relogged player on step 3585 who then talks to Ba'al
"would COMPLETE THE MISSION EARLY". **That is the wrong direction**, and
it is worth recording because the fix is the same either way but the
guard is not.

Mission 1200 step 3585 is objective 4140 (required) plus 5399 (`is_hidden
= t, is_optional = t`). With `optional` forced to `false` at hydration,
5399 comes back *required*. `all_required_complete` then waits on it, so
the failure is that the mission **hangs**: a player who skips Ba'al
completes 4140 and 1200 never finishes. Completing 5399 alone never
completed the mission in either version, because 4140 is still open.

Both directions are now guarded, because only one of them is
revert-sensitive and the other documents intent:

- `optional_and_hidden_flags_survive_a_relog` — the still-open optional
  must not block completion once 4140 is done. **Fails when reverted.**
- `completing_only_the_optional_objective_does_not_complete_the_mission` —
  taking Ba'al's advice must not end the mission. Passes either way;
  kept so the fix cannot later be "simplified" into actually causing the
  early completion the packet feared.

## Decision: the status byte is NOT a bug

The packet flagged a note in agent memory saying `complete_objective`'s
auto-complete sends the wrong status byte on `onMissionUpdate`. **That
note is stale and has been corrected in memory.**

There are two enums and they are not interchangeable:

| Enum | Values | Lives |
|---|---|---|
| `MISSION_*` | 0 not_active, 1 active, 2 completed, 3 failed | `MissionInstance.status`, `sgw_mission.status` — server-side only |
| `STATUS_*` | 0 active, 1 completed | the wire |

`onMissionUpdate` carries the two-value `STATUS_*` enum, consistently
across all five emitters: `accept_mission` (0), `abandon_mission` (1),
`serialize_resend` (0), `complete_mission_direct` (1) and the
auto-complete branch (1). `MISSION_ACTIVE` and `STATUS_COMPLETED` are
both `1`, so the wire was always right while the source named the wrong
constant; the base already corrected the name and left the comment
explaining it. Nothing to fix, and a future reader "fixing" it to
`MISSION_COMPLETED` (2) would break the client. The `MissionUpdate`
persist message correctly uses `mission.status`, the `MISSION_*` value —
a different field, not the wire byte.

## Adjacent finding: `all_required_complete` is vacuously true on an all-optional step

`all_required_complete` is `.all()` over a filter, so a step with **no**
required objectives returns `true` and the first completion of any
objective on it ends the mission. **37 seeded steps have that shape**
(e.g. 333, 491, 553, 875, 3429, 4490, 4612, 4962).

**Decided out of scope, logged not changed.** This is pre-existing on the
fresh path — `advance_step` has always loaded the real `is_optional` from
the seed — so it is not introduced here. But it was previously
*unreachable* on the restore path, where the flags were forced to
`false`, and this change makes it reachable there too. Matching the fresh
path is the defensible behaviour and changing the semantics is outside
the packet, so `complete_objective` now emits a `warn!` naming the
mission, step and objective when it auto-completes with
`required_count == 0`. **Coordinator: this is the one behaviour change
here that could surprise a UAT session**, and none of the 37 steps belong
to a mission this campaign has authored.

## The respawn-resend seam

Playtest finding H8 (2026-09-18): a same-world respawn recreates the
client pawn and the mission log is never re-sent, so the log is broken
for the rest of the session. **Re-sending on respawn is not in this
packet and was not done.**

No new seam was needed — the right one already exists and this change
kept it out of `player_init`:

```rust
cell::missions::resend_missions(entity_id, tx, space_mgr)
```

A free function taking the entity, the outbox and the space manager,
called from `player_init` at one site, with no `player_init` state in its
signature. **A respawn caller needs nothing but those three arguments**,
and must call it *after* the pawn exists client-side. Two caveats for
whoever writes that caller:

- `MissionManager::serialize_resend` filters on `active_missions()`, so
  hidden and completed missions are correctly skipped. `is_hidden` is
  restored per instance from `mission_defs` at hydration, so a respawn
  resend after a relog behaves the same as one in the login session.
- It emits three frames per mission (`onMissionUpdate`, `onStepUpdate`,
  one `onObjectiveUpdate` per objective). It is not idempotent on the
  client's side in the sense of being free; a respawn caller should fire
  it once per pawn recreation, not per tick.

## Headline finding: all three abilities the packet named are unusable

The packet text says to give set 4 "1482 Ground Blast, 1768 Double Blast
alongside 594 Strike". **None of the three qualifies**, and the reason is
structural rather than per-ability.

H11 established the membership rule: an ability needs a non-NULL
`event_set_id`, because that column gates the entire Ability_Begin /
Ability_End `onSequence` broadcast
(`crates/services/src/cell/abilities/use_ability/handle.rs:524`). An ability
without one deals damage and plays no animation at all.

| id | name | `event_set_id` | `is_ranged` | `max_range` | `items_event_sets` bindings | verdict |
|---|---|---|---|---|---|---|
| 594 | Strike | **NULL** | f | 0 | **0** | rejected — no animation; also generic melee bound to no weapon |
| 1482 | Ground Blast | **NULL** | t | **3000** | **0** | rejected — no animation; `max_range = 3000` also poisons `ability_ranges`, so the NPC stops closing distance on whatever tick it is selected |
| 1768 | Double Blast | **NULL** | t | 0 | **0** | rejected — no animation |
| 479 | Staff Blast | NULL | t | 0 | 0 | rejected — no animation |
| 540 | Staff Strike | NULL | f | 0 | 0 | rejected — no animation |

The structural part: **only 35 of the 1,886 rows in `resources.abilities`
have a non-NULL `event_set_id`, and every one of the 35 is an auto-attack or a
melee auto-attack.** There is no animatable "special" staff or ribbon ability
anywhere in the seed. A variety set built out of Ground Blast / Double Blast /
Staff Blast is not something this packet declined to build — it is not
expressible in the shipped data.

What the data *does* express is a pair. `resources.items_event_sets` binds
every weapon to exactly two abilities, `EVENT_ITEM_RANGED = 7` and
`EVENT_ITEM_MELEE = 6`:

- **staff** — 204 distinct staff items, all binding 584 (ranged) + 710 (melee)
- **ribbon device** — 151 distinct items, all binding 712 (ranged) + 711 (melee)

So the honest full list for each set is two rows, not three. The three-row
acceptance case is exercised by a test-local sentinel set instead; see
[Guards](#guards).

### Two consequences worth stating plainly

**1. Melee at 30m.** `ability_ranges`
(`cell/service/npc_ai/ability_select.rs`) returns `NPC_ATTACK_RANGE` (30)
whenever the def's `max_range` is the `0` sentinel, which is true for every
ability in the seed except 1482 (3000) and 1949 (2500). It does not
distinguish melee from ranged. So a Jaffa that picks 710 on a tick plays a
staff-swing animation at up to 30 metres.

This is **not a new artefact.** The python selector never range-gated ability
choice either — `deprecated/python/cell/SGWMob.py` `classifyHostileAbility`
filters on hostile type, `TCM_Single`, cooldown and ammo, and then carries the
literal comment `# TODO: Check distance, LOS` (line 227) before returning
`ABILITY_Usable`. Cimmeria's fight tick is strictly *more* conservative than
the original (it gates `in_range` on the chosen ability's `max_range`,
`npc_ai/fight.rs:229-240`), but with `max_range = 0` everywhere that gate is a
no-op. Shipping 710/711 reproduces original behaviour; fixing the range model
is a chooser change and out of scope.

**2. Attack rate roughly doubles for sets 4 and 5.** There is no GCD — only
the per-ability cooldown is started (`handle.rs:399-406`) — and the AI tick
runs every ~2s. One 3s ability fires on alternate ticks (~1 attack / 4s); 584
(3s) + 710 (2s) leaves something off-cooldown nearly every tick (~1 attack /
2s). Same for the ribbon pair. The 1x rate was an artefact of the primary-key
bug, not a tuning decision anyone made, so this is accepted rather than
compensated for. Flagged for M1 UAT.

**3. Set 5 is melee-first.** `choose_npc_ability` sorts ascending and takes the
first off-cooldown id, so 711 (melee) is the ribbon NPC's *primary* and 712
(ranged) is the fallback — the inverse of set 4. This is cosmetically inert
(711 and 712 share `event_set_id = 300`, so they emit the same `onSequence`),
but 711 is `is_ranged = false`, so most ribbon attacks roll against melee
rather than ranged defence in `calculate_qr`
(`abilities/damage_apply/mod.rs:92-93`). Recorded, not fixed — reordering is a
chooser change.

## What changed

### Schema — the packet names the wrong file

The packet's entry list and owned-paths list both name
`db/resources/Abilities/Tables/ability_set_abilities.sql` as the file holding
`PRIMARY KEY (ability_set_id)`. **It does not.** That file is a bare
`CREATE TABLE` with two `NOT NULL` columns and no constraint of any kind.
Every primary key in the resources schema lives in
`db/resources/_primary_keys.sql`, and inlining this one would have been the
only deviation in the tree.

The widen therefore landed in `db/resources/_primary_keys.sql`. The `Tables/`
file gets a six-line comment pointing at where the key actually lives, so the
next reader who follows the packet's owned-path list to that file does not
find an empty hole. Recorded as a correction to the packet text.

`db/database.sql` ordering, verified: DDL at line 190, `_primary_keys.sql` at
264, the seed at 273, `_foreign_keys.sql` at 348. Primary keys before seed is
exactly why a second row aborted a fresh load.

### Nothing references the key

Both foreign keys naming `ability_set_abilities` are **outbound** — it is the
child in both (`ability_id → abilities`, `ability_set_id → ability_sets`,
`_foreign_keys.sql:29,37`), and `entity_templates_ability_set_id_fkey`
already targets `ability_sets`, the parent table. So `DROP CONSTRAINT` is not
blocked and nothing cascades. No additional index was added: `ability_set_id`
is the leading column of the composite key, so the three production
subqueries' `WHERE asa.ability_set_id = …` is a prefix scan and `ability_id`
as the second column makes the index covering and already in
`ORDER BY ability_id` order.

### Rust — no chooser change was needed

Both advisors independently confirmed the Rust side was already multi-row
ready, which is what H11's integration request 2 predicted:

- All three ability-set loaders use the same correlated
  `array_agg(asa.ability_id ORDER BY asa.ability_id)` subquery —
  `cell/spawner/npcs.rs:151`, `cell/spawner/templates.rs:92`,
  `base/gm_spawn.rs:183`.
- `spawn_npc_from_record_into` (`cell/space_manager/spawn.rs:241-249`) already
  loops `record.ability_ids` and only falls back to `NPC_DEFAULT_ABILITY` when
  the bucket is empty.
- `choose_npc_ability` (`cell/service/npc_ai/ability_select.rs`) sorts the
  known ids and `find`s the first off-cooldown one — it walks N.

So the only Rust edits are **visibility widenings plus documentation**, no
behaviour change:

| File | Change |
|---|---|
| `cell/service/npc_ai/ability_select.rs` | `choose_npc_ability` from `pub(in crate::cell::service)` to `pub(in crate::cell)`; added a `# Multi-ability sets` doc section explaining that ascending-id order makes the lowest id the primary and the rest cooldown fallbacks. |
| `cell/service/npc_ai/mod.rs` | the `#[cfg(test)]` re-export from `pub(super)` to `pub(in crate::cell)`. |
| `cell/service/mod.rs` | `mod npc_ai;` → `pub(in crate::cell) mod npc_ai;`. **Outside the packet's owned paths** — see [Integration requests](#integration-requests). |

All three exist so the live-DB guard in `cell/spawner/tests/harset/` can name
`choose_npc_ability`. `npc_ai` is a private module inside a private `service`

## Guards

Live-DB guards (TESTING.md type 3), all `require_db_or_skip!`, in
`crates/services/src/cell/spawner/tests/harset/`.

### New

| Test | What it pins |
|---|---|
| `ability_set_primary_key_is_the_composite_pair` | `pg_get_constraintdef` is `PRIMARY KEY (ability_set_id, ability_id)`; set 4 holds two distinct abilities (the **accept** half); re-inserting `(4, 710)` fails with SQLSTATE **`23505`** on constraint **`ability_set_abilities_pkey`** (the **reject** half); the count is still 2 afterwards. |
| `multi_ability_set_reaches_the_chooser_and_every_member_is_selectable` | A three-row sentinel set survives `ability_set_abilities` → `load_spawn_templates`'s `array_agg` → `SpawnRecord.ability_ids` → `spawn_npc_from_record` → the NPC's bucket → `choose_npc_ability`, and the selector reaches **every** member as cooldowns stack, then returns `None` when all three cool. |

Two deliberate choices in the reject probe, both from the
`database-persistence` round. The assertion is on the SQLSTATE and the
constraint *name*, not a bare `is_err()` — `is_err()` would also pass on a
`23503` FK violation, which would make the test pass for a reason unrelated to
the key. And nothing is cleaned up because nothing is written: the duplicate
INSERT fails, and each `sqlx` statement against `&PgPool` runs in its own
implicit transaction, so the rejection poisons no later statement. (The probe
must *not* be wrapped in `pool.begin()` — inside an explicit transaction every
following statement would fail `25P02`.)

Three choices in the sentinel test:

- **A sentinel set, not set 4 padded to three rows.** Padding a production set
  would put a third ability on every live Harset Jaffa and change their attack
  rate a second time.
- **Rows inserted out of ascending order (712, 584, 710).** Inserting them
  ascending would let the test pass even if someone deleted the
  `sort_unstable()` in `choose_npc_ability`, because physical row order would
  already be the answer. This is the difference between a guard and a
  happy-path test.
- **Real ability ids (584/710/712), not invented sentinels.**
  `ability_set_abilities_ability_id_fkey` is `ON DELETE/UPDATE RESTRICT`, so
  unlike `SENTINEL_SPAWN_ID` an ability id cannot be conjured. The sentinel
  *set* id (`0x7000_6200`) and *template* id (`0x7000_6300`) reference nothing
  and are free. Cleanup deletes by exact id, child-before-parent (template,
  then `ability_set_abilities`, then `ability_sets`), and runs before the
  inserts too so an aborted run cannot wedge the next one. Insert → load →
  delete → assert, so a failing assertion cannot leak rows.

### Statements applied by hand to `sgw_harset`

Wrapped in an explicit transaction on the `database-persistence` round —
`DROP CONSTRAINT` and `ADD CONSTRAINT` as separate autocommit statements can
half-apply and leave the shared DB with **no primary key at all** if the
second fails.

```sql
BEGIN;

SET LOCAL lock_timeout = '5s';

ALTER TABLE resources.ability_set_abilities
    DROP CONSTRAINT IF EXISTS ability_set_abilities_pkey;

ALTER TABLE resources.ability_set_abilities
    ADD CONSTRAINT ability_set_abilities_pkey
    PRIMARY KEY (ability_set_id, ability_id);

INSERT INTO resources.ability_set_abilities (ability_set_id, ability_id)
VALUES (4, 710), (5, 711);

COMMIT;
```

`lock_timeout` so an `ACCESS EXCLUSIVE` request fails fast instead of queueing
behind another packet's open transaction on the shared DB. `IF EXISTS` makes a
re-run safe; no `ON CONFLICT DO NOTHING` on the INSERT, because if those rows
are already present that should be visible, not silently absorbed.

Result: `BEGIN / SET / ALTER TABLE / ALTER TABLE / INSERT 0 2 / COMMIT`,
exit 0. Post-state: `PRIMARY KEY (ability_set_id, ability_id)`; sets 1/2/3
unchanged at `{579} / {221} / {559}`, set 4 `{584,710}`, set 5 `{711,712}`.

### Revert proof

`h09_revert.sql` restores the exact pre-H09 database state: it deletes rows
`(4, 710)` and `(5, 711)` and then narrows the key back to `(ability_set_id)`.
**Statement order is load-bearing** — narrowing first would fail on the very
duplicates it is meant to forbid and roll the transaction back, leaving a
state that is not pre-H09 and a proof that means nothing.

```text
##### 3. BASELINE
     Summary [   2.484s] 13 tests run: 13 passed, 2140 skipped
ok: no self-skip line in baseline

##### 4. REVERT (drop the H09 rows, narrow the key back)
     Summary [   0.889s] 13 tests run: 9 passed, 4 failed, 2140 skipped

##### 5. RESTORE
     Summary [   1.399s] 13 tests run: 13 passed, 2140 skipped
```

## Integration requests

1. **`choose_npc_ability` needs python's pre-filter.** The original rejected
   `ABILITY_TYPE_Heal`, `ABILITY_TYPE_Buff`, `ABILITY_TYPE_Undefined` and
   anything whose `targetCollectionMethod != TCM_Single` *before* the
   three-bucket partition. Cimmeria's selector takes the lowest off-cooldown
   id unconditionally. Inert today because every NPC set holds only
   single-target hostile auto-attacks — but H09 is the packet that makes
   multi-ability sets possible, so the first content author who drops a
   self-buff or an AoE into a mob set will have it fired at the player as an
   attack. Owner: whoever owns `cell/service/npc_ai/`.
2. **Remove or rename `AbilityManager::first_known_ability()`**
   (`crates/entity/src/abilities/manager.rs:140-143`). It returns
   `self.known_abilities.iter().next()` over a `HashSet`, so the result is
   arbitrary and unstable across runs, and its doc comment recommends it "for
   NPCs using their default attack" — exactly the use case that is now wrong.
   Zero production callers today (tests only), so this is a cheap cleanup
   before someone takes the doc comment at its word.
3. **`decision_outcome = "no_ability"` log text is inaccurate.**
   `npc_ai/fight.rs:476` says "all cooling or needs-ammo", but Rust has no
   needs-ammo bucket and no NPC reload path. One-line message fix.
4. **Confirm the ranged+melee pairing against mob evidence.** The pairing is
   reconstructed from `items_event_sets`, which is the *player* weapon-binding
   table. It is well-motivated (the `EntityTemplate` moniker loop proves sets
   held weapon-bound abilities) but not proven for mobs. A mob-combat pcap or
   a finding in `docs/reverse-engineering/findings/weapon-ammo-pipeline.md`
   would settle whether a 2009 mob set held both halves. Not blocking.
5. **`crates/services/src/cell/service/mod.rs` is outside this packet's owned
   paths** and carries a one-token change (`mod npc_ai;` →
   `pub(in crate::cell) mod npc_ai;`). It is required for the loader-to-chooser
   guard to compile, is documented in place, and grants nothing outside
   `crate::cell`. Flagging for the coordinator rather than assuming consent.
   If it is vetoed, the alternative is to move
   `multi_ability_set_reaches_the_chooser_and_every_member_is_selectable` into
   `cell/service/tests/npc_ai/selector.rs` — which is also outside the owned
   list, and pulls live-DB and seed knowledge into a module that is otherwise
   pure in-memory fixtures.
6. **Event set 300 is shared** by staff-melee (710), ribbon-melee (711) and
   ribbon-ranged (712). Three weapon-specific animations would not normally
   share one event set; this smells like a generic fallback. Worth a look from
   whoever owns the sequence tables — it may mean ribbon NPCs have no
   distinct ranged animation at all.
7. **H11's worknote needs a correction breadcrumb.** Its integration request 2
   ("widen `ability_set_abilities_pkey`") is now done, and its statement that
   "no NPC can have more than one ability" is stale. Not edited here — H11.md
   is another packet's worknote.

## The defect

`enter_region` is an edge. The client reports one crossing; if the chain's
gate is not yet true the edge is spent and nothing re-delivers it. Castle
lost objective 2484 to exactly that ordering (`no chains matched` at
7:05:45.79, step 2144 activates at 7:05:46.97, the next real crossing at
7:07:15.79). The Harset lanes then found the same shape four more times —
742's offer, 1326's offer, 1361's offer, the 1360 letter hand-back — and
closed each in seed with a second `mission_completed` trigger. That idiom
works when the gate opens on a *completion*. It cannot work when the gate
opens because a step activated with the player already standing in the
volume, which is the 1343 patrol's whole shape: the first leg is handed out
inside the Jaffa Zone.

## The three hazards, and how each is answered

### (a) Re-entrancy — **bounded by a guard on `SpaceManager`**

A replayed chain can `advance_step`, which activates another step, which
replays again. The bound is `StepRegionReplayGuard`: a depth cap of 4 **and**
a per-activation visited set of `(entity_id, mission_id, step_id)`, cleared
when the depth returns to zero so a later genuine activation of the same step
replays normally.

It lives on `SpaceManager` rather than in a thread-local or a threaded
parameter. A thread-local would be wrong outright — the cell task is `async`
and tokio may move it between worker threads at any `await`. A parameter
cannot be threaded because the recursion runs through
`executor::execute_actions`, which knows nothing about the replay. The
`&mut SpaceManager` every frame in the chain already holds *is* the exclusive
token, so a plain field on it is correct with no locking.

`a_two_region_two_step_ping_pong_terminates` builds the adversarial case: two
overlapping volumes on the origin, two steps, each chain advancing into the
other's step. It terminates and leaves the guard idle. Note the visited set
alone is sufficient for that shape — the depth cap is the second line, and
has its own unit guard.

### (b) Double fire — **only mission-gated chains are replayed**

The client may send the real hint a moment after the replay. For a chain that
carries `mission_status` / `step_status` / `objective_status`, the second
delivery is a no-op by construction: the chain's own actions move the state
its gate reads, so the gate is closed when the hint lands. For a chain with no
such gate — a bare `enter_region` → `display_dialog` — the second delivery
runs it again and the player sees the dialog twice.

**Decision: refuse the ungated chain rather than replay it.** The alternative
(replay everything, then suppress the client's subsequent hint) was rejected:
suppressing a legitimate client event is a worse failure than not replaying,
because it is invisible and it breaks the chains that are correct today. The
cost of the choice is that an author who wants a replay must write the
`step_status` gate — which is the gate that chain wanted anyway, and which the
ledger's authoring rules already ask for. The refusal is logged at `debug` on
`target: "content.resolve"` with `reason = "filtered_out"`, so "my chain
didn't replay" is answerable from the logs.

`world` and `archetype` are deliberately **not** mission gates. They look
adjacent, but neither changes when the chain runs, so neither makes a re-fire
idempotent. `is_mission_gated_recognises_only_mission_state_conditions` pins
the classification in both directions.

### (c) Rings and stargates — **structural, not conventional**

`triggerClientHintedGenericRegion` drives three things off one hint: content
chains, the ring-transporter FSM, and `REGION_FLAG_STARGATE` passage. The
last two are sequenced by the *dispatch arm* in
`cell_methods::player::world`, after `fire_enter_region` returns — they are
not inside the dispatcher. The replay calls the content path only, so it
cannot start a ring transport or carry a player through a gate, and that is a
property of where the code lives rather than of a flag test.

`replay_never_touches_rings_or_gates` pins it against a volume that is both a
**live** ring pad and a stargate region: the content chain fires, the pad's
occupant list stays empty, the player stays in their world, no gate dial is
armed. `the_ring_fixture_is_live` is its anti-vacuity companion — the same
fixture driven through `ring_transport::handle_region_trigger` *does* register
the player, so the negative above is measuring something.

## Other decisions worth recording

- **Containment is `is_point_in_region`, not `region_contains_xz`.** H06 made
  the first the tolerance band (including the vertical arm) and the second the
  exact test. The replay asks the same question the client hint asks — "is
  this player standing in the volume?" — so it uses the same predicate the
  hint gate uses. The exact test would refuse a player one unit above the
  floor that the real hint path accepts. No third containment function was
  added.
- **Only `REGION_FLAG_CLIENT_HINTED` volumes replay.** A server-only region
  was never handed to the client, so there is no hint to stand in for and
  replaying it would invent an event.
- **Firing order is sorted by tag.** `SpaceManager::regions` is a `HashMap`;
  without the sort, which of two overlapping volumes wins a race would vary
  run to run.
- **Re-validated before every fire.** An earlier chain in the same loop can
  teleport the player, move them out of a volume or destroy the entity, so
  containment is re-tested per tag rather than once up front.
- **NPCs are skipped.** No mission state, no client, no hint.
- **`advance_step` now returns `bool`.** The replay must not run for a
  missing entity or an untracked mission. The early `send_mission_update`
  behaviour is unchanged — only the replay is gated — so no existing warn
  disappeared.

## Follow-ups for the coordinator

1. **The cover edge is still open.** H52 covers `enter_region` only. Objective
   2484's `player_entered_cover` race has the identical shape and the same
   fix would apply (`fire_cover_entered` for sets the player already occupies,
   filtered the same way). It belongs to the Cellblock lane; the seam in
   `missions::progression` already computes `cover_sets` for the diagnostic
   log, so the data is there.
2. **The authoring rule can be relaxed, but only for `enter_region`.** The
   ledger's 2026-09-19 rule tells authors to add a second
   `mission_completed` trigger to any edge-gated chain. That is still required
   for `player_loaded` and cover. For `enter_region` it is now only required
   when the chain has no mission gate — and such a chain should acquire one
   instead. The ledger paragraph was updated accordingly.
3. **Nothing in the Harset seed needs changing for H52.** The existing
   second-trigger rows on 742's and 1326's offer chains remain correct and
   harmless: they are mission-gated, so a double delivery is a no-op either
   way. Do not strip them as part of this packet.

## 1. What the WIP got right

Almost all of it, and it is worth saying so plainly — the reassessment below found one real hole, not a rewrite.

- **The player-side scrub.** Routing through `combat::clear_dead_npc_from_all_player_threat` rather than clearing `npc.threat_list` in place, with the scrub running *before* the drain (it reads the list to find who to scrub) and an `onStateFieldUpdate` per returned pair. This is H04 worknote request B, and it is the shape `apply_death_transition` uses. Verified against the current code: `exit_player_combat` uses `threatened_mobs` emptiness as the refcount and the raw `&= !BSF_IN_COMBAT` is gated on it, so every player on the list is handled, not only whoever landed the last hit.
- **`is_auto_cycle_target_valid` as a predicate on the 100 ms tick**, not only a one-shot sweep on the ~2 s AI tick. This is the mechanism that actually closes the kill window, and the WIP's reasoning for it was correct.
- **Surrender is not a faction flip.** `faction` gates whether an offensive ability may target the entity at all, so flipping it would make the surrendered NPC unattackable, and it doubles as the NPC-versus-NPC aggro filter. The WIP chose `ai_state` + `aggression = 0` instead, and recorded why.
- **The adjacent cleanup inherited from the death path**: channel cancel, cover-slot release, `ai_retry_at` clear — the subset in `.claude/agent-memory/combat-systems-advisor/combat-exit-tail-parity.md`, with the death-only half (loot, reticle drop, `InteractionType` push, dead-bit flip) correctly left out.
- **`aggression = 0` as belt-and-braces**, because `set_npc_ai_state idle`, `set_follow_target`'s no-target arm, the GM console and the respawn tick can all push a submitted NPC back to Idle behind the handler's back.

Everything in that list survives unchanged.

## 2. What changed, and why

### 2.1 A DoT could still kill the surrendered NPC (the real hole)

PR #662's review fix R1 rewired `effects/pulsing/tick.rs::dot_kill_credit` to `abilities::kill_npc_out_of_band`. **Before R1 a lethal pulse left the mob alive at zero health** — a bug, but one that happened to make this packet's problem invisible. After R1 a pulse produces a real corpse. So a damage-over-time effect the player applied *before* the surrender now kills the surrendered NPC a few seconds later, and the WIP only stopped the auto-attack loop. The packet was specified against a tree where this could not happen.

**The fix**: `fire_pulse` floors an `AiState::Submit` target's `HEALTH.cur` at 1. The pulse still lands its full damage; only the killing blow is refused.

**The decision, and the one it beat.** H08's rule is that a surrender survives everything the *server* re-delivers on its own cadence, and changes nothing a player does deliberately. A pulse is on the automatic side of that line by the same definition `is_auto_cycle_target_valid` already uses: the deliberate act was applying the effect, and every tick after it belongs to the scheduler. The two guards are therefore one rule at two seams.

The alternative — strip hostile player-applied pulsing effects at the moment of surrender — was rejected because the surrender handler runs on the ~2 s AI tick while pulses run at 100 ms, so it leaves a window of up to twenty pulses. It also has a worse failure mode: it would strip a DoT a player deliberately applied *after* the surrender, which is exactly the explicit-attack behaviour the packet says to record rather than change.

The floor does narrow explicit-attack behaviour in one place: a player cannot finish a surrendered NPC with a DoT. Taken knowingly, recorded here and in the ADR. A direct shot still kills.

**Placement**: in `fire_pulse` after both the script and NVP damage branches, not in `dot_kill_credit`. The dirty-stat flush below it is that same pulse's `onStatUpdate`, so the client is told `1` and never renders a zero-health frame; and `dot_kill_credit`'s existing `cur > 0` probe then early-outs on the floored value without needing its own `ai_state` check to drift out of sync. One guard, not two.

Recorded as decision 18 in [abilities-and-effects-system.md](../../../architecture/abilities-and-effects-system.md).

### 2.2 Every health-mutation path, and whether it can kill a surrendered NPC

Enumerated from `.claude/agent-memory/combat-systems-advisor/health-mutation-paths.md` and re-verified against the current tree. "Automatic" means the server re-delivers damage on its own cadence after a single player act.

| Path | Entry | Can it kill a surrendered NPC? | Intended? |
|---|---|---|---|
| Auto-cycle loop | `service/ticks/auto_cycle.rs` | **No** — `is_auto_cycle_target_valid` clears the loop on the 100 ms tick | Yes. The packet's headline rule. Automatic |
| DoT / HoT pulse | `effects/pulsing/tick.rs::fire_pulse` then `dot_kill_credit` | **No** — floored at 1 HP (§2.1) | Yes, newly. Automatic; the R1 regression this packet closes |
| Primary single-target hit | `abilities/damage_apply::apply_damage_to_target` | **Yes** | Yes. One press, one hit — deliberate. Recorded, not changed |
| Ground-AoE secondary | `abilities/dispatch.rs` | **Yes** | Yes. One press; splash that catches a surrendered bystander is deliberate at the press. H21's death-path fallback chain covers the mission consequence |
| Cone-AoE secondary | `abilities/cone_aoe/fan_out.rs` | **Yes** | Same as ground AoE |
| Deferred attack-while-holstered | `service/ticks/pending_holster.rs::pending_attack_tick` | **Yes** | Yes. A one-shot promotion of an explicit press, not a repeat — deliberate |
| Content `apply_effect` damage | `cell/content/effect_apply.rs` | **Yes** | Yes. A chain author asked for it; gating it would break scripted executions |
| GM kill | `cell_methods/gm/world.rs` then `kill_npc_out_of_band` | **Yes** | Yes. A GM override that refused a state would be worse than useless |
| NPC AI attack | `npc_ai/fight.rs` | **Yes**, if another mob is hostile to it | Not addressed. Out of scope: surrender is player-facing, and nothing in Harset puts a second faction on the duel NPC. Flagged in §6 |
| Player regen | `service/ticks/regen.rs` | n/a — players only | — |
| NPC respawn reset | `service/ticks/npc_respawn/` | n/a — heals | — |

So: **the two automatic paths are closed; every deliberate path still kills, unchanged.**

### 2.3 The acceptance test now drives the real seam

R1 also moved the `entity_health_below` sample off the single-target path and onto the shared health-application seam (`fire_pending_health_below` / `fire_health_below_for_hit`, called from `damage_apply`, the pulse tick and content `effect_apply`). **The hop H04 wired is not the hop that runs today.**

The WIP's `submit_from_a_health_crossing_takes_the_attacker_out_of_combat` did not involve a health crossing at all: it seeded threat directly and wrote `ai_state = Submit` by hand. That shape asserts what the handler does, which is useful, but it cannot notice the path to the handler being broken. It is renamed to `submit_takes_the_attacker_out_of_combat` and its doc comment now points at the end-to-end test instead of implying coverage it never had.

New `tests/health_crossing.rs` drives all five hops with a real shot: `handle_use_ability_with_kill_credit`, `note_pre_damage_health`, the dispatcher, engine resolve plus `execute_actions`, `executor::world::set_npc_ai_state`, then `npc_ai_tick` into `npc_ai_submit`.

### 2.4 `Submit` *is* ticked — verified, not assumed

`npc_ai/dispatch.rs:57` admits `AiState::Submit` into the snapshot filter and `:92` dispatches it to `npc_ai_submit`, so the WIP's assumption holds and the one-shot transition does not have to do all the cleanup itself. Two consequences were still worth fixing:

- The handler runs **every** ~2 s pass for the life of the space, and the WIP recorded `decision_outcome = "submit_init"` unconditionally at the top — so a parked NPC posted "first-entry combat-clear" forever, making `npc_ai_decisions_total{submit_init}` unreadable. Split: `submit_init` for the pass that actually disengages, new **`submit_hold`** for the quiescent pass. Both are in the enum table in [observability.md](../../../architecture/observability.md).
- The re-run is *correct*, not merely harmless: `generate_threat` calls `enter_player_combat` outside the state-preemption guard, so any stray bullet at a surrendered NPC re-strands the shooter in permanent combat, and Submit has no death or leash exit to undo it. The `!threat_list.is_empty()` probe term is what re-arms the scrub. Pinned by `re_engaging_a_surrendered_npc_scrubs_the_attacker_again`.

### 2.5 The live-NPC combat exit (2026-09-18 Castle playtest)

- **`nav_path` cleared, velocity zeroed** — the WIP had both. Verified they reach the client without extra fan-out: `space_manager/aoi.rs` pushes an `EntityMoved` carrying position, direction and velocity for every entity in a witness's AoI on every 100 ms tick, unconditionally.
- **Facing** — added. `super::fight::face_target` (from H51, now `pub(super)`) is called with the **highest-threat** attacker, captured before the scrub drains `threat_list`. Without it the yaw freezes wherever the last chase step left it, because the movement tick only writes `direction` as a side effect of translation and skips NPCs with an empty `nav_path` — which the surrender itself clears (findings H4b, H6). Two guards, including a two-player one: a naive `.next()` on the threat map passes the 1v1 duel and picks a bystander in a group fight.
- **`setMovementType`** — the WIP's `broadcast_movement_type(npc_id, None, ...)` is the codebase-wide "stopped" convention and every other AI stop path uses it, so it stays. **It puts nothing on the wire**: it clears the server-side cache, and the client keeps playing whatever animation the last broadcast selected. The enum has no "stopped" discriminant to send instead (`Cover`, `CombatAdvance`, `Patrol`, `Follow`, `Wander`, `Leash`, `Avoid` are all *how am I moving* kinds), so inventing one here would be a wire change on a guess. What visibly stops the NPC is the zeroed velocity. Now stated in a comment at the call site. Coupling `setMovementType` to path start/stop is the repo-wide fix (playtest recommended change 9) and is not this packet's — see §6.
- **Not silent** — `submit_init` / `submit_hold` reach the `npc_ai.tick` row, the dispatcher span and the counter, and the `info!` line now carries `surrender_to`.

### 2.6 Bit discipline

`npc.state_field &= !BSF_IN_COMBAT` is a raw clear and that is correct: nothing ever calls `set_state_flag(BSF_IN_COMBAT)` on the NPC side, so `state_flag_counts` has no entry for the bit and `unset_state_flag` would `return false` without touching `state_field`. Now stated in a comment so the next reader does not "fix" it. The player-side clear is not raw — it goes through `exit_player_combat`, which uses `threatened_mobs` emptiness as its refcount.

## 5. What H21 must do (the Rin'la duel, the only consumer)

1. **Seed the crossing chain**: trigger `entity_health_below`, `event_key = "<duel tag>:30"`, gated on `step_status 1325 / 3959 eq active`, actions `set_npc_ai_state submit` (sort 0) then `advance_step` (sort 1) — world-state first, mission-state last. The shape is pinned by the live-DB fixture in `cell::content::chain_replay_tests::entity_health_below` (H04) and driven end to end by `npc_ai::lifecycle::tests::health_crossing`.
2. **Ship the death-path fallback chain anyway** (H04 integration request A). H08 closes the two automatic kill paths; it does not close the deliberate ones, and it cannot: a groupmate's AoE, a content-applied effect, or the duelist simply shooting again all still kill the NPC. An `entity_dead_tag` chain on the same tag, gated on the same `step_status`, advancing to 4036, converts a hard softlock into a slightly-wrong cutscene. **This is now the only remaining softlock route, so it is required, not optional.**
3. **Do not author a `set_aggression` or faction row on the duel NPC.** The handler zeroes `aggression` itself, and a faction flip would make the NPC unattackable — the duel needs the player to be able to shoot it.
4. **Expect the NPC to end at 1 HP or more, facing the player.** If the beat needs a kneel or a specific pose, that is an animation the chain has to drive; the server does not send one (§2.5).

## 6. Gaps and integration requests

- **`setMovementType` has no "stopped" discriminant** (§2.5). Every AI stop path in the tree, not just this one, leaves the client playing a stale animation. Repo-wide, playtest recommended change 9, needs an enum-per-state decision and a UAT. Not H08's to take.
- **An NPC-faction attacker can still kill a surrendered NPC** (§2.2, last row). No Harset content puts a second hostile faction on a duel NPC, so this is theoretical today. If a future surrender is used in a three-way fight, `npc_ai/fight.rs` needs the same target-validity gate the auto-cycle got.
- **No NPC-side `ON_STATE_FIELD_UPDATE`** for the NPC's own cleared `BSF_IN_COMBAT`. Pre-existing and shared with every other AI exit path; the memory note `combat-exit-tail-parity.md` flags it as unclosed and says to check `state-flag-broadcast.md` before "fixing" it. Untouched here.
- **`health-mutation-paths.md` trap 3 is now stale** — "Pulsing DoT never kills properly" was true when written and was fixed by R1. The memory note has been corrected.

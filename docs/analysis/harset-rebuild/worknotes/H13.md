## The default respawn value: 30 seconds, one tier

30 is the documented "typical mob" floor from the `respawn_secs` column
comment in `db/resources/Entities/Tables/entity_templates.sql`
("Minimum: 3 seconds… Recommended floor for typical mobs is 30 seconds;
bosses 300+"). It is repo-documented policy, not an invented number, and
this packet applies it uniformly rather than tiering.

I initially proposed 300 for the two named NPCs (Petbe, Anat) on a
"bosses 300+" reading and the `npc-ai-spawn-advisor` talked me out of it,
with two mechanical arguments I could verify:

- **The boss tier exists to rate-limit farming a rich loot table.** No
  Harset template has a `loot_table_id`, and per spec rule L-01 / D-H17
  none will. The delay therefore controls only how fast world density is
  restored, never a farm rate — so shorter is strictly better.
- **The cost function is asymmetric in exactly one direction.** Too short
  costs a slightly odd-looking pop-in. Too long — or NULL — costs *every
  player on the shard* missions 1200 / 1324 / 742 until the next restart,
  because Anat is one global entity in a shared startup space (D-H04).
  Availability wins; use the floor.

A third argument killed the "longer for the plaza so a returning player
isn't re-aggroed" idea: `aggression` has **no DB column** (it is `0` at
construction in `crates/entity/src/cell_entity/construction.rs:88`, written
only by the `set_aggression` content action and the `.aggression` console
command), so a respawned guard is passive. A returning player has to shoot
it again. The scenario the longer value would have protected cannot happen.

## `is_stationary` breadth: 14 rows, not the 12 in the packet scope

The packet scope named the 8 plaza guards and 4 lieutenants. I extended it
to Petbe (223) and Anat (222) after checking the cost, and I want this
called out because it is a deliberate two-row widening of my own scope:

- **Cost is nil.** `is_stationary` is read in exactly three places, all in
  `crates/services/src/cell/service/npc_ai/fight.rs` — the cover-reservation
  gate (:256), the chase-pathfinding skip (:343) and the min-range backup
  skip (:436). It does not touch facing, aggro, threat, interaction/dialog,
  loot, leash or respawn.
- **Benefit is the same as for the sentries, for a different reason.**
  Anat's world 68 has no navmesh at all; Petbe stands off-mesh on the
  fragmented world-57 mesh. Both reduce to "a pathfind from here returns
  `None`", which without the flag means the NPC freezes silently. With the
  flag it takes the explicit `stationary_holds` branch, which logs
  `in_range` / `has_los` / `dist_to_target` — the same standstill, but
  diagnosable.
- **Consistency with H12.** H12 will set `is_stationary = true` on the ~20
  rows it adds to world 68 ("correct for a council room"). Leaving the one
  pre-existing world-68 row non-stationary would have handed H12 an
  inconsistency to explain.

Two caveats recorded in the seed comment because the column name
over-promises:

- `is_stationary` does **not** suppress patrol, wander, follow or
  investigate — none of those modules read it, and they *do* have
  straight-line fallbacks when the mesh is missing. Combined with
  `COALESCE(s.patrol_path_id, t.patrol_path_id)` in the loader, a
  template-level patrol path added by a future packet would make these
  "stationary" guards walk. It is a fight-behavior flag, not a movement lock.
- GM-spawned copies are forced `is_stationary: false` and
  `respawn_secs: None` (`crates/services/src/base/gm_spawn.rs:246,250`), so
  `.spawn 160` will **not** reproduce the seeded behavior. Do not let that
  confuse the M1 UAT — verify against the seeded spawn, not a `.spawn` copy.

## Why the INSERT column list, not trailing UPDATEs

The packet allowed either. I extended the 14 specific INSERTs' column lists
because:

- **It is the file's existing convention.** Spawn 10
  (`ArmYourself_PrisonerRetrievalUnit`) already carries `is_stationary` in
  its own column list — the one pre-existing non-default row in the file
  does it exactly this way.
- **There is no `UPDATE` anywhere under `db/resources/`.** Appending one
  would have introduced the first imperative statement into a declarative
  data file, which is the shape CLAUDE.md's "no `db/scripts` migrations" rule
  exists to keep out.
- **The Harset rows are not contiguous.** They are scattered across the file
  (lines 55–337 pre-edit) with no Harset block, so a trailing UPDATE would
  have put the intent ~280 lines away from every row it describes. Per-row
  self-description wins for a reader landing on one line.

Diff size is comparable either way: 14 modified lines + 2 deletions (this
approach) versus ~4 added statements + 2 deletions.

Cross-cutting rationale for the whole edit living **per-spawn rather than
per-template**: templates 159 and 160 are *shared with the Castle hub*
(world 8, spawns 119 / 121 / 123 / 124). A template-level `respawn_secs`
would have silently changed Castle's guards too. The per-spawn override
keeps the blast radius inside Harset, and — via
`COALESCE(s.respawn_secs, t.respawn_secs)` in `cell/spawner/npcs.rs:149` —
wins over whatever H11 later puts on the template. That precedence is
deliberate but it does mean these 14 rows will silently shadow a considered
per-template value if H11 lands one; the seed comment says so at the point of
use.

pick. My argument for 30 is in

if the campaign prefers 300, the cheaper fix is to change H13's 14 rows and

and 160 are shared with the Castle hub (world 8, spawns 119 / 121 / 123 /

desirable — Castle's guards were one-shot too — but it is a change to
another campaign's zone arriving as a side effect of a Harset packet, and

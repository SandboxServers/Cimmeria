## Scope as delivered

### 1. The action

`Action::GrantStargateAddress { stargate_id }`, seed verb `grant_stargate_address`,
`target_id` = `resources.stargates.stargate_id`. No params: 2009's
`addStargateAddress(addressId, isHidden)` had a hidden flag, and Cimmeria has no
hidden list at all — no column, no wire slot, `mercury::world_data::map_loaded`
hardcodes an empty hidden array — so there is nothing for a `hidden` param to do.

Grant-only. 2009's node had a `Remove` port (`removeStargateAddress`) and no
shipped content used it; `revoke_stargate_address` can be added when a chain
needs one.

### 2. Three legs, all emitted from the cell

A grant has to reach three places — H06's integration request 6 named exactly
these:

1. **`CellEntity::known_stargates`.** This is what `handle_dial_gate` enforces
   against. Written in memory, immediately.
2. **The client**, via `updateStargateAddress`. The client is handed its whole
   address book exactly once, by `setupStargateInfo` at map load, so a
   mid-session grant is invisible without this.
3. **`sgw_player.known_stargates`**, through a new `CellToBaseMsg::GrantStargateAddress`
   and an idempotent append on the base.

**Legs 1 and 2 go out before leg 3 is confirmed, deliberately.** The obvious
alternative — have the base send 66 after the write commits, the way
`handle_grant_cash` sends `onCashChanged` — was rejected: the cell's copy is
the thing the dial gate reads, so making the client's copy wait on a database
round trip reopens exactly the divergence H06 closed on the arrival path, where
"the client renders an address book one hop out of date while the cell enforces
the current one" is the named failure. The failure modes are also asymmetric: a
lost leg-3 write costs the address at next login and warns loudly, while a lost
leg-2 send makes a granted address undialable with no error anywhere the player
can see.

The precedent for a cell-side client method is already in this exact code path:
H06's own dial refusal sends `onErrorCode` as a `CellToBaseMsg::EntityMethodCall`
from `cell/gate_travel/address_book.rs`, as do `PlaySequence` and
`SetActiveSlot` in the executor.

### 3. Idempotency, twice

The cell returns early — no write, no client method, no base round trip — when
the player already holds the address. The DB append is *separately* idempotent,
because those are not the same lock: the cell's copy can be a snapshot taken at
`onClientReady` while another session writes the row.

The base statement is deliberately **the same shape** as H06's
`persist_arrival` append, minus the origin-world `UNION ALL` branch that only an
arrival has, with `$1` bound as a one-element array rather than a scalar so the
two statements stay textually comparable (and so a future multi-address grant is
a bind change, not a rewrite):

```sql
known_stargates = known_stargates || (
     SELECT COALESCE(array_agg(DISTINCT t.x ORDER BY t.x), '{}'::integer[])
       FROM (SELECT unnest($1::integer[]) AS x) t
      WHERE t.x IS NOT NULL AND NOT (t.x = ANY(known_stargates))
    )
```

A `CASE WHEN $1 = ANY(known_stargates) THEN … END` would have been one line and
is the "second, subtly different append" the coordinator asked not to exist.
The inline-correlated-rather-than-CTE reasoning carries over verbatim from
`persist_arrival`: under READ COMMITTED a correlated sub-SELECT in `SET` is
re-evaluated against the freshly-locked row on an EvalPlanQual recheck, while a
CTE is a stable subplan from the old snapshot.

`WHERE player_id = $2 AND account_id = $3` is H06's ownership rule. The base
resolves `account_id` from the session (`entity_id` → address →
`ConnectedClientState`) the same way `handle_gate_travel` does, and fails closed
with a `reason`-tagged warn if either lookup misses.

### 4. Refusals are never silent

Per `docs/architecture/negative-logging-convention.md` and the 2026-09-18 Castle
playtest lesson (a silent refusal and a message that was never sent look
identical in-game):

| `reason` | Level | When | What the player sees |
|---|---|---|---|
| `grant_unknown_stargate` | WARN | `target_id` has no `resources.stargates` row | Nothing. The alternative — granting anyway — puts an address in their DHD that the dial handler is guaranteed to refuse one layer down, which reads as a server bug |
| `grant_non_player_actor` | WARN | the executor's `player_id` is `<= 0` | Nothing. Every dispatcher derives it as `entity.player_id.unwrap_or(0)`, so this is an NPC, a prop, or an unloaded player |
| `grant_entity_missing` | WARN | no cell entity for the actor | Nothing |
| `grant_notify_send_failed` | WARN | the cell→base channel is closed on leg 2 | The server accepts the dial; their DHD does not offer the address until the next map load |
| `grant_persist_send_failed` | ERROR | closed on leg 3 | The address works this session and is gone at relog |
| `grant_address_no_db_pool` | WARN | base, no pool | same as above |
| `grant_address_no_client_addr` / `grant_address_no_session` | WARN | base cannot resolve the owning account | same as above |
| `grant_address_rows_affected_zero` | WARN | the `(player_id, account_id)` pair names no character | same as above |
| `grant_address_persist_failed` | ERROR | the UPDATE errored | same as above |

The grant also appends a `stargate_address` entry to the player's journal
(`kinds::STARGATE_ADDRESS`), so a `.bug` bookmark answers "could they dial it
yet?" without a database read.

### 5. Seed

Castle chain 1357 — the Livewire victory, "the DHD works, advance to the dial
step" — gains `(1357, 'grant_stargate_address', 3, NULL, '{}', 0, 3)`.

Sort order 3 is cosmetic. Every action in one resolved list runs in the same
synchronous batch (`chain/mod.rs::resolve_event` concatenates and
`execute_actions` iterates), and the grant neither gates nor is gated by the
`advance_step` above it.

**No `player_loaded` restore chain was added.** The packet says to add one only
if the grant can be lost. It cannot: the append is persisted, and the base reads
`known_stargates` back into `InitPlayerState` through `client_ready`'s
`PlayerInitRow` SELECT on every world entry. A restore chain would also be a
*second* grant path for the same address with its own step gate to keep in sync.

**Cross-campaign.** The Castle campaign is closed out (CA00–CA10 merged), so
this packet owns that one row and it is recorded in the Castle ledger's CA09
entry.

## Scope item 3: does a created character know its starting world's gate?

**Decision: no. `base/character_create.rs` is unchanged.**

The evidence, which is the same evidence H06 recorded and did not act on:

- `SGWPlayer.addStargateAddress` (`deprecated/python/cell/SGWPlayer.py:609`) has
  exactly two callers in the whole 2009 tree: the GM console command
  `giveaddress` (`deprecated/python/cell/commands/Player.py:74`) and the Atrea
  node `Act_StargateAddress` (`entities-editor/editor/Nodes.xml:2428`). Nothing
  in character creation touches the list.
- The 2009 first address was therefore always authored content — and as of this
  packet, Cimmeria has the verb that authors it. The gap H06 recorded ("no chain
  can grant an address, so a character who has never travelled can dial
  nothing") is closed by content, not by creation.
- Seeding the origin gate would also be the wrong shape for the one case it
  looks like it helps. A character starts in a tutorial-adjacent world; handing
  them that world's own gate grants an address they can never usefully dial
  (`handle_dial_gate` refuses a same-world dial), so it would change nothing
  observable while adding a second, silent grant path.

If a future starting zone needs the player to be able to gate out on day one,
the answer is a `player_loaded`-triggered `grant_stargate_address` chain in that
zone's seed — visible, testable and gated like any other content — not a column
in `character_create`.

**Two notes on how the proof was set up.**

The seed guard was proven with an in-place `DELETE` against the scratch database
and re-`INSERT`ed afterwards, rather than editing the SQL and paying a second
30-second reload. The other ten reverts were code edits run under one lane hold
with `DATABASE_URL` exported against the already-loaded database.

The end-to-end test `the_grant_is_what_turns_a_refused_harset_dial_into_an_accepted_one`
is **not** separately revert-proven, because it has no single guard of its own:
it is the packet's acceptance criterion, and it fails under the executor-arm
revert along with everything else. Its two-phase shape is what keeps it from
being vacuous — asserting "the dial is accepted" alone would pass against a
`handle_dial_gate` with no address check at all, so the first phase pins the
refusal (including the seven `onErrorCode` bytes) before the grant runs.

## Open questions

1. **Does the client actually re-render the DHD list on method 66?** The wire
   shape is verified against the def and the 2009 call site, and 2009 sent
   exactly this on every add, so the server side is right. Whether the client's
   `Event_NetIn_updateStargateAddress` handler updates an already-open DHD
   window or only the backing list has not been traced
   (`docs/reverse-engineering/findings/stargate-dhd-state-machine.md` flags the
   pending-vs-active vector question as unresolved). B19 observes it.
2. **Should the grant also fire when the player is mid-dial?** It cannot today —
   the only seeded grant is on a minigame victory, and the DHD's dial UI is a
   separate interaction. If a future chain grants an address while a dial is
   armed, nothing re-validates the armed dial; that is correct (the armed dial
   was already authorised) but worth knowing.

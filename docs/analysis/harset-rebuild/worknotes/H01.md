## Behaviour implemented

### Arrival (audit defect H-B1, decision D-H07)

`handle_dial_gate` previously sent the `resources.stargates` row verbatim as
the arrival. That row is the `GLB-Stargate_Prefab_Seq` prop transform, and the
2009 server did the same thing (`deprecated/python/cell/SGWPlayer.py:2129` —
`moveTo(addr.xPos, addr.yPos, addr.zPos, addr.yaw, ...)`), which was harmless
only because it never validated containment. Harset is the first
navmesh-backed destination; there the prefab origin sits ~1.5 units above the
floor with the nearest walkable vertex ~5 units away in XZ, so the traveller
lands off-mesh and every inbound position is suppressed — a frozen avatar to
witnesses, with `CorrectionSuppressed` as the only trace.

- **Representation: absolute `arrival_x/y/z/yaw`, not a yaw-relative offset.**
  Every one of the 28 gate rows is a prefab origin, so the problem is
  universal, but the error has a vertical component a planar offset cannot
  express, and D-H15's M0 pin session produces absolute coordinates from the
  map debug HUD. The four columns are all-or-nothing (CHECK constraint plus a
  loader-side warn-and-ignore, because a database restored from an older dump
  predates the constraint): a half-pinned row would otherwise read as a valid
  partial arrival and drop the traveller at `(x, 0, z)`.
- **`arrival_yaw` falls back to `stargates.yaw`**, which is already the
  authored "face this way on arrival" value — not to zero.
- **Validation** happens in `cell::arrival` before anything destructive, so
  the warn names the gate whose pin needs fixing. Order: accept the point if
  the destination's navmesh and space AABB both accept it; otherwise take the
  world's nearest respawner that is not exactly `(0,0,0)` and that passes both
  layers; otherwise keep the point and log at `error`.
- **`NavMesh::get_nearest_point` is deliberately not used.** It returns the
  input unchanged on a miss, so its output can never be trusted without
  re-validation — but the stronger reason is that an arrival Detour *can*
  reproject is a pin that is a metre or two wrong and should be fixed in M0,
  not papered over at runtime.
- **Zero-coordinate respawner guard** (Castle CA00 / overlap row U16) is
  self-contained here: `resolve_respawn_target` still has no such guard on
  `main`, and six seeded respawner rows are literal `(0,0,0)` placeholders.
  Exact equality, not an epsilon — this is a sentinel test, and an epsilon
  would exclude a legitimately-authored near-origin respawner.

### DHD (audit defect H-B2, decision D-H08)

`onDisplayDHD` (120) was never emitted and no interaction handler existed, so
right-clicking a DHD prop dead-ended. `try_open_dhd` now fires on the
`INT_DHD` (16) bit of `entity_templates.interaction_type` — templates 1 and
162 carry it; the Harset DHD is `spawnlist` spawn 37, tag `Harset_DHD`,
template 1.

**Deviation from the packet text, deliberate.** The packet says "emits
`onDisplayDHD` (method 120) with the player's known-stargate list". The wire
signature is a single `UINT8 PointOfOrigin`
(`entities/defs/SGWPlayer.def:1236-1238`,
`docs/protocol/client-method-dispatch-table.md:267`), and the 2009 handler
passes exactly one value (`deprecated/python/cell/interactions/DHD.py:31` —
`player.client.onDisplayDHD(gate.addressOrigin)`). The known-address list the
dialling UI filters against rides `setupStargateInfo` at world entry, not
here. Implemented per the def.

Three details worth carrying forward:

- `address_origin` is a **glyph, not an identifier** — it repeats across rows
  (value 1 on both `SGC W2` and `SGC`, 13 on both Dakara E2 and E3). Never key
  `stargates` by it.
- Out-of-range values **refuse to emit** rather than `as u8`-wrapping, because
  256 would wrap to a perfectly in-range-looking 0 and render a silently wrong
  DHD nobody would report as a data error.
- The world-to-gate pick is by lowest `stargate_id`, because `stargates` is a
  `HashMap` and two worlds carry more than one gate row; unordered iteration
  would hand the client a different glyph across restarts.

```text
## Arrival placement

A stargate row's `x_pos/y_pos/z_pos/yaw` is the stargate prop's own transform
— the `GLB-Stargate_Prefab_Seq` origin from the cooked map. The 2009 server
arrived travellers on exactly that point and never validated it. On a
navmesh-backed world the prefab origin is usually *inside* the prefab's
footprint carve-out: at Harset it sits ~1.5 units above the floor with the
nearest walkable vertex ~5 units away in XZ, so an arriving player lands
off-mesh, every position update they send is suppressed, and witnesses see a
frozen avatar with no error anywhere.

`resources.stargates` therefore carries four nullable columns —
`arrival_x`, `arrival_y`, `arrival_z`, `arrival_yaw` — holding an absolute
"stand here on arrival" point pinned in-game. All four are set or all four
are NULL (`stargates_arrival_all_or_nothing`); when NULL the arrival falls
back to the gate row, `yaw` included.

`cell::arrival::validate_gate_arrival` resolves the final placement:

1. The authored pin, or the gate row when there is no pin.
2. If the destination world has a resident navmesh, the point must pass both
   `is_point_valid` and the space AABB.
3. On failure, the world's nearest authored respawner that is not a
   placeholder `(0,0,0)` row and that passes the same two checks, logged at
   `warn` with `reason = "arrival_off_navmesh"` naming the gate to re-pin.
4. If nothing qualifies, the requested point stands and the failure is logged
   at `error` — the player will arrive off-mesh.

The helper never uses `NavMesh::get_nearest_point`: it returns its input
unchanged on a miss, and an arrival Detour *can* reproject is a pin that is
slightly wrong and should be corrected at authoring time rather than papered
over every arrival.

Destinations that are instanced worlds, or that live on another cell, have no
resident space to validate against and are accepted unvalidated (logged at
`debug`).
```

## Open questions

1. **Is `rotation` index 2 the right slot for yaw on a cross-world arrival?**
   `handle_dial_gate` has always sent `[0.0, 0.0, yaw]` and it flows into
   `CellEntity.direction` unchanged, but Y is the vertical axis in this
   coordinate space, so heading-about-vertical would conventionally be index
   1. If index 2 is wrong it is uniformly wrong for all 28 gates and would
   never have been noticed. Observable during M0: arrive at Harset and check
   whether the avatar faces the authored yaw or due north. Worth settling
   before a pinned `arrival_yaw` gets blamed for it.
2. **Should the client hint stop shipping `radius`/`height`?** 2009 zeroes
   both after expanding a cylinder to a four-point box; Cimmeria ships the DB
   values alongside the expanded points. Cosmetic today, load-bearing once
   CA10's region routing lands, because a client/server geometry divergence
   becomes both a false-reject source and a probe surface.
3. **Does the DHD emit want a failure path?** 2009 sends
   `player.onError("Cannot display DHD: No stargate found on this world")`.
   Cimmeria's `onErrorCode` is an enum-coded surface with no free-text arm, so
   a DHD prop on a gateless world currently logs and shows the player nothing.
   Acceptable for the seeded worlds (every DHD prop has a gate); a question if
   GH2 places DHD-flagged props anywhere new.

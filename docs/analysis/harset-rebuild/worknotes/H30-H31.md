## The defect found and fixed

`no_template_slot_ever_holds_two_binds_at_once` failed on first run. Chain 6502
(mission 1360's letter indicator) and chain 6526 (mission 1361's Praxis turn-in
indicator) both bind template slot 10, Col. Marsh, and each was gated only on
its own step. A player who is on 1360 step 4038 **and** 1361 step 4694 at the
same world entry received both binds, and `interactions::handle_interact` takes
the first entry carrying a non-NULL dialog and ignores the rest, so the second
was permanently unreachable.

The state is reachable. 1361 is accepted only while 4038 is not active (chains
6511/6512 require `neq active`), but nothing stops a player from returning to
the Castle mid-Praxis, looting Frost, advancing 1360 to step 4038, and coming
back.

Fix, in two parts:

1. Chain 6502 now carries the same `step_status 1361/4694 neq active` row that
   chain 6501 already had on the interact side, so bind precedence matches
   interact precedence exactly: while the Praxis turn-in is pending, Marsh wears
   the Praxis "?" and the letter waits.
2. **New chain 6505**, triggered on `mission_completed '1361'`, hands the letter
   indicator back the instant 1361 completes. Without it the letter turn-in
   would be unreachable until the player next crossed a world boundary:
   `entity_templates` row 10 ships `interaction_type = 0` and
   `static_interaction_sets = '{}'`, so with no bind on slot 10 the client never
   registers an interaction on Marsh and the right-click that fires chain 6501
   is never sent. `fire_mission_completed` runs after 6527's
   `remove_dialog_set 5253`, so slot 10 ends that event holding exactly one bind.

## Playtest lessons applied

The 2026-09-18 Castle playtest findings were checked one by one against these
chains. Two changed the work; the rest were verified clean and are recorded so a
reviewer does not have to re-derive them.

### Changed the work

**Edge-trigger race (finding H9) is a class, and it bit this packet twice.** H9
is about a chain keyed on an edge event that never fires because the player is
already inside when the step activates. The same shape exists for
`player_loaded`: a step or gate that opens while the player is standing still in
the destination world gets no second `player_loaded`, so a restore chain alone
can never paint its indicator.

Every bind, offer and restore chain in both packets was walked for it. For each
`player_loaded` chain, ask which chain opens its gate and whether that chain runs
in the same world.

| Restore / offer | Gate opened by | Same world? | Covered by |
|---|---|---|---|
| 6502 (1360 letter "!") | the Cellblock leg advancing 1360 to 4038 | no | the crossing into world 68 |
| 6502, second gate | 6527 completing 1361, world 68 | **yes** | **new chain 6505** |
| 6511 (1361 offer "?") | 6501 completing 1360, world 68 | **yes** | **new second trigger row on 6511** |
| 6514 (4040) | 6513 `accept_mission`, world 68 | yes | 6513's in-chain `add_dialog_set 6397` |
| 6516 (4041) | 6515 in 68; Hansen is in 57 | no | the 68 to 57 crossing |
| 6519 (4042) | 6518 in 57; Moh'katan is in 68 | no | the 57 to 68 crossing |
| 6521 (4043) | 6520, world 68 | yes | 6520's in-chain `add_dialog_set 6395` |
| 6523 (4693) | 6522, world 68 | yes | 6522's in-chain `add_dialog_set 6396` |
| 6526 (4694) | 6525, world 68 | yes | 6525's in-chain `add_dialog_set 5253` |
| 6504 (567 turn-in "?") | 567's Castle-side legs, unauthored | no, **today** | residual, noted in the seed |

Session 1 had the four intra-1361 same-world hand-offs right (6513, 6520, 6522,
6525 all bind in-chain) and correctly did **not** bind across the door, because
`cross_world_teleport` destroys the cell entity and a bind made on the far side
would not survive. The two it missed are both cross-*mission*, which is where
"one mission has one current step" stops being an argument:

1. **Chain 6502**, fixed by chain 6505 — see the defect section above.
2. **Chain 6511**, the Praxis offer, fixed by a second trigger row
   `mission_completed '1360'`. This one is on the **guaranteed first-visit
   path**, which makes it the more serious of the two. The player walks into the
   Command Center from the Cellblock carrying Frost's letter, right-clicks Marsh,
   and chain 6501 completes 1360 and clears dsm 5356 from template slot 10 in the
   same click. 6511's gate (`step_status 1360/4038 neq active`) has just opened,
   but no second `player_loaded` is coming — so Marsh ends that click with **no
   bind at all**, and template 10 ships `interaction_type = 0` with
   `static_interaction_sets = '{}'`, so the client stops registering an
   interaction on him entirely. Meet The Praxis would be unreachable until some
   unrelated world crossing. `fire_mission_completed` populates world, archetype
   and mission context after the mutation and runs after 6501's
   `remove_dialog_set` (sort_order 2), so slot 10 ends the click holding exactly
   one bind, dsm 5254.

Chain 6504 is a residual, recorded in the seed rather than fixed: it is
`player_loaded`-only, which is correct **only** while 567's earlier legs (steps
2000 and 2012, both unauthored) stay Castle-side. If a Castle packet ever makes
step 4039 current while the player is already in world 68, 6504 needs the same
treatment. There is no `advance_step` trigger to hang it on, so the fix would
have to be an in-chain bind on whatever advances to 4039.

Guards: `chain_6511_offers_the_praxis_the_moment_the_letter_is_handed_over`,
`chain_6511_second_trigger_is_gated_as_tightly_as_the_first`, and
`every_same_world_step_handoff_binds_in_chain`, which pins the whole table above
so a future edit cannot quietly drop an in-chain bind.

**Vacuous negatives.** `resolve_event` checks `chain.trigger.matches(event)`
before it evaluates a single condition, and the keyed triggers read their key out
of the event params: `OnInteractTag` wants `entity_tag`, `OnDialogChoice` wants
`dialog_id`, `OnMissionCompleted` wants `mission_id`. A negative whose context
omits the key resolves nothing for a reason unrelated to the gate it claims to
test, passes, and keeps passing when the gate is deleted. Every negative in this
packet was audited and all of them already set their key; the revert
verification below is the independent confirmation, since a vacuous negative
would have stayed green there. `every_keyed_trigger_matches_the_context_the_negatives_build`
now pins it so a key rename cannot turn the file green.

**Item defects.** Both items this packet moves exist in `items.sql` with their
own name and description, so the Castle item-2135 shape is not repeated. One
defect to record, not to fix here: item 2698 "Romney's Files" ships
`icon_location = 'set:CoreWidgets image:IconMissing'`. That is shipped 2009 data,
and 2698 has no grant path anywhere, so the row is unreachable today; the icon
should be resolved by whichever Castle packet first grants it. Item 3730
"Frost's Letter" is clean (`set:ItemIcon003 image:Letter`).

### Verified clean, no change needed

**Two copies of one named NPC with a marker.** Col. Marsh is the shared NPC
between the Castle and Harset campaigns. `spawnlist.sql` has exactly two
template-10 rows — spawn 7 in world 12 (`Preparation_ColMarsh`) and spawn 118 in
world 8 (`Castle_ColMarsh`) — in different worlds, and `harset_opcore_chains.sql`
is the only seed file in the repo that binds template slot 10 at all, so no
second Marsh can light up. **Constraint for M0:** `CmdCenter_Marsh` must be a
single new `spawnlist` row in world 68. A second one in world 8 or 12 would
reproduce the Zuritskas bug directly, because a slot-10 bind addresses a
template, not an entity.

**Dialog displacement (a second `display_dialog` inside about 3 s replaces the
first).** 1361 is six talk steps in a row, so every hand-off was checked. No
chain in the file emits more than one `display_dialog`, and the two cases where
two chains share a trigger key are proven pairwise disjoint against the whole
seeded DB by `marsh_interact_chains_are_pairwise_disjoint` (three chains on
`CmdCenter_Marsh`) and `mohkatan_interact_chains_are_pairwise_disjoint`. The two
outcome dialogs that do replace a predecessor (4460 after 4459, 4463 after 4462)
are deliberate: the player clicked the button that asks for them.

**`set_interaction_type` on a shared hub NPC.** Not used anywhere in this file.
Every indicator is a per-player `add_dialog_set` bind, which is why the seven
`interact_tag` chains are allowlisted in `interact_tag_linter.rs`. All six
templates involved (10, 42, 43, 48, 54, 212) were confirmed to carry
`interaction_type = 0` and `static_interaction_sets = '{}'`, so the bind is the
only source of the bit and no zone-wide flag is ever cleared.

**Hostile actions on shared hub NPCs.** No `set_aggression`, `generate_threat`,
`destroy_entity` or `set_visible` anywhere in this file. Neither mission needs a
hostile.

**Completion acknowledgement.** Rewards are out of scope (design gate GH3, and
every Harset mission ships `reward_xp = 0`), so each of the three completions
displays a closing dialog first: 6501 plays 4576, 6503 plays 2044, 6527 plays
4465. No mission in this packet can vanish silently.

## Corrections to the session-1 authoring notes

Three claims in the seed header were true when written and were made stale by
the wave-2 merge. They are corrected in place rather than left to mislead the
next author.

| Note | Session-1 claim | Current engine |
|---|---|---|
| (C) | `last_interaction_target` is pinned inside `interactions::handle_interact`, so an `interact_tag` chain that short-circuits it leaves the pin unset; filed as an engine follow-up | The pin now happens in `cell_methods/player/interaction/interact.rs` **before** all chain dispatch, right after the `interact_target_in_range` gate. **The follow-up is closed — do not re-file it.** |
| (D) | `handle_interact` picks `available_interactions[template_id].first()` | It is a `find_map` that skips interaction-only binds (`dialog_id IS NULL`) and takes the first entry with a real dialog |
| Anat / 742 | The static `entity_interactions` row is shadowed by the per-player bind | `entity_interactions` has **no Rust consumer at all**; the table never reaches the runtime |

The bind path for Hansen and Anat (chain ids 6517 and 6524 left deliberately
unused) is unchanged and still correct, on a stronger reason: `fire_interact_tag`
short-circuits `interactions::handle_interact`, which is the only code that opens
a *bound* dsm's dialog. An `interact_tag` chain on either NPC would suppress the
button-bearing dialog (4459 or 4462) that their step depends on, so chains 6518
and 6525 could never fire.

## Blocked

**On M0 (in-client placement pins), everything in this file is inert.**
`spawnlist.sql` currently has **zero** `CmdCenter_*` tagged rows, so every
`interact_tag` chain here (6501, 6503, 6515, 6520, 6522, 6527) addresses a tag
that does not yet resolve to an entity. This is by design — the packet forbids
seeding coordinates — but it means none of this content is UAT-testable until M0
lands. M0 must seed, in world 68: `CmdCenter_Marsh` (template 10),
`CmdCenter_Copplemann` (48), `CmdCenter_Mohkatan` (54), `CmdCenter_Baal` (42),
and it must fill `tag = 'CmdCenter_Anat'` into the **existing** spawn 222
(template 43, world 68, currently `tag = NULL`) rather than add a second Anat.
In world 57 it must seed `Harset_Hansen` (template 212).

**On chain 6007** (the 68 to 57 Command Center return door): chains 6511-6513
stay disabled. M0 must flip 6007 and those three together.

**On a Castle grant for item 2698** (U17): chains 6503 and 6504 stay disabled.
Flipping `enabled` on both rows is the only change needed;
`chain_6503_is_authored_ready_for_the_day_2698_is_granted` pins the action list
so it cannot rot in the meantime.

**On GC3** (the XP formula, D-H10): no `grant_xp` action is authored. Three
`-- GC3:` markers in the seed name the insertion points. Do not hardcode a
constant.

## For the coordinator

1. **`entity_interactions` is dead data.** `grep -rn entity_interactions crates/`
   returns nothing. The table is shipped 2009 content with no loader, so every
   static NPC interaction it describes — including Anat's 742 offer, the only row
   in it — is currently unreachable. Worth a ledger row: either wire it, or
   record that per-player binds have superseded it.
2. **The `interact_tag` linter allowlist is past 20 of 32 entries** in the
   "bit comes from elsewhere" family, and every remaining Harset mission packet
   (H32, H33, H36, H37, H41 and on) will add more of exactly this shape. A
   per-file exemption rule for dialog-set-driven files, or the issue #97
   entity-template walker, is the right fix — not another nine entries per packet.
3. **`Action` now derives `PartialEq`.** Chain-replay tests can assert an exact
   action list as one `assert_eq!` against a `vec![..]` literal, including
   table-driven cases whose expected values come from the case tuple. Worth
   propagating to the Castle replay files, which still use per-index `matches!`
   arms and so cannot check runtime-valued fields.
4. **Item 2698's icon is `IconMissing`** (see above).
5. **The M0 single-Marsh constraint** (see above) is the direct analogue of the
   playtest's two-Zuritskas bug and should be carried into the M0 checklist.

## Layout comparison (CookedDataItems.pak, composed vs source)

- Methods: both use Deflated for `_<key>` entries and Stored for `MetaData`; `MetaData` is last and 4 bytes in both.
- Entry order differs: the source PAK lists entries in lexicographic name order (`_10`, `_1086`, `_1087`, ...), the composed PAK in ascending numeric key order (`_10`, `_17`, `_19`, `_20`, ...), as the LP-01 contract says. The client reads entries by name, so order is believed not to matter; not proven on the live client (LP-06 covers that).
- Entry counts differ (6075 lines composed vs 6060 source, both including `MetaData`) because the composed PAK carries the served key set. Compressed sizes of the same entry differ by a few bytes (different deflate encoder).

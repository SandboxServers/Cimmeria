# Launcher cooked-data presync (launcher-cache-presync)

> **Type:** Reference
> **Audience:** The orchestrator, ops, packet-coders, packet-reviewers and the owner
> **Last updated:** 2026-10-26 (owner answers D-LP1, D-LP2, D-LP4 folded in)
> **Companions:** [Work packets](work-packets.md) (rules, contract, wave 1), [wave 2](packets-wave2.md), [waves 3-5](packets-wave3.md), [resume card](RESUME.md), [cooked-data pipeline](../../engine/cooked-data-pipeline.md), [cooked PAK format](../../engine/cooked-data-pak-format.md), [launch.md](../../../crates/launcher/desktop/docs/launch.md)

When the client's cooked-data cache doesn't match the server, character select hangs for about a minute while the server pushes every entry of every mismatched category (the full resync, #840). This campaign makes the desktop launcher bring the cache up to date before the game starts, with visible progress, so that resync never fires for a player who presses Play. Prefix `LP`. Designed 2026-10-26 against `main` `2019922fe`; re-specced the same day for the owner's answers. Line numbers below are from that commit; every packet re-greps its anchors.

**Owner scope (final):** launcher and server only. No client patch, no new Mercury opcode, and no change to `cooked_sync`, which stays server-side for clients that skip the launcher. The launcher never falls back to it: **a presync that fails blocks Play** with a specific message and a Retry (D-LP4, reversed 2026-10-26). The owner rejected server-side pacing, delta sync and any in-game UI.

## Design in one paragraph

On startup the server builds a **served catalog** from its `ResourceCache`. For each category the catalog holds the served version, the full list of entry keys, the bytes of only those entries the server changed (overrides, additions, attribute patches), and a SHA-256 digest of the full served category. The login port (8081) serves it at `GET /api/cooked/v1/index` and `GET /api/cooked/v1/category/{id}?version=v`. At Play, after the telemetry mint, the launcher fetches the index and works out what the client will itself see after its startup copy from `SourceCache.en-us`. For each stale category it downloads the body, composes the full category from the player's own `SourceCache.en-us` PAK plus the changed entries, checks the digest, and **stages** the PAK as a temp file. Only when every stale category has staged does it **commit** them by rename into `Documents\My Games\FireSky\SGWGame\Cache.en-US`. The client then reports matching versions, and `cooked_data.version_reply` answers `up_to_date`. If any step fails, the game is **not** started: the launch ends `not_started`, the launcher shows which step, category or route failed, the HTTP status or OS error and why, and the Play button reads **Retry**. Only a server that says it doesn't presync (kill switch, or no route) lets Play continue without a sync (D-LP19). The launcher sends no CME bytes: they come from the player's own install.

Fail-fast spends no requests or disk on a launch that won't start. |
| D-LP19 | **The server says skip.** 503 `disabled` (kill switch) and 404 on the index (a server without the routes) give `skipped`, reason `disabled` or `server_unsupported`. Play continues and the launcher shows a visible note that character select may take about a minute. This is not a fallback on failure: the server declared it doesn't presync. Every other refusal is a failure. | Decided | The kill switch is the operator's bypass for a broken catalog; if it blocked Play it would lock every launcher player out. A server built before wave 2 has no routes and can't be synced at all. |
| D-LP20 | **Transient refusals.** 503 `catalog_unavailable` and 429 `rate_limited`: if `Retry-After` (503 default 5 s) is at most 30 s and fits the remaining deadline, wait and retry that request, at most 3 waits a run; the status keeps showing the current step. Otherwise fail with `retry_after_s`. 409 `version_changed`: restart once from the index, then fail. 503 `catalog_failed`: fail at once. The quota default stays 60 (owner-decided; F20 is a documented risk for LP-12). | Decided | Bounded waits keep a freshly booted server or a busy NAT from blocking a player who would otherwise sync. |
| D-LP21 | **Server unreachable** (connect refused, DNS, connect or idle timeout) is a failure. The message names the login server's `host:port` and the OS error. | Decided | The game couldn't log in to that server either; the owner asked for the exact cause. |
| D-LP22 | **Never half-composed.** Two phases: stage every stale category (compose, digest check, write `<pak>.cimmeria-presync.tmp`, `sync_all`), then commit. Commit first opens each existing destination exclusively (Windows `share_mode(0)`) and fails with nothing renamed if any is in use, then renames in ascending category order. A failure before commit leaves the cache untouched. A rename failure after the pre-check leaves every PAK file either its old whole self or the new whole one; the categories already renamed are correct, which the client and server accept because they decide per category (F1), and Retry finishes the rest. A `Staged` value deletes its temp on drop; each run first sweeps stray `*.cimmeria-presync.tmp` files from `Cache.en-US` only. A closed launcher is the same as a failure before or during commit. | Decided | The owner's "never half-composed": no PAK is ever partly written, and no failure before commit changes anything. |
| D-LP23 | **Cancel.** The engine's cancel token (no UI caller, F17) stops the run at its next step boundary: staged temps are dropped and deleted, the outcome is `cancelled`, and nothing is launched. A commit that has begun runs to completion, so a cancel during commit still leaves whole PAKs. | Decided | Keeps D-LP22 true for every path. |
| D-LP24 | **No escape hatch** for players, as the owner asked. None is needed: the operator's kill switch covers a broken server, Repair covers a broken install, "close Stargate Worlds" covers a locked PAK, and starting `SGW.exe` outside the launcher still works (the server's `cooked_sync`). | Decided | Owner's ask; each failure has a remedy the message names. |
| D-LP25 | **Time limits.** Connect 5 s; index 15 s in total; a body fails after 15 s with no bytes (per-chunk idle timeout), with no total limit per body; the whole run has a 120 s deadline (was 45 s). On the deadline the failure names the step and category in progress. | Decided | A blocking presync must not fail a slow but moving download; the deadline is only a backstop. LP-05 records body sizes. |
| D-LP26 | **Failure contract.** Closed codes: `step` (`prepare`, `index`, `plan`, `download`, `stage`, `commit`) and `reason` (the Contract's failure table), plus `category_id`, `pak`, `http_status`, `io_kind`, `os_code`, `retry_after_s`, `source_version`, `served_version`, `deadline_s`. They travel in `LaunchStatus.content_sync.failure` (memory only: the journal's `Observation` is unchanged, F18, so after a launcher restart the UI shows the generic `not_started` text) and in the `cooked_presync_finished` event. The UI also shows the login server's `host:port`; telemetry never carries a host, path or free text. The frontend owns the English. | Decided | One closed vocabulary for the UI, the event and the docs; no persisted-format change. |
| D-LP27 | **SigNoz coverage.** Server-side refusals and catalog failures are always in SigNoz (`cooked_presync.refused` with route, reason, status and category; the counters). Launcher-side failure fields reach SigNoz with the game-diagnostics opt-in, or when the player uses Upload debug logs; the local launcher log always has them (F19). | Decided | That is everything the consent model allows. |
| D-LP28 | Add the presync failure `step` and `reason` to the anonymous launcher summary (the separate launcher-diagnostics opt-in), so more failures reach SigNoz? It changes the summary's export schema. Default: no, and no packet waits on it; yes adds follow-up LP-F4. | **BlockedDecision (owner)**, non-blocking | F19. The summary is an anonymous export contract, which is an owner decision. |
| D-LP29 | **Retry.** After a presync failure the Play button reads **Retry** and starts a fresh Play (new operation id); its first press shows "Starting…", as Play does. Categories committed by an earlier run are `up_to_date`, so a retry fetches only the rest. | Decided | Owner's "retry"; one action button, so no second button that does the same thing. |

**Owner decisions:** D-LP1, D-LP2 and D-LP4 are decided. D-LP28 is open and blocks nothing.

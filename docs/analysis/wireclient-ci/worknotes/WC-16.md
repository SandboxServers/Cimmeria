# WC-16 worknote: shakedown

> Type: worknote. Audience: the coordinator and WC-17.

The shakedown counts runs of the `wireclient e2e (live DB)` job on `main`
(`wireclient.yml` has no `workflow_dispatch`, so the count uses re-runs of
the latest `main` run). The packet's change waits for 10 green runs in a row.

Earlier `main` failures of the same job, before WC-14, were all on the
runners, not in a test:

- `e98995c64` ([38153170645](https://github.com/SandboxServers/Cimmeria/actions/runs/38153170645)):
  the same upload failure, on `node1-r2`.
- `187fb8b5f` ([38153561739](https://github.com/SandboxServers/Cimmeria/actions/runs/38153561739)):
  the Postgres service container could not bind 5432 ("port is already
  allocated") on the runner's Docker daemon.
- `30594736d` ([38156942638](https://github.com/SandboxServers/Cimmeria/actions/runs/38156942638)):
  the Postgres service container failed to initialise.

Cause of the upload failures: GitHub's results accounts
`productionresultssa9`, `16`, `17` and `18` share the Azure stamp
`bn9prdstrz04a`, whose DNS rotates `20.150.82.228`, `20.150.88.228` and
`52.239.172.36`. The colo cannot reach `52.239.172.36` (0 of 5 connects from
node1), and the node egress proxy sent only `57.0.0.0/8` through the
workstation exit, so every connect that drew that address first timed out
after 20 s: about 450 failed CONNECTs a day across node1, node2 and node5.

Fix (2026-10-11, deployed): `52.239.0.0/16` joins `57.0.0.0/8` in the node
proxies' `--via-dst` and the exit's `--allow-dst`
(`tools/ci-runners/README.md`, "Colo egress"); the upload step stays a
normal step. The exit was restarted with `start-exit.ps1`, and only the
`egress` service was rebuilt and recreated on node2, node1 and node5, so no
runner was recreated. Six CONNECTs to sa17 from node1 afterwards all went
through the exit and reached the account in about 0.5 s, including the
rotations that put `52.239.172.36` first. node3 picks the range up from
`windows/setup.ps1` on its next setup run (its pool is idle while
`CI_WINDOWS_RUNNER=hosted`).

The two Postgres service failures
are runner faults outside this campaign; if they recur in the count they go
to the runner owners, and the count records them as infrastructure, not as
test flakes (D-WC9 covers the tests).

## Counts 2 and 3 (2026-10-11), stopped at the Postgres service

| Attempt | Result | Runner | Note |
|---|---|---|---|
| 5 | green | | 88 s |
| 6 | green | | 117 s |
| 7 | red | `desk-r3` | Postgres service never healthy |
| 8 | green | | 85 s (count 3 starts here; count 2's script was stopped by memory pressure) |
| 9 | red | `desk-r2` | Postgres service never healthy |

No test ran in either red attempt. Both are desktop runners, in Docker
Desktop on the operator's workstation, whose disk the build lanes share. The
container log stops at initdb's "performing post-bootstrap initialization",
before "syncing data to disk". Reproduced on that workstation with the same
image (`postgres:17.9`) and env:

| `POSTGRES_INITDB_ARGS` | Outcome |
|---|---|
| none | not ready after 150 s |
| `--no-sync` | initdb in 0.3 s, then the entrypoint's temporary server hung in its shutdown checkpoint past `pg_ctl`'s 60 s stop timeout, and the container exited 1 |
| `--no-sync -c fsync=off -c synchronous_commit=off -c full_page_writes=off` | initialised and ready in 25 s and 24 s (two runs; `docker run` alone took up to 36 s) |

Fix: the three CI Postgres services (`test.yml` twice, `wireclient.yml`) set
the last row. The database is thrown away with the job, so it needs no
durability. The earlier "failed to initialise" on `30594736d` was also
`desk-r3`, with its log stopped at the same line. The "port is already
allocated" failure on `187fb8b5f` is a different fault.

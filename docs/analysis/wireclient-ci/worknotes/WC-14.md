## What the test does

One test, `praxis_start_completes_mission_622_live_db`, on sentinel account
`0x7000_9C02` (`wc14_praxis`, access level 2). It creates a Praxis Commando
on the wire, plays it, cancels the intro movie, finds Frost through the
mirror (`template_query(14)`), then sends the capture's ten calls and waits
for the answers the packet's step table lists, plus the extras below, in the
capture's order. It ends on the server's own record: `sgw_mission` 622
status 2 and 1360 status 1, polled while the script keeps pumping. No entity
id is a literal and nothing sleeps.

The test is a module directory: `mod.rs` holds the test and its steps,
`waits.rs` the sends, cursor-free log scans, the DB poll and the failure
message, `predicates.rs` the log matchers and the fixture-record readers.

## Differences from the packet spec and the ADR table

1. **The pistol is not in the world-entry inventory.** The packet says to
   find it in the world-entry `onUpdateItem` by the start profile's weapon.
   Since Class Start v6 (OD-CS01) the `PRA_OPCORE_COMMANDO` profile has no
   starter weapon: `char_creation_items` has no row for char def 3. The
   pistol (design 55) is granted by chain 1005 (`dialog_open` 3996,
   `add_item` 55 to container 1) when the player searches the Guard's body.
   The test reads that design id from the seed
   (`support::item_granted_by_dialog(3996)`: the `add_item` actions of every
   enabled chain triggered by opening dialog 3996, kept to designs whose
   `container_sets` include the bandolier, which must agree on one design;
   chains 1005 and 1010 both grant 55), waits for the `onUpdateItem` that
   carries it after step 6, and takes the instance id from
   `mirror.inventory()`. It asserts the pistol is not in container 3 before
   the move.
2. **`onKnownAbilitiesUpdate` order is not stable.** The capture shows
   `[597, 1218, 592, 594]`; two failing runs here printed
   `[1218, 597, 592, 594]` and `[594, 592, 1218, 597]`. The message carries
   the player's whole known set from `AbilityManager::known_ability_ids`,
   which iterates a hash set. The test checks containment. Not a server bug
   as far as the client is concerned (it rebuilds its known list from the
   array), but any golden that pins this array's order will flake.
3. **The region trigger goes after the teleport line**, not in the same send
   as `gmGotoXYZ`: fixture #8 follows #5, the client reports leaving the
   region once it has moved.
4. **The movie and the arrival dialog race.** `onPlayMovie` (base, on
   `onClientReady`) and the arrival `onDialogDisplay 2982` (cell, on
   `player_loaded`) can arrive in either order, so steps 0a and 0b scan the
   log from its start instead of moving the cursor past one of them. The
   cursor first moves at step 2's teleport line, which only the step-2 send
   can produce.
5. **The pistol's `onUpdateItem` arrives before the step-6 mission
   updates** (base and cell order), so it is checked with a log scan from
   the step-6 send rather than inside the ordered list. The same for the
   move's inventory answer after step 9.
6. **Step 9 is pinned to the move by a check before the send, not by the
   cursor.** `ScriptSession` has no way to set its cursor, so the ordered
   wait still starts after step 6's last match. The test asserts instead
   that nothing logged before the move is `Sequence 10000` or
   `MissionUpdate { 622, 1 }`, and the coordinator added
   `ScriptSession::skip_to_end`, called right before the send, so step 9's
   ordered wait matches only what is logged after it. A completion already
   in flight (sent before the move, not yet pumped) could still match; the
   pre-send check makes that window one pump wide.
7. **Chain order sets step 3's order.** Chains 1003 and 1121 both trigger on
   `dialog_open 3995` at priority 0 and run in chain-id order
   (`engine_loader.rs` loads `ORDER BY chain_id`; `content-engine`
   `chain/mod.rs` sorts each bucket by priority with a stable sort). That
   is why "80623 started" comes before "1360 accepted". A priority change on
   either chain flips it, and the test would fail on the order.

## Finding: the inventory answer after the move

The base does answer `moveItem`: `after_commit` sends the full-inventory
resync (`send_full_inventory_update`), an `onUpdateItem` to the player with
the pistol in container 3, slot 1 (the wire slot is 1-based; the base adds
one to the stored slot). The test asserts both. README F11 and the ADR's
"No server inventory message appears in the tap after `moveItem`" describe
the tap's coverage (it does not see base-originated traffic), not a missing
server answer. For WC-17: the ADR bullet can say so.

## Finding: the raw trail drowns in avatar updates

While the script waits, the Cellblock's NPCs send `0x10` avatar updates
several times a second, so `ScriptSession::trail(30)` at a timeout is all
`0x10` lines and shows none of the answers that did arrive. Every failure
in the test adds a second list, the last 30 log entries that decoded to an
event. A `ScriptTimeout` already carries the raw trail, so for it only the
decoded list is added (it was printed twice before the review). A follow-up
could make `trail` itself skip position-only updates (WC-12's file).

## Guard experiment

`handle_move_item` (`cell-methods` `inventory/item_ops.rs`) was made to drop
every call (`if args.len() >= 16 && entity_id == u32::MAX`), the test was
run, and the change was reverted (`git diff` shows no server change). The
test failed at step 9 after its 10 s deadline:

+0.149s entity 2 StepUpdate { step_id: 80622, status: 0 }

answered the move. (That run predates the review: step 9 now has five
steps, and the raw trail is no longer repeated after the timeout text.)

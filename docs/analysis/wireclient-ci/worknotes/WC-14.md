# WC-14 worknote

> Type: worknote. Packet: WC-14, the Praxis-start end-to-end test
> (`crates/wireclient/tests/it/praxis_start_live_db.rs`). Written 2026-10-11
> by the `rust-gameserver-dev` implementer.

## What the test does

One test, `praxis_start_completes_mission_622_live_db`, on sentinel account
`0x7000_9C02` (`wc14_praxis`, access level 2). It creates a Praxis Commando
on the wire, plays it, cancels the intro movie, finds Frost through the
mirror (`template_query(14)`), then sends the capture's ten calls and waits
for every answer the packet's step table lists, in order. It ends on the
server's own record: `sgw_mission` 622 status 2 and 1360 status 1, polled
while the script keeps pumping. No entity id is a literal and nothing
sleeps.

## Differences from the packet spec and the ADR table

1. **The pistol is not in the world-entry inventory.** The packet says to
   find it in the world-entry `onUpdateItem` by the start profile's weapon.
   Since Class Start v6 (OD-CS01) the `PRA_OPCORE_COMMANDO` profile has no
   starter weapon: `char_creation_items` has no row for char def 3. The
   pistol (design 55) is granted by chain 1005 (`dialog_open` 3996,
   `add_item` 55 to container 1) when the player searches the Guard's body.
   The test reads that design id from the seed
   (`support::item_granted_by_dialog(3996)`: the `add_item` actions of every
   chain triggered by opening dialog 3996, which must agree on one design),
   waits for the `onUpdateItem` that carries it after step 6, and takes the
   instance id from `mirror.inventory()`. It asserts the pistol is not in
   container 3 before the move.
2. **`onKnownAbilitiesUpdate` order is not stable.** The capture shows
   `[597, 1218, 592, 594]`; the two failing runs here that printed it showed
   `[1218, 597, 592, 594]` and `[594, 592, 1218, 597]`. The message carries the player's whole
   known set from `AbilityManager::known_ability_ids`, which iterates a hash
   set. The test compares it as a set. Not a server bug as far as the
   client is concerned (it rebuilds its known list from the array), but any
   golden that pins this array's order will flake.
3. **The region trigger goes after the teleport line**, not in the same send
   as `gmGotoXYZ`: fixture #8 follows #5, the client reports leaving the
   region once it has moved.
4. **The movie and the arrival dialog race.** `onPlayMovie` (base, on
   `onClientReady`) and the arrival `onDialogDisplay 2982` (cell, on
   `player_loaded`) can arrive in either order, so steps 0a and 0b scan the
   log from its start instead of moving the cursor past one of them. The
   cursor first moves at step 2's teleport line, which only the step-2 send
   can produce.
5. **The pistol's `onUpdateItem` arrives before the step-6 mission
   updates** (base and cell order), so it is checked with a log scan from
   the step-6 send rather than inside the ordered list. The same for the
   move's inventory answer after step 9.

## Finding: the inventory answer after the move

The base does answer `moveItem`: `after_commit` sends the full-inventory
resync (`send_full_inventory_update`), an `onUpdateItem` to the player with
the pistol in container 3, slot 1 (the wire slot is 1-based; the base adds
one to the stored slot). The test asserts both. README F11 and the ADR's
"No server inventory message appears in the tap after `moveItem`" describe
the tap's coverage (it does not see base-originated traffic), not a missing
server answer. For WC-17: the ADR bullet can say so.

## Finding: the raw trail drowns in avatar updates

While the script waits, the Cellblock's NPCs send `0x10` avatar updates
several times a second, so `ScriptSession::trail(30)` at a timeout is all
`0x10` lines and shows none of the answers that did arrive. The test's
failure message adds a second list, the last 30 log entries that decoded to
an event (`events_trail`). A follow-up could make `trail` itself skip
position-only updates, or print both lists (WC-12's file, not touched here).

every call (`if args.len() >= 16 && entity_id == u32::MAX`), the test was
run, and the change was reverted (`git diff` shows no server change). The
test failed at step 9 after its 10 s deadline:

## Contract

- **Packet:** PT-03, "summon via ability". A summon branch in `use_ability/`, ahead of the damage pipeline and the #444 gate, for abilities with a `pet_summons` row. The warmup is the spawn timer, a second summon replaces the pet, the source and target VFX play, and the cooldown is as seeded. The #444 gate is not widened.
- **Acceptance:**
  - casting 2826 spawns template 350, owned by the caster;
  - a second cast replaces the first pet;
  - an interrupted warmup spawns nothing;
  - a non-summon self-cast is still rejected, with a revert guard on the gate;
  - a failure (such as a missing template) gives the player visible feedback.
- **Decisions in force:**

## Evidence

1. **`AF_CHANNEL_ALLOWS_MOVEMENT` was the client's `SpeedPet`.**
   - `crates/entity/src/abilities/defs.rs:27` defined it as 16384 ("reserved bit 14, not in any python reference").
   - `entities/defs/enumerations.xml:51` is `<Name>SpeedPet</Name><Value>16384</Value>`.
   - A full parse of `abilities.sql` (1,886 rows, multi-line descriptions included) found 14 rows with bit 14 set, and all 14 are summons: turrets 962, 963, 964, 966; Goa'uld 1643, 1644, 1645, 2825, 2826; copies 3491, 3493, 3495, 3496, 3497. No row sets bit 20.
   - So before this packet, every summon warmup was exempt from the move interrupt (`warmup/tick.rs:101`).
2. **Python sequence targets.**
   - `AbilityManager.playSequence` sends `targetId or ent.entityId` (`:888-892`), so a Self cast went out targeting its caster.
   - Effect sequences were played on the effect's target entity, with source = invoker and `InstanceId` 0 (`:300-308`, `:473`).
3. **The client cannot place a sequence on an entity it has not created.**
   - A spawned pet is introduced by the next AoI tick, so an `onSequence` targeting the pet in the summon's own pass would reach clients first.
   - Hence the arrival queue. The client's handling of an unknown TargetID is not verified; the queue avoids depending on it.
4. **Auto-cycle.** 2826's flags (18192) include `DoNotActivate_AutoCycle` (512) and `Deactivate_AutoCycle` (1024). Python kept 512 abilities out of the loop (`SGWPlayer.py:1177`). Rust stashed every fired ability as `last_fired_ability_id`, so `setAutoCycle(1)` would re-fire a summon.

## Design decisions

1. **Keyed on the ability id, not an effect script.** A-26 says there is no effect to hang a script on. `player_summon(space_mgr, caster, ability)` returns the `PetSummon` only for a player caster. NPCs never summon.
2. **The client's target is discarded at launch** (`target_id = 0`), straight after the weapon redirect and before anything reads it: the #444 block, LOS, `PendingCast.target_id` and the fire-time re-checks. The gate is unchanged. A summon never reaches it; any other ability aimed at the caster still fails there. The authority review preferred discarding to rejecting, because a Self ability legitimately arrives with 0 or with the caster's own id.
3. **Launch refusals, before the cooldown.** The summon must be in the trained set; a weapon grant does not count (authority review). The template must be cached. Both send `onErrorCode(0, ability, code)` plus a `CHAN_FEEDBACK` line:
   - not trained: code 167 `EntityDoesNotHaveAbility`, "You have not trained that summon.";
   - template missing or spawn failed: code 0 `InvalidEntity`, "Your pet could not be summoned.".

   `onErrorCode` rendering is unverified (AT-E1). The chat line is the route known to render.
4. **Warmup.** `effective_warmup` gains `(AF_SPEED_PET, SPEED_PET)`. It is `max(0)`-clamped, so a 100% `speedPet` gives an instant summon, which is what "Heed Our Calling: Summons Chosen Pet Instantly" describes. All AT-10 interrupts apply.
5. **The flag fix.**
   - `AF_SPEED_PET = 16384`.
   - `AF_CHANNEL_ALLOWS_MOVEMENT` moves to `1 << 20`, above the client enum's `PetCommand = 65536`.
   - The only readers use the constant (`warmup/tick.rs`, `pulsing/channel_cancel.rs`, tests).
   - No seed row sets either bit for channels, and a live-DB guard pins that.
6. **Fire** (`fire_cast` diverts before ammo, channel cancel and damage):
   1. Re-check caster alive, in a space, and template cached. This runs **before** the current pet is touched (authority review), so a failing summon never costs the player its pet.
   2. On a refusal: `Ability_Interrupt` (2904) plus the feedback pair. The cooldown stays charged.
   3. `Ability_End` (2292).
   4. Despawn the oldest pets down to `max_active - 1`. The loop is bounded by the list taken up front, and counts all of the owner's pets, so cycling summon abilities cannot stack pets.
   5. `spawn_pet_from_template(owner, template, ability)`.
   6. Queue the target VFX.
7. **Phase sequences carry TargetID = caster** (`sequence.rs` via `summon::phase_sequence_target`) for summons only, per python. The pending cast's target stays 0.
8. **Target VFX** (`pets/arrival.rs`):
   - The queue is on `PetRegistry::arrivals`. It holds the finished `onSequence(2293, source = owner, target = pet, InstanceId 0)` bytes.
   - `pet_arrival_tick` runs after the AoI tick, right after `pet_owner_sweep`. It sends once the owner witnesses the pet, to every witness of the pet, as `WitnessEntityMethod` on the pet.
   - It checks `owner_of(pet) == owner` (id reuse). A missing or relocated pet drops the VFX (DEBUG). An owner who never witnesses the pet drops it after 2 s (WARN, the intro went missing). `forget_pet` scrubs it.
   - The 1122 set is a constant (`SUMMON_TARGET_EVENT_SET`), because `pet_summons` has no column for it; every seeded summon is Goa'uld.
9. **Auto-cycle stash.** An ability with 512 or 1024 is not stashed as `last_fired_ability_id`. This is general: it applies to every such ability, which is python parity.
10. **Logs** stay on the existing `pets.lifecycle` target (no new target):
    - `summon_refused` (WARN, `reason`);
    - `summon_feedback_send_failed`;
    - `arrival_vfx_sent` / `arrival_vfx_dropped` / `arrival_vfx_send_failed`.

    The `cimmeria-server logging` tests (target scan, parity) pass.

## Known gaps

- **The client's rendering of the whole flow is unproven in game.**
  - The Straegis body has never been spawned by this server (PT-S gap).
  - `onErrorCode` rendering is unverified (AT-E1).
  - The 2293 ground effect has only been checked byte-for-byte against the python shape.
  - UAT needs a level-50 Goa'uld or a GM grant of 2826 (A-40).
- **No AI.** A summoned pet stands where it spawned until PT-05.
- **The target set is a constant (1122).** A turret summon may need its own set; a `pet_summons` column would carry it (PT-11 or the turret packet).
- **`Response` (16) is not applied.** Python scaled the cooldown by the `response` stat (`AbilityManager.py:602`); Rust applies it to no ability. This divergence predates the packet and is general.
- **The caster TargetID is summon-only.** Python sent `targetId or ent.entityId` for every target-less ability. PT-03 applies that only to summons, because a general change would alter the wire of every Self and ground cast. Worth a separate look.
- **Auto-cycle is only half of python's 512 rule.** The 512/1024 stash exclusion is general. Python's other half, never arming the loop for a 512 ability, is not ported beyond the existing 1024 clear.

## Design decisions

1. **Guard first, in one helper.** `owned_pet_or_refuse` runs `SpaceManager::owned_pet(caller, claimed)`, then checks that the owner is alive (legacy `@mustBeAlive`) and that the pet is in the owner's space (review N2). After the rebase, `owned_pet` is main's: it checks the pet's per-pet summoner identity (`PetRegistry::summoner_matches`), so a player given a departed owner's entity id does not inherit the pet, and it logs every mismatch itself (DEBUG, `event = "ownership_rejected"`, `reason` = `not_owner` \| `not_a_pet` \| `pet_gone` \| `owner_identity_mismatch`). PT-04 dropped its own WARN for the same seam (coordinator decision) and only sends `onErrorCode` to the caller: `IsNotPetOwner` 236, or `DoesNotHavePet` 190 for `pet_gone`. PT-04 makes no bare owner-id comparison anywhere. A negative wire id wraps to an id no pet holds, so it is `not_a_pet`.
2. **Feedback goes to the owner, never the pet id.** An `EntityMethodCall` addressed to an NPC reaches no client. `handle_use_ability` answers out-of-range with `onErrorCode` on the caster's id, so CM 88 pre-checks range itself.
3. **CM 88 pre-checks, in order:** the ability is on the pet's bar (167), not toggled off (167), the pet is alive (14), not warming up another cast (99), and the ability is off cooldown (99). An explicit target must be in the pet's space (0), a hostile NPC that is not a player and not a pet (37), alive (14), within `max_range` or 30 u (42, the same default as `handle_use_ability`), and in line of sight (39, `attack_line_of_sight`; review M1). `targetId <= 0` is an untargeted cast, which `fire_cast` resolves without damage.
4. **The #444 rule on the owner's behalf.** `handle_use_ability` gates player casters only, because the NPC AI calls it to attack players. A pet is an NPC, so without this gate an owner could aim the pet at a vendor, a quest NPC, a player or another pet.
5. **Cast through the kill-credit wrapper** (`handle_use_ability_with_kill_credit` with `EngineEvents(engine)`). PT-06 confirmed that its `credit_recipient` change inside the wrapper credits the owner with no change here.
6. **Engage after a committed cast.** The target goes on the pet's threat list at the current highest threat + 10, capped at 1e6 (review N3), and the pet goes Fighting with the new `AiTransitionReason::PetCommand`. An untargeted cast engages nothing, and neither does a cast that killed the target. An explicit order is obeyed whatever the stance; the stance rules for autonomous engagement are PT-05's.
7. **CM 89 polarity.** `SGWPet.toggledAbilities` is "abilities toggled OFF", so `toggle` is read as the ability's new state: 1 on, 0 off. The `.def` says only "toggle on/off" and no Lua calls it (A-06), so this is an assumption. Any other value changes nothing, and the bar is re-sent as the visible reaction. Every toggle re-sends `onPetAbilityList` to the owner only.
8. **CM 90 resolution order.** A listed `EPetStance` id is taken as sent. Any other value, including a real id the pet may not take, is read as a 1-based slot into the list the owner was sent. A value that is neither is refused, and the current stance is re-sent so the client's highlight snaps back. The brief said to use the slot reading only "outside `EPetStance`". I widened it to unlisted in-enum ids because the info window only shows listed stances, so an unlisted id can only be a slot from the small bar. The result is always a listed stance.
9. **Log levels (review S4).** WARN is kept for `malformed_args`, `ability_not_in_list` for an ability the server has a definition for, and `cast_refused`. Everything else is DEBUG. That covers ordinary play (cooldown, friendly target, out of range, no line of sight, small-bar slots 4 and 5) and forgeable values (an ability id with no definition, a target in another space, a bad toggle value). This is the same split as `useAbility`'s not-known path.
10. **Warmup re-check (review S1).** `warmup/tick.rs` applied the target rule to player casters only, and `fire_los` skips NPCs. A pet's owner-ordered warmup cast now gets both checks at fire time, so a target that turns friendly or goes behind a wall during the warmup is interrupted (`target_lost` / `no_line_of_sight`), not hit.

## Known gaps

- **Small-bar ambiguity (A-07, N6).** Values 1 and 2 are both valid stance ids and valid slot numbers. With the full list `[0, 1, 2]`, small-bar buttons 1 and 2 give Defensive and Aggressive, not Passive and Defensive; button 3 gives Aggressive. Only a client fix or a live capture of which bar sent the call can separate them. The pet info window works correctly.
- **`malformed_args` is not throttled.** One WARN per short packet. A Pattern D throttle keyed by `(player_id, reason)` is the follow-up if it shows up in practice.
- **CM 89 polarity is an assumption** (design decision 7). Nothing in the shipped client sends it.
- **`onPetAbilityList` carries no toggled state.** After a toggle the owner's bar is re-sent, but it cannot show which abilities are OFF. Whether the client marks them (the `PetToggled` ability flag) is unresolved.
- **A Fighting pet's leash still targets `spawn_position`**, and a Passive pet's autonomous behaviour is not stance-aware yet. Both are PT-05's. A target that turns friendly after the pet has engaged is PT-05's to drop (its `select_target` re-check); PT-04 no longer engages before the ordered cast fires.
- **`onErrorCode` rendering is unverified** (AT-E1: no Lua consumer). The codes are the closest `EConditionHandlerFeedback` names.

## Evidence

- `grant_kill_xp` sent `GrantXP { entity_id: attacker_id }` for any non-player target (`death/side_effects.rs:76-111` at base). A pet attacker sent it to the pet's id (no base session). A mob that killed a pet sent it to the mob's id. Both confirmed by mutation M1 below.
- `credit_single_target` read `player_id` from the caster (`kill_credit.rs:144` at base), so a pet caster skipped `EntityDeath` with a warn. The NPC AI fight tick called bare `handle_use_ability` (`npc_ai/fight.rs:371`), so a pet's AI kill never reached the credit code at all.
- `fire_entity_death` raises the event with `killer_entity_id` as the chain source and reads its mission context from that entity (`lifecycle/mod.rs:100-110`). `IncrementCounter` writes to the source entity's `counters` (`executor/counter.rs:27`). So the credited entity must be the owner, not the pet, for a KillCount chain to count.
- **Loot ownership does not exist.** `generate_loot_on_death` stores the drop on the corpse with no owner (`loot_drop.rs:29-113`). `handle_interact` and `handle_loot_item` gate only on range and the looter having a `player_id` (`loot.rs:120-155`). Python `Lootable.looters` only tracks who has the window open (`Lootable.py:49,115`). So "loot from a pet kill is owned by the owner" holds already: the owner is a player and may loot any corpse. PT-06 adds no loot-owner concept (that would be a new feature, tagging, for every kill) and pins only that a pet killer does not suppress the roll.

## Design decisions

1. **XP recipient decided in `grant_kill_xp`.** `kill_xp_payout(attacker, base_xp)` returns `(recipient, xp)` or `None`. The recipient is `credit_recipient(attacker)`. The scale is the attacker's `PetState::transfer_xp` when it is a pet, else 1.0. A zero, negative or non-finite scale pays nothing (fails closed, no XP minted). A non-1.0 scale rounds to the nearest XP.
2. **No `GrantXP` when nobody is credited** (NPC attacker, orphaned pet). Logged at `debug`, because it happens on every mob-kills-pet and is the designed outcome. The `info` "Granting kill XP" row gains `credited`, `via_pet` and `base_xp`.
3. **Mission credit via `credited_player(attacker) -> Option<(entity, player_id)>`**, one helper for the single-target, cone, ground and DoT credit paths. The event's `killer_entity_id` is the owner. The cone scratchpad (`last_aoe_deaths`) is still drained from the caster.
4. **Pets use the kill-credit wrapper from the AI fight tick; mobs do not.** Routing every mob through the wrapper would also start draining the health-below queue on mob casts. That drain has only ever run on player-driven paths, and changing that is outside this packet.
5. **Warmup tick gate widened to "credits a player".** A pet's warmed-up cast now credits its owner; a mob's still credits nobody.

## Known gaps

- **Warmup and DoT credit paths have no pet-specific test.** Both now use the same seam (`credit_recipient` / `credited_player`) as the tested paths; a pet with a warmup ability or a DoT does not exist yet (PT-S / PT-03).
- **A player killing a pet** would be paid `kill_xp(pet.level)`. The #444 gate stops players damaging a non-hostile pet (D-PT06), so this is unreachable today. If PvP or a hostile-pet case ever opens it, `grant_kill_xp` should refuse a pet target.
- **No loot tagging.** Whoever reaches the corpse first loots it, for pet kills and player kills alike. A tagging rule (first damager owns the loot) is a server-wide feature, not a pet one.
- **The owner's reticle** is not cleared on a pet kill (`attacker_is_player` is false for the pet). The owner never targeted through the pet, so nothing is stuck.

## Evidence

1. **The trainer cannot sell 2826 to a tester.** `try_open_trainer` (`crates/cell-interactions/src/cell/interactions/trainer.rs:131`) offers `trainer_abilities[(list, archetype)]`, and `evaluate_train` (`crates/cell-catalog/src/ability_tree/predicate.rs:138`) requires the ability in the player's archetype tree, the level, the prerequisites and the branch spend. 2826 is the Goa'uld Servant Lord capstone: level 50, prerequisites `{1643,2069,2846}`, 20 branch points (`archetype_ability_tree.sql`). 1643 is the Servant Lord root (level 1, cost 1). So the UAT path for 2826 is `.giveability 2826`; the trainer is still useful for a Goa'uld from level 1 (1643) and shows the pet roster in one place.
2. **The grant can persist cheaply.** Known abilities load from `sgw_player.abilities` at login; only the trainer purchase and the respec write that column, and the base session caches no ability list. A guarded one-statement append (the `train_ability.rs` shape without the debit) is enough. Respec (`respec.rs:65`) removes only `trained_abilities` from `abilities`, so a grant kept out of `trained_abilities` survives it.
3. **The name.** No shipped moniker says "Pet Trainer". 8000 `DN_npc_trn_TBD_Harset_Goa'uldAdvancedSkills` ("Goa'uld Advanced Skills") is in `data/cache/TextStrings.pak` (entry `_8000`, read with Python `zipfile`).
4. **The body.** Template 17 (Prisoner 329, Praxis-armoured Goa'uld male) is placed in this world by spawn 6, so the look is proven.
5. **`trainer_abilities.sql` is generated.** `generate_seed.py:662` regenerates list 1 and appends every other list's rows verbatim (no comments). The list-350 rows use its exact format.
6. **Ranges.** PT-S's `pet_templates_are_never_placed_in_spawnlist` required every template in 350-369 to be class `pet` and unplaced; a placed trainer at 360 fails it (proof below). The packet asks for the trainer in 350-369, so the pet guards now cover 350-359 and 360-369 are the campaign's placed NPCs.
7. **Non-GM `.`-text.** Before PT-07 a non-GM's `.pet summon 2826` was broadcast as chat to everyone nearby, with no feedback to the sender (`chat.rs`, test `non_gm_dot_text_is_normal_chat`).

## Design decisions

1. **Trainer NPC.** Template 360 (class `mob`, faction 1, `INT_Trainer` 128, list 350, name 8000, template 17's body, event set 570), spawn 450 (tag `DebugHub_PetTrainer`) on the hub line one slot past the crate, heading to the room centre. List 350 is keyed to `ARCHETYPE_Goauld` only: rows for other archetypes would log `trainer_offered_unbound` on every open and show permanently greyed rows. No dialog, so no `DIALOG_OVERRIDES` or pinned-id edits.
2. **`.pet summon` resolution.** A `pet_summons` ability id first (2826 → template 350, `summon_ability_id` recorded), else any cached template (recorded as ability 0; a non-`pet` class is spawned as a pet and the feedback says so). Every check runs before the caller's current pet is dismissed, so a refused summon never leaves the GM petless. The replace and `.pet dismiss` use `despawn_pet(.., Dismissed, ..)`, as PT-02/PT-03 ask. No warmup and no summon VFX (that is PT-03's ability path).
3. **Ownership.** `.pet dismiss`, `.pet stance`, the replace in `.pet summon` and `.pet info` without a selection act only on `owned_pets(caller)`: each candidate from `pets.pets_of(caller)` must also pass `SpaceManager::owned_pet`, which checks the pet is live and that the caller is the player who summoned it (main's per-pet summoner identity). No client-supplied pet id is read. A pet registered to the caller's entity id by an earlier holder of that id is refused (logged once by `owned_pet`, `event = ownership_rejected`, `reason = owner_identity_mismatch`) and left for the teardown sweep. `.pet info` reads a selected pet of any owner (read only, logged with `subject_player_id`, taken from the summon-time identity since the owner id may have been reused).
4. **Stance.** Parsed wide, then `i8::try_from` and `PetStance::try_from`, then `pet.allows`; 3, -1, 258, 300 and `x` are refused (258 must not truncate to 2). `onPetStanceUpdate` goes to the owner only through `WitnessEntityMethod`. PT-04's CM 90 handler lives in `cimmeria-cell-methods`, which `cimmeria-cell-console` cannot call, so the console sets the stance itself.
5. **`.giveability` persists through the base.** `CellToBaseMsg::GmGrantAbility { entity_id, player_id, ability_id, gm_entity_id, gm_player_id }` → `handle_gm_grant_ability`: one `UPDATE sgw_player SET abilities = abilities || $1 WHERE player_id = $2 AND NOT (abilities @> ARRAY[$1])` → `BaseToCellMsg::GmAbilityGranted` → the cell adds to the known set (not `trained_abilities`), sends `onKnownAbilitiesUpdate` and re-sends a pinned trainer. The base checks that the subject's session still plays `player_id` (entity-id reuse), sends the GM line only while `gm_entity_id` still plays `gm_player_id`, and the cell mirror ignores a `player_id` mismatch (the `respec.rs` shape). Only the console builds the message; the base does not re-check GM rights (doc comment on the variant). The subject is the selected player in the caller's space, else the caller, and the fallback is named in feedback. The feedback says the grant is saved to the character.
6. **Non-GM refusal.** A non-GM `.`-line whose first word is a registered command is consumed and answered ".X is a GM command; you do not have GM rights" (no arguments echoed). The enforcer preferred this over gating only `pet`/`giveability`: a GM demoted mid-session would otherwise broadcast `.giveability 1234`. The gate and the dispatcher share `find_command`. It logs one DEBUG line, not `playtest_friction::console_rejected`, whose streak detector is a GM-hunting WARN a player could raise by typing.

## SigNoz queries for pets UAT (for the handoff)

Logs explorer, service `cimmeria-server`; `body` is the message. Replace `<acct>` with the tester's account id (from any login line), `<pet>` with a pet entity id.

| Question | Filter |
|---|---|
| Everything one tester did with pets | `attributes.target LIKE 'pets.%' AND attributes.account_id = <acct>` |
| Why a GM `.pet` command did nothing | `attributes.target = 'pets.command' AND attributes.decision_outcome = 'gm_refused' AND attributes.account_id = <acct>` (group by `attributes.reason`) |
| One pet's whole life (summon, commands, despawn with reason) | `attributes.target LIKE 'pets.%' AND attributes.pet_id = <pet>` |
| Why a pet vanished | `attributes.target = 'pets.lifecycle' AND attributes.decision_outcome = 'despawned' AND attributes.owner_id = <owner entity>` (read `reason`: `dismissed`, `owner_dead`, `owner_left_space`, ...) |
| Failed summons | `attributes.target = 'pets.lifecycle' AND attributes.decision_outcome = 'summon_failed'` (read `reason`) |
| Stance changes | `attributes.target = 'pets.command' AND attributes.event = 'stance_changed'` |
| Was `.giveability` saved | `body LIKE 'GmGrantAbility%' AND attributes.subject_player_id = <player>` (read `decision_outcome`, `persisted`, `reason`) |
| A player tried a GM command | `attributes.reason = 'not_gm' AND attributes.account_id = <acct>` |
| Refusal counts by reason (dashboard) | `attributes.target LIKE 'pets.%' AND attributes.reason EXISTS`, group by `attributes.target, attributes.reason` |

## Evidence

- **One level writer.** `handle_grant_xp` is the only code that writes `sgw_player.level` (a grep for `level = $` / `SET … level` over `crates/` finds only its UPDATE). Every level source reaches it through `CellToBaseMsg::GrantXP`: mob kills (`cell-combat/.../death/side_effects.rs`), content-chain `GrantXP` (`cell-content/.../executor/mod.rs:515`), and the GM `.givexp` / `gmGiveXp` (`cell-console/.../give.rs:89`, `gm/give.rs:68`). There is no GM set-level command: the cell-console command tables have no level setter. So no other path needs routing through the grant.
- **ASP has no session cache.** `ConnectedClientState` holds level, XP and training points but not ASP; the crafting code reads ASP from the row every time (spend, GM grant, login sync). So the grant only writes the row and pushes; there is nothing in memory to mirror.
- **New characters.** `character_create.rs` did not name `applied_science_points`, and the column default is `0` (`db/sgw/Players/Tables/sgw_player.sql:40`). Training points use the same shape: the column defaults to 0 and the INSERT binds `STARTING_TRAINING_POINTS`.
- **Seeded characters.** The nine seeded rows (player ids 62-70) are all level 1 with `applied_science_points = 0` inserted explicitly, so no column default would reach them.
- **Level-up threshold is strict.** `apply_level_ups` raises the level while `total_xp > LEVEL_XP[level]`, so reaching exactly 100 XP stays level 1; 101 is level 2. The tests use 101.

## Design decisions

- **One statement.** `asp_earning::persist_grant` replaces the old `UPDATE … SET exp, level, training_points`. A CTE reads the row's level and ASP `FOR UPDATE`, then one UPDATE writes XP, level and training points and adds `GREATEST(new_level - level_before, 0) × APPLIED_SCIENCE_POINTS_PER_LEVEL` to `applied_science_points`, saturated at `i32::MAX` like the GM grant, `RETURNING` the level and ASP before and the ASP after. A level is never committed without its points.
- **Counted against the row, not the cache.** The levels gained come from the row's level under the lock, not from `levels_gained.len()` (which comes from the session cache). If the cache is stale and the row already holds the level being written, the write earns nothing, so a point is never paid twice for the same level. The XP bundle still reports the cache's levels, as before.
- **No change for a de-level.** `GREATEST(…, 0)`: a write that lowers the level (not possible today, only a stale cache could do it) earns nothing and takes nothing back.
- **Push after the bundle, as its own packet.** `push_asp` (the CR-03 helper) sends `onEntityProperty(2, total)` after the XP bundle, only when the level rose. It carries the `push_failed` WARN seam (`what = asp`) already. Folding the property into `build_grant_xp_bundle` would keep a level-up to one packet, but it would change the pinned burst shapes of five existing tests and lose the crafting send seam; a level-up is now two packets (recorded in `mercury-bundle.md`).
- **Starting point.** `createCharacter` binds `STARTING_APPLIED_SCIENCE_POINTS` (1), mirroring training points; the column default stays 0, so the many test fixtures that insert minimal players (and the CR-04 `no_asp` refusal tests) are unaffected. The seed sets 1 for the nine level-1 characters.
- **Telemetry.** `event=asp_earned` (INFO, target `crafting`) with `account_id` (from the session), `player_id`, `entity_id`, `level_before` / `level_after`, `asp_before` / `asp_after`, logged once the write commits and only when the level rose. The missing-row branch of `handle_grant_xp` became a structured WARN: `event=persist_failed`, `phase=grant_xp_update`, `reason=rows_affected_zero`, `rows_affected=0`, `expected=1`, with the identity. It keeps its original (module) target, because the failed write is the XP grant's; the observability row says so.

## Known gaps and open questions

- **Backfill (open question for the owner).** Characters that levelled before this change keep whatever ASP they had, usually 0: a level-10 character has 0 instead of 10. No `db/scripts` migration was written (repo rule). Options: (a) nothing, since the colo database is rebuilt from the seed on deploy and the seeded characters are all level 1; (b) a one-off lazy top-up at login, `asp = max(asp, level - learned disciplines)`, which is wrong for characters that received GM grants and then spent them, so it needs an owner call; (c) an operator SQL run by hand. Recommendation: (a), unless a long-lived database with levelled characters needs to keep them.
- **Two packets per level-up.** See the design decision; if the owner wants a level-up to stay one packet, the ASP property can move into `build_grant_xp_bundle` at the cost of updating the five burst-shape tests.
- **No in-client record.** The discipline trainer's live count after a level-up has not been seen in a client (CR-14 UAT).
- **Concurrent grants.** The base's cell-message dispatch awaits `GrantXP` inline (`base-world-entry/.../cell_dispatch/mod.rs:138` routes it to `progression_dispatch::grant_xp`), so grants for one player do not interleave today. If they ever did, two grants computed from the same cache could write a lower level after a higher one; that level loss is pre-existing for XP and training points. The new statement would then earn nothing on the lowering write and would pay the lost levels again when the player re-levelled from the lowered row. Writing `level = GREATEST(level, $2)` would close both; it changes the XP path's semantics, so it is left for a separate change.

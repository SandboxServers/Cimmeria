## Design decisions

- **Directory, not one file.** `alloy/` holds `rules.rs` (pure, no database), `job.rs` and `mod.rs`, so the rules are unit-testable against a hand-built catalog and every file stays well under 500 lines. The module path is still `crafting::alloy`.
- **What is consumed.** The component is consumed by design (one 5192 from bag 15, then bag 1) and is checked at the request but **not named** in the transaction: a queued alloy whose named component an earlier alloy used up still completes while the bags hold another (CR-07 does the same for its components). The elementary components are consumed **instance-exact** (`consume_named`). The count the client checked is the named stacks' quantities, so the server takes exactly the met quality's count from the named stacks in request order (Good stacks of 3 and 4 give 3 + 2). A stack of the same design that the request did not name is never touched.
- **What is not consumed.** Named items of a quality whose count was not met (allowed: the native check only rejects when zero or two-plus buckets are met), Poor items, and surplus beyond the count. They are validated (owned, carried, right tier) but not named in the plan, so they stay put.
- **Order of checks.** Catalog lookup, known, `is_alloy`, the discipline in the catalog and known (PR #904 review: known before `is_alloy`, so an unlearned craft blueprint is also `unknown_blueprint`; a discipline missing from the catalog is the `alloy_discipline` data fault); then the current-tier item (owned, carried, design, enough in the two bags); then each elementary item (owned, carried, tier) in request order; then the counts. An unknown blueprint and an unlearned one share `unknown_blueprint`, so the reply does not reveal which blueprints exist.
- **Refusal reasons.** The four the packet names, plus `unknown_blueprint` and `discipline_unknown` (the names and texts proposed to CR-07, which needs them too). The transaction's existing `component_missing`, `component_not_in_crafting_bags`, `component_mismatch` and `not_enough_components` are reused at the request for the current-tier and elementary items. `count_not_met` and `multiple_buckets` carry the per-quality sums as `elementary_counts`.
- **Resync after every request refusal** (D-CR14), because the page empties its slots on confirm (C-33). It uses the transaction's `resync_inventory` with `job_id = 0`, the same "no job" id the transaction tests use.
- **Data faults** (a blueprint without a discipline, component or product, a non-positive product quantity, an item missing from the catalog) log `lookup_failed` (WARN) and send the `unavailable` line; they are not rule refusals. A non-positive quantity would otherwise consume the inputs and grant nothing, because the transaction skips non-positive grants.
- **Forged lists.** A list of more than ten elementary ids is dropped before any database read, logged as `malformed` (WARN, `reason = too_many_elementary_items`), per D-CR25. Repeated ids count once (a `HashSet`).
- **Bar id.** The job's `timer_id` is the blueprint id, as the legacy `onCraftingStarted(blueprintId, …)` did for alloying.
- **Success line.** "Alloying complete: 2 x Blend (Bio-Medical Alloy)." on `CHAN_FEEDBACK`, sent after the commit through `send_to_player` (`client_sync_failed what=success_line` on failure). The product name is read with the request (`resources.items.name`, trimmed; `item <id>` if missing).
- **Blueprint and discipline are re-checked at completion**, before the transaction (as CR-07 does): a respec during the bar refuses the job with `unknown_blueprint` / `discipline_unknown` through `reject_at_completion`, plus a resync. An unreadable state is `lookup_failed phase=alloy_completion_state` (WARN) and `induction_failed`.

## Telemetry

Everything logs under target `crafting`; the `crafting` row of `docs/architecture/observability.md` is updated.

- `request` and the `crafting.request` span are CR-01's; the whole argument list is in `args`.
- `rejected` (INFO) with `verb = alloying`, `account_id`, `player_id`, `entity_id`, `reason`, and per reason: `blueprint_id` (`unknown_blueprint`, `not_alloy`, `discipline_unknown`), `discipline_id`, `item_id` / `type_id` / `tier` / `required_tier` (`wrong_tier`), `elementary_counts` = `normal:N,good:N,great:N,fantastic:N` (`count_not_met`, `multiple_buckets`), and the component reasons' existing fields.

- Metrics: `crafting_requests_total{verb=alloying, outcome=accepted}` once per `Started` or `Queued` submit (the engine's `QueueFull` refusal is already counted as rejected; `NotConnected` has no player to answer); `crafting_rejections_total{verb=alloying, reason}` through `reject`; `crafting_jobs_total` by the engine.

## Known gaps

- **The completion re-check is not under the player row lock.** It reads the crafting state just before the transaction, so a respec landing in the milliseconds between the read and the commit still gets the product. Closing it fully needs the transaction to re-check under its own locks.
- **Spend can lose an alloy's expertise** (authority advisor finding 4; pre-existing, not introduced here). `save_crafting_state_in` rewrites every expertise row, so a spend that read expertise before an alloy committed its +1 writes the old value back. The spend path locks `sgw_player` and the crafting transaction deliberately does not, so they do not serialize. Only the player's own expertise is affected. Fix: have spend update expertise rows in place, or take the player-wide advisory lock the transaction takes.
- **Walking away from the station during the bar still completes the alloy**, as for every induction verb; the gate is checked at the request only.
- **A Poor item in the request** is accepted and left untouched. The client cannot slot one (no Poor radio), and the native map has no Poor bucket; whether the native check would count a Poor item somewhere is not decompiled in detail. Left as "counts toward nothing".
- **`feedback/reason.rs`** grows to about 480 lines with the six variants. CR-07 and CR-08 add more, so the next packet to land may need to split `text()` and `compared()` out.

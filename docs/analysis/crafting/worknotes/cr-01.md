## Evidence

- **`CraftingOptions` order.** `alias.xml:513-520` declares `crafting`, `research`, `reverseEngineering`, `alloying`, and a `FIXED_DICT` goes on the wire as its fields in declaration order with no header. The task prompt's order (craft, alloying, research, reverseEngineering) does not match the def. The def order is implemented and pinned by `crafting_options_sections_follow_alias_xml_order`. The client unpacker (`0x00e49180` → `0x00e47250`) was not checked; that is CR-E1 question 2.
- **Array encoding.** A `u32` count, then the elements, as in every other entity-method array this server sends (`onUpdateItem`, the old inline 139 builder).
- **Seed counts** match audit C-20 to C-24 on a fresh `sgw_cr01`: 78 disciplines, 498 blueprints, 2,556 component rows, 40 alloy blueprints (all quantity 2, all `requires_elementary_components`). Blueprint 21 has no components, blueprint 412 has sets 1-4, `Kicker` is on exactly items 5668-5671, item 5481 has `tech_comp` 20 and disciplines {21, 22}, and item 5192 is tier 2, Good.
- **`HasCraft` / `DoesNotHaveCraft`** (224/225) share their values with `AbilityPulseCheckFailed` / `AbilityPulseCheckPassed` in the defs. They are not defined as constants, and `has_craft_feedback_values_collide_in_the_defs` pins the collision.
- **Player-visible text path.** Players see method 28 (`onPlayerCommunication`) on channel 9 (`tell`) with speaker `SYSTEM`, which is what the base's `send_gm_feedback_to_client` sends. It has no GM check, so the crafting rejection reuses it. `onErrorCode` alone is not known to show anything (AT-E1; CR-E1 question 3).

## Design decisions

- **Catalog.** `CraftingCatalog { disciplines, blueprints, items }` holds public `HashMap`s keyed by id. `from_rows` builds it (the grouping is unit-tested) and `load` fills it with four queries. `ComponentSet`s are sorted by `set_id` and components by `item_id`. `items` covers every `resources.items` row, because research and reverse engineering take arbitrary gear. The quality column is read as its enum label and mapped to `ItemQuality` (1000-5000). `shared_crafting_catalog(pool)` is the process-wide `OnceCell`, as for the ability tree. The cell warms it at startup; nothing stores it on `SpaceManager` yet (CR-05 can hold the `Arc`).
- **Constants.** `CraftType` is an enum with `bit()`, `allowed_by(mask)`, `entity_flag()` and `TryFrom<u8>` (a mask of several bits is not a verb). `ItemFlags(u32)` is a newtype with associated constants and `is_researchable`, `is_reverse_engineerable` and `is_kicker`. It offers no predicate for `ELEMENTARY_COMPONENT` (C-24). The duplicate `ITEM_FLAG_CanBeSold` constants in `vendor/` are untouched.
- **Wire.** The serializers are free functions that return argument bytes, like the ability-tree ones. 136 stays in `cimmeria-entity` and is re-exported as `update_discipline_args`. `CraftRequest` and `CraftVerb` live in `crates/wire/src/crafting/request.rs` and are re-exported from `cell::messages`. `CellToBaseMsg::Crafting(CraftRequest)` is the only change to `cell_to_base.rs`.
- **Parsing.** `parse_verb(method_index, args)` in `player/crafting/mod.rs` is strict. A truncated argument, a trailing byte or a forged array count is an `ArgsError`, logged at WARN (`crafting`, `event = "malformed"`) and dropped without feedback. The 2009 client always sends the def's shape, so only a forged or corrupted packet lands there. An array count is checked against the bytes present before anything is allocated.
- **Forward.** `forward.rs` resolves `player_id` (a WARN and a drop when there is none) and sends `allowed = NO_STATION_GATE` (0), with a `TODO(CR-05)`.
- **Base.** `request.rs::handle_craft_request(request, &CraftCtx)` logs `request` with every argument (`args = ?verb`) and answers each verb with `CraftReject::NotAvailableYet`. `CraftCtx` carries the pool, `cell_tx`, the transport and the session maps, so later verbs never touch the dispatch arm. `feedback.rs::reject(entity_id, player_id, &CraftReject, transport, connected, entity_to_addr)` logs `rejected` with its `reason`, sends the text line and, when `error_code()` maps a code, `onErrorCode` (system 0, instance 0, the code). The signature is wider than the ledger's `reject(entity_id, reason)` because the base has no global client handle.
- **Dispatch arm.** One arm in `cell_dispatch/mod.rs` rather than a new family module: there is a single variant, and `request.rs` does the per-verb routing.
- **Sentinels (#800).** `persistence.rs` moved from `0x7000_2000` to `0x7000_C000` (it uses up to `+0xB55`), and `handlers.rs` from `0x7000_3000` to `0x7000_CC00`. The non-DB tests use plain small ids, so the `0x7000_Cxxx` block holds only live-DB rows.
- **Observability.** `crafting=debug` and `cimmeria_wire::crafting=debug` in `OTEL_FILTER`, a paragraph in the filter's doc comment, `("crafting", INFO)` and `("crafting", WARN)` pinned in `scan_finds_known_targets`, and a catalog row in `docs/architecture/observability.md`.

## Known gaps

- `CraftReject::error_code` maps no code for the one CR-01 reason, so the `onErrorCode` branch of `reject` has no test yet. CR-04's first code-mapped reason (214) should add one.
- `crates/wire/src/cell/messages/cell_to_base.rs` was 786 lines (over the 700-line hard cap) before this packet and is 793 now. Splitting it touches every variant and belongs in its own change.
- The new dispatch-table section links to `../analysis/crafting/audit.md`, which exists on `main` only once the plan PR (#851) merges. Merge the plan first.
- A malformed or player-less request is dropped without player feedback, by design: only a forged packet can produce one.
- Other docs still cite `player/crafting.rs` line numbers: the CAT-F findings (C-64, CR-13) and `docs/audits/telemetry-audit-2026-06-01.md` (historical). Chain-replay test comments that list `0x7000_2000` / `0x7000_3000` as used ranges are left alone; `0x7000_2000` is still used by `engine_loader.rs`.

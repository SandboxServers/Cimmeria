## Evidence

- **The client's send path.** `respecCrafting()` (100, no arguments) is sent once, only from the Yes of the dialog that 112 opens (`Crafting.lua:181-191`, `crafting-client-ui.md` Q1). No client UI opens the dialog. So the server must open it, and a 100 is only a confirmation when a prompt is outstanding.
- **What 137 does on the client.** It zeroes the expertise of every discipline the client knows (audit C-37); the trainer draws each discipline's expertise and the "can learn" arrows from `getDisciplineExpertise` (`DisciplineTrainer.lua:110`, `:126`), so the tree reads as unlearned. Nothing on the client clears blueprints.
- **Legacy.** The Python server never implemented respec (`crafting-client-ui.md` §1), so there is no legacy behaviour to match.
- **`.`-console.** Before this packet, every `.`-line from a non-GM fell through to chat (`chat/mod.rs`), and the console registry is GM-only. `.respeccraft` needed a player path.
- **Chat flood limit.** A `.`-line is a `sendPlayerCommunication`, which the base throttles before the cell forward (`crates/base/src/base/dispatch/tests/chat_flood_limit.rs`), so `.respeccraft` cannot be used to hammer the database.

## Design decisions

- **Two messages, one per step.** `.respeccraft` crosses as a new `CellToBaseMsg::RespecCraftOpen { entity_id, player_id }` (payload in `wire/src/crafting/respec.rs`, as the rules for the over-cap `cell_to_base.rs` require). The Yes is the existing `CraftVerb::Respec`, routed in `request.rs` next to `Spend`. `CraftVerb` is unchanged.
- **Player command path.** `console::player_commands::handle_player_command` runs in the chat `CHAN_SAY` arm before the GM gate. Its list is only `respeccraft`. It acts on the speaker, takes no target, consumes the line, refuses arguments with a line, and is not in the GM `COMMANDS` registry (`.help` does not show it). Documented as an ADR amendment in `dev-console-channel.md`.
- **Where the pending respec lives.** `CraftingSessionOptions::pending_respec: Option<PendingRespec { player_id, expires_at }>` on the session's `ConnectedClientState::crafting_options`. It dies with the connection, needs no edit to the seven `ConnectedClientState` literals, and a character switch resets it (`play_character.rs` resets the session's crafting state). It is not an input to 140.
- **Taking the pending respec.** `pending::take` always empties the slot, under the session mutex, before any database work: `Open` (same player, inside 60 s), `Expired`, or `Nothing` (none, or another character's). So a replayed or second 100 is `no_pending_respec`. A failed transaction also consumes it; the player types `.respeccraft` again.
- **Open step.** Reads the state without a lock; nothing known and no expertise rows → `nothing_to_respec`, no prompt, nothing opened. Otherwise records the pending respec (re-opening replaces it, `replaced = true`) and sends `onCraftingRespecPrompt(0)`.
- **Transaction** (`respec_in_db`): `take_inventory_locks(player, [])` (the player-wide advisory key 0) first, then `load_crafting_state_locked` (`sgw_player` `FOR UPDATE`), re-check nothing-to-clear, read `applied_science_points_spent`, `UPDATE sgw_player SET discipline_ids = '{}', applied_science_points = LEAST(asp + refund, i32::MAX), applied_science_points_spent = 0`, `DELETE` every expertise row, commit. The refund is the ASP spent on disciplines since the last respec (review-driven addition 3; the first version refunded one per distinct id in `discipline_ids`). `blueprint_ids` and `racial_paradigm_levels` are not written.
- **Serialization with completions.** Inside its transaction the respec takes key (player, 0), then locks `sgw_player` `FOR UPDATE` through `load_crafting_state_locked` before any write, and holds both until commit. A craft completion that re-checks blueprint and discipline knowledge by reading `sgw_player` `FOR SHARE` after its inventory rows therefore waits for the respec to commit and sees the cleared state. A completion that holds key 0 first makes the respec wait instead.
- **Lock order.** Respec touches only the `sgw_player` row and the player's `sgw_player_discipline_expertise` rows, no item rows. It still takes the player-wide advisory key before the player row, as the campaign's lock order requires, so it queues behind a research completion that holds item rows and will wait for the player row.
- **After the commit.** `onDisciplineRespec` (137), `onUpdateKnownCrafts` (139, the unchanged list, per D-CR16), the ASP total, as three single reliable sends through `sync` (`push_discipline_respec`, `push_known_crafts`, `push_asp`). No 136 or 138: 137 zeroes the expertise, and paradigms do not change.
- **Refusals** (new `CraftReject` variants, no `onErrorCode`): `NothingToRespec` "You have no crafting disciplines to unlearn. Nothing was changed.", `NoPendingRespec` "No crafting respec is waiting to be confirmed. Type .respeccraft to start one.", `RespecExpired` "The crafting respec was not confirmed within 60 seconds. Type .respeccraft to start again."; failures use the existing `Unavailable` ("Crafting respec is unavailable right now. Nothing was changed.").

## Review-driven additions

Asked by the coordinator after the CR-09 (alloy) review, on the same branch after the rebase onto CR-15 (`479b06061`).

1. **Respec drops the induction queue.** `respec::confirm_with` calls `CraftingSessions::drop_player(entity, DropReason::Respec, "respec_confirmed")` after taking the open respec and before `respec_in_db`. New `DropReason::Respec`, label `respec`. Dropping before the transaction (not after the commit) closes the window where a deadline fires between the commit and the drop. A completion already running holds the player-wide key, so the respec waits for it; its expertise step only updates rows that exist, so a completion that lands first raises expertise the respec then clears. If the respec is refused after the drop (nothing to clear, database failure), the queue is still gone: the jobs never ran, so nothing was consumed, and `queue_dropped` records it. `handle_respec_confirm` uses the global engine; `confirm_with` takes one so the test can drive a `ManualScheduler`.
2. **Lost update against the completion transaction.** The completion takes the player-wide advisory key and changes expertise without locking `sgw_player`. Reading the code, the lost update is in the **GM expertise grant** (`handlers::grant_expertise_in_db`), which reads the state and rewrites every expertise row with `save_crafting_state_in`: a grant that read 78 at 50 while a completion's +1 was uncommitted wrote 50 back. Spend does **not** lose an update: it writes only the learned discipline's row (`INSERT … ON CONFLICT`), never `save_crafting_state_in`. Its real exposure is a stale prerequisite read (a check against 49 while a +1 to 50 is in flight), which refuses a request that should pass. The smaller correct change for both is the one the campaign already uses: take `take_inventory_locks(player, [])` (key 0) before `load_crafting_state_locked`, in spend, respec and the GM grant. Updating rows in place would fix the grant but not the spend's stale read, and would change `save_crafting_state_in`, which `.allcraft` and `item_use` share. `.allcraft` sets every discipline to 100, which a racing +N cannot exceed, so it was left alone; `item_use` already takes the locks first.

3. **Refund bound to ASP paid (blocking, from the server-authority review).** The first version refunded one point per discipline held; a GM expertise grant or `.allcraft` adds disciplines for free, so a respec minted points. Design: a persisted counter, `sgw_player.applied_science_points_spent integer DEFAULT 0 NOT NULL` (schema in `db/sgw/Players/Tables/sgw_player.sql`; the seed inserts name their columns, so they take the default; no `db/scripts` migration, the colo rebuilds from the schema). The spend raises it in the same `UPDATE` that takes the point; the respec reads it under the row lock (`phase=read_spent`), refunds exactly it and sets it to 0 in the same `UPDATE`. `respec` logs it as `asp_refund`. Why a counter and not a list of paid disciplines: the refund only needs the number, one integer cannot drift from a second array, and a paid-disciplines array would need every writer of `discipline_ids` (GM grant, `.allcraft`, respec) to keep it in step. The counter is always at most the number of known disciplines, because only a spend raises it and only a respec (which clears them all) lowers it. A character that learned disciplines before this column existed has 0 and refunds nothing (never more than paid). D-CR02 still holds: the respec is free and keeps blueprints and paradigm levels; "full reset" gives back what was paid.

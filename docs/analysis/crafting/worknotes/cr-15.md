## Design decisions

- **Seed table, one source.** `resources.crafting_item_effects (item_id, blueprint_id, racial_paradigm_id)`, exactly one effect per row (CHECK), unique per `(item_id, blueprint_id)` and `(item_id, racial_paradigm_id)`, FKs to `items` (cascade), `blueprints` and `racial_paradigm` (RESTRICT on delete, so deleting a mapped blueprint fails loudly). The seed is generated by `tools/crafting/generate_item_effects.py` from the CSV and the item and paradigm seeds, with pinned counts and a `--check` mode. Kept in `Items/` because it is keyed by item.
- **Routing, not an event handler.** `handle_use_inventory_item` adds `EXISTS (... crafting_item_effects ...) AS is_crafting_item` to its existing instance query (no extra round trip) and, after the bandolier branch, hands such items to the crafting use and returns. `OnItemUse` is never fired for them, so a content chain cannot consume one a second time (the double-consume trap), and a live-DB guard fails if an `item_use` trigger targets one. Both advisors agreed.
- **Transaction owner.** The decision and the transaction live on the base in `base-session` `crafting/item_use/` (crafting state is there, and the outbox is too). `base-methods` owns only the inventory client sync after the commit (`onRemoveItem`, `send_full_inventory_update`, dispatching the outbox row), because `send_on_remove_item` is private to the inventory module and `base-session` cannot depend on `base-methods`.
- **One transaction** (`item_use/transaction.rs`): advisory lock `(player_id, INV_MAIN)` first (the trade and vendor convention, from the server-authority review), then the item row `FOR UPDATE` with `character_id` in the `WHERE` (a row traded away after the caller's ownership check is refused, never consumed from its new owner), carried-bag check, stack check, effect rows, `load_crafting_state_locked`, decide, consume one (DELETE when the stack is 1, else `stack_size - 1 WHERE stack_size > 1`, `rows_affected == 1`), `save_crafting_state_in`, the `InventoryItemRemoved` outbox row when the instance is gone, commit.
- **Carried bags are main (1) and crafting (15).** The items advisor proposed 15 only, on the grounds that 1 is not in these items' `container_sets`; but `gmGiveItem` puts them in bag 1, so a 15-only rule would refuse every GM-granted item. Bank, buyback (a sold item could otherwise teach and then be bought back), equipment slots and org banks are refused with `not_carried`.
- **Partial teach.** An item that names a known and an unknown blueprint teaches the unknown one and is used; it is refused only when all are known (D-CR22 "a known blueprint" read per item).
- **`target_id` is ignored.** The effect comes only from the seed and applies to the user.
- **Feedback texts:** "You already know this blueprint. The item was not used." ("these blueprints" for 8882); "Your <paradigm> racial paradigm is already at 10, the maximum. The guide was not used."; "That item is no longer in your inventory."; "Move that item to your crafting bag to use it."; failures use the existing `Unavailable` line ("Using that item is unavailable right now. Nothing was changed.").
- **139 carries the saved list** (the state the transaction wrote), not a re-read.

## Known gaps

- **No loot placement.** The only loot table with crafting drops is the debug-hub crate (table 3). Adding guides or Blueprint items there, or anywhere, is harmful today: loot grants into the first `container_sets` entry, 17 (bank), where the use refuses them, and a refused grant would destroy the item (CR-16, `loot.rs:185`). Loot placement should follow CR-16. Until then the sources are GM grants (into bag 1, usable) and the CR-11 vendor.
- **96 unresolved Blueprint items** are not seeded (D-CR26); using one fires `OnItemUse` as any other item and does nothing.
- **Trade window + stack.** Trade holds live in cell memory and the swap does not compare `stack_size`; for a stack, "offer 5, use 4 before accept" would hand over 1. All 198 items have `max_stack_size = 1`, so it does not arise here; the same hole exists for split and move (server-authority review, should-fix 5). Not in scope.
- **No in-client check** that the client offers "Use" on these items (CR-E2 OQ1). The client sends `useItem` for right-click on any item as far as the Rust path is concerned.
- **Advisory lock** unproven by test (above).

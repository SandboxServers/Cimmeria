## Evidence

- **What login sent before.** The `mapLoaded` bundle sends `onEntityProperty(2, applied_science_points)` and 139 from the `sgw_player` row (`map_loaded.rs`, step 20 and 23). Nothing called `load_crafting_state` and nothing sent 136 or 138 (audit C-05). The legacy server sent the same two and no more (`SGWPlayer.py:510`, `:524`), so relogging lost the client's disciplines, expertise and paradigm levels there too.
- **The client reads the ASP property live.** `DiscTrainMod.onModLoaded` reads `getUnitProperty(Unit.Player, Property.AppliedSciencePoints)` at load and `onPropertyUpdate` replaces the shown count with the value (`DisciplineTrainer.lua:24`, `:49-54`). So the property must carry the total (C-57). `onDisciplineUpdate` and `onParadigmUpdate` redraw the tree (`:246-255`).
- **The client never updates its own state on a click.** `onTrainDiscipline` only calls `requestSpendSciencePoint` (`:229-231`); the tree colours come from `getRacialParadigmLevel` and `getDisciplineExpertise` (`:117-128`). A refused spend therefore leaves nothing on the client to correct (relevant to D-CR14's "client state correction").
- **Paradigm ids.** `resources.racial_paradigm` is 1 Common, 2 Human, 3 Goa'uld, 4 Asgard, 5 Ancient. The persistence layer stores `racial_paradigm_levels[i]` as paradigm `i + 1` (`persistence/mod.rs`, the load loop); the column default `{5,1,1,1,1}` follows that encoding.
- **Seeded characters.** Every seeded `sgw_player` row inserts `racial_paradigm_levels = ARRAY[]` explicitly (C-27), so the column default does not reach them; the load-time default does.

## Design decisions

- **Where the login sync runs.** After the `onClientReady` burst, next to `push_contact_lists_on_login`, not in the `mapLoaded` bundle. The entity is live and its UI loaded by then, the bundle's fragment burst does not grow, and `onClientReady` runs on every world entry (initial login, same-world respawn and the synthesised cross-world `mapLoaded`). One reliable bundle carries it: 136 per known discipline in `discipline_ids` order, 138 for each paradigm by id, 139, then the ASP property.
- **ASP and 139 are sent twice at login.** The `mapLoaded` bundle still carries them from the row (left alone: `map_loaded.rs` is contended and they are the first paint, as in the legacy server). The login bundle re-sends them from `load_crafting_state`. Both are absolute values, so the repeat is harmless; it keeps `push_login_bundle` a complete state push that later packets (respec, reanchor replay) can reuse.
- **140 is not sent.** CR-05 owns `onUpdateCraftingOptions`; the client's default disables every tab until then.
- **`sync/` API.** `CraftClient { transport, connected, entity_to_addr }` (Copy) plus `push_discipline`, `push_paradigm`, `push_known_crafts`, `push_asp`, `push_login_bundle(state)` and `push_crafting_on_login(entity, player, db_pool, client)`. The pure `crafting_state_messages(state)` and `build_crafting_state_bundle` are what the byte tests pin. Method constants come from `cimmeria_wire::cell::client_methods` (the authoritative table; `mercury::method_idx` has no 138).
- **Paradigm defaults.** `DEFAULT_RACIAL_PARADIGM_LEVELS` in `cimmeria-entity`; `CraftingState::apply_default_paradigm_levels` fills an empty map and leaves any stored level, even a partial list, alone. Every load path applies it (`load_crafting_state`, the missing-row default, and the new locked load). New characters get the same array from the column default; `character_create.rs` does not name the column, so it needs no change. Nothing is written back until a save (the GM expertise grant, respec) persists the map; no migration.
- **Locked load and in-transaction save.** `load_crafting_state_locked(&mut PgConnection, player_id) -> Option<CraftingState>` reads `FOR UPDATE`; `save_crafting_state_in` writes inside the caller's transaction. Both count on `crafting_persist_attempts_total` like the pool versions.
- **GM grants (adjacent fix, same class as C-06).** `handle_grant_applied_science` is now one `UPDATE … SET applied_science_points = LEAST(… + amount, i32::MAX) … RETURNING`, which takes the row lock itself, then sends the GM line and pushes the total. The old load-then-save rewrote `discipline_ids` from a stale read, so a grant racing a CR-04 spend could drop the learned discipline or the spent point. `handle_grant_expertise` now runs its load, clamp and save in one `FOR UPDATE` transaction for the same reason. The wrong "no client push" doc comment is gone (C-63).
- **Logging.** `crafting` target: `login_sync` (DEBUG) and `persist_failed` (WARN, `op = "login_load"`) when the login load fails; the client then keeps only the row's ASP and blueprints from `mapLoaded`.

## Telemetry (added after the owner's telemetry rule, D-CR27)

Coordinator follow-up on the same branch, commit `9647f972`; the shared parts (identity, metrics, the recording meter, the comment clean-up) are described in [cr-04.md](cr-04.md#telemetry-added-after-the-owners-telemetry-rule-d-cr27).

- **`login_sync`** (INFO) with `account_id`, `player_id`, `entity_id`, the counts sent (`disciplines`, `paradigms`, `blueprints`, `asp`) and `defaults_applied` (the load reports whether the starting paradigm levels were filled in; `load_crafting_state_reporting`). `login_sync` fires only once the bundle went out. A failed load or an unsent bundle is `login_sync_failed` (WARN, `reason` = `load` \| `send`, `error_class` = the SQL error class or the send failure). A single push that does not go out is `push_failed` (WARN, `what` = `discipline` \| `paradigm` \| `known_crafts` \| `asp`, `reason`). The push helpers now take `player_id` for that identity.
- **`asp_granted`** (INFO) with `amount`, `asp_before`, `asp_after` and the identity. The GM grant reads the old total under `FOR UPDATE` and writes the new one in one statement (a CTE). A missing row is `persist_failed` (ERROR, `phase = asp_grant_update`, `reason = rows_affected_zero`, paired `rows_affected = 0` / `expected = 1`).

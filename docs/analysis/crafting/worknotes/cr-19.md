## Evidence

Client paths are relative to `Stargate Worlds-QA/Working/SGWGame/Content/UI/`. Addresses are file offsets in `Working/binaries/SGW.exe`.

1. **The crafting window opens only from the keyboard binding and the access menu.** `CraftingMod.onToggleCrafting(this)` (`Core/Crafting/Crafting.lua:23-30`) flips `CraftingWin`'s visibility. It has exactly two callers:
   - the key binding: `CraftingWin:subscribe(Actions.ToggleCrafting, 'CraftingMod.onToggleCrafting')` (`Crafting.lua:223`), where `ToggleCrafting` is the rebindable `J` action in `Common/Bindings/Bindings.toc:190-198`;
   - the access bar: `AccessMod.onCraftingClicked` (`Core/Access/Access.lua:171-174`).

   No other Lua shows `CraftingWin` (`grep` for `CraftingWin:show`, `CraftingWin:setVisible` and `onToggleCrafting` over all 93 client Lua files).
2. **No server-driven UI event reaches the window.** `Crafting.lua:223-229` subscribes `CraftingWin` to `Actions.ToggleCrafting`, `EventShown`, `Events.CraftingAllowedUpdate` (140), `EventCloseClicked`, the drag end and `Events.CraftingRespecPrompt` (112). Only the first shows the window. `onCraftingAllowedUpdate` (`Crafting.lua:33-51`) rewrites the status line, and `onCraftingRespecPrompt` (`:181-184`) opens a prompt. The page scripts subscribe to `CraftingBlueprintUpdate`, `CraftInductionStart`, `DisciplineExpertiseUpdate` and `InventoryUpdateSlot`, and none of them shows a window (`CraftingPage.lua:470-480`, `:502-532`; `ResearchPage.lua:382-385`; `AlloyPage.lua:482-510`; `ReverseEngineeringPage.lua:174-176`).
3. **The client's UI event registry has no "open crafting" event.** The UTF-16 table of `Events.*` names in `SGW.exe` (164 strings around `0x15b4118`) lists every event the native code can raise into Lua. Windows the server can open all have an event there: `VendorOpen`, `TrainerOpen`, `BMOpen`, `LootDisplay`, `DialogDisplay`, `GreetDisplay`, `DHDVisibility`, `VaultVisibility`, `MailUpdateMailbox`, `StartMinigameDialog`. Crafting has only `CraftingAllowedUpdate`, `CraftingBlueprintUpdate`, `CraftingRespecPrompt`, `CraftInductionStart`, `DisciplineExpertiseUpdate` and `ParadigmLevelUpdate`. The matching RTTI is `Event_UI_CraftingAllowedUpdate` (`0x1a0b268`), with no `Event_UI_*Crafting*Open*` class.
4. **The native client cannot fire the key action itself.** `ToggleCrafting`, `CraftingMod` and `CraftingWin` do not occur in `SGW.exe` in ASCII or UTF-16. Actions are defined by name in `Bindings.toc`, so native code could fire the action only by that name. `CraftingOpened` (`0x1554bac`) is a `UITutorial` id, which `onOpenCrafting` raises *after* the window is shown (`Crafting.lua:12-15`).
5. **The client runs no Lua that the server supplies.** There is no `loadstring`, `dostring` or dynamic `_G[...]()` call in the client Lua, and no dialog or greet path calls into crafting (`Core/Greet/Greet.lua` only lists topics).
6. **What a machine click does today.** Interaction rows 56-60 (`interactions.sql`) give the `INT_Machine_*` bits a marker body set (`GLB_Components.Reverse_Engineering`, `.Biomedical`, `.Power_Systems`, `.Materials`, `.Electronics`), the `InteractionCursor` and a minimap icon. They are not static (`is_static=false`). The client's right-click route (`FUN_00e85860` → `FUN_00e84b20` → `FUN_00def4b0` → `Event_NetOut_Interact`; `right-click-routing-on-corpse.md`) sends `interact(targetId)` for a picked entity. On the server, `handle_interact` has no arm for these bits. An in-range click reaches the `None` arm and the `interact_no_effect` friction log (`dispatch/interact.rs:256-283`). An out-of-range click is silent except for bankers and registrars (`:73-87`). So seeding the bits alone gives a cursor, a marker and an icon, and still a dead click.
7. **What "relevant" can mean in the stock window.** The tab order is Alloy 0, Craft 1, Research 2, Reverse Engineering 3 (`Crafting.layout:26-33`, `LayoutImport` order). The default tab is 1 (`GCraftMod_SavedData.lastWindow`, `Crafting.lua:215-218`). The Craft page has an applied-science filter, `CraftWin_ScienceFilter`, filled from `getAppliedSciences()` (`CraftingPage.lua:28-33`). Showing the blueprint list resets it to "Any" (`:128-137`), so a science preset has to be applied after the window is shown. Applied-science ids: Biomedical 1, Materials 2, Power Systems 3, Electronic 4 (`crafting-system.md`, tools paragraph).

**Confidence:** HIGH that the stock client cannot open the window on a server message or on a machine click (points 1-5: complete Lua subscription list, complete UI event registry, no native reference to the action). Not live-tested: no client was running, so no x64dbg was used, and Ghidra was not needed.

## Proposed patch design (for an owner decision; not built)

The existing `cimmeria-client-patches` DLL already has the pieces: the dispatcher detour, the main-thread `FEngineLoop::Tick` queue and Lua calls through `lua_cpcall` (`docs/architecture/client-patches.md`). Two shapes work. Both keep the server authoritative.

### Option A (recommended): open on the server's 140 answer, no new opcode

- **Server (no client patch needed, useful on its own):**
  - Templates 310-313 get `INT_Machine_Biomedical` / `_Electronics` / `_Power` / `_Materials`, so the client shows the cursor, marker and icon.
  - `handle_interact` gets a station arm, placed before the static match. It recognises a target whose template carries an `ENTITYFLAG_Craft_*` bit or an `INT_Machine_*` bit. Out of range (5 units, the `stations_in_range` rule), it sends a feedback line such as "You are too far from the BioMedical Crafting Station." and logs `rejected reason=out_of_range`. In range, it asks the base to resend `onUpdateCraftingOptions` (140) at once, with this station as the machine of every section. It also sends a feedback line such as "BioMedical Crafting Station: crafting enabled. Press J to open the crafting window." and logs INFO `station_opened` with `account_id`, `player_id`, `entity_id`, `station_entity_id`, `template_id`, `science` and `page`. A failed send is a WARN.
- **DLL:**
  - A passthrough observer on the interact firer (`FUN_00def4b0`, or its `Event_NetOut_Interact` emit) records `(entity id, click time)` when the clicked `GameEntity`'s interaction type (`mInteractionType`, set from `Event_NetIn_InteractionType`) has a bit 56-60.
  - A passthrough observer in the existing dispatcher detour watches for `onUpdateCraftingOptions` on the local player. If a machine id in it equals the recorded entity within about 2 s, it queues one Lua call for the main thread:

    ```lua
    if not CraftingWin:isVisible() then CraftingMod.onToggleCrafting(CraftingWin) end
    CraftingWin_Tab:setSelectedTabAtIndex(tab)       -- 1 Craft; 3 for INT_Machine_ReverseEng
    if tab == 1 then CraftingMod.selectComboboxItemByID(CraftWin_ScienceFilter, science, CraftMod.onScienceFiltered) end
    ```

  - Order matters. `onOpenCrafting` restores the saved tab on `EventShown`, and showing the blueprint list resets the filter, so the tab and the filter must be set after the show.
- **Cost:** it departs from the ADR's "claim on the drop path only" rule. This is an observer on a live method, and it never consumes or changes the call. The ADR would need a new consequence row. No new opcode, no `.def` change and no new UI: only stock Lua functions are called.
- **What "relevant" means:** a science station opens the Craft tab filtered to its applied science (Biomedical 1, Electronic 4, Power Systems 3, Materials 2). An `INT_Machine_ReverseEng` machine opens the Reverse Engineering tab. Every station still enables all four tabs through 140, so the player can switch tabs.

### Option B: a dedicated carrier method

The server sends a named client method the DLL claims on the drop path, carrying `(stationEntityId, tab, science)`. This matches the ADR exactly, but it needs a method the stock client parses and drops. None of the known shelved methods (the `onBM*` 90-95) fits, so it would be a new `.def` entry, which is a new opcode and needs a maintainer decision.

### Option C: DLL only, open on the click

Open the window in the interact observer with no server answer. This is the simplest option, but the window would open even when the server refuses the click (out of range) and would say "Disabled". Not recommended.

### No-patch fallback (available now, for an owner decision)

Only the server half of Option A: the bits, the station arm, the 140 refresh and the feedback line. A right-click then gives a visible answer on the first press ("… Press J …") and never opens the window. It meets the feedback rule but not D-CR30. It would take a normal packet: live-DB guards, and the CR-11 seed guard that asserts interaction 0 on 310-313 (`cell-catalog` `spawner::tests::live_db_crafting_hub::crafting_hub_templates_are_stations_and_a_vendor`, mutation R4 in `cr-11.md`) would change to assert the machine bit.

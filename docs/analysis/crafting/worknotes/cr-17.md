## Design decisions

- **Whitelist `[1, 15]`** (`placement.rs` `TRADEABLE_CONTAINERS`), still a whitelist: 2-14, 16 and 17-20 are refused with `IneligibleContainer`. Bound items are refused from either bag.
- **Destination** = `item_placement::grant_container(container_sets, source_bag)`, filtered to {1, 15}: the rule grants use, with the bag the item came from as the request. `{17,15}` from 15 or 1 goes to 15; `{3,1,17}` / `{1,17}` from 1 stays 1; `{2}` in bag 1 keeps bag 1 (today's behaviour for every existing bag-1 trade); `{}` from 15 goes to 1. A type with no `resources.items` row is refused (`NoDestination`, reason `no_destination`) rather than guessed at (server-authority review). `container_sets` is read in the same statement that locks the item row (`LEFT JOIN resources.items ... FOR UPDATE OF i`).
- **Slots per (recipient, bag)**, lowest free first, excluding the slots the recipient vacates in that bag; capacities from `bag_max_slots` (1 = 40, 15 = 100). A full destination bag refuses the whole trade and never spills into the other bag. Items are moved, not merged into existing stacks (items-systems review: crafting consumption is instance-keyed; mail and vendor do the same).
- **Lock order** is the shared inventory order: `take_inventory_locks(lower, [1, 15])`, `take_inventory_locks(higher, [1, 15])` (keys 0, 1, 15 each), then the offered item rows, then each recipient's destination-bag rows, then both `sgw_player` rows ascending. Every destination is in {1, 15}, so no advisory lock is taken after a row lock. Server-authority review: cycle-free against crafting, the move path, vendor purchase, item use, grant and every mail op; also removes the old player-rows-then-items versus items-then-player-row cycle with paid repair / recharge.
- **Every refusal is `Cancelled` (2) to both players** (coordinator, after the owner asked for the client's result support to be reverse-engineered): the client closes its window only on 1 and 2 (`docs/reverse-engineering/findings/trade-result-client-handling.md`), so the Python-parity codes 3-6 are no longer sent (`abort.rs` `REFUSAL_RESULT`). The cell had already cleared both players' trade state before the hand-off (`request_execute_trade` calls `clear_trade_state`, the same teardown `cancel_session` uses), so Cancelled is truthful and the base holds no session state to tear down. Every refusal with a cause also sends each player a feedback line (`abort.rs` `refusal_lines`): crafting bag full / backpack full (naming whose), no cash (whose), untradeable item (bound, ineligible bag, unknown type). Server faults, a missing item and a duplicated instance get only the client's own "Trade Cancelled".
- **Code layout:** `execute/mod.rs` was 531 lines; `TradeAbort` and its mappings moved to `abort.rs`, placement and reservation to `placement.rs`. Files now: `mod.rs` 468, `swap.rs` 388, `placement.rs` 206, `abort.rs` 279, `tests.rs` 490.

## Known gaps and out-of-scope findings

- **Vendor buyback deadlock: fixed in this PR at the coordinator's request.** Buyback locked the bag-16 rows and `sgw_player`, then took `(p,1)` inside `reserve_free_inventory_slots`, never `(p,0)`: a trade holding `(p,1)` and waiting for the player row deadlocked with it. Buyback now takes `take_inventory_locks(p, [1, 16])` (keys 0, 1, 16) first, then the buyback rows, then the main-bag rows (the slot pick moved ahead of the balance read), then `sgw_player`. The `(p,1)` inside the shared slot helper is now a no-op re-acquire and stays (the helper is shared). **Sell** had the mirror cycle once buyback held key 16 before rows: sell locked the sold main-bag row, then waited for `(p,16)`, while a buyback holding 16 reached for the main-bag rows. Sell now takes keys 0 and 16 before any row. Guards: `vendor/lock_order_tests.rs` `buyback_waits_for_a_trade_on_the_same_player` and `sell_waits_for_a_buyback_on_the_same_player` (sentinels `0x7000_C590..=0x7000_C5A9`); each fails at about 1.2 s (deadlock victim) with its handler's pre-fix file restored.
- **Trade window stuck open on codes 3-6: fixed** by sending `Cancelled` for every refusal (see Design decisions). Open item: live-trace the native `onTradeResults` handler (in the finding).
- **Tool lending** (server-authority review). The station/tool gate runs only when a craft is requested (`request.rs:59`, `gate.rs:83`), not at completion (`transaction/mod.rs:96-104`). A Field Crafting Tool traded away still covers crafts already queued, and the partner can queue with it too. A gate bypass, not a dupe; the fix is to re-check the gate at completion, on the crafting side. Trade should not refuse tools.
- **Stale test comment in crafting item use: fixed.** `crates/base-session/src/base/crafting/item_use/tests/locks.rs` (`a_use_waits_for_a_trade_instead_of_deadlocking`) now says the simulated order is the one trade used before; the test body is unchanged.
- **Crafting-bag stacks are not merged** on arrival; two partial stacks of one component can sit in bag 15. Same as mail and vendor; crafting consumption is instance-keyed.

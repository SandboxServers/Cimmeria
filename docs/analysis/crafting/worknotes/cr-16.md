## Design decisions

- **One placement rule** (`item_placement::grant_container`), applied on the base where every cell caller ends up: a storage request falls through to `first_player_container` (`None` = storage-only, refused by BV-01's guard, unchanged); a carried-bag request the item does not allow moves to the carried bag it lists; allowed requests and non-carried containers (bandolier, mission, equipment) are kept. So weapons still go to the bandolier from loot and to bag 1 from `gmGiveItem`; a `{2}` mission item given into bag 1 stays in bag 1 (no carried bag to fall to). Both advisors confirmed nothing else changes.
- **The cell cache skips storage too** (`default_grant_container`: the first non-storage entry, else the first entry), so loot and content ask for 15. The base rule is the backstop for any stale request (a content chain that names 17, a GM command).
- **Placement before the vault guard.** `resolve_placement` reads `container_sets` and the account id in one query; the guard then sees the resolved container, so `validation.rs` did not change.
- **Loot: remove-then-restore, not mark-pending.** The item is always in exactly one place: the corpse, the in-flight `GrantItem`, or the inventory. The base answers `LootGrantRefused` only from a `PersistOutcome::Refused`, which is built only before the commit. A `COMMIT` error is classified: `sqlx::Error::Database` (the server answered, so it rolled back) is refused and handed back; anything else (I/O, closed pool) is `CommitUnknown` and is **not** handed back (`loot_restore_skipped`), trading a possible loss for no duplicate (server-authority review). Mark-pending was rejected: it needs an ack both ways, a field on the entity `LootItem` (another campaign's crate), and a lost ack hides the item forever.
- **Same corpse only.** `LootGrantSource` carries the corpse's `respawn_at` and `template_id` at take time; the put-back also needs `index < next_loot_index` and a free index. A respawned or re-killed corpse is `corpse_changed`; a second copy of the same refusal is `index_taken` (never doubled).
- **Stale looter id.** Feedback and the window refresh go only to an entity that still has the refusal's `player_id`; the refresh only if it is still looting that corpse. The loot bit is re-set and re-broadcast (`INTERACTION_TYPE` through `send_entity_method`, as the clear path does) when the take had emptied the corpse.
- **Unsent grant.** A failed `tx.send(GrantItem)` hands the item straight back (`return_unsent`).
- **Vendor purchases** place each line by `first_player_container(sets).unwrap_or(INV_MAIN)` and reserve slots per container in ascending order (items advisor: avoids an inverted per-bag lock order between two purchases); the player-wide lock `(player, 0)` still comes first.
- **GM feedback on refusal.** A refused `gmGiveItem` now sends "gmGiveItem: could not give item N: …" (before, a refusal was silent).
- **Feedback texts** (cell, `CHAN_FEEDBACK`): "Your crafting bag is full. The item was left on the corpse." / "Your inventory is full. …" / "That item cannot be carried. It was left on the corpse." / "That item could not be picked up right now. It was left on the corpse." / lost: "That item could not be picked up, and the corpse it was on is gone."
- **Loot rows.** Table 3 rows 18-23: 7805-7809 and 6483 at 0.2, `min = max = 1` (all six stack to 1, and the fresh-slot INSERT has no stack cap, items advisor). The four existing rows stay at 1, so the corpse always has loot. The old guard ("every table-3 row is probability 1") was relaxed to "the naquadah row and at least one item row always drop, every row can drop"; the dispatch test now checks certain rows ⊆ dropped ⊆ table.
- **File caps.** `grant_item.rs` was 681 lines; the transaction moved to `persist.rs` and the equipment epilogue to `equip_epilogue.rs`. `progression_dispatch.rs` would have reached 703, so the `GrantItem` body moved to `item_grant_dispatch.rs` (656). `loot.rs` became `loot/` with its tests split out.

## Known gaps

- **Crafting components cannot be traded or mailed.** They now live in bag 15, and they cannot sit in bag 1 (`item_allows_container`). Trade (`TRADEABLE_CONTAINERS`) and mail escrow (`mail/send/escrow.rs:72`, owner rule 2026-09-27: "mail sees only the backpack") accept only bag 1. This was already true for any `{17,15}` item placed correctly; it now covers every source. An owner call (allow 15 in trade/mail, or allow 1 for components).
- **GM-granted items before this change** sit in bag 1; they stay usable (CR-15 accepts 1 and 15) and nothing migrates them.
- **Cash** (`GrantCash`) has the same remove-then-send shape but no deterministic refusal; a DB error loses the naquadah. Not handed back (server-authority: acceptable, follow-up).
- **Fresh-slot grants do not cap the stack** at `max_stack_size` (the merge path does): a `grant_item` of 5 × a stack-1 item writes one row of 5 (items advisor, pre-existing). The new loot rows use quantity 1.
- **lootItem rate limit.** Re-looting a restored item costs a transaction per click; a per-player `lootItem` rate limit is a follow-up (server-authority, not a correctness issue).
- **No end-to-end cell→base loot test**; the two halves are tested on each side of `GrantItem` / `LootGrantRefused`.
- **Four WARN seams have no LogCapture guard** (`grant_outcome_unknown`, `loot_restore_skipped`, `lookup_failed phase=placement`, cell `feedback_send_failed`): each needs one exact connection or channel failure that nothing injects; recorded in `negative-logging-convention.md`.
- **No in-client check** of the refusal lines or of the window refresh.

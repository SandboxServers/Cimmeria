## Evidence

- **The set id is not on the wire.** `CraftMod.onGoConfirmed` builds the list from `CraftMod.components[i].itemID`, one per component of `CraftMod.setID`, and calls `requestCraftBlueprintProduct(blueprint.ID, setID, componentsList, {}, quantity)` (`CraftingPage.lua:299-313`); method 96 carries only `(aCraftId, aItems, aQuantity)`. A component the player has none of leaves a `nil` that `table.insert` drops, so the list can be shorter than the set.
- **Sets are often subsets of each other.** In `sgw_cr07`, 146 (blueprint, set) pairs have a sibling set of the same blueprint whose designs contain theirs (blueprint 412: set 1 `{5254×14}`, set 2 `{5254×1, 5256×5}`, set 4 `{5188, 5254, 5366}`). One pair has identical designs: blueprint 159 sets 1 `{5188×15, 5189×5}` and 2 `{5188×1, 5189×5}`. No set lists a design twice. `Crafter.py:214-218` takes the first set whose components are all covered, so a set-2 submission for 412 would be charged set 1's 14 cores.
- **Seed shapes the tests assert:** 412 is discipline 21, product 5401, quantity 1, not an alloy; 5254, 5256 and 5401 are `{17,15}` with `max_stack_size = 1`; blueprint 21 has no component rows; 42 is an alloy of discipline 21. Discipline 21 is named "Biomedical Engineering".

## Design decisions

- **Rule order** (`rules.rs`, `mod.rs::decide`): quantity (no database needed), blueprint known and in the catalog, not an alloy, discipline known, named instances (each once; the player's; bag 1 or 15), set choice, bag totals. A missing blueprint product is a data fault: `lookup_failed phase=blueprint_product` and "unavailable" (no seed row has one).
- **Set choice.** The set whose distinct designs equal the distinct submitted designs; among equal-design sets, the first the bags can pay for; if none can, the first one's shortfall is reported. A blueprint with no set, an empty submission and an extra design all give `no_component_set`. This deviates from `Crafter.py` (D-CR11: the client's page picks one set and names exactly its designs).
- **Named instances only choose the set.** CR-06's contract has verbs pass the named instances as `NamedItem`s. For `craft` that makes a queued craft fail `component_missing` when an earlier craft drained the named stack, although the bags still hold enough (the page names the last stack it found, both requests name the same one, and the crafting bag is consumed first). The items advisor found it; `plan_craft` passes no named items, and the completion consumes by design, which re-checks ownership, bag and quantity under lock. The request already validated the named instances. Reverse engineering, which consumes its named instance exactly, is unaffected.
- **Completion re-check, inside the transaction.** The plan carries `required_knowledge` (blueprint and discipline); after consumption and placement the transaction reads `blueprint_ids, discipline_ids` from `sgw_player` `FOR SHARE` (`transaction/knowledge.rs`) and refuses with `unknown_blueprint` / `discipline_unknown`, rolling everything back. A respec that updates the row serializes with the completion: committed first, it is seen; later, it waits. Lock order: advisory locks, inventory rows, then the player row, the vendor stack's order; the player-wide advisory lock keeps trades and purchases out. The first version re-checked outside the transaction with a plain read (PR #905 review: a respec committing between the two was missed); it is gone.
- **Expertise:** +1 per craft request, not per unit (D-CR15, `Crafter.py:268`). The transaction skips disciplines the player no longer knows and clamps at 100.
- **Lines.** A started craft's answer is the bar. A queued craft gets "Crafting <product> x<n> is queued behind <k> other crafting job(s)." (first-press feedback). Completion sends "You crafted <product> x<n>." after the item and discipline updates. Product names come from `resources.items.name`, read at the request; a missing name falls back to "item <id>" with a WARN.
- **No resync on a request-time refusal.** The craft page keeps its slots on confirm (C-33), so only the line is sent. A completion refusal gets the transaction's line and resync.
- **Reuse of CR-06 reasons.** A bad named instance at the request is refused with CR-06's `component_missing` / `component_not_in_crafting_bags` rather than new craft-only reasons. The packet's `insufficient_components` is a new reason next to CR-06's `not_enough_components`, so a dashboard can tell a request-time shortfall from one at completion.
- **Counting.** `crafting_requests_total{verb=craft, outcome=accepted}` once for `Started` or `Queued`; nothing for `QueueFull` (the engine's `reject` counted it) or `NotConnected`.

## Telemetry

All under target `crafting`, with `account_id`, `player_id` and `entity_id` on every event.

- `rejected` (INFO) with `verb=craft` and reason `bad_quantity` (`quantity`), `unknown_blueprint`, `is_alloy`, `discipline_unknown` (`discipline_id`), `no_component_set` (`type_ids`), `insufficient_components` (`design_id`, `needed`, `available`), each with `blueprint_id`; plus `component_missing` / `component_not_in_crafting_bags` at the request. `unknown_blueprint` / `discipline_unknown` can come at completion.
- `completed` gains `component_set_id` and `quantity` (a verb field on `JobReport`, logged by the engine); `blueprint_id` was already there.
- `lookup_failed` (WARN, `phase`, `blueprint_id`, `error_class` = SQL class or `miss`, `error`): `no_pool`, `catalog`, `crafting_state`, `blueprint_product`, `inventory`, `product_name`, all at the request. At completion the knowledge check's failures are the transaction's `persist_failed` `phase=knowledge`.
- `bad_quantity` carries `blueprint_id` too (PR #905 review), so every craft refusal has it.
- `client_sync_failed` (WARN) `what = craft_queued` for the queued line (sent from the request, so no `job_id`), and `what = craft_result` for the success line (through the shared `send_to_player`).
- No new span (the request is inside `crafting.request`) and no new metric.

## Known gaps

- **The station gate is not re-checked at completion.** A player can queue ten crafts and walk away from the station; they finish. The same holds for every verb on the engine.
- **A flood of craft requests costs four reads each** before the engine refuses a full queue. The client sends one per confirm.
- **`NotConnected` sends nothing.** It is the engine's case of a request for an entity with no session; nobody can be answered.
- The per-reason `LogCapture` assertions live in the live-DB refusal tests, so they run only with a database.

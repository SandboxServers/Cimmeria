## Design decisions

- **Queue size counts the running job.** "One active and a queue of at most 10" read literally is 11. The acceptance names the 11th request as the one refused and the client bursts 10, so `MAX_INDUCTIONS = 10` includes the running induction.
- **Registry.** A process-wide `LazyLock<Arc<CraftingSessions>>` (`crafting_sessions()`), keyed by player entity id, so the dispatcher context and `ConnectedClientState` (18 literal constructors) are unchanged. Tests build their own `CraftingSessions` with a `ManualScheduler`. The hooks call `drop_player_inductions(entity_id, reason)`.
- **Clock.** The state machine takes `now` as a parameter and stores a monotonic `tokio::time::Instant` deadline. Production waits with `TokioScheduler` (a spawned `sleep_until`); unit tests fire wake-ups by hand through `ManualScheduler`, and one test runs the production scheduler on tokio's paused clock. No test sleeps for an induction.
- **Busy while completing.** When a job's deadline passes, the job is taken out but the session stays busy until `finish`, so a request arriving during the transaction queues behind the others instead of starting ahead of them.
- **Completion guard.** Besides the explicit drops, a job runs only if the entity still maps to a connected session whose `player_entity_id` is the entity and whose `active_player_id` is the job's character, with the same world name. A missed teardown path therefore consumes nothing, and a recycled entity id never runs another character's job.
- **Lock order.** Every advisory lock first (the player-wide move key 0, then each bag in container order: 1, 15 and each product bag), then the named instances, then the stacks. The player row is read, never locked: the transaction writes nothing on `sgw_player`, and the vendor stack (purchase, sell, repair, buyback) locks inventory rows before the player row, so holding it while waiting for an inventory row would close a cycle. Vendor purchase takes the player-wide key 0 before any row (PR review), so its row, player, bag order cannot cycle with a completion's advisory-first order either. The first version locked the player row first; the items advisor and the authority advisor each found a cycle (move bag 15 then 1 against craft 1 then 15; trade advisory then row against craft row then advisory), and review found the vendor ones.
- **Consumption.** By design, bags 15 then 1 (the crafting pages stage components in bag 15), slot order within a bag. A named instance carries the design the verb expects (`NamedItem`); the row lock checks owner, bag and `type_id`, and the plan must consume every named instance, by its design or exactly (`consume_named`, which takes only from that instance: the reverse-engineering path). The named instances are not preferred by consumption by design, because the client names the last stack it found (C-31). A non-positive consume quantity refuses the transaction (a verb bug must not grant for free); a non-positive grant quantity is skipped.
- **Placement.** `first_player_container(container_sets)` in `cimmeria-cell-catalog` (reachable by the cell's loot map, the base grant path and base-session): the first main or crafting bag listed, the main bag for an empty list, `None` for storage-, bandolier-, equipment- or mission-only items. List order decides. Merge follows the generic grant's all-or-nothing rule (one unbound stack with room for the whole quantity); otherwise one free slot per full stack.
- **Client updates.** One `onRemoveItem` with every drained instance id (the method takes an array), one `onUpdateItem` with the shrunk and granted stacks, `onUpdateDiscipline` per changed discipline. If the item read fails, a full `onUpdateItem` resync instead. The inventory row select is a filtered copy of `INVENTORY_ITEM_SELECT` (base-methods sits above base-session, so the original is not reachable).
- **Outbox.** `InventoryItemRemoved` (instance id) per drained stack and `InventoryItemGranted` (design id) per placed stack, enqueued inside the transaction and dispatched after commit, as `remove_instance` and vendor purchase do.
- **Refusals.** Seven new `CraftReject` variants, each with a readable line. A refused transaction sends the line then a full inventory resync. A full-queue refusal sends the line every time but resyncs only once per full episode (reset when a slot frees), so a request flood does not become a flood of full-inventory reads.
- **RNG.** `CraftRng { fn unit(&mut self) -> f64 }`, `OsSeededRng` (a `StdRng` seeded from the OS, `Send`), `ScriptedRng` for tests. The engine hands each completing job a fresh one through `Completion.rng`.
- **Dropped queue, no line.** A drop on logout or world change sends no feedback: the client is gone or reloading.

## Telemetry

Everything logs under target `crafting`. The canonical list is the `crafting` row of `docs/architecture/observability.md`, updated in the same commit.

- **Identity.** Every job event carries `job_id`, `account_id`, `player_id` and `entity_id` as fields of the event (`telemetry::JobIds`), never only on a span. The engine reads `account_id` from the session at submit and keeps it on the `CraftingSession`, so a drop after the client left still names the account.
- **Transitions.** `queued` (`position`, `queue_len`), `induction_started` (`timer_id`, `queue_len`, `expires_at` = the game-clock `BigWorldTimeComplete` sent), `induction_expired` (`queue_len`), `completed` (`blueprint_id`, `item_id`, `consumed` = `item_id:type_id:before→after,…`, `granted` = `type_id:bag:slot:before→after,…`, `expertise` = `discipline_id:before→after,…`, `result`, `chance`, `roll`). All INFO. A merge shows a non-zero `before` in `granted`, a new stack 0.
- **Drops.** `queue_dropped` (INFO) with `reason` = `logout` / `world_change` (the contract's two) plus three the engine needs: `session_changed` (the completion guard found another session or world), `stale_session` (a request found a leftover queue of another character on a recycled entity id) and `not_connected` (a submit for an entity with no session). `cause` is the caller's own label, `jobs_dropped` the count, `job_ids` the `id:verb` list. `drop_player_inductions(entity_id, DropReason, cause)` replaces the one-argument form.
- **Seams (WARN).** `persist_failed` for every rollback that is not a game-rule refusal: `phase` (`begin`, `resolve`, `lock`, `lock_player`, `check_named`, `consume`, `place`, `expertise`, `outbox`, `commit`) and `reason` = `db_error` (`error_class`, `sqlstate`, `error`), `rows_affected_mismatch` (`rows_affected`, `expected`, logged where the write happened), `invalid_quantity`, `unknown_product`, `player_missing` or `no_database`. `client_sync_failed` for every client update that did not go out (`what` = `induction_timer`, `remove_item`, `update_item`, `update_discipline`, `resync`; `reason` = `entity_to_addr_miss`, `send_error`, `inventory_read_failed`); DEBUG with `reason = client_disconnected` when the session had already ended, because that is the logout race and there is nothing to correct. The one remaining `let _ =` in the transaction is the rollback after an error that is itself returned and logged.
- **Refusals.** Every induction refusal goes through CR-03's `reject`, which logs `rejected` with `verb`, `account_id`, `player_id`, `entity_id`, `reason` and the values the rule compared, sends the line, and counts it. The engine's full-queue refusal is the request's answer: `rejected reason=queue_full` (with `queue_limit`), `crafting_rejections_total` +1 and `crafting_requests_total{outcome=rejected}` +1. A refusal when a job completes uses `reject_at_completion`: the same event and `crafting_rejections_total`, but no second request count, because the request was answered when the job was queued. Its reasons carry what they compared: `component_missing` (`item_id`), `component_not_in_crafting_bags` (`item_id`, `container_id`), `not_enough_components` (`design_id`, `needed`, `available`), `inventory_full` (`design_id`, `container_id`), `no_carried_bag_for_product` (`design_id`), `induction_failed` (after its `persist_failed`). `Unavailable` (CR-03's server-failure reason) was not reused for `induction_failed`: it is a request-time answer, and a rolled-back completion is a different question on a dashboard.
- **Metric.** `crafting_jobs_total{verb, outcome}`, `outcome` = `completed` / `failed` / `dropped`, counted once per job where it ends: in `expire_at` from the job's `JobOutcome`, or in the drop for each unrun job. A job whose completion is already running when its queue drops is counted by its own outcome, not as dropped. `verb` is the cell method name (`CraftVerb::method_name`), as on the request counters; `JobIds` carries it. Tests read the process-wide recording meter (`cimmeria_observability::testing`), with probe verbs no other test emits.
- **Spans.** None in the engine or the transaction: they are per-job timer work, not dispatch entrypoints.
- **Verb API change.** `InductionJob::complete` returns `JobOutcome::{Completed(JobReport), Failed}`; `Completion` carries `ids: JobIds`; `apply_craft_transaction(env, &ids, &plan)`; `CraftApplied::report()` fills the report's item and expertise lists, and the verb adds `blueprint_id` / `item_id` / `result` / `chance` / `roll`.

## Known gaps

- **Other vendor-stack paths are not covered by a concurrency guard.** Sell, repair, recharge and buyback lock an inventory row, then the player row, and do not take the player-wide lock. With the completion no longer locking the player row they share no lock pair in opposite order with it, as far as their code reads; only purchase has a two-connection guard. Moves and trades are argued from the Evidence section, not raced in a test.
- **World name is stale across gate travel** (see Evidence). Not changed here; the gate-travel drop covers crafting. The other readers of `world_name`, the admin online-player `zone` (`crates/base/src/base/service.rs:131`) and the gate-travel Discord world-exit origin (`gate_travel/mod.rs:170`), show the first world of the session after any gate trip. Worth an issue.
- **Post-commit sends are not re-checked against the character.** If the player logs out during the few milliseconds of the transaction and the entity id is reused at once, the item updates would go to the new session. The same holds for every inventory path today.
- **The drop hook in `logOff` sits after the `entity_to_addr` removal**, so if it were removed the completion guard would still stop the job; its test pins the queue count rather than the consumption.
- The generic grant path (loot, content `grant_item`, GM give, vendors) still places into the first `container_sets` entry; wiring `first_player_container` there is CR-16. `crates/cell-catalog/src/cell/spawner/loot.rs:71` (`container_sets[1]`) is the cell-side spot.
- **`feedback/reason.rs` is 521 lines**, past the 500 soft cap: CR-03's enum plus the seven induction variants, each with an arm in six methods, and its tests. The natural seam is the inline `mod tests`; left for whoever adds the next reasons (CR-07 to CR-10) rather than moving CR-03's tests here.
- **`expires_at` only on `induction_started`.** A queued job has no deadline yet, and `induction_expired` fires at the deadline itself; the contract lists `expires_at` for all three.
- The queue is in memory. A server restart loses queued requests, but nothing was consumed for them.

## Integration edits for the coordinator

## The eligibility rule (unchanged, now shared)

An eligible discipline is one of the item's `discipline_ids` that the player knows (`sgw_player.discipline_ids`) with an expertise row where `0 < expertise < item tech_comp`. An expertise row for a discipline not in the known list does not count. This is exactly the filter `rule::roll` used before the packet (`crates/base-session/src/base/crafting/research/rule.rs:90-102` at `352248e2f`); it now lives in `eligible_disciplines` (`research/rule.rs`), which `roll`, `check_eligible` (request and completion) and the transaction's `check_research` all call. No rule was invented.

## Design decisions

- **Request.** `research_job` already had the catalog and the named items; it now also reads the crafting state (`load_crafting_state`, unlocked, as craft's request does) after `check_request`, and refuses with `NoEligibleDiscipline` before the job is built. A failed state read is `lookup_failed` WARN `phase=crafting_state` (with `item_id`), then `rejected reason=unavailable`, the same shape as the craft verb.
- **Completion, before the roll.** The job re-runs `check_eligible` on the state `state_at_completion` read. On a refusal it sends the line through `reject_at_completion` (the shared `CraftReject` path, `rejected` event, `crafting_rejections_total`), resyncs the inventory as `apply_craft_transaction` does on its refusals (the research page empties its slots on confirm), and ends the job `Failed`. Nothing is rolled or consumed.
- **Completion, inside the transaction.** The plan carries a `ResearchedItem` (item id, type, applied science, tech competency, discipline ids). `apply_in_tx` calls `knowledge::check_research` after the knowledge check and before the expertise rows are locked and written: it reads the state with `load_crafting_state_locked` (player row `FOR UPDATE`, the lock every crafting write takes; the learn step may already hold it) and runs `check_eligible`. A refusal is `CraftTxError::Rejected`, so the whole transaction rolls back, and `apply_craft_transaction` sends the same line and resyncs. A database error or a missing player row there is `persist_failed phase=research_eligibility`. Lock order: after the advisory locks and every inventory row, the order the learn and knowledge steps already use.
- **Why both completion checks.** The transaction check is the authoritative one (a change between the completion's unlocked read and the transaction). The pre-roll check keeps a research whose unlocked read shows no eligible discipline from reaching the transaction with nothing rolled: without it, a discipline re-learned in that window would let the transaction consume with no roll. It is redundant with the transaction check in every other case (see Regression proof, P4).
- **Refusal values.** `NoEligibleDiscipline { item_id, type_id, applied_science_id, tech_comp, item_disciplines, known }`, `known` = every known discipline as `(id, expertise)` in id order (0 for a known discipline with no row). `rejected` carries `item_id`, `type_id`, `applied_science_id`, `tech_comp` (new `Compared` field), `item_disciplines` = `21,22`, `known_disciplines` = `21:0,22:20`. `error_code` none.
- **Text:** "None of your disciplines can learn from that item: research needs one of its disciplines at an expertise above 0 and below <tech_comp>. Nothing was used."
- **Result line.** The "learned nothing new" branch of `result_line` is no longer reachable; its `None` arm now returns the plain failure line with a comment, and its unit assertion was dropped.

## Telemetry

- `rejected` (INFO) `reason=no_eligible_discipline` with `verb=research`, `account_id`, `player_id`, `entity_id` and the values above, at the request, at completion, and from the transaction. `crafting_rejections_total{verb=research, reason=no_eligible_discipline}`; at the request also `crafting_requests_total{outcome=rejected}`. A completion refusal counts `crafting_jobs_total{outcome=failed}` and logs no `completed`.
- `lookup_failed` (WARN) `phase=crafting_state` at the research request; `persist_failed` (WARN) `phase=research_eligibility` in the transaction.
- `observability.md` `crafting` row updated for both. CR-14's SigNoz table filters `event IN (...)`/`reason` generically and lists no research reasons, so it needs no edit; a research UAT step would use `event = 'rejected' AND reason = 'no_eligible_discipline'`.
- Gap (pre-existing, not widened): `reject_at_completion`'s `rejected` event carries no `job_id`, so a completion-time refusal correlates to its job only through `player_id` and time.

## Known gaps and out-of-scope findings

- **Stale roll with another discipline still eligible.** When the rolled discipline is dropped or maxed during the bar but another of the item's disciplines stays eligible, the transaction does not refuse: the roll made against the unlocked read applies (expertise for an unknown discipline is skipped, as before). D-CR29 covers only "no eligible discipline". Refusing or re-rolling there is a separate decision.
- `.allcraft` sets every discipline to 100, so after it only an item with a tech competency above 100 can be researched; every other research is now refused with this line instead of eating the item. Worth a note on the CR-14 run order.
- `rejected` from `reject_at_completion` has no `job_id` (pre-existing; affects every verb's completion refusals).

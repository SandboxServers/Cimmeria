## Evidence

- **Ids free.** On `origin/main` @ `479b06061` no template 310-314 and no spawn 410-414 exists (spawns 310-314 are Harset's, unrelated). Of the open branches that touch the same seeds, pets PT-07 adds spawn 450 on the hub's A-B line (-328.08, -237.07) and the black market adds spawn 238 at (-325.0, -206.5), outside the room past the C-D side. Neither collides with 410-414 or their positions.
- **Stations need only the flags.** `stations_in_range` reads `entity_flags` (the template `flags` column) for any `ENTITYFLAG_Craft_*` bit, and `spawn_npc_from_record_into` copies `flags` straight across. The interaction bits play no part.
- **`INT_Machine_*` would dead-end.** The bits 56-60 match interactions 56-60 (the "Reverse_Engineering", "Biomedical", … marker body sets and minimap icons), but `handle_interact` has no arm for them: a click reaches the `None` arm and the `interact_no_effect` friction log. The client does not send a click for an entity with no interaction bit (debug-hub authoring traps), so the stations have none.
- **Where a vendor purchase lands.** `handle_purchase_vendor_items` always inserts into `INV_MAIN` (1), whatever `container_sets` says (`vendor/purchase/mod.rs`, `INV_MAIN` const). All 24 supplies have `{17,15}` except 5481 (`{3,1,17}`); none lands in 17. Bag 1 is a carried bag for item use (CR-15) and an input bag for crafting consumption (CR-06), so everything but the tools is usable at once; a tool counts only in bag 15 (D-CR21), and moving it there is allowed by its `container_sets`.
- **Where `.craftkit` lands.** Through CR-06's grant (`first_player_container`), a `{17,15}` component goes to bag 15 (100 slots). No component stacks, so a kit of blueprint 25 takes 13 slots per craft; 10 crafts would need 130 and are refused `inventory_full` by the transaction.
- **UAT supply choice.** Blueprint 25 set 1 = 13x 5254; 412 set 1 = 14x 5254, set 2 = 1x 5254 + 5x 5256; 161 set 1 = 5401 + 5254; alloy 42 = 5192 (tier 2 Good), plus tier-1 elementary items: 5189 T1 Cell (Bio-Medical), tier 1 Good, meets the client's Good bucket at 5 (D-CR11). ## Design decisions

- **One station per science, each with all four verbs** (flags 30724 = 30720 | 4, the 4 copied from template 19). The packet asks for all four bits on each; the gate does not check science, so the names are labels only.
- **Mesh:** template 19's `Em-Props.EM-ViewScreen02` + `GLB_Components.WorldObject_Small`, class `being`, faction 1, level 1: a prop already rendering in world 12.
- **Placement:** the D-A wall, 3 units in, at 6.0 / 8.6 / 11.2 / 13.8 / 16.4 units from A (vendor first), headings `atan2(dx, dz)` towards the room centre. Derived from the region corners like 400-404; not checked in the client. Nearest is 7.4 from the respawner, 3.1 from spawn 400; a player standing at the vendor reaches the BioMedical station (2.6 units).
- **Tags `CraftHub_*`, not `DebugHub_*`.** `cell-methods` `debug_hub_dispatch_tests::staged_hub` spawns every `DebugHub_`-prefixed tag and asserts the count (5 on main, 6 on the pets PT-07 branch). A `DebugHub_` tag would change that count and conflict with pets. The docs still present them as part of the hub.
- **Supplies vendor sells only** (buy list 310, no sell / repair / recharge), 24 rows at quantity 1, 1 naquadah, no `item_list_prices`.
- **GM commands:** the cell parses and forwards one `CellToBaseMsg::GmCraftGrant { entity_id, player_id, gm_entity_id, grant: Kit { blueprint_id, count } | LearnBlueprint { blueprint_id } }` (one variant in the over-cap `cell_to_base.rs`, payload in `wire/src/crafting/`, as `.allcraft` did). The base re-checks `access_level >= 2` with `.allcraft`'s helper, validates against the shared crafting catalog, and answers the GM with exactly one line for every outcome.
- **`.craftkit <blueprint> [count]`:** count 1-10 (default 1); component set 1 only, each component `quantity x count`; granted through CR-06's `run_craft_transaction` as a grant-only plan via the new `transaction::apply_grant_transaction` (the success half of `apply_craft_transaction`, without the player reject line, the rejection metric or the resync, which are wrong for a GM grant). Job id 0 marks its transaction events; `verb=craftkit`.
- **`.learnblueprint <id>`:** blueprint must exist in the catalog and not be known; load under `FOR UPDATE`, push, sort, save, commit, then 139 with the saved list. The success event is CR-15's `blueprint_learned` shape plus `source=gm`.
- **Target feedback:** the target sees the inventory update (kit) or the 139 list (learn); the GM gets the line. No crafting `rejected` event or `crafting_*` metric is emitted for a GM command: those count player crafting requests.

## Telemetry

Target `crafting`. Spans `crafting.craftkit` / `crafting.learnblueprint` (INFO, one per grant). Every event carries `account_id`, `player_id`, `entity_id` and `gm_entity_id`.

| Event | Level | Fields |
|---|---|---|
| `gm_craftkit` `outcome=granted` | INFO | `blueprint_id`, `count`, `component_set=1`, `granted` = `type_id:bag:slot:qty_before→qty_after,…` |
| `gm_craftkit` `outcome=refused` | INFO | `reason` = `bad_count` \| `unknown_blueprint` \| `no_components` \| `inventory_full` \| `no_carried_bag_for_product`, `blueprint_id`, `count` |
| `gm_craftkit` / `gm_learnblueprint` `outcome=refused` `reason=not_gm` | WARN | `access_level` |
| `blueprint_learned` | INFO | `source=gm`, `blueprint_id`, `blueprints` = `id:false→true`, `known_before`, `known_after` |
| `gm_learnblueprint` `outcome=refused` | INFO | `reason` = `unknown_blueprint` \| `already_known`, `blueprint_id` |
| `lookup_failed` | WARN | `command`, `phase` = `db_pool` \| `catalog` \| `load_state` |
| `persist_failed` | WARN | `.learnblueprint`: `command`, `phase` = `begin` \| `load_crafting_state_locked` \| `save_crafting_state` \| `commit`, paired `rows_affected` / `expected`, `error_class`. `.craftkit`: the transaction's own `persist_failed` (`job_id=0`) |
| `forward_failed` | WARN | cell side, `kind=gm_craft_grant` |

No new metric. `client_sync_failed` covers a failed kit inventory update (CR-06's `send_applied`); `push_failed what=known_crafts` a failed 139.

## Known gaps

- **Placement is unchecked in the client**, as for 400-404: no navmesh or occluder data for this room. The D-A wall may hold stasis pods.
- **No click on a station.** Deliberate (see Evidence). If the owner wants the machine cursor and minimap icon, the stations need `INT_Machine_*` bits and a server answer to the click (for example a line naming the station and "open the crafting window (J)"), which is an interaction-dispatch change.
- **Crafting verbs.** The stations and supplies enable the pages; whether craft / research / reverse engineering / alloying do anything depends on CR-07 to CR-09.
- **Advisor not consulted.** The packet names items-systems-advisor; the design reuses the vendor path unchanged and CR-06's transaction, and every rule has a guard, so no review was run. The coordinator may want one on the vendor finding below.

## Out-of-scope findings

- **Vendor purchase ignores `max_stack_size`.** `load_vendor_purchase_lines` grants `row.quantity x requested_quantity` as one stack, so buying 13 Steel Cores (max stack 1) makes a single stack of 13 in bag 1 (pinned by `crafting_supplies_land_in_the_main_bag_and_are_usable`). Crafting consumes it correctly by stack quantity, but the client shows a stack of a non-stackable item. It predates this packet (every vendor) and is outside CR-11; worth an issue for the vendor path.
- **Vendor purchase refusals are silent to the player** (not enough slots, not enough naquadah: WARN only, no line). Pre-existing, D-CR14-shaped, outside CR-11.

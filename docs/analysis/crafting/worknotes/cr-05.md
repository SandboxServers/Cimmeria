## Evidence

- **The client trusts 140 entirely.** It keeps the last id of each array, registers the machine id as a unit alias without an existence check, and the Lua only tests `~= 0` (`crafting-client-ui.md` §2). So the server gate is the only enforcement, and the player's own entity id works as the "craft anywhere" machine (Python `Crafting.py:85-95`).
- **`CraftingInfo.items` is an inventory instance id.** `Crafting.lua:45` resolves the tool with `getItemSlot(tool)`, so 140 sends `sgw_inventory.item_id`, not the item type.
- **Tools carry no science field.** `applied_science_id` is NULL on all 48 seeded tools (items 5369, 8402-8466), and CR-E2 Q3 found `AppliedScienceID="0"` in the cooked data. The prefix is the only structured source. The live-DB test cross-checks every prefix against the free-text description.
- **Tool `tech_comp` vs the name.** Item 8407 is named "BMAS-10" but has `tech_comp` 5, the same as 5369 "BMAS-5". D-CR21 says the tool's `tech_comp`, so the column wins; `tech_comp_comes_from_the_column` pins that. The seed's other tools agree with their names.
- **Applied science ids** (`applied_science.sql`): 1 Biomedical, 2 Materials, 3 Power Systems, 4 Electronic. Disciplines: 19 / 21 / 19 / 19 per science.
- **Every inventory commit ends in `send_full_inventory_update`** (move, grant, remove, use, trade, the vendor paths, the resync), which already reads every row with its container, so the tool refresh needs no new query and no edit to `move_/mod.rs`, `containers.rs`, `BAG_SIZES` or `grant/validation.rs`.

## Design decisions

- **Station tracking at 1 Hz, not on movement.** The station set changes when the player moves, when a station spawns or despawns, on a world change and when the cell entity is re-created. A sweep beside the cover tick catches all four at one seam, at one spatial-grid query of radius 5 per player per second. The tick only drives the window label: `forward.rs` recomputes the mask for every request, so the gate never runs on stale positions.
- **Reach** is `MAX_INTERACT_DISTANCE` (5) in 3-D, the same test `interact` applies, limited to the player's own space. Equal distances pick the lower entity id, so the reported machine never flaps.
- **Report on change only.** `CraftingStationState::record` returns whether the set differs from the last report; the first tick after the entity is created always reports (even an empty set), so after a world change the base cannot keep the old world's station. A player without a `player_id` is skipped and reports once loaded.
- **Per-session base state** lives in one new `ConnectedClientState` field, `crafting_options: CraftingSessionOptions` (stations, tools, craft anywhere, last sent). It dies with the connection and survives a world change, so "craft anywhere" lasts until logout.
- **140 sends.** Unconditional at every world entry, as the last message of CR-03's login crafting bundle (`options::login_options` feeds `sync::push_crafting_on_login`), then only when the payload changes. Before the login send nothing goes out, so a station report that arrives while the client loads the world never reaches an entity the client has not created. Per section: the station as the machine; the best tool (highest `tech_comp`, then lowest instance id) for every section but alloying.
- **Gate order** (`gate.rs`): no gate for spend and respec; then the station mask; then craft anywhere; alloying stops there; then the tools, read fresh from the database (not the session cache) with the discipline from the blueprint (craft) or the owned item instance (research, reverse engineering: any of its disciplines). Every failed read refuses. The rejection is `CraftReject::NoStationOrTool { verb, station_mask, tools }` (in `feedback/reason.rs`), text "No crafting station or tool for <verb> nearby.", reason `no_station_or_tool`, no `onErrorCode`.
- **`.allcraft`** stays a `Target::Player` command. The cell sends `GmAllCraft { entity_id, player_id, gm_entity_id }`; the base re-checks the caller's session `access_level >= 2`, then sets every paradigm (from `resources.racial_paradigm`) to 7, every catalog discipline to expertise 100 and every blueprint, in one `save_crafting_state`, pushes the saved state with CR-03's `sync::build_crafting_state_bundle` (136 per discipline, 138 per paradigm, 139 and the unchanged ASP total) as one reliable bundle, turns on craft anywhere and forces a 140. ASP is untouched.

## Telemetry

Per the work-packets "Telemetry contract" (PR #877) and the CR-05 **Telemetry** line. Every event below is on target `crafting` and carries `account_id`, `player_id` and `entity_id`.

| Event | Level | Where | Fields |
|---|---|---|---|
| `options_changed` | INFO | `options.rs`, on every 140 send | `cause` (`moved`, `station_despawned`, `world_change` from the cell's `StationChangeCause`; `bag15_changed`, `login`, `gm_anywhere` on the base), `stations` and `tools` per section (0 = none) |
| `rejected` `reason=no_station_or_tool` | INFO | `feedback::reject` | CR-03's event, whose `verb` is the cell method name (`craft`, `research`, `reverseEngineer`, `alloying`), plus `station_mask` and `tools` (crafting-bag instance ids considered) |
| `gm_allcraft` | INFO / WARN | `allcraft.rs` | `outcome=granted` with `disciplines_before/after`, `blueprints_before/after`, `paradigm_levels_before/after`; `outcome=refused` (WARN) with `access_level` |
| `persist_failed` | WARN | `allcraft.rs` | `phase=save_crafting_state`, paired `rows_affected` / `expected`, `error_class` |
| `lookup_failed` | WARN | `options.rs`, `gate.rs`, `allcraft.rs` | `phase`: `session`, `tool_table`, `login_tools`, `gate_tools`, `gate_catalog`, `gate_item`, `db_pool`, `catalog`, `paradigms`, `load_state` |
| `push_failed` | WARN | `options.rs`, `allcraft.rs` | CR-03's event: `what` = `crafting_options` \| `allcraft_state`, `reason` (the send outcome) |
| `login_sync` | INFO | `sync::push_crafting_on_login` | CR-03's event, plus `crafting_options` (whether the bundle carried 140); the state counts are omitted when the state did not load |
| `forward_failed` | WARN | cell station tick | `kind=crafting_stations`; the tick logs nothing else, nothing per tick |

The cell tells the base why its set changed (`CraftingStations::cause`): the first report after the entity is created is `world_change` (login or world change), a report where a previously reached station no longer exists is `station_despawned`, anything else `moved`.

Metrics: a gate refusal goes through CR-03's `reject`, so it counts as `crafting_requests_total{verb, outcome=rejected}` and `crafting_rejections_total{verb, reason=no_station_or_tool}`. CR-05 adds no metric of its own. `lookup_failed` is not in the contract's event list yet; the coordinator should add it.

- **Spam cost of refused requests** (server-authority-enforcer review, low): a refused craft-family request away from any station costs one or two queries (the bag, the item). The session already caches the tools; a later packet can consult the cache first or rate-limit.
- **Craft anywhere is not revoked** before logout, even if the GM ran it on the wrong player. Fine for UAT.
- **Research and reverse engineering** resolve the item in any container of the player's; the verb packets (CR-08) must restrict the source container.
- **A timed craft** (CR-06) must decide whether leaving the station cancels it; the gate checks once, at request time.
- Provenance ids were removed from the source comments this packet wrote and from the `(CR-05)` mentions in `cell-catalog/src/crafting/constants.rs`, `wire/src/crafting/request.rs` and `player/crafting/mod.rs`.

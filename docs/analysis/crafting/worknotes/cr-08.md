## Design decisions

- **Request-time checks, then the job.** `research_job` / `reverse_engineer_job` read the catalog and the named instances (`item_lookup::held_instances`: owned, in bag 1 or 15, in request order), apply the pure rule, and build the job; `handle_*` submits it through `induction_verb::submit_job`, which counts `crafting_requests_total{outcome=accepted}` only for `Started` / `Queued`. The split lets tests run the job on their own engine with a scripted RNG.
- **Refusals reuse CR-06's `component_missing` / `component_not_in_crafting_bags`** for a named item that is gone or outside the crafting bags. CR-15 (in review) adds `item_missing` / `not_carried` for item use; the coordinator may prefer those after both land.
- **A kicker with no applied science is `not_kicker`.** The client could not slot it in any science window.
- **Duplicates.** The same kicker instance named twice is the same science twice (`kicker_duplicate_science`); the item named as its own kicker is `kicker_same_science`.
- **No eligible discipline is not a refusal.** As in the legacy server, the item and kickers are used and the line says nothing was learned (`result=failure`, no `chance` or `roll`). Refusing it instead would change the owner-approved D-CR15 flow; open question below.
- **Roll order.** One sample picks the discipline from the eligible list sorted by id, a second is the roll in `[0, 100)`; success is `roll < chance`. The pick is `min(floor(u × n), n − 1)`, so the top of the interval never indexes past the end (C-50).
- **Blueprints taught.** Every blueprint whose product is the item and whose discipline the player knows, not yet known, in id order. The plan carries `(blueprint_id, discipline_id)` pairs and `transaction/learn.rs` re-checks the discipline under the `sgw_player` row lock (server-authority review: a respec between the unlocked read and the transaction must not leave a blueprint of a dropped discipline).
- **Lock order.** `learn_blueprints` is the only step that locks `sgw_player`, after every inventory row and before the expertise rows: vendor paths take item row then player row, spend and respec take player row then expertise. A plan with no blueprints never locks the player row, as before.
- **Reverse engineering.** Candidates are the blueprints that make the item and have at least one component set, sorted by id; blueprint and set are each one uniform sample, then one sample per component. When every component comes to zero, the one with the highest sample (first on a tie) recovers one unit, which spends no extra sample. `consume_named: [(item, 1)]` so only the named instance is used.
- **Completion state.** Both jobs read the crafting state unlocked at completion (`induction_verb::state_at_completion`); a read failure is `lookup_failed` WARN `phase=completion_state` and `rejected reason=induction_failed`. Expertise is written from the locked row (`before + 5`, capped), so a stale read only shifts the chance slightly.
- **`JobOutcome::Completed(Box<JobReport>)`.** The six new report fields made clippy's `large_enum_variant` fire; CR-07 and CR-09 write `Box::new(applied.report())` (told cr07 directly).
- **Timer id 0** for both verbs, as the legacy server sent.

## Known gaps

- **No in-client record.** The research page's chance display ignores the tech-competency limit (C-39), so a player at or above the item's tc sees a chance and gets "learned nothing new".
- **Stale pre-read.** The roll uses expertise read before the transaction; a spend or GM grant landing in between shifts the chance by the difference and can take expertise up to 4 past the item's tc. Not an exploit (server-authority review).
- **Future respec (CR-10)** must not lock inventory rows or take advisory keys after locking `sgw_player`, or it can deadlock with a research that teaches (it holds item rows and waits on the player row). Taking advisory key 0 first also avoids it.
- **A component set with an empty component list** would consume the item and grant nothing; the catalog groups sets from rows, so no such set can exist today.
- **No uniformity property test.** The pick is checked at the ends of the interval and between, not statistically.

## Evidence

### The client clock (SGW.exe, Ghidra, 2026-09-26)

| Address | What it does |
|---|---|
| `0x00dd62a0` | `updateFrequencyNotification` handler: `u8` hertz, as a float, into the global `0x01e51cb8` |
| `0x00dd6d00` | `tickSync` handler: `+0x32c` = `gameTime`; `+0x334` = previous arrival time; `+0x33c` = now; `+0x344` = `tickRate * 0.001` (`DAT_01848ab8` = `0x3F50624DD2F1A9FC` = 0.001) |
| `0x00dd6820` | `setGameTime` handler: `+0x32c` = low 16 bits; `+0x330` = the rest (the getter never reads `+0x330`) |
| `FUN_00c6e220` -> `FUN_00dd6c60` | clock = `(+0x32c + (now - +0x334) / +0x344) / hertz` seconds |
| `FUN_00c6d1c0` | `CooldownManager`: remaining = complete - clock, clamped to 0 |
| `0x00e09160` | `EffectSet` (type 5): creates a new entry only when clock < complete |
| `0x00e47800` | crafting timer (type 16): remaining = complete - clock |

**Binding (closes the link CR-E1 left open).** A static initialiser stores each handler in a `ClientMessageHandler` object and registers it by name with the client interface `0x01ef2518`: `0x00dd62a0` at `0x017bb0a7`/`0x017bb0e7` as `"updateFrequencyNotification"` (length 1), `0x00dd6820` at `0x017bb137`/`0x017bb177` as `"setGameTime"` (length 4), and `0x00dd6d00` at `0x017bb6d7`/`0x017bb717` as `"tickSync"` (length 8). The getter's singleton (`FUN_00c6f690`) stores a freshly built `ServerConnection` at `+0x28`, which is the object `FUN_00dd6c60` reads. `cre1` independently re-verified the three handler bodies and named them in Ghidra.

So the client's clock is `TICK_SYNC.gameTime / hertz` seconds, and `tickRate` is **milliseconds per tick**. The domain is certain, and no client patch is needed; D-CR20's fallback is not triggered.

### The legacy server

`deprecated/cpp-config/config/BaseService.config:66` sets `tick_rate` to 100 (ms). `client_handler.cpp:46` sends `updateFreq = 1000 / tickRate` (10 Hz), then `TICK_SYNC {ticks, tickRate}` and `SET_GAME_TIME {ticks}`, where `ticks = (now - server start) / tickRate` (`cell_manager.cpp:200`), one count for the whole server. Python `getGameTime()` is `ticks * tickRate / 1000` (`base_py_util.cpp:180`).

### What was actually wrong

The packet and audit C-13 say the declared rate (100 ticks/s) and the 10 Hz loop disagree. They don't: hertz 10, 100 ms per tick and one tick per 100 ms send already agreed. The "10x slow" claim came from reading `tickRate` as ticks per second, and the combat advisor's memory note carried it. The real defects were:

1. Each session's tick loop counted from 0 at its own login, and login sent `TICK_SYNC {0}` and `SET_GAME_TIME {0}`. Every client held a different clock, so the cell could not build an expiry that meant the same instant to anyone.
2. Every timer sender passed `0.0` (cooldown, warmup, reload: the client showed no remaining time) or the relative duration (effects, `.net_timer`).

The bigworld-engine-advisor reviewed the design read-only and agreed; it re-checked `FUN_00dd6c60` in Ghidra.

## Design decisions

- **One process-wide epoch**, a `LazyLock<Instant>` in `cimmeria-wire`, forced in `Orchestrator::new` so it counts from server start. Cell and base run in one process (`services/src/orchestrator.rs`), so one static serves both. The epoch is server start, not Unix time: `BigWorldTimeComplete` is `f32`, and seconds since 1970 would round to about two minutes.
- **One rate source.** `UPDATE_FREQUENCY_HZ = 10`, `TICK_PERIOD_MS = 1000 / HZ`, `TICK_SYNC_INTERVAL = TICK_PERIOD_MS`. `build_time_sync`, `build_ongoing_tick_sync` and the loop use them; the two literal `TICK_RATE = 100` consts are gone.
- **Ticks are derived from elapsed time** (`elapsed_ms / 100`), not counted per send, so they cannot drift from the declared rate however the loop is scheduled.
- **Login sends the current ticks** in both `TICK_SYNC` and `SET_GAME_TIME`, in the C++ order. The client keeps only the low 16 bits of `SET_GAME_TIME`, so after 6553.6 s of uptime its clock reads low for about 100 ms until the first heartbeat. No timer is on screen at that point. The advisor suggested appending a second `TICK_SYNC` after `SET_GAME_TIME`; not done, because it changes the bundle and the packet said to keep the wire unchanged.
- **`build_time_sync` takes `ticks` as a parameter.** It stays a pure builder that byte-exact tests can drive.
- **Timer senders switched to absolute.** The domain is certain, so per the packet's third bullet the ability cooldown (`TotalTime = cooldown + warmup`), warmup and reload senders now send `game_time_secs() + duration`. The warmup-interrupt and effect-clear timers keep `0.0` on purpose.
- **Adjacent fix, same class:** the duration-effect timer (`pulsing/register.rs`) and `.net_timer` sent the relative duration. With a server-wide clock the effect icon would almost never appear (`0x00e09160` skips an expiry in the past), so this change would have made it worse. Both now send absolute expiries. The coordinator can split this commit (`173abd44`) off if it is out of scope.

## Known gaps

- **Test clock trap.** The epoch starts at the first read in a test process, and `d + 1e-7` rounds to `d` in `f32`. The expiry-window tests therefore wait until the clock is 10 ms past its epoch before sampling. Without that, a relative-expiry revert passed; `0e12e5fe` fixed it.
- The client's clock runs about one tick ahead of the server's (`+0x334` is the previous arrival), so client cooldowns end up to 0.1 s early. The server's cooldown check has no slack for that. Not changed here.
- Category cooldown timers (type 8, one per `monikerId`, `AbilityManager.py:611`) are still never sent.
- A server restart resets the clock. No absolute expiry is persisted today; CR-06's induction queue must store remaining time, not the expiry.
- The in-game bar is unverified here; CR-14 checks it.

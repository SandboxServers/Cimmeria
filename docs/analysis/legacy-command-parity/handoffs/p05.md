## Behavior implemented

### `.givecash <amount>` / `.givexp <amount>` (both new)

`Target::Player`, arity 1/1. Grants to the *selected target*; the calling
GM receives the definitive feedback line. Ported from legacy `giveCash`
(`deprecated/python/cell/commands/Player.py:146-156`) and `giveExperience`
(`:210-219`) — read both directly and confirmed the coordinator's summary
exactly (target-selected grant, `player.feedback(...)` to the caller). D02
keeps the current Rust amount bound (`<= 0` rejected, matching the native
`gmGiveCash`/`gmGiveXp` handlers) rather than reproducing legacy's unbounded
`giveCash`/`giveExperience`.

`.givexp`'s `amount > 0` is confirmed before the `i32 -> u64` cast, matching
the native `gmGiveXp` ordering exactly (guards against a negative `i32`
wrapping into an absurd unsigned grant).

Both resolve the target's `player_id` cell-side
(`space_mgr.get_entity(target).and_then(|e| e.player_id)`) and reject with a
clear message if absent — even though `CellToBaseMsg::GrantXP` itself
carries no `player_id` field (base-side `handle_grant_xp` derives it
independently from its own `connected` session state); this is the
console layer's own guard that the selection is a real player before
forwarding anything.

### The `gm_feedback_to: Option<u32>` fix (the reason this packet exists)

`GrantCash`/`GrantXP`'s prior `notify_gm: bool` field conflated the GM
feedback recipient with `entity_id` (the grant's DB/UI recipient) — correct
for the native `gmGiveCash`/`gmGiveXp` paths (caller grants to self) but
wrong for `.givecash`/`.givexp` (caller grants to a selected target). The
rename makes the recipient explicit: `Some(gm_entity_id)` sends the
definitive post-commit line to that entity; `None` sends none. Native
`gm/give.rs` paths pass `Some(entity_id)` (same entity, zero behavior
change); mob-kill XP and loot-pickup cash pass `None` (unchanged from
`notify_gm: false`); the two new console handlers pass
`Some(caller_id)` — the actual fix.

`GrantItem`/`RemoveInventoryItem`/`GrantExpertise`/
`GrantAppliedSciencePoints` have the identical caller/subject conflation
(where applicable — `GrantExpertise`/`GrantAppliedSciencePoints` don't
currently have any console-driven selected-target caller yet) but are
explicitly out of scope per the brief — see Flagged follow-up.

## State / persistence / client-recipient evidence

- `legacy_p05_grant_cash_feedback_goes_to_caller_not_target` /
  `legacy_p05_grant_xp_feedback_goes_to_caller_not_target` (live-DB, base-
  side): two distinct fully-connected `ConnectedClientState` sessions
  (target, caller) at distinct addresses. Assert exact DB totals after the
  grant (`naquadah`/`exp`/`level`/`training_points`), `send_count_to(
  target_addr) == 1` (the wire push only), `send_count_to(caller_addr) == 1`
  (the feedback line only), `transport.len() == 2` (no other traffic —
  rules out a duplicate send to either address).
- `legacy_p05_give{cash,xp}_emits_grant_with_caller_feedback_split`
  (cell-side, no DB): asserts the exact `GrantCash`/`GrantXP` tuple
  (target entity id, target player id, amount, `Some(caller)`) and that
  zero feedback lines are emitted from the cell side (proves no optimistic
  "requested" message).
- Failure/rejection paths (non-positive amount, target with no player_id,
  non-player target): assert `grant == None` (no message sent) alongside
  the specific feedback substring, for both commands.
- No test asserts a distinct caller-cash-unaffected scenario as a *separate*
  DB row, because `GrantCash`/`GrantXP` never touch a "caller row" at all —
  the caller only ever appears as the `gm_feedback_to` wire recipient, never
  as a DB write target, for both commands. The caller/target DB-isolation
  acceptance criterion is therefore covered by the same two tests above:
  only `target_player`'s row is ever queried/asserted, and the caller's
  session never receives a DB-driven wire push (only the feedback line).

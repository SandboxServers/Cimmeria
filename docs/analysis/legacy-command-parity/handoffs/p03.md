## Dead-code fix (applies to all seven commands, same class as a P02 fix-up)

`show()` previously took `target_id: Option<u32>` with `let subject =
target_id.unwrap_or(caller_id);` — a "fall back to the caller" branch. Every command routed to
`show` (`primarystats` … `stealthstats`, now `stats`) is registered `Target::Being`, a **typed**
target kind. `dispatch::resolve_target` returns `Err` (rejecting the command before `exec` is ever
called) when a typed command's caller has no current selection — it never produces `Ok(None)` for
a typed spec, only for `Target::None` commands. So the fallback branch was unreachable in
production for every command in this file, identical in shape to the `query::facing`/
`query::combat_info` dead-code P02's independent reviewer flagged and fixed. Applied the same fix:
`show(cmd, caller_id, target: u32, tx, space_mgr)`, with `dispatch.rs`'s call site
`.expect("Target::Being guarantees a resolved target")`-unwrapping at the one place that
legitimately knows the invariant holds. Behavior-preserving — the removed branch could never
execute either way.

## Flagged follow-up — not a stop condition, proposed for a future packet

**The ledger's "missing-stat" acceptance criterion (a stat "genuinely absent from the target's
stat block") cannot be reached through any real `CellEntity` fixture under the current data
model.** Confirmed by reading the full construction path, not assumed:

- `CellEntity::new` (`crates/entity/src/cell_entity/construction.rs:20-34`) is the single
  constructor for every entity, player or NPC, and it unconditionally sets
  `stats: StatList::new()`.
- `StatList::new()` (`crates/entity/src/stats/stat_list.rs:23-151`) inserts every stat id used by
  all seven groups in this file, unconditionally — verified every constant used in `stat_set()`
  against the template block.
- `StatList` exposes `get`/`get_mut` but **no removal method** and no partial/empty constructor;
  its internal `HashMap` is private.

So `entity.stats.get(*stat_id)` is unconditionally `Some` for every id every group here looks up —
there is no way, from `crates/services` (this packet's entire owned-path scope), to build a fixture
that exercises the `None`/`"n/a"` branch end-to-end. Handled by splitting the coverage into two
layers instead of forcing an artificial fixture:

- Extracted the exact `Some`/`None` formatting logic into `format_stat_line`, with co-located unit
  tests in `stats.rs` pinning both branches — this tests the real production code that would run
  if a stat were ever absent, just not through a full `show()` → `CellEntity` round-trip.
- Did **not** add a `StatList::remove` (or equivalent) method to `crates/entity` to force an
  end-to-end fixture — that crate is outside this packet's owned paths, and this is a
  "verification, not new work" packet per its own scope statement; adding new public surface to a
  shared crate other in-flight/future packets depend on should get an explicit grant, not a
  unilateral addition here.

**Proposed disposition**: no action needed to close P03 — the two unit tests are a genuine
regression guard on the only code that formats a missing stat, and every relevant stat is provably
always present today, so the gap is theoretical, not a live bug. If a future packet ever needs to
simulate a genuinely partial stat block (e.g. for save/load partial-hydration testing), a small
`pub fn remove(&mut self, stat_id: i32) -> Option<Stat>` on `StatList` would close it cheaply —
noting it here rather than adding it unasked.

## Regression proof

**Field-set/order/value drift** (`legacy_p03_all_groups_report_exact_field_sets`): temporarily
mutated `stat_set()`'s `"primarystats"` arm to both reorder two fields (`coordination`/
`engagement` swapped) and drop one (`morale` removed) in a single edit. Re-ran the test — failed
immediately:

```text
thread '...legacy_p03_all_groups_report_exact_field_sets' panicked:
assertion `left == right` failed: primarystats: field set/order/values must match the legacy statIds list exactly
  left: ["engagement: 1/1", "coordination: 1/1", "fortitude: 1/1", "perception: 1/1", "intelligence: 1/1"]
 right: ["coordination: 1/1", "engagement: 1/1", "fortitude: 1/1", "morale: 1/1", "perception: 1/1", "intelligence: 1/1"]
```

Restored; re-ran; green (6/6). This single test doubles as the regression guard for all seven
groups (parameterized over the command name), so this one manual mutation demonstrates the guard
works for the whole family — a drop/reorder/mis-value in any of the other six arms would fail the
same assertion for that command.

**Selected-target isolation**: not separately reverted — the test
(`legacy_p03_stats_reports_selected_targets_values_not_callers`) asserts both a positive
(`"    health: 55/200"` present) and a negative (`"    health: 100/100"` absent) condition against
deliberately distinct caller/target values, so a caller/target mixup bug (e.g. reading
`caller_id`'s stats instead of `target`'s) would flip both assertions simultaneously; this is the
same class of proof P02 used for its analogous isolation test.

## Behavior implemented

### `.players` (registered, scope fixed)

`Target::None`, no args. Lists every player online on this CellApp service — not just the
caller's space — as `" - <name> (<world>)"` per player, preceded by the legacy header verbatim
(`"Players online on this CellApp:"`). Ported directly from legacy `players`
(`deprecated/python/cell/commands/Misc.py:174-183`).

`SpaceManager::all_player_entity_ids` (`space_manager/queries.rs:105-111`) already walks every
loaded space (`self.spaces.values()`), confirming the coordinator's pre-dispatch read — the bug
was entirely in `query::players` re-filtering that already-CellApp-wide result down to
`caller_space_id`. Fix: removed the filter. World resolution reuses the pre-existing
`get_entity_world_name` (`space_manager/queries.rs:49-53`); name resolution uses
`CellEntity.character_name`, falling back to `"player {id}"` when unset (legacy's `getName()`
fallback behavior for a nameless player was outside this packet's read set, per the brief — this
fallback is a Rust-side choice, not a ported legacy string, and is called out as such in the
worknote).

Sorted by entity id for deterministic output — legacy iterated a Python dict
(`PlayersByName.values()`) in unspecified order, so exact-order parity isn't meaningful here; this
is a legacy-bug correction under D02, not a content deviation.

**Not implemented — confirmed unreachable, not scoped down arbitrarily**: legacy's `"In
transition"` fallback (a connected player not yet bound to any space). Grepped
`crates/services/src/cell/` for `in.transition|InTransition|ConnectedClientState|
connected_players|pending_players` — no cell-side "known players" registry exists beyond each
space's `players` set; base-side `ConnectedClientState` isn't visible from the cell service. A
player only appears in `all_player_entity_ids()` once `connect_entity` has placed them in a
space, so every id `.players` resolves already has a world — the `"In transition"` fallback string
is present in the code (for shape-parity with legacy's format) but unreachable in practice. Per
the coordinator's explicit instruction, no fake in-transition tracking was invented. `.players`
covers every real GM use case (every player who has completed world entry).

### `.listabilities` (new)

`Target::Player`, no args, no fallback (matches `deprecated/python/cell/commands/Player.py:
222-234`'s signature — the audit's `()`; P). Prints `"Ability list of entity {target}:"` then
`"    {name}"` per known ability id (resolved via `space_mgr.ability_defs`), or
`"    <unknown ability {id}>"` for an id with no matching `AbilityDef` — retained rather than
dropped, matching legacy's own `"    <unknown ability %d>"` fallback. Sorted by ability id for
deterministic output (legacy iterated `target.abilities.abilities` in unspecified order).

Read `listAbilities`'s actual body directly (not just the brief's summary) before implementing,
per the packet's stop condition: it is a flat, unfiltered dump with no category grouping or type
filtering — the brief's summary was accurate, no scope surprise.

The ability catalog (`SpaceManager::ability_defs: HashMap<i32, AbilityDef>`) is populated at
startup (`service/startup.rs:169-171`) with no DB round-trip in the console-command hot path.
`.listabilities` is a distinct, independent handler from the native
`gm::query::handle_list_abilities` (which prints raw numeric ids with no name resolution and falls
back to the caller when unselected) — the two commands have genuinely different contracts
(required-target-no-fallback vs. selected-or-self), so they were kept separate rather than
unified.

## Flagged follow-up — not a stop condition, proposed for a future packet

**`.players`'s "In transition" case is unreachable from cell-side state today.** See "Not
implemented" under `.players` above for the full evidence trail. If a future packet ever threads
base-side `ConnectedClientState` visibility into the cell service (or builds an equivalent
cross-service roster), `.players`'s existing `unwrap_or_else(|| "In transition".to_string())`
branch is already the correct splice point — no `query.rs` changes would be needed beyond making
`get_entity_world_name` genuinely return `None` for such a player, which it already does by
construction.

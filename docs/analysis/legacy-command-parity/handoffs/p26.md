## Behavior implemented

### `.gotoxyz <x> <y> <z>` (new)

`Target::None`, arity 3/3. Moves the selected target, falling back to the
caller when nothing is selected — ported from legacy `gotoXYZ`
(`deprecated/python/cell/commands/Player.py:368-382`, read directly,
confirmed exactly): `entity = target or player`,
`entity.teleportTo(Vector3(x, y, z), 0.0)`, feedback to the caller
(`"Moving entity %s to (%f, %f, %f)"`, legacy uses `entity.getName()`; this
packet reports the numeric entity id instead — no cell-side name resolution
exists, and D02 asks for exact spelling/arity/defaults/target semantics, not
verbatim legacy prose, matching P05's precedent for feedback wording).

Reuses the exact mechanism the native `gmGotoXYZ`/`gmSummon` handlers
already use (`crates/services/src/cell/cell_methods/gm/travel.rs`):
`space_mgr.update_entity_position(...)` first (spatial grid +
`cell_entity.position` together, confirmed by reading the function body —
`update_entity_position` calls `grid.update_position(...)` in the same call,
so there's no separate "refresh" step), then
`space_mgr.note_authorized_teleport(...)` (reseeds the movement-validator
clock, called unconditionally for both player and NPC targets — matches
`handle_summon`'s existing precedent; confirmed safe for NPCs by reading
`MovementValidator`: `move_clock` is a bare `entity_id`-keyed map only ever
consulted against *client* movement packets, which NPCs never send).

**Player vs. NPC split** (the core of this packet):

1. **Player target** (caller or another player): additionally sends the
   authoritative `TeleportPlayer` snap
   (`entity_id`, `space_id`, `position`, `prev_pos`) — this pushes
   `BASEMSG_FORCED_POSITION` to the moved player's own client and persists
   position base-side. `TeleportPlayer` carries **no GM-feedback field at
   all** (confirmed reading `cell_to_base.rs` — unlike P05's
   `GrantCash`/`GrantXP`, which needed the `gm_feedback_to: Option<u32>`
   fix), so no shared-message-struct change was needed this packet, exactly
   as the brief predicted. If the send fails (base channel closed), the
   handler logs a warn and returns without sending caller feedback — it does
   not claim a snap that never sent. This check is **reimplemented locally**
   in `travel.rs` rather than calling
   `cell_methods::gm::forward_to_base`, because that helper is `pub(super)`-
   scoped to `cell_methods` and not visible from `cell::console` — confirmed
   by reading its declaration. Behaviorally identical to the native
   handlers' own check.
2. **NPC target**: no client, no `TeleportPlayer`. `update_entity_position`
   alone is sufficient for other players to see the move — confirmed both by
   reading the function body (grid update happens inside it, not as a
   separate step) and by a new test
   (`legacy_p26_gotoxyz_npc_move_broadcast_to_witness`) mirroring the
   existing `summoned_npc_is_broadcast_to_caller_witness` proof for
   `gmSummon`, run against `.gotoxyz`'s own dispatch path rather than
   assuming the existing proof generalizes.

Both paths send the caller (not the moved entity, when they differ) an
immediate feedback line once the move is confirmed — `TeleportPlayer` having
no feedback field means this is simply `send_gm_feedback(caller_id, ...)`
called directly from `travel.rs` after the send succeeds, not a base-side
post-commit line like P05's grants.

Non-finite coordinates (`NaN`/`inf`) are rejected — not via a separate check
like the native `gmGotoXYZ`'s raw-byte parser, but via the shared
`parse::parse_f32` helper's existing `.filter(|v| v.is_finite())`, since
`.gotoxyz` parses string args through the console framework's shared parser
like every other float-taking command. Same outcome, no duplicated check.

## State / persistence / client-recipient evidence

- `legacy_p26_gotoxyz_player_target_emits_teleport_player_exact_bytes`:
  asserts the exact `TeleportPlayer` tuple (target entity id — never the
  caller's — the target's actual `space_id` fetched from the fixture rather
  than hardcoded, the exact destination position, and the pre-move
  position captured from the fixture) plus that the caller (not the target)
  receives the feedback line.
- `legacy_p26_gotoxyz_npc_move_broadcast_to_witness` /
  `legacy_p26_gotoxyz_player_target_move_broadcast_to_witness`: both drive
  a real two-tick `compute_aoi_changes()` sequence (enter-AoI, then move) and
  assert the exact `EntityMoved` position delivered to the witness — proves
  the spatial grid, not just `cell_entity.position` in isolation, reflects
  the destination.
- `legacy_p26_gotoxyz_caller_unchanged_when_moving_selection`: asserts the
  caller's own position is byte-identical to its pre-command value when a
  distinct target was moved (D03).
- `legacy_p26_gotoxyz_falls_back_to_caller_when_no_target`: asserts the
  caller is a player, so the fallback move still emits `TeleportPlayer` for
  the caller's own id — not silently skipped.
- `legacy_p26_gotoxyz_cross_space_selection_falls_back_to_caller`: asserts
  the cross-space entity is left completely untouched (position unchanged)
  while the caller is moved instead — proves the fallback doesn't
  accidentally reach across spaces.
- `legacy_p26_gotoxyz_player_target_survives_closed_channel`: asserts the
  cell-side grid write survives even when the base push is dropped — matches
  the documented "position is cell-authoritative the instant
  `update_entity_position` runs" behavior already established by the native
  handlers.
- Rejection paths (non-finite, malformed): assert zero position mutation
  and zero `TeleportPlayer`/grant alongside the specific feedback substring.

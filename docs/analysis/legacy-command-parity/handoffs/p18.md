## Status

Complete. `.location` and `.rotation` both fully implemented as real
dual-mode read/set commands. **The brief's Euler-orientation stop condition
did not trigger** — `CellEntity::direction` represents pitch/yaw/roll in
radians cleanly and legacy's `rotation` Vector3 uses the same component
order, so no axis is dropped and no design sign-off is needed. Evidence
chain in [worknotes/p18.md](../worknotes/p18.md) under "The Euler question".

The coordinator's registry/dispatch plumbing was correct as landed
(`Target::Spawnable`, arity 0-3, routed to `placement::dispatch`) and was
**not modified**. No files owned by P46 or P47 were touched.

One real limitation was found and is documented rather than worked around:
`BASEMSG_FORCED_POSITION` carries no orientation field, so `.rotation` on a
*player* target cannot snap that player's own camera. See "Known gaps".

One pre-existing defect outside this packet's files was found and is flagged
for a new packet rather than fixed here. See "Flagged follow-up".

## Behavior implemented

### `.location` (report) / `.location <x> <y> <z>` (set)

`Target::Spawnable`, arity 0-3. Legacy
`deprecated/python/cell/commands/Entity.py:101-116`.

- **0 args** — reports the target's current position, mutates nothing.
- **3 args** — sets the position, then reports the *actual* post-write
  value (re-read from the space manager, not an echo of the request).
- **1 or 2 args** — rejected with an explicit line; nothing is written and
  no readout is produced. Legacy gated its write on `z is not None`, so a
  partial tuple silently fell through to the readout as though the GM had
  asked for a report; corrected per D02 and per the ledger's "reject
  cleanly, don't silently pad" criterion.
- **4+ args** — already rejected upstream by the registry's `max = 3`.
- Non-finite (`NaN`/`inf`/`-inf`) and non-numeric components are rejected by
  the shared `parse::parse_f32` filter, same as `.gotoxyz`.

The set path reuses `.gotoxyz`'s snap abstraction exactly:
`space_mgr.update_entity_position(...)` (writes `cell_entity.position` and
the AoI spatial grid in one call), then
`space_mgr.note_authorized_teleport(...)` (reseeds the movement-validator
clock, unconditionally for player and NPC — `move_clock` is only ever
consulted against client movement packets, which NPCs never send), then
`TeleportPlayer` gated on `is_player`. On a failed `TeleportPlayer` send the
handler logs a warn and returns without claiming a placement the client
never received; the cell-side grid write is authoritative regardless.

**One deviation from `.gotoxyz`'s call shape, and it is the point of the
packet.** `update_entity_position`'s third parameter is `direction: [i8; 3]`
and it overwrites `cell_entity.direction` from it unconditionally. Every
server-authoritative caller in the tree passes `[0, 0, 0]`, so all of them
zero the moved entity's facing as a side effect. Legacy `location` assigned
`target.position` and nothing else, so `.location` captures `direction`
before the call and restores it immediately after via `get_entity_mut` —
the same write-back `cell/service/ticks/npc_movement.rs` already performs
for the same reason. This is the packet's primary regression guard.

### `.rotation` (report) / `.rotation <pitch> <yaw> <roll>` (set)

`Target::Spawnable`, arity 0-3. Legacy
`deprecated/python/cell/commands/Entity.py:119-134`. Same arity gate, same
rejection semantics, same re-read-before-report discipline.

The set writes `direction = Vector3::new(pitch, yaw, roll)` directly — no
`atan2`, no normalisation, no vector interpretation. `direction.y` is yaw in
radians, which is what `pack_angle(direction[1])` sends on the wire, what
`npc_movement.rs` writes, and what the legacy player row persisted as
`heading = rot.y`.

Deliberately **no** `note_authorized_teleport` (the validator only scores
position deltas; turning in place moves nothing) and **no** `TeleportPlayer`
(see below). Witnesses pick the new facing up on the next AoI tick, because
`space_manager/aoi.rs` emits `EntityMoved { position, direction, velocity }`
for every in-AoI entity every tick regardless of whether anything moved.

### Feedback

Both commands address `send_gm_feedback` to `caller_id`, never the subject
entity (D03). Wording keeps legacy's sentence shape at `{:.3}` precision:

```text
Position of entity 100000 is: (99.500, 1.250, -42.500)
Rotation of entity 100000 is: (pitch 0.500, yaw -1.250, roll 2.000) rad; heading -71.6 deg
```

`.rotation`'s axis labels and degree suffix are a deliberate addition to
legacy's bare tuple: `direction`'s semantics were ambiguous enough in this
codebase to produce a shipped bug class (P48), so the readout states them.
Same D02 latitude on feedback prose that P05 and P26 used.

## Regression proof — controlled negative runs

Two reverts, each applied and restored inline (no `git checkout`, so nothing
else in the worktree could be clobbered), full 13-test suite re-run clean
after each restore.

**1. Orientation write-back removed** (`if let Some(e) =
space_mgr.get_entity_mut(target) { e.direction = facing; }` deleted from
`location`):

```text
---- cell::console::tests::p18::legacy_p18_location_set_preserves_orientation stdout ----

  left: [0.0, 0.0, 0.0]

```

Exactly the one test pinned to the workaround failed; the other 12 were
unaffected, so the guard is pinned to the behaviour and not passing by
coincidence. The observed `[0.0, 0.0, 0.0]` is the literal
`update_entity_position([0, 0, 0])` side effect, i.e. the failure reproduces
the real bug shape rather than an artificial one.

**2. Partial-tuple rejection replaced with legacy's fall-through**
(`parse_triple`'s `n => { feedback; Triple::Rejected }` arm replaced with
`_ => Triple::Report`, reproducing legacy's `if z is not None` gate):

```text
---- cell::console::tests::p18::legacy_p18_partial_tuple_is_rejected_without_mutating stdout ----

test result: FAILED. 12 passed; 1 failed; 0 ignored; 0 measured; 1817 filtered out
```

The failure output *is* the legacy bug — a one-argument `.location` silently
reporting as though nothing had been asked. Confirms the guard reproduces

## Known gaps

1. **`.rotation` on a player target cannot move that player's own camera.**
   `compose_forced_position_body` (`mercury/aoi/update.rs:110-128`) writes
   entity id, space id, `vehicleID = 0`, position and previous position —
   **no angles at all**. There is no orientation field in
   `BASEMSG_FORCED_POSITION`, so there is nothing to send. The write is
   server-authoritative and witness-visible, and the target's next
   `avatarUpdateExplicit` overwrites it. This matches legacy exactly (legacy
   `rotation` wrote `target.rotation` and pushed nothing), and the realistic
   use of the command — posing an NPC — works fully. Recorded in
   `placement.rs`'s module doc and asserted by
   `legacy_p18_rotation_does_not_move_or_snap_player_target`. **If the
   coordinator wants a player's own camera to snap, that is a new wire
   surface and needs its own design round — it is not a defect in this
   packet.**
2. **`.location`'s persistence is not newly tested.** It rides
   `TeleportPlayer`'s existing base-side handler, the same shared
   infrastructure P26's handoff already flagged as belonging to whichever
   packet owns `crates/services/src/base/world_entry/teleport.rs`'s coverage.
3. **Client UAT: pending user session.** M4 Player Administration, per the
   README's Validation And UAT Gates table.

## Flagged follow-up — not stop conditions

1. **Inbound client `direction` is never unpacked — pre-existing, outside
   this packet's files, worth its own packet.**
   `base/connect_loop/encrypted/mod.rs:278` reads three raw packed-angle
   bytes out of `avatarUpdateExplicit` as `payload[32..35] as i8` and passes
   them through `BaseToCellMsg::EntityMove` ->
   `apply_client_position_update_at` -> `update_entity_position`, which
   stores them as `i8 as f32`. But `pack_angle` on the way out divides by
   `2*pi/256`, i.e. it assumes **radians**. So a moving player's
   `direction` holds packed-byte units in the `-128..127` range, which then
   get re-packed as if they were radians. Consequences: a player's facing is
   wrong for every witness once that player moves, and a `.rotation` readout
   on a moved player shows byte units rather than radians. The fix is an
   `unpack_angle` on the inbound path (or making `update_entity_position`
   take `[f32; 3]`), both of which touch shared movement code this packet
   does not own. Recommend a sibling packet to P48 — it is the same
   `direction`-semantics bug family.
2. **`update_entity_position`'s `[i8; 3]` direction parameter silently zeroes
   facing for six callers.** `.gotoxyz`, native
   `gmGotoXYZ`/`gmGoto`/`gmSummon`, respawn, ring transport and the content
   executor's transport action all pass `[0, 0, 0]`. `.location` (this
   packet) and `npc_movement.rs` are the only two callers that work around
   it. Consider either a `update_entity_position_keeping_facing` helper or
   changing the parameter to `Option<[f32; 3]>` — a shared-signature change
   that needs coordinator ownership, not a worker edit.
3. **`.lookat` (`console/entity.rs:226-250`) writes a Cartesian unit vector
   into `direction`** (`Vector3::new(dx / len, 0.0, dz / len)`). Under the
   now-confirmed `[pitch, yaw, roll]` semantics that is wrong — the correct
   write is `direction.y = dx.atan2(dz)` with `.x`/`.z` left alone. Same bug
   family as P48's `.facing` and `handle_show_rotation`. Left untouched per
   the brief; recommend folding it into P48's scope.

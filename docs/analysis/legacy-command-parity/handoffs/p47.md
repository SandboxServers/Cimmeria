## Behavior implemented

### `.speed <value>` — `Target::Being`, arity 1/1

Ported from legacy `setSpeed`
(`deprecated/python/cell/commands/Entity.py:537-548`, read directly and
confirmed exactly):

```python
target.getStat(Atrea.enums.movementSpeedMod).setCurrent(speed)
target.getStat(Atrea.enums.rotationSpeedMod).setCurrent(speed)
target.sendDirtyStats()
player.feedback('Set speed of entity %d to %f' % (target.entityId, speed))
```

Rust flow:

1. `super::parse_i32` — a non-integer feeds back `"speed must be an integer"`
   and returns with zero mutation.
2. Resolve the target; a vanished id feeds back `"speed: no entity."`
   (same defensive shape as `stats::show`).
3. Validate `speed` against **both** stats' live `[min, max]` *before* writing
   either. Out of range feeds back
   `"speed: <stat> must be between 0 and 500 (100 = normal)"` and mutates
   nothing. A stat missing from the block feeds back
   `"speed: target has no <stat> stat."`.
4. `set_current(speed)` on both — **current only, never `max`**, matching
   legacy.
5. `serialize_dirty()` (player target) or `serialize_dirty_public()` (NPC
   target), `clear_dirty()`, then `abilities::send_entity_method(target,
   ON_STAT_UPDATE, …)` — the entity-aware router that goes direct-to-client
   for a player and fans out to AoI witnesses for an NPC. Both speed ids are
   in `PUBLIC_STATS`, so the NPC path really does carry them (proved by a
   dedicated test, not assumed).
6. `send_gm_feedback(caller_id, "Set speed of entity {target} to {speed}")` —
   **D03**: addressed to the calling GM, which for `Target::Being` is
   routinely not the entity that changed.

### Deliberate deviations from legacy

1. **Reject out-of-range instead of silently clamping.** Legacy relies on
   `Stat.setCurrent`'s clamp into `[min, max]`, so `.speed 9000` quietly
   became 500 and `.speed -5` quietly 0 *while the feedback still echoed the
   typed value*. Per D02 ("correct legacy bugs rather than reproducing them")
   and matching the native `gmSetHealth` handler's existing
   reject-don't-clamp precedent, an out-of-range value is now rejected and
   **neither** stat is touched. Validating both before writing either also
   makes the two-stat write atomic — a GM can never end up with movement
   clamped one way and rotation another should the two stats' ranges diverge.
   The inclusive bounds themselves (`0` and `500`) are accepted.
2. **Integer feedback.** Legacy's `%f` renders the int stat as
   `100.000000`. The prose is preserved verbatim; the float rendering is not.
   Same call P05/P26 made on feedback wording.

## Scope escalation

Exhaustive grep of `MOVEMENT_SPEED_MOD` / `ROTATION_SPEED_MOD` /
`movementSpeedMod` / `rotationSpeedMod` across `crates/` and `entities/`
found the constants, their `PUBLIC_STATS` membership, their `StatList`
defaults `(0, 100, 500)`, the initial NPC stat payload in
`mercury/aoi/create.rs`, the read-only `.speedstats` dump, the canonical
`entities/defs/alias.xml` comments — and **no site that applies either stat
to anything**. `npc_movement_tick` steps by `CellEntity.move_speed`.

So the ledger's "deterministic movement/rotation speed effect — a real
tick-level movement assertion" was unsatisfiable within the originally-owned
paths: a faithful port would have set a stat nothing read.

The approved fix, in `npc_movement.rs`:

```rust
fn effective_move_speed(base: f32, stats: &StatList) -> f32 {
    let pct = stats.get(MOVEMENT_SPEED_MOD).map_or(100, |s| s.cur).max(0);
    base * (pct as f32 / 100.0)
}
```

called in place of the bare `npc.move_speed` read at the top of the per-NPC
loop. This is the server-side half of a contract `entities/defs/alias.xml`
already documents ("multiplies movement speed by curr/100") and that the
client already honours for its own local prediction — not a new server-only
knob. It is a no-op at the default `cur = 100`, so all four pre-existing
`npc_movement` tests keep their exact expected positions unchanged. Missing
stat falls back to 100 (unmodified, so a sparsely-built entity still paths);
a negative `cur` floors at 0 (stall, never reverse along the path).

No conflict risk: P18 owns `placement.rs`, P46 owns `travel.rs`; nothing else
in flight touches `npc_movement.rs`.

- `legacy_p47_speed_sets_both_current_values_and_leaves_bounds_alone`:
  asserts the full `(min, cur, max)` triple for both stats — `(0, 250, 500)`
  — which is what pins legacy's "current only, never max" contract, and
  asserts the feedback `Vec` is **exactly one** line with the exact text.
- `legacy_p47_speed_publishes_on_stat_update_with_both_stat_ids`: decodes the
  raw `onStatUpdate` `ARRAY<StatUpdate>` payload
  (`[count u32][{id,min,cur,max} 4×i32]…`) and asserts it contains exactly
  `(6, 0, 300, 500)` and `(81, 0, 300, 500)` — not a count-only payload, not
  `movementSpeedMod` alone.
- `legacy_p47_speed_on_npc_target_fans_out_to_witness`: drives a real
  `compute_aoi_changes()` enter-AoI tick first, then asserts the change
  arrives as a `WitnessEntityMethod` carrying both ids — proving
  `serialize_dirty_public` doesn't filter them out.
- `legacy_p47_speed_feedback_goes_to_caller_not_target` and
  `legacy_p47_speed_leaves_the_caller_alone`: D03's caller/subject split,
  asserted on both the message recipient and the caller's own unchanged stat
  state.
- Rejection paths (`"fast"`, `"501"`, `"-1"`, `"9000"`): each asserts zero
  stat mutation **and** zero `onStatUpdate` **and** no success line, not just
  the presence of an error string.
- `legacy_p47_speed_accepts_inclusive_bounds`: `0` and `500` are accepted —
  guards against an off-by-one in the new range check.
- Tick tests: exact `f32` position equality (the fixture geometry makes every
  step ratio an exact binary fraction), including the two-tick accumulation
  case and the `.speed 0` freeze that must *not* consume a waypoint.

## Known gaps

1. **`ROTATION_SPEED_MOD` has no server-side consumer.** `.speed` sets and
   publishes it (legacy parity, and the client applies it), but the NPC tick
   snaps yaw whole in one tick (`yaw = dx.atan2(dz)`) and has no turn-rate
   integration to scale. Adding one would be a new movement feature, not a
   parity port — deliberately out of scope. Coordinator approved recording it
   here rather than building it.
2. **Not persisted.** A `.speed` change lives in `CellEntity.stats` only and
   does not survive a relog. Matches legacy. If durable GM speed is wanted,
   it needs its own packet (and a column).
3. **Player targets get no server-side movement change.** For a player, the
   stat reaches the client and the client applies the multiplier; the server
   side of player movement is the warn-only speed layer in
   `MovementValidator` (`DEFAULT_TOP_SPEED`), which does **not** consult
   `movementSpeedMod`. So `.speed 400` on a player will emit
   `movement.speed_warning` events as the client legitimately outruns the
   tolerance. Not a correctness break (the layer is warn-only, never
   snap-back), but it will be visible in SigNoz and would need addressing
   before that layer is ever promoted to enforcement. Flagged for whichever
   packet owns the movement validator.
4. **Worktree provisioning:** this worktree was created without `external/`
   (not in git), so the first `cargo check` failed inside `cimmeria-entity`'s
   Recast/Detour `cc` build. Fixed by junction-linking `external/` from the
   main checkout. Worth folding into the coordinator's worktree setup step.

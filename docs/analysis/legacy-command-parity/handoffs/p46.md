## What the three commands do

| Command | Subject moved | Destination | Legacy |
|---|---|---|---|
| `.goto <name>` | `target or caller` | the named player's **exact instance** + position | `Player.py:298-318` |
| `.summon <name>` | the **named player** | `target or caller`'s instance + position | `Player.py:321-341` |
| `.gotolocation <world> <x> <y> <z>` | `target or caller` | named world, explicit coordinates, D15 default instance | `Player.py:344-365` |

All three feed back to `caller_id` only (D03) and all three resolve the
subject with legacy's `entity = target or player` (`Target::None` +
`target.unwrap_or(caller_id)`, the P26 pattern).

## The one design call: same-space moves bypass the transfer primitive

`transfer_player_to_space` checks `is_player` (D15) **before** it resolves the
destination, so handing it every move would refuse an NPC subject even when
the destination turns out to be the NPC's own space and no transfer is needed.
That is a capability regression against legacy (`entity.teleportTo(...)` was
kind-agnostic) and against P26 (`.gotoxyz` moves NPCs today), and D15's
restriction is explicitly scoped to "any cross-space/cross-world transfer".

So `move_subject` decides first:

```text
dest_space_id == Some(subject's current space)  ->  same-space snap (P26 path)
otherwise                                        ->  transfer_player_to_space
```

No resolution logic is duplicated to answer that: every call site already
knows the exact destination space (`.goto`/`.summon` from P44's
`Found.space_id` / the anchor entity; `.gotolocation` only names an exact
space when the destination world *is* the subject's current world).
`TransferOutcome::SameSpace` is still matched and still falls through to the
snap — the primitive owns the authoritative resolution, so its answer is
honoured rather than assumed unreachable.

**Coordinator decision point:** this is the only place P46 interprets rather
than wires. If the intent of D15 was "players only, full stop, even for a
zero-distance in-place move", say so and the pre-check collapses to an
unconditional primitive call — it is a five-line change plus three test
edits. The worknote argues for the scoped reading.

## GM-facing wording

Legacy strings are emitted **verbatim and unprefixed**; Rust-side diagnostics
carry the conventional `"<cmd>: "` prefix.

| Situation | Line | Source |
|---|---|---|
| name not live on this CellApp | `Player is not available on this CellApp` | `Player.py:308`/`:331` |
| name resolved, not in a space | `Player is not on any reachable space` | `Player.py:313`/`:336` |
| `.goto` success | `Teleporting to player <Bob>` | `:318` |
| `.summon` success | `Summoning player <Bob>` | `:341` |
| unknown world | `Unable to find world: Chulak` | `:361`, via `TransferRejected::describe()` |
| `.gotolocation` success | `Moving entity Vala to Agnos (40, 0, 40)` | `:365` |
| duplicate name | `Multiple players named <Daniel> -- refusing to guess (2 matches)` | **no legacy equivalent** |
| NPC subject, cross-space | `goto: target is not a player — cross-world transfer needs a client` | Rust-only (D15) |

Two deliberate deviations, both recorded in the worknote rather than applied
silently:

1. **`Ambiguous` wording is new.** Legacy's `PlayersByName` dict structurally
   cannot hold duplicates. Collapsing this onto "not available" would hide a
   uniqueness violation behind "no such player"; the lookup already logs it at
   `error` on `player.name_lookup`.
2. **`.gotolocation` uses Rust's `{}` float formatting, not C's `%f`** — `40`
   rather than `40.000000`, matching the `.gotoxyz` line a GM sees next to it.
   Sentence shape and field order are legacy's.

## Known gaps / deliberate non-fixes

1. **P44's `InTransition` gap is inherited, unchanged.** A player mid-gate-travel
   reports `NotFound` → "Player is not available on this CellApp" where legacy
   said "not on any reachable space", because `character_name` is cleared on
   the freshly created entity until `InitPlayerState` re-caches it. Closing it
   needs a name roster that outlives the entity (out of scope per P44). P46's
   mapping is already correct for both variants, so that future packet touches
   only the lookup body. The variant is covered today via a constructed
   entity.
2. **Success feedback on a cross-world move is queued behind `GateTravel`.**
   Same channel, FIFO, so when the subject *is* the caller the base processes
   the transfer (→ `RESET_ENTITIES`, `pending_world_entry`) before the chat
   line, and the GM may be mid-loading-screen when it lands. Sending it first
   would claim a transfer that had not been accepted, which the README
   forbids. Legacy has the same shape. Worth one line in the M4 UAT script:
   *does the GM actually see "Teleporting to player <X>" after a cross-world
   `.goto`?* If not, the fix is a base-side deferred line, not a reordering.
3. **No offline or cross-cluster name resolution** (D05 defers both), no fuzzy
   matching, no instance-selector argument (D15).
4. **`.summon` does not check whether the victim is in combat, dead, in a
   cutscene, or mid-minigame.** Neither did legacy. Flagged rather than added,
   because "when may a GM forcibly move a player" is a policy question, not
   wiring.

## Client UAT status

**Pending user session.** Scenarios, folded into M4 ("Travel within a space
and across worlds, especially same-world different-instance destination, with
transfer failure/disconnect recovery"):

1. `.goto <player>` where the target is in **another instance of the same
   world**, with a second player already in that instance — the GM must
   arrive next to them, and must see them. This is the acceptance criterion no
   unit test can fully prove (it ends in the base's world-entry handshake and
   the client's AoI).
2. `.goto <player>` to a world with no live instance — a fresh instance is
   allocated and the GM lands in it.
3. `.summon <player>` across worlds while the victim is **mid-trade** — the
   partner must get `onTradeResults(Cancelled)`, not a dangling reference
   (P45's S2 fix; P46 is its first real caller).
4. `.summon` with an NPC selected — the named player arrives at the NPC.
5. `.gotolocation <own world> x y z` while in a non-default instance — must be
   a snap, **no loading screen**.
6. `.gotolocation <unknown world>` — the GM gets `Unable to find world: X`,
   stays exactly where they were, and can keep playing without relogging.
7. `.goto`/`.gotolocation` with an **NPC selected** and a cross-world
   destination — refused with a readable reason, NPC unmoved.
8. Does the success line actually reach the GM after a cross-world move? See
   *Known gaps* #2.

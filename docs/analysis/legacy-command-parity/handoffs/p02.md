## Behavior implemented

### `.info [entityId]`

Selection wins over the explicit `entityId` arg (opposite precedence from the native
`gm::query::handle_show_player`, which was deliberately left untouched — other callers depend on
its existing behavior). Falls back to `entityId` only when there's no current selection, scoped to
the caller's space (a cross-space id resolves to "Could not find entity", matching every other
console command's cross-space rejection convention rather than legacy's unscoped `Atrea.
findEntity`). Prints, each only when present/nonzero:

- Header `----- ENTITY <label> (<id>) -----` (label: character name → NPC name → `template N` →
  `player`/`entity`)
- `Flags:`/`Interaction:` as raw hex (no Rust name table exists for `EEntityFlags`/
  `EInteractionNotificationType` — see Gaps)
- `Kismet event set:`, `Name ID:` (both `!= 0` gated, matching legacy)
- `Template: <id>` (id only — no name cache cell-side, see Gaps)
- `Tag:`, `Static mesh:`, `Body set:` (all `Option` fields, printed when `Some`)
- `Archetype: <name> (<id>)` — legacy's 9-entry `ARCHETYPE_*` table ported directly
- `Alignment:`/`Faction:`/`Level:` — always printed (these are non-`Option` fields on `CellEntity`,
  always meaningful). Alignment reuses `.alignment`'s existing 3-entry name table (P13); Faction
  uses a **different, this-codebase-specific** 4-entry table — see worknote for why legacy's
  34-entry `FACTION_*` table would be actively wrong here.
- **Omitted entirely, not faked:** primary/secondary/skin-tint colors — `CellEntity` has no tint
  fields at all.

### `.facing`

Required target (`Target::Spawnable`, no fallback to self; `dispatch::resolve_target` guarantees a
resolved target before this handler runs, so it takes `target: u32` directly — no dead
"not found" branch). Computes the bearing angle from the caller to the target relative to the
caller's own facing direction, and the 5-bucket facing class (Above/Below/Front/Flank/Rear), both
ported directly from `SGWSpawnableEntity.facing`/`facingType` with the exact legacy `CAS_*`
geometry constants. Reports `Facing: <rad> rad / <deg> deg (<class>)` and
`Distance: <3D distance>` (caller to target, matching `player.distanceTo`).

### `.combatinfo`

Required `Target::Mob`. Diagnostic checklist — emits feedback **only for problems found**, silent
on success (verified: `legacy_p02_combatinfo_healthy_target_is_silent`). Implements 2 of legacy's 3
checks:

- No template → `- Entity is not spawned from a template` (feedback line has a leading space before
  the hyphen)
- No known abilities → `- Entity has no ability set` (same leading-space convention)

**Does not implement** the "no weapon" check or the ability-type-bucket "no damaging abilities"
check — see "Flagged stop condition" below.

## Flagged stop condition — needs a coordinator decision

Two of `.combatinfo`'s three legacy checks hit missing data-model concepts, not missing time:

1. **`target.template.weapon is None`** — no per-template "weapon" concept exists anywhere in the
   Rust entity model for NPCs. `weapon_visual`/`bandolier_items` on `CellEntity` are explicitly
   player-only (per their own doc comments); nothing identifies "this NPC's weapon" as a queryable
   fact.
2. **The six `ABILITY_TYPE_{Undefined,Buff,Debuff,Heal,DOT,DD}` bucket counts** (legacy's actual
   check is just "count == 0 for DD", but that requires the full per-ability type field to exist).
   `AbilityDef` (`crates/entity/src/abilities/defs.rs`) has no type/category field; `AbilityManager`
   tracks only known ability *ids*. There is no ability-type taxonomy anywhere in the codebase to
   map legacy's 6 buckets onto.

This is one of P02's own named stop conditions ("the ability-type enum for `.combatinfo`'s DD-check
doesn't exist in a form you can map legacy's 6 buckets onto"), confirmed by reading `abilities/
defs.rs`/`manager.rs` in full rather than assumed. Per the packet's own guidance, I did not invent
a taxonomy or a "weapon" field to force parity — both would be new data-model design work with
game-design implications (what counts as a "damaging" ability? does every NPC template need a
weapon reference field, or is it derived from equipped items?) outside a read-only query packet's
scope. Options for the coordinator:

- **(a)** Accept `.combatinfo` as scoped-down v1 (2 of 3 checks, both fully real) and file a
  separate design item for the ability-type taxonomy / NPC-weapon-reference question — likely as
  its own `G`-group given the cross-cutting implications for other combat systems that might also
  want ability categorization (not just this one dot command).
- **(b)** Block `.combatinfo` specifically, leaving `.info`/`.facing` to integrate now, until that
  design item resolves. (I did NOT do this — I judged a real, functional, honestly-scoped
  `.combatinfo` more useful than blocking, per D06's "stubs are not parity" cutting both ways: an
  unregistered `.combatinfo` is also not parity.)

## Other gaps (smaller, not stop-condition-worthy — see worknote for full detail)

- `.info`'s `Flags`/`Interaction` lines print raw hex, not decoded flag names (no `EEntityFlags`/

## Regression proof

**`.info` selection-wins-over-explicit-id precedence** (`query.rs::info`'s `target_id.or_else(...)`
temporarily inverted to `args-first().or(target_id)`, i.e. the explicit-id-wins bug):
`legacy_p02_info_selection_wins_over_explicit_id` failed, reporting the *other* entity's data
(`" ----- ENTITY template 99 (100001) ----- "`, `"Template: 99"` — the explicit-arg entity, not the
selected one). Restored; passes again. Full `legacy_p02_` suite re-verified green after restoring
(19/19).

The other two commands' tests were written against the implementation as built (no separate
before/after revert was run for every individual check) — `.facing`'s bucket tests each pin an
exact class label reachable only through the correct bearing/bucket math (e.g. swapping the
`CAS_FRONT_FACING`/`CAS_REAR_FACING` window or the close-distance branch order would flip which
test passes), and `.combatinfo`'s silent-success test would fail immediately if either implemented
check were removed or if a naive "always summarize" implementation had been written instead
(exactly the failure mode the packet's acceptance criteria called out as easy to get backwards).

**(Fix-up round) `.facing`'s caller-yaw coverage gap**: with `facing_angle`'s `caller_yaw` line
temporarily hardcoded to `0.0` (simulating "the caller's own facing direction is silently
ignored"), `legacy_p02_facing_uses_callers_own_yaw_not_just_bearing` failed —
`"(Flank)"` reported instead of the expected `"(Front)"` — while all 7 other `.facing` tests
(including the pre-existing 5 bucket tests) stayed green, exactly matching the reviewer's
independent finding. Restored; full 19-test `legacy_p02_` suite green again.

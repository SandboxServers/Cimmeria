## Behaviour implemented

### `.spawn <templateId>` (new)

`Target::None`, arity 1/1 — matching legacy's
`Command('spawn', ..., 1, None)`. Ported from
`deprecated/python/cell/commands/Resource.py:108-124` (`spawnEntity`), read
directly.

Flow: parse `templateId` → reject non-positive cell-side → resolve the
caller's space / world / **exact position** / **exact facing** → reject a
non-finite placement → enqueue `CellToBaseMsg::GmSpawnNpc` → **silence**.

Three deliberate deviations from the legacy body, all D02 corrections:

1. **No optimistic success line.** Legacy printed
   `'Spawning entity of type <%s>'` *before* `space.createEntity` ran, so a
   creation that never happened still read as a success. `.spawn` reuses the
   existing `gmSpawnByCmd` round-trip's already-correct contract instead: the
   enqueue is silent, the base sends `spawn failed: template <n> not found`
   when the catalog lookup misses, and the cell sends
   `spawned npc <id> (template <n>)` only after
   `spawn_npc_from_record_in_space` returns `Ok`. This is the same standing
   pattern as P05's `GrantCash`/`GrantXP` fix, except the truthful machinery
   already existed here and only needed to be *not* undermined.
2. **Caller heading is actually carried.** Legacy passes `player.rotation`;
   the Rust round-trip hardcoded `SpawnRecord { heading: 0.0 }`. Fixed by
   adding `heading` to `GmSpawnNpc` (Integration request below).
   `spawn_npc_from_record_into` already turns `record.heading` into
   `direction = (0, heading, 0)`, so the spawned entity faces the way the GM
   was facing.
3. **No autosave.** Legacy chained `saveSpawn(player, target)` on the GM's
   `autosaveSpawns` flag — and passed the *stale selected target* rather than
   the entity it had just created. Excluded per the packet contract; that is
   P11's work, and P11 should not copy the stale-target bug.

Validation: `templateId <= 0` is refused cell-side before the round-trip
(`spawn: templateId must be a positive template id (got N).`) — the same gate
the native `handle_spawn_by_cmd` applies. A *well-formed but unknown* template
id is refused by the base's catalog lookup, which is where the catalog lives.

### `.despawn` (new)

`Target::Mob`, arity 0/0. Ported from `Resource.py:155-162` (`despawnEntity` =
`Atrea.destroyCellEntity(target.entityId)`).

Calls the new `SpaceManager::despawn_npc`, which:

1. Refuses a player (`is_player || space.players.contains(&id)`) →
   `DespawnOutcome::RefusedPlayer`, nothing mutated.
2. Collects the observers — players in the space, other than the target, whose
   `witnesses` set contains it (O(players), same scan
   `disconnect_entity` uses; NPCs never receive `LeftAoI`).
3. Sends one `CellToBaseMsg::LeftAoI { witness_id, entity_id }` per observer,
   counting only the sends that actually succeeded.
4. Scrubs the target out of every entity's witness set.
5. `destroy_entity`.

Returns `DespawnOutcome::Despawned { witnesses_notified }` / `NotFound` /
`RefusedPlayer`; the console handler turns each into its own truthful line.

**Why not plain `destroy_entity`:** it removes the entity from
`space.entities` and the spatial grid but leaves it in every observer's
`witnesses` set. The next AoI tick's "in previous but not in current" arm
*would* emit `LeftAoI` — so the removal is not silently lost — but only up to
a tick later, only for players that tick actually visits (the
`space.players.is_empty()` guard skips a whole space, and an observer who
leaves in between never gets it), and never as an assertable count the handler
can report. Fanning out immediately makes the acceptance criterion a fact
rather than a timing accident. Scrubbing in the same pass means the next tick
finds nothing to diff, so there is no duplicate `LeftAoI`.

**Security boundary — NPC-only, enforced twice.** The legacy registration was
`SGWSpawnableEntity`, and the legacy hierarchy is
`SGWPlayer(SGWBeing(SGWSpawnableEntity))` — so legacy `.despawn` on a selected
*player* would have destroyed their cell entity. The Rust `Target::Spawnable`
carries the same "any entity in the world" semantics, so porting the target
type literally would have shipped the hole. Corrected to `Target::Mob`, **and**
the primitive refuses a player independently so a future registry edit cannot
reopen it. Revert 3 below demonstrates the layering: with the spec loosened
back to `Target::Spawnable`, the player entity still survived.

**No spawnlist mutation.** `.despawn` never calls `seed::record`, the sole
emitter of `CellToBaseMsg::ExecuteAuthoringSql`. Guarded explicitly on an NPC
that has a `spawn_id`, so a future packet that chains `.delspawn`'s DELETE
into `.despawn` trips the test.

### Side effects on already-registered commands

- **`.spawnrandom`** now sends the caller's heading too (legacy
  `spawnRandomEntity` also passes `player.rotation`, and P12's ledger
  acceptance line asks for "caller heading"), and gains a feedback line on the
  "caller entity not found" path that previously returned silently. Both via
  the shared `caller_placement` helper. Flagged for P12's owner.
- **Native `gmSpawnByCmd`** is behaviourally unchanged — it passes
  `heading: 0.0` because its wire signature
  (`WSTRING DesignId, FLOAT XOffset, FLOAT ZOffset`) has no rotation argument
  to forward. Pinned by an assertion so it stays deliberate.
- **The round-trip's outcome wording** changed from `gmSpawnByCmd: …` to
  command-neutral (`spawned npc <id> (template <n>)`,
  `spawn failed: template <n> not found`, `spawn failed for template <n>`),
  because three different GM commands now ride it and naming one of them
  misreports which command the GM typed. No test asserted the old prefix
  (checked before changing).

## Known gaps / exclusions

- **Autosave on successful `.spawn` is not wired** (P11). `.autosavespawn`
  still only toggles the preference. P11 should consume it against the
  *newly created* entity id, which is only known in the cell's
  `GmSpawnNpcReady` handler — not the stale selected target legacy used.
- **An unknown-but-well-formed template id** is refused by the base, not the
  cell, so the GM's failure line arrives via `send_gm_feedback_to_client`
  (direct transport) rather than the cell's `send_gm_feedback`. Same client,
  different path. The existing live-DB `gm_spawn_missing_template_sends_nothing`
  guards the no-reply half; the feedback half is not separately asserted (it
  would need a `TestTransport` with a populated `entity_to_addr`, which that
  test deliberately leaves empty).
- **`.delspawn` still uses plain `destroy_entity`** and therefore still relies
  on the next AoI tick for witness removal. Deliberately not changed —
  `console/spawn/authoring.rs` is P09/P10's ownership. **Recommend P10 switch
  it to `despawn_npc`**, which would also fix `.delspawn`'s current
  destroy-even-on-DB-failure behaviour that its own ledger row already flags.
- **`.respawnall`** was moved (not modified) by the file split; it still emits
  no AoI refresh after moving NPCs back to spawn positions. G01's problem.
- **In-client UAT: Pending user session** (M2 World Authoring milestone —
  "Spawn, save twice, move/save, delete persistence while entity survives,
  despawn separately, … visibility off/on and observer re-entry"). Not run in
  this session.

## Hypothesis / evidence (from the audit + a fresh read of current source)

1. **`.info` gap** — confirmed absent. Native `gm::query::handle_show_player` is the closest
   analogue but has **opposite precedence**: it treats a nonzero explicit `TargetID` arg as
   overriding the current selection, while legacy `entityInfo` and this packet's contract require
   selection to win, falling back to the explicit id only when there's no selection. Did not touch
   `handle_show_player` (other callers depend on its existing behavior) — implemented `.info`'s own
   precedence directly in `query.rs::info`.
2. **`.facing` gap** — confirmed absent, and confirmed **not** a pure wrapper as the ledger
   speculated. The actual geometry lives in `SGWSpawnableEntity.facing`/`facingType`
   (`deprecated/python/cell/SGWSpawnableEntity.py:304-352`), not in `Entity.py` alone. No existing
   Rust helper computes this bearing-angle-relative-to-caller-facing + 5-bucket classification;
   `gm::query::handle_show_rotation` computes a different thing (absolute heading from a direction
   vector, not bearing-to-target relative to the caller's own facing). Implemented as new geometry
   functions (`facing_angle`/`facing_class`) in `query.rs`, ported directly from the legacy source
   with the exact `CAS_*` constants from `Constants.py`.
3. **`.combatinfo` gap** — confirmed absent, and confirmed **partially blocked** by missing data-
   model concepts (see "Deferred / gaps" below): two of legacy's three checks (`target.template.
   weapon is None`, and the six `ABILITY_TYPE_*` bucket counts) have no equivalent field anywhere
   in the current Rust entity/ability model. This matches one of the packet's named stop
   conditions verbatim.
4. **`CellEntity` field coverage for `.info`** — checked every legacy `entityInfo` field against
   `entity_struct.rs`:
   - Present and used: `entity_flags` (u64, raw hex — no `EEntityFlags` name table exists),
     `interaction_type_flags` (i64, raw hex — no `EInteractionNotificationType` name table exists),
     `event_set_id`, `name_id`, `template_id` (id only — the cell has no template *name* cache,
     confirmed by this same module's own doc comment re: `.searchtemplate`'s base round-trip),
     `tag`, `static_mesh`, `body_set`, `archetype_id`, `alignment`, `faction`, `level`.
   - Absent entirely: primary/secondary/skin-tint **colors** — `CellEntity` carries no tint fields
     at all (character appearance/tint lives base-side). Omitted per the packet's explicit
     allowance to label unavailable fields rather than invent placeholder values.

## Design decisions

- **`.facing` geometry ported verbatim from `SGWSpawnableEntity.py`**, not re-derived: bearing
  `atan2(dx, dz)` relative to the caller's own facing (`caller_dir.x.atan2(caller_dir.z)`,
  normalized to `[0, 2π)`), then bucketed by the same close-distance/steep-ratio/front-rear-window
  checks using the exact legacy constants (`CAS_CLOSE_DISTANCE=5`, `CAS_ENTITY_HEIGHT=2.5`,
  `CAS_ABOVE_TAN=1.732`, `CAS_FRONT_FACING=CAS_REAR_FACING=π/4`). `CAS_FRONT_FACING`/
  `CAS_REAR_FACING` are expressed via `std::f32::consts::FRAC_PI_4` rather than retyping legacy's
  `0.78539816` literal — clippy's `excessive_precision`/`approx_constant` lints flagged the literal
  as an approximation of the same stdlib constant, and using it directly is equivalent and safer.
- **Faction/alignment/archetype naming — three different judgment calls, not one rule:**
  - **Alignment**: reused the same 3-entry `undefined`/`praxis`/`sgu` lowercase table `.alignment`
    already established in `console/entity.rs::set_alignment` (P13) — legacy's `ALIGNMENT_*` order,
    scoped to the values this codebase actually uses.
  - **Faction**: did **not** port legacy's full 34-entry `FACTION_*` table. This codebase's
    `faction: u8` field already uses a different, simplified numbering (documented at
    `entity_struct.rs:154` and `cell/messages/data.rs:27`: `0=neutral, 1=Tau'ri, 3=SGC,
    10=hostile`) — legacy's `FACTION_SGC = 2` would be plain wrong under this scheme (`3` means
    SGC here). Naming raw ids from the incompatible legacy table would misrepresent data, so
    `faction_name` only names the 4 values this engine's scheme documents; everything else prints
    `"unknown"` alongside the raw id.
  - **Archetype**: ported legacy's `ARCHETYPE_*` table directly (`Any`..`Jaffa`, 9 entries,
    `deprecated/python/Atrea/enums.py:218-226`) — a small, closed, stable table with no evidence of
    a divergent in-repo scheme (nothing else in the codebase assigns archetype ids), unlike
    faction's confirmed divergence.
- **`.info`'s "Could not find entity" fallback-id resolution is scoped to the caller's space**,
  matching every other console command's cross-space rejection convention (`dispatch.rs::
  resolve_target`, `gm::query::handle_show_player`'s "target is in a different space" case) —
  legacy's `Atrea.findEntity` is a CellApp-wide lookup with no such scoping, but allowing a GM to
  fish for entity data in unrelated spaces via id guessing would be a real (if minor) information
  disclosure regression versus the rest of this console family's existing convention. Treated as
  D02 "correct legacy bugs" territory rather than an unapproved scope change.
- **`tests.rs` → `tests/mod.rs` + `tests/p02.rs` split.** Adding the P02 regression suite directly
  to `tests.rs` would have pushed it from 561 to 953 lines — past the 700-line hard cap. Converting
  `tests.rs` into `tests/mod.rs` (unchanged content, same module path) plus a new `tests/p02.rs`
  sibling keeps `crates/services/src/cell/console/mod.rs`'s existing `#[cfg(test)] mod tests;`
  declaration byte-for-byte unchanged — `mod tests;` resolves to either `tests.rs` or
  `tests/mod.rs` with no external difference, so this needed **zero edits to any file outside my
  owned-paths list**. `tests/p02.rs` reaches back into `tests/mod.rs`'s private `setup`/
  `decode_feedback` fixtures via `super::` (both already private-not-pub — a child module can see
  a private ancestor item without a visibility change). Final sizes: `tests/mod.rs` 568 lines,
  `tests/p02.rs` 410 lines — both comfortably under cap.

## Deferred / gaps (explicitly not done — see Handoff for coordinator disposition)

- **`.combatinfo`'s "no weapon" check** (`elif target.template.weapon is None`) — **not
  implemented**. No per-template "weapon" concept exists anywhere in the Rust entity model for
  NPCs (`weapon_visual`/`bandolier_items` are explicitly player-only per their own doc comments;
  `spawner/abilities.rs` has a weapon+event→ability override cache but nothing that identifies "an
  NPC's weapon" as a queryable fact). Adding one would be new data-model design work, not a
  read-only query packet.
- **`.combatinfo`'s ability-type bucket counts / "no damaging abilities" check** — **not
  implemented**. `AbilityDef` (`crates/entity/src/abilities/defs.rs`) has no type/category field at
  all; `AbilityManager` tracks only known ability *ids* (`HashSet<i32>`), with ability metadata
  (cooldown/range/effects) looked up by id elsewhere. There is no `ABILITY_TYPE_{Undefined,Buff,
  Debuff,Heal,DOT,DD}`-equivalent concept anywhere in the codebase to bucket on. This is one of
  P02's own named stop conditions, confirmed rather than assumed.
- **Both gaps together mean `.combatinfo` only implements 2 of legacy's 3 diagnostic checks**
  (no-template, no-ability-set). It is still a genuinely functional, non-stub command — a target
  with a template and a nonempty ability set now correctly produces zero feedback (verified by
  `legacy_p02_combatinfo_healthy_target_is_silent`), matching legacy's "silent on success"
  contract for the checks that do run.
- **`.info`'s `Flags`/`Interaction` lines are raw hex, not decoded flag names.** `entity_flags`
  (u64) and `interaction_type_flags` (i64) both exist and are printed when nonzero, but there is no
  Rust `EEntityFlags`/`EInteractionNotificationType` name table anywhere in the codebase (only a
  single named constant, `INT_NormalLoot`, exists for the latter). Decoding ~40+ legacy flag names
  accurately is out of scope for this packet; raw hex is real data, not a placeholder.
- **`.info`'s `Template:` line has no name**, only the id — the cell caches template *ids*, never
  display names (confirmed by this same module's own top doc comment re: search commands needing a
  base round-trip for names). A future packet giving the cell a template-name cache (or routing
  `.info` through a base round-trip like `.searchtemplate`) could close this.
- **`.info`'s Colors line is omitted entirely** — `CellEntity` carries no primary/secondary/skin-
  tint color fields at all (character appearance/tint lives base-side in `world_entry_appearance`).
  Per the packet's explicit instruction, omitted rather than inventing a value.

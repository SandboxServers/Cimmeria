## Hypothesis / evidence (from the coordinator's brief + a fresh read of current source)

1. **The coordinator's diagnosis was exact, confirmed by direct read.**
   `GrantCash`/`GrantXP`'s `entity_id` conflates three roles: DB/player_id
   resolution subject (well, `GrantCash` carries a separate `player_id` field
   already — only `GrantXP` derives it from `entity_id` via
   `connected[addr].active_player_id`), the client wire-push recipient
   (`onCashChanged` / the XP bundle), and — the bug — the `notify_gm`
   feedback recipient (`send_gm_feedback_to_client(entity_id, ...)` in both
   handlers). Confirmed directly in `progression/mod.rs`.
2. **`GrantXP` has NO `player_id` field** — only `GrantCash` does. Base-side,
   `handle_grant_xp` resolves `player_id` from `connected[entity_to_addr[entity_id]].active_player_id`,
   where `entity_id` is the XP *recipient* (the target, for `.givexp`). This
   means the new `.givexp` console handler does NOT need to resolve or send a
   `player_id` — only confirm cell-side that the target actually has one
   (via `space_mgr.get_entity(target).and_then(|e| e.player_id)`), matching
   the acceptance criterion's "reject with clear feedback if the target has
   none." The base-side lookup is a separate, independent check on its own
   connected-session state.
3. **Legacy text confirmed exactly.** Read `Player.py:146-156`
   (`giveCash`) and `:210-219` (`giveExperience`) directly — both grant to
   `target` (the selected entity), feedback via `player.feedback(...)`
   (the caller), with `'Gave %d naquadah to <%s>'` / `'Gave %d exp to <%s>'`.
   No deviation from the coordinator's summary. (This packet doesn't attempt
   to reproduce that exact feedback string — the base's definitive line
   already differs in wording from every other GM-grant feedback line in
   this codebase, e.g. `gmGiveCash: +{amount} naquadah (total {total})`; D02
   asks for exact spelling/arity/defaults/target semantics, not verbatim
   legacy prose, and every existing grant sink in this codebase already
   established its own feedback wording independent of the Python string.)
4. **The exact `GrantCash`/`GrantXP` construction-site enumeration in the
   brief was complete for the ENUM VARIANT construction sites** — grepped
   `GrantCash\s*{`/`GrantXP\s*{` across the whole crate after the rename and
   found nothing beyond the 6 non-test sites the brief named (definitions,
   `progression_dispatch.rs` route + 2 passthrough fns, `progression/mod.rs`
   2 handlers, `gm/give.rs` 2 constructions, `damage_apply/mod.rs` 1,
   `loot.rs` 1) plus the 3 named test files. **One additional site the brief's
   enumeration didn't cover**: `crates/services/src/base/world_entry/methods/
   progression/tests.rs` calls `handle_grant_cash(...)` directly with
   `notify_gm` as a *positional bool argument* (3 call sites) — not an enum
   construction, so the brief's `GrantCash\s*{`-shaped grep wouldn't have
   caught it, but the Rust compiler does (a `bool` no longer coerces to
   `Option<u32>`). This is a necessary consequence of renaming
   `handle_grant_cash`'s own parameter, not scope creep — flagged per the
   stop condition's spirit ("additional construction sites my grep missed")
   even though it's a call site, not a construction site.
5. **`GrantItem`/`RemoveInventoryItem`'s `notify_gm: bool` fields are
   correctly untouched** — confirmed by reading `loot.rs`'s item-grant arm
   (line ~207, `GrantItem { ..., notify_gm: false }`, unchanged) and
   `gm/give.rs`'s `handle_give_item`/`handle_remove_item` (unchanged). Both
   have the identical caller/subject conflation bug, explicitly flagged as
   out-of-scope by the brief for a future P06/etc. packet — see "Flagged
   follow-up" below.
6. **`console/crafting.rs`'s `.learndiscipline`/`.forgetdiscipline` send an
   OPTIMISTIC feedback line immediately** (`send_gm_feedback(caller_id,
   "learndiscipline [...] discipline ... +...", tx)`, right after
   `tx.send(GrantExpertise {...})`, without waiting for the base commit).
   This is NOT the pattern to follow for `.givecash`/`.givexp` — the brief
   and the README's Architecture Guardrails explicitly require "real outcome,
   not an optimistic 'requested' message." The correct precedent is
   `cell_methods/gm/give.rs`'s native `handle_give_xp`/`handle_give_cash`,
   which send zero success-path feedback from the cell (only rejection
   feedback on validation failure) and rely entirely on the base's
   post-commit `gm_feedback_to` line. `console/give.rs` follows that pattern,
   not `crafting.rs`'s.
7. **`registry.rs` was already at 683/700 after P04** — adding the 2 new
   `.givecash`/`.givexp` specs (14 lines) brings it to **698/700, comfortably
   under the hard cap but very close**. Flagged prominently in the handoff:
   P06 (`.giveitem`) and any future packet adding registry entries should
   check this file's line count *first* and may need to split before adding
   more specs.

## Design decisions

- **`gm_feedback_to: Option<u32>` replaces `notify_gm: bool` on `GrantCash`
  and `GrantXP` only**, per the brief's exact scope — `GrantItem`/
  `RemoveInventoryItem`/`GrantExpertise`/`GrantAppliedSciencePoints` are
  untouched. `Some(caller_id)` sends the definitive post-commit feedback
  line to that caller; `None` means no GM feedback at all (mob-kill XP,
  loot-pickup cash).
- **Native `gmGiveXp`/`gmGiveCash` pass `gm_feedback_to: Some(entity_id)`**
  — same entity as the recipient, since those paths grant to the calling
  GM's own inventory. Zero observable behavior change for these two native
  paths (confirmed by the unchanged `gm/tests/give.rs` assertions, just
  restated as `Some(1)` instead of `true`).
- **New console handlers live in `crates/services/src/cell/console/give.rs`**
  (parallels the existing native `cell_methods/gm/give.rs` naming), not
  `query.rs` (read-only) or `crafting.rs` (different family, different
  feedback-timing contract — see hypothesis point 6).
- **No optimistic feedback from the cell side.** `give_cash`/`give_xp` only
  emit feedback on a *rejection* (malformed amount, non-positive amount,
  target with no player_id) — the success path sends the typed grant message
  and returns silently; the base's `gm_feedback_to` line is the only
  caller-visible success signal. This matches the native `gm/give.rs`
  handlers, not `console/crafting.rs`'s optimistic pattern.
- **Target's `player_id` resolved and validated cell-side for BOTH
  commands**, even though `GrantXP` itself doesn't carry a `player_id`
  field (see hypothesis point 2) — this is the console-layer's own guard
  that the selected target is a real player before forwarding the grant,
  independent of what the base-side message shape needs. Matches the
  acceptance criterion "target with no player_id" rejection.
- **`amount > 0` checked before the `i32 -> u64` cast for `.givexp`**,
  matching native `gmGiveXp`'s ordering exactly — prevents a negative `i32`
  wrapping into an absurd unsigned grant.
- **Registry placement**: new `── Player grants ──` section in
  `registry.rs`, placed after "Mission gaps" and before "G. server /
  maintenance" — no existing lettered section fit (`.givecash`/`.givexp`
  aren't search/query, stat dumps, entity authoring, or crafting); mirrors
  the unlettered "Mission gaps" heading precedent already in the file.

## Planned tests (see Handoff for actual results)

Filter prefix `legacy_p05_`. Planned before writing, split across two files
since the caller/target wire-recipient split needs a fully-connected
`ConnectedClientState` fixture that only exists base-side:

**Cell-side (`console/tests/p05.rs`, no DB)**:
- `.givecash`/`.givexp` happy path: exactly one `GrantCash`/`GrantXP` with
  the target's entity/player id, the amount, `gm_feedback_to: Some(caller)`
  — and zero cell-side feedback lines (proves no optimistic message).
- Non-positive amount (`0`, negative) for both: no grant, feedback mentions
  "positive".
- Target with no `player_id` for both: no grant, feedback mentions "player
  id".
- Non-player target for both: rejected by the shared `Target::Player` guard
  before the handler runs (`"expected a player as a target"`).

**Base-side (`progression/tests.rs`, live-DB, the tightest coverage per the
brief's explicit acceptance-criteria emphasis)**:
- `legacy_p05_grant_cash_feedback_goes_to_caller_not_target`: two distinct
  fully-connected sessions (target, caller); asserts exact DB total after
  the grant, `send_count_to(target_addr) == 1` (the `onCashChanged` push),
  `send_count_to(caller_addr) == 1` (the feedback line), and
  `transport.len() == 2` (no other traffic).
- `legacy_p05_grant_xp_feedback_goes_to_caller_not_target`: same shape for
  XP, with `xp_amount` deliberately under `LEVEL_XP[1]` so no level-up fires
  (keeps the bundle a single packet, avoids the Discord/contact-fanout side
  paths). Asserts exact `exp`/`level`/`training_points` after the grant.

## Decisions taken while implementing

### 1. Same-space moves do not go through the transfer primitive

The single design call of this packet. `transfer_player_to_space` validates
`is_player` (D15) *before* it resolves the destination, so routing every move
through it would reject an NPC subject even when the destination turns out to
be the NPC's own space and no transfer is needed at all.

That would be a capability regression against both legacy
(`entity.teleportTo(...)` never cared what kind of entity it was) and P26
(`.gotoxyz` moves NPCs today). D15's restriction is scoped — "for any
cross-space/cross-world transfer" — so the adapter decides first:

```text
dest_space_id == Some(subject's current space)  ->  same-space snap (P26 path)
otherwise                                        ->  transfer_player_to_space
```

The adapter can always answer that question without duplicating P45's
resolution rules, because every call site already knows the exact destination
space: `.goto`/`.summon` get it from P44's `Found.space_id` / the anchor
entity, and `.gotolocation` only names an exact space when the destination
world *is* the subject's current world. `TransferOutcome::SameSpace` is still
matched, and still falls through to the snap — the primitive owns the
authoritative resolution, so its answer is honoured rather than assumed
unreachable.

### 2. `.gotolocation` into the subject's own world keeps their instance

Taken from P45's handoff rather than re-derived. `TransferDestination::in_world`
resolves through `default_space_for_world`, i.e. the *oldest* loaded instance.
A GM standing in instance C of an instanced world who runs `.gotolocation
<that world> x y z` would be pulled into instance A through a full loading
screen just to change coordinates. Naming their current space turns it into
the same-space snap. This is a refinement of D15's rule for the
subject's-own-world case, not a departure from it: D15 governs which instance
a *cross-world* `.gotolocation` lands in, and that is untouched.

Guarded by `legacy_p46_gotolocation_own_instanced_world_keeps_the_current_instance`.

### 3. Error-wording prefixes

Console handlers here conventionally prefix their feedback with the command
name (`gotoxyz: entity not found`). Legacy's own strings are not prefixed.
The split adopted:

- Strings legacy actually emitted — the two name errors, the two success
  lines, `"Unable to find world: %s"` — are sent **verbatim, unprefixed**.
- Everything else (P45 rejection shapes with no legacy equivalent: not a
  player, instance not loaded, enqueue failed; plus the local entity-not-found
  guards) is prefixed `"<cmd>: ..."`, because those are Rust-side diagnostics
  and the GM needs to know which command produced them.

`TransferRejected::describe()` already renders `UnknownWorld` as legacy's
exact sentence, so that arm just forwards it.

### 4. `Ambiguous` wording

P44 flagged this as needing a decision: legacy's `PlayersByName` dict cannot
hold duplicates, so there is no legacy string to copy. Adopted the shape
suggested in `handoffs/p44.md`, with the match count appended:

```text
Multiple players named <Daniel> -- refusing to guess (2 matches)
```

Deliberately *not* collapsed onto either legacy error: reporting a uniqueness
violation as "no such player" hides a real data problem, and the lookup
already logs it at `error` on `player.name_lookup`.

### 5. Float formatting in `.gotolocation`'s success line

Legacy's `%f` renders `10` as `10.000000`. Rust's `{}` renders `10`. Kept
Rust's, so the line reads the same as the `.gotoxyz` line a GM sees next to
it. Sentence structure and field order are legacy's.

### 6. `.summon`'s anchor may be an NPC

`entity = target or player` is only the *destination* for `.summon`; the entity
being moved is always the named player. Rejecting an NPC anchor would be
over-applying D15. Guarded by `legacy_p46_summon_accepts_an_npc_anchor`.

## File split

`travel.rs` reached 508 lines — over the 500-line soft cap, under the 700 hard
cap, with a real seam. Split (via `git mv`, so history follows) into:

- `travel/mod.rs` (261) — module docs, the two shared mechanisms
  (`snap_in_current_space`, `move_subject`), `dispatch`, and `.gotoxyz`, the
  one command that is only ever a same-space snap.
- `travel/named_destination.rs` (282) — the three P46 commands, whose
  destination comes from a name (a player's, or a world's), plus
  `resolve_named_player` and the legacy string constants.

`console/dispatch.rs` was **not** touched: `travel::goto_xyz` and
`travel::dispatch` both still resolve, because both stayed in `travel/mod.rs`.
That was the reason for putting `.gotoxyz` on the mechanism side of the seam
rather than grouping it with `.gotolocation` as "the coordinate commands".

## Regression proof — four controlled reverts

Each applied to the working tree, run, then restored; `travel.rs` restored
from a byte-identical backup (SHA-256 `c16ae650…5233f` before and after) and
its mtime touched so Cargo could not reuse the probe binary.

| # | Reverted | Tests that failed |
|---|---|---|
| 1 | `.goto` passes `None` instead of `Some(dest_space_id)` (re-resolve by world name) | `goto_joins_the_named_players_exact_instance` (`left: Some(65538)`, `right: Some(65539)` — landed in instance A), `goto_picks_the_instance_holding_the_named_player`, `goto_same_space_moves_a_selected_npc` |
| 2 | Same-space pre-check disabled **and** `Ok(SameSpace)` reported as success without moving (the `is_ok()` adapter P45 warned about) | 6 tests across all three commands |
| 3 | `.gotolocation` always uses the default instance | `gotolocation_own_instanced_world_keeps_the_current_instance`, `gotolocation_same_world_moves_a_selected_npc` |
| 4 | `Ambiguous` collapsed into the `NotFound` arm | `goto_ambiguous_name_refuses_to_guess` |

Probe 1's first run exposed a weak test:
`goto_picks_the_instance_holding_the_named_player` originally spawned the
shared instance *first*, which made it the lowest-numbered instance and
therefore also `default_space_for_world`'s answer — so the regression landed
on the right space by coincidence and the test passed. Fixed by spawning two
decoy instances first and asserting `default_space_for_world(INSTANCED) !=
shared`, after which the probe fails it. Recorded because it is exactly the
"happy-path test wearing a guard's clothes" shape TESTING.md warns about, and
it was only visible *because* the negative run was done.

No other packet's work was reverted to demonstrate any of this.

## Open questions / things the coordinator may want to weigh in on

1. **Feedback ordering on a successful cross-world move.** The success line is
   sent after the confirmed enqueue, so it is queued behind `GateTravel` on
   the same channel. When the subject *is* the caller, the base processes
   `GateTravel` (→ `RESET_ENTITIES`, `pending_world_entry`) before the chat
   line, so the GM may be mid-loading-screen when it arrives. Sending it first
   would mean claiming a transfer that had not been accepted yet, which the
   README explicitly forbids. Left as-is; legacy has the same shape.
2. **P44's `InTransition` gap is inherited unchanged.** A player mid-gate-travel
   reports `NotFound` → "Player is not available on this CellApp", where legacy
   said "not on any reachable space". Documented in `handoffs/p44.md` as
   needing a name roster that outlives the entity; P46's mapping is already
   correct for both variants, so that future packet changes only the lookup
   body. `legacy_p46_goto_in_transition_reports_not_reachable` covers the
   variant today via a constructed entity.

## The Euler question — resolved, NOT a blocker

The brief's explicit stop condition was: stop and escalate if full Euler
orientation cannot be represented cleanly. It can. Evidence, in order of
weight:

1. **Rust outbound wire** — `crates/services/src/mercury/aoi/{create,update}.rs`
   pack `pack_angle(direction[1])` as yaw, `[0]` as pitch, `[2]` as roll,
   unconditionally for both players and NPCs. `pack_angle` divides by
   `0.024543693` (= 2*pi/256), so `direction` is **radians**, not a Cartesian
   vector and not pre-packed bytes.
2. **Rust server-authoritative writer** — `cell/service/ticks/npc_movement.rs`
   writes `npc.direction = Vector3::new(0.0, yaw, 0.0)` with
   `yaw = dx.atan2(dz)`, i.e. radians in `.y`.
3. **Legacy agrees, three independent sites** —
   `SGWPlayer.connected` builds `Vector3(0, self.heading, 0)` and assigns it
   to `self.rotation`; `SGWPlayer.save` persists `heading = rot.y`;
   `SGWSpawnableEntity.lookAt` computes a heading and writes only `rot.y`;
   `SGWSpawnableEntity.facing` reads `self.rotation.y` as the entity's own
   facing angle; `commands/Resource.py:176` does `rot = target.rotation.y`.

So legacy `target.rotation = Atrea.Vector3(x, y, z)` maps 1:1 onto
`direction.x/.y/.z` as pitch/yaw/roll. No axis is dropped, no vector math is
involved, and no design sign-off is needed. The `entity_struct.rs` doc
comment still says "unit vector or yaw/pitch/roll encoded" — that ambiguity
is what produced the `atan2` bug class P48 tracks; `placement.rs`'s module
doc now records the settled answer at the point of use.

There *is* a real limitation, but it is a wire-surface one rather than a
representation one, and it does not block the packet: see "What cannot reach
the target's own client" below.

## Hypothesis / evidence

1. **Legacy `location`/`rotation` are the same function twice**
   (`commands/Entity.py:101-134`). Both are
   `if z is not None: target.<field> = Atrea.Vector3(x, y, z)` followed by an
   unconditional readout. The write gate is on `z`, not on all three, so a
   1- or 2-argument invocation silently fell through to the readout and the
   GM saw "here is the position" as if nothing had been asked for. This is
   the bug D02 asks to correct and the ledger's "malformed partial tuple
   causes no mutation / reject cleanly, don't silently pad" criterion.
   Resolution: `parse_triple` accepts only arity 0 or 3 and rejects anything
   else with an explicit line and no readout at all.
2. **`update_entity_position` destroys orientation.** Its signature is
   `(entity_id, position: [f32; 3], direction: [i8; 3], velocity: [f32; 3])`
   and it does `cell_entity.direction = Vector3::new(direction[0] as f32,
   direction[1] as f32, direction[2] as f32)` unconditionally. Every existing
   server-authoritative caller passes `[0, 0, 0]` — `.gotoxyz`, native
   `gmGotoXYZ`/`gmGoto`/`gmSummon`, respawn, ring transport, the content
   executor's transport action. All of them therefore **zero the moved
   entity's facing as a side effect**. `npc_movement.rs` is the one caller
   that already works around it, by re-writing `direction` through
   `get_entity_mut` immediately after the call. `.location` follows that
   precedent: capture `direction` before the call, restore it after. Legacy
   `location` assigned `target.position` and nothing else, so preserving
   facing is the faithful behaviour, not an embellishment.
   This is the packet's primary regression guard
   (`legacy_p18_location_set_preserves_orientation`).
3. **A `direction` write needs no explicit fan-out.** `space_manager/aoi.rs`
   emits `CellToBaseMsg::EntityMoved { position, direction, velocity, .. }`
   for *every* entity in a witness's current AoI on *every* tick — the
   emission is not gated on a position delta. So a rotation-only change
   reaches witnesses on the next tick with zero extra work from the handler.
   Proven by `legacy_p18_rotation_broadcast_to_witness` rather than assumed.
4. **`note_authorized_teleport` belongs only on the position path.** The
   movement validator's `move_clock`/`check_kinematics` only ever score
   *position* deltas against client movement packets. Turning in place moves
   nothing, so `.rotation` deliberately does not reseed the clock — calling
   it there would be a meaningless side effect on an unrelated subsystem.
   `.location` does call it, unconditionally for player and NPC targets,
   exactly matching `.gotoxyz`/`handle_summon`'s precedent.
5. **`Target::Spawnable`, arity 0-3, was the right plumbing choice** — no
   adjustment needed. `resolve_target` (dispatch.rs:128-161) requires a live
   selection in the caller's space for any non-`Target::None` spec, which is
   exactly legacy's `Command(..., 'SGWSpawnableEntity')` contract (no
   caller fallback, unlike `.gotoxyz`'s `entity = target or player`). And
   `Target::Spawnable::matches` returns `true` for everything, so a player
   target is accepted — correct, since legacy `SGWPlayer` derives from
   `SGWBeing` derives from `SGWSpawnableEntity`. `registry/commands.rs` and
   `dispatch.rs` were left untouched.

## What cannot reach the target's own client

`compose_forced_position_body` (`mercury/aoi/update.rs:110-128`) writes
`BASEMSG_FORCED_POSITION` as entity id, space id, `vehicleID = 0`, position,
previous position — **no angles at all**. There is therefore no wire
mechanism to snap a player's own camera yaw, and `.rotation` on a player
target is server-side plus witness-visible only; the target's next
`avatarUpdateExplicit` overwrites it. That matches legacy exactly (legacy
`rotation` wrote `target.rotation` and pushed nothing to any client), and
the realistic use of the command — posing an NPC — works fully. Recorded in
`placement.rs`'s module doc and asserted by
`legacy_p18_rotation_does_not_move_or_snap_player_target`.

`.location` has no such gap: a player target gets the normal `TeleportPlayer`
snap, identical to `.gotoxyz`.

## Design decisions

- **Shared `parse_triple` + a three-variant `Triple` enum**
  (`Report` / `Set([f32; 3])` / `Rejected`) rather than duplicating the
  arity logic in both handlers or returning `Option<Option<[f32; 3]>>`. The
  no-mutation guarantee then lives in exactly one place, which is also what
  the negative run pins.
- **Re-read the entity for the readout instead of echoing the requested
  tuple.** A set is followed by re-fetching `position`/`direction` from the
  space manager and reporting *that*. If a write is ever silently dropped
  (entity vanished between the gate and the write, a future validator
  rejection), the GM sees a stale readout rather than a confirmation of
  something that did not happen. Legacy had the same property for the same
  reason — it reported `target.position` after the assignment, not `(x,y,z)`.
- **Feedback text keeps legacy's sentence shape** (`Position of entity {id}
  is: (...)`) at `{:.3}` precision instead of Python's `%f`, and `.rotation`
  additionally names the axes and appends the yaw in degrees
  (`(pitch p, yaw y, roll r) rad; heading N deg`). The axis labels are a
  deliberate addition: `direction`'s semantics were ambiguous enough in this
  codebase to produce a shipped bug class, so the readout states them. Same
  D02 latitude P05/P26 used for feedback wording.
- **No `TeleportPlayer` on the rotation path, no `note_authorized_teleport`
  on it either** — see hypothesis points 3 and 4.
- **Feedback addressed to `caller_id` throughout** (D03), never the subject
  entity; asserted by
  `legacy_p18_caller_placement_unchanged_when_acting_on_selection` and by
  the exact-vector feedback assertions naming the target's id in the body of
  a line delivered to the caller.
- **`placement.rs` stayed a flat file** (300 lines after implementation,
  under the 500-line soft cap) — no directory promotion.

## Planned vs. actual tests

`crates/services/src/cell/console/tests/p18.rs`. 13 `#[tokio::test]`s, all
unit/command-level per TESTING.md's picker — no live-DB (neither command

base-side handler, same as `.gotoxyz`, and is not newly introduced here), no
wire-format test (no serializer changed; `EntityMoved`/`TeleportPlayer`

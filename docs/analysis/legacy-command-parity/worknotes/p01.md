## Hypothesis / evidence (from the audit + a fresh read of current source)

1. **`.help` gap** — confirmed. `query.rs::help`/`help_specs` only printed `name: summary`,
   sorted/substring-filtered. It had no per-argument detail view and no zero-match line matching
   legacy wording. `registry.rs::Spec` had no per-argument metadata field.
2. **`.searchitem`/`.searchmission`/`.searchtemplate` gap** — confirmed.
   `base/console_authoring.rs::handle_console_search` bound the raw query as
   `format!("%{query}%")` into an `ILIKE $1` pattern with no escaping, so `%`, `_`, `\` in a GM's
   search text acted as SQL wildcards/escape-introducers instead of literal characters (differs
   from legacy's plain Python substring search). `LIMIT 25` was silent — no way to tell "exactly
   25 hits" from "more than 25, truncated".
3. **Two-token join** (`query.rs::search`'s `args.join(" ")`) already matches legacy's
   `name.lower() + (' ' + name2.lower() if name2 else '')` shape — verified by reading, no code
   change needed.
4. **GM gate** — already enforced upstream in `chat.rs::handle_chat_message` (channel ==
   `CHAN_SAY` && text starts with `.` && `console::is_gm(access_level)`), independent of this
   packet's commands. Existing `chat.rs::tests::non_gm_dot_text_is_normal_chat` and
   `console::tests::is_gm_threshold` already cover it; not reimplemented.

## Design decisions

- **Where the per-argument metadata lives:** `README.md`/`work-packets.md` suggested a sibling
  `registry_help.rs` file (or similar) to avoid bloating `registry.rs`'s `COMMANDS` array literal
  and to keep `registry.rs` under the 700-line hard cap. I scoped the verified `ArgSpec` table down
  to only the 4 commands this packet's read set actually covers (`help`, `searchitem`,
  `searchmission`, `searchtemplate` — see "Deferred / gaps" below), which added ~50 lines to
  `registry.rs` (586 → 636). That's well under the 700-line hard cap, so I kept it inline in
  `registry.rs` rather than creating a new file — a new file would have required adding a `mod`
  declaration to `crates/services/src/cell/console/mod.rs`, which is **not** in my owned-paths
  list (only `registry.rs` was granted for this serialized window, not `mod.rs`). If a later
  packet's `ArgSpec` additions push `registry.rs` close to the cap, splitting into a sibling file
  at that point is the right call (and that packet will need `mod.rs` access, or a coordinator
  integration request).
- **Legacy `index <= argsMin` off-by-one (D02 "correct legacy bugs"):** `ConsoleCommands.py::help`
  determines required-vs-optional via `index <= cmd.argsMin`, which mis-marks a command's last
  optional argument as required whenever `argsMin` equals that argument's index (e.g. `.help`'s
  own single optional `command` arg: `argsMin = 0`, `index = 0`, `0 <= 0` → wrongly "required").
  Implemented the intended `index < min` semantics instead (`spec.min` already carries the exact
  legacy `argsMin` value for every registered command), per D02's "restore... correct legacy bugs
  rather than reproducing them." Regression-proved by reverting to `<=` — see Handoff.
- **Zero-match line:** restored legacy's exact wording, `"No command found with that name"`
  (`ConsoleCommands.py::help`), replacing the prior Rust-only `"help: no command matched."`. Kept
  as a bare string (no `"help: "` prefix) since that's what the legacy source emits, and it's
  explicitly called out in the P01 acceptance criteria as needing review.
- **Search escaping:** added `escape_ilike_pattern` (escapes `%`, `_`, `\` with a leading `\`) and
  an `ESCAPE '\'` clause on all three search SQL statements, so a GM's literal text always matches
  literally under `ILIKE`, matching legacy's plain Python substring search.
- **Search truncation:** split `handle_console_search` into a pure-ish `run_console_search(pool,
  kind, query) -> Result<(&'static str, Vec<(i32,String)>, bool truncated), sqlx::Error>` and a
  thin feedback-sending wrapper. `run_console_search` fetches `SEARCH_LIMIT + 1` (26) rows and
  truncates to 25 if 26 came back, returning whether truncation occurred — this lets the GM tell
  "exactly 25 hits" from "more than 25, refine your search" without a second `COUNT(*)`
  round-trip. This split also makes the escaping/truncation logic directly unit- and live-DB-
  testable without needing a full transport/`ConnectedClientState` fixture (the existing
  `db-test-revert-verification` pattern in my agent memory).

## Deferred / gaps (explicitly not done — see Handoff for coordinator disposition)

- **Per-argument metadata for the other ~59 registered commands** is NOT populated.
  `arg_specs(name)` returns `&[]` for every command outside `help`/`searchitem`/`searchmission`/
  `searchtemplate`, so `.help`'s `<= 3`-match detail view silently omits argument rows for those
  commands (it still prints their one-line summary correctly). Building accurate legacy-sourced
  per-arg names/types/descriptions for the rest requires reading their owning legacy family files
  (`Entity.py`, `Net.py`, `Player.py`, `Mission.py`, `Crafting.py`), which are outside this
  packet's assigned read set and outside P01's command scope (D01 audit boundary). This is
  explicitly one of the ledger's listed P01 stop conditions ("the legacy per-argument help
  semantics for `argsMin` are ambiguous against actual `Command.args` shapes you can't resolve
  from the Python alone") — rather than stopping the whole packet, I scoped the `<= 3` detail
  mechanism down to what I could verify, and left the rest as a documented, non-fabricated gap.
  Each future packet that restores a given command's real behavior should add that command's
  `ArgSpec` row to `registry.rs` (or a split-out `registry_help.rs` if the table grows past a
  clean size) at the same time, reading that command's own legacy docstring for the arg
  name/type/description.
- **`.help`'s legacy access-level filter** (`cmd.accessLevel <= player.accessLevel`) intentionally
  NOT restored — D02 explicitly keeps the current Rust GM threshold rather than reintroducing
  legacy access levels 0/1.
- **GM denial for the P01 commands** — not independently retested; already covered by the
  existing channel-level gate tests (`chat.rs::tests::non_gm_dot_text_is_normal_chat`,
  `console::tests::is_gm_threshold`), and the P01 commands don't add any new authorization path.
- **Search SQL-error feedback path** (`handle_console_search`'s `Err(e) =>` arm) — structurally
  unchanged by this packet (still reports `"{label}: query failed ({e})"`), but not independently
  exercised by a new regression test: forcing a live SQL error safely (without corrupting the
  shared local Postgres) wasn't attempted. The other two "no results" outcomes ARE covered: the
  "empty result set" half (`legacy_p01_search_no_matches_returns_empty_untruncated`) and, per
  review feedback, the "no live DB pool configured" half
  (`legacy_p01_search_no_live_db_reports_exact_feedback` — decrypts the real
  `send_gm_feedback_to_client` wire packet via `TestTransport` +
  `test_default_connected_client_state` and asserts the exact
  `"searchitem: no live DB connection"` text; no live DB needed since `db_pool: &None`
  short-circuits before any query).

## Log

### 2026-09-17 — discovery: the stat had no server-side consumer

Exhaustive grep of `MOVEMENT_SPEED_MOD` / `ROTATION_SPEED_MOD` /
`movementSpeedMod` / `rotationSpeedMod` across `crates/` and `entities/`
returned only:

| Site | Kind |
|---|---|
| `crates/entity/src/stats/stat_ids.rs:15,93` | the constants (6, 81) |
| `crates/entity/src/stats/stat_ids.rs:128,136` | membership in `PUBLIC_STATS` |
| `crates/entity/src/stats/stat_list.rs:41,119` | defaults `(min 0, cur 100, max 500)` |
| `crates/services/src/mercury/aoi/create.rs:322` | the initial NPC stat payload |
| `crates/services/src/cell/console/stats.rs:54,55` | the read-only `.speedstats` dump |
| `entities/defs/alias.xml:199,244` | canonical: "multiplies movement/rotation speed by curr/100" |

Plus tests. **No read site applies either stat to anything.**
`cell/service/ticks/npc_movement.rs` steps NPCs by the `CellEntity.move_speed`
*field*, never by the stat. So a faithful port of legacy `setSpeed` — set
both `cur`, send `onStatUpdate` — would have had zero server-side effect,
making the packet's "deterministic movement effect, a real tick-level
movement assertion, not just the stat value" acceptance criterion literally
unsatisfiable within the originally-assigned owned paths.

### 2026-09-17 — scope escalation, raised and approved

Raised to the coordinator before writing any code, with the finding above and
a proposed minimal fix. **Approved** the same round: scale
`npc_movement_tick`'s per-tick step by `movementSpeedMod.cur / 100`, taking
ownership of `crates/services/src/cell/service/ticks/npc_movement.rs`
(no other in-flight packet touches it — P18 owns `placement.rs`, P46 owns
`travel.rs`). Rationale recorded by the coordinator: it is a real gap, not
scope creep; it is a no-op at the default `cur = 100` so the four existing
`npc_movement` tests keep their exact expected positions; and it matches
`alias.xml`'s canonical semantics rather than inventing a server-only knob.

`ROTATION_SPEED_MOD` was *not* given a server-side consumer — the NPC tick
snaps yaw instantly (`yaw = dx.atan2(dz)`, applied whole in one tick) and
has no turn-rate integration to scale. Building one would be a new movement
feature, not a parity port. The stat is still set and published (the client
applies it), and the gap is recorded in the handoff.

### 2026-09-17 — design decisions

1. **Reject out-of-range instead of clamping.** Legacy leans on
   `Stat.setCurrent`'s silent clamp into `[min, max]`, so `.speed 9000`
   quietly became 500 and `.speed -5` quietly 0 *while the feedback still
   echoed the value the GM typed*. D02 says correct legacy bugs rather than
   reproduce them, and the native `gmSetHealth` handler already sets the
   reject-don't-clamp precedent (`"amount must be >= 0"`). Both stats are
   validated against their own live `[min, max]` **before** either is
   written, which also makes the two-stat write atomic — a GM can never end
   up with movement clamped one way and rotation another should the two
   stats' ranges ever diverge.
2. **Integer feedback.** Legacy's format string is `'Set speed of entity %d
   to %f'`; Python renders an int stat through `%f` as `100.000000`. The
   prose is preserved verbatim; the bogus float rendering is not. Same call
   P05/P26 made on feedback wording (D02 pins spelling/arity/defaults/target
   semantics, not verbatim legacy prose).
3. **`SPEED_STATS` is a separate const, not `stat_set("speedstats")`.** The
   `speedstats` readout group also carries `speedReload`/`speedGrenade`/
   `speedDeploy`/`speedAttack`, which `.speed` must not touch. Sharing the
   table would have silently widened the setter the next time someone edited
   the readout.
4. **Player vs. NPC serialization split** copied from `gm/stats.rs`:
   `serialize_dirty()` for a player target (full set to the owning HUD),
   `serialize_dirty_public()` for an NPC (public subset to AoI witnesses),
   then `clear_dirty()`, then `abilities::send_entity_method` to route.
   Both speed ids are in `PUBLIC_STATS`, so the NPC branch does carry them —
   verified by a dedicated witness-fanout test rather than assumed.
5. **Exact-`f32` test fixture.** The tick tests put the NPC at the origin
   with one waypoint 80 units down +X and `move_speed = 5.0`, so every step
   ratio (`t = speed / 80`) is an exact binary fraction (0.0625, 0.03125,
   0.125, 0.25) and position assertions can use exact equality instead of an
   epsilon compare that could mask a small scaling error.

### 2026-09-17 — test placement

The tick-level assertions live in `npc_movement.rs`'s own `#[cfg(test)] mod
tests` (same `legacy_p47_` filter prefix), not in
`console/tests/p47.rs`. `npc_movement_tick` is
`pub(in crate::cell::service)` behind `mod service;` (private in
`cell/mod.rs`) and `mod npc_movement;` (private in `ticks/mod.rs`) — reaching
it from the console test tree would mean widening three `mod` declarations in
files this packet does not own, for a test. `cargo test --lib legacy_p47_`
runs both halves as one suite.

### 2026-09-17 — environment note

The worktree was provisioned without the `external/` tree (not in git,
populated by `setup.ps1`), so the first `cargo check` failed in
`cimmeria-entity`'s Recast/Detour `cc` build with
`C1083: Cannot open source file '../../external/recast/...'`. Fixed by
junction-linking `external/` from the main checkout into the worktree. This
is a worktree-provisioning gap, not a code problem — worth adding to the
coordinator's worktree setup step for future packets.

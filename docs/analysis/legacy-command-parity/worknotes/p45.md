## Tracing `handle_gate_travel` — what the packet brief assumed vs what is there

The brief said "reuse `handle_gate_travel` directly; a `None` ring call
should work". That is true as far as it goes, but the brief's mental model —
that `handle_gate_travel` is the transfer — is wrong, and the packet's whole
risk sits in the gap.

### 1. `handle_gate_travel` is the *back half*. It never tears anything down

Its own doc comment says it: *"The CellService has already removed the entity
from its old space."* The destructive step is `space_mgr.destroy_entity`, and
it lives in the **cell**, in each caller:

| Caller | Ordering before this packet |
|---|---|
| `cell/gate_travel.rs::handle_dial_gate` (stargate) | `destroy_entity` **then** `let _ = tx.send(GateTravel)` — unchecked |
| `cell/cell_methods/gm/travel.rs::handle_goto_location` (native `gmGotoLocation`) | `send(GateTravel)` checked, **then** `destroy_entity` |
| `cell/content/executor/transport.rs` (chain teleport) | `destroy_entity` then checked send |
| `cell/ring_transport/dispatch.rs` | `destroy_entity` then checked send |
| `cell/cell_methods/player/combat/respawn.rs` | `destroy_entity` then unchecked send |

So "validate the destination before tearing down the entity's current
space/AoI state" is **not something `handle_gate_travel` can do at all** — by
the time it runs, the teardown already happened. It has to be done cell-side,
which is why P45 is a new cell module rather than a thin base-side wrapper.

`handle_goto_location` already got the ordering right and is the precedent
the new primitive follows. It does **not** validate the world, though —
its doc comment explicitly says *"an unknown world is the base side's
concern"*, and the base side has no way to refuse once the entity is gone
(see §3).

### 2. `handle_gate_travel` cannot express "join *that* instance"

The only destination input is `world_name`, which the cell resolves through
`SpaceManager::find_or_create_space`. For an **instanced** world that
function *always allocates a brand new space*:

> *Instanced: always create a fresh space — do NOT cache in world_spaces*

So `.goto <player>` could never have joined the target's instance through the
existing message shape. It would have created a third, empty private copy of
the map. This is the packet's acceptance criterion "the destination instance
ID is *exact*", and it required a new field on two messages:
`CellToBaseMsg::GateTravel.destination_space_id` →
`BaseToCellMsg::CreateEntity.destination_space_id` →
`SpaceManager::create_entity_in_space`.

### 3. `resolve_space_id_fallback` is not a "default loaded instance" mechanism

D15 approved reusing `resolve_space_id_fallback` as the first/default
loaded-instance selector. **Read it: it is not one.** It is a hardcoded
three-entry table (`Castle_CellBlock`/`SGC_W1`/`CombatSim`) whose catch-all
arm warns and returns `DEFAULT_SPACE_ID` — i.e. Castle_CellBlock. Routing
`.gotolocation`'s instance selection through it would send a GM to
Castle_CellBlock for every world outside those three, while telling the
client a space id nothing is in.

The sibling `space_registry::register_space` writes a `world_name → space_id`
map that **nothing ever reads** (confirmed by grep: one writer in
`cell_dispatch/aoi_dispatch.rs`, no readers outside its own test). So the
base has no live world→space index at all.

What the base *does* have is the `CreateEntity` oneshot: the cell resolves and
replies with the real space id. The authoritative default-instance knowledge
lives in the cell's `SpaceManager`. So D15's intent is implemented as a new
`SpaceManager::default_space_for_world` (startup space, else lowest-numbered
loaded instance), resolved cell-side before teardown — not via
`resolve_space_id_fallback`, which is left untouched as the degraded
last-resort path it already was.

### 4. Disconnect-mid-transfer recovery — mostly there, one real hole

The brief's working assumption was that the existing flow covers it. Traced
stage by stage:

| Stage | Disconnect behavior found |
|---|---|
| Cell validated, nothing torn down | Normal `DisconnectEntity` teardown. **Covered.** |
| Cell enqueued `GateTravel` and destroyed the entity; base hasn't run yet | `destroy_client_entities` removes `entity_to_addr` **before** queuing `DisconnectEntity`, so `handle_gate_travel`'s first statement (the addr lookup) `Err`s out and never sends `CreateEntity`. **Covered** — and now pinned by a test, because it was covered by accident of statement order, not by design. |
| Base read the addr, sent `CreateEntity`, awaiting the oneshot | **NOT covered.** `CreateEntity` and `DisconnectEntity` share one FIFO `BaseToCellMsg` channel. If the disconnect's `DisconnectEntity` is enqueued first, the cell processes it against an entity that is already gone (no-op), and *then* processes our `CreateEntity` — resurrecting a clientless ghost entity in the destination space that nothing will ever reap. |
| `RESET_ENTITIES` sent, `pending_world_entry` stored, awaiting `ENABLE_ENTITIES` | `destroy_client_entities` → `DisconnectEntity` reaps the destination entity. **Covered.** |

Stage 3 is fixed here by re-checking `entity_to_addr`/`connected` right after
the create round-trip and sending `DestroyEntity` if the session is gone.
That is not "new disconnect-recovery state" (the packet's exclusion) — it
reuses the existing `DestroyEntity` teardown; it just stops using it
*after* we already know the client left.

### 5. A pre-existing partial-teardown bug the packet's ordering criterion names

`handle_gate_travel` had **two** fail-closed `active_player_id` guards (one
guarding the persist UPDATE, one guarding the character reload), and both sat
*after* the `CreateEntity` round-trip. Hitting either meant: the cell entity
has moved worlds, the client never got `RESET_ENTITIES`, no
`pending_world_entry` — a desynced player with no way back. Hoisted to a
single check before `CreateEntity`.

**Corrected after review — the hoist is lateral on failure shape, not a
strict improvement.** The old ordering aborted with the entity in the
*destination* space (present but desynced). The new ordering aborts with the
entity in *no* space, because the cell tore it out before we were called.
Both need a relog and neither corrupts the DB, so hoisting is still right —
there is no reason to cross the point of no return when we already know the
transfer must fail — but "strictly safer" was wrong, and the new shape is
exactly what acceptance criterion 3 forbids.

So the abort now **ends the session** (`abandon_unspaced_session`): it
cancels the tick-sync loop, drops the session and its reverse mapping, and
tells the cell to disconnect the entity, so a reconnect rebuilds the player
from the DB. That is the only recovery available at this seam — the base is
never told the *origin* space id, only the destination, so it cannot put the
entity back. It deliberately is not `destroy_client_entities` (that needs the
`EntityManager`, which the cell-dispatch chain does not carry); the cost is a
leaked base-side entity id on a branch that is unreachable in practice.

## Design decisions

1. **The primitive lives in the cell** (`cell/space_transfer/`), not the
   base. The teardown is cell-side, so validation must be too. Cell-side
   also owns the only live world/space tables (see §3).
2. **`handle_gate_travel` was modified, not duplicated** — one new parameter,
   one hoisted guard, one disconnect reap. No parallel teardown/re-entry
   path was built. The coordinator's stated preference.
3. **Players only (D15)**, checked on `CellEntity::is_player`. An NPC target
   returns `TransferRejected::NotAPlayer` with nothing torn down.
4. **`SameSpace` is an `Ok` outcome, not an error.** If the destination
   resolves to the subject's current space, a full `RESET_ENTITIES` reload
   would be a gratuitous loading screen. The primitive reports it and tears
   down nothing, so P46 can finish with P26's cheap authoritative snap.
   This also means `.goto <player in my own instance>` is a `.gotoxyz`, for
   free.
5. **Rejection is typed, not stringly.** `TransferRejected` has a variant per
   failure shape plus a `describe()` for default wording, so P46 can map
   `UnknownWorld` to legacy's exact `"Unable to find world: %s"` (already the
   `describe()` text) and keep the others distinguishable — the same
   "distinguishable failure shapes" contract P44 was given.
6. **Exact instance is re-validated cell-side on arrival**, and a stale id
   *degrades* to by-world-name resolution rather than failing the create.
   Instanced spaces die when their last player leaves, and that can happen
   while `GateTravel` is in flight. Landing in the wrong instance of the
   right world is recoverable; landing in no space is not.
7. **`default_space_for_world` picks the lowest space id**, not an arbitrary
   `HashMap` entry. Space ids are allocated monotonically, so lowest ==
   oldest live instance, and the destination is deterministic across runs.
8. **Non-finite coordinates are rejected in the primitive too**, even though
   P46 will parse through `console::parse_f32` (which already rejects them).
   Defence in depth on a destructive, GM-triggered path; matches the native
   `gmGotoLocation` finite check.
9. **Bandolier-ammo flush stays before teardown**, as in `handle_dial_gate` —
   but after validation. It is a persistence write, not a state change: if
   the subsequent enqueue fails, what was persisted still matches the live
   entity.

### 6. Two hazards only the reviews surfaced

Both are cases where `destroy_entity` is not the whole teardown.

**Entity ids are recycled.** `EntityManager::allocate_id` pops a free list
before advancing its counter, and `destroy_client_entities` frees the id on
the way out. So while `handle_gate_travel` is blocked on the create oneshot,
a *second* client can legitimately be handed the same entity id and register
it against their own address. The first cut of the disconnect reap treated
"mapped to a different addr" the same as "unmapped" and would have sent
`DestroyEntity` for the new owner's live entity — the exact false positive
the reap was supposed to be safer than. Now only genuine unmapped /
closed-session reaps; a remap to another address logs at `error` and bails.

**`destroy_entity` does not clean trade state.** That is why both lifecycle
arms call `cancel_trade_on_disconnect` explicitly, and the helper
early-returns as soon as `get_entity` misses — so it *cannot* be called after
the teardown. Without it, `.summon`-ing a player mid-trade leaves their
partner holding a `trade_partner_entity_id` pointing at a freed id, with no
`onTradeResults(Cancelled)`: a stranded session only a relog clears. The
transfer now cancels the trade between the confirmed enqueue and the
teardown, so the "a rejection changes nothing" contract still holds. The same
omission existed in `handle_dial_gate` (stargate travel) and is fixed there
too.

## Adjacent fixes made in the same pass

Both are the same bug class as the packet's own acceptance criterion
("failure must not leave a half-torn-down entity"), in files this packet
already had to touch:

- `cell/gate_travel.rs::handle_dial_gate` destroyed the entity **before** an
  unchecked `let _ = tx.send(GateTravel)`. A closed base channel left the
  player in no space with no transfer in flight — relog-only recovery.
  Reordered to checked-send-then-destroy, matching `gmGotoLocation`.
- `handle_gate_travel`'s duplicated late `active_player_id` guards (§5).

## Known gap, not fixed here

`BaseToCellMsg::CreateEntity.reply_tx` is a `oneshot::Sender<u32>` with no
failure channel. When the cell's create fails it drops the sender, and the
base falls back to `resolve_space_id_fallback` — building a world-entry
packet for a space the entity is not in. The new primitive validates the
world and the destination instance before teardown specifically so that arm
stays unreachable for GM transfer, and the error log now says what happens.
Widening the oneshot to `Result<u32, String>` (4 call sites) is the real fix
and belongs to the gate-travel owner, not to this packet's blast radius.

## Hypothesis / evidence (from the coordinator's brief + a fresh read of current source)

1. **`.players`'s bug is exactly as scoped.** `SpaceManager::all_player_entity_ids`
   (`space_manager/queries.rs:105-111`) already walks `self.spaces.values()` — every loaded space,
   not just the caller's. The pre-existing `query::players` called it and then filtered the result
   down to `space_mgr.get_entity_space_id(pid) == Some(caller_space_id)`, which is the bug: it
   turned an already-CellApp-wide query back into a per-space one. It also printed
   `"{pid} (char {c})"` / bare `pid` instead of a name, and never reported the entity's world.
   Confirmed by direct read, not re-derived from the brief.
2. **`get_entity_world_name` already existed** (`space_manager/queries.rs:49-53`) — resolves an
   entity id to its space's `world_name: String` in one call, exactly what `.players`'s
   `"(<world>)"` needs. No new `SpaceManager` API required.
3. **No cell-side "in transition" registry exists**, confirmed by grep across
   `crates/services/src/cell/` for `in.transition|InTransition|ConnectedClientState|
   connected_players|pending_players` — the only hits are doc-comment references to
   `ConnectedClientState`, which is explicitly base-side (`messages/base_to_cell.rs`'s own comment:
   values are "sourced from"/cached from base, not a queryable cell-side registry). A player only
   ever appears in `all_player_entity_ids()` once `connect_entity` has placed them in a space's
   `players` set, so every id this function resolves already has a world today. Per the packet's
   own scope line ("split if online indexing needs new lifecycle state") and the coordinator's
   explicit instruction not to invent a fake in-transition mechanism, this is documented as
   unreachable rather than implemented — not a stop condition, since `.players` still covers every
   real GM use (every online player who has completed world entry).
4. **`listAbilities` (`Player.py:222-234`) is a flat, unfiltered dump** — confirmed by reading the
   function body directly (not re-derived from the brief's summary): `for abilityId in
   target.abilities.abilities: ability = DefMgr.get('ability', abilityId); feedback(name or
   "<unknown ability %d>")`. No grouping, no category filter, no type bucketing — the brief's
   summary was accurate. Header line is `"Ability list of entity %d:"` (`%d` = `target.entityId`).
5. **The ability catalog is already loaded cell-side with no DB round-trip in the hot path.**
   `SpaceManager::ability_defs: HashMap<i32, AbilityDef>` (`space_manager/mod.rs:136`) is populated
   at startup (`service/startup.rs:169-171`, `spawner::load_ability_defs`) and read via
   `.get(&id)` elsewhere (`abilities/dispatch.rs:88`). `AbilityDef.name: String`
   (`entity/src/abilities/defs.rs:104`) is the exact field `.listabilities` needs — confirmed the
   struct does **not** derive `Default` (checked the `#[derive(...)]` line directly above the
   struct), so ability-def test fixtures in `dispatch.rs` construct every field explicitly; matched
   that pattern in this packet's own test fixture rather than assuming a `Default` shortcut.
6. **The native `gm::query::handle_list_abilities` is a distinct, deliberately-numeric sibling**,
   not a candidate for reuse: it prints raw ability ids
   (`abilities [{subject}] ({count}): {ids...}`), no name resolution at all, and falls back to the
   caller when no target is selected (`subject_or_self`). `.listabilities`'s legacy contract
   requires name resolution and a required `Target::Player` (no fallback) — different enough that
   sharing code would blur two genuinely different contracts, so `.listabilities` is a new,
   independent `query::list_abilities` function.
7. **`spawn_npc` grants a default ability (592, `NPC_DEFAULT_ABILITY`/Pistol Shot) to every NPC it
   creates** (confirmed via `space_manager/tests/npc_spawn.rs:115-116` and
   `space_manager/mod.rs:153-156`'s doc comment). This meant `tests/mod.rs::setup()`'s NPC target
   (built via `spawn_npc`) was unsuitable for an exact-list `.listabilities` fixture — it always
   carries one extra, unrelated known ability. Built a small `bare_player` test helper
   (`create_entity` + `connect_entity`, no `spawn_npc`) instead, so the ability-list assertions stay
   exact and don't couple to an unrelated NPC-spawn default.

## Design decisions

- **`.players` keeps its existing `Spec` entry** (`Target::None`, `0`/`0`) — only the help text
  changed (`"List players in your space"` → `"List players online on this CellApp service"`) to
  match the corrected scope. No registration/arity change.
- **`.listabilities` registered as `Target::Player`** (no fallback, per the audit row and
  `Player.py`'s signature), arity `0`/`0`, placed immediately after `.players` in `registry.rs`'s
  "D. search / query" section (paired with `.players` in this packet, both roster-adjacent reads).
- **Deterministic ordering via explicit sort, not insertion order.** Legacy iterated Python
  collections (`PlayersByName.values()`, `target.abilities.abilities`) in unspecified order — the
  ledger's acceptance criteria explicitly require deterministic output, so both `.players` (sorted
  by entity id) and `.listabilities` (sorted by ability id) sort before formatting. This is a
  legacy-bug correction (D02: correct legacy bugs rather than reproducing them), not a deviation
  from the *displayed content*.
- **`.players`'s empty-loop behavior matches legacy exactly**: legacy always sends the header line
  then loops (zero rows if nobody's online) — no synthetic "none online" message was added, unlike
  the pre-existing Rust implementation's `"players: none in your space."` line, which this packet
  removed as part of restoring the exact legacy contract.
- **Unknown-ability fallback text**: `"    <unknown ability {id}>"`, matching legacy's
  `"    <unknown ability %d>"` (Python `%d` maps directly to Rust's `{id}` for an `i32`).
- **`.players`'s "In transition" branch is retained in code but effectively dead** (see hypothesis
  point 3) — `get_entity_world_name(pid).unwrap_or_else(|| "In transition".to_string())` is
  present so the *header→row* pairing and per-row format exactly matches legacy's shape even in the
  theoretical case, without inventing new lifecycle tracking to make it reachable. Documented
  in-code and here rather than silently dropped, so a future in-transition-tracking packet has an
  obvious splice point.

## Planned tests (see Handoff for actual results)

Filter prefix `legacy_p04_`. Planned before writing:

- `.listabilities`: known id resolves to its real name; unknown id retains the fallback line
  (not silently dropped); both together in one fixture pinning sort order; a target with zero
  known abilities gets the header line and no rows; a non-player target is rejected by the shared
  `Target::Player` guard before the handler runs.
- `.players`: two loaded spaces, one player each, both appear with the correct world — the exact
  regression this packet fixes; a player with no cached `character_name` falls back to a stable
  `"player {id}"` label; caller-only recipient and non-mutation check.

Did not add a redundant "typed command requires target" test for `.listabilities` beyond the
dedicated rejection test above — `cell::console::tests::mod::typed_command_requires_target`
already exercises this rejection path generically using `.primarystats`, matching P02/P03's
precedent of not duplicating existing framework coverage; the dedicated `.listabilities` test adds
value because it also pins the exact rejection wording (`"expected a player as a target"`) for
this specific target type, which the generic test doesn't check per-type.

Test lane: `cargo check -p cimmeria-services`, `cargo test -p cimmeria-services --lib legacy_p04_
-- --test-threads=1`. No live-DB tests — `ability_defs` is an in-memory startup cache, `.players`
reads only in-memory `SpaceManager` state; neither touches the DB in the hot path.

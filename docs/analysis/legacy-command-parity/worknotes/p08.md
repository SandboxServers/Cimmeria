## Legacy source — verbatim behaviour

`deprecated/python/cell/commands/Resource.py:108-124`:

```python
def spawnEntity(player, target, templateId):
    template = DefMgr.get('template', templateId)
    if template is None:
        player.feedback('Cannot spawn entity: invalid templateId %d' % templateId)
        return

    player.feedback('Spawning entity of type <%s>' % template.templateName)
    player.space.createEntity(template, player.position, player.rotation)
    if player.autosaveSpawns:
        saveSpawn(player, target)
```

`deprecated/python/cell/commands/Resource.py:155-162`:

```python
def despawnEntity(player, target):
    player.feedback('Despawning entity <%s>' % target.getName())
    Atrea.destroyCellEntity(target.entityId)
```

Registrations (`ConsoleCommands.py:329,331`):

```python
Command('spawn',   cell.commands.Resource.spawnEntity,   1, None),
Command('despawn', cell.commands.Resource.despawnEntity, 1, 'SGWSpawnableEntity'),
```

So: `.spawn` takes exactly one arg and needs no target; `.despawn` takes none
and requires a selected `SGWSpawnableEntity`.

## Hypothesis / evidence

1. **The round-trip the audit points at already exists and is already
   truthful — the gap is heading, not plumbing.** `.spawn`'s audit row says
   "reuse GmSpawnNpc roundtrip with catalog validation, caller placement/
   heading and actual creation result". Reading all three halves of the
   round-trip confirmed the *creation-result* half is already correct: the cell
   enqueues silently (`cell_methods/gm/spawn.rs:158-161` — "Feedback is
   deferred to the round-trip: a premature 'requested' line could report
   success for a template that doesn't exist"), the base sends the definitive
   not-found line, and the cell sends the definitive "spawned npc `<id>`" line
   only after `spawn_npc_from_record_in_space` returns `Ok`. P08 therefore
   *reuses* that contract rather than re-deriving it, and the one genuine gap
   is that `CellToBaseMsg::GmSpawnNpc` carries no heading:
   `base/gm_spawn.rs` hardcoded `SpawnRecord { heading: 0.0, .. }` with the
   comment "heading = 0 match the 'drop it here facing forward' semantics".
   Legacy passes `player.rotation`, and "exact position/heading" is a named
   acceptance criterion, so the field had to be added. See Design decision 1.

2. **Legacy `spawnEntity`'s feedback lies about success, twice over.** Its
   `'Spawning entity of type <%s>'` line is printed *before*
   `space.createEntity` runs, so a creation that throws or drops still reads as
   a success to the GM. This is exactly the standing pattern the brief flagged
   (P05's `GrantCash`/`GrantXP`). Corrected by simply not porting that line —
   `.spawn` enqueues silently and inherits the round-trip's real outcome
   lines. Guarded by
   `legacy_p08_spawn_emits_exact_request_and_no_optimistic_feedback`.

3. **`destroy_entity` alone does *not* satisfy the witness-removal acceptance
   criterion, but the deficit is subtler than "no LeftAoI at all".**
   `SpaceManager::destroy_entity` removes the entity from `space.entities` and
   from the spatial grid, but leaves it in every observer's `witnesses` set. On
   the *next* AoI tick, `compute_player_aoi`'s "in previous but not in current"
   arm does emit `LeftAoI` for it (confirmed by reading
   `space_manager/aoi.rs:198-213`) — so the removal is not silently lost. But
   it is (a) deferred by up to a full tick, (b) only delivered to players the
   tick actually visits (the `space.players.is_empty()` guard skips a whole
   space, and an observer who leaves the space in between never gets it), and
   (c) not an assertable *result* — the handler cannot tell the GM how many
   observers were notified. `disconnect_entity` already solves exactly this
   shape for a leaving player (fan the `LeftAoI` out immediately, then scrub
   the witness sets), so `despawn_npc` reuses that shape. Because the witness
   sets are scrubbed in the same pass, the next tick's diff finds nothing and
   does not duplicate the `LeftAoI` — guarded by
   `legacy_p08_despawn_scrubs_witness_sets_so_the_next_tick_is_quiet`.

4. **Legacy `.despawn` could destroy a logged-in player, and the Rust
   `Target::Spawnable` would reproduce that bug exactly.** The legacy
   registration's target class is `SGWSpawnableEntity`; the class headers in
   `deprecated/python/cell/` give
   `SGWPlayer(SGWBeing)` → `SGWBeing(SGWSpawnableEntity)`, so a selected player
   satisfies `isinstance(target, SGWSpawnableEntity)` and
   `Atrea.destroyCellEntity(target.entityId)` would run against them. The Rust
   `Target::Spawnable` carries the same semantics — its own doc comment says
   "in practice any entity in the world" and `Target::matches` returns `true`
   unconditionally for it. So porting the legacy target type literally would
   have shipped the hole. Corrected to `Target::Mob` (`!is_player`) per D02.
5. **…and the registry gate alone is not enough.** The brief asked for the
   NPC-only boundary to be structural, not documentary. A registry `Target` is
   one table edit away from regressing and is invisible to any future caller
   that reaches the primitive directly, so `SpaceManager::despawn_npc` refuses
   a player on its own (`entity.is_player || space.players.contains(&id)`) and
   returns a `#[must_use]` `DespawnOutcome::RefusedPlayer`. The revert
   experiment for the registry gate (Log, revert 3) demonstrates the layering
   working: with the spec loosened back to `Target::Spawnable`, the player
   entity still survived — only the *wording* of the refusal changed.

6. **`.despawn` needs no persistence work to satisfy "never mutates a
   spawnlist row" — but it does need a guard.** The handler never calls
   `seed::record`, which is the only path to `CellToBaseMsg::ExecuteAuthoringSql`
   (confirmed by grep: `seed.rs:65` is the sole emitter). The guard asserts the
   absence of that message *and* an empty `authoring_changes` buffer for the
   caller, on an NPC that deliberately has a `spawn_id`, so a future packet
   that "helpfully" chains `.delspawn`'s DELETE into `.despawn` trips it.

7. **`spawn/mod.rs` reaches `crate::cell::console::parse_i32` via `super::`
   unchanged after the directory split** — `spawn.rs` → `spawn/mod.rs` keeps
   the same module path, so `super` is still `console`. Only the moved
   `authoring.rs` needed its paths rewritten (`super::parse_bool` →
   `crate::cell::console::parse_bool`, since its `super` is now `spawn`).
   `console/mod.rs`'s `mod spawn;` needed zero changes — same property P26
   documented for the `registry.rs` → `registry/mod.rs` split.

## Design decisions

1. **Add `heading: f32` to `CellToBaseMsg::GmSpawnNpc` rather than inventing a
   cell-side heading fixup.** The alternatives were worse: the cell cannot
   build a `SpawnRecord` (no template cache), and correlating a "pending
   heading" by requester id across the round-trip would be racy under two
   concurrent `.spawn`s. One field on one message, threaded through
   `progression_dispatch` → `base::gm_spawn` → `SpawnRecord.heading`, is the
   whole change. `spawn_npc_from_record_into` already turns `record.heading`
   into `direction = (0, heading, 0)`, so nothing downstream changed.
2. **The native `gmSpawnByCmd` keeps sending `heading: 0.0`.** Its wire
   signature is `(WSTRING DesignId, FLOAT XOffset, FLOAT ZOffset)` — there is
   no rotation argument to forward, so adopting caller-facing there would be a
   behaviour change to a native command outside this packet's contract. Pinned
   by an assertion in the existing
   `gm_spawn_by_cmd_emits_spawn_with_offset_position` test so the choice is
   deliberate rather than accidental.
3. **Command-neutral wording for the round-trip's outcome lines.** The shared
   round-trip previously said `gmSpawnByCmd: spawned npc <id>` /
   `gmSpawnByCmd: template <n> not found`. With `.spawn` and `.spawnrandom`
   both riding it, that prefix actively misreports which command the GM typed,
   so the two lines became `spawned npc <id> (template <n>)` and
   `spawn failed: template <n> not found`. No existing test asserted the
   prefix (checked before changing), and the one test that asserts the success
   line matches on `"spawned npc"` + `"template 4242"`, both preserved.
   Considered and rejected: adding a `SpawnOrigin` enum to the message so each
   command names itself — that puts presentation in the transport layer for no
   data-level distinction, and costs more shared-file churn than it saves.
4. **`Target::Mob`, not `Target::Spawnable`.** See Hypothesis 4. The feedback
   the GM sees on a wrong target is the framework's own
   `expected an NPC as a target`.
5. **`despawn_npc` returns a `#[must_use]` three-variant outcome rather than
   `bool` or `()`.** `NotFound` and `RefusedPlayer` are different things the GM
   needs told apart, and `Despawned { witnesses_notified }` carries the
   *actual* delivered count (incremented per successful `tx.send`, not per
   intended observer) so the feedback line cannot overstate the fan-out on a
   half-closed channel.
6. **Split `console/spawn.rs` into `spawn/mod.rs` + `spawn/authoring.rs`**
   along the persistence seam (ephemeral lifecycle vs. spawnlist writes), not
   an arbitrary line count. Directory form rather than a flat
   `spawn_authoring.rs` sibling because it needs zero edits to
   `console/mod.rs`, matches the repo's `foo/mod.rs` convention, and gives
   P09/P10/P11 an obvious home (`authoring.rs` for P09/P10, `mod.rs` for P11's
   consumer hook). Result: 372 + 160 lines, both well under the soft cap with
   room for the four packets queued behind this one.
7. **`caller_placement` extracted as a shared helper** for `.spawn` and
   `.spawnrandom` — both need the same (space, world, position, heading)
   quadruple, and `.spawnrandom` was silently returning without feedback when
   the caller entity was missing. Side effect, flagged for P12: `.spawnrandom`
   now also sends the caller's heading (which P12's own acceptance line asks
   for) and gains a feedback line on the missing-caller path.
8. **No autosave consumption.** Legacy chains `saveSpawn(player, target)` on
   `player.autosaveSpawns` — and passes the *stale selected target*, not the
   entity it just created, which is the bug P11's ledger row already calls
   out. Out of scope here; `.spawn` is purely ephemeral.

## Tests — type selection (per TESTING.md picker)

- **Unit / command tests** for arg parsing and the target gate — `.spawn`'s
  non-positive and malformed template ids, `.despawn`'s registry refusal.
- **Fan-out assertions on exact `CellToBaseMsg` values** (the cell→base
  analogue of TESTING.md type 8) for the `GmSpawnNpc` request tuple and the
  per-witness `LeftAoI` set. Asserting *which* witness ids received the removal
  is the acceptance criterion; asserting "a LeftAoI was emitted" would not be.
- **Live-DB regression guard** for the heading threading, because that half of
  the fix lives inside a `sqlx::query` → `SpawnRecord` construction that cannot
  be exercised without a DB. Added as an assertion to the existing
  `gm_spawn_resolves_real_template_and_replies` rather than a new test, since
  it is the same query under test.
- **Not** a wire-format test: no new wire shape is introduced. `.spawn` rides
  the existing `GmSpawnNpc` → `GmSpawnNpcReady` → AoI-create path, and
  `.despawn` rides the existing `LeftAoI` path.

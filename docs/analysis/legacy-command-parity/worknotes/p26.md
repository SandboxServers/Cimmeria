## Hypothesis / evidence

1. **The coordinator's mechanism-reuse claim was exact, confirmed by direct
   read.** `handle_summon` in `cell_methods/gm/travel.rs` (lines 335-422) is
   already the player/NPC split precedent: `update_entity_position` +
   `note_authorized_teleport` unconditionally, then `TeleportPlayer` gated on
   `is_player`. `.gotoxyz`'s handler follows the identical shape, just with
   `target.unwrap_or(caller_id)` in place of a required-target lookup.
2. **`TeleportPlayer` genuinely has no GM-feedback field** (confirmed reading
   `cell_to_base.rs` lines ~512-533) — unlike P05's `GrantCash`/`GrantXP`,
   no shared-message-struct change was needed here. The coordinator's brief
   was exactly right that D03 "doesn't need a shared-message-struct change
   this time" — the console handler just sends its own immediate feedback to
   `caller_id` after the send succeeds, exactly mirroring what
   `handle_goto_xyz`/`handle_summon` already do natively for the GM-is-caller
   case.
3. **`forward_to_base` (`cell_methods/gm/mod.rs:329`) is `pub(super)`,
   scoped to `cell_methods` and its descendants — not reachable from
   `cell::console`.** Rather than widen its visibility (a shared-file edit
   outside this packet's owned paths) or duplicate-import across a module
   boundary the coordinator didn't grant, `travel.rs` reimplements the same
   "send, log+return on error" check inline. Behaviorally identical; zero
   shared-file edits.
4. **`MovementValidator::note_authorized_teleport` is safe to call
   unconditionally on any `entity_id`, player or NPC** (confirmed reading
   `crates/entity/src/movement_validation/mod.rs`): `move_clock` is a bare
   `HashMap<u32, Instant>` with no player/NPC distinction, and
   `check_kinematics` (the only consumer) is only ever invoked from the
   client-movement-packet path — NPCs never submit client movement packets,
   so an NPC's `move_clock` entry is simply never read. This isn't a new
   finding — `handle_summon` already calls it unconditionally on
   `target_eid` regardless of `is_player` — so `.gotoxyz` just matches the
   established precedent rather than reinventing a guard.
5. **`update_entity_position` alone is sufficient for witness broadcast —
   no separate refresh step needed, for player OR NPC targets.** Confirmed
   two ways: (a) reading `update_entity_position`'s body
   (`space_manager/entities.rs:371-406`) — it writes `cell_entity.position`
   AND calls `space.space.grid.update_position(...)` in the same function,
   so the spatial index is never stale after the call; (b) the existing
   `summoned_npc_is_broadcast_to_caller_witness` test already proves this
   for `gmSummon`'s NPC case. This packet adds two of its own equivalent
   tests (`legacy_p26_gotoxyz_npc_move_broadcast_to_witness`,
   `legacy_p26_gotoxyz_player_target_move_broadcast_to_witness`) rather than
   assuming the existing proof generalizes to `.gotoxyz`'s own dispatch path
   and to the player case (which `summoned_npc_...` doesn't cover — it's
   NPC-only).
6. **`Target::None`'s existing `resolve_target` semantics (dispatch.rs
   125-158) already implement legacy's `entity = target or player` exactly**
   — a resolved current-target is passed through only if it's in the
   caller's space; otherwise `None`. No cross-space *rejection* exists for
   `Target::None` commands (unlike typed targets) — an out-of-space
   selection silently degrades to "no target," which then falls back to the
   caller. This is pre-existing shared framework behavior (same as `.info`'s
   pattern), not something P26 introduces or should change; confirmed via
   `legacy_p26_gotoxyz_cross_space_selection_falls_back_to_caller`.
7. **Non-finite coordinate rejection is already covered by the shared
   `parse::parse_f32` helper** (`.filter(|v| v.is_finite())`), which every
   other float-taking console command already uses. The native
   `handle_goto_xyz` has its own separate finite check because it parses raw
   bytes, not string args — `.gotoxyz` parses `&[&str]` through the console
   framework's shared parser, so duplicating a second finite check would be
   redundant. Confirmed via `legacy_p26_gotoxyz_rejects_non_finite_coordinates`
   (`"NaN"`/`"inf"`/`"-inf"` string args, all rejected with a message
   containing "finite").
8. **The registry split is a pure data/types separation, not code/tests** —
   different from the `console_authoring.rs` → `mod.rs` + `tests.rs`
   precedent (P01 handoff) cited in the brief, which split runtime code from
   its test module. Here `registry/mod.rs` keeps `Target`/`Spec`/`ArgSpec`
   types + `spec()`/`arg()`/`arg_specs()` logic, and `registry/commands.rs`
   holds only the `pub(crate) static COMMANDS: &[Spec]` array. `commands.rs`
   reaches `spec`/`Spec`/`Target` via `super::` — all three are already
   `pub(crate)` or private-but-parent-visible, so **no visibility widening
   was needed**; Rust's privacy model makes a private item visible to all
   descendant modules of its defining module, and `registry::commands` is a
   descendant of `registry`. `console/mod.rs`'s `mod registry;` declaration
   needed **zero changes** — `registry.rs` → `registry/mod.rs` resolves
   identically, confirmed by a clean `cargo check` with no edits to `mod.rs`
   beyond adding `mod travel;`.

## Design decisions

- **New file `crates/services/src/cell/console/travel.rs`**, not `query.rs`
  (read-only family) — parallels the native `cell_methods/gm/travel.rs`
  naming, matching the brief's suggested precedent (P05's `console/give.rs`
  alongside `cell_methods/gm/give.rs`).
- **`Target::None` with in-handler `target.unwrap_or(caller_id)`** — not
  `Target::Being`/`Target::Spawnable` with a hard-require. This is the one
  console command so far (besides `.info`) where the memory note's "any
  handler behind a typed spec with a `.unwrap_or(caller_id)` fallback has
  dead code" warning does NOT apply: `.gotoxyz` is genuinely `Target::None`,
  so `resolve_target` really can return `Ok(None)`, and the in-handler
  fallback is live code, not dead code.
- **`note_authorized_teleport` called unconditionally** (both player and NPC
  paths), matching `handle_summon`'s existing precedent exactly — see
  hypothesis point 4.
- **No shared-message-struct change.** `TeleportPlayer` already carries
  everything needed (`entity_id`, `space_id`, `position`, `prev_pos`) and has
  no feedback field to conflate — D03 is satisfied by simply addressing
  `send_gm_feedback` to `caller_id` (never `entity`) after the
  cell-authoritative move + (for players) the confirmed `TeleportPlayer`
  send. This is the one place this packet's scope is *narrower* than P05's,
  exactly as the coordinator's brief predicted.
- **The closed-channel "don't claim a snap that never sent" check is
  reimplemented locally** in `travel.rs` rather than reusing
  `cell_methods::gm::forward_to_base`, because that helper is `pub(super)`
  to `cell_methods` and not visible from `console` — see hypothesis point 3.
  Behaviorally identical (log a warn, return without sending feedback).
- **Registry placement:** new `── Travel ──` section in
  `registry/commands.rs`, placed after "Player grants" and before "G. server
  / maintenance" — anticipates G05's `.goto`/`.summon`/`.gotolocation`
  joining this section later (all four are player-administration travel
  commands), rather than reusing P05's unlettered "Mission gaps"-style
  placement precedent for an unrelated family.

## Planned tests (see Handoff for actual results)

Filter prefix `legacy_p26_`, all in
`crates/services/src/cell/console/tests/p26.rs` (no live-DB — position isn't
persisted through this path, see Handoff):

- NPC target happy path: exact position, no `TeleportPlayer`, caller feedback.
- NPC target AoI witness broadcast (spatial-grid consistency proof, not just
  `cell_entity.position` in isolation).
- Player target happy path: exact `TeleportPlayer` tuple (target id, space
  id, destination, pre-move position), caller (not target) feedback.
- Player target AoI witness broadcast (independent of the `TeleportPlayer`
  snap, which only reaches the moved player's own client).
- No-selection fallback to caller (legacy `entity = target or player`).
- Caller unchanged when moving a distinct selection (D03).
- Non-finite coordinate rejection (`NaN`/`inf`/`-inf`), no mutation.
- Malformed (non-numeric) argument rejection, no mutation.
- Cross-space current selection degrades to "no target" (existing
  `Target::None` framework semantics, not new to this packet) → falls back
  to caller.
- Closed base channel for a player target: no panic, cell-side grid write
  survives (position is cell-authoritative the instant
  `update_entity_position` runs).

## Legacy findings

### `PlayersByName` is a flat, case-sensitive dict — confirmed by direct read

The coordinator's pre-dispatch claim held up exactly. Evidence trail:

| Site | Content |
|---|---|
| `cell/Global.py:5` | `PlayersByName = {}` — a bare module-level dict. |
| `cell/SGWPlayer.py:264` | `PlayersByName[self.playerName] = weakref.ref(self)`, at the end of the world-entry method that also fires `onClientMapLoad`. Key is the raw `playerName` string; value is a **weak** reference. |
| `cell/SGWPlayer.py:268` | `def disconnected(self): del PlayersByName[self.playerName]` — the only removal site. |
| `cell/commands/Player.py:307`, `:330` | `if name not in PlayersByName:` — a raw Python dict-key membership test. |

`in` on a `dict[str, ...]` is `__hash__`/`__eq__` on `str`: exact and
case-sensitive. Nothing in `Player.py`, `SGWPlayer.py`, `Global.py` or
`Misc.py` lowercases, strips or normalizes either the key at registration
or the probe at lookup. **Case-sensitive matching is therefore the ported
behavior, not a default-by-omission.** No fuzzy, prefix or ambiguity
handling exists to port — the dict structurally cannot hold two players
under one name, and legacy never had to decide what to do if it did.

Note the `summon` docstring says `@param name: Name or ID of target
player`, but the body only ever does the dict lookup — there is no
numeric-id branch. The docstring is wrong; the code is the spec (D02:
correct legacy bugs rather than reproduce them, and a stale docstring
isn't behavior at all).

### Legacy's two failure shapes

```python
if name not in PlayersByName:
    player.onError("Player is not available on this CellApp")
    return
destination = PlayersByName[name]()
if destination is None or destination.space is None:
    player.onError("Player is not on any reachable space")
    return
```

Two distinct GM errors:

1. **Name absent from the roster** → "not available on this CellApp".
2. **Name present, but the weakref is dead *or* the player has no space**
   → "not on any reachable space". This is the "in transition" shape:
   registered at world entry, deregistered only at `disconnected()`, so a
   player between spaces keeps its key while `.space` is transiently unset
   (or the entity has already been collected).

These have to stay distinguishable in the Rust return type, or P46 cannot
reproduce the two messages. That drove the enum below.

## Design decisions

### 1. Four-variant enum, not `Option<u32>`

```rust
pub enum PlayerNameLookup {
    Found { entity_id: u32, space_id: u32 },
    InTransition { entity_id: u32 },
    NotFound,
    Ambiguous { entity_ids: Vec<u32> },
}
```

- `Found` carries **`space_id`, not just `entity_id`**. P45's acceptance
  criterion is that a transfer lands on the destination player's *exact*
  instance; re-deriving it from the world name would silently pick the
  first/default instance (D15's `.gotolocation` rule) and put the GM in the
  wrong copy of an instanced world. The scan already knows which space it
  matched in, so returning it costs nothing and removes the temptation.
- `NotFound` vs `InTransition` are legacy's two error strings, kept apart.
- `Ambiguous` is the uniqueness defense — see decision 4.

### 2. The discriminator is `space.players` membership, not a flag

`Found` vs `InTransition` is decided by whether the matched entity id is in
its space's `players` set. That is the same predicate the rest of the cell
uses for "is this a live, client-controlled player" (`all_player_entity_ids`
reads exactly that set; `compute_aoi_changes` skips spaces with no entries
in it). It is also literally what `disconnect_entity` clears first, before
`destroy_entity` drops the entity — so the state is produced by real code
paths, not fabricated for the test.

### 3. Match on `character_name` only; do **not** also gate on `is_player`

`CellEntity::character_name` is player-exclusive by construction — NPC
display names live on the separate `npc_name` field, and the only writer of
`character_name` in the whole tree is the `BaseToCellMsg::InitPlayerState`
arm in `cell/service/base_messages/mod.rs:149`. Adding an `is_player`
condition would buy nothing and would actively break the `InTransition`
branch for any teardown/partial-init shape where `is_player` has been
cleared but the name is still cached. A test (`npc_display_names_are_not_matched`)
pins the NPC exclusion so a future NPC-naming feature trips a red test
rather than silently making `.summon` target a mob.

### 4. Duplicate names return `Ambiguous`, they do not resolve

The acceptance criterion asks for a guard proving the lookup doesn't
"silently pick one of several". Returning the first match would be worse
than nondeterministic-looking — it would be *genuinely* nondeterministic,
because the scan walks `HashMap<u32, SpaceInstance>` and
`HashMap<u32, CellEntity>`, whose iteration order is randomized per
process. A `.goto Daniel` would teleport the GM somewhere different on each
invocation with no error. So: collect all matches first, and if there is
more than one, return them (sorted, so the payload itself is deterministic)
plus a `tracing::error!` on target `player.name_lookup` per the
negative-logging convention. The ambiguity check deliberately runs *before*
the in-space/in-transition split — "prefer the one that's actually in a
space" is still an arbitrary resolution of a broken invariant, and it
degrades to arbitrary again the moment both duplicates are bound.

### 5. Placed in `space_manager/queries.rs`, exported from `mod.rs`

The packet's designated entry file, and the natural home: it is a read-only
accessor over the space/entity tables, sitting next to `all_player_entity_ids`
(the enumeration P04's `.players` uses for the same CellApp-wide scope).
File grew 194 → 288 lines, well under the 500-line soft cap, so no split.
`PlayerNameLookup` is re-exported from `space_manager/mod.rs` following the
existing `pub use entities::ClientMoveOutcome;` precedent, so P45/P46 import
it as `crate::cell::space_manager::PlayerNameLookup` and never need to know
which submodule it lives in.

## Gotchas and things the next packet should know

### `InTransition` is correct, but not reachable in production today

This is the honest version of P04's same finding, and P46 must not be
written assuming otherwise.

- The **data model** produces the state: `disconnect_entity` removes the id
  from `space.players`, then awaits the `LeftAoI` fan-out, then calls
  `destroy_entity`. Between those, a named entity exists outside the player
  set.
- But the cell service is a **single task** that holds `&mut SpaceManager`
  across that whole call, so no other handler (including a `.`-console
  command) can observe the window. It is real state, not observable state.
- The other case a GM would actually hit — `.goto Bob` while Bob is
  mid-gate-travel — **does not land here either**, and this is the one
  behavioral divergence from legacy worth recording. `handle_gate_travel`'s
  own header says "The CellService has already removed the entity from its
  old space"; the base then sends `CreateEntity` for the destination world,
  and `create_entity` builds a fresh `CellEntity` whose `character_name` is
  `None` (`cell_entity/construction.rs:39`). The name is re-cached only when
  `InitPlayerState` arrives, which is after `ConnectEntity`. So for the whole
  transfer window **no entity anywhere carries Bob's name**, and this lookup
  returns `NotFound` → P46 will say "not available on this CellApp" where
  legacy (whose dict key survives until `disconnected()`) said "not on any
  reachable space".

Closing that gap needs a name roster that outlives the entity — new
cell-side state, which is outside P44's scope and is exactly the kind of
invented tracking P04 was told not to build. The variant is the splice
point if a later packet ever adds one (the obvious candidates being a
cell-side `HashMap<String, u32>` maintained across destroy/recreate, or
threading base-side `ConnectedClientState` visibility into the cell).

### Why the ordering claim above is trustworthy

`cell/service/base_messages/mod.rs:145-160` already carries an explicit
comment and a `tracing::warn!` for the case where `InitPlayerState` arrives
before the entity exists — i.e. the codebase itself documents
`ConnectEntity` → `InitPlayerState` as the invariant. `handle_create_entity`
(the `CreateEntity` arm) runs earlier still. That's a three-message ordering,
and the name is only present after the third.

### Test-fixture shape

`spawn_named_player(mgr, id, world, name)` in the new test file reproduces
that exact ordering (`create_entity` → `connect_entity` → set
`character_name`). Reuse it in P45/P46 rather than hand-rolling, and note
that the shared `make_manager()` fixture in
`space_manager/tests/mod.rs` gives you `Agnos`/`Castle` as non-instanced
startup spaces and `Castle_CellBlock`/`SGC_W1` as instanced — which is how
the CellApp-wide test proves the scan reaches an on-demand instance the
caller never named.

### Build-lane / environment gotcha (not a code issue)

1. A fresh worktree has no `external/` (gitignored, populated by
   `setup.ps1`), so `cimmeria-entity`'s Recast/Detour `cc` build fails with
   `C1083: Cannot open source file '../../external/recast/...'`. Fixed by
   junction-linking the main checkout's `external/` into the worktree —
   same workaround already recorded for concurrent worktree sessions.
2. Restoring a file from a backup copy during the controlled negative run
   preserves the *backup's* mtime, which is older than the already-built
   artifact, so Cargo decides the crate is unchanged and re-runs the stale
   (stub) test binary. The restore looks like it failed when it hasn't.
   Touch the restored file's `LastWriteTime` before re-running.

## Scope exclusions (deliberate, per the packet)

- No offline / database-backed name lookup, and no cluster-wide routing
  (D05 defers both to a separate approval).
- No fuzzy, prefix or case-insensitive matching.
- No case-insensitive *fallback* either — a near-miss is simply a miss.
- No new roster state to make `InTransition` production-reachable (see
  above); the variant exists so P46 can express the distinction and so the
  gap has a named splice point.
- No console registry / dispatch / command-handler changes of any kind.

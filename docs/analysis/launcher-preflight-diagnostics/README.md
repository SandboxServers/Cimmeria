## Purpose

The owner wants three things from the desktop launcher (macOS and Windows):

1. Every failure says why it failed, in plain language, in the UI and in the log.
2. Before an operation starts, the launcher detects the dependencies it needs, says clearly what is missing, and says what it will do about it: install it, download it, or ask the user. Per owner ruling D1, it installs missing dependencies for the user after saying what it will install.
3. Every common failure gets a clear statement and a suggested fix.

Owner ruling D2 (2026-10-24) adds: the game must not open in exclusive fullscreen; Settings gets a display mode option the launcher applies on every Play; a running game with no visible window is reported as a failure with a fix. Acceptance: in the default mode on macOS, Cmd+Tab away and back works with no freeze or black screen, on one and two displays.

Owner ruling D3 makes the launcher the source of truth for display settings on every launch, with windowed 1024x768 as the default (always on macOS; on Windows too, D-PD21). Owner ruling D4 adds four Mac extras: borderless plus a safe-mode relaunch; a Retina-aware size list and a monitor picker remembered per display setup; a 30/60/display-rate frame cap; cursor lock plus per-launch logs with an "Open logs" button.

## Trigger incident (macOS, 2026-10-23)

1. Rosetta 2 was missing. Play failed at spawn (`launch_not_started reason="spawn_failed"`), and the UI said only "Game could not start".
2. Repair then failed synchronously inside `start_with_backend` (`E/storage/repair/preparation/mod.rs:118-152`), before `events::repair_started`. The host called `mark_uncertain` (`S/host/repair/mod.rs:186`), which left a durable `reconciliation_required` repair operation. No `launcher.repair` event and no reason were logged, so the exact failing check is still unknown.
3. That operation blocked Play with "Another operation owns the game" (`FE/launch-view.ts:24`, through `launch-workflow.ts:29` → `contract.ts:12` `operationOpen`), and the install panel said "Unknown helper outcomes stay blocked".
4. The only way out was Settings → Abandon preparation (`E/storage/repair/abandon/mod.rs:46-134`).

## Owner UAT (runs on a real Mac and a real Windows PC)

- UAT-PD1: Mac without Rosetta. Open the launcher with a stuck repair from the incident build: it is reconciled on open, and Play is not blocked.
- UAT-PD2: Mac without Rosetta, Play (preflight bypassed with a pre-wave-2 build or by removing Rosetta after preflight): the UI names Rosetta, and the log has `failure_code="rosetta_missing"` (and `os_error=86` if D-PD5 = yes).
- UAT-PD3: Mac without Rosetta, Play on a wave-2 build: preflight says Rosetta 2 is missing and that the launcher will install it from Apple with an administrator prompt; the prompt appears; after install the check re-runs and Play proceeds.
- UAT-PD4: Mac, launcher run from `~/Downloads` (translocated): the preflight warns and says to move the app to Applications.
- UAT-PD5: Windows, a nearly full drive: Install refuses before downloading, with the free and needed sizes.
- UAT-PD6: Both, network off: Install says the release service is unreachable and suggests checking the connection; Play still works.
- UAT-PD7 (after PD-22; again after PD-24): Mac, default settings, one display and then two displays (the ultrawide plugged in). Start the game, reach the world, Cmd+Tab away and back three times. Pass: the window stays at a normal layer (no shield window), no display changes mode, no black screen, no freeze, no GPF line. Run it once with a profile whose saved `windowedMode` is `false` to prove PD-22 alone holds.
- UAT-PD8 (probe for PD-27): Mac, `DXVK_FORCE_WINDOWED=1` with saved `windowedMode=false`, with and without `ResX=`/`ResY=` at the display's point size. Record the window size, layer and frame. Pass: a frameless window that covers the display with no mode change.
- UAT-PD9 (after PD-24, PD-25): Windows. With a profile whose game was fullscreen, the first Play after the update opens a 1024x768 window and Settings shows the "New: ... 1024 × 768 window" note. Fullscreen sets `windowedMode=false` and `StartupFullscreen=True` and leaves `resolution` byte for byte; Windowed 1600x900 opens a 1600x900 window and survives an in-game switch to fullscreen at the next Play; a profile folder that doesn't exist yet (fresh Windows account) opens windowed from the launch arguments.
- UAT-PD10 (gates PD-40): Mac with a Retina panel and a 1x display. Set `RetinaMode=y` in the game prefix by hand, start the game on each display: record the client's rendered size, UI scale, mouse accuracy and frame rate. Pass: correct rendering and mouse on the Retina panel; the 1x result decides whether the switch is offered only on 2x setups.
- UAT-PD11 (after PD-33): a Mac with two displays and a Windows PC with two monitors. Pick the second monitor, Play: the window opens centred there; quit, unplug the second display, Play: it opens on the main display; plug it back: the choice comes back. Record whether the game moved its own window after placement.
- UAT-PD12 (PD-38): Mac, windowed. Drag the mouse past the window edge during mouse-look and with any `MouseLock` binding PD-38 names; Cmd+Tab away and back. Record whether the cursor is confined and whether Cmd+Tab releases it.
- UAT-PD13 (after PD-29, PD-36): Windows. Start the game and minimise its window at once for 40 s: the launcher reports the hidden window and offers "Relaunch in a safe window"; the safe relaunch opens windowed 1024x768 on the main display and leaves the saved preference unchanged.

## Parking lot

- Rosetta phase-out after macOS 27 (F17): a native-ARM Wine path or a clear "not supported on this macOS" state is a separate campaign.
- Notarization and Gatekeeper first-open (F11) belong to the release pipeline, not this campaign.
- The level-load render-thread GPF (F25): its cause is a client, Wine, DXVK or MoltenVK question for the graphics workstream; this campaign only makes it visible (PD-28 logs, PD-29/PD-30 detection). Re-check after PD-22 whether it still happens on level loads in windowed mode.
- A "Display mode: every launch" row in the client-changes list (`crates/launcher-core/src/client_changes.rs`, 648 lines, near the hard cap): needs a split of that file first; follow-up after PD-24.
- A Windows frame cap (D-PD20): needs a client patch or a shipped limiter; revisit if Windows players ask.
- An RE pass on the client's D3D mode list so the launcher can write `resolution` for Windows fullscreen (D-PD21).
- An in-game hint that the launcher overrides display options (D3 asks for it "if feasible without a client patch"): no client-side text hook exists without a patch, so it needs a maintainer decision; the launcher note covers it for now.
- Reading an in-game display change back into launcher Settings after the game exits (research-display-client.md § 3, option 3): D-PD16 chose "the launcher owns it" instead; revisit if players ask.

# Security review: launcher session kind (adoption-flow telemetry)

Read-only design review, 2026-10-20. Evidence: `crates/admin-api/src/routes/dev_session/{handlers,token,quota}.rs`, `crates/admin-api/src/routes/telemetry/{upload_gate,chunk,replay_native,field_caps,session_budget,entity_labels,dto}.rs`. Nothing was built or run; every claim about current behaviour below is from reading that code.

## Verdict

**Acceptable with changes.**

The design is sound in shape: a short-lived, no-join, write-only token with a row allow-list is strictly narrower than a player token. But as written it leans on `kind` (a label) to withhold capabilities, it leaves four existing code paths open to launcher rows (cell round trip, lifted attributes, 8 h refresh, 30k-event budget), and its scrub is a deny-list where an allow-list is needed. None of that is hard to fix. Ship after the Required list below.

Is a launcher kind weaker than player? Not in capability: it is narrower on TTL, refresh, bundle, identity join, row types and volume. It shares the one property that matters most: anyone can mint one with no credential, so volume and content are untrusted exactly as for player tokens. With the proposal as written it is weaker than player in these spots (each fixed by a Required item): (a) shares the 120/h per-IP mint table, so launcher spam can lock players out of minting behind a shared egress; (b) the existing field lifting and entity naming would still run on its rows; (c) the existing decompressed-size and session-budget limits are far larger than a 64 KiB / 200-row launcher needs.

## What was checked and is fine

- Only three routes consume a token: `refresh_inner` (handlers.rs:323), `upload-chunk` and `upload-bundle` via `admit` (upload_gate.rs:281). No other `decode_token` / `verify_bearer` caller exists in `crates/`. So cross-kind reach is a closed set to enforce.
- Kill switch is first in `mint_inner` (handlers.rs:241), `refresh_inner` (:331) and `admit` (upload_gate.rs:289), before the token is read.
- `fields` is emitted as one `%fields_json` (serde_json `Value` Display), which escapes `\n`, `\r` and ESC, and cannot forge sibling attributes (replay_native.rs:336).
- `install_id` is restricted to `[A-Za-z0-9_-]{1,128}` (quota.rs:165); metadata fields reject control characters (quota.rs:189).
- Per-IP keying folds IPv6 to /64 and maps IPv4-mapped addresses (quota.rs:132). The IP charge happens before `install_id` validation (handlers.rs:249), so rotating `install_id` buys nothing from one address. quota.rs:25 already says the per-install quota is a speed bump, not a boundary.

## Required changes

Each is one line and testable. "Revert proof" means the test must fail if the change is removed.

1. Launcher tokens carry scope `telemetry.launcher.write`, not `telemetry.write`; `verify_bearer` takes the route and accepts: chunk = either scope, bundle and refresh = `telemetry.write` only; a token whose `kind` and scope disagree is refused. Reason: `kind` is documented as "a label, never a privilege" (token.rs:51); a restriction that depends on every present and future route remembering to check a label is fail-open, a scope fails closed.
2. `upload-bundle` with a launcher token returns 403 (not 401, so the launcher's re-mint-once-on-401 never loops) before any quota counter or slot is charged. Test: bundle call leaves all four `WindowTable`s and the slot pool unchanged.
3. `refresh_inner` refuses a launcher token with 400 before charging `refresh_ip` and before building new claims. Reason: `new_exp = now_unix + TOKEN_TTL_SECONDS` (handlers.rs:387) is 8 h; one accepted refresh would turn a 15 min token into an 8 h one. Test: no code path returns a launcher token with `exp - iat > 900`.
4. Launcher mint sets `exp = iat + 900` (not `TOKEN_TTL_SECONDS`), signs no `acct` and no `mid`, ignores `machine_id` entirely (not signed, not logged at any level, including the debug line at handlers.rs:307), and never calls `record_stream`. Test: decoded claims have `acct == None && mid == None`, and the client-telemetry stream registry is empty after the mint.
5. Mint with `session_kind = "launcher"` and a non-blank `account_name` returns 400 (`BadField`); `kind_claim` accepts `"launcher"`, still rejects any other unknown value, and its error text names all three kinds.
6. Launcher mints are charged to a per-IP launcher counter (own table, default 30/h, env override) in addition to the shared 120/h table, and to their own per-install table (12/h). Test: after 30 launcher mints from one IP, a player mint from that IP still succeeds and a 31st launcher mint is 429.
7. Per-kind upload limits are chosen from the claims in `admit`/`chunk_flow` before the body is read: compressed body 64 KiB (413 past it without buffering past the cap), decompressed cap 256 KiB or less, row bytes 4 KiB or less, rows 200. Reason: today a launcher token would inherit `MAX_CHUNK_DECOMPRESSED_BYTES`, so a 64 KiB gzip bomb inflates to the player cap. Test: a 64 KiB bomb is cut at the launcher decompressed cap (`truncated: true`).
8. Launcher chunk quotas use their own session, install and IP tables, plus one global launcher rows-per-minute ceiling that does not key on any caller-supplied value. Reason: per-IP is the only load-bearing key (quota.rs:25), and a botnet or /64 rotation beats it; the global ceiling bounds SigNoz volume regardless of caller count. Test: N distinct sessions from N distinct IPs saturate the ceiling and the next chunk is 429.
9. The row allow-list runs on the parsed row inside the decode path with the token kind passed in (`decode_chunk` currently takes only `limits`): every variant except `ClientNative` (including `KeyDump`, `SessionMeta`, `ClientLog`, `DebugLog`) is counted into `bad_rows` and dropped before `admit_budgeted`, naming and replay. Test: a launcher chunk holding a `KeyDump` row produces zero tracing events and `bad_rows == 1`.
10. Launcher `target` must be an exact member of a compiled constant list of adoption event names (ASCII `[a-z0-9._]`, at most 64 bytes, starts `client.launcher.`); a prefix-only rule is acceptable only with a hard cap of 32 distinct targets per session. Reason: attacker-chosen target strings become the log body and the `client_target` attribute, so an open prefix is unbounded SigNoz value cardinality. Test: `client.launcher.x1` ... `x1000` do not all replay.
11. Level normalization overwrites `e.level` itself (not only the local `level` match), because `client_level = %e.level` (replay_native.rs:314) records the raw string; for launcher rows `is_priority` ignores level so a `warn` row cannot spend the priority allowance. Test: a launcher row with level `"info\n\u001b[31mx"` emits `client_level == "info"`.
12. `fields` handling for launcher rows is an allow-list, not a deny-list: at most 16 keys, each key `^[a-z][a-z0-9_]{0,31}$`, values only bool, number or ASCII-printable string of at most 128 bytes; arrays and objects are dropped (not flattened); this runs before `cap_event` flattens nested values to JSON text. Reason: after flattening, a path's backslashes are doubled and the "leading `\\`" test no longer sees it; and the proposed deny list (`ip`, `host`, ...) is trivially evaded by `h0st`, `addr_v4`, `server`, `endpoint`, `url`, `cwd`. Test: table of evasion keys.
13. The allow-list in 12 must also exclude every key `LiftedFields::from_fields` reads (`method_index, msg_id, type_id, entity_id, target_id, source_id, pet_id, ability_id, item_type_id, address, level_name, dll_version, usable, rollup_target, count`), and launcher rows skip `name_chunk` entirely. Reason: those keys become first-class attributes, and entity ids make the ingest query the cell (entity_labels.rs:386-431), so a free token could drive game-server round trips. Test: a launcher chunk full of `entity_id` produces zero `EntityLabelsRequest`s and no lifted attributes.
14. PII scrub (server side, on parsed values, keys and values): replace the whole value with `"<removed>"` when it contains an IPv4 or IPv6 literal in any wrapping (`1.2.3.4:80`, `[::1]:80`, `::ffff:1.2.3.4`, `fe80::1%eth0`, inside `http://...`), a drive-letter path with either slash, a UNC or leading-`\` or leading-`/` path, `file:`, `%USERPROFILE%`-style variables, `\Users\` / `/home/` fragments, an `@` (email or userinfo), or `://`. Test: one table covering each form, with the revert proof that removing the pattern fails the row.
15. Launcher rows get their own session event budget (default 300 events per session lifetime) in a ledger separate from the shared 1024-entry `SessionLedger`; the `client_pid` header is ignored; `lab` is false and `cimmeria.session_kind = "launcher"`. Reason: with minted launcher sessions counted in the shared ledger, enough live sids push every later session into `OVERFLOW_SID` and degrade player and lab accounting (session_budget.rs:21-26).
16. Launcher client: on 429 or 503 hold the next mint/upload for `max(60 s, Retry-After)`; re-mint once on 401 only, never on 400, 403, 413 or 429; no retry of a rejected batch. Test (launcher-core, stubbed transport): a 429 with `Retry-After: 600` produces no request for 600 s; a 403 produces no re-mint. Reason: failed mints are still charged to the IP table (handlers.rs:249), and a fixed 60 s hold is 60 charges/h per stuck launcher.

## Recommendations

1. Consent copy: the opt-in is worded "Send game diagnostics while playing" but the launcher will send adoption steps when the player is not playing. Change the label and description to say the launcher's own setup steps are included before this ships; do this regardless of the technical work.
2. Be honest about unlinkability: dropping `acct`, `mid` and `record_stream` removes the server's world-entry join, but every launcher row still carries `install_id` (`sub`), the same id on that install's player-session rows, which can carry `acct`. If real unlinkability is wanted, mint launcher sessions under a per-session pseudonym `sub` (random UUID, no relation to `install_id`) and key the per-install quota on the real one server-side only. Otherwise document that launcher rows are linkable to the install.
3. Give launcher rows their own tracing target / `service.name` (for example `cimmeria-launcher`) instead of `client.native` under `cimmeria-client`. Game-client dashboards, alerts, retention and cardinality budgets then stay unaffected by free, unauthenticated rows. At minimum, audit every query, dashboard and `launcher_summary/rows.rs` consumer that treats "not lab" as "player", since `launcher` is now a third value.
4. Add an operator switch that disables only the launcher kind (for example `CIMMERIA_TELEMETRY_LAUNCHER_DISABLED=1`, mint returns 503 with `Retry-After`) so a launcher flood can be shut off without pausing game telemetry. The existing kill switch stays the master.
5. Reserve a small separate slot pool for launcher uploads (or cap launcher at a fraction of `CHUNK_SLOTS`): a valid token is free, so slow-body holders could otherwise occupy the shared chunk slots that game DLL uploads need. `SLOTS_PER_PEER` only limits per address.
6. Treat the server scrub as the boundary and the client scrub as defence in depth: a malicious client can ignore the client scrub, so only the server allow-list protects the operator. Keep the client scrub because it also stops honest-client leaks from ever leaving the machine.
7. Keep free-text error messages out of launcher events by design: emit an enum-like `error_class` plus numeric codes, never an OS error string (those carry paths and user names). This removes most of what the scrub has to catch.
8. Tighten `validate_metadata` for the launcher kind to ASCII-printable: `char::is_control` does not cover U+2028/2029 or bidi overrides (U+202E), and `branch`, `git_sha` and `launcher_version` reach the info-level mint log line (handlers.rs:297).
9. Confirm whether the "Functions-side verifier" named in token.rs:36 still exists. If it does, it will not know `kind` and may accept a launcher token as a player one; the distinct scope in Required 1 makes it refuse, but verify.
10. Confirm `with_session_clock(sid, install_id, ...)` (entity_labels.rs:395) is bounded per session; with free sids it must not grow without limit. Launcher rows skip naming (Required 13) but check the generic path.
11. Confirm the transport on the colo login port is TLS (the default endpoint in handlers.rs:30 is `http://`). A bearer token is not worth protecting (mint is free), but row contents are what the scrub exists for.
12. Update `docs/operations/telemetry.md` with the launcher kind, its quotas, the allow-list, and the new env names; add revert-proof tests for Required 1-5, 7, 9, 11-15.

## Residual risks

- **Unauthenticated mint stays unauthenticated.** A distributed caller (many IPs, or many /64s of one IPv6 allocation) gets 12 launcher sessions/h per IP-bucket and the global ceiling (Required 8) is the only backstop; volume is bounded, not prevented. Same as player today.
- **Adoption data is forgeable.** Anyone can mint and post well-formed `client.launcher.*` rows, and a player or lab token can post them too (the target is not a privilege). Funnel dashboards built from these rows measure what clients claim; do not alert or decide on them without that caveat. This is also true of every `client.native` row today (`names_source = "client_claimed"`).
- **Fixed-window counters allow a 2x boundary burst**, and fixed 4096-slot tables share a bucket for colliding keys (fail-closed for the colliders, by design).
- **Shared egress.** Several players behind one NAT share the per-IP launcher counters; a wrongly refused mint costs that session's adoption telemetry only (no disk queue by design).
- **Honest-client PII beyond paths and IPs.** Hostnames, user names not in a path, and free-form text that slips past an allow-listed string value cannot be detected by pattern; Recommendation 7 (no free text) is the real control.
- **Install linkage** (Recommendation 2) unless the pseudonymous `sub` is adopted.
- **Secret compromise** (`CIMMERIA_TELEMETRY_HMAC_SECRET`) lets an attacker sign any kind, scope or lifetime; the scope and kind consistency check does not help there.
- **Slow-body slot holding** with many free tokens across many IPs can starve the shared chunk slot pool until Recommendation 5 is done.

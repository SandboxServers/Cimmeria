# Launcher adopt UX: ledger

Packets: [work-packets.md](work-packets.md) · Resume card: [RESUME.md](RESUME.md) · Designed 2026-10-20

## Purpose

A tester used Settings → **Use an existing game folder…** in the desktop launcher and reported two problems:

1. **(a)** The launcher refused the folder with the generic `unsafe_file` text ("a link, a special file, or a folder that was replaced"). It did not say which file was wrong, why, or how to fix it.
2. **(b)** The two mode radios sat on one line. They read as two buttons, and nothing on screen showed which mode was picked or that a second step follows.

This campaign fixes both, and documents the error, all inside the launcher (`crates/launcher/desktop/`):

- **A. Actionable refusal.** When the scan refuses a folder, the launcher lists up to five offending entries on screen. Each entry gives its path relative to the chosen folder, the reason (a link or junction, a cloud-synced file, a hard link, a special file, a bad name, or a case collision) and the fix. Each offender is also warn-logged under target `adoption` with its relative path only.
- **B. Mode choice.** Each mode is its own row, with a description under it and a visible selected state. The choose button names the picked mode (select, then confirm on the same screen).
- **C. Docs.** The player guide and the migration contract describe the refusal, its causes and the fixes.

- **D. Launcher telemetry (wave 2, added 2026-10-20).** The owner answered OQ-3 with yes: the launcher keeps its own log file, and its adoption events reach SigNoz through the pipeline game diagnostics already use. Under the existing "Send game diagnostics while playing" choice, the launcher queues them and they leave with the next Play.

Out of scope: any wire or protocol change outside the launcher, `db/scripts`, game-server code (wave 2 needs none: D-AU12, D-AU13), and lab or live-client use.

## Decisions

| ID | Decision | Status | Reason |
|---|---|---|---|
| D-AU1 | OneDrive and other cloud placeholders, junctions and symlinks **stay hard refusals**. The launcher now names them and says how to fix them: move the folder out of the synced tree, or put the real folder in place of the link. | BlockedDecision (owner); default applied | The brief's default. Adopting through a reparse point lets the move or the publish land somewhere other than the folder that was checked. The owner may later allow cloud files that are fully hydrated; that would be a new packet. |
| D-AU2 | Offenders **outside the release file set** still block adoption (a hard link in a mod folder, for example). | BlockedDecision (owner); default applied | The scan hashes the whole tree and in-place moves run over it. Relaxing this changes the safety model and needs its own design. The list makes these offenders visible and fixable. |
| D-AU3 | **Yes** (owner, 2026-10-20). The launcher gets a tracing subscriber, a local log file and telemetry to SigNoz, all in wave 2 (AU-07..AU-10). Wave 1 is unchanged: its warn logs carry relative paths only (D-AU7), so wave 2 forwards them as they are. The UI still points at no log (D-AU9). | Decided (owner, 2026-10-20) | The owner answered OQ-3. |
| D-AU4 | The engine explains a refusal **after** it happens. When a source scan or `refuse_links` returns `StorageError::UnsafeFile`, a bounded read-only survey walks the folder and returns `Error::Unsafe(Box<UnsafeReport>)`. `adoption::Error` loses `Copy` (it keeps `Clone`, `PartialEq`, `Eq`). | Decided | The scan itself is unchanged, so it cannot fail open. The survey runs only on the failure path and never descends into an offender. |
| D-AU5 | The shell carries the report in a **new status field** `unsafe_entries`. `AdoptionError` stays `Copy` and `unsafe_file` stays its summary code. | Decided | The summary codes and their tests stay as they are. The new field is additive, and only the adoption status uses it. |
| D-AU6 | On Windows the survey reads the reparse **tag**: `IO_REPARSE_TAG_MOUNT_POINT` and `IO_REPARSE_TAG_SYMLINK` are `link`; the cloud-files family (`tag & 0xFFFF_0FFF == 0x9000_001A`) is `cloud_file`; any other tag is `special_file`. The handle is opened with `FILE_READ_ATTRIBUTES` and `FILE_FLAG_OPEN_REPARSE_POINT`, so the file is never recalled. | Decided | It is the only way to tell a OneDrive file from a junction, and the two have different fixes. |
| D-AU7 | Adoption logs carry paths **relative to the chosen folder** only, `/`-separated (`"."` for the folder itself). The absolute-path fields at `source.rs` 89, 139, 164 and 182 are removed. | Decided | The brief: no user names or home paths in telemetry. |
| D-AU8 | **Select, then confirm, on one screen.** Each mode is a full-width row with a description and a selected style, and the choose button names the selected mode. There is no extra dialog: the native folder picker is already the confirm step, and the review screen follows it. | Decided | It fixes "two buttons, no confirm" without adding a modal. Changing a radio re-renders at once, which meets the first-press feedback rule. |
| D-AU9 | Remove the false log sentences from `duplicate_release_file` and `leftover_launcher_files`. | Decided | F6: there is no log. Naming the actual entry for those two codes is a follow-up. |
| D-AU10 | Caps: at most **5** entries in the report and on screen (in walk order, children sorted by name), a `total` count, at most **100** warn lines per survey plus one summary line, and the scan's own `MAX_FILES` and `MAX_DEPTH` bounds. | Decided | The screen stays readable, the log stays bounded, and the survey stays bounded on a large tree. |
| D-AU11 | "Replaced while checked" is **not** a reason. If the survey finds nothing (a race, or a file that changed), the generic text is shown, reworded to say what to do. | Decided | A race cannot be pinned to an entry after the fact. |
| D-AU12 | **Transport: the existing game-diagnostics pipeline, not an OTLP exporter.** The launcher turns each forwarded log line into a `client_native` event and appends it to the game-telemetry disk queue with `queue_now` (the `install_event.rs` pattern). The next Play's session uploads it to the first login server, and the server replays it into SigNoz. The launcher gets no OpenTelemetry crate and no collector address. | Decided | F20: the collector is not public and has no token, quota or kill switch, while the login-port route has all three, plus the endpoint policy and field caps. Appending to the queue cannot block, and the queue survives an offline launcher and restarts. The cost is the delay: events leave with the next Play, not at once (OQ-6). No server change and no deploy are needed. |
| D-AU13 | **Service: `cimmeria-client`, event name `client.launcher.adoption`.** Query `service.name = 'cimmeria-client' AND client_target = 'client.launcher.adoption'`. No `cimmeria-launcher` service is created. | BlockedDecision (owner, OQ-5); default applied | F21: launcher rows already live in `cimmeria-client` (`client.launcher.install_result`, `launcher.summary`). A separate service would split them, and it needs a server packet (a fourth log provider, after first splitting `filters.rs`, which is over the hard cap) plus a colo deploy. |
| D-AU14 | **Local log file**: `<app data>/logs/launcher.<yyyy-mm-dd>.log` (Windows: `%APPDATA%\app.cimmeria.launcher.desktop\logs`), rotated daily, 7 files kept, written by a non-blocking writer. It takes INFO and above from the launcher crates and the `adoption` target, and WARN and above from everything else. The home folder is written as `~`. It is always on, and the launcher never uploads it. | BlockedDecision (owner, OQ-7); default applied | It is the offline fallback a tester can attach by hand. It stays on this computer, so it needs no consent. Replacing the home folder keeps user names out of a file people share. |
| D-AU15 | **No new toggle.** Launcher telemetry follows the existing "Send game diagnostics while playing" choice (opt-in, off by default), as `client.launcher.install_result` already does. The checkbox's text, its "On." status line and a new one-line privacy note say what the launcher adds. The first-press feedback of that checkbox already exists and is tested. | BlockedDecision (owner, OQ-4); default applied | One choice per destination, and the project's policy: every player-machine upload is opt-in and off by default (F18, F19). A second toggle would need its own consent record and copy for the same upload path. |
| D-AU16 | **Only the `adoption` target is forwarded**, at INFO and above. Every string field is scrubbed before it is queued: the home folder becomes `~`, and a value that still holds an absolute path (a drive path, a UNC path, or a leading `/`) becomes `<path removed>`. Every other launcher log line stays in the local file only. | Decided | The brief's redaction rule: no IPs, account names or home paths. Only the adoption logs were audited for paths (F7, D-AU7), and other launcher warn lines may carry absolute paths. An allowlist also stops the forwarder's own failure logs from looping back into it. |
| D-AU17 | **Six adoption step events** (C10), each with `step` and `decision_outcome` (a closed enum, as the server's decision logs use it), plus `mode`, `error`, `unsafe_total` and `unsafe_entries` where they apply. Wave 1's per-entry survey warns (C3) are forwarded too. | Decided | The brief's list: folder chosen, refused with the reason and the relative path, mode chosen, confirmed, and the result. `review_ready` marks a scan that passed. |
| D-AU18 | **Wave 2 ships as its own PR** from `au-tel-integration` (branch `launcher-adopt-ux/telemetry`). AU-07 and AU-10 start now, alongside wave 1. AU-09 waits for the wave-1 PR to merge. | Decided | Wave 1 already has six packets, so folding four more in would break the size of a wave review. Only AU-09 needs wave-1 code (AU-03's `fail` and `last_unsafe`). |

## Open owner questions

The orchestrator asks these. Each one has a default, and the defaults are built in, so no packet waits on them.

- **OQ-1 (D-AU1).** Should OneDrive placeholders and same-volume junctions stay hard refusals? **Default: yes.** The launcher explains why and how to fix it.
- **OQ-2 (D-AU2).** Should files outside the release set (a mod folder with a hard link, for example) stop blocking adoption? **Default: they keep blocking, and they are listed.**
- **OQ-3 (D-AU3).** Decided by the owner on 2026-10-20: **yes**, the launcher sends telemetry to SigNoz. That decision became wave 2.
- **OQ-4 (D-AU15).** Should launcher telemetry be opt-in (off until the player turns on "Send game diagnostics while playing") or on by default? **Recommended default: opt-in, off.** Every other upload from a player's machine is opt-in, and the toggle copy promises that. On-by-default would need a new consent record, a first-run notice and a privacy-text review, which a separate packet could cover.
- **OQ-5 (D-AU13).** Should the launcher get its own SigNoz service, `cimmeria-launcher`, instead of `client_target = client.launcher.*` rows in `cimmeria-client`? **Default: no.** Saying yes adds a server packet: split `logging/filters.rs` (734 lines), add a fourth log provider in `otel.rs`, add a `client.launcher.` target route, then deploy to the colo.
- **OQ-6 (D-AU12).** The endpoint and the delay. Events go to the first login server's `/api/telemetry/upload-chunk`, the route game diagnostics already use, and they leave with the next Play that mints a session. No public OTLP endpoint is opened. **Default: accept the delay.** The alternative is a follow-up packet: the launcher mints a session and flushes the queue after an adoption, without waiting for Play. It reuses the session loop, needs no server change, and also covers adopted folders that play without the DLL (F23).
- **OQ-7 (D-AU14).** Keep the local log file? **Default: yes.** It is always on, stays on this computer, rotates daily and keeps 7 files. A later packet could add it to **Upload debug logs**.

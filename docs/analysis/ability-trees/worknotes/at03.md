## Live bug on `main` today: the level gate is stuck at 1

**Symptom:** on `main` before AT-03, no ability-tree node above level 1 can be trained in game, whatever the character's level. The trainer greys the node (`trainable = 0`), and a crafted `trainAbility` is rejected with `reason=level_too_low`.

**Cause:** `CellEntity::level` defaults to 1 (`crates/entity/src/cell_entity/entity_struct.rs:171`), and nothing set it for a player:

- `InitPlayerState` carried no level.
- `handle_grant_xp` updated only the base session and the DB row.

The trainer's level gate (`ability_tree/gates/node.rs::level`) reads `CellEntity::level`, so every player trained as level 1. The same field feeds the level that other players see when this player is introduced into their AoI (`cell/service/base_messages/request_entity_update.rs:118`), so that showed 1 too until a later `onLevelUpdate` broadcast.

**Fix (AT-03):**

- `InitPlayerState.level`, read by the `onClientReady` SELECT, stamps `CellEntity::level`.
- `BaseToCellMsg::ProgressionChanged` follows every persisted level-up.

**Guard:** `ability_granted_burst::level_gate_reads_the_level_hydrated_at_world_entry`. It drives `InitPlayerState` at level 5 and expects the level-5 node trainable, and it fails with the stamp removed (proof below). `general::init_player_state_caches_character_name_on_cell_entity` also asserts the stamped level.

**For the close-out:** `docs/gap-analysis.md` already has the new row "Ability-tree purchase (spend gate, per-node cost)", which mentions this bug. The row is NT until a client run.

## Evidence found while implementing

1. **The cell could not evaluate `NotEnoughPoints`.** `training_points` existed only on the base (`ConnectedClientState.player_training_points`). `TreeProgress` gains `training_points`, loaded by the `onClientReady` SELECT.
2. **The cell's player level was never set (pre-existing bug).** `CellEntity::level` defaults to 1 (`crates/entity/src/cell_entity/entity_struct.rs:171`). Nothing assigned it for a player: `InitPlayerState` had no level, and `handle_grant_xp` never told the cell. So on `main` the trainer's level gate treated every player as level 1, and no node above level 1 could be trained in game. `request_entity_update.rs:118` also introduced every player to other players as level 1. Fix: `InitPlayerState.level` (same SELECT) stamps `CellEntity::level`. The coordinator was told before the fix went in.
3. **The cell's level and points drifted after a level-up.** The new `BaseToCellMsg::ProgressionChanged { entity_id, level, training_points }` is sent by `handle_grant_xp` after its `UPDATE` commits, and only when a level boundary was crossed.

   **Paths covered:** every in-world write of `level` or `training_points` goes through `handle_grant_xp` (`ProgressionChanged`) or `handle_train_ability` (`AbilityGranted`). These are the only two base `UPDATE`s of those columns (checked with grep 2026-09-26). All XP sources send `CellToBaseMsg::GrantXP` into `handle_grant_xp`:
   - mob kill (`cell/abilities/death/side_effects.rs:97`);
   - native `gmGiveXp` (`cell/cell_methods/gm/give.rs:68`);
   - `.givexp` (`cell/console/give.rs:89`);
   - content `Action::GrantXP` (`cell/content/executor/mod.rs:528`).

   `play_character.rs` loads the values before world entry, and `InitPlayerState` then carries them to the cell. The values sent are the persisted post-level-up ones, which is AT-07's `apply_level_ups` result as written by the `UPDATE`.
4. `abilities` was already in `OTEL_FILTER` (`abilities=debug`), so no new target and no filter pin are needed.
5. The level-up bundle and the cell's grant burst now share one builder, `ability_tree::training_points_property_args`, which delegates to the existing `build_entity_property_args`.

## Design decisions

- **Gate order:** `node::level`, `node::prerequisites`, `spend::branch_points`, `spend::points`. `SpendGate` ranks before `NotEnoughPoints` because a structural lock is more informative than a transient shortage. AT-04's trainer gates go after these.
- **Base `UPDATE`** (`train_ability.rs::persist_purchase`) is one statement: append to `abilities` and `trained_abilities`, `training_points -= cost`, `tree_points_spent += cost`, guarded by `training_points >= cost AND NOT (abilities @> ARRAY[id])`, returning both counters. The base also refuses a negative `cost`, and a session whose `active_player_id` is not the validated player, before the `UPDATE`. The second check came from the server-authority-enforcer review: a recycled entity id would otherwise overwrite another character's point cache.
- **Cell mirror on `AbilityGranted`:** add the ability, push to `trained_abilities` (deduplicated), and set `training_points` and `tree_points_spent` from the returned values. This happens before any send, so the trainer re-send sees the new state.
- **Grant burst order:** `onKnownAbilitiesUpdate`, then `onEntityProperty(TrainingPoints)`, then `onTrainerOpen` (only while a trainer is pinned).
- **`train_raw_cost_zero`:** a WARN on the cell when a purchase passes the gates and the node's `raw_training_cost == 0`, logged before the request goes to the base. The purchase proceeds at `skill_point_cost`.
- **`player_data.rs` untouched:** the base needs neither `trained_abilities` nor `tree_points_spent`; its `UPDATE` returns them. The new columns ride the `onClientReady` SELECT instead, which the cell's hydration already used.
- **`handle_train_ability` moved** from `progression/mod.rs` (632 lines) to `progression/train_ability.rs`. This keeps `mod.rs` near the soft cap, isolates the function AT-03 owns from AT-07's `grant_xp`, and gives the live-DB tests a callable seam (`persist_purchase`).

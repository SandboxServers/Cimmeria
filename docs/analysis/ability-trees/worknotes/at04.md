## Evidence

- **Forged purchases.** `train.rs` on `13b60f70` built `TrainContext` with no trainer input, so a `trainAbility` from anywhere passed once the node gates held (audit A-06).
- **The pin.** `last_interaction_target` is written only by `interact`, after `interact_target_in_range` (`cell_methods/player/interaction/interact.rs:170-208`). It is never cleared on trainer close (`ability_granted.rs` comment).
- **Error codes.** The mapping is AT-E1's (`worknotes/at-e1.md`). `onErrorCode` rendering is unresolved: no client Lua consumes it (finding §2). That is why every coded rejection also re-sends the trainer.
- **Cross-space hole.** `interact_target_in_range` compared raw positions, and `SpaceManager::get_entity` searches every space (`space_manager/queries.rs:155`). An `interact` naming a trainer in another space at nearby coordinates therefore passed, and set the pin. The server-authority-enforcer review found this, rated MEDIUM.

## Design decisions

- **`TrainerPin` is resolved by the caller.** The predicate never touches `SpaceManager` (AT-01 contract). The cell resolves the pin in `trainer_authority::trainer_pin`, with four outcomes: `Unpinned`, `Despawned`, `NotATrainer`, or `Trainer { offered, in_range }`. The three gates in `gates/trainer.rs` only read the result. Range is `interact_target_in_range`, so this packet adds no distance constant.
- **Gate order.**
  - Node gates run first, then (AT-03's spend gates), then `pinned`, `offered`, `in_range`.
  - `AlreadyKnown` comes from `resolve`, so it outranks every trainer gate. A replay from far away is still a silent duplicate.
- **The window uses the same pin.** `try_open_trainer` passes its `target_entity_id`, which is the pin for both callers (`interact` pins it just before the call, and the re-sends read the pin back). The `trainable` byte and the purchase therefore still agree (`train_trainer_agreement.rs`). After walking away, a re-send shows every node greyed out.
- **One code for all five trainer rejections: 43 `OutsideDistanceCheck`.** The player's remedy is the same for all of them: go to a trainer that teaches the ability. `InstanceID` is always the ability being trained. It is not the missing prerequisite, per the D-AT08 wording.
- **No code means silence.**
  - `error_code` returns `None` for `AlreadyKnown`, and for three rejections a legitimate client cannot produce: `UnknownAbility`, `NoPlayerId`, `NoArchetype`.
  - `send_reject_feedback` returns early on `None`, so no trainer re-send follows either. The review flagged forged ids as a free `onTrainerOpen` build per inbound packet.
  - Those three remain WARN-logged.
- **Exhaustive `error_code` match.** When AT-03's variants land, the build breaks until someone adds their arm. The `STAT_VALUE_LESS_THAN` constant is not declared here: it would be dead code on this base and fail `-D warnings`.
- **Same-space check in `interact_target_in_range`.** This is an adjacent fix of the same class. The gate AT-04 reuses had the hole, and fixing it once closes both `interact` and the purchase. It logs at info, like the other misses.

## Known gaps

- **`onErrorCode` rendering is unverified client-side** (AT-E1 Q2). The re-send is the feedback the player is known to see. UAT step 6 (AT-06) is the check.
- **A dead trainer still teaches.** Neither `trainer_pin` nor `interact_target_in_range` checks `is_dead_state`, and a dead buyer who is still pinned can train. `interact` refuses a dead actor. Low severity: the debug trainer is not attackable.
- **Re-send spam.** A client spamming coded rejections gets one `onTrainerOpen` build per packet. The cost is bounded to its own downlink (the channel is bounded). There is no per-tick limit, and no test pins one.
- **The `not_a_trainer` counter pre-check in `resend_pinned_trainer`** only keeps metrics clean. No test would catch its removal.

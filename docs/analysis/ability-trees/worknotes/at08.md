## Hotbar: the owner decision cannot be done as written

The decision said to strip refunded ability ids from the **saved hotbar**, in the same transaction. No server-side saved hotbar exists:

- **The client owns it.** `Content/UI/Core/ActionButtons/ActionButtons.toc` declares `<CharacterVariable>GActionProfiles</CharacterVariable>`. The client writes it to `Documents/My Games/<profile>/SGWGame/<account>/<shard>-<character>/ActionButtons - Saved Vars.lua`, which holds `buttonInfo[n].actions[layer] = actionId`. The actionId-to-ability binding is native (`setActionToAbility`, `getActionInfo`).
- **No server surface carries it.** There is no method or property in `entities/defs/*.def` or the `docs/protocol/` dispatch tables, no column in `db/sgw`, and nothing in `deprecated/python`.
- **"Hotbar" in this repo means the known list.** Every use of the word (`respawn/resync.rs`, `ability_granted.rs`, `player_init`) refers to `onKnownAbilitiesUpdate` (client method 101).

The coordinator was told when this was found. What was implemented instead:

- The respec `UPDATE` strips the refunded ids from `sgw_player.abilities`, the only server-held list the bar draws from.
- The "hotbar re-send" is `onKnownAbilitiesUpdate` with the post-respec list.
- A bar button bound to a refunded ability stays until the player clears it. Pressing it is refused as an unknown ability (`use_ability/handle.rs:147`).

More than this would need a client Lua change, which is a maintainer decision.

## Design decisions

- **Gate on the cell** (`vendor/respec.rs`). The checks, in order:
  1. The entity has a `player_id`. Failing this is silent, with a WARN.
  2. `trainer_pin` returns `Trainer { in_range: true, .. }`. The offered list is irrelevant for a respec.
  3. `tree_progress` shows something trainer-bought. This is a cheap pre-check; the base guard is the authority.
  4. The retry window, described below.

  Method 72 sits in the combat dispatch range, so `combat::dispatch` forwards it to `vendor::handle_reset_my_abilities`.
- **One constant.** `RESPEC_COST_NAQUADAH` lives in `cimmeria_wire::ability_tree::respec` and is re-exported through `cell-catalog`'s `ability_tree`. It fills `onTrainerOpen`'s `CostToRespec`, and the cell sends it in `ResetAbilities`. The base refuses a negative cost.
- **The base does one `UPDATE`** (`progression/respec.rs::persist_respec`):
  - The guard is `naquadah >= cost AND (tree_points_spent > 0 OR cardinality(trained_abilities) > 0)`.
  - It sets:
    - `abilities` = `abilities` minus `trained_abilities`, with the order kept (`unnest ... WITH ORDINALITY`);
    - `training_points += tree_points_spent`;
    - `tree_points_spent = 0` and `trained_abilities = '{}'`;
    - `naquadah -= cost`.
  - The pre-update `trained_abilities` comes back through a locked self-join (`FROM (SELECT ... FOR UPDATE) old`), because Postgres 17 has no `OLD` in `RETURNING`.
  - When 0 rows match, a read-only `SELECT` classifies the result as `NothingToReset` or `NotEnoughNaquadah`.
  - The base also refuses when the session no longer plays `player_id`, as AT-03 does.
- **Refund exactness.** The refund equals `tree_points_spent` because only trainer purchases add to it (D-AT03). A character with no provenance (D-AT11) is refunded nothing and charged nothing.
- **Replay.** A replay reaches `NothingToReset`: it is free and changes nothing.
  - It gets feedback: `onErrorCode(167)` plus the trainer re-send. A first press on an enabled Respec button with nothing trained is a real press, and the project rule wants it answered.
  - The spam cost is bounded twice: the trainer gate runs first, so only a player at a trainer triggers the re-send, and the retry window drops repeats.
- **The retry window** (added from the review). A press within 1 s of the last forwarded respec is dropped silently (`CellEntity::respec_requested_at`). It is not a first press, since the earlier answer is still on its way. The window:
  - bounds the base to one row-locking `UPDATE` per player per second. This matters because the cell cannot see naquadah, so a player short of it would otherwise reach the base on every packet;
  - stops a double-click from showing success followed by "nothing trained".
- **Feedback codes** (`EConditionHandlerFeedback`, all reuses). `InstanceID` is 0 because a respec names no ability.

  | Case | Code |
  |---|---|
  | Not at a trainer | 43 `OutsideDistanceCheck` |
  | Nothing trainer-bought | 167 `EntityDoesNotHaveAbility` |
  | Too little naquadah | 35 `StatValueLessThan` |

  The 2009 enum has no currency token. Code 35 is the same generic "value below threshold" comparator AT-03/AT-04 use for training points.
- **Order of the cell burst on success:**
  1. `onKnownAbilitiesUpdate`;
  2. `onEntityProperty(TrainingPoints)` (the shared builder);
  3. `onCashChanged(naquadah)`;
  4. the `onTrainerOpen` re-send, while a trainer is pinned.

  The mirror (remove the refunded abilities, clear `tree_progress`, set the points) runs before any send, so the re-send shows the roots as buyable. `onCashChanged` is sent from the cell through `EntityMethodCall`, which keeps the whole burst in one pinned order.
- **Warmup (AT-10).** If the parked `PendingCast` is a refunded ability, `interrupt_unlearned_cast` interrupts it with the new reason `ability_unlearned`. Its two `onTimerUpdate` frames, and `onSequence(Ability_Interrupt)` when the ability has an event set, go out before the burst. A cast of an ability the player keeps is left alone.
- **Identity** (added from the review). `AbilitiesReset` carries `player_id`. The cell ignores the message if the entity id now plays another character.

## Known gaps

- **Action-bar buttons.** Buttons bound to refunded abilities stay on the client bar. This is the hotbar finding above.
- **Unverified in the client.** Whether the client's `onKnownAbilitiesUpdate` bridge handles *removed* ids (AT-E1 open question 2), and whether it renders `onErrorCode` (AT-E1 Q2). UAT (AT-06) should run a respec with the Ability window open.
- **Weapon-granted duplicate.** If the equipped weapon also grants a refunded ability, the cell's `remove_ability` drops it from the known set. `useAbility` still resolves it through the active-weapon fallback (`handle.rs:147-161`), but the next `onKnownAbilitiesUpdate` omits it until the weapon is re-equipped.
- **Content grants of a bought id.** An ability that was trainer-bought and later also granted by content stays in `trained_abilities`, because a grant of a known id is a no-op, so a respec removes it. This is an edge case, and the refund is still exact.
- **Auto-cycle.** An auto-cycle loop on a refunded ability is not cleared explicitly. Each tick's `useAbility` is refused as unknown.
- **`entity_struct.rs`** was already over the 700-line hard cap (747 lines). This packet adds one field, 4 lines with its doc comment.

## Out of scope (for the owning packet)

- **`AbilityGranted` has the same entity-id-reuse gap** that the review found for `AbilitiesReset`: the cell mirrors by `entity_id` alone. That is AT-03's message. The same fix applies: carry `player_id`, and ignore the message on a mismatch.

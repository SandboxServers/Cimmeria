## Design decisions

- **Split, not a second path.** `handle_use_ability` keeps every launch gate and stops after the
  cooldown timer and auto-cycle commit. `fire::fire_cast` is the old tail (ammo, `Ability_End`,
  channel cancel, damage, cone fan-out, auto-reload), called in the same pass for warmup 0 and from
  the tick otherwise. Each step runs once per cast, in the fire phase. NPCs share it.
- **Zero warmup is byte-identical.** `charged = cooldown + 0.0`; no Begin, no warmup timer; End and
  damage in the launch pass. Ammo now decrements in `fire_cast` instead of before the timer send,
  which is not wire-visible (the stat flush was already after the damage). Pinned by `zero_warmup_wire_is_unchanged`.
- **Followed python:** cooldown at launch covering the warmup; ammo at fire; speed stats; death and
  slot-change interrupts; the interrupt refunds the cooldown and sends the zeroed warmup timer and
  `Ability_Interrupt` (1002); second press refused.
- **Deviations (marked in code and ADR decision 21):**
  1. Movement ≥ 0.5 m interrupts (channel rule and its `AF_CHANNEL_ALLOWS_MOVEMENT` exemption); a space change always interrupts.
  2. Fire-time re-validation (python re-checked nothing): target gone/dead/other space/no longer hostile (#444), range (`onErrorCode` 42), player LoS (`onErrorCode` 39), player ammo/reload, and the active weapon instance must be the one launched with (python's slot-change hook also covered "active item swapped/removed").
  3. The interrupt also sends a zeroed `AbilityCooldown` timer so the hotbar matches the refund.
  4. The interrupt stops auto-cycle when the interrupted ability is the loop's; otherwise the refunded cooldown lets the loop relaunch every tick while a player walks.
  5. Second press refused silently (python's error code never reached the client either).
- **Stun is not a trigger.** Nothing in python or the Rust launch gates on stun, and a stun is only
  `BSF_MOVEMENT_LOCK`, shared with ring transport and death. Adding it needs a design decision.
- **Kill credit.** `kill_credit.rs` split into `is_live_npc` + `credit_single_target` (same code);
  the tick wraps player fires with them. Ground kill credit moved into `credit_ground_deaths`, used by
  the `useAbilityOnGroundTarget` handler and the tick. NPC fires credit nothing, as before.
- **Ground casts.** The launch parks the ground point on the cast (`attach_ground_point`); the tick fires
  the primary and collects secondaries around the point at fire time.
- **NPC AI.** `npc_ai_fight` returns early (`decision_outcome = "casting"`) while its NPC casts, so it
  neither WARNs "attack tick produced no ability fire" nor moves (which would interrupt).
- **`dispatch.rs` became `dispatch/`** because the new code took it past the 700-line cap; the tests
  moved verbatim to `dispatch/tests.rs`.
- **No new WARN and no new log target.** Interrupts log INFO `abilities event=warmup_interrupted reason=…`;
  start/complete log DEBUG under `abilities`. `abilities=debug` is already in `OTEL_FILTER`.

## server-authority-enforcer review (read-only)

Verdict CONDITIONAL, no double-fire or double spend. Findings and disposition:

1. MEDIUM-HIGH: ground cast of 592 redirected to a warmup weapon ability applied splash at launch
   (the parked cast was matched by the client's ability id). **Fixed**; guard `redirected_ground_cast_defers_its_splash_damage`.
2. MEDIUM: weapon swapped into the active slot via inventory base messages did not interrupt.
   **Fixed** at fire time (weapon instance on `PendingCast`); guard `weapon_swapped_into_the_active_slot_interrupts_at_fire`.
3. LOW: cast could survive a space change. **Fixed**; guard `a_space_change_interrupts_even_a_movement_allowed_warmup`.
4. LOW: #444 not repeated at fire. **Fixed**; guard `a_target_turned_friendly_during_the_warmup_is_not_hit`.
5. LOW: Begin/Interrupt spam (launch, step, relaunch) amplifies packets to witnesses. **Not fixed**; no gain to the player. Open question below.
6. Note: a holster-queued attack that lands during a non-weapon warmup is dropped (`ticks/pending_holster.rs`). Not fixed; missed input, not an exploit.

## Known gaps

- Not client-exercised. Whether the client renders a warmup bar for timer type 1, and whether it
  honours the zeroed cooldown timer, is unverified in-game.
- The `bigWorldTimeComplete` argument of both new timers is `0.0`, the same TODO as the existing cooldown timer (#271/#718).
- Python's `Response` flag (cooldown × `1 − response/100`) and moniker `CategoryCooldown` timers are still not implemented (pre-existing).
- A reload request during a weapon warmup is accepted and then interrupts the cast at fire; python would have refused the reload (it was itself an ability). Accepted as conservative.
- Stun does not interrupt (see design decisions).

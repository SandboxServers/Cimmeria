## Not fixed

- LT-21b `append` is called even when `entries` is empty, so a game zip with no launcher logs is rewritten (central directory only) for nothing. The spec says to call it always; skipping on empty (`if entries.is_empty() { return Ok(body); }`) is a safe optimisation but not required. Left for the owner.
- LT-21b: if `append` fails the whole upload fails with `CollectFailed`, although the game zip is fine. Falling back to the game zip alone would need `append` to take `&[u8]` and is a behaviour change beyond the spec; N4 only makes the failure visible. A design call.
- LT-21b `entries` reads each launcher log whole into memory before the cap is applied (up to 3 files). Spec-conformant; a runaway log could be large. A tail-read would be a spec change.
- LT-21b `launcher.log`-style names (no date) sort after every dated file and count as "newest". Spec says keep the three greatest by name.
- LT-22 `resolve`'s `"default"` arm is unreachable and untested while `DEFAULT_SUMMARY_BASE` is `None`; `resolve_falls_through_to_no_https_endpoint` asserts `DEFAULT_SUMMARY_BASE == None` and will need updating when LT-41 sets it (the packet says so). Not a defect now.

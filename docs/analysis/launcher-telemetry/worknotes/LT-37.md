## Why it fails, and why no publish can pass today

- The seed's `blob` is an absolute archive.org URL.
- `blob_forms_match` (`crates/launcher-core/src/file_index/check.rs:117`) requires the index blob to be either:
  - an https URL on the **same host** as the seed, or
  - a relative path, but only when the seed's blob is relative too.
- We cannot put a file on archive.org, and the seed is never rehosted. So no hostable blob value passes: neither a GitHub release URL nor a relative name.

The check is stricter than the launcher:

- `manifest::blob_url` (`crates/launcher-core/src/manifest.rs:356`) takes any absolute https URL as it is, and resolves a relative one against the manifest URL.
- `artifacts::index_blob` downloads the index with the same https-only client it uses for the seed and patches.
- The live patches already sit on two other hosts: raw.githubusercontent.com and github.com.

So the check in LT-35's spec blocks a publish the launcher would accept.

## Correction needed (reported, not committed)

`blob_form_matches_seed` should accept any absolute https URL, or a relative blob. For example, it could:

- drop the same-host rule, or
- compare against the hosts the manifest already uses (the seed and the patches).

Its LT-35 test and the runbook line in `docs/client/launcher-distribution-setup.md` § File index need the same change.

D-LT15 also still has to name the per-publication release that holds `file-index.json`. No such release exists yet: the seed is on archive.org and the patches are on raw.githubusercontent.com. This run assumed a new immutable release, `content-file-index-20261021`.

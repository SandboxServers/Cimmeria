# CS-02b2 — Bind minigame callbacks to a Cell launch

> **Type:** Reference. **Audience:** Castle packet implementers and reviewers.
> **Last updated:** 2026-10-14. **Status:** Draft; architecture and test seams require review before dispatch.
> **Companions:** [Castle ledger](../README.md), [packet contract](../work-packets.md#cs-0203-conditional-graph-candidates-not-runtime-seals), [CS-02b0 Base send packet](CS-02b0.md), [CS-02b1 receipt packet](CS-02b1.md), [minigame reference](../../../gameplay/minigame-system.md), [test policy](../../../../TESTING.md).

## Question and boundary

Which live Cell player launched the board whose result Base is forwarding? CS-02b0 binds
each Mercury send to a Base connection instance. CS-02b1 specifies one-use,
ticket-derived result authority at Base. Neither proves that Cell still holds the same
incarnation and launch when its queued result arrives. This packet proposes an internal
launch identity and fail-closed Cell check before any victory chain. It does not enable
Castle callbacks or change the client protocol.

## Candidate internal contract

1. Mint a process-unique, nonzero **Cell incarnation** when a player `CellEntity` is
   created, before replying to Base. Do not derive it from time, the reusable entity ID,
   player ID or space ID. Keep it in server-only Cell state, not
   `CellEntity.properties`, persistence or client Mercury. Bind the Base
   `session_instance_id` to that Cell player at birth; Base already mints a
   process-unique instance (`crates/base-session/src/base/mod.rs:149`, `:360-364`). A
   typed internal key should contain `{ base_instance, cell_incarnation,
   launch_generation }`, with a fresh Cell-owned generation for each launch attempt.
   Keep player ID beside the key and compare it too.
2. Give each `CreateEntity` a server-owned owner/create epoch that Cell can compare
   with the current occupant **before** mutating its entity map or spatial state. An
   older queued create must not overwrite a newer same-ID occupant, even if Base
   would later reject its reply. Seal how the epoch orders two creates within one
   Base instance and a recycled ID in a newer instance; do not trust client timing.
   Keep a per-ID high-watermark after teardown: an empty slot must still reject a
   late create whose epoch predates the most recently accepted occupant. Have the
   create handler return accepted/rejected so later dispatch side effects, including
   `missions::state_lock::mark_load_pending` (`crates/cell/src/cell/service/base_messages/mod.rs:83-107`),
   run only for the accepted identity. Fence later `ConnectEntity` and
   `InitPlayerState` to that same identity before they mutate controller or mission
   state; both are currently entity-ID-only (`crates/wire/src/cell/messages/base_to_cell.rs:67-69`, `:131-143`).
   Make a successful create reply with both resolved `space_id` and its fresh
   incarnation. Base records the incarnation only after rechecking the **initiating**
   Base instance, entity and player against its current owner; a delayed older create
   response cannot install identity on a replacement. If the reply is dropped or
   creation fails, no incarnation is accepted and minigame Start fails closed. This
   launch rule does not treat the existing fallback space ID as proof of Cell creation.
   Do not use the uncorrelated trace-only `EntityCreated` message as the ACK.
   Break the existing gate-travel cycle where Cell awaits `SpaceData` send before
   replying while Base awaits the reply in its serial Cell-to-Base route. Return the
   correlated create result before any potentially blocked send, or use a separate
   nonblocking lane, while preserving the space/world registry ordering needed by
   world entry. Test a full Cell-to-Base channel.
3. Cell allocates a generation before Start and sends the typed key and player ID
   through the internal Start request. Base accepts only a key matching its current
   instance/entity/player and stored Cell incarnation; a queued old-world Start must be
   refused even if the gate reused all three Base identifiers. Return an internal
   **accepted/refused** answer to Cell. A refused first Start clears its pending attempt
   so a later click can retry. If a board is already active, refusal of a duplicate
   Start leaves that board's accepted generation untouched. Base scopes ticket
   registration and `onStartMinigame(URL)` to the accepted key and the original b0
   recipient snapshot. Define a key-matched transition table: a second Start while A
   is Pending cannot replace A; an exact-key refusal, cancellation or timeout clears
   only Pending(A); if B then becomes Pending, a late ACK for A cannot activate B;
   a terminal A result while B is Pending cannot consume B.
4. Specify ACK and URL order before implementation. In particular, either make Cell able
   to process a result that outruns its Start ACK, or guarantee an accepted ACK is
   applied before a result can be forwarded. If the URL send fails after acceptance,
   Base cancels only that ticket and tells Cell to clear only that key. A failed or
   closed ACK path cannot silently leave a pending Cell launch that blocks retry.
   Awaiting an ACK inside the Cell message loop must not create a same-channel deadlock
   or an unbounded stall. A direct oneshot reply after the scoped URL send is one
   candidate because Base serializes Start before a queued result; it still needs a
   bounded wait and an explicit choice about blocking the Cell loop. A Base-to-Cell
   ACK is another candidate only if a full channel has bounded fail-closed handling.
   `Accepted` means the Mercury URL send was queued, not that the SWF opened.
5. Cell's `endCurrentMinigame` snapshots its current key when it receives the client
   method and sends an internal Cancel carrying that key and player ID. Base cancels
   only if the same accepted key still owns the registry board. Cell clears only that
   generation; a stale queued Cancel must leave a newer board intact. The client method
   carries no board token, so a delayed client close first received after a new board
   becomes current remains ambiguous and is outside this server-side queued-Cancel
   guarantee.
6. A redeemed b1 receipt's original key, entity and player travel through the
   **internal** Base-to-Cell result. Base checks current ownership before close and
   again after its awaited close before forwarding. Cell accepts the result only when a
   live player has the same Base instance, Cell incarnation, generation and player ID;
   otherwise it logs a redacted reason and emits zero callbacks. A missing entity or
   player ID `0` is a refusal. One accepted terminal result consumes the matching
   launch **before** awaiting any victory chain, so a chain that starts B cannot be
   cleared by A's later cleanup or a duplicate A result. Extend b1's registered session and
   mutex-deposited receipt with the Cell incarnation and launch generation supplied
   by the server-owned Start key; no SmartFox result or client field supplies them.
   Destroy, disconnect, gate travel and
   replacement invalidate only the old key and its receipt; they cannot erase a newer
   launch. Scope `DestroyEntity`, `DisconnectEntity` and any orphan reaper to the
   expected Cell incarnation or an equivalent Cell-checked create epoch. A Base-side
   owner check before an awaited send alone is insufficient. A teardown with no
   authenticated target key must not destroy a current same-ID occupant.
   Define how an active key clears after the existing registry's 180-second
   pending-session sweep or result-delivery failure so Cell can retry. Any
   provisional reattempt must preserve Base's duplicate refusal and the
   original board. Carry the source Cell presence on `CellToBaseMsg::GateTravel`
   and reject a stale source at Base before RESET_ENTITIES, destination create,
   persistence or other travel side effects. Recheck the initiating Base
   instance, entity, player and source presence after each await; the current
   entity-ID-only `session_owner::owns` check is insufficient.
7. Preserve the existing client Mercury `onStartMinigame(URL)` and `onEndMinigame()`
   payloads and SmartFox login bytes. The key stays on internal channels only. The
   server's placeholder-game outcome limits from CS-02b1 still apply: identity binding
   alone does not prove the puzzle was solved.

## Test seams to seal

Use the real create reply, Cell-to-Base route, Base-to-Cell result handler and registry
state, with deterministic pauses rather than sleeps. Each stale-key case must assert
**zero Cell callbacks, zero close for the new board and preservation of its current
registry ticket** where a new board exists.

- Queue an old `GateTravel` after a same-ID replacement and assert zero
  RESET_ENTITIES, destination create or persistence for the replacement.
  Cover each of the five production travel constructors and repeat while an
  awaited travel step lets the address change owner.
- Create then gate travel to a new Cell incarnation while Base instance/entity/player
  stay equal; queue the old-world Start and result. Drop a create ACK and verify launch
  remains disabled even if world entry chooses a fallback space ID. Delay an old create
  **request** across connection replacement and verify Cell refuses it before insertion,
  preserving the new Cell entity, spatial binding and launch key. Delay an old create
  **reply** and verify Base does not store it. Destroy the newer occupant before the
  delayed old request arrives; the per-ID high-watermark must still reject it. A
  rejected create must not set mission load pending. Queue stale `ConnectEntity` and
  `InitPlayerState` after replacement and verify controller, player and mission state
  remain the newer owner's.
- Refuse the first Start and retry; refuse a duplicate while the first board runs
  without replacing its generation. Exercise second Start during Pending(A), then
  clear A by exact-key refusal, cancellation or timeout before making B Pending;
  a late ACK(A) and result(A) must not consume or activate B. Exercise a result
  before Start ACK, and accepted Start followed by failed URL delivery, according
  to the chosen ordering rule. Sweep an unconnected ticket and fail result delivery;
  neither may leave Cell permanently unable to retry.
- Queue old Cancel, relaunch, then drain it; verify the new ticket survives.
  Destroy/recreate, same-player relog, cross-player entity reuse, and same-entity
  relaunch must reject old results. A missing-entity victory must not call a chain as
  player `0`. Process late old `DestroyEntity`, `DisconnectEntity` and orphan-reaper
  teardown after a newer same-ID player exists; each must preserve the new Cell
  entity, launch and board.
- Replay a victory chain for A that starts B, then deliver duplicate A. B must
  remain active and its chains must not be fired or cleared by A's cleanup.
- Fill the Base-to-Cell channel while teardown, ACK or result forwarding is pending.
  Show the production path makes progress or fails closed without relying on a message
  trapped behind its own await. Fill Cell-to-Base while an instanced-world gate
  create awaits its correlated reply; the reply must not depend on a `SpaceData`
  message that Base cannot drain. Exercise address takeover around URL and close sends
  with distinct Base instances and keys.
- Add regression guards that fail if the Cell incarnation or generation comparison is
  removed. Select focused unit/concurrency/chain-replay and internal-message tests using
  [TESTING.md](../../../../TESTING.md); record actual test names, counts and build-lane
  commands in the implementation packet. No test or live-client result is claimed by
  this draft.

## Proposed staged split (not yet Ready)

A read-only design pass at integration HEAD `2bbea153c` recommends three
ordered packets. These are planning boundaries, not dispatched worknotes.

| Candidate | Boundary | Dependency |
|---|---|---|
| `CS-02b2-prep` | Extract natural handler or lifecycle modules from the four near/over-cap files above without changing behavior. | None; seal exact move and file allowlist. |
| `CS-02b2a` | Create epoch, Cell presence, correlated create reply and the **entire** presence lifecycle: source-scoped GateTravel, Connect, Init, Destroy, Disconnect and orphan-reaper fencing. | Prep extraction and reviewed typed-message contract. |
| `CS-02b2b` | Cell launch state machine, Base Start decision, keyed registry receipt, Cancel, result and exact-key expiry/failure cleanup as one runtime seal. | b2a integrated and ACK/channel policy sealed. |

A create-only packet would leave old ID-only teardown and travel messages able
to mutate a new occupant. Castle callbacks stay disabled through this split.

For b2a, the candidate internal types are `CreateEpoch` (Base instance plus
ordered create serial), `CellPresence` (epoch plus Cell-minted incarnation),
`CreateAck` (space ID plus presence) and a typed create refusal. The
`CreateEntity` reply should be `Result<CreateAck, CreateRefusal>`, not a
space-ID-only oneshot. A per-entity-ID Cell high-watermark must survive
destruction and reject stale or duplicate creates before spatial insertion;
a newer observed epoch rejected due to occupancy must still prevent an older
request from winning after teardown. Only a successful create installs a
fresh nonzero incarnation. Base stores the ACK only after rechecking the
initiating owner and operation. The exact epoch mint, overflow behavior,
failure cleanup and space registry ordering require code and domain review.
The current `mint_session_instance_id` uses an unchecked `AtomicU64::fetch_add`;
lexicographic epoch ordering must account for wrap or use a separate checked
process-global create serial.
The proposed timeout is 10 seconds total for create send plus reply, subject
to review. None of these types or deadlines is an implementation claim.

The current minigame registry's 180-second pending-session sweep and failed
result delivery have no key-scoped Cell abort notice. b2b must define that
notice, ACK/result ordering, bounded decision handling and full-channel
progress before a worker receives an edit allowlist. There is no verified
minigame, world-entry or gate-travel chapter in `docs/spec/README.md`; the
runtime packets must update their current reference documentation and record
the canonical chapter gap rather than cite a nonexistent Bible chapter. In
particular, b2a must update `docs/protocol/internal-cell-to-base.md`'s
GateTravel contract and b2b must update `docs/gameplay/minigame-system.md`.
The doc-update map needs an explicit internal Cell/Base message-contract row;
its current wire-format row primarily describes client Mercury.

## Decisions required before Ready

1. Choose the exact server-only key type and location: `CellEntity`/Cell service state,
   Base accepted-key storage, and the internal message definitions. List every
   `CreateEntity` construction and reply test that must change; its `Sender<u32>` is
   used by login, travel, lab fixtures and tests. Include the per-ID create epoch
   high-watermark, key-scoped Connect/Init/teardown messages and the b1 receipt key
   extension. Keep files below the repository's 700-line hard cap.
2. Seal the Start ACK versus URL/result ordering, including the nonblocking Cell wait
   and compensation signal. Define which component owns pending, accepted and terminal
   transitions so duplicate Start, retry and result-before-ACK are unambiguous. Choose
   exact timeouts or full-channel fail-closed behavior for both create and Start ACKs.
3. Seal gate, destroy, disconnect and replacement invalidation against b1 receipts, with
   exact-key cleanup under interleaving. Specify the owner/create epoch and Cell-side
   pre-insert comparison, then require incarnation-scoped teardown including the gate
   orphan reaper. Confirm a full Base-to-Cell channel cannot strand the serial Base route.
4. Obtain domain, BigWorld, minigame, server-authority and testing review of the typed
   message contract and test seams. Then name the file allowlist, focused lane checks
   and independent review gate. Until those decisions are recorded, this packet remains
   **Draft** and Castle callbacks remain disabled.

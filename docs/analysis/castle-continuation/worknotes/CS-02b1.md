> **Companions:** [Castle ledger](../README.md), [receipt architecture](../work-packets.md#cs-0203-conditional-graph-candidates-not-runtime-seals), [CS-02b0 Base send packet](CS-02b0.md), [CS-02b-prep documentation packet](CS-02b-prep.md), [test policy](../../../../TESTING.md), [minigame reference](../../../gameplay/minigame-system.md).

## Goal and boundary

Make a SmartFox task's terminal report a ticket-only notification to Base. The
registry deposits one short-lived receipt for the claimed, still-current
ticket; Base removes that receipt atomically and derives the result, callback
chains and original owner from it. A missing, forged, canceled or replaced
before redemption, expired or already redeemed ticket produces **zero**
client sends and **zero** Cell forwards. The receipt is server-produced
authority for *which registered
task reported a terminal outcome*. It does not validate a game's puzzle:
`PlaceholderGame` accepts client `_cmd=victory`. Castle callbacks stay disabled.

CS-02b0 is integrated. Its `snapshot_recipient` returns a
`RecipientSnapshot` containing entity, player, address and the nonzero
`session_instance_id`; `send_to_session_bound_reliable` accepts that exact
snapshot. Pass its captured instance into registration. Integrated
CS-02b-prep reduced `cell_to_base.rs` from 909 to 623 lines without changing
the enum shape, clearing the repository's 700-line hard-cap prerequisite. CS-02b2 later binds the Cell entity
incarnation and launch generation through the internal handoff. Keep
`BaseToCellMsg::MinigameResult`
and the existing unrelated Cell callback path unchanged here. A b1 Base
ownership check cannot prove that the Cell still owns the launch when the
forward is consumed. CS-02c may enable Castle only after b0, b1, b2 and the
actor, route, report and client gates pass.

## Candidate receipt contract

1. At `start_minigame`, pass the b0-captured **original** Base connection
   instance into `SessionRegistry::register`. Persist it in `MinigameSession`
   alongside the registered entity, player, game, ticket and victory chains.
   Use the same captured value that scoped `onStartMinigame(URL)` uses; do not
   look up a later connection by entity ID to populate the registration.
   Refuse a zero or missing instance in the production Start path. The b0
   `RecipientSnapshot.session_instance_id` is the identity source; do not
   mint or re-read another one at registration.
2. For a terminal `GameOutput::Victory` or `Failure`, and for the server-owned
   abort result, ask the registry to deposit by claimed session and ticket.
   Under its single mutex, require the current registration to match the
   ticket, be claimed and not be canceled. A successful deposit contains
   `ticket`, `entity_id`, `player_id`, `session_instance_id`, `game_name`,
   `result_code`, `notify_client`, the registered victory chains **only for
   victory**, and an issued `tokio::time::Instant`. Result and UI flag come
   from the server's terminal path; identity, game and chains come from the
   registration, never notification fields or mutable client input. Reject
   unknown result codes. Mark the ticket terminal under the same lock: even
   after redemption removes the receipt, a repeated report cannot deposit
   another one. At most one terminal receipt may ever be issued per ticket.
   An explicit player close removes the session before its later SmartFox
   abort report, so that canceled(0) deposit must refuse and send no Base
   notification; preserve the SmartFox aborted/close frames. Other server
   aborts while the session is still registered (disconnect, idle or send
   failure) may deposit canceled(0) with `notify_client=true`.
3. Deposit **before** sending `CellToBaseMsg::MinigameResult { ticket }`.
   Release the registry mutex before awaiting the channel. No other result
   fields travel in that notification. Return a three-way dispatch outcome:
   `Delivered`, `Refused`, or `DeliveryFailed`. `Delivered` means the
   ticket-only notification was enqueued for Base; redemption, Cell credit
   and mission progress remain unproved. On `DeliveryFailed`, revoke that
   exact receipt and preserve the named ERROR for a lost result. Only
   `Delivered` may emit a victory/defeat Discord event and attempt the
   matching board-result event after enqueue. A concurrent cancellation may
   remove the board before that attempt; absence of a board event is not a
   refused dispatch. A `Refused` terminal output uses
   `EndReason::PlayerCanceled` only when a server-owned cancel reason is
   known at the refusal decision; otherwise it uses new
   `EndReason::ResultRefused`. `DeliveryFailed` uses new
   `EndReason::ResultDeliveryFailed`. The two new reasons have
   `outcome=canceled`, never victory/defeat; neither failure emits a
   victory/defeat board event or Discord. Preserve the underlying
   `EndReason` for a server abort and its named delivery ERROR. The first
   terminal output alone sets the reason and side effects: stop or ignore
   later terminal `GameOutput`s whether the first dispatch was Delivered,
   Refused or DeliveryFailed. Every terminal attempt sets
   `result_reported` so fallback abort cannot emit a second result. Player
   cancel and game victory can interleave: whichever registry operation
   wins the lock decides whether a terminal receipt is deposited. A
   cancel-first refusal has no victory evidence; an enqueue-first result
   remains subject to the redemption and b2 identity boundaries below.
4. `SessionRegistry::redeem_result(ticket)` removes and returns the receipt
   in one locked operation. It does not reconstruct anything from
   `sessions`: normal `remove_if_ticket` can run before Base drains the
   channel. Base must have a registry and a receipt before it sends
   `onEndMinigame` or `BaseToCellMsg::MinigameResult`. Drop a notification
   without either, with a redacted, reason-coded diagnostic. A notification
   cannot supply its own entity, result code, chains, UI flag or player.
5. Before any Base send or forward, compare the receipt's original
   `entity_id`, `player_id` and `session_instance_id` with the current
   `entity_to_addr` and `ConnectedClientState` owner. A mismatch, missing
   connection, zero player or changed character consumes the receipt with
   zero outputs. For `notify_client`, use b0's scoped sender with that
   original instance and owner so an address takeover between check and
   send cannot close another player's board. Forward to Cell only after the
   same original-owner eligibility check, using the receipt's result and
   chains. Because the scoped close is awaited, repeat the original
   entity/player/instance lookup **after** that send and before Cell forward;
   a changed owner then gets zero Cell forwards, even if the old-key close
   packet was already prepared. An accepted server-abort canceled(0) outcome
   has no victory chains
   and `notify_client=true`; the explicit-close canceled(0) report is refused
   after session cancellation and sends no Base notification. Do not use the
   former `has_replacement_ticket` result as authorization.
6. Normal SmartFox teardown (`remove_if_ticket`) leaves an issued receipt
   available after it removes the live session. Explicit public `remove`,
   `cancel`, b0's `cancel_if_ticket`, and a successful replacement `register`
   invalidate
   receipts for the affected old ticket/entity **under the registry mutex**,
   including a receipt left after teardown. An old task's later
   `remove_if_ticket` must not erase a newer receipt. Keep the board snapshot
   lifecycle and pending-session sweep behavior otherwise intact. No new
   entity-wide cleanup is allowed to delete a different live ticket.
7. Bound undrained receipts independently of the 180-second *pending
   session* TTL: **180 seconds from issue and 4,096 total receipts**. These
   are the selected fail-closed bounds for this draft; authority and minigame
   reviewers must approve them before dispatch. Apply expiry at deposit,
   redemption and the existing sweep. At capacity, evict the oldest issued
   receipt before a
   new insert; an evicted ticket redeems to nothing. Use deterministic
   insertion order for ties and `tokio::time::Instant` for paused-clock
   tests. Log expiry/capacity eviction with reason, entity/player/game and
   ticket age or redacted prefix; never log the full bearer ticket or URL.
   The SmartFox listener allows at most 256 simultaneous sockets, so 4,096
   is 16 times that cap and 180 seconds allows a short Base backlog. These
   are fail-closed bounds, not a delivery guarantee: a longer Base stall or
   capacity eviction loses a valid result. Apply expiry at `age >= TTL`.

### Race linearization

Deposit, public remove, cancel, replacement, expiry and redemption each change
registry state under the same mutex. If cancel or replacement wins before deposit,
deposit refuses. If it wins after deposit but before redemption, it erases
the receipt. If redemption wins first, the receipt is spent; Base still
checks the original connection owner before output. A cancel, relaunch or
Cell replacement **after** redemption remains b2's launch-identity gate.
Do not describe b1 as closing that final race or as authorizing any Castle
mission mutation.

The production Base service currently awaits each `route_cell_message`
before receiving the next (`crates/base/src/base/service.rs:331`–`346`).
`StartMinigame`, `CancelMinigame` and `MinigameResult` share that route.
Consequently a later Start cannot register a new board while Base is paused
inside the earlier result's close. If A normally tears down before B Start
is queued first, B may register and invalidate A's undrained receipt. If A
is still live, a duplicate B Start is refused; it does not replace A. If
result is first, its close finishes before B Start. Preserve this ordering
and test all three cases. Direct concurrent
calls to these handlers outside the production route do not inherit this
guarantee and must not be described as safe. A client
`endCurrentMinigame` RPC received only after a new board is current carries
no ticket and remains ambiguous; b2 cannot infer its old origin.

## Packet implementation evidence

The registry deposits once for a claimed, current ticket and keeps the
terminal marker while that registration is live, even after receipt
redemption, TTL expiry or capacity eviction. Normal SmartFox teardown keeps
the issued receipt. Public remove, both cancel variants and a successful
replacement invalidate it under the same mutex. A failed channel send
revokes only its ticket. The Base route redeems before output, checks the
original entity/player/connection instance before close and after its awaited
send, and forwards only receipt-derived result and chains. The internal
notification has just `ticket`; the Cell callback remains unchanged.

`Delivered` means the Base notification entered the channel. Only that state
records a victory/defeat board attempt and emits the corresponding Discord
event. A refused or failed terminal report ends with `result_refused` or
`result_delivery_failed` and `outcome=canceled`; explicit player close refuses
the later abort report. The first terminal output stops further output
processing. The production Base receive helper awaits each routed message;
tests drive result-first, Start-first and live-duplicate orders through the
actual route with controlled transport.

Why this shape (the traps, applied):

- **Sibling disjointness (multi-chain dispatch: one event fires EVERY matching chain, conditions frozen at resolve time, `priority` never excludes).** `interact_tag Castle_HubSupplyOfficer`: 10234 (`10330 neq active`) and 10236 (`10330 eq active`) are disjoint. `player_loaded Castle`: 10231 (`neq active`) and 10237 (`eq active`) are disjoint; the other Castle `player_loaded` chains gate on other missions. Every other key (`mission_completed 704`, `mission_abandoned 10330`, `mission_completed 10330`, `enter_region Castle.Infirmary`) carries one 10330 chain. `enter_region Castle.Infirmary` is shared with other missions' chains (for example 1520 chains) but those gate on their own mission and step, so no overlap.
- **The giver is a new NPC, not the quartermaster.** An `interact_tag` chain short-circuits `handle_interact` (`cell_methods/player/interaction/interact.rs:184-219`): when a tag chain handles the click, the generic per-player dialog path (`cell-interactions/.../dispatch/interact.rs:125-149`) and the vendor store never run. A tag chain on the quartermaster (template 415, a vendor) would therefore break the armory store. Template 420 / spawn 13809 is a non-vendor soldier standing beside him. `REPO`.
- **Action order.** `remove_dialog_set` runs BEFORE `accept_mission` and `complete_mission` because a nested `mission_accepted`/`mission_completed` dispatch runs mid action list. In 10234 the offer binding is removed before the accept; in 10236 the turn-in binding is removed before `complete_mission`, whose nested 10233 rebinds the offer (an absent `remove_dialog_set` entry is a no-op, `executor/dialog/mod.rs:285` `entries.retain`).
- **`pin_interaction_target`** is called before tag dispatch (`interact.rs:163`), so `display_dialog` from a tag chain resolves its target. Monologues need no follow-up `dialog_choice` chain, so none is authored (a forged close or button cannot accept or complete anything).
- **Turn-in is closed by `complete_mission`.** `advance_step` force-completes A's objective and activates B but never completes the mission; B's objective is a turn-in and only `complete_mission` closes it (no `complete_objective` chain).
- **Cap.** After the third completion the 4th click runs 10234: the offer binding is removed, `accept_mission` is refused by the offer guard (Behavior), and `display_dialog 10729` still shows (the refusal returns from `accept_or_advance` only, `executor/mission.rs`; the action list continues). OPEN item 1 covers feedback.
- **`mission_status 10330 neq active`** is used instead of `not_active` because a mission that has been completed once reads `completed`, not `not_active`; only `neq active` keeps the offer open for repeats and the cap itself is enforced by the offer guard, not by a chain condition (there is no `repeats` condition type).

### Validation audit

- **Cap is server-side and per character.** `accept_mission` reads the player entity's own `(status, repeats)` (`lifecycle.rs:61-70`) and refuses `MISSION_COMPLETED if repeats > def.num_repeats` with `repeat_cap_reached` (`:95-96`), a WARN `mission_accept_refused` (`:101-118`) and `return false`. An absent def reads as `num_repeats` 0 (`:95`, `:115`): fail-closed, a completed run is not re-offered. The executor then skips persist and the `mission_accepted` event (`executor/mission.rs:61-77`). Rows are keyed `(player_id, mission_id)` (`base-methods/.../missions/mod.rs:222`), so a second character on the account has its own count (and there is no cross-character path to exploit; with a zero reward nothing is gained either way).
- **Counter integrity.** `repeats` is bumped only in `complete()` and `fail()` (`entity/src/missions.rs:102,112`) and carried across re-accept (`lifecycle.rs:128,153`). Nothing the client sends writes it.
- **Forged accept past the cap.** There is no accept wire. The only path is chain 10234 (interact_tag), reachable only after the range gate (`interact.rs:108`). Even a mis-gated chain hits the backstop at `lifecycle.rs:95`. Result: refused, state untouched, the 4th click still unbinds the offer and shows neutral dialog 10729 (the action list continues after a refused accept; `executor/mission.rs:61-77` returns from the accept action only).
- **Forged complete.** There is no complete wire. `complete_mission` runs only from chain 10236, whose conditions are `mission_status 10330 eq active` and `step_status 10385 eq active` (Frozen (d)). `Castle.Infirmary` entry is server-gated (the region test uses server position, `player/world/mod.rs:279`; the client floats are ignored `:66-71`), so step A to B cannot be skipped by a forged region packet from elsewhere, and a forged hint at the right place only does what walking there does.
- **Abandon does not reset the cap.** `abandon_mission` returns `None` unless `status == MISSION_ACTIVE` (`entity/src/missions.rs:252-255`): a COMPLETED record, including one at the cap, cannot be abandoned or overwritten. For an active attempt with `repeats > 0` it leaves a `not_active_record()` keeping `repeats` (`:256-260`, `:77-88`), saved with that count (`cell-content/.../lifecycle.rs:311-321`); at `repeats == 0` the row is deleted (`base .../mod.rs:180`), which loses nothing. An abandon only ever discards an uncompleted attempt, which never bumped the counter, so it neither spends nor refunds a run. Reaching the cap by abandon is impossible: an ACTIVE record at `repeats` 3 cannot exist, because the accept that would create it is refused at `:95`.
- **Survives relog.** Cell sends `MissionUpdate { repeats }` after every accept and complete (`persist.rs:70-80`, `executor/mission.rs:82-88`, `:185-188`); the base UPSERTs `repeats = EXCLUDED.repeats` (`base .../mod.rs:229`, guarded by `live_db_upsert_propagates_repeats_column_on_conflict`, `tests.rs:125`); restore assigns `mission.repeats = saved.repeats` (`mission_restore.rs:174`). Loaded status plus count means the 4th click after a relog is refused exactly as in-session.
- **Unreadable saved state cannot reset it.** While the saved missions are unreadable or still loading, accept, complete and abandon are refused (`lifecycle.rs:51`, `complete_direct.rs:31`, `lifecycle.rs:267`; `state_lock.rs:93-102`) and persist is refused (`persist.rs:101`, `base .../mod.rs:158`), so an empty tracker (which would read "never taken", repeats 0) cannot grant a fresh cap.
- **Double click / interleaving.** Clicks are processed one at a time on the cell; each re-resolves conditions. After accept, 10234 fails `neq active` and 10236 fails its step gate (Behavior row "Repeat click"). After the turn-in, `complete()` has run, so a second 10236 click fails `eq active`. No TOCTOU window that adds a run: the only interleaving is a disconnect between the cell mutation and the base UPSERT (Residual 1).

### Exploit analysis

- **Forged accept past the cap:** mitigated by `lifecycle.rs:95`, state-preserving.
- **Forged complete / skip the Infirmary:** mitigated by the 10236 state gates and the server-position region test.
- **Out-of-range remote click:** mitigated by `interact.rs:108`. OPEN item 6 of the mission leg claimed the opposite; it is corrected above (this tree has the gate).
- **Abandon to reset or refund the cap:** mitigated by the active-only abandon and the kept `repeats`.
- **Relog to reset the cap:** mitigated by the persisted counter and the load lock.
- **Second character farming:** per-character by design; zero reward, nothing to farm.
- **Replay of a stale packet:** no packet carries state that matters; the framing layer owns sequence dedup and the chain gates re-check live state each time.
- **Dupe / currency:** none (zero reward, no inventory path).

### Residuals

1. **Low: disconnect or DB failure between the cell bump and the base UPSERT.** A failed or lost `MissionUpdate` is logged only (`base .../mod.rs:255-264` `db_write_failed`; `abandon` is the same). The in-memory cap still holds for the session, but a relog reloads the older count, so a run can be regained. With a zero reward this is a counter inaccuracy, not an exploit. Do not add a reward to this quest without a transactional persist (a re-seal of Frozen (f) is already required by Economy).
2. **Low (engine, not 10330): `complete_mission_direct` has no status guard.** It runs `mission.complete()` on any tracked record (`complete_direct.rs:59-96`), so a `complete_mission` against a COMPLETED record would bump `repeats` again (the executor only suppresses the follow-up event, `executor/mission.rs:196`). For 10330 the only caller, 10236, requires `active`, so it is unreachable; a future chain that completes 10330 without an `active` gate would burn runs. Engine hardening suggestion for mission-systems (route redesign there): return early unless `status == MISSION_ACTIVE`.
3. **OPEN: refusal is silent to the player** (mission leg OPEN 1); unchanged. Security-neutral.
4. **OPEN: seed/XML `NumRepeats` drift.** The client display and the server cap come from different artifacts. Test s item 3 compares XML and row (2 vs 2); keep it.

## 3. Never twice

- `SOURCE` Redial: chains 1358 and 1359 need `step_status 708 4462 eq active`
  (seed 862, 880). After 708 completes, step 4462 is past. They do not re-fire.
- `SOURCE` Re-cross: chain 1360 needs `step_status 708 4469 eq active` (seed 907).
  `mission_completed` fires only on the real active-to-completed transition
  (`executor/mission.rs:190-197`), so 1398 cannot re-fire from a second crossing.
- `SOURCE` Relog: `player_loaded` restore chains (1361-1365) only repaint
  interaction flags. Nothing there fires `mission_completed`. Chains gated on
  `not_active` stay quiet on load (`event_dispatch/lifecycle/mod.rs:44-48`).
- `SOURCE` Abandon of 1664: `abandon_mission` removes the instance, so 1664 reads
  `not_active` again (`event_dispatch/mission.rs:159-168`). Chain 1398 is keyed on
  `mission_completed 708`, which cannot recur, so **1398 never re-grants after an
  abandon**. Abandon of 708 is refused: only an active mission can be abandoned
  (`missions/lifecycle.rs:368-385`). Chain 1399 is different; see section 4.
- `SOURCE` The accept itself refuses duplicates in two places. The offer guard
  refuses ACTIVE, FAILED-not-repeatable, and COMPLETED beyond the repeat cap
  (`missions/lifecycle.rs:89-97`). When it refuses, the executor skips the
  persist and the event (`executor/mission.rs:55-61`). The offer guard does
  NOT refuse a COMPLETED mission within `num_repeats`. For 1664 the
  `mission_status 1664 eq not_active` predicate is the only guard in that case.
  The brief cited `executor/mission.rs:55-56`; the actual refusal logic is in
  `lifecycle.rs:89-97`.

## 4. Travel failure

- `SOURCE` The accept is persisted before the transfer runs. The accept sends
  `MissionUpdate` through the executor (`executor/mission.rs:82-85`), and the
  transfer happens later in `crossing_tick`. The persist is best-effort: the
  in-process mutation is committed even if `MissionUpdate` fails to persist
  (`executor/mission.rs:86-92`; `work-packets.md:45-47`). `SOURCE` A refused
  transfer is handled at `gate_travel/tick.rs:82-94`: the movement lock is
  released and the player stays in Castle.
- `SOURCE` After a failed transfer, 1664 stays ACTIVE in Castle. The player
  can still reach Harset by redialing. The dial uses the persistent
  `grant_stargate_address 3` (seed 807, comment 809-811). No mission predicate
  is on the dial path that was read. `RECONSTRUCTION` The live redial path is
  not exercised here.
- `SOURCE` A redial and re-cross after a failed transfer fires `stargate_crossed`,
  but 1360 refuses (708 not active at 4469) and 1398 is never re-triggered.
  No chain re-fires.
- **Chain 1399 is frozen pending a coordinator decision.** It covers the case
  where the accept persist failed, and characters who finished 708 before 1398
  shipped:
  - Trigger: `player_loaded`, key `'Castle'`, scope `player`, `once` false
    (same key convention as chain 1361).
  - Conditions: `world 8`, `mission_status 708 eq completed`,
    `mission_status 1664 eq not_active`.
  - Action: `accept_mission`, target 1664, params `'{}'`, `delay_ms` 0.
  - Idempotent against ACTIVE and COMPLETED 1664: a second run finds 1664 ACTIVE
    and the offer guard refuses (`lifecycle.rs:90-91`), and the `not_active`
    predicate also blocks it. A completed 1664 fails the predicate.
  - **NOT idempotent against an abandon.** Abandon removes the instance (section
    3), so 1664 reads `not_active` with 708 still completed. The next
    `player_loaded 'Castle'` re-accepts 1664. Concrete inputs: a player whose
    transfer failed abandons 1664 in Castle and relogs in Castle; or a player
    abandons 1664 in Harset and later returns to Castle (the CS-04c return
    visits). No state in the tracker distinguishes "abandoned" from "never
    accepted", so no condition can close this gap without a new primitive.
  - The spec rule is to freeze the retry only if the accept is proven idempotent,
    otherwise write "1399 not needed". Proven idempotent only against active and
    completed. **Coordinator decision:** keep 1399 and accept the documented
    re-grant after abandon, or drop it ("1399 not needed": the failed-transfer case
    is covered by the redial, and the pre-CS-06 catch-up and persist-failure cases
    are left unhandled). CS-06a must not seed 1399 until this is answered.
  - Label: `RECONSTRUCTION`.

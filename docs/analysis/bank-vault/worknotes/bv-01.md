## Evidence

- **Dependency direction.** `cimmeria-wire` depends on `cimmeria-entity` (`crates/wire/Cargo.toml:16`); entity depends only on `cimmeria-common`. So entity cannot read wire's table, and the table moved down to `cimmeria_entity::inventory::bag_max_slots`. `cimmeria_wire::containers::bag_max_slots` is now a `pub use` of it, and `cimmeria-resources` still re-exports the wire path. No `Cargo.toml` changed, so no hakari run was needed.
- **Values.** `Constants.py` BAG_SIZES lists 17, 18, 19 and 20 all at 100. The packet names 17, 19 and 20; 18 is also 100 so the world-entry `onBagInfo` keeps declaring 18 at 100, as it did before. The declared list grew from 19 containers to 20 (20 is new; it is not movable).
- **Legal moves before BV-01** (from `move_/mod.rs` at the base): target must satisfy `bag_max_slots(target) > slot`, so targets 1-16; any source. Every other gate is per item (`item_allows_container`). Moving into 16 was refused only by seed data (no item lists 16). The only in-process caller besides the cell dispatch is right-click auto-equip (`use_instance.rs`), whose sources and targets are 1 and 3. So `Yes` = 1-15 keeps every legal move legal.
- **No seeded item allows both 1 and 15.** `resources.items.container_sets` groups on the seed: `{3,1,17}` 1470, `{2}` 801, `{17,15}` 752, `{1,17}` 713, the `{1,N,17}` equipment sets, `{}` 5, `{3}` 1. Query: `SELECT count(*) FROM resources.items WHERE 1 = ANY(container_sets) AND 15 = ANY(container_sets)` returns 0. So today no seeded item can move between 1 and 15 at all; the allowlist keeps both containers open, and `item_allows_container` decides per item. The 1 <-> 15 guard uses a synthetic item type with `{1,15,17}`.
- **Grant hazard created by the capacity change.** Loot (`cell-interactions/.../loot.rs:200-205`) and content `grant_item` (`cell-content/.../executor/inventory.rs:61`, via `item_container`) grant into `container_sets[1]` (`cell-catalog/.../spawner/loot.rs:70-73`). For the 752 `{17,15}` items that is 17. Before BV-01 `reserve_free_inventory_slots` found no slots in 17 (`bag_max_slots(17) = 0`) and the grant failed as "container full". With 17 at 100 the grant would have succeeded into the bank. BV-01 therefore adds an explicit refusal for grants into 17-20 (`grant/validation.rs::grant_container_refused`), which keeps the pre-BV-01 outcome.

## Design decisions

- `bag_max_slots` is a `const fn` in entity; `BAG_SIZES` is `&BAG_SIZES_TABLE`, a `[(i32, i32); 20]` built by a `const fn` loop over ids 1-20. The public name and type of `BAG_SIZES` did not change.
- `Inventory::with_bank_slots(n)` overrides container 17's declared size, clamped to `0..=bag_max_slots(17)`. The CHECK constraint already enforces 40-100; the clamp only stops a hand-edited row from declaring slots the server never accepts. `BANK_SLOTS_DEFAULT = 40` lives next to it.
- `PlayerLoadData.bank_slots: i32`, loaded as `smallint` and widened. `default_player_load_data()` uses 40.
- The resync (`send_full_inventory_resync`) now reads `bandolier_slot, naquadah, bank_slots` in one query **before** sending `onBagInfo`. Packet order and count are unchanged. If the row is missing, `onBagInfo` uses 40.
- The allowlist is `move_/container_policy.rs`: `Movable { Yes, No, VaultSession }` and `player_movable(i32) -> Movable`, both `pub(crate)` inside a private module (BV-03 may re-export them). `refusal(container) -> Option<Movable>` is the one place that decides BV-01 treats `VaultSession` as `No`; BV-03 changes that function (or its call sites) to consult the session.
- The target check runs before the slot-range check, because 17-20 now pass the range check. The source check runs after the `FOR UPDATE` read and rolls the transaction back first.
- Refusal feedback: `send_full_inventory_update` (the same `onUpdateItem` resync the success path sends), matching the legacy "mark dirty and flush" snap-back. No `onErrorCode`: none means "cannot move item".
- Log: `warn!(target: "bank", ..., reason = …, "move_rejected: …")`. Reasons: `source_container_not_player_movable`, `target_container_not_player_movable`, `source_container_needs_vault_session`, `target_container_needs_vault_session`. Grants: `grant_rejected`, `reason=grant_into_storage_container`. Both are WARN, which the leading `info` of `OTEL_FILTER` already exports, so no filter row was added (a row with no DEBUG emitter would be dead). A later packet that logs `bank` at DEBUG must add `bank=debug`.
- The other silent reject arms in `handle_move_inventory_item` (bad slot, quantity, occupied split) are unchanged, per #798's scope boundary.

## Review round (PR #872, Copilot)

- **Refusal resync ordering (moderate).** `refuse_move` read its inventory snapshot outside the `(player_id, 0)` move lock, so a move committing at the same moment could reach the client first and the stale refusal snapshot then undid it on screen. The snapshot is now read and sent inside a read-only transaction that holds that lock (`resync_under_move_lock` in `container_policy.rs`; `send_full_inventory_update_via` in `inventory/core/mod.rs` takes the executor). If the lock cannot be taken, the resync is still sent without it, so the snap-back always happens. `move_/mod.rs` is unchanged apart from a comment.
- **Guard:** `refusal_resync_waits_for_the_move_lock_and_sends_the_committed_state` (live-DB, concurrency). A second connection holds the move lock with the row moved from slot 0 to 4, uncommitted. The refused move must send nothing for 500 ms, and after the commit its one packet must equal the byte-exact `onUpdateItem` for slot 4. Proof: with `refuse_move` calling the old unlocked `send_full_inventory_update`, `live-db-test.sh refusal_resync` exits 100 and the test fails at "the refusal must wait for the move lock".
- **Residual:** the success path still reads its post-commit snapshot after the move lock is released (`move_/mod.rs`, after `commit`). Two successful moves can therefore still deliver snapshots out of order. Fixing that means reading the snapshot before the commit, inside the move transaction; it is a `move_/mod.rs` change, left for the packet that splits that file (BV-03).
- **Nits:** `crates/wire/src/containers.rs` now says it is a re-export of the entity table. The `bag_max_slots` doc now says the Team and Command vaults are sized per organization by the client (organizations audit A-15) and are declared at the ceiling until an org packet stores a size. The hand-typed capacity fixtures (entity tests, wire `bag_info.rs`) cite `deprecated/python/common/Constants.py:142-163`. Ticket numbers are gone from source and test comments.
- **Stale claim elsewhere:** `docs/analysis/organizations/README.md:41` still says "`bag_max_slots` is 0 for containers 19 and 20". That ledger belongs to the organizations campaign, so it is listed under integration edits rather than changed here.
- Commands: `lane.sh cargo fmt --all -- --check` exit 0; `lane.sh cargo clippy -p cimmeria-entity -p cimmeria-wire -p cimmeria-resources -p cimmeria-base-methods --all-targets -- -D warnings` exit 0; `lane.sh cargo nextest run` on the same four crates (no `DATABASE_URL`) 799 passed; `live-db-test.sh inventory:: player_load:: vendor:: trade::` 247 passed against `sgw_bank_bv01`.

## Review round 2 (PR #872, Copilot)

- **Refusal resync raced grants (moderate).** Round 1 sent a full-inventory snapshot under the `(player, 0)` move lock, but grants and vendor paths take `(player, container)` locks, so a grant could commit between that snapshot's read and its send and the older snapshot then hid the granted item. The refusal now resends only the refused item: `send_inventory_item_update_via` in `inventory/core/mod.rs` reads the player's rows through the canonical `INVENTORY_ITEM_SELECT` (left unchanged because a drift test pins it byte-for-byte against the player-load copy), keeps the one row and sends a one-element `onUpdateItem`. It is still read under the move lock (`resync_item_under_move_lock` in `container_policy.rs`), so a concurrent move of the same item finishes first. Grants never touch an existing row. An `item_id` the player does not own gets no packet beyond the `move_rejected` log. Nothing needed the full resync: the refused move changes no row, so the client only needs the dragged item back. `send_full_inventory_update_via` from round 1 is gone; `send_full_inventory_update` is back to reading through the pool, with the packet building shared in `send_update_item`. `move_/mod.rs` is unchanged.
- **Tests.** `refusal_resync_waits_for_the_move_lock_and_sends_the_committed_state` now compares against the one-item packet for the same item's committed slot. New: `refusal_resends_only_the_refused_item` (a second owned item; exactly one packet, byte-equal to `onUpdateItem` holding only the refused item at its unchanged `(16, 2)`), and `refusal_of_an_unknown_item_sends_nothing` (forged `item_id`: still logged, zero packets). New sentinels `0x7000_B160/B161`, `0x7000_B170/B171`, entities `0x7000_B1E5/B1E6`; `B140-B151` were already taken by the grant and player-load guards.
- **Revert proofs** (`live-db-test.sh allowlist_tests`, applied and reverted with `git checkout -- crates/`):
  - `refuse_move` sending the full inventory again: exit 100; `refusal_resends_only_the_refused_item`, `refusal_of_an_unknown_item_sends_nothing` and the concurrency guard fail.
  - Targeted resend without the move lock: exit 100; the concurrency guard fails ("the refusal must wait for the move lock"); the other five pass.
- **CAT-D-07.** The status line now says the refusal resends the refused item, and the "Trust violation" and "Evidence" sections are labelled as the state before BV-01, with the 17-20 "unreachable because `bag_max_slots` returns 0" sentences put in the past tense and pointed at the allowlist. `docs/gameplay/inventory-system.md` describes the one-item resend.

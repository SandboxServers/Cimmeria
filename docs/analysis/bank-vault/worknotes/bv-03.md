## Evidence

- **Items carry no mission flag.** `EItemFlag` (`enumerations.xml:1124`, mirrored in `cell-catalog/src/crafting/constants.rs:76-100`) has no mission bit. What marks a mission item is the mission bag: seeded mission types are exactly `container_sets = {2}`, and none of them lists 17. The server-authority review confirmed the counts on the seed.
- **The Rust `moveItem` had no stack merge.** The legacy `Inventory.py:388-395` combines a whole stack dropped on a same-type stack with room; the port always swapped. `inventory-system.md` listed "Stack merging" as done. The packet asks deposit and withdraw to cover merge, so BV-03 adds it for every container, as legacy parity; that is a behaviour change outside the vault too.
- **`cimmeria-cell-content` cannot reach `cimmeria-cell-interactions`**, which depends on it. The content executor must take the same verdict, so the range rule (`interact_range`, `InteractRangeFail`, `MAX_INTERACT_DISTANCE`) and the vault predicate (`vault_move_allowed`, `VaultReject`) moved down to `cimmeria-cell-world`. `cimmeria-cell-interactions` re-exports all of them at their old paths; the move is mechanical.
- **Base cell-message handling is one serial consumer** (`base/service.rs`, per the review). A verdict is therefore stale only by the queue delay, and a move is applied in the order its verdict was taken.

## Design: how the base learns the session (the cell-to-base message)

The session and the positions live in the cell; the move transaction runs on the base, and only the base knows the source row's container. So the cell attaches a **verdict to every forwarded request**, as `bv-02.md` recommended, rather than the base asking back. This follows the existing cell-to-base pattern of self-contained request messages, adds no round trip, and needs no base-side session mirror that could go stale.

- **Type.** `cimmeria_wire::cell::vault::VaultAccess` is `Open { scope, banker_id, distance }` or `Closed { reason, banker_id, distance }`. `VaultAccess::NO_SESSION` is the closed default.
  - `opens_personal_vault()` is true only for `Open { scope: Personal }`.
  - `personal_vault_refusal()` gives the label: the check's reason, or `vault_scope_mismatch` for an org session.
- **Computed by** `cimmeria_cell_world::cell::space_manager::vault_access(entity_id, space_mgr)`, which runs `vault_move_allowed` at that moment:
  - the session is open, and was opened in the player's current space;
  - with a Banker: the Banker exists, is in the same space, and is within `MAX_INTERACT_DISTANCE` (5), the same `interact_range` rule the opening `interact` passed;
  - a GM `.bank` session (`banker_id = None`) skips proximity;
  - the result records `banker_id`, and `distance` whenever there is a Banker.
- **Carried on** four messages:
  - `CellToBaseMsg::MoveInventoryItem` (`moveItem`);
  - `UseInventoryItem` (`useItem`);
  - `RemoveInventoryItem` (`removeItem`, content `RemoveItem` by instance, `gmRemoveItem`);
  - `RemoveInventoryItemByType` (content `RemoveItem` by type, which always sends `NO_SESSION`: see below).
- **Freshness.** It is taken per request, whether or not the request touches 17 (two map lookups). A drag after walking away carries `banker_out_of_range` with the distance; walking back re-opens it. `cell-methods` `inventory/tests/vault_verdict.rs` pins this through the real dispatchers.
- **Applied by the base** only where 17 is touched: at the target end before the transaction, and at the source end after the `FOR UPDATE` source read. `player_accessible` applies it for use and removal. The in-process `handle_move_inventory_item` (right-click auto-equip, 1 and 3 only) passes `NO_SESSION`. The cell path uses `handle_move_inventory_item_with_vault`.

## Other design decisions

- **Order inside a vault move:**
  1. the allowlist and verdict at both ends;
  2. `account_id` and `bank_slots` read in the move transaction;
  3. slot below `bank_slots`;
  4. the mission-item rule (a deposit from outside 17);
  5. `item_allows_container`;
  6. the occupant and the shape;
  7. for a swap out of the vault, the occupant entering 17 passes the mission rule and `item_allows_container`.
  - The bank checks run before `item_allows_container`, so a seeded mission item (`{2}`) gets the explicit `mission_item_not_bankable`, not a generic refusal.
  - For 17 the pre-transaction range check keeps only the lower bound; a slot at 100 or more is refused in the transaction as `target_slot_beyond_bank_slots`.
- **`bank_slots` is a plain read**, with no row lock. It only grows (BV-05), so a stale value can only refuse a slot the player is about to own. This is an invariant BV-05 must keep (see Known gaps).
- **Merge** needs the same type, room under `max_stack_size` (`checked_add`), and the same `bound`, `durability` and `charges`. A bound stack merged into an unbound one would become sellable, tradable and mailable (review finding 1). A partial merge is allowed, which legacy left unimplemented. A whole merge deletes the source row, and `after_commit` sends `onRemoveItem` for it before the resync. `InventoryItemMoveApplied` names the moved instance, which is the source for a merge.
- **Visible refusals.** Every bank refusal goes through `refuse_move`: `move_rejected`, then a `CHAN_FEEDBACK` line (`send_feedback_line`), then BV-01's one-item snap-back under the move lock and row lock. Non-vault silent rejects (bad slot, split onto an occupied slot outside the vault) are unchanged, per #798's scope boundary.
- **Reason names.** BV-01's `source/target_container_needs_vault_session` are retired: the vault refusals now carry the verdict's own label (`no_vault_session`, `banker_out_of_range`, and so on) plus `vault_end=source|target`. That gives one stable `reason` per cause, which the catalog asks for (see Integration edits).
- **Use and removal.** `player_accessible(container, &vault)` sits beside `player_movable`: 1-15 always, 17 only with `opens_personal_vault()`, never 16 or 18-20. The by-type search binds `container_id = ANY(accessible_containers(&vault))`.
- **Content by-type removal never searches 17** (`NO_SESSION`), even with the window open. This narrows the packet's "17 only with a vault session" for that one caller. Otherwise whether a turn-in eats a banked copy would depend on UI state, and D-BV04 says the bank is storage only (review nit, adopted).
  - Content by instance takes the live verdict: it consumes the item the player just used, which was itself verdict-checked.
  - `gmRemoveItem` takes the GM's own verdict, so a GM removes from their vault only with `.bank` open.
- **`reserve_free_inventory_slots`** bounds 17 by `bank_slots`, read in the caller's transaction (`reservable_slots`). No caller reserves 17 today; grants are refused earlier.
- **Spans.** An INFO `bank.move_item` span wraps a move whose target is 17 (from the start) or whose source is 17 (from the source read on).
- **BV-02 nit.** `log_player_entity_missing` (`bank/open.rs`) now logs `target: "bank"`, `event = "vault_open_rejected"`, `reason = player_entity_missing`, with `entity_id` and `banker_id` only. Its `LogCapture` pin was rewritten to assert the `bank` row and the absence of `account_id` and `player_id`.
- **File split.** The first commit, `b28ef07f6` (merged on its own as #927, so the rebase dropped it), is the pure split: `move_/mod.rs` was 694 lines, and the post-commit side effects moved into `after_commit.rs`. The feature then split the rest along its seams:
  - `mod.rs`: entry points, target checks, locks, source read (464 lines);
  - `finish.rs`: vault rules, shape, commit;
  - `apply.rs`: the four writes;
  - `bank_rules.rs`: refusal reasons and lines, the `bank_slots` and mission reads, `move_accepted`.

## Server-authority review (`server-authority-enforcer`, read-only)

Verdict: conditional, with no blocker and no bypass found. The client supplies only `item_id`, container, slot and quantity; the verdict is never read off the wire.

- **Merge ignored `bound`** (should-fix). Fixed: the merge needs equal `bound`, `durability` and `charges`; otherwise the move swaps. Guard: `a_bound_stack_does_not_merge_into_an_unbound_one`.
- **The verdict had no scope** (should-fix, latent until the org vaults). Fixed: `Open { scope }`; only `Personal` opens 17 (`vault_scope_mismatch`), for moves and for use. Unit guards in `wire` and `container_policy`.
- **Silent vault refusals** (should-fix): `item_allows_container`, split onto an occupied slot, occupant not allowed, slot 100 or more. Fixed with visible refusals and three guards in `vault_refusal_tests.rs`. The missing-player-row case stays an error log, because it is an infrastructure failure.
- **Nits:**
  - Content by-type removal reaching an open vault: adopted as `NO_SESSION`, with a guard.

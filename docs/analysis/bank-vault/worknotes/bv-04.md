## Evidence

- **Room geometry.** Point set 2032 `Castle_Cellblock.Region1` has corners A(-347.17, -230.14), B(-327.67, -240.70), C(-318.89, -224.51) and D(-338.39, -213.94); respawner 8 is at (-334.23, 73.472, -228.03) (spawnlist seed header, line 872 onward). The hub line runs 3 units in from the A-B wall and is full up to corner B: the pet trainer 450 is already 2.1 units from the B-C wall. Crafting CR-11 (PR #909, open) puts 410-414 along the A-D side, around (-341.7..-336.7, -226.3..-217.2).
- **Banker name.** `texts.sql` ships `DN_npc_OmegaSite_Banker` (29462, "Storage Officer") and `DN_npc_Harset_Banker` (29463, "Storage Lotaur"). A new moniker cannot render, so 370 reuses 29462.
- **Banker body (A-34).** `GLB_Components.Banker` is an interaction marker component (interaction 1, minimap icon `Bank`) valid on every playable body set and the four terminal body sets. No seeded template pairs a standing-terminal body set with a verified static mesh, so 370 takes a human body the server already spawns in world 12: template 170's SGC-uniformed human female, without its SMG.
- **`player_name` is unique** (`sgw_player_player_name_key`, `db/sgw/_primary_keys.sql:55`). The first cut had a `target_ambiguous` reason; its live-DB fixture could not insert two characters with one name, so the reason was dropped: a name names at most one character.
- **`gmGiveItem` cannot take a container.** Its wire signature is fixed by the def (`WSTRING DesignId, INT32 Quantity`), and the base's `GrantItem` refuses 17-20 by design (BV-01 `refuse_storage_grant`, D-BV04). A GM grant into 17 would need a new `CellToBaseMsg` field or variant, a bypass of that guard, and a capacity check against the player's own `bank_slots` in `grant_item.rs`, which is already 681 lines and sits in the inventory tree BV-03 is changing. Not cheap, so skipped (see "Known gaps").

## Design decisions

- **Placement.** Spawn 470 at (-325.92, 73.472, -231.18), heading -1.0739 (faces the room centre (-333.03, -227.32), yaw = atan2(dx, dz)). That is the middle of the B-C wall, 3 units in. Distances in XZ: 8.89 to the respawner, 6.28 to 450, 6.56 to 404, 8.03 to 403, 12.7 or more to 400-402, 16.2 or more to every `CraftHub_*` spawn; 9.2 to the A-B and C-D walls. The A-B line has no free slot (the one nearest the respawner is empty on purpose), and the C-D wall holds the exit threshold.
- **Tag `DebugHub_Banker`.** The hub doc lists it as a hub NPC, so `debug_hub_dispatch_tests::staged_hub` now counts seven `DebugHub_*` spawns and the Banker is exercised through the real click path there. Crafting uses `CraftHub_*`, so its PR does not touch that count; a later campaign that adds a `DebugHub_*` NPC bumps it.
- **Template 370.** `interaction_type = 2` (`INT_Banker`) only, `vault_scope = 'personal'` written explicitly, faction 1, class `mob`, event set 570, level 1, no ability set, trainer list, vendor list, loot table, chain or dialog. Anything that runs before the static dispatch would claim the click (BV-02's precedence note), and faction 10 would let a death overwrite the Banker interaction.
- **`.bankdump [name]` is a base round trip.** The cell has no pool. It forwards `CellToBaseMsg::Bank(BankCellToBase::GmDump { entity_id, account_id, player_id, subject })`; the base reads `sgw_player` and `sgw_inventory` (container 17 only), sends one feedback line per row and logs the outcome. `Bank` is a nested family enum (the org and chat pattern), so BV-05/BV-07 add variants in `bank_cell_to_base.rs`. The name goes to the base unresolved and is matched exactly against `sgw_player.player_name`, so an offline character's vault can be dumped, which is what a support question needs. With no name, the subject is the GM's own `player_id`.
- **The listing.** A summary line with the name, player id, item count and `bank_slots`, then `slot N: <name> (type T) xS [item I]` per row in slot order, capped at 100 lines plus "... and N more". A row in a slot at or past `bank_slots` is flagged `(beyond bank_slots)`: the client's window cannot show it, which is the usual reason a GM dumps a vault.
- **GM gate.** `.bankdump` is a registered `.`-command, so the channel gate on the server-side `access_level` applies as for `.bank`. A non-GM gets the generic PT-07 "is a GM command" line (never broadcast) and a `gm_action reason=not_gm` row on `bank`.
- **Levels.** The catalog makes `gm_action` INFO. Refusals the GM caused (`target_not_found`, `caller_not_player`, `not_gm`) stay INFO. Refusals the server caused (`db_unavailable`, `query_failed`, `base_channel_closed`) are WARN with an `error` field, per the negative-logging convention for infrastructure seams.

## Known gaps

- **No GM grant into the vault (`give_to_container`).** Skipped as not cheap (see Evidence): the def fixes `gmGiveItem`'s arguments, and a `.giveitem ... 17` would have to bypass D-BV04's grant guard and check capacity against `bank_slots` inside `grant_item.rs` while BV-03 is changing the inventory tree. A tester fills the vault by dragging from the main bag once BV-03 lands. The catalog's `give_to_container` action value is therefore unused.
- **Placement is unchecked in the client**, like the rest of the hub: there is no navmesh or occluder data for the room. Check in the client that 470 stands clear of the stasis pods.
- **`.bankdump` does not show the org vaults (18-20).** They have no data until BV-07.
- **`entity_templates_template_id_seq` footer** is still `setval(..., 304)` on main; crafting CR-11 (#909) rewrites the footers with a 399 floor, which covers 370. Not touched here, to keep the two PRs disjoint.

## Evidence

- **No seeded template carries `INT_BANKER` (value 2).** A parse of every `entity_templates` seed row found none, so the new derivation changes no existing NPC. BV-04 adds template 370.
- **The seed inserts name their columns.** Every `INSERT INTO entity_templates` lists columns, so a new column with a DEFAULT needs no seed edit.
- **A space change always builds a new `CellEntity`.** The only `entity_space.insert` sites are `insert_entity_into_space` (players), `spawn_npc` and `spawn_npc_from_record_into`, and each constructs a fresh entity. Cross-world, `.goto`, gate travel and logout all go through `destroy_entity` / `disconnect_entity`. So "clear on space change / logout" holds by construction: the session is a field on the entity. `destroy_entity` now logs `vault_session_cleared reason=entity_destroyed` so the end is visible.
- **`interact` pins in two places.** `cell-methods .../interaction/interact.rs` (the outer dispatcher, after its range gate) and `cell-interactions .../dispatch/interact.rs` (`handle_interact`, the fall-through). Both now call `interactions::pin_interaction_target`, which calls `CellEntity::pin_interaction_target`. The other `last_interaction_target =` writes are tests and the `.bug` bookmark read.
- **`handle_interact`'s own gate checks distance but not space.** The same-space check lives in the outer `interact_target_in_range`, which always runs first on the wire path. The smoke tests drive the wire path.
- **Feedback channel.** `onErrorCode` has no Lua consumer (AT-E1 §2, quoted in `respec_feedback.rs`), so refusals use a `SYSTEM` line on `CHAN_FEEDBACK` (9) via `cimmeria_wire::cell::chat::serialize_on_player_communication`, the shape the console and chat refusals use.
- **`onVaultOpen` args** are `INT32 EntityId, VECTOR3 Position` (`docs/protocol/client-method-dispatch-table.md:253`, audit A-02); `ON_VAULT_OPEN = 106` in `crates/wire/src/cell/client_methods/player.rs`.

## Design decisions

- **Banker precedence.** `INT_BANKER` wins over the vendor bits in `static_interaction_for_flags`: the banker bit names one role, the nine vendor bits are store tabs a quest giver can carry as decoration. Anything that answers before the static dispatch still wins (trainer list, `interact_tag` / `interact_template` chain, per-player dialog bind, `INT_DHD`). Documented on the function and in `interaction-flags.md#bankers`. `vault_scope` is read only under `INT_BANKER`.
- **Types.** `VaultScope`, `VaultSession` exactly as the ledger contract, in `crates/entity/src/cell_entity/vault_session.rs`, re-exported from `cell_entity`. `VaultScope: TryFrom<&str>` refuses unknown text; both loaders turn that into `sqlx::Error::ColumnDecode` instead of defaulting (the column CHECK makes it unreachable). `SpawnRecord.vault_scope` is a plain `VaultScope`.
- **`bank` is a directory** (`interactions/bank/mod.rs` + `tests.rs`), not a flat `bank.rs`: BV-05 (expand) and BV-07 (org arms) will add siblings.
- **`vault_move_allowed(player: &CellEntity, space_mgr: &SpaceManager) -> Result<(), VaultReject>`**, exported as `cimmeria_cell_interactions::cell::interactions::vault_move_allowed`. Pure (no logs, no sends). Rules: a session, opened in the player's current space; with a Banker, `interact_range(player, banker)` must pass (exists, same space, within `MAX_INTERACT_DISTANCE` = 5); a GM session (`banker_id: None`) skips proximity. It does not look at `scope`: the caller knows the container. `VaultReject::reason()` gives the `move_rejected reason=` labels: `no_vault_session`, `vault_session_other_space`, `banker_gone`, `banker_other_space`, `banker_out_of_range`, `player_missing`.
- **One range rule.** `interact_target_in_range` was split into the pure `interact_range(...) -> Result<(), InteractRangeFail>` plus its log lines, so the vault predicate reuses the exact rule without logging "interact: too far away" for a move.
- **`.bank` for a non-GM** is consumed by the chat interceptor and answered ("`.bank` needs GM access. Visit a Banker to open your vault."), logging `vault_open_rejected reason=not_gm`. This is the one exception to "a non-GM's `.`-text is ordinary chat"; `.banker` and every other `.`-line from a player still broadcast. Documented in `dev-console-channel.md` §1.
- **Log target `bank`, D-BV19 names.** The first cut logged `vault_open` / `vault_session_cleared`; after the owner's telemetry rule (D-BV19, PR #876) those became the catalog events below. `bank=debug` is in `OTEL_FILTER` (BV-01 added no row because it logs WARN only), pinned twice: the source scan (`every_source_target_reaches_signoz_at_its_level`, with `("bank", DEBUG)` and `("bank", WARN)` in `scan_finds_known_targets`) and the explicit `bank_target_reaches_otlp_at_debug_and_warn`.
- **Out-of-range Banker clicks are refused visibly.** A too-far click on any other NPC stays a silent drop; on a Banker, `reject_banker_out_of_range` (called from both range gates) logs `out_of_range` with the distance and sends a chat line. The project rule is visible feedback on every refusal, and the catalog names the reason.
- **`logout` vs `space_change`.** `disconnect_entity` ends the session with `logout` before it calls `destroy_entity`; any other player destroy (cross-world, GM transfer, gate trip) is labelled `space_change`. `DisconnectEntity` is sent by `logOff`, by the client-timeout path, and by gate travel when it abandons a trip (`base-world-entry/.../gate_travel/mod.rs:82`), so an abandoned trip reads `logout`.
- **The player lookup miss is not a `bank` event.** The merged catalog (#876) fixes `vault_open_rejected`'s reasons to exactly `out_of_range`, `org_vault_not_available`, `not_gm` and `banker_missing`. A miss on the player's own entity has no player to tell, so it is a WARN negative log on the crate's own target (`cimmeria_cell_interactions`, exported by its `OTEL_FILTER` row) with `reason=player_entity_missing`, `entity_id` and `banker_id`; `.bank` answers the GM with a line when it happens.

## Where BV-03 attaches the verdict

The client's `moveItem` reaches the cell as `MOVE_ITEM` (`crates/cell-methods/src/cell/cell_methods/inventory/dispatch.rs`), whose handler `handle_move_item` (`inventory/item_ops.rs:87`) decodes the args and forwards `CellToBaseMsg::MoveInventoryItem` to the base. The base's `handle_move_inventory_item` (`crates/base-methods/.../inventory/move_/mod.rs`) is where BV-01's `player_movable` returns `Movable::VaultSession`, and only the base knows the source row's container. The cell holds the session and the Banker positions. Recommended shape: `handle_move_item` calls `vault_move_allowed(player, space_mgr)` on every move and adds the verdict to `MoveInventoryItem` (for example `vault: Result<(), &'static str>` carrying `VaultReject::reason()`); the base treats `Movable::VaultSession` as allowed only when that verdict is Ok, and logs `move_rejected reason=<label>` otherwise. Computing it unconditionally is cheap (no allocation, one or two map lookups) and avoids the cell guessing which containers the move touches.

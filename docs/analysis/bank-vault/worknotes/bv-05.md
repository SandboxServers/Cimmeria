## Evidence

- **No cell mirror of `bank_slots`, and the cell has no pool.** The Banker click cannot know the size without asking the base, so the offer is a quote round trip (`ExpansionQuote`, then `OfferExpansion`). The quote also supplies the replay key.
- **A mid-session `onBagInfo` is the legacy shape.** `Inventory.py:549-556` re-sends the whole bag list when a size changes, without re-sending items. The same-world resync also sends it mid-session. BV-05 sends the full 20-entry array with 17 at the new size.
- **#943 quarantined every Cimmeria-authored dialog override** after a map-load crash, with the bad field still unknown. The suspects include screen ids 200000+ and button type 4, both of which 60110 has. See "Known gaps".

## Design

**The quote.** `open_personal_vault` (Banker or `.bank`) ends with `request_expansion_quote(entity_id, banker_id.unwrap_or(entity_id))`. The base (`handle_expansion_quote`) reads `bank_slots`, `naquadah` and the next step's price in one `LEFT JOIN` on `bank_expansion_price`:

- **below 100, with a price:** it sends `BankBaseToCell::OfferExpansion { from_slots, price, speaker_id }`;
- **at 100:** no offer, and the line "Your vault is already at its full size of 100 slots.";
- **price row missing:** no offer (WARN).

**The offer.** `offer_vault_expansion` records `ExpansionOffer { from_slots, price }` on the vault session only if the session is still the one the quote was for: the same character, a `Personal` scope, and the same speaker (the Banker, or the player's own entity for GM). Otherwise it logs `expand_offer_dropped`. It then sends `onDialogDisplay(speaker, 60110)` through `send_dialog_display`, which records the #479 offer, plus a chat line naming the size and the price. The chat line is needed because the cooked text cannot carry a seed value.

**The answer.** `handle_dialog_button_choice` routes dialog 60110, after the #479 gate, to `answer_vault_expansion`, never to a content chain:

1. Only `ButtonID 8` (`VAULT_EXPAND_BUTTON_ID`) buys. `-1` and any other id log `expand_dismissed`.
2. The answer takes a **fresh** `vault_access` verdict, the same rule as every bank move, and **takes** the offer (one-shot).
3. It forwards `BankCellToBase::Expand { offer, vault }`.

**The purchase** (`handle_expand`, `persist.rs`):

1. It refuses unless `vault.opens_personal_vault()`, with the verdict's own label as the reason. Then it refuses unless an offer is present (`no_offer`).
2. One statement:

   ```sql
   UPDATE sgw_player AS p
      SET bank_slots = p.bank_slots + 10, naquadah = p.naquadah - x.price_naquadah
     FROM resources.bank_expansion_price AS x
    WHERE p.player_id = $1 AND p.bank_slots = $offered_slots AND p.bank_slots < 100
      AND x.to_slots = p.bank_slots + 10 AND x.price_naquadah = $offered_price
      AND p.naquadah >= x.price_naquadah
   RETURNING p.bank_slots, p.naquadah, x.price_naquadah
   ```

   - The offered size is the replay key. A concurrent duplicate waits on the row lock, re-evaluates against the committed row and matches nothing.
   - The price key means a player is never charged a price they were not shown.
3. A zero-row result is classified by a follow-up read, in this order: `replay` (the size moved), `at_ceiling`, `price_missing`, `price_changed`, `insufficient_cash`, `row_changed` (everything holds now, so the row changed between the two statements).
4. On success it sends `onBagInfo` (full array, 17 at the new size), `onCashChanged` and the line "Your vault now has N slots. You paid P naquadah." A refusal sends a line for its reason.

**The grow-only invariant** (BV-03 known gap). This holds by construction and is documented in the `persist.rs` module docs:

- `persist_expansion` is the only writer of `bank_slots`;
- its only assignment is `bank_slots + 10`;
- it is capped in the statement (`< 100`) and by both schema CHECKs (`bank_slots_sanity`, and `to_slots` between 50 and 100 on the price table).

The unlocked reads in the move transaction and `reservable_slots` therefore stay safe.

**Addressing.** Results go to the **character**: `Client` finds the session whose `active_player_id` is the buyer, and sends through `send_to_current_player(player_id)`. A buyer who gated or logged off gets nothing; world entry re-declares the vault from the database. A recycled entity id never receives another player's vault size or balance.

## Other design decisions

- **Dialog ids:** the bank takes dialogs 60110-60119 and screens 200010-200019. Screen 200010 carries one Generic 1 button with ButtonID 8 and speaker 0, because any Banker, or the GM's own entity, speaks it.
- **The ceiling line is kept.** The review suggested dropping "vault is full" on every visit at 100. I kept it: the packet requires feedback at 100, and so does UAT step 11.
- **Reason names:** the verdict refusals use the verdict's labels (`no_vault_session`, `banker_out_of_range`, ...), the same pass-through BV-03 uses for `move_rejected`. They replace the catalog's `no_session` and `out_of_range` (see "Integration edits").
- **`price_missing` has no live-DB test.** It needs a seed gap, which a shared test database must not get. The classification is unit-tested, and the log row and the line are pinned on `reject` and `quote_warn` directly.

## Server-authority review (`server-authority-enforcer`, read-only)

Verdict: ship, with two should-fixes and no blockers. No lying-client scenario gives a double charge, a free step, a step past 100, a shrinking vault, or a purchase without a valid session and proximity. The scenarios checked were a forged or replayed choice, a double click, two offers, a stale quote, a walk-away, a re-pin, a GM session, gate travel mid-flow, and concurrent moves or cash writes. The client supplies only `dialog_id` and `button_id`.

- **Should-fix 1: results addressed by a bare `entity_id`.** A recycled id could receive the buyer's balance. Fixed: sends go to the character, through `send_to_current_player`. Guard: `a_recycled_entity_id_receives_nothing`.
- **Should-fix 2: any `button_id` but `-1` bought.** Fixed: only ButtonID 8 buys. Guard: `only_the_expand_button_buys`. This departs from the packet's wording "the server ignores `button_id`". That wording described today's gate, and the purchase is stricter than the gate.
- **Nits:**
  - `row_changed` split from `replay`: adopted.
  - The price key: adopted, as `price_changed`.
  - Drop the ceiling line: not adopted (see "Other design decisions").
- **Test gaps it named:**
  - recycled id: closed;
  - an unexpected button: closed;
  - `row_changed` as a unit case: closed;
  - a cell-to-base chain test for a stale offer: covered by the base's replay guard, not added end to end.
- **Out of scope:**
  - `vault_access` checks that the pinned Banker id exists and is in range, not that it is still a Banker, so an id reused by another NPC passes. This dates from BV-02/03.
  - A dialog closed with X leaves 60110 in the offered set until the next open, which is harmless.

Its note is committed at `.claude/agent-memory/server-authority-enforcer/project_bank_vault_bv05_review.md`, annotated with the fixes.

# HT-16: coder-context ruling

> **Type:** Reference · **Audience:** The harness-tuning orchestrator, the HT-17a/HT-17b coders and reviewers, HT-19 · **Date:** 2026-11-01 · **Author:** architect

## Ruling

HT-17 is a code packet, split in two:

- **HT-17a**, a commit-before-cap note plus context habits. It adds a `PostToolUse` hook, `.claude/hooks/coder_context_note.py`, wired in `packet-coder.md`'s frontmatter, so it runs for packet-coder only. On the first tool call whose request carries at least 75,000 tokens (and fewer than the cap's 90,000), the hook adds one note: finish the current step, run its check, and commit the passing files as `(part N)` before any other read or edit. It never denies a tool and never asks for a report (D-HT3). It reads the cap value and never changes it. One new packet-coder bullet adds the note and two habits: Grep with `files_with_matches` first, give `content` a `head_limit` of 30 or less, and never re-read a range.
- **HT-17b** adds the measurement. `metrics coder-context` gets commit, passing-uncommitted-check, whole-read, re-read and unbounded-Grep shares, plus a continuation stop rate. The packet records the baseline from the October window in its commit body, so HT-19 can re-measure both the effect and the cause.

The stop rate is not where the money is. A stop becomes cheap when the coder's passing work is already committed when the cap fires. Today 74% of stopped coders have committed nothing.

Stop rate by kind: first sessions 22.8% (202/885), continuations 19.8% (17/86), fix passes 13.7% (35/255). Packets with lane calls (Rust) 18.1%, without (Python, docs) 27.0%. By brief-length quartile: 15.9%, 16.8%, 20.6%, 28.9%.

Continuations (baseline): 86, 6.67M fresh tokens, median 75.2k fresh each, about a full session. A continuation stops as often as a first session.

Final context of not-stopped coders, per 5k bin from 50k to 90k: 78, 65, 62, 64, 67, 63, 68, 55. That is flat, at about 12 coders per 1k tokens of final context. So a habit that saves S thousand tokens per coder turns about 12×S stops into finishes, if the stopped coders' "needed" context continues the same density past 90k.

What the numbers say:

1. **Stopped coders lose passing work at the wall.** 40.6% of them ran a check that passed over uncommitted edits and never committed afterwards. 80% of those checks ran past 75k, at a median of 82k. The rule in `packet-coder.md` on `main` during the window already said "commit only work whose checks pass" and "past about 90k, stop". But it fired at the same 90k where the user-level cap denies every tool, including `git commit`. The coder needs the cue before 90k, not at it. Candidate 6's condition ("stopped coders hold passing uncommitted work") is met.
2. **Thinking fills most of a stopped coder's context.** Visible tool inputs and results explain only 38% of context growth. Output tokens (37k median), most of them thinking that the transcript doesn't keep as text (0 thinking chars stored), make up the rest. No HT-16 candidate touches it.
3. **Reads and Greps are second.** The unbounded `content` Greps are about 19% of a stopped coder's result chars (72.7% × 26.7%), about 4.5k tokens at the median. Re-reads are 22% of Read chars, about 2.6k. The text "Read only the line ranges you need" was already in the agent for the whole window, and 36% of Read chars still came from whole-file reads, so prose rules move Haiku only part of the way.
4. **Packet docs are a small share.** `docs/analysis` reads are 13.6% of result chars (about 3.2k tokens). Inlining more into packets saves part of that, but raises the first context of all 1,209 coders.

## Rejected options

| Candidate | Ruling | Reason |
|---|---|---|
| 1. Packets inline more | Rejected | `docs/analysis` reads are 13.6% of stopped result chars, about 3.2k tokens. Most stopped-coder reads are `crates/` (31.2%), the code the coder edits, which no packet can inline. More inline text also raises the first context of every coder, and 79% of coders do not stop. The skill already asks packets to carry their contract excerpts. |
| 2. Read guidance (offsets only, no whole-file `docs/analysis` reads) | **Accepted in part, folded into HT-17a** | The Grep habit has the larger, cleaner signal (72.7% of Grep chars come from unbounded `content`), and `head_limit` is a parameter, not a judgment. Re-reads (22%) get one sentence. No new `docs/analysis` rule: it is a small share, and the existing "line ranges" rule already covers it. |
| 3. PostToolUse note on a big Read | Rejected | It speaks after the tokens are spent; the median stopped coder makes 0 reads over 20k chars; and F13/D-HT13 already ruled out a big-read guard. No new evidence. |
| 4. Smaller packets (a sizing rule) | No new rule | The stop rate climbs with brief length (15.9% → 28.9% across quartiles), so the campaign-packet skill's ~40k-working-token sizing stands. But brief length is a proxy, not packet size, and no data separates the two. The architect keeps applying the existing rule. |
| 5. No change | Rejected | A continuation costs a median 75.2k fresh, about a whole session, and stops 19.8% of the time. 81% of stopped coders leave uncommitted edits that the next coder must re-verify against the spec. |
| 6. Soft note at about 75k, packet-coder only | **Accepted (HT-17a)** | The evidence condition holds (finding 1). The note asks for a commit of work that has already passed, which D-HT14 already allows. It never denies and asks for no file (D-HT3). |
| D-HT5 lever: packet-coder `effort` (outside the HT-16 list) | Deferred | Thinking is the largest filler (finding 2), but the window gives no quality evidence. `effort: medium` has been set since 2026-10-10, so there is no before and after. A lower effort could raise `reason=checks` returns, and each costs a Sonnet implementer. If the orchestrator wants it, it is a separate A/B packet after HT-19 (HT-F2). Not an owner call: D-HT5 lists it as an architect lever. |

## Wiring choice

The hook is wired in `packet-coder.md`'s frontmatter `hooks:` (precedent: `orchestrator.md`), not in `settings.json`. A settings hook would start one Python process per tool call in every session. F13 rejected a Read guard for that cost. The frontmatter hook runs only inside packet-coder. Risk: frontmatter hooks inside a *subagent* have no live proof in this repo yet. F12's owed proof is for the main thread. So:

- The script also filters on `agent_type` when the payload carries it. Moving it to `settings.json` later is a one-entry change.
- HT-U2 gains a step: the capped coder's transcript holds `coder_context_note:` before `Context cap reached`.
- If HT-U2 or HT-19 shows the note never fired (`stopped_committed` unchanged and no marker), the orchestrator adds a follow-up packet that moves the entry to `settings.json`.

## Targets (README § Targets)

| Metric | Baseline | Target | Measured by |
|---|---|---|---|
| packet-coder context-stop rate | 20.6% (249/1,209, C1 rule) | ≤ 18.5% | `coder-context` `groups.all.stop_rate` |
| Stopped coders with at least one commit | 26.5% (HT-16 scratch; HT-17b's `Baseline:` line is the reference) | ≥ 60% | `groups.stopped.committed_share` |
| Stopped coders with a never-committed passing check | 40.6% (HT-16 scratch; HT-17b's line is the reference) | ≤ 15% | `groups.stopped.pass_uncommitted_share` |
| Median fresh tokens per continuation | 75.2k | ≤ 65k | `median_continuation_fresh` |
| Grep chars from unbounded `content` (stopped) | 72.7% | ≤ 40% | `groups.stopped.grep_unbounded_share` |

The stop-rate target comes from the flat final-context density. The Grep and re-read habits save about 2-3k tokens per stopped coder, which turns about 25-35 of 249 stops into finishes: 249 → about 220, or 18.2%. The target rounds that up. HT-19 judges the ruling mainly on the two commit rows. If those are met and the rate is not, the note worked and the habits did not.

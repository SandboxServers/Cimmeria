## What the fork changed (verified via GitHub compare API)

The fork is 15 commits ahead and 295 behind upstream master (most recent fork commit is a merge of upstream on 2026-07-08; the fork adds are from 2026-03-17..19). 35 files. Everything is one feature: an **AI sidecar** for task prioritisation.

- `ai_sidecar/` (FastAPI + Pydantic v2 + openai SDK, Python 3.11) with `main.py`, `models.py`, `state.py` (atomic JSON persistence via temp file + rename), `directive_engine.py` (validates AI output, rotating decision log), `ai_client.py`, `prompts/system.txt` and `user_template.txt` (editable, volume-mounted), 7 test files (~1,300 lines of tests).
- `module/ai_hook/hook.py` + about 95 lines in `alas.py`: ALAS posts four events (`cycle_start` debounced to 60 s, `task_complete`, `task_failed`, `unknown_state` carrying a base64 screenshot and the last 15 click records) and receives a JSON **directive**: `continue | reprioritize(task_order) | skip(task) | pause(reason)`. Directives are applied through existing scheduler APIs (`task_delay`, `stop_event`), not new core methods. Unreachable sidecar, unparseable or invalid AI output all degrade to `continue`.
- Docker: compose with sidecar and a split x86 OCR container for arm64 hosts; `COMPATIBILITY.md`; `.env.example`; a small guild-logistics tweak.
- `docs/superpowers/specs/2026-03-17-ai-sidecar-design.md` (431 lines) and `plans/2026-03-17-ai-sidecar.md` (2,039 lines): the design came from an AI "superpowers" brainstorm/plan workflow (spec, then numbered Task 1..11 plan, then one commit per task). The commit log ("Task 1", "Task 2", ... "Task 11") shows plan-driven task-by-task execution. Not much to learn beyond what Cimmeria's campaign-packet flow already does.
- Not verified: whether the sidecar ever ran against a real game; fork has no commits after March other than the upstream sync.

## Upstream core ideas (verified by reading source: module/base, module/ui, module/device, module/config)

1. **Button/Template asset system.** `Button(area, color, button)`: a fast check = average colour of a rectangle vs expected colour (threshold 10); `offset=(30,30)` switches to `cv2.matchTemplate` TM_CCOEFF_NORMED inside a search window, similarity 0.85. Per-server asset folders (cn/en/jp/tw). Assets are PNGs whose file names encode the box; `dev_tools/button_extract.py` generates `assets.py` per module from the PNG files ("auto-generated, don't edit"). `load_offset` lets one found anchor shift related buttons (relative layout). Variants: binary and luma matching, `match_multi` for repeated icons.
2. **State machine loop idiom.** `for _ in self.loop(timeout=...)` takes a screenshot per iteration, then an ordered list of `if self.appear(X): break / if self.appear_then_click(Y, interval=3): continue`. `interval=` per button is a debounce (a per-button Timer) so a slow UI is not spammed with clicks.
3. **Page-navigation graph.** `Page(check_button)` objects declare `page_a.link(button, destination=page_b)`. `Page.init_connection(dest)` runs a reverse BFS from the destination, giving every page a `parent` (next hop). `ui_goto(dest)` then loops: screenshot, if destination check-button visible stop, else find which known page is on screen and click its link to `parent`. `ui_get_current_page` iterates all pages' check buttons; on unknown it clicks a "go home" button or runs popup handlers, with a timeout then raises `GamePageUnknownError`. Popup/interstitial handlers are a pluggable `ui_additional()` chain called whenever nothing else matches.
4. **Stuck and loop detection (two layers).** (a) `stuck_timer` 60 s / `stuck_timer_long` 180 s: reset on every click; if no click happens in 60 s of screenshots, raise `GameStuckError` (with a whitelist of buttons, like battle status, that are allowed the long 180 s wait); it also checks whether the app is still running and raises `GameNotRunningError` instead. (b) `click_record` deque of last 15 clicks: if one button dominates (about 12+) or two buttons ping-pong, raise `GameTooManyClickError`. Every `appear()` call also records the button name in `detect_record`, so the stuck error says exactly what the bot was waiting for. Task runner catches both, restarts the game or the task, and gives up after 3 consecutive failures.
5. **Scheduler.** Each task has `Scheduler.NextRun` in YAML. `get_next_task` splits into `pending_task` (due, sorted by static priority) and `waiting_task` (sorted by next_run); the loop sleeps until the earliest waiting task. Tasks reschedule themselves with `config.task_delay(success=, server_update=, target=, minute=)`. Cross-task setters and `ConfigBackup` / `temporary()` context managers for scoped overrides. Failure counter per task, and `task_call` to wake another task.
6. **Config/GUI.** `argument.yaml` (single schema) generates config classes, i18n and the web GUI (pywebio) via `config_updater`/`code_generator`: one source of truth for settings, defaults, descriptions and UI.
7. **Device control.** Many interchangeable backends behind one interface, selected by config: ADB, uiautomator2, scrcpy, minitouch/MaaTouch, DroidCast, nemu_ipc, LDPlayer OpenGL for screenshots; health check and "run_simple_screenshot_benchmark" to choose the fastest method; app start/stop/orientation checks.
8. **Retry/Timer utilities.** `Timer(limit, count)` requires both a time and a minimum number of checks (so one slow screenshot does not trip it); `retry` decorator with backoff and jitter; `future_time`/time-range helpers.
9. **Testing/CI.** No test directory or `.github/workflows` found in this fork; upstream testing is largely `module/test`-less, relying on screenshot fixtures through `dev_tools`. Nothing to copy.

## Not worth taking

- Template-matching asset pipeline as a primary mechanism: Cimmeria has direct Lua/memory UI state; pixel matching is brittle and ALAS spends most of its maintenance on per-server asset churn (upstream log is dominated by "Fix asset" commits).
- ADB/uiautomator2/scrcpy device layer: Android-only; Cimmeria drives a Windows PC client.
- Pywebio GUI, Docker compose, OCR container, emulator-specific code (MuMu, LDPlayer, nemu_ipc).
- The AI sidecar implementation itself: it is a thin LLM-prompted task re-orderer with a hard-coded game prompt, no evidence it ran live, and GPL-derived. Its `superpowers` plan/spec documents are just a conventional plan-then-task-commits flow that Cimmeria's campaign-packet skill already covers; there is no AGENTS.md/CLAUDE.md or hooks to borrow.
- Upstream "CN-first" asset/server handling and the campaign/map-solving modules (game-specific).

# Persistent player data

> Type: campaign ledger. Packets: [work-packets.md](work-packets.md). Resume card: [RESUME.md](RESUME.md). Owner answers: [OWNER-DECISIONS.md](OWNER-DECISIONS.md) (D1-D7, 2026-10-18).

## Purpose

Today every container start wipes the colo database and reseeds it from the image: a release, a `docker restart` or a host reboot all lose every account, character, item, mail and guild. Locally, `setup.ps1 -ForceDatabase` does the same to a developer's `sgw`. The owner's goal:

- **Player data seeds once.** Accounts, characters and everything hanging off them come from the seeds on the first load only, then persist across restarts, releases and forced reseeds. One exception (owner D6): a seed account that is missing from the DB is inserted again on every rebuild; existing account rows are never touched.
- **Game data reseeds.** The `resources` schema (items, worlds, missions, abilities, dialogs and the rest) is rebuilt from `db/resources/` by each new image, by a forced container rebuild, and by `setup.ps1 -ForceDatabase`.
- **A full wipe is a separate, deliberately named action** (owner D3). Nothing that sounds like "refresh" or "reseed" deletes player data.
- **No migration framework.** Only the minimum needed to keep the two classes apart. Persistent tables change additively; anything else is an owner call, case by case.

Scope:

- **Container deploy** (colo, any Docker host): persistence, the resources rebuild, the seed-account top-up, backups, and a restore-from-backup path for disaster recovery. The first persistent deploy starts fresh from the seeds (owner D4).
- **Local play DB** (`sgw`, owned by `setup.ps1` / `Initialize-CimmeriaDatabase`): `-ForceDatabase` becomes a resources-only refresh when `sgw` already holds the schema; a new `-WipeDatabase` is the full wipe.
- **Unchanged:** `db/database.sql` (flat `\ir` list, F6), and every throwaway-DB path: `reload-db`, `live-db-test`, the per-worktree `sgw_<wt>` DBs, the live-DB slot clones, CI schema loads and the type 4 smoke. These create disposable databases, so they stay full fresh loads of `database.sql`. PP-15 makes sure none of them can target the play DB `sgw`.

## Design in one picture

```text
image build (db-init stage)
  psql -f db/database.sql              -> sgw (unchanged path)
  pg_dump -Fc sgw                      -> /opt/cimmeria/db/fresh.dump
  psql -f db/persistent/meta.sql       -> cimmeria_meta schema + db_state row (state 'baked')
  write image-id, db-source.sha256, copy db/persistent/*

container start
  entrypoint: PGDATA empty? copy baked pgdata : leave it alone
  s6: postgres -> db-sync (oneshot) -> cimmeria-server
  db-sync:
    baked row          -> mark live, first_seeded_at = now()        (first boot, no rebuild)
    same image-id      -> skip                                       (restart, reboot, crash)
    new image-id       -> backup, then rebuild sgw_next with carry-over, swap
    FORCE_REBUILD=1    -> same as new image-id: resources only, player data kept
    no cimmeria_meta   -> adopt: backup, then rebuild with carry-over (pre-persistence DB)
    restore env set    -> disaster recovery only: restore the dump to sgw_restore,
                          rebuild with carry-over from it
    every rebuild      -> seed accounts missing by id and by name are inserted, logged;
                          existing account rows untouched (owner D6)
    any failure        -> drop sgw_next, sgw untouched, exit non-zero, container stops
  first persistent deploy -> new empty volume -> first boot from the baked seeds (owner D4)
  full wipe (operator) -> stop, docker volume rm + create cimmeria-server-pgdata, start (first boot)

local setup.ps1 (Initialize-CimmeriaDatabase)
  no sgw, or sgw without the schema  -> full load of database.sql (first run seeds everything)
  -ForceDatabase on a loaded sgw     -> resources-only refresh:
                                        database.sql -> sgw_fresh -> pg_dump -Fc -> same rebuild
                                        steps as the container (carry-over from sgw), backup, swap
  -WipeDatabase                      -> drop sgw, full load (today's -ForceDatabase)
  -ResetDatabase                     -> delete pgdata, full load (nuclear, unchanged)

throwaway DBs (reload-db, live-db-test, slot clones, CI, smoke)
  full fresh load of database.sql, never into sgw
```

The rebuild: `pg_restore` the fresh dump into `sgw_next` (pre-data, then resources data plus the `public` reseed tables plus the seed `account` rows, which `seed-accounts-stage.sql` moves straight into a staging schema, so no persistent table holds fresh-DB data when the carry-over starts), carry the persistent `public` data and `cimmeria_meta` over from the old DB, insert the missing seed accounts (`seed-accounts.sql`), run `reconcile.sql`, then restore post-data (PKs, FKs, indexes, triggers), verify, and rename `sgw` to `sgw_prev` and `sgw_next` to `sgw`. The container runs it in POSIX sh, the local refresh in PowerShell; both use the same SQL files under `db/persistent/` and the same table lists.

## Decisions

| ID | Decision | Status | Reason |
|---|---|---|---|
| D-PP1 | **Persistence mechanism.** An **external** named volume `cimmeria-server-pgdata` on `/var/lib/postgresql/data` (compose: `external: true`, `name: cimmeria-server-pgdata`; the operator runs `docker volume create cimmeria-server-pgdata` once), plus a backup bind mount `${CIMMERIA_BACKUP_DIR:-./backups}:/var/backups/cimmeria`. The entrypoint copies the baked pgdata only when `PGDATA/PG_VERSION` is missing. | Decided (revised 2026-10-18) | The anonymous volume already survives swaps (F1), but `rm -v`, `down -v` and `volume prune` destroy it (F2). Only an external volume also survives `down -v` (F16), so the only way to lose it is the deliberate `docker volume rm` of D-PP15. The name differs from setup.ps1's `cimmeria-pgdata` (F17). A missing volume makes `compose up` fail with a clear error: fail closed, never an empty DB by accident. External Postgres was rejected: more moving parts, it breaks the self-contained image, and it would still need the same resource refresh. |
| D-PP2 | **How resources reseed against RESTRICT FKs: blue/green whole-DB rebuild.** Never alter the live `sgw` in place. Build `sgw_next` from a fresh dump, carry the persistent data over, reconcile dangling references **before** the FKs exist, add the post-data, then swap names. Used by the container and by the local refresh. | Decided | `DROP SCHEMA resources CASCADE` would drop the player enum columns (F5). Upserting about 100 resource tables doesn't handle DDL, deleted rows or enum changes. An in-place schema swap would need migrations for `public` DDL. Blue/green leaves `database.sql` untouched, applies additive `public` DDL for free (the new schema comes from the fresh DB), uses only `pg_dump`/`pg_restore`, and a failed rebuild leaves `sgw` untouched. |
| D-PP3 | **Table classification.** `resources.*` reseeds. `public.*` **persists by default**: an unclassified table keeps its data (fail safe). The explicit `public` reseed exceptions are listed in `db/persistent/reseed-public-tables.txt`, which holds `shards` only. `db/persistent/persistent-public-tables.txt` lists the rest. A type 1 lint fails when a `public` table is in neither list, or in both. | Decided | The safe failure keeps player data. The lint forces a conscious classification whenever someone adds a table. See the classification table below. |
| D-PP4 | **The one-time seed gate is the `cimmeria_meta.db_state` row,** not a file. The image bakes the row with `state = 'baked'`. The first boot flips it to `live` and stamps `first_seeded_at`. A `docker restart`, crash restart or host reboot of the same image skips: everything kept. A rebuild happens **on every new image** (`image_id` differs). `CIMMERIA_DB_FORCE_REBUILD=1` forces the same resources-only rebuild (operators and the CI smoke); it never wipes player data. | Decided (owner D2, D3) | A row in the DB travels with the data it describes, survives a volume copy, and can be read with psql. Rebuilding on every image, not only when the `db/` hash changes, matches "resources reseed every release" literally, undoes any runtime edits to resources, and keeps the rebuild path running every release so it can't rot. The cost is about a minute per release. |
| D-PP5 | **Forced reseeds refresh resources only; throwaway DBs stay full loads.** Container: `CIMMERIA_DB_FORCE_REBUILD=1` (D-PP4). Local: `setup.ps1 -ForceDatabase` (`Initialize-CimmeriaDatabase -Force`) does a resources-only refresh (D-PP14) when `sgw` exists with the schema loaded (`public.account` present); with no `sgw`, or an `sgw` without the schema, it does today's full load (first run seeds everything). The non-forced "seed looks incomplete" replay (F18) must not re-insert persistent seed rows into a DB that holds accounts; it routes to the refresh instead. `db/database.sql`, `reload-db`, `live-db-test`, the slot clones, CI loads and the smoke keep loading `database.sql` fresh, because they build disposable databases (PP-15 keeps them off `sgw`). | Decided (owner D3, overrides the earlier "full wipe" default) | One meaning for "force a reseed" everywhere a play DB lives. Leaves `database.sql` and both of its parsers (F6) alone. A new seed **account** reaches an existing play DB through the top-up of every rebuild and refresh (D-PP17, owner D6). Every other persistent seed row (a seed character, its inventory) reaches it only through a wipe. |
| D-PP6 | **Implementation language and layout.** Container: POSIX sh, `docker/db-sync.sh` (state machine, backup, retention) and `docker/db-rebuild.sh` (the pipeline), run by a new s6 oneshot `db-sync`. Local: PowerShell, a new private function file in `bootstrap/CimmeriaBootstrap/Private/` (D-PP14). Shared SQL in `db/persistent/meta.sql` and `db/persistent/reconcile.sql`: plain SQL, no psql meta-commands, no transaction control, idempotent DDL (`IF NOT EXISTS`). | Decided | Each side runs with tools it already has. The SQL is testable on Windows through the type 4 smoke harness, the local refresh through a pwsh test against the bundled Postgres, and the shell in CI only (`pr-container.yml`). Coders never run bash or docker locally, and say so in their reports. |
| D-PP7 | **Schema-change policy for persistent tables: additive only.** Allowed: a new table, a nullable column or one with a DEFAULT, a widened type, a new index, a new enum value. Anything else fails closed at boot, in the local refresh and in the CI smoke: a NOT NULL column without a default, a rename, a drop, a narrowed type, a removed enum value used by a row, or a new CHECK/UNIQUE that existing rows violate. A non-additive change needs an owner decision and a one-off plan. A new persistent table's seed rows apply on first load only (seed accounts excepted, D-PP17). | Decided, owner D7 (fail closed) | No migration framework (owner goal). The carry-over is a column-named COPY into the new schema, so additive changes need no code, and everything else errors out instead of corrupting data. PP-11 adds a committed schema snapshot so a reviewer sees a non-additive change in the PR, not at boot. |
| D-PP8 | **Never renumber or reuse a resource id that player data references** (items, worlds, missions, abilities, dialogs and tutorials, disciplines, stargates, respawners, blueprints, content chains). Removing a row is allowed; D-PP9 handles it. | Decided | A reused id silently turns a player's item or mission into a different one. No reconcile can detect that. |
| D-PP9 | **Dangling-id policy.** FK-backed references are reconciled before the FKs are added: inventory, mail-item and vault-item rows whose `type_id` no longer exists are **deleted**, with the full row logged as JSON in `cimmeria_meta.reconcile_log`. A player in a removed world is **relocated** to the fallback start (`Castle_CellBlock`, looked up by name, at -334.231, 73.472, -228.026, from the seed) and logged. If the fallback world is gone too, the rebuild raises (fails closed). Non-FK ids (F9) are left in place and counted in the log. PP-03 verifies that the server tolerates them. | Decided (owner D5) | Deleting with a full log is recoverable by hand. Failing the whole release over one removed item would block deploys. Relocation mirrors what a GM would do. |
| D-PP10 | **Backups.** Container: each rebuild first writes `pg_dump -Fc sgw` to `/var/backups/cimmeria/`, keeping the newest `CIMMERIA_DB_BACKUP_KEEP` (default 10). A retried failed rebuild for the same target reuses the newest backup instead of writing another. Before the first persistent deploy the runbook recommends, without gating on it, one safekeeping dump of the old DB onto the colo data disk (never git); D-PP12 could restore it later. Local: each refresh and each `-WipeDatabase` first writes `pg_dump -Fc sgw` to `server/backups/` (gitignored), keeping the newest 3. Both keep `sgw_prev` until the next rebuild. Off-host copies are a follow-up. | Decided (owner D7) | Two independent copies (dump file and `sgw_prev`) at zero cost, with nothing off-host yet. | D-PP11 | **Tests.** Type 1: the classification lint (PP-02) and the schema-snapshot guard (PP-11). | D-PP15 | **Full wipe actions: separate and deliberately named.** Local: new `setup.ps1 -WipeDatabase` (`Initialize-CimmeriaDatabase -WipeDatabase`, plumbed through `Invoke-CimmeriaBootstrap`) takes the backup, drops `sgw` and does a full load: today's `-ForceDatabase`. `-ResetDatabase` (delete pgdata, re-initdb) stays the nuclear option for a corrupt pgdata or a PG major change; it destroys player data too, and its help text says so. `-ForceDatabase` with `-WipeDatabase` is an error. Both wipes print the account and character counts they are about to destroy when the DB is reachable. Container: no wipe env var (one left in `.env` would wipe at every start). The full wipe is the operator runbook step "stop the container, `docker volume rm` and `docker volume create cimmeria-server-pgdata`, start", which first-boots from the baked seeds. | Decided (owner D3 implication: architect's call) | A wipe can't happen from a flag whose name says "force" or "rebuild". | D-PP16 | **Throwaway-DB scripts never target `sgw`.** From the main checkout, `reload-db.ps1`/`.sh` (and so `live-db-test`) default to the separate test DB `sgwtest` (O10), and they refuse `sgw` as a target, even through `CIMMERIA_TEST_DB`, with a message pointing to `setup.ps1 -ForceDatabase` / `-WipeDatabase`. Worktree DBs (`sgw_<wt>`) are unchanged. | Decided (owner D8) | Otherwise one live-DB run from the main checkout wipes the play DB that D3 protects (F20). |
| D-PP17 | **Seed-account top-up on every rebuild** (owner D6). Container rebuilds (`rebuild`, `adopt`, `restore`) and every local refresh insert each seed account from the fresh DB whose `account_id` **and** `account_name` are both absent from the carried data (F22). An existing row is never updated, even when its seed values changed (password, accesslevel, `test_account`). A seed account whose id or name is taken by a different row is skipped and logged. Accounts only: no characters, inventory or other rows come with it. Mechanism: the step 4 data filter also restores `public.account` from the fresh dump; `db/persistent/seed-accounts-stage.sql` moves those rows into a staging table `cimmeria_seed.account` and empties `public.account` before the carry-over; after the carry-over, `db/persistent/seed-accounts.sql` inserts the missing ones, logs `insert_seed_account` / `skip_seed_account` rows, and drops `cimmeria_seed`. The sequence fixup in `reconcile.sql` runs after it. First boot and `skip` don't run it (the baked seeds are already complete). | Decided (owner D6) | New dev and lab accounts in `account.sql` reach colo and every refreshed local `sgw` with no operator step. Matching on id and name never overwrites a real row and never creates a duplicate login name. Staging inside `sgw_next` keeps the fresh dump and both image-build paths unchanged; the two pipelines only gain one TOC entry and two SQL calls. The trade-off the owner accepted: an operator who deletes a seed account sees it return at the next rebuild. To retire one, remove it from `account.sql`; to lock one out, set `enabled = false` (an existing row is never touched). |

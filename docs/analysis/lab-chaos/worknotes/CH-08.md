## Cleanup paths

| Path | What clears the server chaos |
|---|---|
| Row passes, a step fails, setup fails | `drive_row` after teardown, before a fixture session logs out |
| The set call fails in transport | `drive_row` clears at once (the set may have landed); the row is BLOCKED |
| The set is refused (`{refused}`) | nothing was set; the row is BLOCKED and drives nothing |
| Lease takeover cuts the row off | `run_row`, after `tap_abandon` (the lab MCP is not lease-gated) |
| Panic | `ServerChaosGuard::drop` logs a WARN and spawns a best-effort clear through a fresh `ServerTools::from_env()` (`Drop` cannot await) |
| Everything else (the daemon dies) | the server's TTL: the row's budget plus 60 s |

`cpu` stops when `run_all`'s guard drops: on return, error or unwind.

## Differences from the spec

1. **Burst is refused, not wired.** See below.
2. **`RunRequest.chaos` is `Vec<String>`, not `Vec<ChaosSpec>`.** The
   default seed is the run id's hash, and the run id is made in
   `Runner::new`. So `lab_uat_run` checks the texts with a placeholder seed
   (refusing a bad one before the lease), and `Runner::new` resolves them
   with the run's seed. An appended run (`run_dir`) uses that run's id.
3. **There is no "row timeout".** `RowSpec` has none. The TTL is the row's
   budget, 300 s plus every `wait_ms`, `wait_server.timeout_ms` and clause
   `timeout_ms` it names, plus 60 s. A row whose budget already exceeds
   1800 s is BLOCKED with a message (not clamped), so chaos never ends
   mid-row. A plain row gets 360 s.
4. **Chaos is set before setup, not before the first step.** Setup is part
   of what the row drives, so it runs under the chaos too. It is set after
   the anchor, which needs no chaos.
5. **Server chaos needs an `in_world` row.** It is scoped to the player
   entity (D-CH3), which a `char_select` or `client_stopped` row does not
   have; such a row is BLOCKED under `net`/`flush`.
6. **A failed clear is a flag, not a failure.** The row's own result does
   not depend on it; the flag says the server ends it within the TTL.
7. **The batch header.** Each run's seed differs (its run id), so a batch
   of several runs reports the first run's header and a count of the other
   seeds; `batch.jsonl` has every run's own.

## Burst: deferred

The packet's gate: if `.spawnrandom` does not report the spawned entity
ids, stop. It does not, so burst is refused with "burst is not wired yet;
it waits on CH-13 (.spawnrandom ids, .despawn <id>)", at plan time too (the
plan call fails, `lab uat` exits 3). Evidence, against `main` @ `c37b0f6a2`:

1. `.spawnrandom` (`crates/cell-console/src/cell/console/spawn/mod.rs`,
   `spawn_random`) replies only `spawnrandom: requested {count} x template
   {T}` (or `only {d}/{count} ... delivered`). It enqueues one
   `CellToBaseMsg::GmSpawnNpc` per copy.
2. The ids are allocated later, in the cell's `GmSpawnNpcReady` handler
   (`crates/cell/src/cell/service/base_messages/gm_spawn.rs`), after the base
   resolves the template. Each one sends its own `spawned npc {id} (template
   {T})` line as GM feedback to the player.
3. The lab console tee (`crates/cell/src/cell/service/base_messages/lab_console.rs`)
   captures only the feedback emitted while the command runs, then replies.
   The `spawned npc` lines arrive after that reply, so `server_console_exec`
   never returns them; they go to the client's chat.
4. Despawn is target-only. `.despawn` is `Target::Mob` and resolves the
   caller's `current_target_id` (`dispatch::resolve_target`); the native
   `gmDespawn` also acts on the selected target. Despawning by id would mean
   retargeting the player mid-row, which perturbs the row under test.

The options put to the owner (D-CH5 said "no new server code"; both need
some):

- **(a)** A lab-mcp tool `server_npc_despawn {entity_ids}` calling
  `despawn_npc_releasing_combat` directly, with the runner finding its
  spawns as a before/after diff of `server_entity_query`.
- **(b)** Console changes: `.spawnrandom` waits for the `GmSpawnNpcReady` ids
  before replying (across the cell-base round trip), and `.despawn` takes an
  optional id.

**The owner chose (b) (D-CH9).** CH-13 makes those console changes in its
own worktree; this packet touches no `crates/cell*` file. Once CH-13 lands,
a follow-up adds `crates/lab/src/chaos/burst.rs`, the burst spawn after
setup and despawn after teardown (on failed rows too), and the two burst
tests (`burst_despawns_exactly_what_it_spawned`, and despawn on a failed
row), and drops `BURST_DEFERRED`. Until then
`burst_is_refused_before_the_run` replaces them.

## Open questions

1. **Flush chaos may never meet a first-login flush.** Chaos is scoped to
   the player entity, so it can be set only once the row is in world, after
   that login's flush. CH-05 clears a session's chaos on a return to
   character select, and CH-07 clears it when a new entity owns the address.
   So a `flush` set by the runner reaches only a later flush within the same
   in-world session (if one happens at all). CH-11's acceptance runs (fresh
   first login, FS-01 to FS-P2) need either chaos armed for the next login
   on an address, or a relog that keeps the entity and the chaos. This is a
   design gap for the coordinator to settle before CH-10.
2. Should a chaos clear failure fail the row instead of flagging it?

# CH-06 worknote: per-session net shim

> Packet: [CH-06](../work-packets.md#ch-06-net-per-session-lossy-transport).
> Branch `lab-chaos/ch06-net`. Implementer: rust-gameserver-dev.

## What landed

- `crates/mercury/src/lossy_transport/filter.rs` (new): the filter logic
  extracted from `LossyTransport` so both transports share it.
  `roll_send` (drop, then duplicate only for a survivor, then latency: the
  draw order is the replay contract and is unchanged), `roll_drop`,
  `roll_latency`, `FlowFilter` (one config plus a send and a receive
  ChaCha20 stream; the receive stream is seeded from `seed ^` a fixed
  constant so the send pattern of a seed does not depend on how much the
  peer sent) and `SendShaper` (the per-destination delay lines and reorder
  buckets, with `deliver`, `flush_reorder_buffer` and `release(addr)`).
  `LossyTransport` now calls these; its behaviour and tests are unchanged
  apart from one test reaching `filter::roll_latency`.
- `crates/base/src/base/lab_chaos_transport.rs` (new, feature `lab-chaos`):
  `ChaosTransport`, a `BidirectionalTransport` over the base's real
  transport. `wrap_if_installed` wraps it only when
  `lab_chaos::current()` is `Some` (the registry was installed under
  `DEVELOPER_MODE`), and logs one WARN `event=lab_chaos_net_shim`.
  - Send side: drop, latency, jitter, duplicate and reorder, through
    `FlowFilter::roll_send` and `SendShaper::deliver`. Never sleeps.
  - Receive side: drop only, by source address, no cap on consecutive drops
    (each turn awaits a real datagram, and an error would reach the receive
    loop for every session).
  - One `FlowFilter` per shaped address, built from the entry's `NetChaos`,
    rebuilt when the knobs change, and dropped when the entry is cleared or
    expires. Dropping a peer releases its reorder bucket (held sends go out,
    reversed) and closes its delay line once drained.
- `BaseService::start` (`crates/base/src/base/service.rs`): one
  `#[cfg(feature = "lab-chaos")]` line after the transport is built. With
  the feature off nothing changes.
- `crates/base-session/src/base/lab_chaos/mod.rs`: `LabChaos::has_net()`,
  one atomic load. The count of net entries is recounted by the drop of a
  `SessionsGuard` wrapper around the map's `MutexGuard`, so every path that
  locks the map keeps it in step before the unlock, and no future writer
  can forget to.
- `crates/base/Cargo.toml`: `async-trait` as an optional dependency,
  enabled by `lab-chaos` (`dep:async-trait`). `cargo hakari generate
  --diff` and `manage-deps --dry-run` are clean.

## Differences from the spec

1. **Two atomic loads, not one, per datagram with nothing set:**
   `has_net()` and the shim's own peer count. The second lets the shim
   release state left behind when the last net entry went away (cleared by
   teardown, say) without a lock on every send.
2. **A re-set with identical knobs keeps the RNG streams** if the shim
   never saw the entry gone in between (no datagram to or from the address
   while it was cleared). The runner clears after every row and the server
   sends tick syncs constantly, so in practice each row starts a fresh
   stream. Keying on the entry's `expires_at` would close this, but
   `net_for` returns only `NetChaos`; left as is.
3. **At a chaos boundary a packet can overtake one still on the old delay
   line** (the line drains, a new send goes straight out). Mercury tolerates
   reordering; noted, not fixed.
4. **Tests live in `crates/base`** (`lab_chaos_transport_tests.rs`, with the
   feature), not in mercury's chaos harness: they exercise the registry's
   per-address scope and expiry, which mercury cannot see. They run over a
   recording fake wire, so they are deterministic. Three tests beyond the
   spec: `no_chaos_passes_everything_through`,
   `clearing_chaos_releases_held_reorder_sends` and
   `reorder_matches_the_lossy_transport_contract`. Plus
   `has_net_follows_every_net_entry_change` (base-session) and
   `flow_filter_send_rolls_ignore_recv_rolls` (mercury).
5. **Revert proof:** a sleep of the entry's latency added to `recv_from`
   fails `receive_drop_never_delays_other_peers` (checked, then removed).

## Doc deltas CH-12 owes

### `docs/architecture/network-chaos-testing.md`

Under the L4 note from CH-04, add:

> **L4 net shim.** `cimmeria_base::base::lab_chaos_transport::ChaosTransport`
> wraps the base's UDP transport in a `lab-chaos` build started with
> `DEVELOPER_MODE`. It reads `LabChaos::net_for(addr)` per datagram (after a
> lock-free `has_net()` check) and shapes only that session: send-side drop,
> latency, jitter, duplicate and reorder; receive-side drop only. It shares
> its filter code with `LossyTransport` (`lossy_transport::filter`), so a
> seed means the same in both. Receive latency is deliberately absent: one
> task reads the socket for every session, so the profile's latency grows
> the round trip once, on the server's sends.

And in the "Network-chaos primitives" list, one line for
`lossy_transport::filter` (`roll_send`, `FlowFilter`, `SendShaper`) as the
shared seeded-filter layer under both `LossyTransport` and the lab shim.

### `TESTING.md` type 10

> **Per-session shim tests.** For a transport that shapes some peers and
> not others, test over a recording fake wire (an in-test
> `BidirectionalTransport` that stores sends and serves injected receives),
> with a registry the test builds itself rather than the process-wide one.
> Cover: scope (a second peer on the same socket is untouched), replay (the
> same seed gives the same survivors, another seed does not), expiry (the
> peer is no longer shaped once its TTL passes) and that a receive-side fault on
> one peer never delays another's datagram. Example:
> `crates/base/src/base/lab_chaos_transport_tests.rs`.

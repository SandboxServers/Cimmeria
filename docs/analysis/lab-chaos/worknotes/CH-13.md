# CH-13 worknote: `.spawnrandom` reports ids, `.despawn <entityId>`

> Decision: [D-CH9](../README.md#decisions). Branch
> `lab-chaos/ch13-console-ids`. Implementer: rust-gameserver-dev.

## What landed

### `.spawnrandom` reports the ids it spawned

The ids are allocated by the cell only when the base's `GmSpawnNpcReady`
comes back, after the command has returned. The command now opens a
**spawn batch** and the batch, not the command, reports.

- `crates/cell-console/src/cell/console/spawn/batch.rs` (new, re-exported as
  `cell::console::spawn_batch`): `SpawnBatches`, stored in
  `SpaceManager::resources`. A batch holds the requester, template, the
  count asked for, the copies still outstanding, the spawned ids in arrival
  order, a failure count with distinct reasons, a deadline
  (`SPAWN_BATCH_TIMEOUT`, 5 s) and an optional parked lab reply.
- Wire (`cimmeria-wire`): `CellToBaseMsg::GmSpawnNpc` and
  `BaseToCellMsg::GmSpawnNpcReady` gained `batch: Option<u32>`; new
  `BaseToCellMsg::GmSpawnNpcFailed { requester_entity_id, batch, template_id,
  reason }`. `.spawn` and the native `gmSpawnByCmd` send `batch: None` and
  behave exactly as before.
- Base (`crates/base-session/src/base/gm_spawn.rs`): for a batched copy every
  failure (template not found, query failed, no database) goes to the cell as
  `GmSpawnNpcFailed` instead of a chat line, so the batch can close at once
  rather than wait out its timeout. A single spawn is unchanged (the no-pool
  case stays silent for it, as before).
- Cell (`crates/cell/src/cell/service/base_messages/gm_spawn.rs`): a batched
  `GmSpawnNpcReady` records the new id against its batch and sends no
  per-copy `spawned npc <id>` line; `GmSpawnNpcFailed`, and a batched
  placement failure, count a failure. The copy that closes the batch sends
  the summary. A result for a batch that already reported (timed out) is
  handled by who was waiting; see [Review fixes](#review-fixes).
- Timeout: `spawn_batch_tick`, on the cell loop's 1 Hz cadence
  (`message_loop.rs`), closes every batch past its deadline. So the summary
  arrives at most about 6 s after the command when a copy never answers.
- Lab tee (`crates/cell/src/cell/service/base_messages/lab_console.rs`):
  before running the command it takes the batch table's next id; after
  draining the captured lines it asks the table for a batch the caller
  opened since then. If there is one, the captured lines and the `reply_tx`
  are parked on it and the reply is sent when the batch closes, with the
  summary appended. Otherwise it replies at once, as before. Nothing waits:
  the cell loop goes on to its next message, and other GMs' commands run
  normally.

### `.despawn [entityId]`

- New `Target::MobOrId` in the console registry. With no argument it is
  `Target::Mob` exactly (selected NPC, in view, same space). With an
  argument, `dispatch::resolve_target` calls
  `spawn::resolve_npc_id` (`spawn/despawn_by_id.rs`, new), and the
  resolved id flows into the unchanged `despawn_entity`
  (`despawn_npc_releasing_combat`), the audit log line and the Discord GM
  row like a selected target.
- Accepted: a non-player entity of class `SGWMob` (4) or `SGWBeing` (1) in
  the caller's space that is not a registered pet. Refused: not a number;
  an unknown id or an entity in another space (one answer for both, checked
  first); and, in the caller's space, a player (the caller included), a pet
  (registered in `PetRegistry` or of class `SGWPet`) or any other class
  (spawnable props, duel markers), each with its reason.
- Same GM gate as every console command (the chat channel's
  `access_level` check, and the tee's).

## Reply format (for CH-08's burst parser)

`server_console_exec` returns `output` as a list of lines. For
`.spawnrandom <T> <x> <z> <count>` it is:

```text
spawnrandom: requested <count> x template <T>
spawnrandom: spawned <n>/<count> x template <T>: ids <id,id,...|none>[; <f> failed (<reason>[; <reason>])][; <t> timed out]
```

- The summary is always the **last** line.
- `ids` is comma-separated with no spaces, in the order the copies
  spawned; `none` when nothing spawned. `n` equals the number of ids.
- `n + f + t = count`. `failed` and `timed out` appear only when non-zero.
  Two or more distinct reasons are joined by `; ` inside the parentheses,
  in first-seen order (`2 failed (template 7 not found; could not place it
  in the space)`), so a parser must not split the summary on `; ` before
  taking the parenthesised part.
- `t > 0` (timed out) in a **lab** reply means those copies were never
  reported, and any of them that spawns later is despawned on arrival:
  the ids listed are exactly the NPCs the burst owns. In-world, a late copy
  stays and gets its own line.
- Requests the base channel refused count as failed with reason
  `cell→base channel error`. Through the lab console this shows only in the
  summary (the tee forwards the requests after the command ran, so the
  command itself saw them all delivered and printed `requested`); when no
  copy reached the base the reply comes at once. In-world, the command
  prints `spawnrandom: only <d>/<count> spawn requests delivered for
  template <T> (cell→base channel error)` instead of `requested`, but that
  line travels on the same dead channel, so in practice nobody reads it;
  with `d = 0` there is no batch and no summary.
- Argument errors (bad template id, not in a space) are single lines with no
  summary, as before.

A parser can use:

```text
^spawnrandom: spawned (\d+)/(\d+) x template (-?\d+): ids ([0-9,]+|none)
```

Despawn replies, one line each:

```text
despawn [<id>]: removed from the space; <k> observer(s) notified. Its spawnlist row (if any) is untouched — use .delspawn to remove that.
.despawn: entity <id> is a player; .despawn only removes NPCs
.despawn: entity <id> is a pet; .despawn only removes NPCs (use .pet dismiss)
.despawn: entity <id> is not an NPC (entity class <c>); .despawn only removes NPCs
.despawn: no NPC with id <id> in your space
.despawn: entityId must be a non-negative whole number (got "<arg>")
```

A burst cleanup should treat `removed from the space` as success and
`no NPC with id <id> in your space` as already gone (killed and not
respawned, since a GM spawn never respawns; or the runner changed map).

## Deviations

1. **In-world chat changed for `.spawnrandom`.** A GM used to get one
   `spawned npc <id> (template <T>)` line per copy (up to 50); now one
   summary line after the `requested` line. Intent over parity: one line
   that names every id is the readable answer.
2. **Wire messages changed** (`GmSpawnNpc`, `GmSpawnNpcReady`, new
   `GmSpawnNpcFailed`). All three are internal base↔cell channel messages,
   nothing reaches the client.
3. **`.despawn <id>` has no in-view check**, unlike a selection: the runner
   may have moved since it spawned. The same-space rule stands in for it.
   Beings count as NPCs, matching what `.despawn` on a selection already
   accepts. Pets are refused by the id form only: `.despawn` with no
   argument still removes a selected pet, as before CH-13.
4. **`.despawn` arity is 0 to 1** (was 0). Its `.help` line and arg help
   name the id. Target label in `server_console_list` is now
   `an NPC (selected, or by entity id)`.
5. The base's gm_spawn tests moved to `gm_spawn_tests.rs` (the file passed
   500 lines).

## Open

- The tee now holds a lab reply up to about 6 s for `.spawnrandom`.
  `server_console_exec` has no timeout of its own, so this is fine today; a
  future timeout there must exceed `SPAWN_BATCH_TIMEOUT` plus one tick.
- If the GM logs out mid-batch the in-world summary is dropped (logged);
  the lab reply is still sent.

## Review fixes

Second commit, after the packet review and the authority review.

1. **Late copies of a lab batch are despawned.** A closed batch is
   remembered for `CLOSED_BATCH_MEMORY` (60 s, pruned by the 1 Hz tick).
   A `GmSpawnNpcReady` for a remembered batch that had a lab waiter places
   the NPC and despawns it at once through
   `despawn_npc_releasing_combat` (`"spawnrandom_late"`), with a WARN
   naming the batch, the NPC and its template: the lab reply has gone, so
   nobody would ever learn that id. A remembered batch without a lab
   waiter (a GM in the world) keeps the packet's behaviour: the NPC stays
   and the GM gets `spawned npc <id> (template <T>) after its .spawnrandom
   report` (or `spawn failed for template <T>: <reason>`). A copy for a
   batch neither open nor remembered stays, with a WARN and no chat line,
   since its requester can no longer be checked (fix B).
2. **The tick is tested in the loop.**
   `service/tests/spawn_batch_loop.rs` runs `run_cell_loop` on a paused
   clock with a base that never answers; the lab reply must arrive with
   every copy timed out. Removing the `spawn_batch_tick` call fails it.
3. **Partial delivery.** At command level, a one-slot channel whose reader
   hangs up after two requests makes the send fail mid-loop; the refused
   copies are counted failed, not timed out. In the lab tee, a refused
   forward no longer stops the drain: the remaining feedback lines are
   still captured, batched spawn requests that never left are counted
   failed per batch (`undelivered` now closes a batch with nothing
   outstanding), and when none left the reply comes at once.
4. **Untested failure arms.** The base's batched `could not load template`
   is tested without a live database (a lazy pool on a closed port); the
   cell's batched `could not place it in the space` by a `GmSpawnNpcReady`
   for a space that does not exist.
5. **Dead duplicate guard removed.** The result that takes a batch to zero
   closes it, so an open batch always has a copy outstanding; a duplicate
   finds the batch closed and comes back `Late`. Test renamed
   `a_result_for_a_closed_batch_is_late_and_an_unknown_id_is_unknown`.
6. **Logging.** The base logs a failed `GmSpawnNpcFailed` send (WARN). A
   batch closing with failed or timed-out copies logs WARN, a clean one
   INFO; late copies log WARN.
7. File-size debt is under [Owed](#owed).
- **A. No cross-space facts from `.despawn <id>`.** The space check runs
  straight after the existence check, and both answer `no NPC with id <id>
  in your space`, so the id form cannot tell a GM whether an entity on
  another map is a player. Guard test:
  `despawn_by_id_does_not_reveal_a_player_in_another_space`.
- **B. Deferred lines check who they go to.** A batch stores a
  `Requester` (entity id, account id, player id) when it opens. The
  in-world summary and both late lines go out only while that entity id
  still belongs to the same character (`Requester::still_here`); otherwise
  they are logged and dropped. The lab reply is unaffected (it goes to the
  parked `reply_tx`, not to an entity).
- **C.** The doc lines now say the pet refusal is the id form's only.

Revert proofs, run by hand (each mutant made the named test fail, then was
restored): 1, drop the `late.lab` despawn
(`lab_spawnrandom_reports_partial_delivery_after_the_timeout`); 2, comment
out the tick call (`the_loop_closes_an_unanswered_batch_and_sends_the_lab_reply`);
A, check the player before the space
(`despawn_by_id_does_not_reveal_a_player_in_another_space`); B, send the
summary to the bare entity id
(`summary_is_dropped_when_the_gm_id_belongs_to_someone_else`); 3, skip the
tee's undelivered count (`lab_reply_counts_requests_the_base_channel_refused`)
and the command's (`spawnrandom_counts_copies_the_channel_refused_mid_loop`).

## Differences from the packet

1. **`apply` signature.** The spec's
   `apply(addr, phase1, phase2) -> Option<Duration>` could not be called
   once per flush: the records are built per lifecycle segment, inside
   `dispatch_segment`. It is
   `apply(addr, witness_id, witness_name, &mut segments) -> (Option<Duration>, Phase1Shape)`.
   Reorder permutes the introductions inside each segment before the
   records are built (so an entity's phase-1 record and its cascade move
   together, and the tail keeps its order); the shape applies to every
   segment's phase-1 bundle.
2. **A flush with no introductions is left alone.** The self-method flush
   ahead of a cinematic hold carries none. Without this, `Delay` would also
   hold the self methods back and `ShiftSweep` would spend a draw on a flush
   it cannot shift.
3. **`Pack` with more introductions than `records`** sends the rest in a
   second phase-1 bundle, still ahead of phase 2.
4. **`Pack` bound tightened to 34**, refused above it (never clamped).
   34 records plus the longest filler (38) is 1296 bytes, under the
   1300-byte `FRAGMENT_BODY_SIZE`.
5. **ShiftSweep "a new one per flush"** uses a process-wide draw counter
   mixed into the seed (SplitMix64). Lengths replay from the log: each
   `flush_shift_swept` row carries `seed`, `draw` and `len`. Two sessions
   sweeping at once interleave their draws.
6. **`pack_puts_records_in_one_packet`**: the spec's "889 bytes" is the
   client cursor after the last of 24 records; the bundle body is 888
   bytes, which the test asserts. The test also packs 34 of 40
   introductions, a case the ordinary flush fragments, so it fails if Pack
   is ignored (24 records fit one packet either way).
7. **Test seam.** Tests cannot call `install` (server startup only), so
   `flush_chaos::lend_registry` lends a test-owned registry to the test's
   thread under `cfg(test)`.

## Review fixes

Second commit, after the packet, AoI and BigWorld reviews.

1. **`Delay` no longer sleeps in the receive path.** The base's receive
   loop (`run_connect_loop`) awaits `onClientReady` and `cancelMovie`
   inline, so the old sleep in `dispatch_deferred` stopped packet
   processing for every session, and near the 60 000 ms cap the server's
   60 s inactivity reaper tore sessions down. It also slept after the
   pre-ready gate had opened and the buffer had been drained, so live AoI
   traffic (a `LeftAoI`) could overtake the held creates and leave a ghost.
   `Delay` now reuses the cinematic AoI hold
   (`world_entry_appearance/cinematic_aoi_hold/chaos_delay.rs`):
   `handle_on_client_ready` begins a hold under the same lock that opens
   the pre-ready gate when a delay is set (as it does for a first login),
   flushes the player-self calls, and releases the hold where the ordinary
   flush would have run. Every hold release reads the delay once, right
   after it claims the hold; with one set it spawns the drain behind a timer
   and returns, so the hold stays up and live traffic keeps buffering, then
   the whole buffer goes out, introductions first. `flush_chaos::apply`
   ignores `Delay`, so the release loop's later passes never wait again: a
   delay applies once per hold. On a first login the delay follows the
   cinematic release (timeout or `cancelMovie`).
2. **Default flush pinned to pre-CH-07 bytes.**
   `tests_flush_default_bytes.rs` hashes every packet of a 28-introduction
   flush with a full tail (method call, witness method, invisible, leave)
   and compares with the hashes captured by running the same flush on
   900aa0751's `deferred_flush.rs` (12 packets: 1 phase-1, 7 phase-2, 4
   tail). The no-chaos registry cases and the `Delay` case (no wait, same
   bytes) compare with that capture, not with the new code.
3. **Test gaps.** `reorder_is_seeded` also checks the UPDATE_AVATAR order
   and the phase-2 cascades follow the shuffled creates;
   `shift_38_packs_34_records_in_one_packet` (40 introductions);
   `shift_sweep_draws_a_new_length_each_flush` (through `apply`, read back
   from the `flush_shift_swept` rows); the `flush_delayed` row is asserted;
   `pack_cap_is_one_packet_with_the_longest_filler` now reads the refusal
   texts.
4. **`shift_for_cursor`** computes in `u64` (a cursor near `u32::MAX`
   overflowed); `flush_shift_packs` logs `shifted_segments`.
5. **Filler policy switch.** `flush_chaos::FILLER_POLICY` selects between
   the CH-07 design (`02 0A` plus `voiceData`) and update-frequency only
   (`L / 2` copies of `02 0A`, even lengths only). `filler`, `sweep_len` and
   `shift_for_cursor` follow it. The registry is unchanged: switching also
   needs `LabChaos::set` to refuse odd `Shift` lengths, which would
   otherwise go out unshifted with a `flush_shift_refused` WARN. The RE
   pass (`docs/reverse-engineering/findings/client-voicedata-and-update-frequency.md`,
   commit 878763bf7 on `lab-chaos/feature`) statically verified `voiceData`
   as safe for bodies of 0 to 33 bytes: `SGWMessageQueue` slot 13 queues it,
   `EntityManager` reads and discards the body, `data()` is non-null at
   length 0, and the client's element table confirms WORD_LENGTH. A resent
   `updateFrequencyNotification` rewrites the same float. So the CH-07
   design stays the default; the update-frequency-only form was already
   built and tested, so it stays as an unused fallback.
6. **Behaviour to know.** Chaos stays set until its TTL or a clear, so it
   disturbs every later flush with introductions on that session (gate
   travel, a relog on the same character), not only the first one. The
   sweep's draw counter is process-wide and interleaves across sessions;
   each row logs `seed`, `draw` and `len`. `Reorder` moves an entity's
   phase-1 record and its phase-2 cascade together.

# CH-14 worknote: arm chaos by account for the next world entry

> Packet: CH-14 ([ledger](../README.md), decision D-CH10). Branch
> `lab-chaos/ch14-arm-account`. Implementer: rust-gameserver-dev.

## What landed

- Registry (`crates/base-session/src/base/lab_chaos/armed.rs`, new):
  `ArmedChaos` and four `LabChaos` methods. `arm(account_id, label, net,
  flush, ttl_s, now)` runs the same checks as `set` (both now call
  `bounds::check_request`) and keeps one arm per account, a second replacing
  the first. `promote_armed(account_id, addr, entity_id, now)` takes the arm
  (one-shot) and inserts it at `addr` as a `SessionChaos` tagged with
  `entity_id`, under a new generation, through `SessionsGuard`, so
  `has_net` recounts. `clear_account(account_id)` removes one arm;
  `armed_status(now)` lists live arms by account id. Arms live in their own
  map (`armed`) and are not net entries until promoted. (Locking changed in
  the review fixes below.)
- `clear(None)` also clears every arm and counts them in its return.
  `clear(Some(addr))`, which teardown and character select call, leaves
  arms alone. Expired arms are swept by `arm` and `armed_status`, and an
  arm past its TTL at promotion is dropped, not promoted.
- An arm keeps the TTL it was armed with: `expires_at` is fixed at the arm
  and carried into the session entry, so the 30-minute cap holds from the
  set, however long the login takes.
- Promotion (`crates/base-world-entry/.../play_character.rs`): right after
  `query_world_entry` returns a real entity id (the `NO_ENTITY_ID` bail is
  above it) and before RESET_ENTITIES is sent, under
  `#[cfg(feature = "lab-chaos")]`, through the new
  `cell_dispatch::flush_chaos::promote_armed`. It uses the session's
  `account_id` (the handler's argument, from the authenticated session),
  never a client value.
- Tools (`crates/lab-mcp/src/tools/chaos.rs`, `chaos_args.rs`):
  `server_chaos_set` and `server_chaos_clear` take `account`;
  `server_chaos_status` adds `armed` (and `armed_more`). The account name
  resolves through `tools/account_lookup.rs`
  (`SELECT account_id FROM account WHERE account_name = $1`, the same exact
  match as the auth credential lookup).

## Ordering: why the arm is on the session before any flush reads it

The flush reads chaos in three places, all after `onClientReady`:
`chaos_wants_hold` (under the `connected` lock in `handle_on_client_ready`),
`flush_delay` (each hold release) and `flush_chaos::apply` (each flush).
Each first calls `clear_if_not(addr, witness_id)`. The client sends
`onClientReady` only after ENABLE_ENTITIES, which answers the
RESET_ENTITIES that `handle_play_character` sends after the promotion, and
the receive loop awaits `handle_play_character` before it reads the next
packet. So the entry exists, tagged with the same entity id the witness id
will carry, before any of the three runs, and `clear_if_not` keeps it. A
brand-new character's first login takes the same `playCharacter` path; the
held path (`hold_play_character`, waiting on a cooked-data resync) runs
`handle_play_character` later, still before RESET_ENTITIES.

`play_character/chaos_tests.rs` drives `handle_play_character` and then
`handle_on_client_ready` with a lent registry: the armed `Delay` holds the
first flush. Tagging the promotion with any other entity fails it (checked
by mutation: tag 0, both tests fail).

## Decisions

1. **Key: account id (u32), not the name.** The session carries
   `account_id` at world entry; the tool resolves the name once, exactly as
   login does, so an arm cannot wait for an account that login never picks
   (a case-only match).
2. **Logging the account.** The registry logs `account_id` only (marked
   `nt:id-only`): it is never given the name. The tool's `lab.tool_call`
   audit row keeps the arguments as sent, the name included, as it does for
   every lab tool; account names are logged next to ids across the server
   under Rule 6, so this adds nothing new. No password or token passes
   through the tools.
3. **Reach.** Any account may be armed, as any entity may be set. An arm
   does reach further than a set: it waits for an account that is not
   online, up to its TTL, and attaches at that account's next login. Only
   deployment keeps it off real players (no colo image is built with
   `lab-chaos`; the registry also needs `DEVELOPER_MODE`). There is no
   GM-account gate (the fixture tool has one because it writes rows; chaos
   writes none and expires). An armed net profile does not shape
   authentication, the character list or `playCharacter` itself: shaping
   starts with the RESET_ENTITIES send.
4. **Teardown and relaunch.** An arm survives teardown, character select
   and a relaunch takeover: all come before the account's next world entry.
   It is spent by exactly one `playCharacter`; a promoted entry then
   behaves like a `set` one (cleared by teardown and character select).
5. **Exactly one target, checked in the parse.** Both or neither of
   `entity_id` and `account`, and an empty `account`, are refused as
   `bad chaos knob:` before the registry is looked at, so a malformed call
   says so even on a server where chaos is off.
6. **Not consumed by gate travel or reanchor.** Only `playCharacter` is a
   world entry for D-CH10.

## Differences from the packet

- `clear(None)` returns sessions plus arms, so `{cleared: n}` from a clear
  with no target counts both.
- `server_chaos_status` always carries `armed` (empty `[]` when none); a
  consumer that compared the whole reply to `{sessions: []}` must expect
  `{sessions: [], armed: []}`.
- Fixed in passing: the `records` and `shift` argument docs in
  `chaos_args.rs` still said 1 to 255 and 0 or 2 to 36 (pre-CH-07).

## What CH-15's runner must send

Before the row's login steps (before `lab_login` / `lab_play_character`,
or before the relog when the character is already in the world):

```json
server_chaos_set {
  "account": "<the lab account name the client logs in with>",
  "flush": { "mode": "shift", "shift": 3 },
  "ttl_s": 600,
  "label": "flush:shift len=3"
}
```

(any profile `server_chaos_set` takes; `seed` only when the profile reads
one). Expect `{armed: true, account_id, expires_in_s}`; anything with
`refused` stops the row. Pick `ttl_s` to cover the login plus the row: it
counts from this call, not from the world entry.

After `playCharacter`, confirm the attach: `server_chaos_status` lists the
character's entity id under `sessions` and nothing under `armed` for that
`account_id`, or `server_log_tail` with `target: "lab.chaos"`,
`contains: "set on its new session"` shows the `lab_chaos_promoted` row. If
the arm is still listed, the login never reached `playCharacter` (or the
entry failed and gave the arm back, `lab_chaos_rearmed`): report it, do not
grade the flush.

The attach alone does not grade the row. Grade a chaos login only after a
`lab.chaos` flush row for that entity (`witness_id` = the promoted entity
id): `flush_packed`, `flush_shift_packs` (with `flush_shift_swept` for a
sweep), `flush_reordered` or `flush_delayed`, whichever the profile makes.
A session entry with no flush row means the flush never read it.

Teardown, always (a row that failed before its login leaves the arm
pending for the next login on that account):

```json
server_chaos_clear { "account": "<the same name>" }
server_chaos_clear { "entity_id": <the promoted entity id> }
```

or one `server_chaos_clear {}` when nothing else on the server is under
chaos.

## Review fixes

From three reviews of the packet commit. Each has a test that fails with
the fix reverted (checked by hand for the first two and for the adjacent
fix).

1. **Promotion only onto this entry's session.** A held `playCharacter`
   runs on its own task and the handler awaits the fixture write, the
   world-entry query and the cell, so a teardown or a relaunch takeover
   could leave another session at the address, and the promotion (keyed by
   address) put chaos on it and spent the arm. The entry latch now keeps
   the session's `cancelled` Arc as its owner token, and
   `play_character/chaos.rs::promote_if_owner` promotes under the
   `connected` lock only while `connected[addr]` holds that same Arc
   (`Arc::ptr_eq`). Lock order: `connected`, then the registry's sessions,
   then its arms, as `chaos_wants_hold` already does. Test:
   `promote_if_owner_skips_a_replaced_session`.
2. **Adjacent fix (same root cause, pre-existing): the late handler's
   writes.** The same unchecked handler wrote the old character's world
   entry (entity id, world, ids, pending entry) into the replacing session
   and sent RESET_ENTITIES under the old session's key, the address-keyed
   late writer class from the #1246 review. `play_character/mod.rs` now
   checks the owner before the send and again before the store (and before
   resetting the latch on the `NO_ENTITY_ID` bail), logs a WARN
   `reason = "session_replaced"` with the account, character and entity,
   and abandons the entry. The reliable-send registration moved after the
   store check, so it never lands in a new session's channel. Tests:
   `play_character_leaves_a_session_replaced_during_the_cell_wait` and
   `..._during_the_send`. Not handled: the cell entity `query_world_entry`
   created for the abandoned entry stays registered (as it did before).
3. **Take and insert are one step.** `promote_armed` takes the registry's
   sessions guard first, then the arms lock, removes the arm and inserts
   the entry before releasing sessions; `clear(None)` holds both, sessions
   first, while it clears. A clear of everything finds the arm or the
   promoted entry, never neither. Tests (lock order, deterministic in the
   passing direction): `a_promotion_takes_its_arm_under_the_sessions_lock`,
   `a_clear_of_everything_holds_the_sessions_lock_over_the_arms`.
4. **The arm comes back when the entry fails after promotion.**
   `promote_armed` returns a `Promotion` (address, generation, the arm as
   taken, an operator-clear count). On any error after it, or an entry
   abandoned for a replaced session, the handler calls `rearm`: it removes
   the promoted entry (that generation only) and re-arms the account with
   the same knobs and `expires_at`. It does not when the arm has expired,
   when the account was armed again (the newer arm stays), or after an
   operator clear (everything, the entity, the account) since the
   promotion, so a failure cannot bring back chaos the lab cleared.
   Teardown is not an operator clear. Tests:
   `a_failed_entry_after_the_promotion_gives_the_arm_back`,
   `a_session_replaced_after_the_promotion_gives_the_arm_back`,
   `a_world_entry_that_never_loads_leaves_the_arm` (the `NO_ENTITY_ID`
   bail), and the `rearm` cases in `lab_chaos/tests_promotion.rs`.
5. **First login.** `armed_pack_reaches_a_first_login_flush` arms a
   `Pack`, runs `playCharacter` and a `first_login: 1` `onClientReady`, and
   checks the flush released after the intro-movie hold logs
   `flush_packed` for the new entity (the #1341 case CH-11 reproduces).
6. **Account name cap.** `account` over 32 characters (the
   `account.account_name` column) or with a control character is refused
   by the parse on set and clear, without echoing it; `audit_args`
   replaces such a name by its length, as for labels.
7. **Docs.** The guide and this worknote now say an armed net profile does
   not shape authentication, the character list or `playCharacter`, that
   an arm reaches offline accounts up to its TTL and only deployment keeps
   it off real players, and that CH-15 grades only after a flush row.
   `play_character.rs` became `play_character/` (handler, `chaos.rs`,
   tests, test fakes); the registry's clears moved to
   `lab_chaos/clear.rs`.

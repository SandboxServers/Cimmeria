## Design decisions

- **Coordinator's "length cap only, do not rebase onto #871" (2026-09-27)** arrived after #871 had already merged into `main` (`953d9e3c`). The branch is rebased onto a `main` that contains it, so the cap is the `org_text` one; reverting to a local cap now would be the second filter the contract forbids. The integration edit the coordinator planned is therefore already done.

- **The index is a view over `connected`, not a second map.** A maintained `Arc<Mutex<HashMap<name, ..>>>` would have to be threaded into `destroy_client_entities` (four callers), `abandon_unspaced_session`, `handle_log_off`, `handle_play_character` and every lookup site, all contended files, and every future teardown path would be one more place to forget it. As a view, removing the session removes the listing. The one in-session state the view cannot infer, "this character left the world but the session lives on" (full-exit `logOff` keeps the session and `player_name` until the client's disconnect reaps it), is the `listed_online` flag. Consequence: `helpers/mod.rs` (`destroy_client_entities`, ORG-06's file) is **not** edited, so cimmeria-fa need not be told about a line there. Cost: a lookup is O(sessions) with a lowercase allocation per listed name on an exact miss, which is nothing at our player counts; callers must rate-limit before looking up.
- **Listed at `onClientReady`, not `playCharacter`** (Copilot on #880, coordinator decision). `play_character` names the session; `handle_on_client_ready` sets `listed_online` in the same critical section that takes `pending_client_ready`, so the client has created the player entity before a tell or challenge can find it, and a `logOff` that cleared `pending_client_ready` first leaves nothing to list. It lists only when not already listed: gate travel re-runs `mapLoaded` / `onClientReady` for a character that stays listed, and must not log a second `online_index.insert`. Reanchor does not pass through `onClientReady` at all.
- **Name `OnlinePlayer` collides** with the admin-API snapshot `base::OnlinePlayer`. The contract name is kept inside `player_index`; it is not re-exported at `base::`.
- **Bucket before length cap.** An over-long line spends a token, so a client cannot turn a stream of bad packets into a stream of feedback packets.
- **Integer tokens, whole periods.** Partial progress is kept by advancing `last_refill` by whole periods; a backwards `Instant` earns nothing.
- **`notify` per category**, so a chat flood does not suppress the mail or duel feedback.
- **`rate_limit.exceeded` level:** WARN when it notifies (at most one per category per player per 5 s), DEBUG for the silent drops. The per-line `sendPlayerCommunication` INFO row now fires only for lines that pass both gates (server-authority review finding: it logged the client-supplied target on every packet, before the bucket).
- **GM exemption** reads `ConnectedClientState::access_level`, set only from the login row. `CHAT_EXEMPT_ACCESS_LEVEL = 2` repeats `cimmeria_commands::AccessLevel::GameMaster` rather than adding a dependency edge to the session crate.
- **`feedback.rs` uses the wire crate's serializer** (`cimmeria_wire::cell::chat::serialize_on_player_communication`), not a third copy; `gm_feedback.rs` lost its private copy. `send_gm_feedback_to_client` keeps its signature and addresses `entity_id` as before; its entity-to-address miss now logs `GM feedback: no client addr for entity` (reason `entity_to_addr_miss`) instead of the generic AoI line.
- **Feedback texts** (project policy): chat and mail "You are sending messages too quickly."; duel "You are sending duel challenges too quickly." (provisional, SS-D1 may swap it for a client text id); over-cap "Your message is too long."; any forbidden character "Your message contains a character that cannot be sent.".
- **`chat.rejected` reasons** are `TextReject::reason()` (`too_long`, `control_char`, `bidi_control`, `zero_width`, `format_char`, `line_separator`), the ORG vocabulary, not a chat-specific one.

## Text rules (D-SS12) and ORG-01

ORG-01 (`org_text::validate`, `TextField`) was still open (#871) when SS-00 started, and the first two commits shipped only the length cap; the coordinator was told. #871 merged before the push, so after the rebase SS-00 follows the contract as written: `TextField::ChatText` (0 to 255 UTF-16 units, one line, not normalised) is added to `org_text`, `MAX_CHAT_TEXT_UNITS` moves to `cimmeria_entity::organization::limits` (re-exported from `rate_limit::limits`), and the chat path calls `validate(TextField::ChatText, &text)`. There is no second filter. The cap is 255, provisional until SS-E1 C-Q3 reports the client input cap (SS-E1 has not landed; `chat-wire-formats.md` has no cap). cimmeria-fa should know `org_text.rs` gained a variant.

Ids follow [instrumentation-discipline.md](../../../architecture/instrumentation-discipline.md) Rule 5: every player-activity log carries `account_id` and `player_id`, the stable identities, and `entity_id` "stays alongside them" as the per-space correlator. Rule 5 does not require `entity_id`; it is on the chat and rate-limit events (Copilot on #880) so they join the entity-scoped stream, for example `player.journal`. The `online_index` events carry `addr` instead, because the index is keyed by session, not entity.

`online_index` is a new target: `online_index=debug` in `OTEL_FILTER`, pinned at DEBUG in `scan_finds_known_targets`. `log_unlisted` is called from `destroy_client_entities` (`helpers/mod.rs`, ORG-06's file: one line, before the session is removed).

Regression proof for the telemetry (mutation, then restore): removing the `log_unlisted` call from `destroy_client_entities`, `logOff` or the gate-travel abandon, the `log_listed` call from `play_character` (now `handle_on_client_ready`), the `missing` lookup row, or `account_id` from `rate_limit.exceeded` each made its guard in the table FAIL.

### SigNoz queries

Run these in the SigNoz logs explorer, filtered to `service.name = 'cimmeria-server'` and, on the colo, `cimmeria.deploy_env = 'colo'`. Start from the player's `.bug <note>` bookmark for the timestamp. SigNoz exposes a Rust tracing target as the `scope_name` field ([observability.md](../../../architecture/observability.md), "Stable target catalog"), so every query below filters on `scope_name`; there is no `target` key.

| Question | Query |
|---|---|
| Why was my chat line dropped? | `scope_name = 'rate_limit' AND player_id = P`. `tokens` and `next_token_ms` show how close to the limit the player was; rows at DEBUG are the suppressed repeats. Then `scope_name = 'chat' AND event = 'chat.rejected' AND player_id = P`, grouped by `reason` |
| What else did that entity do around the drop? | `entity_id = E` from the `rate_limit.exceeded` or `chat.rejected` row, near T, across all scopes; `scope_name = 'player.journal' AND entity_id = E` for the ordered per-player story. Filter on `player_id` once the session ends, since entity ids are recycled |
| Is someone flooding? | the `rate_limit_exceeded_total` metric by `category`; drill in with `scope_name = 'rate_limit'`, grouped by `player_id` |
| Was player X online at time T? | `scope_name = 'online_index' AND player_name = 'X'`, ordered by time. The last `online_index.insert` before T, with no `online_index.remove` between it and T, means listed; the `path` on the remove says how they left |
| Why did a tell, mail or duel say "no such player"? | `scope_name = 'online_index' AND event = 'online_index.lookup'` near T. `reason = missing` means not online or misspelled; `reason = ambiguous` with `listed` means the name matched more than one character |

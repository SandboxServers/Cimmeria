# DW-03S-C — bounded Mercury-shaped receive candidates

The lab bridge mints a fresh 128-bit OS-random epoch when it starts. It is independent of the telemetry session ID and is returned by `events_read`. The existing Winsock `recvfrom` IAT detour remains the sole receive hook: it calls the original first, reads a successful bounded datagram, preserves its error code, and sends at most one lab `mercury.wire_proof` candidate row per qualifying read. The row has the bridge epoch, diagnostic socket and parsed IPv4 peer when available, exact UDP wire-byte length and 16-digit FNV-1a fingerprint. The Phase-3 login reply is plaintext before AES; the row does not prove encryption. It contains no payload bytes or process identity.

The `events_read.mercury_wire_proof` snapshot has `hook_installed`, `received`, `rejected`, `dropped` and `gap`. Before any qualifying read its gap is `hook_unobserved`. A shape match is `source_kind: recvfrom_candidate`, `eligible: false`, `encryption_state: unknown` and `gap: mercury_socket_unverified`; a missing parseable peer retains `peer: null` and `peer_gap: peer_unavailable`. Every unverified candidate increments rejected, as do nonmatching request shapes. A same-shape unrelated socket can never yield eligible proof. The bridge event ring is bounded; a proof row lost to capacity increments the dedicated dropped counter. The supervisor must stamp its own PID and process creation ticks at ingestion in DW-03S-I. Neither the socket nor peer is a game-session identity.

Offline tests cover exact wire-byte fingerprint and serialization, no raw byte field, unknown peer, non-Mercury reads, counters, capacity plus one, bridge epoch rotation under the same telemetry session ID, and the `events_read` fixture. The 32-bit lab DLL built and linked. The native x86 stub fixture exercises the detour-to-record call and WSA error restoration. The hook and candidate row have not been observed in a live client.

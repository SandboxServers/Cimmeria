# DW-03S-D: Direct world-entry and Base send origins

> Status: implemented locally, pending review and integration. No live lab action.

Review amendment: the coordinator extended D's owned scope to `crates/base-session/src/base/helpers/{mod.rs,reliable_fit.rs,reliable_fit_tests.rs}` so an expected content owner can be checked inside the reliable helper before normal or fragment sequence/ACK reservation. This stayed within D's 45–50k packet ceiling; threading a receive-generation token through connect-loop callers is a separate packet. The packet-local world-entry reliable registration compares the original sequence Arc and boot/generation/peer/admission identity under the connected lock after send, and preserves `send_site`, kind and `mercury.reliable_send` context.

The two pre-Phase-3 login sends remain `send_to_pre_phase3`. The displaced-session LOGGED_OFF send retains the original evicted state only when that owner still exists; if replacement or removal happened before sequence reservation, it sends nothing. Inbound character create/delete/visuals, ENABLE_ENTITIES, mapLoaded, playCharacter and logoff handlers have no immutable ingress-generation token before their first connected-map lookup. A same-key A request may therefore first observe B. These replies use untagged transport sends even if B has a Phase 3 seed. Cell reanchor and gate-travel events likewise carry numeric entity IDs without an immutable event-generation ticket and remain untagged. All of these paths block `coverage_complete=true`; DW-03S-F must classify them as gaps until a separate ingress/Cell owner-token packet supplies the missing provenance.

Content captured after the first lock still carries its sequence Arc and origin through later awaits. `map_loaded` and both character-list reply paths verify the owner before packet construction. Create-player and character-visuals call `send_reliable_to_addr_for_owner`; the helper checks that Arc under its own connected-map lock before taking B's ACKs or sequence numbers, including its fragment route. Their owner-fencing transport refuses a later B helper ticket for A content. Its successful send is untagged, and its reliable entry uses an `_unproven` kind. The retransmit collector reads that marker from the exact cached-byte entry and leaves its resend untagged. Direct reanchor, gate-travel and other uncertain sends use the same marker. No retransmit can turn an unproven first send into B proof.

After-send `map_loaded` entity/address and pending-ready commits now check the original owner under the connected lock; `enable_entities` checks that owner before marking `char_list_sent`. Other gameplay-state races predate this proof packet: a relog before first handler lookup can process an A create/delete payload against B state, reanchor can resolve a reused entity/address to B, and Base login/dispatch teardown can act on a replacement after awaits. Later ingress-token and behavior work owns those transitions.

Regression: paused A world-entry send across same-peer B replacement stays unproven and cannot put A ciphertext in B's window; fragments have distinct wire fingerprints; failed sends add no successful row/window entry. Same-key replacement before the first handler lock produces no B proof, including create-player helper traffic. A-content/B-helper-ticket refusal, untouched B sequence/ACK state on normal and fragment reservation, unproven reanchor retransmit, mapLoaded and character-list post-await commit fencing, and send-site retention are tested. Base eviction paused/failure fixtures and a family source census remain. No live client, native receive hook or visual UI was used.

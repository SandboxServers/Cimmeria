# DW-13 causal trace handoff

The offline assembler and cookie-gated passive `GET /workbench/api/v1/trace`
are implemented. It reads the existing bounded client event store without
draining the bridge or advancing a named reader. It exports eight stages,
raw evidence for unique joins, unknown/ambiguous statuses, candidate counts,
the first gap, and a finite latency interval only when the two endpoints
share a bounded clock. The read API has no trusted server event source yet,
so its three server stages remain unknown. It does not infer a server event
from a client receive. `client.cme.event` and other `client.mercury.*`
rows are exported as bounded, unjoined snapshot context; CME is
deliberately unclassified as apply/visible evidence. The client click row
uses host ingest time; its unbounded Lua sampling delay means a live
click-to-visible interval is null.

**Scope amendment:** DW-13 named new causal modules and an API route, but
the supervisor's `EventStore` was private and `events_read` would have moved
another consumer's cursor. The parent authorized the smallest extra edit in
`crates/lab/src/supervisor/events/mod.rs`: `trace_snapshot` returns a capped,
non-consuming slice and the upstream drop total. Its regression test pins
eviction and drop reporting and unchanged `events_read` cursor.

Offline tests cover actual bridge-before-Lua ingest order, interleaved
production-shaped clicks/sends with unknown joins, a future-ID ambiguous
send, missing receive-to-apply/show identity, relogged cast-ID rejection,
failed shown handlers, a future eight-stage bounded latency fixture, and
cookie/instance, malformed-ID, eviction and drop API responses. The full
chain fixture uses synthetic identity fields and is not evidence of current
live capability. No live game client, server, pixels, or clock calibration
was used. DW-14 should display unknown stages and null latency explicitly.

## Blocked dependencies for follow-up DLL packets

| Dependency | Current evidence gap | Proposed bounded packet |
|---|---|---|
| `BlockedDependency: click_to_send_identity` | `ui.click` carries `event_id`, but stock `client.ability.sent` and `client.net.out` do not. One pump stores bridge rows before the Lua click, so store order and timestamp cannot fill the gap. | A separate 40–45k packet in the client telemetry click/ability/net hooks: propagate a verified per-click identity across the UI handler and outbound send on the same process epoch, stamp it at emit time, and add two interleaved-click and relog tests. Keep non-click sends explicitly unbound. |
| `BlockedDependency: receive_to_apply_show_identity` | Stock `client.ability.applied` and most `client.ability.shown` rows lack a stable receive/cast key. A matching cast integer alone can repeat after relog. | A separate 40–50k packet in the client telemetry receive, apply and shown hooks: carry a verified receive/cast identity plus process/session epoch to the handlers where the stock path exposes it, report exact gaps elsewhere, test concurrent casts, relog reuse and failed handlers. |

Both packets depend on an ingestion-time process/session scope for bridge
events. They must preserve the injected DLL's existing fail-closed hook
policy and avoid any speculative wire decoder. The current server stages
also await the independent session-bound server capture work.

## 2. Server origin and send path

`crates/base/src/base/service.rs::BaseService::start` constructs one `Arc<dyn BidirectionalTransport>`, projects clones to `Arc<dyn Transport>` for the receive loop, Cell message loop and sweepers, and starts tick/handler tasks. Production uses `crates/mercury/src/transport.rs::UdpTransport::send_to`, which awaits `UdpSocket::send_to(bytes,addr)` and has only `(bytes,addr)` at that common seam. The trait has **no immutable session-origin argument**. A wrapper at this seam can observe exact post-send bytes and success, but a lookup by address after the await can mislabel an old send as a replacement connection. The outbound sampled `mercury.packet` log there is not a complete proof ring.

`crates/base/src/base/login/mod.rs::handle_login` sends encrypted connect-reply and time-sync **before** inserting `ConnectedClientState { connected_at: Instant::now(), player_entity_id: None }` into the address map, then starts `run_tick_loop`; these two initial packets must be excluded from generation-bearing proofs or be explicitly associated with a pre-insertion origin that is outside the frozen contract. The ticket/peer relaunch path in `connect_loop/mod.rs::handle_datagram` can replace the session at the same address. `login/eviction.rs::send_logged_off` and `login/mod.rs::handle_log_off` also send at teardown. A generation based only on `addr` is therefore unsafe.

This inventory covers production `transport.send_to` call sites under `crates/base`, `base-session`, `base-world-entry`; the `crates/mercury` transport itself and optional chaos/lossy transport can delay sends further. `crates/base-session/src/base/helpers/reliable_send.rs::shadow_register_reliable_send_with_details` calculates encrypted length/fingerprint and logs a reliable registration, but is not a complete post-send observer: unreliable tick/witness sends and retransmits are absent, and its session lookup happens at registration time. `docs/protocol/mercury-wire-format.md` § reliable-send diagnostics explicitly describes FNV-1a fingerprint and cached encrypted retransmit bytes. A fingerprint is a diagnostic observation key, never authentication.

**BlockedDependency:** DW-03S-S owns `crates/base` files only, yet the source shows no common API that carries immutable `SendOrigin` through every awaited `Transport::send_to`. A BaseService-only wrapper with a peer-keyed registry cannot prove A versus B after peer reuse. Before DW-03S-S code, revise its ownership/design to include a typed origin-carrying seam in `crates/mercury/src/transport.rs` **and** the sending helper/caller modules above, or narrow the proof contract to explicitly covered paths and leave all other joins unknown. Do not silently attach origin after send. The exact mechanism (ticketed trait method, task-local scope proven across async fan-out, or explicit call-site instrumenting) needs a design and regression fixture; a task-local guess is not evidence.

## 3. Authoritative roster and lifecycle

`BaseService::online_players` in `crates/base/src/base/service.rs` filters `world_entry_sent`, returns `OnlinePlayer`'s entity ID, name, world, status and `session` formatted from UDP address. `crates/lab-mcp/src/state.rs::online_players` and `tools/sessions.rs::{list_sessions,shape}` expose this as `server_sessions`. It has no server boot ID or session generation and cannot bind a DLL instance. `crates/lab/src/workbench/dossier.rs::server_bound` currently compares address/session and entity ID, while live dossier input keeps server fields unknown. The new generation-bearing lab-only roster must replace that predicate, not decorate it.

The current `BaseService::new/start/stop` lifecycle in `service.rs` has no boot ID. `login/mod.rs::handle_login` inserts `connected_at`; duplicate login eviction (`login/eviction.rs`) and logoff (`login/mod.rs::handle_log_off`) destroy old connected state. Gate travel in `crates/base-world-entry/src/base/world_entry/gate_travel/mod.rs::handle_gate_travel` retains the connected session while setting `pending_player_entity_id`, pending entry, and destination `world_name`; its early-abandon path removes the session. `gate_travel/session_owner.rs` checks the owner around awaits. A gate trip eventually changes roster world, but after the origin-space teardown and before the later destination world_name assignment, the roster world and status can stay unchanged. The generation-bearing roster must expose an authoritative gate-transition epoch/state (or an equivalent fail-closed transition signal) that changes no later than origin-space teardown and remains in progress until arrival settles; the binder must reject a transition in progress even when two ordinary roster snapshots are byte-for-byte equal. A completed trip also invalidates any cached dossier join even if the underlying generation remains the same. A process/server restart rotates epoch/boot; relog rotates generation even at the same peer.

The compact tuple order above is literal and fixed; the Rust binder test should use typed struct literals rather than parse the table. `f1/f2/g1/g2` denote distinct 16-hex-digit fixture fingerprints, e.g. `0000000000000001/0000000000000002/0000000000000003/0000000000000004`. They are test data, not captured game traffic. For rows with a client pair, `process_now` is `{instance:lab-a,pid:41,process_created_ticks:10001,bridge_epoch:e1}` unless overridden. Both `Unit.Player` observations must equal the current roster player. Before/after roster reads must be full equality on boot, generation, entity, world/shard and active state, plus an authoritative gate-transition epoch/state. A transition-in-progress state refuses the join even when the ordinary roster tuple and displayed status stay the same. If no such authoritative transition signal exists, keep joined server fields unknown rather than assuming stability from unchanged roster fields. No joined server field is populated on any named gap.

## 5. Stop conditions and verification

DW-03S-C must demonstrate the Mercury-only hook, exact encrypted bytes, source peer when parseable, bridge epoch and drop status offline; absent live hook observation remains `hook_unobserved`. DW-03S-I must stamp identity at both drains and reject delayed old-process batches. DW-03S-S cannot proceed with the current all-send contract until the origin ticket crosses the transport await and retransmit collection without an address-only lookup; this is the **packet scope/design blocker** found by static tracing. DW-03S-X must return a unique active generation-bearing roster with server-clock capture time and an authoritative gate-transition epoch/state (or a fail-closed transition signal); DW-03S-B must reject an in-progress or changed transition signal. DW-03S-B keeps DW-03's `server_session_unbound` fail-closed state until all producers exist. Live proof belongs to DW-35 after separate owner approval.

Validation here: paths/functions were checked against the current source tree and protocol findings; no executable or lab test was run. The fixture is a specification for later regression guards, not evidence of a live client/server match.

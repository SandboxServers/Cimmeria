Why `Window/MouseClick` and not `PushButton/Clicked`: one subscription
covers push buttons (the title-bar X, `<Frame>__auto_closebutton__`), tab
buttons (whose own `Clicked` fires in the `TabButton` namespace) and the
image and text widgets the stock UI makes clickable. Subscribing both would
record every push-button click twice.

## What was built

`crates/lab/src/supervisor/events/lua_rings.rs`: a third ring, `click`, in
the same install-and-read chunk. Records are `{ window, button, mouse }`:

- `button`: the clicked window's name (`TutorialWin__auto_closebutton__`).
- `window`: the top-level window holding it, the ancestor whose parent is
  `Root`. These are the names `client_ui_state` lists under `windows`, which
  LR-11 compares against.
- `mouse`: `left`, `right`, `middle`, or the raw value.

They land in the event store as kind `ui.click` (`events/mod.rs`, with its
own `click_mark` in `store.rs`), and `client_wait_event` on `ui.click` pumps
the Lua rings (`wait.rs`).

Design points:

- **Once per Lua state.** With no `unsubscribeGlobal`, subscribing on every
  pump would stack handlers. The subscribe runs only while `L.click_host` is
  unset and sets it only on success. An interface reload rebuilds the Lua
  state (a new ring `epoch`), so the next pump installs again.
- **Host window:** `getWindow("Root")`, else `BackgroundWin`. Root is the
  ancestor of every window, so even if a global subscription were scoped to
  the host's subtree it would see every click. (`BackgroundWin` is a sibling
  of `TutorialWin` under `Root`, and the stock link-click subscription is
  no proof of a non-ancestor host: `RichTextItemEntry` windows live inside
  `Inst1ChatWin`, the window that subscribes.)
- **Own `pcall`.** The click install runs under its own `pcall`, so a fault
  there cannot cost the combat and chat rings their pump.
- **Never marks a click handled.** The handler returns nothing, so the stock
  handlers and CEGUI's bubbling behave as before.
- **Bubbling.** In CEGUI 0.6 an unhandled `MouseClick` is offered to each
  ancestor in turn, and every offer fires the global event. A fire at the same
  UI time and cursor position whose window is one of the previous record's
  ancestors (never the clicked window itself) is that bubble, and is
  skipped; a fire on `Root` is never recorded. Two real clicks on one
  widget both record. If `getSystemTime` fails (`t = 0`), the position alone
  decides.

## Not verified (needs a live client)

- That a global `Window/MouseClick` subscription on `Root` fires for clicks
  anywhere (expected: global events are not scoped, and Root is every
  window's ancestor regardless).
- Whether `getSystemTime` has fine enough resolution for the bubble check.
  If two fires of one click straddle a tick, the parent is recorded as a
  second click; LR-11 would then see a parent-window click with no step.
- Whether any stock handler marks `MouseClick` handled, stopping a bubble
  before our dedupe matters. Either way the deepest window is recorded first.
- The close button's name in a click record. The widget is named
  `<Frame>__auto_closebutton__`, as LR-11 expects: `client_window_click
  {target: "TutorialWin__auto_closebutton__"}` closes the tutorial live
  (first-session calibration, `.claude/agents/lab-driver.md:49`). It has not
  yet been seen in a `ui.click` record.

LR-13 (live acceptance) is the first run that sees a real `ui.click`.

## Offline check

The Rust tests only check the chunk's text (the workspace has no Lua
runtime). After review, the rendered chunk was run under Lua 5.1 (`lupa`)
with stub windows `Root > TutorialWin > TutorialWin__auto_closebutton__`:
it installs once (`installed`, then `ok`, one subscription), records the
close-button click as `TutorialWin` / `TutorialWin__auto_closebutton__` /
`left`, drops the same click's fires on `TutorialWin` and `Root`, and keeps
two more real clicks on the same widget in the same clock tick.

## For LR-11: the sampler must pump the Lua rings

The subscription is installed, and the ring read, only inside
`pump_events(true)` (today: `client_wait_event`, `combat_log`, `chat_log`,
defeat and `use_ability`). The recorder never calls those, so LR-06/LR-11's
sampler must call `pump_events(true)` itself: once at start (clicks before
the install are lost) and every tick, before reading `ui.click` from the
store.

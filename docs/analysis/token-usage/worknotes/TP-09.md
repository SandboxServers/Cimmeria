## Numbers for the ledger

Profiler database ingested 2026-10-03 13:15Z, transcripts 2026-09-17 to 2026-10-03 (17 days). USD is list price, a plan-usage proxy.

**Method.** A rebase episode starts at a Bash call that runs `git rebase` (not `--continue`/`--abort`/`--skip`), `git merge ... main` or `git pull`, and takes in the same transcript's following requests while they are rebase-related (continue/abort, conflict output, `git add` or `checkout --ours/--theirs` after a conflict), ending at the next `git push` or after a gap of more than 25 requests. Conflicted files come from `CONFLICT (...)` and `both modified:` lines in tool results. The episode's cost is every request in it, whole context included. The window is a heuristic: an episode that ends at a push can include unrelated work before the push, so the request and USD figures are upper bounds.

**What the script saves.** The large item is the clean case. 494 clean rebases took 2,933 requests (about $0.18 each at the contexts above); the script makes each one a single tool call, saving about 2,400 requests and roughly **$440 per 17 days (about 4% of spend)**, an upper bound because of the episode window. For the 113 conflicted rebases the gain is that a fresh worker starts at about 70k tokens instead of the median 315k, and gets the conflicted file list up front; at most about half of the $244, not measured.

## Done

- `tools/build-lane/rebase-pr.sh` (wrapper) and `rebase_pr.py`: target is a PR number (`gh pr view`), branch, or worktree path; fetches `main` and the branch; refuses a dirty worktree, a rebase in progress, or (with `--push`) an origin branch with commits the local one lacks. The rebase runs in a throwaway worktree with an index only, every entry skip-worktree, so nothing is checked out (setup is about 0.1 s; `read-tree -mu` cost 6 s in this repo). On success it moves the branch (`reset --keep` in its worktree, or `update-ref` with the old value) and pushes with `--force-with-lease` against the head fetched at the start, only with `--push`.
- Mechanical resolution only:
  - **Generated blocks** (`<!-- gen:NAME -->` and the crate graph): every body is blanked on all three sides; if that merges cleanly, the bodies are refilled from main's side (the branch's for a block only it has). A block that is duplicated or added beside one main has is semantic.
  - **`Cargo.lock`:** main's copy, then `cargo update --workspace` (`REBASE_PR_LOCKFILE_CMD` overrides). It restarts in a full checkout, since cargo needs the manifests.
  - Anything else, including added or deleted files: abort, the branch and its worktree untouched (contents and mtimes, so no rebuild), and `status=conflict`, `semantic=`, `mechanical=`, `stopped_at=` and `preview=` (every file a squashed merge conflicts in, from `git merge-tree`). `--json` gives the same as one object. Exit 0 clean, 1 semantic, 2 precondition, 3 git or push failure.
- **Found and fixed: `merge=union` duplicates generated rows.** `docs/readme.md` is `merge=union` (#923) and holds generated counts. A smoke rebase of a throwaway branch 40 commits behind `main` that edited prose on a count line rebased "cleanly" with the row twice, once with each count; plain git does this today. The script reads attributes from a copy of main's tree in which union files that have generated blocks are `merge=text`, and resolves them with union outside the blocks. `.gitattributes` now says so beside the `docs/readme.md` entry.
- 16 tests in `tools/build-lane/test_rebase_pr.py`, each in a throwaway repository with a bare origin: clean (silent, worktree follows, shared config unchanged), up to date, branch without a worktree, push with lease and diverged-origin refusal, inline and table generated blocks, crate graph, lockfile, union (no duplicate row; appended rows still both kept), semantic conflict (HEAD, status, contents and mtimes unchanged, no scratch worktree left, generated block reported as mechanical), prose beside a generated block is semantic, dirty worktree, three resolver unit tests including CRLF, and the bash wrapper. The union test fails without the attribute override. The `build-lane job log tests` step in `test.yml` already runs `test_*.py` in this folder.
- Smoke on the real repo (throwaway branch, deleted afterwards): the generated-block case resolves in 5 s without fetch (the remaining time is moving the real worktree 40 commits); a semantic case reported its files and left the branch alone.
- Docs: a worker rule in `development-workflow.md`, a sentence in `build-system.md` §3, a row in `tools/README.md`.

## Left

- Not tried on a real open PR (the packet forbids touching other branches). The coordinator's first use is the real test.
- `cargo update --workspace` was not run by the tests (they use the override). The one lockfile conflict in the data predates this; if it misbehaves, set `REBASE_PR_LOCKFILE_CMD`.
- workspace-hack conflicts are reported as semantic; none were seen. `cargo hakari generate && cargo hakari manage-deps --yes` could be added the same way as the lockfile if they appear.
- During the rebase the attributes come from main's tree, so a branch that changes `.gitattributes` is merged under main's rules.

```bash
bash tools/build-lane/rebase-pr.sh <PR> --push      # coordinator use
```

The measurement was a scratch script over the profiler database and the transcripts it lists (`ingest_files`), not committed: it reads raw transcript text, which the profiler's scrubber does not cover. The method above is enough to redo it; TP-11 could fold it into a report section.

## Open questions

1. Should the coordinator run the script before every merge, or only when GitHub says the PR is behind? It costs one tool call and about 5-10 s either way.
2. Should `docs/readme.md` stay `merge=union`? With the script it is safe; with plain git a count line can come out twice. Taking it out of the union list trades that for an append conflict now and then.

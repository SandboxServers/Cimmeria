## Behaviour the runner (FX-06) can rely on

- Success: `{ "staged": true, "player_id", "player_name", "replaced" }`,
  `player_name` the full `sgw_player.player_name`.
- Every refusal is a JSON-RPC `invalid_params` error (code -32602) whose
  message starts `stage refused: `. Through `ServerTools::call` it arrives
  as a failed `ToolOutcome` with `error = "lab-mcp error -32602: stage
  refused: ..."`, not as an `isError` result: the other `server_*` tools
  return `isError` results, this one follows the contract.
- A database failure (the character or a seed lookup) is not a refusal
  of the call: it is a JSON-RPC `internal_error` (code -32603) whose
  message still starts `stage refused: ` and says `lookup failed`.
- A malformed call (unknown field, bad state string, missing `character`)
  is a `stage refused: arguments: ...` refusal too, naming the field's
  path (`arguments: missions[0].state: unknown variant ...`,
  `arguments: items[0].count: ...`, `arguments: character: missing`;
  an unknown top-level field is named in serde's own message), and is
  audited: the
  tool takes the raw JSON (`StageFixtureCall`, whose schema is
  `StageFixtureArgs`'s) and parses it itself, because rmcp would otherwise
  reject it before the tool body with its own message and no audit row.
- Character match: `lower(player_name) = lower($1)` or the last
  space-separated word of `player_name` equal case-insensitively;
  exactly one row, else `matches no character` / `matches N characters`.
- Fixture character: the matched row's `player_name` must end in a word
  matching `^Fx[A-Za-z]+$` (case-sensitive), the shape of the runner's
  `fixture_character_name` (`crates/lab/src/uat/fixture.rs`). Otherwise
  `character <full name> is not a lab fixture character (last name must
  be Fx...)`, before the GM gate, so a token holder cannot stage onto a
  real GM's main and a probe learns nothing about a real name's account.
- Offline or mid-login: a session whose `player_id` is the character's,
  or (before `playCharacter` set one) whose name equals the character's
  full name, refuses it. A character whose world entry has not been sent
  yet counts as offline; a fixture staged then applies at that account's
  next Play within 10 minutes. A nameless character-select session of the
  same account does not block staging, so the runner may stage while
  logged in at character select.

## Logging

Every refusal logs exactly one event, message `lab fixture stage
refused`, with `reason`, `error` (the refusal text) and, once the
character resolved, `player_id` and `player_name`:

- WARN for a caller refusal. Reasons: `arguments`, `no_database`,
  `no_character` (empty name or no match), `ambiguous`,
  `not_fixture_character`, `not_gm`, `online`, `position`, `world`,
  `mission`, `step`, `item`, `tutorial`.
- ERROR `lookup_failed` for a database failure, with the sqlx error in
  `error`.

Success stays the INFO `lab fixture staged`.

## Deviations from the spec

- **World lookup.** The spec said "the same lookup `.gotolocation`
  uses". `.gotolocation` resolves through the cell's in-memory world
  catalog, which this endpoint can only reach by a cell round trip. The
  tool uses the base precheck's lookup instead (`resources.worlds`, the
  foreign key `sgw_player.world_location` needs), which is what the apply
  would refuse on.
- **Items are accepted although FX-02's apply still refuses every item
  list** (`ITEMS_NOT_YET`). FX-03 removes that refusal; refusing here
  would need a follow-up edit when it lands. Until FX-03 merges, a staged
  item fixture is accepted and then logged "lab fixture not applied"
  (`reason = "precheck_refused"`) at Play.
- **Duplicate item design ids are refused**, a check the spec does not
  list: FX-03 deletes every carried instance of a design and then grants,
  so a second entry for the same design would undo the first.
- **Online refusal wording** uses the name as requested
  (`character Fxpraxisdefa is online`), matching the contract example.

## The context seam, and its accepted risk

`stage_fixture(&LabState, call)` is `stage_from(ctx, call)` over the
`StageContext` trait (`pool()`, `roster()`). Production's impl for
`LabState` is two forwarding lines to `LabState::db_pool` and
`LabState::online_players`; the tests' `FakeContext` returns a fixed pool
and roster, so the path from the roster to the online gate, and every
refusal's log line, is the one the tool runs. Accepted risk: the
`LabState` impl itself is not under test, because a `LabState` needs an
`Orchestrator` with a live base session to have a non-empty roster, and
no test in the crate builds one.

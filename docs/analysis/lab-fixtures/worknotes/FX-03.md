## The write

One transaction for the whole list:

1. `take_inventory_locks(player, 1..=15)`: the player-wide advisory key,
   then one per carried bag, the shared inventory order (advisory locks,
   then item rows, then the player row).
2. Per item: `DELETE ... WHERE character_id = $1 AND type_id = $2 AND
   container_id BETWEEN 1 AND 15 RETURNING container_id` (bounds bound from
   `FIXTURE_CARRIED_CONTAINERS`). `removed` counts rows; the returned
   containers say whether anything left the bandolier (container 3).
3. Per item with `count > 0`: split into stacks of the design's
   `max_stack_size` (a non-positive size is treated as 1), take that many
   slots with `reserve_free_inventory_slots`, insert one row per stack with
   the grant INSERT's columns and defaults (durability 100, the design's
   charges, ammo type and types, `bound` from the BIND_ON_ACQUIRE flag).
   No room: Err, and the dropped transaction rolls the deletes back.
   `granted` counts rows (stacks), not units.
4. Bandolier reconcile (below), only when step 2 removed a bandolier row,
   then commit.

## Checks before any write

`plan_items` runs in the precheck, so a bad item refuses the whole fixture
(missions included) with `reason = "precheck_refused"`:

- static: a design listed twice, `count > FIXTURE_MAX_ITEM_COUNT`, a
  container other than 1 (`main`) or 2 (`mission`);
- the design must be in `resources.items` (its name and stack size are read
  here; error text says `item <name> (<id>)`);
- the design must allow the requested container, by the grant path's rule
  (`item_allows_container`, called directly): a non-empty `container_sets`
  must name it, and an empty or NULL one allows only the backpack (1). So a
  design with no sets cannot go to the mission bag, and a `{2}` or
  `{17,15}` design cannot go to the backpack. The refusal reads
  `item <name> (<id>) does not allow container <n>`;
- **a dry run**: the whole write above, in a transaction that is rolled
  back. Whether the stacks fit depends on what the deletes free, so the
  only exact answer is running the write. A full backpack is therefore a
  precheck refusal, not a `write_failed` after the missions landed. The
  real write can still fail (a concurrent change between the two), and
  then it rolls back on its own. A failed dry run rolls back explicitly
  before the refusal is returned, so the inventory locks are released at
  once rather than when the pooled connection is next used.

## What a fixture item does not do

- **A fixture never equips.** Every listed design is deleted from all
  carried containers, the equipment slots and the bandolier included, and
  re-granted into main or mission. Listing an equipped or readied weapon
  therefore unequips it; the carried-total verify (FX-05) still counts it,
  so the check passes with the weapon in the backpack. A row that needs the
  weapon in hand must equip it as a step, not through the fixture.
- **Bound designs** are written with `bound` from the design's
  BIND_ON_ACQUIRE flag and stack by `max_stack_size`, as the grant path
  stacks them.
- **Mission-consumed items.** A fixture that clears an item a mission step
  consumes (3730 while 622 is on its use step, for example) can strand that
  step: the step waits for an item the character no longer has. A fixture
  that stages a mission on such a step must list what the route to the
  step grants (the README Review outcomes FX-02 rule).

## Reviewer focus: dangling references after a removal

The only persisted pointer into the carried inventory is
`sgw_player.bandolier_slot`, a slot number in container 3. Nothing else
references an `sgw_inventory` row: no foreign key points at
`sgw_inventory.item_id`; mail escrow and org vaults hold their own rows;
equipment (containers 4 to 14) is rebuilt from the rows at load; the
character is offline when a fixture is staged (FX-04), so no trade or
session holds an instance id.

`onClientReady` reads `bandolier_slot` and the bandolier rows
(`query_bandolier_items`) separately and hands both to the cell. If the
fixture removed the active weapon while another stayed in the bandolier,
the slot would point at an empty slot and the character would load
unarmed with a weapon on the belt, a state no other removal leaves:
`sync_bandolier_after_inventory_change` moves the slot to the lowest
occupied one. So the write does the same, in its transaction, as the last
statement:

```sql
UPDATE sgw_player p SET bandolier_slot = b.slot
FROM (SELECT min(slot_id) AS slot FROM sgw_inventory
      WHERE character_id = $1 AND container_id = 3) b
WHERE p.player_id = $1 AND b.slot IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM sgw_inventory i WHERE i.character_id = $1
                  AND i.container_id = 3 AND i.slot_id = p.bandolier_slot)
```

An emptied bandolier keeps its slot value, as the sync leaves it: with no
bandolier rows the cell holds nothing either way. Guarded by
`live_db_fixture_removing_the_active_weapon_moves_the_bandolier_slot`.

The UPDATE runs only when the deletes returned a container-3 row. A
character whose slot already points at an empty bandolier slot (slot 0
with the only weapon in slot 1) is in a state the player left, and a
fixture that never touched the bandolier must not move it. Guarded by
`live_db_fixture_items_leave_the_bandolier_slot_when_the_bandolier_is_untouched`.

## Tests

`items_live_db_tests.rs` (all `live_db_fixture_*`, so FX-02's
`live_db_fixture` filter runs them):

| Test | Sentinel | Fails when |
| --- | --- | --- |
| `live_db_fixture_item_count_replaces_every_carried_instance` | `0x310` | the delete range is widened, even to `1..=16` (buyback row deleted) |
| `live_db_fixture_item_count_zero_removes_all_carried` | `0x320` | the same, over main, mission and chest |
| `live_db_fixture_item_into_the_mission_inventory` | `0x330` | (happy path: stack split into container 2) |
| `live_db_fixture_items_are_all_or_nothing` | `0x340` | the deletes commit when the grant fails |
| `live_db_fixture_full_backpack_writes_nothing` | `0x350` | the precheck's dry run is dropped (mission written) |
| `live_db_fixture_item_refusals_write_nothing` | `0x360..=0x36B` | any of the item checks is dropped, the container rule's two cases included (each case its own character, all failures reported) |
| `live_db_fixture_removing_the_active_weapon_moves_the_bandolier_slot` | `0x370` | the bandolier reconcile is dropped |
| `live_db_fixture_items_leave_the_bandolier_slot_when_the_bandolier_is_untouched` | `0x380` | the reconcile runs when nothing left the bandolier |

Each "fails when" was run as a mutation through the lane and failed as
listed (2026-10-11, three mutation runs; the review fixes' three guards in
one further run: range `1..=16`, container check removed, reconcile made
unconditional); the source was restored after.

Test designs are read from the seed, not hard-coded, and each satisfies the
container rule for the container it is granted into: `max_stack_size = 1`
designs the backpack allows (lowest two ids); a mission-bag design stacking
to 2..=4 (lowest id); a stackable backpack design for the all-or-nothing
and full-backpack grants. The refusal cases read a design whose
`container_sets` exclude the backpack and one with none.

## SQL shapes

All three match the character by the end of its name
(`player_name ILIKE '% <name>'`, FX-05's review), with the name guarded to
ASCII letters before it is formatted in:

- missions: `mission_id AS id, status, current_step_id AS step` from
  `sgw_mission`. Status 1 reads `active`, 2 `completed`, anything else
  `status <n>`.
- items: `type_id AS id, container_id AS container,
  coalesce(sum(stack_size), 0) AS n` over containers 1 to 15
  (`FIXTURE_CARRIED_CONTAINERS`), grouped by id and container.
- tutorials: `tutorial_id AS id` from `sgw_player_tutorials` (a row means
  seen, as in the verify step).

A truncated result is a snapshot error, not a partial snapshot: a missing
row would read as missing state.

## Parity rules as built

- World: when the fixture names one, the session's world must equal it
  (`world: chain is in X, fixture wants Y`, or `chain has no session`).
- Missions: active on the fixture's step; completed by status only (the
  objective arrays are not in the snapshot, and FX-02 leaves
  `active_objective_ids` empty where the route leaves the last roster);
  `not_active` means no row, as the verify step checks. Text:
  `mission 622: chain has step 2113, fixture wants 80623`, with `it
  completed`, `it not active` and `chain does not have it` for the other
  cases.
- Items: the carried total first (`item 55: chain carries 0, fixture wants
  1`); only when the total holds, the named container (`... carries 0 in
  container 2, ...`), so one wrong count is one line.
- Tutorials: `tutorial 5882: chain has seen it, fixture wants it unseen`.
- Missions the chain has and the fixture does not name: `unspecified`
  (`mission 1360: it completed`), a flag that never fails the row.

## Differences from the packet text

- **`Parity.snapshot_error`.** The packet's `Parity` has `mismatches` and
  `unspecified` only. A snapshot error is kept on it as well, so the row
  JSON says why parity was not checked and a re-grade can rebuild the
  reason. `Parity` also derives `Deserialize` (the row JSON is read back).
- **`lab_uat_attest` applies parity after its re-grade.** Without it, a
  row held at NEEDS_HUMAN or UNVERIFIED with a parity mismatch would become
  PASS once attested. `apply_parity` is the one place both callers use.
- **Mismatches on a result other than PASS are a flag**, not a reason, so
  they stay visible without restating the row's own failure; only PASS
  turns to FAIL, as the packet says.
- **Unspecified missions are also a flag** (`fixture parity: the fixture
  does not name ...`), so a reader of the ledger sees them without opening
  the row JSON.
- **`never` mode checks parity too.** It runs a fixture row on the chain
  path (`fixture_mode = chain`), so the row gets the same snapshot.
- **The snapshot calls are `kind = "fixture"`** like the rest of the
  fixture plumbing: lab-golden strips them, so a chain run and a
  fixture-mode run of the same row fingerprint alike.
- A chained row run with no lab endpoint gets the non-failing reason
  `fixture parity not checked: no server lab MCP ...`.

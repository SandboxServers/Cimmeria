## Mission row shape (for FX-05 verify and FX-10 parity)

| Fixture state | `status` | `current_step_id` | `completed_step_ids` | `completed_objective_ids` | `active_objective_ids` | `repeats` |
| --- | --- | --- | --- | --- | --- | --- |
| `Active { step_id }` | 1 | `step_id` | steps ordered before `step_id` | those steps' objectives | `{}` | 0 |
| `Completed` | 2 | NULL | every step | every step's objectives | `{}` | 1 |
| `NotActive` | row deleted | | | | | |

Confirmed against the code:

- **Completed repeats = 1.** `complete_mission_direct`
  (`crates/cell-content/src/cell/missions/progression.rs`) calls
  `MissionInstance::complete` (`crates/entity/src/missions.rs`), which
  takes `current_step_id` into `completed_steps` and does `repeats += 1`;
  a first completion from a fresh accept (`repeats = 0`) persists 1
  through `mission_update_msg` (`cell/missions/persist.rs`).
- **Step ordering column: `resources.mission_steps.index`, ascending.**
  `load_mission_defs` (`crates/cell-catalog/src/cell/spawner/missions.rs`)
  picks a mission's first step with `ORDER BY s.mission_id, s.index ASC`.
  The other two cited loaders do not order steps: `load_step_missions` is
  a step-to-mission map and `load_step_objectives` orders by
  `step_id, objective_id`. The column is nullable, so the apply uses
  `ORDER BY index ASC NULLS LAST, step_id ASC`. For 622 that is 2113 (0),
  80623 (1), 80622 (2).
- **Objective order** inside `completed_objective_ids`: step order, then
  `objective_id`. Hydration reads the array as a set, so order only matters
  for a byte-level parity diff.

Two choices the spec left open:

- `Completed` also fills `completed_objective_ids` with every step's
  objectives (the spec named only the steps). A route completion leaves
  the visited steps' objectives completed, and `objective_status ... eq
  completed` chain gates read that array.
- `active_objective_ids` is `{}` for `Completed` too. The route leaves the
  final step's roster there, but hydration of a finished row uses the
  array verbatim and nothing ever completes those objectives again, so an
  empty roster is the same state for every reader. FX-10's parity check
  should ignore this column on completed rows.

## Deviations from the spec

- **`handle_mission_update` swallows write errors** (it logs and returns
  `()`), so "on the first Err stop" could not see a failed mission write.
  `missions.rs` still writes every row through it (one persist, one F16
  delete rule) and then reads `(status, current_step_id, repeats)` back;
  a mismatch is the Err. The missions part is therefore one write per
  mission, not one transaction, but every mission is checked and its row
  built before the first write.
- **Prechecks before any write** in `apply_staged_fixture`: ownership
  (`sgw_player.account_id` = the session's account), the world exists in
  `resources.worlds` (the `world_location` foreign key), and the position
  is finite. The spec ordered missions, items, tutorials, position; a bad
  world would otherwise fail after the missions were written.
- **The hook body is `lab_fixture::apply_at_play`**, not inline in
  `play_character.rs`, which stays under the 500-line soft cap. Same
  placement and behaviour as the spec's snippet, plus a WARN when there is
  no database pool (the fixture is taken and nothing is written).
- **`FixtureApplied` and its fields are `pub(crate)`**, not `pub`: the
  crate has `#![warn(unreachable_pub)]` and the module is private. The
  name and fields are the contract's.
- `account_id` reaches `apply_staged_fixture` as `i32` (the contract);
  the session holds it as `u32`, cast as every other base query does.

## Review fixes (2026-10-10)

- **Account-scoped take (authority review).** `take_fixture(player_id)`
  ran before anything knew who owned the character, and `playCharacter`
  carries a client-chosen id: any logged-in account could send
  `playCharacter(victim_id)`, consume the victim's fixture, and retry
  (world entry resets the latch on the foreign id; ids are sequential).
  Now `take_fixture_for(player_id, account_id)` compares the staged
  `account_id` inside the store lock; a mismatch leaves the fixture staged
  and logs WARN `reason = "account_mismatch"` (player id and name, both
  account ids). An expired fixture is still dropped whoever asks. The GM
  check stays after the take, so a demoted GM's own fixture is consumed
  and discarded. The precheck's `sgw_player.account_id` check stays as a
  second line against the row itself.
- **Every check before the first write.** `apply_missions` became
  `plan_missions` (seed checks, row build, no writes; called from the
  precheck) and `write_missions`. The precheck also refuses a non-empty
  item list until FX-03, so an item fixture writes nothing.
  `move_player` lost its own finite-position check: its one caller's
  precheck covers it (guarded by the NaN half of
  `live_db_fixture_unknown_world_writes_nothing`).
- **`confirm_written` compares the arrays too** (`completed_step_ids`,
  `completed_objective_ids`), not only status/step/repeats.
- **TG-DB-12 interaction.** `handle_mission_update` now refuses every row
  write for a player whose saved missions are locked
  (`refuse_persist_if_locked`). A fixture applied at Play while a lock from
  an earlier session is still held is therefore refused; the read-back
  turns that into an Err (`write_failed`). The fixture does not clear the
  lock: the world entry that follows reads the missions and clears it, and
  the lab run's verify step reports the missing state.
- **Rule 6 reasons.** The "lab fixture not applied" ERROR carries
  `reason = "precheck_refused"` (nothing written) or `"write_failed"`
  (a part failed after earlier parts wrote); `apply_staged_fixture`
  returns `ApplyError::{Precheck, Write}`. All the refusal rows are pinned:
  `expired` and `account_mismatch` in the store's unit tests, and
  `account_mismatch`, `not_gm`, `no_database`, `precheck_refused`,
  `write_failed` in `live_db_fixture_negative_log_rows_carry_a_stable_reason`.
- New tests: `another_account_leaves_the_fixture_staged` (store),
  `live_db_play_character_leaves_another_accounts_fixture_staged`,
  `live_db_fixture_completed_writes_every_step_and_repeats_one`,
  `live_db_fixture_unknown_world_writes_nothing`,
  `live_db_fixture_reports_a_refused_mission_write` and the log-row test
  (`refusal_live_db_tests.rs`); `live_db_fixture_items_are_refused_until_fx03`
  now also asserts the mission row is untouched. Sentinels stay in the
  `0x7046_0200` block (`0x204..=0x206` store, `0x290..=0x2E0` live-DB).

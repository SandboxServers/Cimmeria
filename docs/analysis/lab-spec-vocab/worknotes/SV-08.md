# SV-08 worknote: server-event waits and polled clauses

Implementer notes (2026-10-11). The code is the reference where it differs from the packet.

## Deviations

- **The watermark read names the wait.** The packet's mark call is `server_log_tail { limit: 1 }`. The runner instead calls it with the wait's own `contains` (and `target`) and `limit: 500` (the ring's capacity), because the slack window below needs the lines that already match near the watermark. `newest_ms` is taken before filtering, so the mark is the same. A read with `since_ms` alone never happens.
- **`RowCtx.log_mark` is `Option<Result<LogMark, String>>`**, not `Option<u64>`: the newest timestamp, the keys of the matching lines already in the slack window, and the mark call for the action's `calls`; or why the pre-action read failed. A failed pre-action read is logged (`lab.uat` `wait_server_mark_failed`) and recorded in the wait's `calls` as `{"pre_action_mark": "<error>"}`, and the wait then reads a late mark at its start.
- **The mark is handed over after the action in front of the wait has run.** `drive_steps` reads it before that action and stores it in `ctx.log_mark` afterwards, so in `wait, wait` the second wait still waits from before the first one, not from the first one's own mark.
- **Setup actions get a pre-action mark too** (review fix). Before each setup action `drive_steps` reads the mark for the next setup action, or for the first step after the last one, so a first-step wait sees a line its setup caused. Only a row's very first action reads its own mark when it starts.
- **Same-millisecond and late-push handling** (review fix). Every read asks from `cursor - 2`, keeps lines at `cursor - 1` or later, and skips the ones it has already examined there (key: timestamp, target, message, fields). The 1 ms slack catches a line stamped just before a read but pushed into the ring after it. Two identical lines within 2 ms, one before and one after the mark, count as one.
- **Audit rows.** Besides always passing `contains`, the runner drops every `lab.tool_call` line itself, so a wait whose text happens to be in "lab MCP tool call" still cannot match its own polls. It also refilters target, message text and time (a server older than SV-02 ignores them).
- **A failed log read fails the wait at once** ("server_log_tail: ..."), rather than polling an unreachable server for the full timeout.
- **Every call is bounded by the deadline** (review fix): the mark read, each poll and the inline `client_entity_find` run under `tokio::time::timeout_at`. One that has not returned fails the wait with the expiry error. A polled clause's reads are bounded by its `timeout_ms` the same way; a read cut off is a FAIL with "the read did not return within <n> ms".
- **A `${var}` left in `log` or `target` fails the wait at once** ("unresolved variable ${x}"), as `fields` already did (review fix).
- **`loose_eq` compares text first** (review fix): `"Nan"`, `"inf"` and `"infinity"` parse as floats that never compare equal, so a wait field `player_name = "Nan"` never matched.
- **The polled-clause tests live in `polled_clause_tests.rs`**, beside `server_wait_tests.rs`, which would otherwise pass the 700-line cap.
- **Clause polling sleeps 250 ms under `no_settle` too.** The packet said `no_settle` makes the sleep zero. A zero sleep spins in real time and never advances a paused test clock (the loop would never end), and the tests pin the interval through elapsed paused time. The tests run with `start_paused`, so they are still instant.
- **`polls` is in the clause's `detail`** (`"polls: 3"`, or `"polls: 3; <detail>"`), not in `observed`: `observed` can be a scalar, and `capture_var` captures it unchanged.
- `clause::loose_eq` is now `pub(crate)` so the wait reuses the packet clauses' numeric comparison.
- `${player_entity_id}` is resolved inline with `client_entity_find { include_player, limit 1, project false }` `/player/id`, marked `// SV-07: use player_entity` for the coordinator.
- The wait's action `calls` hold the mark call and one summary of the polls (`polls: n`), not one entry per poll.
- `players_tests::wait_server_blocks_without_the_server_mcp_and_fails_until_sv08` became `..._fails_when_it_cannot_read_logs`: the fake server has no `server_log_tail`, so the wait fails with that read error.

## For SV-14 (docs)

- `wait_server`: the watermark is read before the action in front of the wait; the wait polls `server_log_tail` every 250 ms with `contains`, `target`, `since_ms = mark - 2` and `limit 500`; the first line whose `fields` all equal the wait's (numbers numerically, `"8"` equals `8`) passes. The action result is `{"matched": {"timestamp_ms", "message", "fields"}}` with only the named fields. Timeout error: `no server log '<log>' <fields JSON> within <n> ms` (no fields part when the wait names none).
- `${player_entity_id}` in a wait's `fields` is read from the client when unset and then kept in the row's vars.
- Lines on `lab.tool_call` never satisfy a wait.
- A poll asks for the whole 500-line ring, so a burst of matching lines between two polls is examined in full. A reply that still holds fewer lines than matched logs `wait_server_clipped`.
- Residual risk: a line stamped more than 1 ms before a read (on the server's wall clock) but pushed into the ring after it is still missed. The slack covers the stamp-then-push gap, not a clock step.
- Every server call a wait makes is bounded by `timeout_ms`; a server that does not answer fails the wait as an expiry does.
- Tool and server clauses with `timeout_ms` re-read a FAIL every 250 ms until PASS or the time is up; UNVERIFIED, BLOCKED and read errors are not retried. A clause read more than once says `polls: n` in its detail.

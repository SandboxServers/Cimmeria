# SV-08 worknote: server-event waits and polled clauses

Implementer notes (2026-10-11). The code is the reference where it differs from the packet.

## Deviations

- **The watermark read names the wait.** The packet's mark call is `server_log_tail { limit: 1 }`. The runner instead calls it with the wait's own `contains` (and `target`) and `limit: 50`, because SV-02's same-millisecond trap needs the lines that already match at the watermark millisecond. `newest_ms` is taken before filtering, so the mark is the same. A read with `since_ms` alone never happens.
- **`RowCtx.log_mark` is `Option<LogMark>`**, not `Option<u64>`: the newest timestamp, the keys of the matching lines already in that millisecond, and the mark call for the action's `calls`.
- **The mark is handed over after the action in front of the wait has run.** `drive_steps` reads it before that action and stores it in `ctx.log_mark` afterwards, so in `wait, wait` the second wait still waits from before the first one, not from the first one's own mark.
- **Only steps get a pre-action mark.** A `wait_server` in `setup` (or a row's first step) reads its own mark when it starts.
- **Same-millisecond handling.** Every poll asks from `cursor - 1`, keeps lines at `cursor` or later, and skips lines at `cursor` it has already examined (key: timestamp, target, message, fields). Two identical lines in one millisecond, one before and one after the mark, count as one.
- **Audit rows.** Besides always passing `contains`, the runner drops every `lab.tool_call` line itself, so a wait whose text happens to be in "lab MCP tool call" still cannot match its own polls. It also refilters target, message text and time (a server older than SV-02 ignores them).
- **A failed log read fails the wait at once** ("server_log_tail: ..."), rather than polling an unreachable server for the full timeout.
- **Clause polling sleeps 250 ms under `no_settle` too.** The packet said `no_settle` makes the sleep zero. A zero sleep spins in real time and never advances a paused test clock (the loop would never end), and the tests pin the interval through elapsed paused time. The tests run with `start_paused`, so they are still instant.
- **`polls` is in the clause's `detail`** (`"polls: 3"`, or `"polls: 3; <detail>"`), not in `observed`: `observed` can be a scalar, and `capture_var` captures it unchanged.
- `clause::loose_eq` is now `pub(crate)` so the wait reuses the packet clauses' numeric comparison.
- `${player_entity_id}` is resolved inline with `client_entity_find { include_player, limit 1, project false }` `/player/id`, marked `// SV-07: use player_entity` for the coordinator.
- The wait's action `calls` hold the mark call and one summary of the polls (`polls: n`), not one entry per poll.
- `players_tests::wait_server_blocks_without_the_server_mcp_and_fails_until_sv08` became `..._fails_when_it_cannot_read_logs`: the fake server has no `server_log_tail`, so the wait fails with that read error.

## For SV-14 (docs)

- `wait_server`: the watermark is read before the action in front of the wait; the wait polls `server_log_tail` every 250 ms with `contains`, `target`, `since_ms = mark - 1` and `limit 50`; the first line whose `fields` all equal the wait's (numbers numerically, `"8"` equals `8`) passes. The action result is `{"matched": {"timestamp_ms", "message", "fields"}}` with only the named fields. Timeout error: `no server log '<log>' <fields JSON> within <n> ms` (no fields part when the wait names none).
- `${player_entity_id}` in a wait's `fields` is read from the client when unset and then kept in the row's vars.
- Lines on `lab.tool_call` never satisfy a wait.
- More than 50 matching lines between two polls (250 ms) are not all examined: the poll sees the newest 50.
- Tool and server clauses with `timeout_ms` re-read a FAIL every 250 ms until PASS or the time is up; UNVERIFIED, BLOCKED and read errors are not retried. A clause read more than once says `polls: n` in its detail.

# SV-07 worknote: runner targets and @stand

Implementer notes (rust-gameserver-dev, 2026-10-10). The code is `crates/lab/src/uat/runner/targets.rs`; tests are in `runner/targets_tests.rs`.

## Decisions taken in the packet

- **`pose` together with `name`, `entity_id` or `point`** (the SV-03 worknote's open point; coordinator decision at review): an error, not a silent drop. The spec validator reports "`<row>`/`<label>`: pose with `<key>`: give one", like the tag rule, also for `face_name`, `face_entity_id` and `face_point` on `client_camera`; the runner refuses the same clash again, for arguments built from `${vars}`. Every other argument given next to a pose wins over the pose's value: `rotate_camera`, `pitch_deg`, `yaw_offset_deg`, `zoom`, and also `aim` / `aim_dy_m`. `aim_dy_m` when the resulting aim is `entity` is an error ("aim_dy_m needs aim = \"point\""), not ignored.
- The up-front blocks (tag args need the server lab MCP; tag args and `@stand` need `client_entity_find`) apply to the action `exec` will choose: the primary when routed, else the first available fallback.
- Stand polls ask for the player by `entity_id` (from the lookup), so the client scans no other entity. The 5 s deadline bounds the whole wait: the last sleep is cut short and none starts past it (one lookup plus 20 polls when the player never arrives). `stand_at` resets `rec.ok` / `rec.error` before the teleport, so a caller's earlier failure does not end it.
- `rotate_camera = false` is added only when a `pose` is named (the stand and camera set the view). A bare `tag` keeps the click tool's own default (true).
- The pose's `zoom` is not added when the action gives `zoom_to`, because `client_camera` refuses both.

## Deviations from the packet

- `@stand { point = {...} }` is not BLOCKED without the server lab MCP: it resolves no tag. Only an action whose args carry `pose`, `tag` or `face_tag` is blocked with "`<tool>` by tag needs the server lab MCP (CIMMERIA_LAB_MCP_URL/_TOKEN)".
- An extra up-front block: an action with tag args, or any `@stand`, needs `client_entity_find` routed on its client ("`<tool>` needs tool client_entity_find, which is not routed").
- `exec_stand` takes the substituted args (`exec_stand(who, &args, ctx, rec)`) rather than the `ActionSpec`, since `exec_tool` has already substituted `${vars}`.
- The `resolve` record carries `pose` only when the action named one: `{ "resolve": { "tag", "entity_id", "space_id", "pose"? } }`.
- The reply is filtered by tag and also by `space_id` (when an entity carries one). A zero-match error appends " (the reply was capped)" when the server's reply says `capped: true`, which can happen only on a pre-SV-01 server that returned the whole space.
- A stand whose polls never return a position fails with "stand: no player position after 5 s (client_entity_find: ...)" instead of the "still ... m" message, which needs a distance.
- `PoseSpec::to_inline_toml`, `round_to` and `toml_string` keep `#[cfg_attr(not(test), allow(dead_code))]`: their first non-test callers are SV-09 and `lab-record`. The attribute on the rest of `impl PoseSpec` is gone.

## Doc deltas for SV-14

- Lab guide tool table: `@stand` (`uat_stand`, tier G): `pose`, `tag` + `radius_m` + `bearing_deg` (+ `dy_m`, default 0.1), or `point = { x, y, z }`. Types `/gmgotoxyz x y z` (2 dp) and polls `client_entity_find { entity_id = <player>, include_player }` every 250 ms until the player's server x/z is within 0.5 m, at most 5 s. Failure: "stand: still `<d>` m from (`x`, `y`, `z`) after 5 s".
- Tag arguments: `pose`, `tag`, `face_tag`, `aim`, `aim_dy_m` never reach a client tool; the action's `args` in the bundle shows what the tool got. Errors: "no entity with tag `<tag>` in space `<id>`", "tag `<tag>` matches entities `<ids>` in space `<id>`".
- Bundle: each server read appears in the action's `calls` as `{ tool, args, ok }`, plus the player lookup and the last stand poll; the resolution as `{ resolve: { tag, entity_id, space_id, pose? } }` (lab-golden keys on it).
- The precedence rules above (a pose next to an explicit target is an error; explicit args win over the pose's values).

# SV-02 worknote: `server_log_tail` filters

Review outcomes carried forward (packet-reviewer, 2026-10-10).

## Deviations from the packet (approved)

- `tail_reply(entries, &LogFilter, limit)` builds the reply from a snapshot,
  so `newest_ms` is unit-testable without a `LabState`. `log_tail` calls it.
- `LogFilter` carries `level` too, so every filter ANDs in one place.

## For SV-08 (server-event waits)

- **Same-millisecond race.** `since_ms` is strictly greater at 1 ms
  resolution. An entry logged in the same millisecond as the watermark, but
  after the snapshot that produced it, has `timestamp_ms == W` and is never
  returned. Poll with `since_ms = W - 1` and de-duplicate on
  `(timestamp_ms, target, message)` against the entries seen at the
  watermark poll, or document the race.
- **The tool's own audit rows.** Every lab-mcp call writes an INFO
  `lab.tool_call` row into the same ring, and it advances `newest_ms`. A wait
  must always pass `target` or `contains`; `since_ms` alone matches its own
  polls. Each poll also adds one row to the 500-entry ring, so keep the poll
  interval at 250 ms or more.

## For SV-14 (docs)

- `total_buffered` counts entries *after* filtering (as it did for `level`
  before this packet), while `newest_ms` describes the whole buffer. Say so
  in the tool row.
- `limit` is uncapped and replies are not truncated (pre-existing); a
  caller should pass a small `limit` with the filters.

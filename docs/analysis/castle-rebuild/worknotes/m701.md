### Turn-in split into three chains

`Castle.py` does `removeDialog` → `complete(701)` → `accept(702)` in one
node. I split that across chains 1237 (unbind + complete 701), 1238
(accept 702) and 1239 (accept 703) because:

- the review rule in `content-chains.instructions.md` requires a
  `mission_status <id> eq not_active` gate on every chain containing
  `accept_mission`, and one chain with two accepts would need both gates;
- with both gates on one chain, a player who somehow already held 702 or
  703 could never complete 701 — a permanent soft-stuck on the mission's
  last step. Pinned by
  `turn_in_completes_701_even_when_702_is_already_active`;
- chain 1239 is the D-CA05 reconstruction and can now be withdrawn with a
  single `enabled = false` flip, touching neither 701's completion nor
  702's accept.

All three match the same event and all conditions are evaluated against
one pre-action context snapshot, so 1237's `complete_mission` cannot gate
1238/1239.

## Evidence and engine facts established

Verified directly in this tree; several correct or contradict advisor
claims, so they are recorded with file:line for the ledger.

1. **World 8 is named `Castle`** (`worlds.sql:177`), so every
   `player_loaded` trigger keys on `'Castle'`.
2. **Row 3062 is unbindable today.** `dialog_id` is NULL
   (`dialog_set_maps.sql:2281`) and `load_dialog_set_maps` drops NULL
   rows (`spawner/dialogs.rs:45`); the bind then warns and no-ops
   (`executor/dialog.rs:172-177`). Templates 48 and 149 both have
   `interaction_type = 0` **and** `static_interaction_sets = '{}'`, so the
   per-player bind is the only source of the client's interaction bit.
   Until CA02 lands, neither NPC is clickable and chains
   1202/1203/1231/1233 cannot fire in-client. The seed header lists the
   exact eight rows that change if CA02 closes negative (3062 → 3059 for
   Gerschon, 3062 → 3061 for Copplemann; the 3063 turn-in rows do not
   move).
3. **`fire_dialog_choice` does not populate `archetype`**
   (`event_dispatch/dialog.rs`). An archetype condition on a
   `dialog_choice` chain can never match. The Human/Jaffa split therefore
   lives on the `interact_tag` chains, and the two accept chains are keyed
   by dialog id. Same shape as Cellblock 1018-1021. The test helper
   `dialog_choice_ctx` deliberately omits the param so a future chain
   cannot pass a test it would fail in the game.
4. **A chain-handled interact never sets `last_interaction_target`.**
   `handle_interact` — the only writer of that pin
   (`interactions/dispatch/interact.rs:90`) — runs solely in the
   `if !handled` branch of
   `cell_methods/player/interaction/interact.rs:161-200`, i.e. only when
   no content chain matched. Consequences:
   - `display_dialog 2575` on victory chain 1234 falls through to the
     **monologue** branch (2575 is one screen with `speaker_id = 0`) and
     binds the player — which is exactly the Python's
     `displayDialog(None, 2575)`. Works.
   - `display_dialog 5862` on chain 1205 had no `target_entity_id`, no
     pin, and is **not** a monologue (screens 93218/93220/93222 carry
     speaker 2499, Moh'katan), so it warned and bailed.
   - **FIXED in this packet** (coordinator decision 2): `interact.rs` now
     pins `last_interaction_target` before the content-chain dispatch,
     mirroring python's `SGWPlayer.interact()`, which pins first. The
     write sits after the hostile-combat reroute so an attack cannot make
     its victim the next dialog's speaker, and `handle_interact`'s own
     write is left in place for the non-chain path. Guard:
     `chain_handled_interact_pins_target_for_a_later_chain_dialog` in
     `cell_methods/player/interaction/mod.rs`.
   - Scope of the fix: this was **not** a 701-only bug. Every follow-up
     chain that displays an NPC-speaker dialog was affected — from a
     `dialog_choice`, from a minigame victory (`fire_chain_by_id` builds
     `ResolvedActions` with empty params by construction,
     `event_dispatch/mod.rs:81-85`), or from the deferred-action drain.
     Before the fix only monologue dialogs could render from those
     triggers. CA07 and CA09 both author a victory dialog and would have
     hit it. Documented in `docs/content/content-engine.md` §4.
   - Residual constraint, unchanged: a chain fired from a trigger that
     follows **no interact at all** (a bare `player_loaded`, a region
     entry, a timer) still has no speaker to resolve, so an NPC-speaker
     dialog there still warns. That is inherent to the resolution order,
     not a bug.
   - Note this also means **no server-side range check runs on a
     chain-handled interact**: the `MAX_INTERACT_DISTANCE` (5.0,
     `interactions/dispatch/mod.rs:25`) gate lives in the skipped
     `handle_interact`. Out of scope here; flagged below.
5. **Button-less dialogs still raise `dialog_choice`.** Dialogs 2574,
   2575 and 5862 have zero `dialog_screen_buttons` rows. Shipped Cellblock
   chains 1018/1020/1021 trigger on 5020/5021/2300, which are also
   button-less, so the client evidently sends `dialogButtonChoice` on a
   button-less dialog's close. This is an **inference from shipped
   precedent, not a client observation**, and the whole 701 tail hangs off
   `dialog_choice 2575`. It is the single largest untested assumption in
   this packet — see UAT below.
6. **Death does NOT strand the escort timer.** `resolve_respawn_target`
   (`respawn.rs:301-347`) matches the World 8 respawner rows by world
   name, so a Castle death takes the **same-world** in-place branch
   (`respawn.rs:152+`) and never calls `destroy_entity` — only the
   cross-world branch at `respawn.rs:131` does. The deferred queue
   survives a death and fires normally. This **disproves** a
   soft-stuck-on-death hazard raised in review, which had assumed
   `deferred.rs`'s doc-comment list ("... GM despawn, death") applied to
   players. The paths that do scrub the queue (logout, cross-world hop)
   are all followed by a `player_loaded`, which chain 1242 re-arms from.
7. **`get_chain_actions` ignores `content_chains.enabled`**
   (`chain/mod.rs:117-135`). `enabled = false` is therefore **not** a kill
   switch for a triggerless victory chain such as 1234. It does work for
   1239 (the D-CA05 reconstruction), which is trigger-driven — one reason
   the turn-in split is worth keeping.
8. **Livewire parameters.** `Minigame('', 1, gameIds[0], 1, 0xffff, cb)`

   `0xffff` is an **archetype permission mask**, not a seed and not a
   timeout; `setSeed()` is never called, so the server picks the seed,
   which is what `cell_dispatch/minigame.rs:36` already does. **701 wants

   the param. Warning for CA04: do not map the Python `archetypes` mask
   onto the Rust `abilities_mask` — that field becomes joinOK's
   `abilityBitfield` (`minigame/server.rs:161`, consumed at
   `games/livewire/setup.rs:387`) and `0xffff` there would change the
   Livewire board.
9. **Arrival geometry.** Chain 1109 lands the player at
   (466.365, 70.397, 991.466); Gerschon (spawn 112) is at
   (429.638, 70.111, 996.556). Distance **37.08 units**, dy 0.29 — far
   outside the 5.0 interact range but a short walk on flat ground.

10. **Livewire defeat is replayable.** The session is removed on exit

## Server-authority fix: range gate on the chain-handled interact path

Found while reviewing the pin fix (PR #659 review item 2), fixed here.

`interactions::handle_interact` has always validated that the target
exists and is within `MAX_INTERACT_DISTANCE` (5.0 units). But it is the
**last** thing the outer dispatcher
(`cell_methods/player/interaction/interact.rs`) tries: the trainer UI and
the content-chain dispatch both run ahead of it, in the `if !handled`
ladder, and so never inherited the check.

The exposure: a client could send `interact` naming any tagged NPC
anywhere on the map and drive that tag's content chains — accepting
missions, advancing steps, launching minigames, granting items — from
arbitrary distance, with no line of sight and no proximity. This is
pre-existing and campaign-wide, not introduced by this packet; it affects
every `interact_tag` chain in the repository. Moving the
`last_interaction_target` pin ahead of the chain dispatch made it
slightly worse, because `interactions/dispatch/initial_response.rs`
stamps that pin directly onto the wire as an `onDialogDisplay` EntityId,
so an unvalidated entity id could reach the client.

Fix: a shared `interactions::interact_target_in_range` helper, called by
the outer dispatcher before the pin, the trainer UI and the chain
dispatch. Rejection logs at `info`, matching the inner path — a too-far
click is ordinary client behaviour (lag, a moving target), not an error.
It sits **after** the hostile-NPC combat reroute on purpose: attacks have
their own range rules and gating them on the 5-unit interaction distance
would break every ranged weapon.

`handle_interact` keeps its own inline check; the two are not redundant,
because the inner one keeps that function correct for any future caller
that bypasses the outer dispatcher. The existing guard
`out_of_range_interact_does_not_pin_target` now carries a scope note
saying it covers the inner path only.

Guards: `out_of_range_interact_does_not_pin_or_fire_chains`,
`interact_on_a_missing_target_does_not_pin_or_fire_chains`,
`in_range_interact_pins_and_fires_chains` (the positive control, so the
two negatives cannot pass with the gate stuck closed), and
`hostile_reroute_does_not_pin_the_target` (pins the ordering so a
refactor cannot hoist the pin above the combat branch, which is where
python writes it).

## Engine fix: monologue dialogs outrank any resolvable NPC

Second finding from the same review (item 1), and a direct consequence of
the pin fix.

`executor/dialog.rs` used to treat the monologue cache as the *last*
fallback, after `params["target_entity_id"]` and the pin. That was safe
only while the pin was usually empty. Once the pin is written on every
interact, it is sticky and never cleared, so from the player's first
click onward there is always an NPC resolvable — and every monologue
would have been bound to whichever NPC was clicked last.

Concretely: Castle 701's Livewire victory chain displays dialog 2575,
"You manage to free Capt. Copplemann from her security boot." One screen,
`speaker_id = 0`, player narration. `Castle.py` displays it with an
explicit `displayDialog(None, 2575)`. With the old ordering plus the new
pin, Copplemann would have been bound and would have appeared to speak
the player's own narration.

Fix: check the monologue cache **first**; a monologue binds the player and
ignores any NPC in scope. Guards:
`monologue_binds_player_even_when_an_npc_is_resolvable` (covers both a
sticky pin and an explicit `target_entity_id`, which is the stronger
source) and the executor-level
`chain_1234_victory_dialog_binds_the_player_not_copplemann`, which drives
the real victory chain through `execute_actions` and asserts the wire
EntityId is the player. A resolve-only test cannot catch this: the action
list is byte-identical either way.

## Behaviour differences a player could notice

1. **Copplemann does not walk.** She stays at (352.692, 70.272, 952.320)
   for the whole mission. Step 2401's log text still says "Escort Capt.
   Copplemann to the safe zone at the end of the hall", so the text and
   the world disagree for 10.5 seconds. That is the D-CA02 option-A
   compromise, made because all three primitives the Python used are
   unusable (see mission-chains.md).
2. **The 2401 → 2421 advance is on a timer, not on a click.** In the
   Python, `n65_propagator_Out` advanced 2401 → 2421 and then immediately
   re-checked 2421 and displayed 2576, so one click did both. Our engine
   evaluates all conditions against one pre-action snapshot, so splitting
   that across two `interact_tag` chains would need two clicks. Option A
   sidesteps it by putting the advance on the timer. If the coordinator
   prefers the click-driven shape, the faithful form is a single chain
   `interact_tag Castle_Coppleman` + `step 2401 active` →
   `advance_step 2421` + `display_dialog 2576`, plus keeping a bind on
   slot 48 through 2401 so she stays clickable.

### 1360 persistence: substitutes shipped, full two-service fixture not built

The packet asked for a live-DB test that mission 1360 (Frost's letter) and
688-completed both survive the Cellblock → Castle world hop, "if feasible
with existing fixtures". The end-to-end version is **not** built, per
coordinator decision 3: the hop is `Action::CrossWorldTeleport` →
`CellToBaseMsg::GateTravel`, whose cell-side half calls
`space_manager::destroy_entity` and hands off to the base service
(`cell/gate_travel.rs:128`, `executor/transport.rs:135`). Asserting across
it needs a fixture driving both services over a world boundary, and none
exists in `crates/services` — everything is either cell-only
(`SpaceManager` + a channel, as in my deferred test) or DB-only. That is
test-infra work, recorded as a known gap.

Both substitutes are implemented in
`chain_replay_tests/mission_701/persistence.rs`:

- `missions_survive_the_cellblock_to_castle_world_change` seeds a player
  in `Castle_CellBlock` with 1360 active and 688 completed, calls the
  **production** restore path `query_saved_missions`, flips
  `sgw_player.world_location` to `Castle` (the only persisted effect the
  hop has on the player row), calls it again, and asserts the restored set
  is identical. A world or space filter added to that query's `WHERE`
  clause fails it.
- `sgw_mission_has_no_world_scoping_column` is the blunt companion: the
  table must offer nothing to scope by, so a future "just filter by world"
  change has to add a column and trips here first.

Placed in `mission_701/` rather than beside `query_saved_missions` because
`base/world_entry/methods/missions.rs` is at 691 lines — one test short of
the 700-line hard cap — and is shared base-side surface several concurrent
packets touch. Noted for a later split.

The end-to-end behaviour remains a UAT step (M1: "arrive near Gerschon,
letter 1360 still active").

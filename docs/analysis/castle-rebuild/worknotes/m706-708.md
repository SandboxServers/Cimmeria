## Evidence And Hypotheses

Every chain in this packet is `RECONSTRUCTION`. There is no recovered server
script for 706 or 708: `deprecated/python/cell/spaces/Castle.py` stops at
mission 701 and never names 702, 703, 704, 706 or 708. What is original data and
is reproduced rather than invented: the step, objective and task rows; the
dialog ids and their screens; the dialog-set map rows; the region, spawn and
item rows. The wiring — which trigger drives which step, in what order — is the
reconstruction. The objective text carries most of the signal: objectives 2794
and 2795 literally read "(Option #1) Force a guard to surrender…" and "(Option
#2) Use the Access Panel on the Goa'uld Throne…", and 2798/2799 name the NID
officers and Warden Muelbach as the crystal sources.

### Four engine facts that changed the design

**1. Button-less dialogs do fire `dialog_choice`, with `button_id = -1`.**
Not one of 2584, 2586, 5003, 5004, 5008, 5009, 5010 or 5011 has a row in
`dialog_screen_buttons.sql` — checked by `screen_id`, the third column, not by
`dialog_id`. This looked like it would soft-lock steps 2415 and 2417. It does
not. The mission-systems advisor resolved it from the client: the SGW dialog
window is CEGUI + Lua and ships uncooked at
`…\SGWGame\Content\UI\Core\Dialog\`. `Dialog.lua:48-51` wires
`selectActiveDialogChoice` only to the buttons in `DialogMod.dialogButtonMap`,
so a zero-button dialog has no click path — but Done / Decline / the window's X
route to `onDialogDoneClicked` → `discardAvailableDialog` (`Dialog.lua:64-67,
83-85`), whose native implementation (`FUN_00ad86c0` → `FUN_00d249c0`) walks the
dialog's screens accumulating a button count and, **iff the total is zero**,
sends `Event_NetOut_DialogButtonChoice` with `ButtonId = 0xFFFFFFFF`. A dialog
that HAS buttons sends nothing on close. That is exactly why `Castle.py` could
key `dialog.choice::2574` and `::2575` — both also button-less — and why shipped
chains 1020/1021 key on 2300/5020. Cimmeria reads the id as a plain `i32`
(`interaction/dialog.rs:21-22`) and the #479 gate keys only on the open dialog,
so `-1` is handled.

**Hard rule that falls out: never add a button to 5003, 5004, 5008 or 5009.**
Doing so stops the close path emitting and silently soft-locks steps 2415 and
2417. Recorded in the seed header as engine fact (6).

**2. `fire_dialog_choice` does not populate `archetype`.**
`event_dispatch/dialog.rs:87-93` sets `dialog_id`, `button_id` and mission
context — nothing else. `Condition::Archetype` reads a missing key as `-1`
(`conditions.rs:225-230`), so on a `dialog_choice` chain `archetype eq 8` is
permanently false (branch dead) and **`archetype neq 8` is permanently true — a
guard that reads correct and fails open.** Confirmed against the existing seed:
every archetype-gated chain that ships today (1011/1012, 1051/1052, 1098/1099)
triggers on `enter_region` or `interact_tag`, both of which populate it. No
shipped chain puts an archetype condition on a dialog chain.

**3. The #479 open-dialog gate makes dialog-id discrimination
server-authoritative — but only because nothing binds 5008/5009 as a dialog
set.** `handle_dialog_button_choice` (`interaction/dialog.rs:36-49`) rejects a
choice unless `open_dialog_id` matches, and the pin is set only by
`send_dialog_display`. The server-authority pass correctly pointed out that the
gate proves *display*, not *entitlement*, and that `initialResponse`
(`interactions/dispatch/initial_response.rs:33-43`) lets a client name any
`dialog_set_map_id` sitting in its own `available_interactions`, unscoped by
template. That path is closed here because `available_interactions` is written
in exactly two places — `executor/dialog.rs`'s `add_dialog_set` and a GM console
command — and this packet never binds set-656 rows 5850/5851. The only way to
display 5008 is chain 1352, which is archetype-gated on the interact side.
`report.rs::archetype_conditions_are_never_placed_on_the_dialog_halves` pins
both halves of that argument against the seed.

**4. `advance_step` cannot auto-complete a mission; `complete_objective` can.**
`advance_step` force-completes the leaving step's objectives by calling
`MissionInstance::complete_objective` directly (`progression.rs:57-66`),
bypassing the module-level `all_required_complete` check at `:176-183`. So
"complete the one objective we want ticked, then advance" is safe. It is safe on
step 2417 only because all three of that step's objectives are
`is_optional = false` (`mission_objectives.sql:6631/6633/6635`): ticking 5185
leaves 5184 and 5186 active. Flip either to optional and completing 5185 ends
mission 708 three steps early. The same latent hazard exists on 2415 (survives
only because hidden objective 2796 is required) and 2416 (2797 required).
`report.rs::reporting_in_advances_the_step_without_completing_the_mission`
executes the chain against a fixture carrying the real optional flags and
asserts the mission is still `MISSION_ACTIVE` afterwards, so a seed-data flip
fails a test rather than shipping.

## Design decisions

### Deviation from the packet text: the Access Panel glow is never cleared

Packet CA08 says chain 1322 should `set_interaction_type Castle_AccessPanel ~
1073741824`, and CA09 says the 2415 routes should "clear both". **Both clears
are omitted, deliberately.** The reasoning, with evidence:

- `set_interaction_type` mutates the SHARED `CellEntity.interaction_type_flags`
  and broadcasts to every witness (`executor/world/mod.rs:19-64`). There is no
  per-player interaction state short of a dialog-set bind — design gate GCA1.
- Template 147 (the Access Panel) ships `interaction_type = 0`
  (`entity_templates.sql:25`), so the glow is the ONLY bit that makes the panel
  clickable. Clearing it renders it scenery for the entire zone.
- Two different missions use the same prop at overlapping times: 706 step 2412
  (chain 1322) and 708 step 2415 route B (chain 1344). A player finishing 706
  would strip the panel from a player mid-2415, and vice versa, until one of
  them relogged into chain 1323 or 1361.
- The clear-then-reaccept ordering has a worse failure: `accept_mission` returns
  early when the offer guard refuses (already active / completed at repeat cap /
  failed non-repeatable / entity missing — `executor/mission.rs:64-72`) and
  **skips `fire_mission_accepted` entirely**. On that path chain 1341 never
  runs, and the panel stays dark for the whole zone permanently.

Setting a bit is harmless to bystanders (an extra cue); clearing one can strip
another player's only affordance. The seed therefore clears NPC `!` cues and the
DHD's Livewire bit — where a stale bit is actively misleading and the Cellblock
precedent 1107 does the same — and never clears the panel glow. Cost: the panel
keeps a quest glow after both missions are done, and clicking it then does
nothing. Flagged for the coordinator as the one place this packet does not
follow its brief literally.

### Where the archetype gate lives

On the interact chains (1352 / 1354 / 1350 / 1351 / 1358 / 1359 / 1362 / 1363),
never on the `dialog_choice` chains (1343 / 1345 / 1353 / 1355). See engine
facts 2 and 3 above. The dial chains 1358/1359 CAN carry it because
`fire_stargate_dialed` populates `archetype` (`event_dispatch/stargate.rs:96-101`).

### Step 2417 uses `complete_objective` + `advance_step`, never `complete_mission`

Both report objectives are required, so `complete_objective` alone can never
finish step 2417 — the untaken branch would pin the mission open forever. The
chain completes only its own objective and lets `advance_step` force-complete
the other two. Never complete both report objectives: with 5184 also done that
would satisfy `all_required_complete` and end 708 at step 2417.

### Step 2412 and step 4469 use `complete_mission`, not `complete_objective`

`complete_objective`'s auto-complete branch sends `onMissionUpdate` with the
`MISSION_ACTIVE` status byte (`progression.rs:200`, with the giveaway comment
`// Status sent as "completed" removal`). `complete_mission_direct`
(`progression.rs:226-309`) emits the correct sequence: `onObjectiveUpdate`
(COMPLETED) per objective, `onStepUpdate` (COMPLETED), then `onMissionUpdate`
with `STATUS_COMPLETED`. Packet CA08 already called for this on 706; the same
reasoning is applied to 708's chain 1360.

### The crystal single-grant guard, and its one precondition

The step gate is the guard. Each source chain advances out of 2416 in the same
action list it grants in; `advance_step` mutates `current_step_id`
synchronously in memory (`progression.rs:76`) before returning; the cell service
is a single task owning `SpaceManager` by value, so nothing interleaves; and
`fire_entity_death` cannot re-fire for one corpse (`kill_credit.rs:56-69`
short-circuits on the `was_alive_before` snapshot). A respawned officer is the
SAME entity with the SAME tag (`ticks/npc_respawn/mod.rs:116-165`), so the step
gate is the only thing standing between a re-kill and a second crystal — and it
holds.

**Precondition: every action row must carry `delay_ms = 0`.**
`execute_actions` QUEUES rather than runs any action with `delay_ms > 0`
(`executor/mod.rs:96-120`); a deferred `advance_step` would leave 2416 active
across the delay window and turn four officers plus a warden plus respawn timers
into an unbounded crystal faucet. Every action row in the file is 0, and both
test modules assert it per chain via `assert_no_deferred_actions`.

### 2416's report cue is two multi-trigger chains, not eight

Chains 1350/1351 each carry four `entity_dead_tag` trigger rows (the precedent
is chain 1087) so the archetype gate is written once per faction instead of once
per corpse. Conditions for every matching chain are evaluated against one
pre-action context snapshot and the action lists are then concatenated
(`chain/mod.rs:288-325`), so 1350's `step_status 2416 eq active` still passes
even though 1346-1349 advance to 2417 earlier in the same batch. The replay test
registers every expansion via `load_chain_expansions_for_test` — using
`load_single_chain_for_test` would register only the first trigger row and mask
drift in the other three.

### Chain 1357's `add_dialog_set 3073` and chain 1365 are seeded but inert today

`spawner/dialogs.rs:45` still drops every `dialog_id IS NULL` row at load, so
binding map row 3073 is a warn and a no-op (`executor/dialog.rs:172-177`) until
packet CA02 widens `DialogSetMapEntry.dialog_id` to `Option<i32>`. Seeded now
because the packet asks for it, because the coordinator's CA02 wire evidence
says a flag-only bind is legal on the wire, and because it costs nothing when
inert. Worth recording: **the bind is a TOPIC ("Dial Harset"), not the dial
capability.** Template 162 already ships `interaction_type = 16` (`INT_Dhd`,
`entity_templates.sql:131`) and `space_manager/spawn.rs` copies the template
column onto the entity, so the DHD is dialable from spawn for everyone and the
dial is NOT gated on step 4462. Chains 1358/1359's `step_status 4462 eq active`
gate the mission ADVANCE, which is all mission 708 needs.

### Restore coverage

One `player_loaded Castle` chain per step that owns a cue: 2415 (1361), 2417
(1362 Tau'ri / 1363 Jaffa), 2418 (1364), 4462 (1365), plus 706's step 2412
(1323). Steps 2416 and 4469 own no cue — 1350/1351 paint at the 2416 → 2417
transition, and the resulting 2417 state is covered by 1362/1363.

## Known gaps

1. **Five tags do not exist yet.** `Castle_SurrenderGuard`,
   `Castle_BravoOfficer1..3` and `Castle_Muelbach` are contracts owed by packet
   CA05 and are absent from `spawnlist.sql` world 8. Until CA05 seeds them,
   `find_entity_by_tag` returns `None`, `set_interaction_type` debug-logs and
   no-ops (`space_manager/queries.rs:325-332`), and the four death triggers
   never fire. The replay guards exercise the chains against hand-built
   fixtures and pass regardless; **the zone does nothing for mission 708's steps
   2415 and 2416 until CA05 merges.** Make that explicit at UAT.
2. **Three Bravo officers is CA05's default N.** If CA05 seeds a different
   count, add or remove chains in the 1346-1348 block and the matching trigger
   rows on 1350/1351, and update the `SOURCES` table in `crystal.rs`.
3. **Dialogs 5010 and 5011 depend on the interaction pin.**
   `fire_stargate_dialed` stamps no `target_entity_id`, so `display_dialog`
   falls back to `last_interaction_target` (`executor/dialog.rs:54-90`). At step
   4462 the DHD has no matching interact chain (1356 requires 2418), so the
   click that opens the dial UI falls through to `handle_interact`, which pins
   the DHD (`interactions/dispatch/interact.rs:89-91`). The portrait therefore
   binds to the DHD while the screens' own speakers (261 Marsh / 2499
   Moh'katan) name the voices. If UAT shows the closing line missing, a null
   pin is the cause. The coordinator's CA17 candidate (`display_dialog` optional
   `target_tag`) is the clean fix and would let 5010/5011 bind the named actor
   instead.
4. **Item 2136's role is a guess.** It is named "Muelbach…" and carries a
   copy-pasted Ambernol description. It is granted as the identifying drop that
   distinguishes the Muelbach route, mirroring item 2135 on mission 703. Nothing
   consumes it. If UAT says it is meaningless, delete the one action row from
   chain 1349.
5. **Livewire on the DHD is provisional (D-CA09).** At step 2418 the DHD's flags
   are `16 | 256 = 272` and the client offers both a dial and a hack affordance;
   `fire_interact_tag` short-circuits `handle_interact`
   (`cell_methods/player/interaction/interact.rs:160-200`), so chain 1356 wins
   the interact while 2418 is active and the native dial path takes over once it
   is not. Workable, but it needs a client UAT.
6. **The Access Panel sits just outside its own region.** The panel is at
   x = 330.49 (`spawnlist.sql:133`); point set 2049's bounding box starts at
   x ≈ 331.35 (`point_set_points.sql:121-127`). Harmless today — chain 1321
   fires on region entry, not on proximity to the panel — but a future
   tightening of the region test would bite.
7. **`enter_region` is client-hinted.** A player who somehow accepted 706 while
   already standing in the Throne Room never fires chain 1321 and stalls on
   2411. 706 is accepted in the Communications room (CA07), so this is fine
   today; do not let a future re-order break it.
8. **Objective state does not survive a relog** — `executor/mission.rs:85,242`
   persist `active_objective_ids: vec![step_id]` and no completed objectives.
   After a relog, chain 1353's `complete_objective 5185` silently no-ops and the
   step machine still recovers, so 708 is not broken, but the client's objective
   ticks are fiction. Pre-existing and cross-mission; already filed as **#657**
   by the m702-704 packet. Not re-filed here.
9. **`advance_step` force-completes optional objectives too.** A player who took
   the surrender-guard route at 2415 will also see "(Option #2) Use the Access
   Panel" tick. Engine behaviour (`progression.rs:57-66`), not something the
   seed can suppress.

## Wire evidence (packet step 1 — the gate on the whole packet)

**Question:** what does the client message that `add_dialog_set` ends in carry for the dialog id —
is it required, optional, or can it be 0 / absent?

**Answer: the dialog id is not on the wire at all.** A bind's only client-visible effect is a flags
bitfield. A flag-only bind is therefore legal, and nothing has to be invented for the absent dialog.

The chain, traced from the executor outward:

1. `Action::AddDialogSet` → `executor/dialog.rs::add_dialog_set`. It pushes
   `(dialog_set_map_id, dialog_id, interaction_flags)` onto the player's `available_interactions`
   and then calls `send_interaction_update_if_visible`.
2. That helper emits, per witnessing player and per template-matching NPC,
   `CellToBaseMsg::WitnessEntityMethod { method_index: method_idx::INTERACTION_TYPE, args: (merged as u64).to_le_bytes(), .. }`
   where `merged = npc.interaction_type_flags | entry.interaction_flags`
   (`crates/services/src/cell/content/executor/dialog/mod.rs`, `send_interaction_update_if_visible`).
   The same payload shape is re-sent on AoI entry at
   `crates/services/src/cell/space_manager/aoi.rs:157-179` (the `dynamicUpdate` half of the C++
   `createOnClient(base)` → `dynamicUpdate(merged)` flow).
3. Base side: `cell_dispatch/aoi_dispatch.rs:126` routes the variant to `witness_entity_method`,
   which builds one `build_entity_method_packet` frame to the witness's address only.
4. `method_idx::INTERACTION_TYPE = 3` (`crates/services/src/mercury/mod.rs:177`,
   `crates/services/src/cell/client_methods/spawnable_entity.rs:10`) is
   `SGWSpawnableEntity.InteractionType`, and its signature is **one argument**:

   ```xml
   <InteractionType>
       <Arg>   UINT64   <ArgName>   TypeId  </ArgName></Arg>
   </InteractionType>
   ```

   `entities/defs/SGWSpawnableEntity.def:114-116`. Mirrored in
   `docs/protocol/client-method-dispatch-table.md:80` (`| 3 | InteractionType | UINT64 TypeId |`) —
   which already matched, so **no protocol doc needed a change**; the doc is itself part of the
   evidence.

Corroborating facts:

- `onDialogDisplay` is a **separate** client method (`SGWPlayer.def:1149-1155`, five args starting
  `INT32 EntityId, INT32 DialogID`). It is sent when the player clicks, not when the bind is
  installed. So "bind" and "display" were never one message.
- `onInitialInteraction(ARRAY<DialogChoices> Choices)` (`SGWPlayer.def:1145-1147`, index 104 in
  `client_methods/player.rs:16`) is the topic-list push the original used to offer several bound
  topics at once. It is **declared and named in the wire log but never emitted** — no send site
  exists in `crates/`. So today a bind's whole client-visible footprint is the flags bitfield, and
  `topic_text` on a `dialog_set_maps` row never reaches the client.
- The dialog id is consulted only server-side, on the click paths: `handle_interact` (per-player
  binds take priority over the static `interaction_type`) and `handle_initial_response` (matches the
  `DialogSetMapID` the client echoes back — `SGWPlayer.def:629-632`).

**Conclusion.** D-CA03's "MEDIUM on the wire behaviour of a NULL bind" resolves to HIGH: there is no
wire behaviour to be uncertain about, because the bind message has no dialog field. The risk was
never the push; it was the *click*, where an absent dialog could be papered over with a substituted
id. That is what the click-path changes and their guards address.

## Design decisions

- **`Option<i32>`, not a `0` sentinel.** `DialogSetMapEntry.dialog_id` and the
  `available_interactions` value tuple both widen to `Option<i32>`. Nothing in the code substitutes
  a value for `None`. Dialog 0 is not "no dialog" anywhere in the data, and sending
  `onDialogDisplay(.., 0, ..)` would open an empty dialog box — strictly worse than the pre-CA02
  no-op, because it would also consume the click the `interact_tag` chain was meant to answer.
- **`handle_interact` scans, it no longer takes the first entry.** `entries.first()` became
  `entries.iter().find_map(|&(_, dialog_id, _)| dialog_id)`. Two reasons: an interaction-only bind
  must not answer the click, and it must not *mask* a sibling bind on the same template that does
  carry a dialog. `available_interactions` is append-ordered and the `!` bind is installed at
  `player_loaded`, i.e. first — so `first()` plus any later topic bind would have dropped the real
  dialog. Behaviour is unchanged whenever every entry has a dialog (the first still wins), so this
  is not a behaviour change for existing content.
- **Falling through, not returning early.** With only interaction-only binds, `handle_interact`
  returns `None` and control reaches the static `interaction_type` dispatch, as it did before any
  bind existed. The caller (`cell_methods/player/interaction/interact.rs:161-203`) has already run
  `fire_interact_tag` / `fire_interact_template` *before* `handle_interact`, and a matching chain
  short-circuits it — so Gerschon's dialog comes from CA01's `interact_tag Castle_SgtGerschon` chain
  and never needs the bind to carry one. This is the mechanism that makes a flag-only bind useful.
- **`handle_initial_response` bails with its own log.** The lookup now distinguishes "set map not
  bound" (`debug`, unchanged) from "bound but interaction-only" (`info`, new). Neither emits a
  frame.
- **Two distinct logs on the interact path** for the same reason: "no per-player interactions for
  template" versus "binds are all interaction-only … falling through". An operator debugging a
  silent click needs to tell those apart, and the second one is expected behaviour rather than a
  fault, so neither is a `warn`.
- **Tuple kept, not promoted to a struct.** `Vec<(i32, Option<i32>, i64)>` is less readable than a
  named struct, but promoting it would touch every reader for no behavioural gain and widen a packet
  whose point is one nullable column. The field's doc comment now spells the tuple out. Flagged for
  the coordinator as a cleanup candidate, not done here.
- **`.adddialog` GM feedback** prints `dialog none, interaction-only` instead of a fabricated id, so
  a GM binding row 3062 by hand can see the bind succeeded.
- **Test file split.** `dispatch/tests.rs` (427 lines) would have passed the 500-line soft cap, so it
  became `dispatch/tests/mod.rs` plus `dispatch/tests/interaction_only_bind.rs`. `mod tests;` in
  `dispatch/mod.rs` resolves identically either way, so **no other module changed**, and the private
  helpers stay reachable through `super::super::`.

## Regression proof

Each guard was shown to fail with its half of the fix reverted, then to pass again once restored.
The reverts were applied mechanically (`scratchpad/revert.py`, four named patches) and undone with
`git checkout --`, so the restored tree is bit-identical to the commit.

**Phase 2 — loader reverted** (re-add the `dialog_id.is_none() → continue` drop, so NULL rows never
reach the cache: the original B3 bug):

```text
FAIL cell::spawner::tests::live_db_loaders::live_db::load_dialog_set_maps_retains_rows_with_null_dialog_id
  panicked at live_db_loaders.rs:313:
  dialog_set_map_id 1565 has NULL dialog_id in DB but was dropped from the cache
```

The guard trips on the first NULL row the seed happens to yield (1565), not on a Castle id — which
is the right shape: the bug was never Castle-specific, and the assertion walks every NULL row in the
table.

**Phase 3 — click paths and executor reverted** (three patches: `handle_interact` back to
`first()` + `unwrap_or(0)`; `handle_initial_response` bail removed *and* `unwrap_or(0)` substituted;
`add_dialog_set` returns early on a dialog-less entry, reproducing the pre-CA02 no-op from a
populated cache). 4 failed, 2 passed:

```text
FAILED add_dialog_set_with_null_dialog_pushes_flag_only
  the bind must be recorded with dialog_id None -- a substituted 0 would make the click open an empty dialog
FAILED interact_with_only_null_dialog_bind_displays_nothing
  an interaction-only bind opens no dialog -- returning Some(0) here would also fire a bogus dialog_open content event
FAILED interact_skips_null_dialog_bind_and_uses_the_real_one
  the flag-only entry must be skipped over, not answer the click
FAILED initial_response_on_null_dialog_bind_displays_nothing
  (at interaction_only_bind.rs:157 — a frame was emitted where none may be)
ok     add_dialog_set_with_dialog_pushes_same_flag_only_payload
ok     interaction_type_bind_push_is_flag_only_on_the_wire
```

**The two that passed are supposed to pass**, and saying so is part of the proof. Both describe the
*with-dialog* path and the wire shape, neither of which any of the three reverts touches. Stated
plainly: `interaction_type_bind_push_is_flag_only_on_the_wire` is a **wire-shape pin, not a
revert-guard** — it asserts the claim this packet rests on (the `InteractionType` body is one
`UINT64` and a with-dialog bind produces identical bytes), so it fails if someone later appends a
dialog id to the payload, not if the CA02 logic is undone. It was checked by hand against a
4-byte-longer expected payload, which diverges as intended. `add_dialog_set_with_dialog_…` is the
companion that pins no behaviour change on the existing path.

**Phase 4 — restored:** `test result: ok. 6 passed; 0 failed` on the same filter, and the live-DB
guard back to `1 passed` in Phase 1's shape.

A first attempt at this proof (an earlier lane hold) aborted in Phase 2: the revert patterns were
written with `\n` while git had checked the files out with CRLF, so the substitution matched zero
times and the script exited rather than testing a half-reverted tree. Recorded because the failure
mode is silent in the other direction — a patch that matches *nothing* and a patch that matches
everything both look like "the script ran".

## Review round (PR #661, testing-validation-engineer: yellow — code sound, coverage gaps)

Six items, all applied. One was a real engine bug the original packet shipped.

1. **Bind-time push folded only the new entry (engine bug, fixed).**
   `send_interaction_update_if_visible` sent `base_flags | entry.interaction_flags`, while
   `remove_dialog_set` and the AoI re-send both fold every entry on the slot. `InteractionType`
   *replaces* the client's bitfield rather than OR-ing into it, so a second bind on the same
   template cleared the first bind's indicator until the next AoI entry re-sent the full fold.
   Latent before CA02 (two binds on one template were vanishingly rare); CA02 makes the shape
   deliberate — an interaction-only indicator alongside a topic that carries a dialog — so it had to
   be fixed here, not deferred. The helper now folds `available_interactions[slot]`, which both
   callers have already written to, and takes `dialog_id` for logging instead of the whole entry.
   Guard: `second_bind_on_same_template_pushes_both_indicator_bits`.
2. **Fan-out test trimmed and relabelled.** Dropped an `args.len() == 8` assertion on a
   `u64::to_le_bytes()` result (a tautology — the compiler guarantees it) and a second half that
   re-sent the same byte vector through the arm and asserted the output matched, i.e. that a pure
   function is pure. Added an observee address with `send_count_to(observee_addr) == 0`, which is
   the wrong-recipient class this file exists for and what the removed half should have been.
   Renamed to `…_and_reaches_only_the_witness`.
3. **Dispatcher-level coverage added.** The three click-path guards call the inner
   `interactions::handle_interact`, which the real flow never reaches for a Castle story NPC:
   `fire_interact_tag` runs first and short-circuits it. The new test stages the CA01 shape (NULL
   bind + matching `interact_tag` chain) and asserts the chain's dialog is the only frame emitted.
4. **AoI re-send covered.** `compute_player_aoi`'s standalone `InteractionType` had no test, and it
   is the packet's client-visible acceptance: a bind installed while the NPC is out of view reaches
   the client only on AoI entry. Gated on `has_dynamic_properties`, which the test sets explicitly
   rather than relying on.
5. **Click-path ordering pinned** in both bind orders, so a future "first entry wins" regression
   cannot pass because the seed happened to order its binds favourably.
6. **This section, and the type-label correction above.**

Structural note: `executor/dialog.rs` reached 766 lines, past the 700 hard cap, so it became
`executor/dialog/mod.rs` (440) + `executor/dialog/tests.rs`. `cell_methods/player/interaction/mod.rs`
is now 621 lines — inside the 500-700 band where a split is optional. Left whole deliberately: PR

## Known gaps

- **`onInitialInteraction` (104) is still never emitted.** The original offered several bound topics
  in one list and let the player pick; we shortcut to the first bound dialog. `topic_text` on a
  `dialog_set_maps` row is therefore dead data. Out of scope here and not needed by any Castle
  packet, but it is the reason `handle_interact` has to pick a dialog at all instead of sending a
  list. Worth a packet of its own if a zone ever needs two simultaneous topics on one NPC.
- **No UAT.** The packet's client-side acceptance ("the `!` appears over Gerschon before accept")
  needs CA01's chain to exist and an in-client session. Nothing in this branch is observable in the
  client on its own: it makes a bind *possible*, and no seed row binds an interaction-only row yet.
- **`available_interactions` is a bare tuple.** See the design note above.
- **Interaction-only rows on `remove_dialog_set` were not specially handled** and did not need to
  be: `remove_dialog_set` matches on `dialog_set_map_id` and re-folds the remaining flags, never
  reading a dialog id. `removeDialog(149, 3062)` therefore maps 1:1 already, which CA01 needs when
  it swaps the Gerschon bind for the Copplemann one.
- **`cell_methods/player/interaction/mod.rs` is 910 lines, past the 700-line hard cap, and was
  left that way.** It was already 818 on `origin/main` before this branch touched it — #659 added a
  test block and two helpers to a file that was 621 — so the violation is pre-existing, not

## Evidence / hypotheses

1. **B1 confirmed as described.** `resolve_respawn_target` priority 1 (`respawner_id` from the
   Defeat Window) and priority 2 (first respawner for the player's world) both matched the
   World 8 rows and returned their `(0,0,0)`. The Castle-default and in-place fallbacks below
   were unreachable *because the rows existed*. World 8 resolves as world name `Castle`
   (`worlds.sql` row 8), which is a real non-instanced space in `entities/spaces.xml`
   (`MinX=0 MaxX=2400 MinY=0 MaxY=2400`), so the world-match path definitely fired for a
   player dying in Castle — and `(0,0,0)` is on the corner of that AABB.
2. **The Castle default is a different world.** `CASTLE_WORLD` in `respawn.rs` is
   `Castle_CellBlock` (world 12) with position `[-334.231, 73.472, -228.026]`, which is
   respawner row 8 (`Stasis Chamber`). It was never a fallback for world 8; a player dying in
   `Castle` with no usable respawner takes the priority-4 in-place branch instead.
3. **Side effect of authoring the rows: world 8 gains movement-validator recovery targets.**
   `resolve_recovery_position` (priority 2) snaps an out-of-bounds / off-navmesh player to the
   nearest respawner for their world that passes bounds + navmesh validation. The origin rows
   never passed, so Castle previously had none and fell through to the AABB clamp. The four
   authored points now become candidates. That is an improvement, but it means a badly-placed
   checkpoint would also become a bad rubber-band target — one more reason the UAT matters.
4. **Second consumer of the same rows.** `space_manager/client_move.rs::resolve_recovery_position`
   already filters respawners through navmesh + bounds soundness before using one as a
   movement-validator recovery target, so an origin row was harmless there (it fails
   `is_point_valid` / bounds). Only the respawn path trusted the coordinates blindly. No change
   needed there; the comment at `client_move.rs:507` documents the same "no validation in the
   loader" observation this packet's guard acts on.
5. **No proximity aggro as seeded.** `CellEntity::aggression` is constructed at `0`
   (`crates/entity/src/cell_entity/construction.rs:88`) and only raised by the `set_aggression`
   content action or the GM console; `npc_ai` runs `npc_ai_idle_auto_aggro` only when
   `aggression > 0`. Standing a respawn point ~8 units from the faction-1 Praxis Jaffa at
   Checkpoint Alpha therefore does not start a fight on its own. (A mob that was already
   Fighting the player when they died keeps its threat entry — same-world respawn preserves the
   entity id — so a respawn inside `LEASH_DISTANCE = 50` of the mob's spawn can be re-engaged.
   That is true of every candidate point in that area and is not something this packet can fix.)
6. **World 23 has no recoverable positions.** Rows 6/7 (`Respawner`,
   `Respawner_bet_Infirmary`, world `Beta_Site_Evo_1`) are at the origin too. The names give no
   location — there is no point set, spawn, region or sequence named for a Beta Site infirmary
   anywhere in the seed — and no Python script reads or writes respawner positions
   (`Respawner.py` is a pure row-to-object mapper; both `SGWPlayerRespawner.py` files are empty
   stubs). The only world-23 coordinates that exist at all are the stargate (`617.866,
   -59.314, 388.971`) and its DHD spawn, which are evidence of *a* walkable point, not of where
   either respawner stood. Left at the origin per the packet instruction not to invent.

## Design decisions

1. **Coordinates authored by interpolation inside known-walkable footprints, not extrapolation
   past their edges.** Every world-8 actor position in the seed is a point the original
   designers placed on floor. A point between two such actors is almost certainly floor; a point
   5-10 units beyond the outermost actor is as likely to be a wall, a ledge or a drop. The
   failure modes are asymmetric — spawning in geometry is unrecoverable for the player because
   `unstuck` is still unimplemented (`cell_methods/player/combat/mod.rs`, `UNSTUCK =>
   UNIMPLEMENTED`), while spawning a few metres further from the intended checkpoint is
   cosmetic. So:
   - **1 Checkpoint Alpha** `(800, 55.21, 513)` — on the line between the Praxis Jaffa guard
     group (spawnlist 121/123/124, x 786-790) and the Marsh / Moh'katan / Jaffa-Lieutenant group
     (spawnlist 118/120/119, x 807-811), all at y 55.20-55.30. Nearest authored actor is the
     `Castle_DHD` prop (spawnlist 2) at 7.6 units; nearest NPC is Moh'katan at 7.9. The packet
     suggested `~(814, 55.2, 509)`, which is ~5 units past the easternmost actor; I moved it
     inside the cluster instead for the reason above. Both are guesses until UAT.
   - **2 Throne Checkpoint** `(345, 41.2, 650)` — inside point set 2049 `Castle.ThroneRoom`,
     biased west rather than box-centre. The box's two west corners are at y 41.13/41.15 and the
     `Castle_AccessPanel` spawn just outside the west edge is at y 41.18, while both east
     corners are at y 48.19 — a ~7-unit step or ramp of unknown extent. A centre point has to
     guess which side of that step it lands on; the west half has corroborated floor height.
   - **3 Op-Core Triangle** `(371.037994, 70.1490021, 904.648987)` — **provisional, pending
     CA05.** Nothing in the seed is named for an Op-Core Triangle (no point set, spawn, region
     or sequence), so there is nothing to interpolate from. This is a corner point of point set
     2051 `Castle.Infirmary` (point 2325) — authored region geometry on the y ~= 70.1-70.3
     interior level that the Coppleman / PRU corridor NPCs (spawnlist 87/90/114) stand on, 20-40
     units away. The packet described this point as being "on the mission-701 hallway route"; I
     could not corroborate a mission-701 link (nothing in `mission_*`/`event_*` references point
     set 2051), so the seed comment claims only what the geometry supports. Flagged
     `PROVISIONAL -- pending CA05 recon`.
   - **4 Armory** `(466.365, 70.397, 991.466)` — the best-evidenced point in the zone: it is
     simultaneously `ring_transport_regions` row 34 `Castle_ArmoryRingDropZone` (point set 2081)
     and the `cross_world_teleport` target of Castle_CellBlock chain 1109, i.e. the spot every
     player who arrives from the Cellblock is already standing on.
2. **The runtime guard tests exact equality with `[0.0, 0.0, 0.0]`, not a radius.** The origin is
   a sentinel produced by the data-recovery gap, not a coordinate anyone authored. A tolerance
   band would start silently discarding legitimate near-origin respawn points (`CombatSim` and
   the test spaces sit on the origin). `-0.0 == 0.0` under IEEE-754, so negative zeros are
   covered. Pinned by `resolve_respawn_target_honours_a_respawner_just_off_the_origin`.
3. **The guard skips at both priorities and keeps scanning.** Priority 1 (explicit id) warns and
   falls through; priority 2 filters origin rows out of the world scan rather than testing only
   the first match, so a world with `[origin, authored]` rows resolves to the authored one. The
   priority-2 warn only fires when at least one row was actually skipped and none was usable, so
   the healthy path stays silent.
4. **`is_unauthored` is a named private fn, not an inline comparison,** so the "why" lives in one
   doc comment that both call sites point at, and a future third consumer (e.g. the Defeat
   Window list) can reuse it.
5. **`combat/tests.rs` was not split.** It lands at ~620 lines, inside CLAUDE.md's discretionary
   500-700 band. There is a real seam (dispatch tests vs respawn tests), but
   `docs/testing/inventory/services.md` deep-links two of these tests by `tests.rs#L<line>`, and
   the file is a plausible merge target for other Castle packets; a rename now costs more than
   it buys. Recorded here as a future cleanup rather than done silently.
6. **The Defeat Window list was left alone.** `damage_apply/mod.rs` still offers every respawner
   for the player's world by name, including an origin row. With the guard in place, clicking
   such an entry no longer strands the player — it falls through to the fallbacks — so the
   remaining wart is cosmetic (a checkpoint that silently sends you somewhere else). Filtering
   there changes an `onBeginAidWait` wire payload and would need a type-2 byte test; out of
   scope for CA00. See "Integration edits / follow-ups".

## Regression proof

One lane hold, scripted, so the DB was never reloaded under another worker's tests. Both halves
fail with the change reverted:

**Live-DB guard (seed side).** Loaded the DB from this worktree's seed → guard PASSes. Then
`UPDATE resources.respawners SET pos_x=0, pos_y=0, pos_z=0 WHERE world_id=8` — exactly the
pre-CA00 seed state, applied to the loaded rows rather than re-loading a reverted file, to avoid
a second 3-minute reload of the shared DB — → guard FAILs (`B_EXIT=100`) naming all four rows:

```text
respawner rows sitting at the world origin: ["4 'Armory Respawn' (world Castle)",
"3 'Op-Core Triangle Respawn' (world Castle)", "2 'Throne Checkpoint Respawn' (world Castle)",
"1 'Checkpoint Alpha Respawn' (world Castle)"] — a player who picks one of these in the Defeat
Window is teleported to (0,0,0). ...
```

Restoring the four rows makes it PASS again (`C_EXIT=0`).

**Unit guards (code side).** `git checkout 3c1fed6c -- respawn.rs` (the pre-CA00 file, guard
removed) → `cargo test --lib resolve_respawn_target` FAILs (`D_EXIT=101`) on exactly the two new
guards, with the three pre-existing `resolve_respawn_target` tests still green:

```text
resolve_respawn_target_skips_origin_respawner_on_explicit_id ... FAILED
  left: [0.0, 0.0, 0.0]   right: [42.0, 1.0, 17.0]
resolve_respawn_target_skips_origin_row_for_a_later_authored_one ... FAILED
  left: [0.0, 0.0, 0.0]   right: [-5.0, 5.0, -5.0]
test result: FAILED. 5 passed; 2 failed
```

`left: [0.0, 0.0, 0.0]` is the bug itself — that is the position the pre-CA00 code hands the
respawn path. Restoring the file returns the suite to 34 passed / 0 failed (`E_EXIT=0`), and the
proof script left the working tree clean apart from the still-uncommitted docs.

The third new unit test (`..._honours_a_respawner_just_off_the_origin`) is deliberately **not** a
guard — it passes both before and after. It pins the blast radius of the exact-equality test so a
later "tolerance band" refactor has to break it consciously.

## Known gaps

1. **Every coordinate is provisional until in-client UAT** (D-CA11 says MEDIUM confidence on each
   one). The UAT is: die once at each of the four checkpoints and confirm the landing spot is
   walkable, in the right room, and not inside geometry.
2. **Respawner 3 (Op-Core Triangle) is a placeholder on the Infirmary corner point**, not the real
   checkpoint. CA05's recon owes the position; the seed comment says so.
3. **World 23 rows 6/7 stay at the origin** with a KNOWN GAP comment in the seed. The new guard
   makes them fall through to in-place respawn, so world 23 degrades to "respawn where you died"
   instead of "(0,0,0)".
4. **No per-player unlock gating** (#233) and **no corpse lifecycle** (#62) — explicitly excluded.
   All four Castle checkpoints are offered to every player from the first death.
5. **Y heights are inferred from neighbouring actors' spawn heights**, which are authoring
   positions, not measured floor. If a checkpoint lands slightly above the floor the client
   settles it with gravity; slightly below is the failure case UAT needs to catch.

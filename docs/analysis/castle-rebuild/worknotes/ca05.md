## Part 1 — Recon

### Method

Four passes over all 145 local `.umap` tiles (`Castle.umap` + 144 sublevels;
`Castle_MapData.upk` is not a `.umap` and was not walked), via `tools/upk_parser.py`'s
`PackageReader` with the `extract_actors()` class whitelist bypassed so no actor type could be
silently excluded. Passes 1-3 are the earlier session's; pass 4 is what closed the
Communications room.

1. **Name-keyword scan** on a landmark word list (interrogation, comm, terminal, infirmary,
   symbiote, bunker, bravo, alpha, checkpoint, armory, respawn, triangle, throne, stargate,
   dhd, cell, detention, prison). 64 hits, all Kismet `Sequence`/`SeqEvent_Stargate`/
   `SeqAct_ConsoleCommand` objects with no `Location`.
2. **Mesh/prefab-reference resolution** — for every export with `serial_size > 32`, resolve
   `StaticMesh`/`StaticMeshComponent`/`TemplatePrefab`/`Archetype` `ObjectProperty` to its
   import/export name (one extra hop through the component export) and match the *resolved*
   name, because a UE3 actor's own `object_name` is usually an auto-numbered
   `StaticMeshActor_142`. 793 hits, 47 distinct prefab families.
3. **Class-based scan** — every `PlayerStart`/`*Respawn*`/`*SpawnRegion*`/`*SpawnSet*`/`Note`
   export. **Zero** `PlayerStart` or spawn/respawn-class actors exist anywhere in the Castle
   tree. This is a firm negative, not a parsing gap, and it is why D-CA11 is right: respawn
   points in this engine are server-authored.
4. **Screen/monitor family scan (this session)** — passes 1-3 searched for the words
   *comm*, *terminal* and *workstation* and found nothing, and pass 1's conclusion was that no
   Communications room asset exists. That conclusion was wrong, and the reason is a naming
   assumption: `texts.sql` moniker 7720 is
   `DN_Ob_D_HumanViewScreen_Castle_CommTerminal` = 'Communications Terminal'. The *string* is
   "Communications Terminal"; the *asset family* is **ViewScreen**. Re-scanning every tile's
   name table for the screen/monitor families found `EM-ViewScreen00/02/03`,
   `CA-Monitor_Wall_Screen00*`, `GP-Monitor_Wall00`, `EM-CmdPostScreens00` and `Em-Screen00`,
   none of which any earlier pass could match. Lesson for the remaining Castle packets: search
   the `texts.sql` moniker for the asset family before concluding an asset is absent.

Note also that a plain binary `grep` over the `.umap` files is **not** a valid substitute for
the parser — the packages are chunk-compressed, so grep sees only fragments (it returns
`_Screen00_` where the name table actually holds `CA-Monitor_Wall_Screen00A_FX`).

### Axis/scale calibration (HIGH confidence)

Actor `Location` values are raw UE3 cm in the source frame; `server.x = rawY/100`,
`server.y = rawZ/100`, `server.z = rawX/100`. Chunk-filename offsets do **not** apply — actor
`Location` is already absolute world space, and the filename only tells NavBuilder which OBJ
patch to load (`navmesh-extractor/src/chunk_id.rs`). The swizzle documented in `chunk_id.rs`
(`v.x=obj.z/100 …`) is for triangle-soup export, a different purpose. Cross-checked against
two ground-truth seeded coordinates:

- `GLB-Stargate_Prefab` in `Castle.umap`, raw `(54999.79, 76451.27, 6187.99)` →
  `(764.51, 61.88, 550.00)`, the same room as `Castle_DHD` (spawn 2, `(806.27, 55.10, 517.24)`)
  and the audit's gate coordinate `(761.68, 63.47, 551.72)`.
- A `Ca-ThronePillar00` actor in `Castle-00060003.umap`, raw `(63600.00, 35342.00, 3817.00)` →
  `(353.42, 38.17, 636.00)`, inside the existing `Castle.ThroneRoom` box (2049) on x and z and
  within ~3 units on y.

#### Zuritska is male — corrected after review (was a BLOCKER)

The first draft of template 168 cloned template 48 (Capt. Copplemann) and shipped Zuritska as
`BS_HumanFemale`. That was wrong, and the seed was the only place that thought so:

- `work-packets.md:69` already specified "body from a **human male** set".
- Every shipped dialog screen referring to Dr. Zuritska is masculine, decisively the one that
  drives this actor — dialog 2576 screen 96821 (`dialog_screens.sql:11759`): *"I need you to
  rescue Dr. Zuritska and take **him** to the Communications room on Level 5. **He** has to
  patch me into the Castle's comm systems."* Corroborated by dialog 88 screen 9427 ("Dr.
  Zuritska has also finished **his** weapon") and dialog 514 screen 5212 ("...if you can stand
  to be in the room with **him**").
- A sweep of every Zuritska-bearing screen finds no feminine pronoun referring to him. The one
  nearby "her" — dialog 2572 screen 96765, "Reinforce Copplemann in **her** efforts to get to
  Dr. Zuritska" — is Copplemann, who *is* female. That is how the error happened: the draft
  picked template 48 as a *gender source* for the wrong character.

Re-cloned from template 149 (Sgt. Gerschon), the closest in-zone friendly male civilian
archetype (faction 1, level 50, event_set 570, `BS_HumanMale`, no `WP-*` component), keeping
`name_id` 7066, `move_speed` 0.9 and the prisoner boots. Two deliberate departures from 149 are
in the table above and commented in the seed.

#### Display names are recovered originals, and new ones cannot be minted

The earlier draft left `name_id` NULL on Zuritska and the terminal and reused 7417 ('NID Guard')

   are usable — which is exactly why recovering them mattered rather than inventing one.
   A NULL/0 `name_id` is silent: the property is simply omitted and the NPC appears unnamed.
   Guard `castle_ca05_story_actors_all_have_a_client_resolvable_name_id` pins this.

Be clear about what the region linter does and does not prove here. An earlier version of this
worknote claimed the linter "proves" these names; it cannot yet.
`every_chain_region_key_matches_a_seeded_point_set` (`crates/content-engine/tests/interact_tag_linter.rs`)
walks chain seed files and checks each `enter_region`/`exit_region` `event_key` against
`point_sets.name` with no normalisation. **CA05 authors no chains**, so no chain references
either name and the linter has nothing to check for them — its 6/6 pass below confirms only that
these seed edits did not break the existing chains. Byte-exactness becomes a real, checked
assertion the moment CA06/CA07 land their `enter_region` triggers, and it is *their* acceptance
item: if either worker retypes a name, the linter fails in their PR, not this one. The failure
mode it protects against is worth restating for them — a casing or spelling drift makes the
chain silently never fire, with no error anywhere.

**All four boxes have a real vertical extent, and that was a bug fix, not a detail.** An
`AreaSet` volume is the point-wise min/max of its corners, so four corners sharing one y
describe a box of *zero* height — one that contains only a player standing exactly on the floor
plane. The shipped convention puts three corners on the floor and raises the fourth, which is
precisely what the engine's own cylinder→bbox workaround emits (`spawner/regions.rs`, whose
comment insists the asymmetry is intentional: "do not 'normalize' by raising all four corners"),
and every pre-existing `BoundingBox` set follows it: 2040 +6.31, 2041 +5.70, 2042 +16.31,
2043 +7.26, 2044 +7.61, 2049 `Castle.ThroneRoom` +7.04, 2050 +8.07, 2051 `Castle.Infirmary`
+4.33.

## Regression guards

Six live-DB tests in **`crates/services/src/cell/spawner/tests/live_db_castle_seed.rs`**
(`mod live_db`, `require_db_or_skip!`, serialised under `ci-live-db`).

These began life appended to `live_db_loaders.rs`, which took that file to 860 lines — past the
700-line hard cap. They now live in a sibling file, and the seam is a real one rather than a
line-count dodge: `live_db_loaders.rs` guards the *loader queries* (column renames, type drift,
JOIN breakage — bugs that make sqlx return `Err`), while these guard *seed content* that loads
perfectly well and is simply wrong. `live_db_loaders.rs` is back to its pre-CA05 691 lines and
`tests/mod.rs` gains one `mod` line. Sibling Castle/Harset seed packets should land their
content guards in the new file.

Guards 1 and 2 are driven by one `CA05_ACTORS: [(&str, i32, i32); 9]` table of
`(tag, template_id, name_id)`, so they cannot disagree about the cast.

| test | asserts | bug shape |
|---|---|---|
| `castle_ca05_story_actor_tags_resolve_to_exactly_one_spawn_row` | each of the 9 tags resolves to exactly one World 8 `SpawnRecord`, **bound to its pinned `template_id`**, with a non-empty `template_name` | a deleted/duplicated spawn row; a broken join; **a tag repointed at another template** — which keeps `template_name` non-empty and would pass a laxer assertion while silently swapping the actor's body, faction and stats |
| `castle_ca05_story_actors_carry_their_recovered_name_ids` | each actor's `name_id` **equals** its recovered value, and that id **exists in `resources.texts`** | NULL/0 ships a nameless NPC (the AoI create packet omits the property entirely); a wrong-but-nonzero id ships another character's name — `!= 0` caught neither |
| `castle_ca05_point_sets_are_four_corner_world8_boxes` | each of the 4 sets loads in `world_name == "Castle"` with **exactly 4** points **and ≥ 1 unit of vertical extent** | a degenerate 3-point box the client hit-tests wrongly, or a 0-point set whose `enter_region` never fires. Four is an engine invariant, not taste — `space_manager/mod.rs:74`: "After the cylinder→bbox workaround, all regions should have exactly 4 points". | `castle_ca05_actors_stand_inside_their_claimed_point_set` | 8 actors fall inside their box in x/z and within its floor-to-ceiling extent (3.0 units of slack below the floor for terrain slop) | an actor and its trigger volume drifting apart — exactly what the first draft shipped (both comms actors 11.6 units below and ~190 units away from `Castle.CommsRoom`) |

| `castle_hostile_world8_spawns_all_have_a_respawn_timer` | every `faction == Some(10)` World 8 `SpawnRecord` has `respawn_secs.is_some()` | a hostile row losing its timer and permanently despawning for the whole shard |

**What the position guards are not.** The server does not hit-test these boxes: region entry is
client-reported (`fire_enter_region`'s own doc comment — it fires "when the client crosses a
Kismet trigger volume"), and the box is pushed to the client at player-init
(`service/base_messages/player_init/mod.rs:369`). So these are seed-*consistency* guards. That
is the point: a mismatch has no runtime symptom at all except a mission step that never fires
in-client, which is why it survived a full green test run in the first draft.

The `resources.texts` half of guard 2 cannot be revert-proven independently — any id that fails
the lookup also fails the equality assertion first. It is a typo guard, and it cannot prove the
*client* has the string either (that lives in the PAK, not the DB).

## Evidence

### The emission order, from the Python

`SGWPlayer.py` is the emitter and it is unambiguous:

- `beginDialing` (2078-2089): cancels any dial in flight, sets `dialedAddress`,
  clears `gatePassable`, arms `Atrea.addTimer(now + 4.0)`.
- `cancelDialing` (2091-2103): drops the timer and the address. **Emits no
  sequence.** The `stargate::destroy` fire is only reached when the timer has
  already expired, and it is an internal event, not an `onSequence`.
- `gateDialTimerExpired` (2105-2114): sets `gatePassable = True`, sends
  `onSequence(dialingStargate.eventSet.getSequence(Stargate_MakeGate).seqId,
  entityId, entityId, 1, gameTime, [], KISMET_VIEW_EventInvoker, 0)`.
- `stargatePassed` (2117-2129): no-op unless `dialedAddress is not None and
  gatePassable`; then `onSequence(... Stargate_CrossGate ...)`, then
  `fire('stargate::passage')`, then clears the state, then `moveTo`.

Two details that changed the implementation:

1. **The sequences come from the ORIGIN gate, not the destination.**
   `onDialGate` (2073-2075) sets `dialingStargate = world.stargates[0]` from the
   player's current space, while `dialedAddress` is the destination. Our
   stargate cache is keyed by `stargate_id`, so "first gate in the world" is the
   lowest id in that world.
2. **Source and target in the payload are the PLAYER's entity id**, twice. There
   is no gate entity server-side — the gate is a client-side Kismet prefab. So
   "every witness of the gate" can only mean every witness of the dialer, and
   that is what the fan-out uses.

### The crossing is a region, and the region already loads

`GenericRegion.triggerRegion` (`GenericRegion.py:152-183`) tests
`region.flags & REGION_FLAG_Stargate` (bit 2) **first** and calls
`entity.stargatePassed()`. `GenericRegionManager.load` reads
`resources.point_sets` where `type = 'AreaSet'` — the same table our
`spawner::load_regions_from_db` reads.

`point_sets` set 1002 is `Castle.Stargate`, world 8, flags 3
(`ClientHinted | Stargate`), radius 2.5, height 10. The Castle gate volume is
therefore already loaded, already registered with the client through
`addClientHintedGenericRegion`, and already round-trips via
`triggerClientHintedGenericRegion`. Twelve such regions exist: Castle, Harset,
SGC, SGC_W1, Lucia, Tollana, Dakara_E1, Beta_Site_Evo_1, Omega_Site,
Ihpet_Crater_Dark, Ihpet_Crater_Light, Menfa_Dark.

**The `generic_regions` table is a red herring.** It also holds a row 1002, with
handler `cell.SGWPlayer.stargateRegionTriggered`, but neither the Python nor the
Rust server reads that table — both read `point_sets`. The packet's "region
1002" is `point_sets.set_id = 1002`, whose runtime id is assigned by insertion
order and is not 1002.

### Sequence resolution

Castle's gate (`stargate_id = 2`) carries `event_set_id = 10011`.
`event_sets_sequences` maps 10011 to sequences 10145-10158, and `sequences`
gives 10145 → event 6100 and 10158 → event 6113. Resolution goes through
`SpaceManager::sequence_map` keyed `(event_set_id, event_id)`, exactly as the
ring emitter does. Nothing is hardcoded. `stargates.event_set_id` was not in the
cache before this packet; `StargateEntry` gained the column.

## Design decisions

1. **The dial no longer travels.** Before CA10, `handle_dial_gate` sent
   `CellToBaseMsg::GateTravel` immediately. It now arms a dial and returns; the
   crossing travels. This is the behaviour change the packet implies and the one
   CA09 step 4469 depends on.
2. **Fallback for worlds with no gate volume.** Only twelve of the ~30 seeded
   stargates' worlds have a `REGION_FLAG_Stargate` region. On a world without
   one there is nothing to walk into, so a dial there travels immediately, as
   before, with a `warn!` naming the world. Without this, dialling out of the
   other worlds would strand the player. Deliberate divergence from the Python,
   which would have left them standing there.
3. **Tick-drained deferral, not a spawned task.** `pending_gate_dials` lives on
   `SpaceManager` and is drained by `gate_dial_tick` on the existing 100 ms cell
   tick — the C08a `deferred_content_actions` pattern, for the same reason (a
   spawned task has no route to `&mut SpaceManager`). It also buys the
   cancellation requirement for free: `destroy_entity` and `disconnect_entity`
   already scrub entity-keyed session state, so "cancel the pending 6100 if the
   dialer leaves the space" is one `.remove()` in each, with no separate
   cancellation path to forget.
4. **Re-dial cancels.** `begin_gate_dial` replaces the map entry, which is
   `beginDialing`'s `if self.dialedAddress is not None: self.cancelDialing()`. A
   re-dial therefore closes an already-open gate.
5. **One `onSequence` arg builder.** The 26-byte payload was already written out
   three times (ring transport, item sequences, the `PlaySequence` executor
   arm). Rather than add a fourth, the layout moved to `cell/kismet.rs` and
   `ring_transport::wire_helpers` now delegates to it. The other two call sites
   were left alone — different `ViewType`, out of scope.
6. **`engine` threaded into `cell_methods::gm::dispatch`.** `gmDHD` reuses
   `handle_dial_gate`, which now fires a content trigger, so the GM path needs
   an engine too. One signature change plus 113 mechanical test call-site
   updates; the alternative (an `Option<&ChainEngine>`) would have made a GM
   dial silently skip mission progress.

## Harset H01 seam

Per the coordinator's agreement with the Harset session (H01 owns the generic
stargate-region routing, `REGION_FLAG_STARGATE` in `space_manager/mod.rs`, and
`cell_methods/player/world/mod.rs`):

- The passage-side work is one self-contained function,
  `cell::gate_travel::on_stargate_passage(entity_id, player_id,
  origin_event_set_id, destination_world, tx, space_mgr, engine)`. It emits 6113
  to the dialer and every witness, then fires `stargate_crossed`. It does **not**
  travel and does **not** read the dial state, so H01's flag-2 entry point can
  call it unchanged — the rebase is a call-site move, not a rewrite.
- This branch's caller is `handle_stargate_region_entered`, which owns the "is a
  dial armed and open?" gate, consumes the dial, and performs the travel. That
  is the piece H01 replaces.
- The region handler contains **no region-id special case**: the routing is
  `region_flags & REGION_FLAG_STARGATE != 0`, and it runs *after*
  `fire_enter_region` / `fire_exit_region` and the ring-transport forward, so the
  ordinary region event still fires (H01's stated behaviour). It runs last
  because a successful crossing destroys the cell entity.
- `REGION_FLAG_STARGATE = 2` is added in `space_manager/mod.rs` by both branches;
  identical constant, trivial conflict.
- `stargate_dialed` fires inside `handle_dial_gate`'s success path, as agreed.
  The 6100 timer stays wholly on the dial side. Harset adds no triggers of its
  own and consumes these two.

## Content triggers (Scope B)

| `event_type` | Variant | `event_key` |
|---|---|---|
| `stargate_dialed` | `OnStargateDialed { destination_world }` | destination world name; NULL = any |
| `stargate_crossed` | `OnStargateCrossed { destination_world }` | destination world name; NULL = any |

Both dispatchers populate mission context and `archetype` like every other
`fire_*` site, so `step_status` and `archetype` conditions work. The match
param is `destination_world`; the origin world is also in the context as
`world_name`.

## Known gaps

- **DHD chevron animations** (6106-6112) and `Stargate_DestroyGate` (6103) are
  deliberately not emitted — D-CA10. Excluded by the packet.
- **Ring multi-player sync** (#406) and **squad travel** are untouched.
- **`known_stargates` enforcement** is still absent (Harset H06); any address in
  the cache can be dialled.
- **No exit handler for the gate volume.** The 2009 server had none either, so a
  player already standing inside the volume when the gate opens gets no fresh
  `entering` event and must step out and back in.
- **The fallback path's `stargate_crossed`** fires in the same call as
  `stargate_dialed`. A chain expecting a gap between the two sees none on those
  worlds.
- **`ImpactTime` is sent as 0.0, not the game clock.** The Python passes
  `Atrea.getGameTime()`; every existing Rust `onSequence` emitter (ring
  transport, item sequences, ability fire) sends `0.0f32`, and this one follows
  suit rather than diverging from the shared builder. The client treats it as an
  animation offset; ring transport works with 0.0, so this is believed harmless,
  but it is an unverified deviation.
- **No seed rows use the new triggers yet.** The chain-replay guards seed their
  own sentinel chains (`0x7000_6000`, `0x7000_6001`, `0x7000_6010`); when CA09
  lands real rows, those assertions should move to a mission-keyed module.

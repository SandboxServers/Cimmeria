  and his follow start on this exact event, so the line lands on the beat where he

- **1177 / the long-table cue** is the most literal of the three. The line says "take a
  flanking position behind that table" and mission 681's own objective **2725** says
  "Take position behind the long table to flank the guards and negate their cover".
  Same table, same room. It fires on **entry**, not on the flank, because it is an

- **1178 / the second flank cue** is 96352 with the table taken out of it — the same

### The line that could not be authored

**96353, "Crouch down when you're in cover!"** ships no chain, per the packet's explicit
instruction to leave it unauthored rather than hang it on an unrelated event.

The only trigger that means "the player is in cover" is `player_entered_cover`, which
needs a cover set placed in world space. `resources.cover_sets` has exactly five columns
— `chunk_id, chunk_name, primary_author, has_variant, src_pak`
(`db/resources/AI/Tables/cover_sets.sql:18-24`) — and `cover_nodes` adds position and
orientation but no world binding either. There is **no world, space or placement-transform
column anywhere in the schema**, and the loader pulls every row into one process-global
index (`crates/services/src/cell/cover/mod.rs:16-17`: "Per-process (not per-space)").
C05's extraction pass concluded from this that the 1,380 auto-extracted sets store
prefab-**local** coordinates and are non-functional as placed cover in *every* space
(Cellblock ledger `work-packets.md:84`). The one world-space-correct set in the game is
the hand-seeded **1381** `Castle_CellBlock_MedStationDesk` (`cover_sets.sql:1405`), which
is the tutorial med station in the Preparation room — not the Mess Hall, not Hallway05.

This is **deferred, not impossible**. Hand-seeding a Mess Hall cover set the way C05
seeded 1381 makes this line and C06's flank objectives 2725/2731 reachable in one stroke.
That is a UE3 `.umap` actor-placement extraction packet, not a dialog packet.

## Design decisions

1. **`content_triggers.once` is dead, so the gate is the only fire-once mechanism.**
   The column is read into `DbTriggerRow.once` (`crates/content-engine/src/loader/mod.rs:64`,
   `cell/content/engine_loader.rs:79`) and `convert_trigger` never looks at it again;
   `Chain` has no such field and `ChainEngine` keeps no firing history. `once = true` on
   shipped chains 1008 and 1044 is therefore inert. All three new rows say `false`
   rather than encode a guarantee the engine does not provide, and the seed comment says
   why. Confirmed independently by the mission-systems advisor.
2. **1176 is gated on the step, not the mission.** `mission_status 680 eq active` reads
   true from acceptance all the way to Region9, and nothing on the `teleport_in '3'`
   edge closes it — so a mission gate would re-speak the line on a second ring ride
   (die topside, respawn at a Preparation-room respawner, walk back to ring switch 2,
   ride up). Step **2344** is what chain 1072 advances away from on this same event, so
   it retires into `completed_steps` and the gate shuts for good. Deliberately **not**
   2345: `advance_step` re-sets the new step unconditionally, so a 2345 gate would
   re-open on a second ride. This came out of the advisor review; the original proposal
   had the leaky mission gate.
3. **Conditions read the pre-mutation state, which makes co-firing safe.**
   `ChainEngine::resolve_event_filtered` is a pure collector — it evaluates every chain
   in the bucket against one `&ExecutionContext` and pushes cloned actions, never
   executing (`chain/mod.rs:328-403`) — and `executor::execute_actions` is a separate
   later pass over that frozen list. So on the first crossing both the gameplay chain
   (1072 / 1073 / 1083) and the bark resolve; on any later crossing the bark's gate is
   re-evaluated and has been closed by the action the first pass ran.
4. **1178 duplicates chain 1083's gate exactly, on purpose.** Both bind the Region5
   enter edge, and 1083's `accept_mission 686` is what shuts the second arm. A comment on
   **both** chains says to keep the condition sets identical, and
   `chain_1178_is_gated_identically_to_the_mission_accept_it_rides` asserts it across
   three states so a one-sided edit fails a test rather than starting a repeating bark.
5. **The `counter` condition was considered and rejected as a vacuous guard.** A
   `counter messhall_kills eq 0` row on 1177 would look like a tighter gate and be none:
   `Condition::Counter` defaults a missing context key to 0
   (`conditions/mod.rs:306`, `unwrap_or(0)`) and `fire_enter_region` never calls
   `populate_counters_context` (`event_dispatch/region.rs:44-49`), so it would read 0
   forever and always pass. Recorded in the seed comment so nobody adds it later.
6. **Speaker string is `"Col. Marsh"`.** Two shipped 2009 speaker rows name this NPC:
   `speakers.speaker_id 261 = 'Col. Marsh'` (`speakers.sql:37`) and
   `941 = 'Colonel Marsh'` (`speakers.sql:69`, which is template 10's own `speaker_id`
   and matches his nameplate, `texts.moniker_id 7569`). 261 was chosen because it is the
   spelling 5019's companion-phase sibling dialog **2309** actually ships on its Marsh
   lines (`dialog_screens.sql:10576, 10580`), and chain 1171 displays that dialog in this
   same phase — so the chat line and the dialog window agree with each other. Both
   spellings are already visible in shipped content. The advisor argued for the nameplate
   spelling; this is a three-row edit if the owner prefers it.
7. **No `delay_ms` on any row.** All three land on a threshold the player just crossed,
   so a delay would move the line off the beat that justifies it. Pinned by
   `assert_no_deferred_actions`.
8. **No `world` condition**, matching sibling chains 1073 and 1083. `region_key` is a
   bare `point_sets.name` with no world on the trigger, so a world condition is the only
   separator between two worlds with an identically-named volume. The
   `Castle_Cellblock.*` names are world-prefixed by convention and none of the shipped
   chains gates on world; matching the siblings is right, but the guard is not there.
9. **Region key casing copied byte-for-byte from `point_sets.sql`.** This file mixes
   `Castle_CellBlock.Region8` (capital B, chain 1008) with `Castle_Cellblock.Region9`
   (lowercase, chain 1073) and trigger matching is an exact string compare. Both new
   region rows use the lowercase-b spelling the point sets carry.

- **The whole escort may be inert, and it is not this packet's to fix.** The
  npc-ai advisor found that `Preparation_ColMarsh` is template 10 with
  `class = 'being'` (`entity_templates.sql:25`), which maps to `class_id = 0x01`
  (`cell/spawner/npcs.rs:108`), while both the AI tick and the movement tick select
  entities with `class_id == 0x04` (`space_manager/queries.rs:224-228`,
  `service/ticks/npc_movement.rs:67`). If that holds, chain 1174 sets `ai_state = Follow`
  and `follow_target_id` and nothing ever reads them — Marsh stands at the Ring 3 pad
  from the moment 1173 snaps him there until 1161 destroys him. See out-of-scope finding
  1. **Consequence for DU-07:** the barks fire correctly and say the right things, but
  lines 2 and 3 may be attributed to an NPC the player left behind. The lines are not
  wrong; his position is. The T30 UAT row asks the tester to record where he actually was.
- **Relog mid-escort strands Marsh**, a pre-existing GC1b-1 gap already documented in
  the seed (`castle_cellblock_chains.sql`, GC1b-1 comment) and in UAT scenario T28. The
  barks still fire correctly after such a relog; they are simply attributed to someone
  standing in the Preparation room. Not gated around, because there is no condition
  primitive that reads an NPC's follow state or position, and gating on Marsh at all
  would (given the class-filter finding) gate the lines to never firing.
- **One accepted repeat window on chain 1177.** A player who backs out of the Mess Hall
  and charges back in *before killing a guard* hears the line a second time. The engine
  has no fire-once primitive and every `enter_region` chain in this file carries the same
  exposure; for a combat callout a repeat on a re-entry is the least-bad failure mode. It
  is called out in the seed comment and in the T30 UAT row so a tester does not file it.

   `spawn_npc_from_record_into` reads the template's `class` (`spawn.rs:176`). **Not
   verified by me** — reported as the advisor found it. It deserves its own issue: the
   fix is plausibly one seed word plus a production-path test, and it silently disables a

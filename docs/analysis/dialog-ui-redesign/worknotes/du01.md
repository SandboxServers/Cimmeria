## Evidence

A census over all 5,405 committed `CookedDataDialogs.pak` entries (python `zipfile` + regex, 2026-09-21) settled four questions the ledger left open. All four are recorded in code comments at the point they matter.

| Question | Finding |
|---|---|
| `<Buttons>` attribute order in the shipped data | All 4,349 button elements are `ButtonType ButtonID Text`. No other order occurs. |
| Self-closing buttons | None. All 4,349 use an explicit `</Buttons>`. |
| `ButtonID` domain | 8 (3,069 uses), 9 (918), 70 (28), 71 (3), then a long tail to 688. All non-negative, so `u32` is right. `ButtonType` is only ever 1, 2 or 4 — no shipped 3, 5 or 6. |
| `<Screens>` shape variants | 13,230 screens carry `SpeakerID Text ScreenID`; **229 screens across 218 dialogs carry no `ScreenID` at all**. None of those 218 is in the Target Matrix, but the parser has to round-trip them. |

That last row is the one that changed the design: `CookedScreen::screen_id` is `Option<u32>` and the emitter omits the attribute when it is `None`, rather than inventing `ScreenID="0"` for a screen key the client never shipped.

The QA entries also confirm three escaping quirks the patcher must not "fix": `&#xA;` for a newline, raw apostrophes (`isn't`, not `isn&apos;t`), and `&lt;&lt;playername>>` template markers.

## Design decisions

**Text is kept escaped, never decoded.** `CookedScreen::text_escaped` and `CookedButton::text_escaped` hold the attribute value exactly as it sits between the quotes. A decode-then-re-encode round trip would rewrite `&#xA;` to a literal newline (which an XML reader normalises to a space, silently reflowing the line) and would have to guess which of the five predefined entities to re-emit for a raw apostrophe. Keeping the raw form makes "change the buttons, keep the text" byte-exact rather than best-effort. Rust-authored text goes the other way and is escaped by `escape_xml_attr` on the way in — that is the only place the patcher writes new text.

**Button attribute order: `ButtonType`, `ButtonID`, `Text`.** The task allowed alphabetising like the root. The evidence says not to. The Server Build alphabetises the root but *not* the children: `docs/engine/cooked-data-pak-format.md` shows `<Screens SpeakerID ScreenID Text>` where alphabetical would be `ScreenID SpeakerID Text`. Comparing QA (`SpeakerID Text ScreenID`) to Server (`SpeakerID ScreenID Text`), the cooker's child transform was "move `Text` last, leave everything else in its cooked order". Applying that same transform to `<Buttons>` is a no-op, because all 4,349 shipped buttons already have `Text` last. So the emitted order is the shipped order, which also matches ledger fact F3. This is a readability choice, not a functional one — the client's cooked parser looks attributes up by name — but it keeps a diff between a patched entry and its canonical original legible.

**quick-xml, not a hand-rolled scanner.** `cimmeria-services` already depends on `quick-xml` 0.41 (auth handlers, minigame protocol, `spaces.xml`), so using it adds no dependency at all, which beats both a new dependency and a purpose-built parser. It also handles what a substring scanner gets wrong here: a `>` inside an attribute value, values split across lines, and the five `xmlns:*` declarations on a QA root. `attr.value` hands back the still-escaped bytes, which is exactly the form the design wants.

**The parser is strict, and a refusal is not a fallback.** Unknown element, missing required attribute, non-numeric id, `<Buttons>` outside a `<Screens>`, unterminated `<Screens>`, non-UTF-8 — all return `None`, and the caller keeps the canonical entry. Shipping a half-understood rewrite of a dialog is worse than shipping the dialog unchanged.

**`OnlyOn` checks before it mutates.** The missing-screen check runs over the parsed screens before any button is cleared, so a refused patch can never leave an entry stripped-but-not-repopulated.

**Module became a directory.** Seven files (`mod.rs`, `emit.rs`, `parse.rs`, `patch.rs`, `patch_tests.rs`, and the two zone tables) is well past CLAUDE.md's "4+ siblings → directory" rule, and the foresight rule says make the directory now. `mod.rs` re-exports the types external callers use so `resources/mod.rs`'s imports stay short.

**Zone-table names.** The ledger suggested `dialog_patches_cellblock.rs` / `dialog_patches_castle.rs`. Inside a `dialog_overrides/` directory the `dialog_` prefix is redundant, so the files are `patches_cellblock.rs` and `patches_castle.rs`. Two siblings, flat, per CLAUDE.md. The task prompt asked me to pick names that satisfy the file-organization rules; this is that choice. **Wave 1 packets: use the names below, not the ledger's.**

**Bump neutrality on an empty ship.** `compute_dialog_metadata_bump` hashes button fields and patch fields one at a time inside loops, rather than hashing the slices. An empty button list and an empty patch table therefore write nothing to the hasher, so the bump for the two existing overrides is byte-identical to what it was before this packet. Shipping the engine with no rows causes no client refetch. A test pins it.

**Patches compose on top of regenerations.** The emitter's output parses back, so a patch applied to a regenerated entry works. Nothing does that today; two tests keep the tables disjoint (`no_dialog_is_both_regenerated_and_patched`) and prove composition works if a future packet wants it.

## Regression proof

Two independent reverts, run against the same filter (`cargo test -p cimmeria-services --lib dialog_overrides -- --test-threads=1`).

**Revert 1 — downgrade the missing-screen negative log.** Changed `tracing::warn!` to `tracing::debug!` on the `PatchError::ScreenMissing` arm in `patch.rs`.

- `missing_screen_warns_and_leaves_the_entry_untouched` **FAILED**.
- The other two negative-log guards stayed green, confirming they are independent rather than one guard catching everything.

**Revert 2 — stop `OnlyOn` stripping the buttons it replaces.** Removed `screen.buttons.clear();` from the `OnlyOn` loop, so the plan only *adds* a button.

- `only_on_leaves_exactly_one_button_on_the_named_screen` **FAILED**, printing the exact bug shape: `[(Some(96821), 1), (Some(96822), 1), (Some(96823), 1), (Some(96824), 0), (Some(96825), 1)]` — four buttons where one was promised, i.e. the mid-dialog soft-lock survives the "fix".
- `only_on_strips_the_mid_dialog_buttons_it_replaces` **FAILED**.
- `only_on_emits_expected_server_build_bytes` **FAILED**.

Combined run with both reverts in place: `39 passed; 4 failed`. Both reverts were then undone and the suite returned to `43 passed; 0 failed`.

## Known gaps

- **`ButtonPlan` carries `#[allow(dead_code)]`.** Its only non-test constructors are the two zone tables, and both ship empty, so clippy's `-D warnings` would otherwise fail the build. The attribute names the reason and says to drop it; whichever Wave 1 packet adds the first row should delete it and confirm clippy still passes.
- **`shipped_patch_tables_are_empty_until_wave_1` is a deliberate landmine.** It asserts `no_patches_registered()`. The first Wave 1 row makes it fail. Its message says to delete it. `shipped_patch_tables_apply_as_a_no_op` will also need its assertions re-pointed once a table is non-empty.
- **Seed agreement is not enforced by this packet.** `DialogPatch` rows and `db/resources/Dialogs/Seed/dialog_screen_buttons.sql` are kept in sync by hand, exactly as the full-regeneration overrides already are. The ledger assigns the patch-versus-seed agreement test to DU-02a/DU-02b and the seed-side linter to DU-L. I did not build a generic agreement helper, because it would have to read the seed and nothing in `dialog_overrides/` does DB or file IO today.
- **`ui_screen_type` is the only root attribute a patch can change.** `DialogFlags` and `KismetEventSetID` are carried through untouched. Nothing in the Target Matrix needs them; add a field if DU-04 turns out to.
- **No hot reload.** Overrides and patches apply once at PAK load, like every other override module. Editing a table needs a server restart.
- **Type 3 (Tutorial) and types 4/5 are untested in the client.** This packet can emit any `ui_screen_type`; whether the client's cooked parser accepts 4 and 5 is DU-00's question, not settled here.

## Integration notes for Wave 1

Nothing in `crates/services/src/base/dialog_overrides/` outside the two zone tables needs to change for DU-02a or DU-02b. The exact syntax:

**DU-02a**, in `crates/services/src/base/dialog_overrides/patches_cellblock.rs`, replacing `&[]`:

```rust
pub const CELLBLOCK_DIALOG_PATCHES: &[DialogPatch] = &[
    // 3999 — Future Self. Receive Item sat on 7 of 9 screens, so a player
    // who read to the end had no button and the grant chain never fired.
    DialogPatch {
        dialog_id: 3999,
        ui_screen_type: None,
        buttons: ButtonPlan::StripAll,
    },
    // ... 2299, 4001, 5022, 5023, 2309, 2516, 5859 the same way
];
```

**DU-02b**, in `crates/services/src/base/dialog_overrides/patches_castle.rs`:

```rust
pub const CASTLE_DIALOG_PATCHES: &[DialogPatch] = &[
    // 2576 — Copplemann's turn-in. Take Missions moves from screens
    // 96821/96822/96823 onto the final screen 96825. Closes 701 seed GAP 3.
    DialogPatch {
        dialog_id: 2576,
        ui_screen_type: None,
        buttons: ButtonPlan::OnlyOn {
            screen_id: 96825,
            button_type: 4,
            button_id: 71,
            text: "Take Missions",
        },
    },
    // 2573 — Accept (type 2, id 8) on final screen 113558.
    // 5861 — Accept (type 2, id 8) on final screen 96789.
];
```

**DU-05** (type labels) uses `ButtonPlan::Keep` with `ui_screen_type: Some(5)`, and for the two Cimmeria-authored dialogs edits `DIALOG_OVERRIDES[n].ui_screen_type` directly rather than adding a patch — 3995 and 3996 are regenerations, and `no_dialog_is_both_regenerated_and_patched` will fail if someone patches them instead.

Three things every Wave 1 packet must do:

1. Delete `#[allow(dead_code)]` from `ButtonPlan` in `patch.rs` (first packet to land only).
2. Delete `shipped_patch_tables_are_empty_until_wave_1` in `patch_tests.rs` and re-point `shipped_patch_tables_apply_as_a_no_op` (first packet to land only).
3. Leave `no_dialog_id_is_claimed_by_two_patch_rows` and `no_dialog_is_both_regenerated_and_patched` in place. They are what catches DU-02a and DU-02b claiming the same dialog id when the two branches merge.

> Type: worknote. Packet: DU-08 of the [dialog UI redesign ledger](../work-packets.md).

## 1. Contract

Replace `CellEntity::open_dialog_id: Option<i32>` with a small bounded set of
offered dialog ids. `send_dialog_display` inserts; a valid choice removes
exactly that id (still one-shot, so a replay stays rejected); the set clears on
logout, entity teardown and world change. Bound at eight, evict the oldest with
a `warn!`. Do not weaken the gate: a forged id that was never offered must still
be rejected. Then audit every Castle and Cellblock chain where an eviction can
now deliver a previously-rejected `(A, -1)`.

## 4. Evidence

Ghidra pass on SGW.exe, 2026-09-21, image base `0x00400000` (DU-RE report Q2,
Q5, Q8; summarised in the ledger's Native Findings):

- `DialogController`'s ctor `FUN_00d26850` builds a two-element slot array at
  `this+0x3c` (non-tutorial) and `this+0x40` (tutorial).
- The display core `FUN_00d24f10` picks the slot by screen type. If the slot
  holds a DIFFERENT id it calls the discard function `FUN_00d249c0` on the old
  id BEFORE installing the new one. The same id re-arriving is an idempotent
  re-display and does not discard.
- Discard closes the window and sends
  `Event_NetOut_DialogButtonChoice{ButtonId = 0xFFFFFFFF}` **if and only if**
  the old dialog has zero cooked buttons. A dialog with buttons sends nothing
  when it is evicted.
- Clicking a button sends the cooked `ButtonID` and closes (`FUN_00d24860`).
- `activateAvailableDialog` (`FUN_00d25160`) re-enters the same display core
  locally and sends nothing, so a lure opened minutes later is invisible to the
  server (F10).

So when the server displays B while zero-button A is open, the client's
`(A, -1)` arrives AFTER the server has already recorded B. The pre-DU-08 single
pin rejected it and A's `dialog_choice` chain never fired. Legacy python kept a
dict (`deprecated/python/cell/SGWPlayer.py`, `displayedDialogs`), not a slot.

## 5. Design decisions

1. **`VecDeque<i32>` on `CellEntity`, bounded at 8, FIFO eviction.** The client
   can hold two active dialogs plus lure queues; eight leaves headroom without
   letting a player who ignores everything accumulate an unbounded list. The
   bound and the one-shot guarantee live in four methods on `CellEntity`
   (`offer_dialog`, `take_offered_dialog`, `dialog_is_offered`,
   `offered_dialogs`) so there is exactly one implementation.

2. **The field is private (`pub(super)`), a deliberate exception to this
   struct's all-`pub` convention.** A direct `push_back` cannot forge past the
   gate, but it could break the bound or duplicate an id into a double-fire.
   The enforcer confirmed this costs zero call sites.

3. **Re-offering an id de-duplicates and refreshes recency.** Re-display is
   idempotent on the client, so a second entry would let one dialog's chain fire
   twice. Pushing to the back also makes the just-displayed dialog the last
   evicted.

4. **The eviction `warn!` lives at the call site, not in the entity crate.**
   `offer_dialog` returns the evicted id; `send_dialog_display` logs it with
   `player_id`, `dialog_id`, `evicted_dialog_id`, `max_offered` and the full
   offered set, per `docs/architecture/negative-logging-convention.md`.

5. **The take happens before the chain fires.** A chain action may display a
   follow-up dialog, whose `send_dialog_display` must be free to record its own
   id; and taking first is what makes a replay find the id gone.

6. **Clear on logout / world change: already covered, by entity lifetime.**
   Logout, cross-world travel and GM despawn all route through
   `SpaceManager::destroy_entity`, which removes the entity from
   `space.entities` (`crates/services/src/cell/space_manager/entities.rs:166`),
   taking the set with it. No explicit clear was added; a test pins the property
   instead (`the_offered_set_does_not_survive_entity_teardown`) so a future
   change that keeps the entity across a session boundary trips.

7. **Same-world respawn deliberately does NOT clear the set.**
   `cell_methods/player/combat/respawn.rs` is an in-place reanchor that
   preserves the cell entity. The offers were made to this same player in this
   same session, each is still single-use, and each choice chain still evaluates
   its own conditions at answer time. Clearing would destroy exactly the case
   this packet exists to protect (a zero-button dialog whose late close is
   interleaved with a death) and buy no authority. A comment in that block says
   the omission is deliberate, because everything adjacent to it IS cleared.

8. **The rejection `warn!` keeps its shape** but now logs `offered_dialog_ids`
   (the whole set) instead of the single pin, and its message says "was never
   offered to this player" rather than "no matching open dialog".

## 7. Seed audit — where an eviction can now deliver a previously-rejected close

Scope: all 165 chains in `castle_cellblock_chains.sql`, `castle_701_chains.sql`,
`castle_702_704_chains.sql`, `castle_706_708_chains.sql`. All 165 are seeded
`enabled = true`. `display_dialog` is the only display action used; there is no
`start_dialog` or `offer_mission` in these files. `add_dialog_set` binds a topic
and does not display.

### 7.1 The mechanism, stated precisely

A newly-accepted event needs three things at once: the evicted dialog must have
ZERO cooked buttons (a buttoned dialog sends nothing on eviction, RE Q5), its id
must still be in the offered set (not already consumed by a button click), and
some chain must key on that id. A chain that triggers on `dialog_choice` cannot
evict the dialog that triggered it, because the client discarded that dialog to
send the event.

The packet asks this to be verified against the code: **a dialog whose chain
already fired via a button click has its id REMOVED from the set, so a later
eviction close is still rejected.** Confirmed. `handle_dialog_button_choice`
calls `take_offered_dialog` before `fire_dialog_choice`
(`cell_methods/player/interaction/dialog.rs:44`), and `take_offered_dialog`
removes the id and returns `true` exactly once. The test
`a_forged_id_is_rejected_and_an_answered_id_cannot_be_reclosed` pins it: a
button click on A followed by a late `(A, -1)` fires A's chain exactly once.
Independently, the client closes a dialog when a button is clicked, so a
buttoned dialog cannot be evicted after being answered anyway.

### 7.3 What "fixes a latent loss" means

For the fourteen rows marked so, the victim of an eviction would be one of the
zero-button keyed dialogs the Castle content is built on: 2300, 5021, 5020,
2574, 2575, 2577, 2581, 5003, 5004, 5008, 5009 (all covered by the ledger's
inherited hard rule "never add a button"), plus 2299, 4001, 5022, 3999 and 5023
once DU-02a strips their buttons. For every one of those, the actions its chain
runs are exactly the actions a deliberate close runs — closing the window IS the
intended advance under F8. Today that close is rejected if anything else
displayed a dialog in between, and the player is silently stuck. After this
change it fires, once.

Worked example. A player reads Copplemann's 2574 (zero-button, keyed by chain
1232, which advances 701 to step 2400), leaves the window open, and right-clicks
Gerschon. Chain 1202 displays 2573; the client discards 2574 and sends
`(2574, -1)`. Today that is rejected and the player must re-interact with
Copplemann to progress. After this change chain 1232 fires once, 2574 leaves the
set, and 2573 is still independently answerable.

2573, 5861 and 2576 are the exception in the other direction: they carry buttons
today and keep one on their final screen after DU-02b, so the client sends
nothing when they are evicted. They stay in the offered set until the player
answers them or the session ends.

### 7.4 The one pair that co-fires by design

Chains 1161 and 1172 both trigger on `mission_completed 686` with no conditions
and are deliberately staggered (`castle_cellblock_chains.sql:2292`, delay
10100 ms; `:2454`, delay 10600 ms). 5859 evicts 2516 500 ms later, by design.

- Today both carry an Accept button, so the eviction sends nothing.
- After DU-02a strips both (Target Matrix rows 2516 and 5859), the eviction
  sends `(2516, -1)`. That is now accepted. 2516 keys no chain, so nothing runs;
  the only visible difference is that the rejection `warn!` stops firing.

This is the only place in the four files where the server displays two dialogs
to one player from one event. Everywhere else the same-trigger display chains
are mutually exclusive: 1051/1052, 1056/1057, 1098/1099, 1202/1203 and 1352/1354
split on `archetype eq 8` versus `neq 8`; 1231/1233/1236, 1299/1294, 1342/1344
and 1322/1344 split on `step_status`; 1051/1052 versus 1171 split because
`mission_status 641 eq not_active` is false once 641 is completed
(`mission_context.rs:104-108` maps a completed mission to `completed`, not
`not_active`).

## 11. Known gaps

- **The window widens in time, and that is intentional.** A dialog WITH buttons
  that is evicted sends nothing, so its id stays offered until eight more
  displays push it out or the session ends. The player can answer it later, out
  of context. The enforcer judged this not exploitable in shipped content; the
  residual risk is future content that satisfies its three-way conjunction, and
  integration item 4 is the mitigation.
- **No client UAT.** Nothing here was exercised against the real client. The
  eviction behaviour is Ghidra-derived (high confidence, Q5) but the end-to-end
  "close A after B opened, watch A's chain fire" path is unproven in-game. It
  belongs in DU-UAT, most cheaply as the 2574-then-Gerschon sequence in 7.3.
- **The bookmark schema changed.** `.bug` telemetry now emits
  `offered_dialog_ids` (a list) instead of `open_dialog_id` (a scalar). A saved
  SigNoz query filtering on the old key stops matching.
- **`button_id` is still unvalidated**, unchanged and by design (CAT-J-01's
  "Not Filed" note): `OnDialogChoice` matches on dialog id only until DU-06
  lands the `button_id` condition.

## Evidence

### The text catalogue IS reachable from the cell executor - no fallback needed

The packet allowed an explicit `"text"` param fallback if the executor could not reach
`dialog_screens` text without a disproportionate refactor. It can, and the fallback is **not**
shipped.

- The cell already queries `resources.dialog_screens` at startup:
  `crates/services/src/cell/spawner/dialogs.rs:104` (`load_monologue_dialog_ids`), wired at
  `crates/services/src/cell/service/startup.rs:105`.
- `SpaceManager` already carries about twenty such startup caches
  (`crates/services/src/cell/space_manager/mod.rs:127-200`), and the executor gets `&SpaceManager`
  on every action.
- So the addition is one loader (`load_dialog_screen_text`), one field
  (`SpaceManager::dialog_screen_text`), one re-export and one startup block - the same four edits
  every other cache needed.

Sizing: the seed has **13,467** `dialog_screens` rows and `screen_id` is **globally unique across
all of them** (verified by counting the seed file: 13,467 rows, 13,467 distinct `screen_id`), so
the cache is a flat `screen_id` to `text` map rather than keyed on `(dialog_id, screen_id)`.
`text` is `NOT NULL` (`db/resources/Dialogs/Tables/dialog_screens.sql:9`). A future duplicate
`screen_id` would make bark text resolution order-dependent, so the loader counts duplicates and
warns rather than silently taking last-wins.

### Bark lines confirmed present in the seed

`db/resources/Dialogs/Seed/dialog_screens.sql:21706-21712` - dialog 5019 screens 96351-96354,
all `speaker_id = 0`, which is why `speaker` is an explicit param. The chain-replay guard asserts
screen 96351 still reads `Let's move out!`, so a seed edit to that row cannot silently change
what a player hears through a bark row that names only the id.

### `CHAN_say = 0` is unambiguous

`entities/defs/enumerations.xml:116` and `crates/services/src/cell/chat.rs:18` agree. See
"Out-of-scope findings" for the channels that do **not** agree.

## Design decisions

1. **Reuse the chat serializer, do not copy it.** `cell::chat::serialize_on_player_communication`
   went from private to `pub(crate)`; `executor/bark.rs` calls it. There are already three copies
   of this twelve-line serializer in the tree (`chat.rs`, `cell_methods/gm/feedback.rs`, and an
   inline build in `console/net.rs`); a fourth was not acceptable for the one route the campaign
   depends on. Consolidating the existing three is out of packet scope.
2. **`method_idx::ON_PLAYER_COMMUNICATION`, not `chat.rs`'s local copy.** `chat.rs:49` declares a
   private duplicate of the constant. The new module uses the canonical
   `crate::mercury::method_idx` one, as `cell_methods/gm/feedback.rs` does.
3. **Loader rejects, never defaults through.** All three params drop the row with a `warn!` on a
   bad value. The reasoning is in the module doc of `action_bark.rs`: the failure modes are not
   "no line" but "a visibly wrong line" - a blank `speaker` renders as the client's empty-name
   prefix (the `[] says` garbling that got `system_message` disconnected from method 28), and a
   channel the client never registered pops its red unknown-channel splash.
4. **`channel` accepts only `"say"`, case-insensitively, defaulting to `say`.** `CHAN_splash` is
   rejected at load per the packet: its native trigger was never traced.
5. **`speaker` is trimmed.** A trailing space in a seed row would otherwise reach the chat window.
6. **The `npc_bark` loader arm lives in a sibling module.** `loader/action.rs` was already at 495
   lines against a 500 soft cap; inlining the three warn blocks put it at 573. The arm is now one
   line delegating to `loader/action_bark.rs`, mirroring the existing `loader/action_spawn.rs`
   seam. `action.rs` ends at 500 lines, `action_bark.rs` at 110.
7. **`executor/mod.rs` gains twelve lines**, from 665 to 677 - one `mod bark;`, one module-doc
   bullet, and a four-line arm delegating to `bark::npc_bark`. Still under the 700 hard cap, but
   the file is close enough that the next packet touching it should split rather than append.
8. **Triggering player only.** One `EntityMethodCall`, no witness fan-out and no sender echo. A
   bark is per-player mission feedback; the say-chat path would speak one player's escort line
   into a stranger's chat window in a shared world. The chain-replay guard stages a second player
   in the firing player's witness set specifically to catch a regression to that path.
9. **Three executor refusals, each with a stable `reason`** per the negative-logging convention:
   `screen_not_cached`, `empty_text`, `actor_not_player`. All three send nothing. The third is the
   same shape as `spawn_entity`'s refusal of a non-player actor, and it matters because method 28
   addressed to an NPC resolves to no client address.
10. **A new `player_journal` kind `bark`,** distinct from `dialog`. A `.bug` report that lumped
    the two together could not tell "the player was interrupted by a window" from "the player was
    told something while they kept moving" - which is the entire point of this packet.
11. **`SystemMessage` untouched**, per the packet.

## Seed syntax for DU-07

One `content_actions` row per line. `target_id` and `target_key` are both NULL.

```sql
-- NEW CONTENT: Col. Marsh escort bark. The line is dialog 5019 screen 96351
-- (ORIGINAL_DATA), resolved server-side from resources.dialog_screens -- do
-- not retype the text into the row.
INSERT INTO content_actions
  (chain_id, action_type, target_id, target_key, params, delay_ms, sort_order)
VALUES
  (<chain_id>, 'npc_bark', NULL, NULL,
   '{"screen_id": 96351, "speaker": "Col. Marsh", "channel": "say"}'::jsonb, 0, 0);
```

The four usable 5019 screens:

| `screen_id` | Line |
|---:|---|
| 96351 | Let's move out! |
| 96352 | I'll draw their fire! Take a flanking position behind that table. |
| 96353 | Crouch down when you're in cover! |
| 96354 | Flank their position while I draw their fire! |

Notes for the author:

- `"channel": "say"` may be omitted; it is the default. Any other value **drops the row at load**.
- `"speaker"` is mandatory and must be non-blank. These screens carry `speaker_id = 0`, so the
  server cannot recover the name.
- The chain must be triggered by something a **player** does. A chain whose acting entity is an
  NPC (an `entity_dead_tag` chain, say) refuses the bark with `reason = "actor_not_player"`.
- "Each line once per mission run" is the packet's own requirement and is **not** enforced by the
  action. Use `content_triggers.once` or a mission-step gate, as any other one-shot chain does.
- Barks are neither persisted nor replayed. A relog after a bark fired simply does not re-speak
  it, which is the DU-07 acceptance shape.

## Known gaps

- **No seed rows ship.** Per the packet, DU-07 authors the first ones. The verb therefore has
  zero seed rows and its only coverage is the sentinel chain in
  `chain_replay_tests/npc_bark.rs`, exactly as `grant_xp` did.
- **UAT is owed** (ledger DU-03 row): the line appears in the chat window as Marsh while the
  player keeps moving and firing, and no window opens. Nothing in this packet has been seen in
  the client.
- **The splash route stays unimplemented**, per the packet. If DU-00 or a later RE pass traces
  `Event_UI_SplashMessageReceived`, the loader's channel match is the single place to widen.
- **The startup cache costs roughly 1.3 MB per cell** (13,467 strings). That is acceptable next
  to `dialog_set_maps`, but a cell that never fires a bark still pays it. Narrowing it would mean
  the cell knowing which screens content references, which it cannot without reading
  `content_actions`; not worth the coupling today.

## Out-of-scope findings

1. **`cell/chat.rs` channel constants diverge from `entities/defs/enumerations.xml` for every
   channel at or above 7.** The `.def` says `CHAN_server = 8`, `CHAN_feedback = 9`,
   `CHAN_tell = 10`, `CHAN_splash = 11`; `chat.rs:32-43` says `CHAN_SERVER = 7`,
   `CHAN_FEEDBACK = 9`, `CHAN_TELL = 9`, `CHAN_SPLASH = 10`. Ledger fact F12 also puts
   `CHAN_splash` at 11, matching the `.def` and not `chat.rs`. The GM-feedback value of 9 is
   deliberate and documented at `gm_feedback.rs:14-22` - the client registers a different set
   than the `.def` declares - but `CHAN_SPLASH = 10` in `chat.rs` looks like a plain off-by-one
   against canon, and it is dead code today with no reader. It matters to whoever eventually
   verifies the splash route. Nothing in DU-03 depends on any of them: `CHAN_say = 0` is the one
   value both sources agree on.
2. **The method-28 serializer exists three times** (see design decision 1). Consolidating onto one
   `pub(crate)` builder is a clean, test-covered refactor for whoever next touches that area.

## 1. The bandolier model and reload refill

| ID | Finding | Evidence |
|---|---|---|
| A-01 | Per-slot ammo lives in `CellEntity::bandolier_items: HashMap<i32, BandolierItem>`, mirrored to `Stat[AMMO_SLOT_1+slot]` (49-53) for the client UI. `BandolierItem` is canonical; both are written only through `set_slot_ammo()`. | `docs/gameplay/weapon-ammo-reload.md` §"Per-slot ammo storage"; `crates/entity/src/cell_entity/bandolier.rs` |
| A-02 | `requestReload` (cell method, wire opcode `0x56`) pins the active slot (`reload_slot_id`), starts a warmup timer, and the 100 ms `reload_completion_tick` refills the pinned slot to `clip_size` **from nothing** — no reserve read, no stack decrement — when the warmup elapses. | `crates/cell/src/cell/service/ticks/reload_completion.rs:24`; `crates/cell-combat/src/cell/cell_methods/player/world/reload.rs` (284 lines) |
| A-03 | Legacy `Reload.py` also refilled with `setCurrent(max)` — the free-refill behavior is not a Cimmeria regression, it is what the reference implementation did too. AM-02 is new restoration work, not a bug fix. | `deprecated/python/cell/effects/Reload.py`; `docs/gameplay/weapon-ammo-reload.md` §"Reload timing" |
| A-04 | Ammo persistence is batched (`bandolier_ammo_dirty: HashSet<i32>`), draining at reload completion, active-slot swap, ammo-type change, disconnect, logout and world transition, via one `CellToBaseMsg::BandolierAmmoUpdate` per dirty slot. A reserve draw/return needs its own base round trip on the same cadence points, or a mid-magazine crash could lose reserve rounds that were already decremented but never persisted the other way. | `docs/gameplay/weapon-ammo-reload.md` §"Persistence cadence"; `crates/cell-combat/src/cell/cell_methods/inventory/bandolier/active_slot.rs:19` (`flush_dirty_bandolier_ammo`) |
| A-05 | The active-slot swap flushes the **previous** slot if dirty (mid-magazine swap case) before changing `active_bandolier_slot`. AM-02's switch-return (D-AM05: unfired special rounds return to the bag stack on ammo-type change, not on slot swap) is a **different** event than this existing flush — do not conflate them. Switch-return fires from `requestAmmoChange`, not `requestActiveSlotChange`. | `crates/cell-combat/src/cell/cell_methods/inventory/bandolier/active_slot.rs:81-571`; `docs/gameplay/weapon-ammo-reload.md` §"Active slot swap" |

## 7. Cooked item-data push

| ID | Finding | Evidence |
|---|---|---|
| A-19 | The only existing mechanism that changes what the client sees for an item id is `crates/resources/src/base/item_overrides.rs`: it **patches an existing `_<itemId>` `<COOKED_ITEM>` entry's attributes** (icon, `MaxStackSize`) in memory at server startup, then leans on `versionInfoRequest → onVersionInfo(InvalidKeys=[...]) → resourceFragment(_key, patched XML)` to push the patch. | `crates/resources/src/base/item_overrides.rs:1-70`; the Slappack (item 2893/#405) precedent inside it patches an id that already existed in the 2009 cooked PAK |
| A-20 | **Resolved by AM-01, MEDIUM-HIGH confidence, not proven.** The cooked-data element fetch (`versionInfoRequest → onVersionInfo → InvalidKeys → elementDataRequest → resourceFragment`) reads elements by a numeric key with **no static id-range check** — the key is a `long` end-to-end and the client's local ZIP cache entry name is built by plain decimal-digit streaming, not a bounds-checked table index. This is the same mechanism (same `ServerSource<N>` template) already confirmed for the category-5 dialog-override crash finding, corroborating it across two categories. PR #405 is the only *proven* case, and it patched **existing** ids (2893/4735); nobody has verified a genuinely new key end-to-end. **Architecturally the client should accept a fragment for a key it never had, materializing a new cache entry — but AM-01 recommends validating this with a real spike before depending on it structurally.** | `docs/reverse-engineering/findings/ammo-system.md` §Q4; `docs/reverse-engineering/findings/cooked-data-pipeline.md` Findings 4/6/7; `docs/reverse-engineering/findings/cooked-dialog-override-crash.md` |
| A-21 | The `InvItem` wire payload (`crates/entity/src/inventory.rs:105-131`) carries only instance state (`id, dbid, stackSize, slotID, containerID, isBound, durability, ammoTypes, curAmmoType, charges`) — no name, icon, or stack cap. The client resolves those purely from its own cooked catalogue keyed by `dbid`. This is why AM-07's spike matters even though A-20 leans favorable: a new item id with no cooked entry at all has nothing to render from until the spike proves the fragment materializes a usable entry. | `crates/entity/src/inventory.rs:105-131`; `item_overrides.rs`'s own doc comment |
| A-22 | **Resolved: widening a weapon's `ammo_types` needs no client push at all.** `getAmmoTypes`, `getCurrentAmmoType` and `requestAmmoChange` all resolve through the identical live, server-populated pointer chain `SGWPlayer+0x8c → +0x24` (four independently-decompiled native functions converge on it: `FUN_00add4a0`, `FUN_00ad8ee0`, `FUN_00ad8f10`, and `FUN_00ad8ad0` from a separate prior finding) — not `CookedDataItems.pak`. AM-F's `ammo_weapon_widening.sql` `UPDATE` is a pure DB/server-side change; AM-07's client push scope narrows to **only the 15 new ammo item definitions**, never the widened weapons. This directly de-risks acceptance criterion 1 and the TODO this audit's §2 already covers. | `docs/reverse-engineering/findings/ammo-system.md` §Q2 (HIGH confidence on the live-cache source; MEDIUM on the exact lookup key, not load-bearing here) |

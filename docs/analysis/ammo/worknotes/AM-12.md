## Changes from the brief

1. **An unrecognised flag value turns the flag off,** not "falls back to the default". With the default now on, falling back to it would leave the feature on when an operator mistypes the rollback lever (`=of`). Unset is on; `0`/`false`/`off`/`no` is off; anything else is off with the `feature_flag_invalid` WARN.
2. **Nine pre-campaign tests assumed the flag off.** Their fixtures loaded ammo type 2, which has been `Bullet_Armor_Piercing` since AM-F, so with the flag on a reload took AM-02's draw path. The reload, holster and bandolier-sync fixtures now load `Bullet_Default` (1): the tests are about reload timing, not ammo. The two AM-03 dispatcher tests that pin `requestAmmoChange`'s message shape set the flag off explicitly, because with it on a default clip switched to a special type is emptied first (AM-02's `switch_return_tests` pin that).
3. **`ammo_loot_dropped` fires when the grant is sent,** not when it commits. The cell knows the ammo type and the corpse; the base knows the commit. A refused grant (bags full) logs the `inventory` target's `loot_restored` and puts the rounds back on the corpse, so a SigNoz reader pairs the two. The row carries `quantity` (rounds), `ammo_label`, `corpse_id`, `corpse_template_id` and `loot_table_id` beside the correlators.
4. **The catalog names every `ammo` event, not only the contract rows.** `catalog_covers_every_ammo_event_in_the_workspace` reads the workspace sources for `target: "ammo"` and fails on an event the catalog does not list, so the next packet cannot drift the way Wave 1 and Wave 2 did (14 AM-02 events, 3 AM-11d events and 3 others were missing).

**Exempt, with the reason** (the Bank campaign's "Known gaps" pattern):

- `feature_flag`, `feature_flag_invalid` (AM-F): startup only, once per process, no player. `cimmeria-entity` has no `cimmeria-test-support` dev-dependency; the resolution the rows report is pinned by `ammo_feature::tests` (`default_is_on`, `zero_is_the_rollback_lever`, `unparseable_value_falls_back_to_off_and_is_flagged`).
- `catalog_loaded`, `catalog_load_failed` (AM-F): cell startup only; a guard needs a database (or a broken pool) at startup. The loader is pinned by `live_db_ammo_catalog::load_ammo_catalog_reads_both_tables`.
- `gm_give_ammo` on the base (INFO granted; WARN `session_mismatch`, `bags_full`, `no_reserve_item`; ERROR `db_error`) (AM-06): the grant's arithmetic and the answer lines are pinned by `live_db_am06_giveammo_*` and `ammo_gm_give::tests`, not by a log row.
- The send-failure rows `reserve_request_send_failed`, `reserve_answer_send_failed`, `feedback_send_failed`, `ammo_feedback_send_failed`, `ammo_support_feedback_send_failed`: they fire only on a closed channel between cell and base (shutdown), which no test in these crates injects.
- The race rows `reload_drawn_stale`, `switch_returned_stale` (`entity_gone`, `slot_changed`), `reload_draw_clip_mismatch`, `switch_return_clip_mismatch` and `ammo_switch_dropped` (AM-02): the behaviour they report is pinned without a log row (`answer_after_a_slot_swap_still_loads_the_rounds`, the duplicated and concurrent draw live-DB tests, `special_clip_defers_and_asks_for_the_return`'s second switch).

**Revert proof.** Setting `FINITE_SPECIAL_DEFAULT` back to `false` fails `default_is_on`. Removing the `log_ammo_loot` call fails `looting_special_ammo_logs_ammo_loot_dropped`. The four other new log guards assert rows that existed before this PR, so each fails if its event is renamed or its level changes; they were written against the emitting code and pass on it. Removing a name from `ALL_EVENTS` fails the sweep.

**Checks run locally** (through the build lane; workspace-wide runs left to CI because of the disk limit): `cargo nextest run` on `cimmeria-entity`, `-cell-interactions`, `-cell-combat`, `-cell-world`, `-cell-console`, `-cell-methods`, `-cell`, `-cell-content`, `-cell-pets` and `-base-methods` (all pass after the fixture changes; before them, the nine flag-off tests above failed, which is how they were found); `cargo clippy --all-targets -- -D warnings` on the six changed crates; `cargo fmt --all -- --check`. Live-DB tests were not run locally; CI's `test-live-db` covers them.

## Things I could not reconcile

- **`ammo_loot_dropped`'s catalog fields.** AM-F's contract row says `loot_table_id`, `quantity`; the brief asked for "ammo type, rounds and corpse". The row carries all of them. `loot_table_id` is the corpse's template table, which for a live container (the debug crate) is still table 3.
- **Whether a support dart at yourself is reachable.** The server path is tested; whether the client lets you select your own entity is not (AMMO-18 notes it).
- **The flag's default and nextest.** Tests that call `set_finite_special(false)` rely on nextest's one-process-per-test model, as the module docs say; under a plain `cargo test` the two AM-03 dispatcher tests can race a test that sets it on. CI runs nextest.

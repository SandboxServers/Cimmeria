## What shipped

`crates/resources/src/base/item_overrides.rs` became a directory:

| File | What |
|---|---|
| `item_overrides/mod.rs` | The Slappack patcher, unchanged, plus `ITEM_ADDITIONS` (= `AMMO_ITEMS`) and the re-exports |
| `item_overrides/new_items.rs` | `NewItem` and `generate_item_xml`: a whole `COOKED_ITEM` for an id the PAK does not ship |
| `item_overrides/ammo_items.rs` | The 15 definitions |
| `item_overrides/new_items_tests.rs` | Byte-exact, served-category and seed-agreement guards |

Outside the owned file, three small edits were unavoidable. None is in another ammo packet's ownership:

- `resources/apply_overrides.rs`: `apply_item_overrides` inserts each addition after the patches, skipping (with `reason = "id_ships_in_pak"`) any id the PAK already ships.
- `resources/metadata_bump.rs`: `compute_item_metadata_bump` takes the additions too and hashes every field.
- `resources/tests/overrides.rs`: the new signature, the longer overridden-id list, and two new guards.

### What each item carries

| Field | Value | Source |
|---|---|---|

| `IconLocation` | `set:AmmoType_Icons image:<EAmmoType label>`, for example `image:Bullet_Hollow_Point` | the client's own ammo imageset, declared in `TaharezLook.scheme` and used by `Bandolier.lua` / `WeaponBar.lua`; its image names are exactly the `EAmmoType` labels |
| `MaxStackSize` | 500 | seed |
| `ContainerSet` | 1, 15, 17 | seed |
| `IsSellable` / `IsDeletable` | true / true | seed flags 3072 |
| `TechComp` | 1 | seed |
| `Description` | "Special ammunition. Select Hollow Point in a compatible weapon's ammo menu to fire these rounds." (darts: "... these darts.") | written for the tooltip; cooked-only, the server never sends `resources.items.description`. It says how to use the item, not what it does, because the effects land in AM-04 and later |

### How the client gets them

Since #840 a `CookedDataItems` version mismatch resyncs the whole category (`InvalidateAll=1`, every entry, the real version last). The additions change the category's metadata bump, so every client that holds the shipped PAK, or the version the Slappack override produced, gets one full items resync on its next connect, and the resync carries 9000-9014. A client that asks for one of those keys directly (`elementDataRequest`) is served the generated bytes from the same cache. No new wire code: the version and fragment path are unchanged.

The ids are genuinely new keys. The shipped PAK stops at 8951, so nothing is shadowed, and 9000-9014 are well under the 65535 bound that the dialog-override crash set.

## Deviation: no toggle

The instructions said to ship behind whatever toggle the plan specifies. The plan specifies none for AM-07. Its only flag, `ammo.finite_special`, gates the reserve **draw** (AM-02) and nothing else. Gating the definitions on it would be wrong: AM-05 loot and AM-06 grants (and `/gmgiveitem` today) hand out 9000-9014 while the flag is off, and without the definitions those stacks show the missing-icon square and no name.

The definitions are inert on their own. Nothing grants the items unless a GM or a later packet does. The kill switch is the table: making `ITEM_ADDITIONS` an empty slice withdraws them in one line. The next resync then evicts them, because `InvalidateAll=1` empties the category before refilling it. Before #840 a removed override lingered in the client's disk cache.

- With the prologue `\n` dropped, both byte-exact guards failed.

## UAT (the spike)

Needs a GM account, a client that has connected to this server before (so it holds an older `CookedDataItems`), and a server built from this branch. Nothing else: `/gmgiveitem` already grants by id, so AM-06 is not needed.

1. Start the server. In the server log, confirm 15 lines `Added Cimmeria item definition` (item_id 9000-9014) and one `Cimmeria item overrides applied; metadata bumped` with `count = 17`.
2. Log in to a character and enter the world. The client resyncs the items category. There is no visible sign, and it should not stall world entry.
3. **Spike item.** Type `/gmgiveitem 9001 1`. Check that:
   - (a) a new stack appears in the main bag;
   - (b) its icon is the Hollow Point ammo icon, the same one the weapon bar shows for Hollow Point, not the missing-icon square;
   - (c) hovering it shows the name "Hollow Point Rounds" and the description text above.
4. **Stack cap.** Type `/gmgiveitem 9001 600`. The bag should hold one stack of 500 and one of 101: the client and the server agree on the cap of 500.
5. **Relog.** Log out and back in. The stacks keep their icon and name; the client now holds the new version and must not resync again.
6. **Batch.** Give one of each of the other 14 (`/gmgiveitem 9000 1`, then 9002 through 9014). Each should show its own icon (Armor Piercing, Incendiary, EMP, Explosive, then the ten dart icons) and its own name.
7. Optional: move a stack into the personal vault (container 17) and back, then delete one stack. Both are allowed.

Record the result here: pass, or which step failed and what the client showed (a screenshot of the bag and tooltip, and the SigNoz `versionInfoRequest` / `Pushing` lines for the session).

## Contingency if the spike fails

**Failure looks like** one of these, on the first login after the push:

- the stack shows the missing-icon square with no name;
- the tooltip is empty;
- the client never fetches the keys, which SigNoz shows as no fragment pushed for 9000-9014.

The plan's fallback (work-packets.md, AM-07 step 3) is to repurpose existing, already-cooked item ids instead of the reserved block:

1. Pick 15 ids that ship in `CookedDataItems.pak` and that nothing uses. An id qualifies if no loot table, vendor, mission, crafting recipe or character template names it, and no player holds it (`sgw_inventory`). The shipped PAK has 6059 entries, 1-8951.
2. Re-seed `ammo_items.sql` and `ammo_item_types.sql` (AM-F's files; coordinate the edit) to point the 15 ammo types at those ids. No other packet changes, because AM-02 to AM-06 go through `ammo_item_types`.
3. Here, move the 15 entries from `ITEM_ADDITIONS` to a replace path. For shipped ids the generator's output replaces the entry whole, with the same `NewItem` data, instead of being skipped. That is the Slappack mechanism (patching a key the client already has), which is proven in production. The per-attribute `ItemOverride` patcher only rewrites the icon and the stack cap, so it cannot rename an item. Generating the whole entry is simpler than growing the patcher. `additions_are_new_unique_16_bit_keys` has to flip for those ids, deliberately.

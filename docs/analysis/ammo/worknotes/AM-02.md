## Contract

- **Packet:** AM-02, the reserve. D-AM05 (rounds, never punish), D-AM09 (infinite ammo frees the draw only).
- **Gate:** everything below runs only with `ammo.finite_special` on (`CIMMERIA_AMMO_FINITE_SPECIAL`). With it off, reload and the ammo switch behave exactly as on `main` before the campaign.

## Design

The cell owns the clip and the base owns the bag stacks, so each reserve operation is one cell-to-base round trip and **one base transaction that moves rounds between the stacks and the weapon row**. No round is ever in both places or in neither.

| Step | Where |
|---|---|
| Wire: `CellToBaseMsg::AmmoReserve(AmmoReserveRequest)`, `BaseToCellMsg::AmmoReserve(AmmoReserveAnswer)` | `crates/wire/src/cell/messages/ammo_reserve.rs` |
| Reload gate, draw request, draw answer, completion refill target | `crates/cell-combat/.../player/world/reload_reserve.rs` |
| Warmup start split out of `handle_reload` (`start_reload_warmup`, `handle_reload_with(finite)`) | `.../player/world/reload.rs` |
| Switch return: `begin_switch_return` (the AM-03 hook) and its answer | `crates/cell-combat/.../bandolier/switch_return.rs` |
| Base transactions: `commit_reload_draw`, `commit_switch_return` | `crates/base-methods/.../inventory/ammo_reserve/commits.rs` |
| Base shell: client bag updates, catalog events, answer | `.../ammo_reserve/requests.rs` |

**Reload draw.** With a special type in the active slot (and infinite ammo off), a reload flushes the slot's clip (`BandolierAmmoUpdate`), then sends `ReloadDraw`. The base takes the inventory advisory locks (bags 1, 3, 15), locks the weapon row, counts `clip_size - row.ammo` from **the row, not the cell's number**, draws through `ammo_reserve::draw`, and writes `ammo = row.ammo + drawn` in the same commit. The answer loads the rounds into the clip and only then starts the ordinary warmup. The completion tick then leaves that clip as it is (`completion_target`, matched on the warmup deadline) instead of refilling to `clip_size`.

- Loading at commit time, not at warmup end, is the "never punish" guarantee: a slot swap, death or a second press that cancels the warmup cannot lose rounds that already left the bags.
- An empty reserve refuses before any warmup: `onErrorCode(Ability, 596, 61)` (`CONDITION_FEEDBACK_AmmoCountLessThan`, the legacy insufficient-ammo code) plus a feedback line (`You have no Hollow Point rounds left.`). The clip is untouched.
- A second press while a request is in flight is ignored (`ReloadGate::Blocked`, 5 s timeout). Independently, the base counts from the locked row, so a duplicated request finds a full clip and draws nothing.

**Switch return.** `requestAmmoChange` calls `begin_switch_return` after validation. A special clip with rounds left returns `Deferred`. The cell flushes the slot, sends `SwitchReturn`, and empties the clip (rounds in transit, so none can be fired). The base returns the row's rounds through `return_rounds` and settles the row in the same commit:

- Everything fits → the row holds 0 rounds of the new type. The cell finishes the switch.
- Bags full → the `remainder` stays in the row **as the old type** and the switch does not happen. The feedback line reads "Your bags are full: 7 Hollow Point rounds stay loaded. Make room and switch again." The next switch attempt returns them. Nothing is deleted or relabelled.
- A duplicated request finds the row already on the new type and moves nothing.

A default clip switched to a special type is emptied (`ammo_switch_default_emptied`): default rounds are free (D-AM02), and keeping them would fire a free special clip.

**Infinite ammo** (`cimmeria_entity::ammo_infinite::is_on`, AM-06) makes the reload gate `Free`: no draw, but the clip still empties and still reloads to full.

## Changes from the plan

1. The draw happens **before** the warmup, and the rounds load when the draw commits. The completion tick does not add rounds for a special reload. The plan had the tick refill to `current + drawn`, but a tick-time refill loses the drawn rounds whenever the warmup is cancelled.
2. The bags-full remainder keeps its **old type** and the switch is refused (approved by the coordinator, 2026-09-28). There is no separate "pending in the weapon" store, and no DB column was needed.
3. New telemetry names beyond the catalog, all on target `ammo`, for the coordinator to add to the table: `reload_draw_requested`, `reload_drawn_loaded`, `reload_drawn_stale`, `reload_refused_feedback`, `ammo_switch_return_requested`, `ammo_switch_refused` (`reason=bags_full`, or a refusal reason), `ammo_switch_default_emptied`, `ammo_switch_dropped`, `switch_returned_stale`, `reserve_request_send_failed`, `reserve_answer_send_failed`, `feedback_send_failed`, `reload_draw_clip_mismatch`, `switch_return_clip_mismatch`. The new refusal reasons are `weapon_changed` and `db_error` (`ReserveRefusal::reason`). Spans: `ammo.reserve_request`, `ammo.reload_draw`, `ammo.reload_drawn`, `ammo.switch_return`, `ammo.switch_returned`.

## Dispatch rule and budget

**Worktree base correction:** `mk-worktree.ps1` creates every packet branch at `origin/main`. Before dispatch, move the clean new branch to the recorded Castle feature SHA and verify HEAD and merge-base exactly as [the shared execution contract](execution-contract.md) requires; repeat for every wave. The optional Cellblock evidence story's Castle recipient/turn-in belongs to CB-N05b on the **Cellblock** feature branch, which must ship its full quest before Castle consumes it. Castle packets do not add a duplicate recipient action.

Each implementation packet is designed for **50–60k net coder working tokens** and **under 100k billed tokens for the whole packet across coder, reviews and fixes**. The coordinator tracks actual billed use and re-scopes before the cap; review quality still requires up to three fresh rounds. Give a fresh Haiku-tier `packet-coder` only this document's common contract, that packet's section, its frozen evidence/ID table and the named source excerpts. Do not load all four zone dossiers, all campaign ledgers or full transcripts into the worker context. If the expected coder work exceeds 60k net, split on an independently testable boundary before dispatch. Archaeology, design, ambiguous client behavior and closeout go to named specialists, not Haiku. A worker edits only the frozen allowlist, commits once, reports the commit and test evidence, then exits. Review fixes go to a **fresh** fixer, never back to the implementer.

The campaign coordinator creates `content/castle-campaign` as an integration branch from current `origin/main` after reconciling active branches and old packet status. For packet `CS-XX`, use branch `castle/cs-xx-<slug>`, a distinct worktree `.claude/worktrees/castle-cs-xx`, and its own `sgw_castle_cs_xx` test database (the exact name produced by `mk-worktree.ps1` controls). Use `pwsh tools/build-lane/mk-worktree.ps1 <branch> <worktree-name>` from the main checkout. Packet branches start from the current campaign feature-branch tip or a documented dependency packet; one implementer per worktree. After packet review and tests, integrate its commit into the **local campaign feature branch**, record the merge SHA in the ledger, and retire its worktree. Do not open a packet PR. At each wave boundary, run local CI-equivalent checks on the feature branch, obtain a fresh adversarial review of the cumulative wave diff, send all verified findings to a new fixer agent, then to a fresh reviewer. Repeat for **up to three review rounds or until a round has no issues**. If findings remain after round three, hold the wave and redesign/split rather than calling it reviewed. Repeat the same gate on the entire cumulative campaign at the end. Only after all packets, local CI, and the final three-round review gate pass may the coordinator open one remote campaign PR. Merge that PR to `main` after remote CI/review passes. The remote PR is the campaign's sole integration PR.

This feature-branch integration sequence is the owner's campaign policy for this effort; it supersedes the older `campaign-packet` skill's per-packet PR default. Follow the skill's one-worktree, one-worker, adversarial review, test and ledger rules otherwise. The coordinator owns conflict resolution and may not silently combine two workers' seed edits. No campaign starts during this planning PR.

Before any worktree or dispatch, check `git worktree list`, recent campaign branches and the agent board to avoid a duplicate campaign. Read `CLAUDE.md`, `docs/agents/rules-and-gotchas.md`, `docs/agents/domain.md`, `docs/agents/development-workflow.md`, `TESTING.md`, `tools/README.md`, `crates/README.md`, and this ledger. Use the `seed-change`, `lane-build`, `re-lookup` and `lab-uat` skills where their triggers apply. The lab requires the owner's explicit yes before lease, client/server start or server switch.

1. Copy the packet's allowlist and the frozen rows from CS-00 into its worktree.
